## 0. 企业环境设定（模拟公司：以设定倒推全部技术决策）

**业务背景**：「NewMall 商城」中型电商平台（对标素材中 vivo/京东到家的体量起步，向字节/美团的目标演进）。

| 维度 | 设定 | 来源依据 |
|---|---|---|
| 用户规模 | 注册用户 2000 万，DAU 200 万 | vivo 商城量级 |
| 券规模 | 日发券 500 万，存量用户券 10 亿级 | 京东到家实测数字 |
| 峰值场景 | 大促 0 点开抢：单批次 10 万张券、瞬时 5000 QPS 领券 | 阶段目标（docs/00） |
| SLA | 核心链路（领券/核销）可用性 99.95%，P99 < 200ms | 大厂通用基线 |
| 资损红线 | 超发=0（DB 条件更新保证）、总限领=0（uk_user_seq 唯一索引保证）、一券多用=0；日限=Redis 计数概率性保证（failover 丢计数敞口=丢失数，收窄手段已落地 A2：docker/redis/redis.conf=noeviction+AOF everysec【审查-A2，2026-09-16】；M4 哨兵时启用主从写安全参数；M2 补日键探测器使敞口可度量【审查-B4】） | 券=钱 |
| 团队设定 | 产品/架构/后端/测试/SRE 五角色（你我分饰，工件见 §3） | 模拟多部门协作 |
| 基础设施 | 自建机房模拟（Docker）：MySQL 主从、Redis 哨兵、RocketMQ、Prometheus/Grafana | 全部本地容器化 |

**决策总原则**：每个技术组件的引入必须由上面某个数字或红线触发——没有对应痛点的技术是负资产（阿里规约：禁止超前设计）。

## 0.5 对账分级发现 SLA（2026-09-16 用户裁定"对账按大厂标准"后立项【审查-§3草案】）

对账从"一套巡检"升级为**三档速度**，每档独立载体、独立验收（资损注入演练+MTTD 度量，不是"对上了就行"）：

| 档 | 对象 | 发现时效 | 载体 | 落点 |
|---|---|---|---|---|
| 资金核心 | 恒等式/在途/账本互证 | 分钟级 | Redis 原子快照巡检（已有，保持） | ✅ 现状 |
| 资产维度 | 占用单×券状态交叉核对/悬挂 | **小时级**（现状 24h） | 独立 XXL 任务 1h（B3） | M2 |
| 账证旁证 | 事件流水×状态机配对（**独立数据源**，治"同应用写双方账本"的结构性盲区——P0 Bug① 的教训） | 小时级→分钟级演进 | 批次增量核对（D4）→ binlog→MQ 对账 consumer → 流式 | M4 起 |

**架构原则**：①账证分离——旁证核对采集链路独立于业务代码（binlog 消费，不依赖同一应用写双方）；②流水是最高优先级证据（事件表=事务性 outbox，M1-M3 守住"每个状态变迁必落事件"纪律——已基本成立）；③**Flink 流式的触发条件写死**：M5 后若日发>500 万或 1h 档敞口不可接受→上 CDC+Flink 双流 join（规则三句：按 event_no 配对/恒等式累加/超窗报警）；此前不建平台（无痛点技术是负资产）。

  ① RocketMQ 接入：发放事件/outbox、定向发券管线（亿级批量，docs/01 4.7-D+docs/07 §4.6——**v3 修正原错指针 docs/02**）；**异步补偿 attempt-UUID 凭证**（ADR-0006 增补）② **人群包侧（管线另一半）**：audience 表+发放任务明细表+批量撞 uk_user_seq 跳过语义+"建券客群=发券客群"校验【E4】③ **MQ 治理**：outbox vs 事务消息 ADR 收口（三份文档三种口径→一页 ADR 统一）；rocketmq-exporter+lag 告警+消费幂等/重试/死信协议【E5】④ **优惠计算引擎（措辞对齐 docs/05 既有裁决：平行式+互斥组内贪心，明确不做全局最优）+成本分摊落账**：核销事务 INSERT coupon_share_detail（按商品行×承担主体拆分），sum(share)=discount_amt 守恒校验进日审【E2】⑤ **退款冲销链路（前置 ADR 裁决三处文档矛盾）**：refund_no 幂等+占用单第五终态"已冲退"+红字冲销（与分摊同维度）【E3】⑥ **预算管控**：建券与 appendStock 金额上限校验（面额×库存≤预算余量，超限拒发）【E1】⑦ 经营指标：核销请求补 order_amount/pay_amount；核销率/补贴率/ROI 口径；实时大盘（分钟桶消费者，非关键路径可丢可重放）【E6】⑧ 外部对账文件（渠道对账单下载比对）⑨ 领券异步开关（M3 数据若要求）⑩ **模板缓存广播刷新通道**（调研新增 2026-09-17）：L6 本地缓存的"短 TTL 兜底 + MQ 广播立即刷新"双层模式——MQ 到位后补广播通道（阿里云官方同款）
- **技术含量**：预算-活动-批次三层模型、成本分摊与冲销守恒、MQ 可靠投递、批量管线、优惠计算
- **验收**：定向发券 100 万/分钟可暂停可重试且**人群包可导入可复跑、批量撞索引有明确跳过语义**；sum(share)=discount_amt 全量对平；退款冲销后三方账（平台/商家/用户）金额正确；超预算发放被拒；报表口径与事件表对平且含活动维度
- **角色工件**：退款/作废口径 ADR、outbox ADR、分摊明细设计、报表口径文档

### M6 中台化与开放（v3 扩容：变更治理+券码裁决）【审查-F 组】
- **交付**：① biz_id 多租户贯穿 ② HMAC 签名+防重放+**管理面鉴权模型**（操作台账/访问控制——接 M2 冻结标志的解冻口=双人复核）【F3】③ 按上游配额限流 ④ 规则表达式引擎（含定向券人群可见性）⑤ 审批流+交叉审核（L1）⑥ 登录态接入（L12）⑦ 客服工具（查券/补发/作废/解冻，双人复核）⑧ 运营闭环：appendStock（**含预算余额闸**——E1 的最后一公里）与 OFFLINE（L17）⑨ **变更治理三件套**：模板变更审计表（old/new diff+操作人+理由）+影响面查询+动态字段白名单灰度——与 appendStock 同批（引入可变性的同时带上治理）【F2】⑩ **券码体系二选一裁决**（不能继续悬置）：最小版（券码生成复用位段+混淆设计+verifyByCode 复用三段幂等+核销频控）**或** ADR 写死"纯线上形态不做兑换码型券"【F1】⑪ AB 分流最小闭环（user_id 哈希分桶+标签透传+分组对比视图）【F4】
- **技术含量**：多租户隔离、开放安全、变更治理、内控
- **验收**：新业务接入沙箱四类用例准出；**安全用例集全绿**（越权 IDOR/重放/签名失效/管理面未授权 四类清单化用例——验收不再只看结果，工件留档）；模板变更有 diff 留痕且灰度可控；券码方向有 ADR 留痕
- **角色工件**：变更审计设计、券码 ADR、运营后台、**安全用例集（测试）**

### M7 平台化部署：Kubernetes 与 GitOps（应用层上云）
- **前置说明**：刻意排在 M2 之后——M2 用 compose 手工做蓝绿/扩容/健康检查，先体验"K8s 自动化掉的那些繁琐"；M7 再把同一套应用迁上 K8s，每个对象都能对上"我手工干过的活"。
- **交付**：① kind 本地集群（Kubernetes-in-Docker，单节点约2GB内存）② 应用无状态层 K8s 化：Deployment/Service/Ingress/ConfigMap/Secret（消化 L20）+ liveness/readiness 探针（复用 /actuator/health）③ RollingUpdate 滚动发布与回滚（对照 M2 手工蓝绿）④ HPA 自动扩缩容（对照 M2 手工扩容演练）⑤ Helm Chart 模板化 ⑥ 流水线延伸：镜像推送→部署（可选 ArgoCD GitOps 体验）⑦ 诚实取舍：MySQL/Redis/MQ 留在 compose（真实公司常见做法——有状态服务不进 K8s 或用 Operator，复杂度另算）
- **技术含量**：K8s 核心对象与生产实践、声明式部署、GitOps、探针与自愈
- **验收**：杀掉应用 Pod 自动恢复无人工介入；滚动发布零中断且可一键回滚；HPA 压测中自动扩容；Secret 中不再有明文密码

### M8 微服务化拆分演练（沿限界上下文拆，重演 vivo 演进史）
- **前置说明（刻意最后拆）**：M1-M7 保持模块化单体——DDD 限界上下文的包结构本身就是拆分预案；待 M3 压测给出扩容画像、M5/M6 制造出真实拆分动机（发布节奏冲突/多业务方接入）后再沿既有边界拆。拆分原则：**拆分是痛点的结果，不是技术先进性的目标**（vivo 四痛点触发；数禾 10 亿数据仍单服务+分表为反例见证）。
- **交付**：① 沿边界拆三服务：券模板服务（M端低频）/ 交易核心服务（领券+用券高频）/ 统计服务（M5 计域）② RPC 通信（OpenFeign 或 Dubbo）+ 注册与配置中心（Nacos）③ API 网关（鉴权/限流前置，消化 L18）④ 分布式链路追踪（SkyWalking/Micrometer Tracing——traceId 跨服务传播）⑤ **跨服务一致性升级**：锁券/核销跨服务边界后的 TCC/事务消息真分布式落地（docs/05 设计兑现）⑥ K8s 上多服务部署（M7 集群复用）
- **技术含量**：服务拆分决策、RPC 与服务治理、分布式追踪、真分布式事务

## 3. 企业开发流程模板（每个需求/里程碑通用）

> **工序纪律 v2（2026-09-13 用户裁定）：Bug 检出 → 文档先行 → 实施。** ② 之前必须先有 **⓪ Bug 检出**：能运行时复现的写红灯测试实锤（断言期望的正确行为，亲眼看它失败）；不能运行时复现的（子系统缺失类 Bug——现有 API 摸不到"不存在的东西"）做静态穷举/时序推演检查。检出的 Bug 连同"具体怎么发生、怎么解决"写成方案文档（②），**待批准后才动代码**；实施时验收测试先红后绿（⑤ 的用例在 ③ 之前写好）。铁律：**每一个防御措施都必须由一个亲眼见过它红（或被穷举证明存在）的故障来买单**——没有痛点证据的技术是负资产。

```
⓪ Bug 检出（红队）→ 红灯测试/静态穷举证明——问题真实存在的证据（L2 起生效，v2 固化）
① 需求评审（产品视角）→ 需求卡片：业务目标/验收标准
② 技术方案（架构视角）→ 方案文档：选型对比/风险/回滚 —— 评审通过才开发
③ 开发（后端）→ 小步提交，每提交可运行可测试
④ 代码评审（交叉）→ 对照检查单（正确性/规范/测试覆盖）
⑤ 测试（测试视角）→ 单测+集成+验收用例，报告留档
⑥ 上线（SRE视角）→ 上线检查单：变更范围/回滚预案/观察指标 —— M2 起走流水线
⑦ 观察（SRE视角）→ 大盘/告警确认，STATUS 更新，复盘进登记簿
```
