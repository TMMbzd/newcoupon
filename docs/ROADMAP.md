#### 2b：库存批次分片（旧 M3-⑥，提前实施——数学已定不等压测）

**依据**：背景 5000 QPS vs DB 热行 ~400 TPS 饱和（[腾讯云 618 实证](https://developer.cloud.tencent.com/article/2623908)、[阿里 PolarDB-X 基准 512 并发下普通更新 400 TPS 饱和](https://help.aliyun.com/zh/polardb/polardb-for-xscale/update-hot-rows)）。

**方案 v2**（2026-09-18 裁决修订——[完整方案](P2b-库存批次分片-技术方案-2026-09-17.md) v2 + [测试大纲](P2b-测试大纲与风险清单-2026-09-18.md)，v1 经 7 领域测试团队评审 TOP12 全设计缺陷后重写）：
```
三层结构：
  DB① coupon_template：total / allocated（单调不减，只被开桶 CAS 推进）
  DB② stock_bucket 分桶账本（每桶一行 quota/used）：
      领券事务内逐笔条件扣 UPDATE stock_bucket SET used=used+1 WHERE used<quota
      ——超发红线"DB 条件更新保证"原样保留，热行从模板行分散到 16 桶行（312 TPS/行 < 400 饱和）
  Redis：c:stk:{tpl}:{bucket}:{gen} 四族键按（桶,世代）拆分
        c:alloc 镜像（开桶 Lua 原子同步）/ c:opening 单飞锚 / c:fz 冻结牌

三条可判定等式（治 v1 层2自相矛盾）：
  E1 分代桶内：stk+pend+dbi+void ≡ bucket_total（纯 Redis 原子）
  E2 Redis 全局：Σ(活跃代四键和)+c:alloc ≡ total（纯 Redis 原子）
  E3 镜像（方向判据）：c:alloc↔allocated ｜ 分代 dbi↔stock_bucket.used ｜ Σdbi↔SUM(used)，deep 权威=COUNT

关键裁决（A-G 七簇）：stock_bucket 保红线｜ic 冻结换锚｜epoch 世代隔离（迟到 cancel 落旧代 void）
｜开桶 single-flight+尾量 min()｜V10 存量回填+quiesce 切流+回滚协议｜平移资损被 DB 封顶+单调差分检测
｜allocated 生命周期+publish 最小鉴权（提前）
```

**实施清单**（v2 详表见方案 §11）：
- 第 0 步：故障注入基建（6 类钩子——不建则半数红灯是纸面文章）

- 守恒巡检：E1/E2/E3 三层 + 分代镜像 + void/dbi 单调差分 + ic 换锚

#### 2e：实时性三改进 + 最小可观测（用户质询"大厂不可忍受分钟级修复"后，实时性件从 P3 提前）

> **核心思想**：大厂的"实时"不是修复实时，是**发现+止血**实时；修复保持可慢（宁慢勿错），但已止血就不持续伤害。本小节把发现+止血从"120 秒+人工"改成"毫秒+自动"。

- ① 守恒巡检确认改**三步当场确认**（发现 120 秒→亚秒级；每步滤的假阳性来源明确）：
  (1) 失配后**主键新鲜重读 DB total**——滤"列表快照旧"（total 非 Redis 键，守恒式右侧本来自 DB）；
  (2) 延迟 ~200ms **第二次独立 CONSERVATION 原子快照**——滤"resetAll/appendStock 非原子管理窗口"。注：同一段 Lua 内读两次必然同值（脚本执行期间引擎独占），重读必须是独立 EVAL；正常流量全是恒等变换 Lua、两次读数不会变，会变的只有非原子管理操作；
  (3) 仍破缺才升级。清扫故意破缺（崩溃残留）不会自己好——它等来的是修复不是痊愈，时间过滤对它无意义
- ② **模板冻结标志 c:fz:{tpl}**（从 P3-⑥ 提前）：DEDUCT Lua 首行加冻结短路键（与售罄牌同款机制），后续请求全部 Redis 层挡住（-11 冻结码）。**冻结只绑危险方向**：sum>total（超发方向）或幻影 dbi>新鲜ic 才冻结；sum<total（清扫故意破缺/崩溃残留——日常发生）**不冻结**只走 deep 慢修，卖券不中断。与镜像臂方向性判据同构：不是"不相等就动作"，是"朝哪个方向不相等才动作"。
  **管理操作顺序铁律：先 DB 后 Redis**——窗口期偏差永远落在良性方向（sum<total），冻结永不被管理窗口误触发。**假阳性代价有界**：下一轮巡检干净且无修复动作则自动解冻（误冻结最多挡 60 秒）。破坏性修复（FORCE）仍走两轮确认——粗动作快、精修复慢
- ③ **假售罄当场修**（从 P3-⑫ 提前）：领券发现 -3 且无售罄牌 → 当场查 DB → 有货即重建重试，用户零感知
- ④ **售罄牌短 TTL**（从 P3-⑬ 同批提前）：EXPIRE so 10 秒自续期（DEDUCT 命中时续期）——防清除消息丢失导致永久假死
- ⑤ Micrometer + 基础指标：QPS / RT / 错误率 / 库存余量 gauge（按桶） / 分桶命中率 / MQ lag——只够"看得见改对了没有"，不做完整大盘

**P2 验收标准**：
- 注入库存漂移 → **毫秒级检测（当场重读）→ 自动冻结（c:fz 置位，请求被 -11 挡住）→ 修复后自动恢复**；注入假售罄 → 下一个请求零感知修复
- 分桶后守恒式全绿（两轮+两层验证）
- MQ outbox 端到端幂等（重复消费/迟到补偿全部 no-op）
- 本地缓存命中（首次加载后不再打 DB）
- 基础指标在 Prometheus 可查
- 2000 并发分桶集成测通过

**角色工件**：批次分片技术方案 v2（架构）、**风险先行测试大纲（测试，73 风险×用例+好用性指标）**、outbox ADR、V8/V9/V10 迁移脚本、分桶集成测报告（测试）

### P5 钱的后半程（≈ 旧 M5 剩余——schema 已在 P2a 定版，此处纯实现）

## 5. 总原则备忘

| 原则 | 含义 |
|---|---|
| **正确性优先** | 零超发/零超领/一券多用=0——数据库条件更新独扛，与 Redis 无关 |
| **结构前置** | 不可逆 schema/键结构/写路径架构一次定死——之后只填数据不改结构 |
| **观测建终态** | 监控大盘/告警/止血建在最终架构上——不为中间态建一次性监控 |
| **验证建终态** | 压测/容量规划验证最终架构——不验证旧态再"根据结果决定要不要改" |
| **无痛点技术是负资产** | 每个组件由量级数字或红线触发——但数学已定的不等实测 |
| **拆分是痛点的结果** | P9 微服务化按写死条件触发，非技术先进性目标 |
| **每个防御措施由红灯买单** | 没亲眼见过它红（或穷举证明）的故障，不上防御 |
