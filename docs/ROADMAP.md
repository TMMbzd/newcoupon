# 技术路线图 v2（企业化重组）

> 取代 docs/00 第 4 节的原始路线（该路线按"周"组织、无环境设定、无角色流程——被评审正确地批评为"想到什么做什么"）。
> 配套：《STATUS.md》（系统现状总账）。**每个里程碑开题前出技术方案、收尾时更新 STATUS、全程按 §3 流程模板走。**

## 0. 企业环境设定（模拟公司：以设定倒推全部技术决策）

**业务背景**：「NewMall 商城」中型电商平台（对标素材中 vivo/京东到家的体量起步，向字节/美团的目标演进）。

| 维度 | 设定 | 来源依据 |
|---|---|---|
| 用户规模 | 注册用户 2000 万，DAU 200 万 | vivo 商城量级 |
| 券规模 | 日发券 500 万，存量用户券 10 亿级 | 京东到家实测数字 |
| 峰值场景 | 大促 0 点开抢：单批次 10 万张券、瞬时 5000 QPS 领券 | 阶段目标（docs/00） |
| SLA | 核心链路（领券/核销）可用性 99.95%，P99 < 200ms | 大厂通用基线 |
| 资损红线 | 超发=0、超领=0、一券多用=0 | 券=钱 |
| 团队设定 | 产品/架构/后端/测试/SRE 五角色（你我分饰，工件见 §3） | 模拟多部门协作 |
| 基础设施 | 自建机房模拟（Docker）：MySQL 主从、Redis 哨兵、RocketMQ、Prometheus/Grafana | 全部本地容器化 |

**决策总原则**：每个技术组件的引入必须由上面某个数字或红线触发——没有对应痛点的技术是负资产（阿里规约：禁止超前设计）。

## 2. 里程碑（M1→M6，顺序有依赖理由，不并行）

> 原则：**正确性 > 可观测 > 规模 > 吞吐 > 平台化**。先还正确性的债（M1），再让系统"看得见"（M2），然后才谈规模（M3/M4/M5）与开放（M6）。

### M1 债务清偿与正确性收口（当前）
- **交付**：① 券过期全链路（任务表+定时+惰性判断+事件，docs/06 整章，L2）② 锁定超时兜底任务（L5）③ ul 计数自愈（L3）④ 对账扩展（占用单×券状态交叉核对，docs/01 4.9 的三层对账补齐第一层）⑤ 领取窗口列（L13，随过期补列）⑥ release 幂等分支读券真实状态（L15）
- **技术含量**：海量数据过期不扫主表（时间轮/任务表方案对比）、资产悬挂自愈、交叉对账
- **角色工件**：技术方案（架构）、实现+单测/集成测（后端/测试）、STATUS 更新
- **验收**：过期券不可用且核销被拒；锁死券 30 分钟后自动释放；人为制造计数漂移→撞索引自愈；对账发现人为注入的占用单/券状态不一致

### M2 可观测性与 CI/CD（把工程架起来）
- **交付**：① Micrometer 指标（QPS/RT/错误码分布/库存余量 gauge）+ Prometheus + Grafana 大盘 ② 告警规则（错误率/RT/库存漂移）③ CI 流水线（**全本地**：Gitea+act_runner 容器化，语法兼容 GitHub Actions，可随时迁其免费档；提PR→流水线→人工评审→合并的完整企业流程）：编译→单测→集成测→覆盖率门禁→OWASP 依赖扫描→Docker 镜像构建 ④ 生产形态 compose（应用×2+Nginx 负载均衡+健康检查+优雅停机+**蓝绿发布与回滚演练**+**水平扩容 1→2 实例演练**——后者前置修复 L16 对账多实例锁）⑤ 环境矩阵与密钥外部化（dev/test/prod 三 profile、密码出库）+ 备份恢复演练 + Spring Boot 升级到 OSS 支持版本（L19/L20）
- **技术含量**：企业监控体系、质量门禁、制品化、SLA 度量（错误预算）
- **验收**：大盘能实时看到压测流量曲线；故意注入故障→告警触发；PR 触发流水线全绿才能合并；容器重启业务无损
- **角色工件**：监控大盘（SRE）、流水线配置（SRE/后端）、上线检查单

### M3 全链路压测与容量治理（用数字说话）
- **交付**：① wrk/JMeter 压测脚本与基线报告（同步链路真实 QPS/RT/瓶颈定位）② 依据数据实施：模板本地缓存（Caffeine 二级，L6）③ 需要则热点分桶（L9）④ 连接池/线程池/Redis 池参数按数据配平 ⑤ 1.5 倍冗余结论
- **技术含量**：容量规划方法论（自底向上找瓶颈）、压测流量隔离、热点治理
- **验收**：5000 QPS 目标达成或给出"同步打不动→切换方案"的数据论证（异步 vs 分段的决策依据：领券体验要求实时到账，同步优先）
- **角色工件**：压测报告（测试/SRE）、容量结论与决策记录 ADR（架构）

### M4 存储规模化（十亿级用户券）
- **交付**：① ShardingSphere-JDBC 按 user_id 8 库×32 表 ② 不停机迁移演练（双写法，docs/07）③ 冷热归档（终态券归档）④ 运营/客服查询走 ES 宽表（binlog→MQ→ES）⑤ Leaf 分布式 ID 替换自增（docs/04）
- **技术含量**：分片路由设计（路由因子进唯一索引）、在线迁移、异构查询
- **验收**：迁移演练数据零丢失可回滚；跨维度查询不再广播；归档后在线表缩减 70%+

### M5 异步化与"计"域（吞吐与经营闭环）
- **交付**：① RocketMQ 接入：发放事件/outbox、定向发券管线（亿级批量，docs/02 12 步）② 领券异步开关（M3 数据若要求）③ 优惠计算引擎（可用券+最优勾选，docs/05）④ 统计报表三层（明细→批次→天）与财务对账口径
- **技术含量**：MQ 可靠投递、削峰、批量管线、优惠计算（叠加/互斥/分摊守恒）
- **验收**：定向发券 100 万/分钟且可暂停可重试；报表口径与事件表对平

### M6 中台化与开放（多业务接入）
- **交付**：① biz_id 多租户贯穿 ② HMAC 签名+防重放 ③ 按上游配额限流 ④ 规则表达式引擎 ⑤ 审批流+交叉审核（L1 兑现）⑥ 登录态接入（L12）⑦ 客服工具（查券/补发/作废，双人复核）⑧ 运营闭环：模板追加库存 appendStock（同步回补 Redis）与模板下线 OFFLINE（L17）
- **技术含量**：多租户隔离、开放平台安全、规则引擎、内控
- **验收**：新业务接入沙箱四类用例才准出；越权/重放全被拦截

### M7 平台化部署：Kubernetes 与 GitOps（应用层上云）
- **前置说明**：刻意排在 M2 之后——M2 用 compose 手工做蓝绿/扩容/健康检查，先体验"K8s 自动化掉的那些繁琐"；M7 再把同一套应用迁上 K8s，每个对象都能对上"我手工干过的活"。
- **交付**：① kind 本地集群（Kubernetes-in-Docker，单节点约2GB内存）② 应用无状态层 K8s 化：Deployment/Service/Ingress/ConfigMap/Secret（消化 L20）+ liveness/readiness 探针（复用 /actuator/health）③ RollingUpdate 滚动发布与回滚（对照 M2 手工蓝绿）④ HPA 自动扩缩容（对照 M2 手工扩容演练）⑤ Helm Chart 模板化 ⑥ 流水线延伸：镜像推送→部署（可选 ArgoCD GitOps 体验）⑦ 诚实取舍：MySQL/Redis/MQ 留在 compose（真实公司常见做法——有状态服务不进 K8s 或用 Operator，复杂度另算）
- **技术含量**：K8s 核心对象与生产实践、声明式部署、GitOps、探针与自愈
- **验收**：杀掉应用 Pod 自动恢复无人工介入；滚动发布零中断且可一键回滚；HPA 压测中自动扩容；Secret 中不再有明文密码

### M8 微服务化拆分演练（沿限界上下文拆，重演 vivo 演进史）
- **前置说明（刻意最后拆）**：M1-M7 保持模块化单体——DDD 限界上下文的包结构本身就是拆分预案；待 M3 压测给出扩容画像、M5/M6 制造出真实拆分动机（发布节奏冲突/多业务方接入）后再沿既有边界拆。拆分原则：**拆分是痛点的结果，不是技术先进性的目标**（vivo 四痛点触发；数禾 10 亿数据仍单服务+分表为反例见证）。
- **交付**：① 沿边界拆三服务：券模板服务（M端低频）/ 交易核心服务（领券+用券高频）/ 统计服务（M5 计域）② RPC 通信（OpenFeign 或 Dubbo）+ 注册与配置中心（Nacos）③ API 网关（鉴权/限流前置，消化 L18）④ 分布式链路追踪（SkyWalking/Micrometer Tracing——traceId 跨服务传播）⑤ **跨服务一致性升级**：锁券/核销跨服务边界后的 TCC/事务消息真分布式落地（docs/05 设计兑现）⑥ K8s 上多服务部署（M7 集群复用）
- **技术含量**：服务拆分决策、RPC 与服务治理、分布式追踪、真分布式事务
- **验收**：交易核心独立扩容不影响模板服务；故障注入只隔离受损服务；链路追踪跨三个服务还原一次领券全程；拆分前后 76+ 测试全部保持绿（行为零变化的纯架构重构）

## 3. 企业开发流程模板（每个需求/里程碑通用）

```
① 需求评审（产品视角）→ 需求卡片：业务目标/验收标准
② 技术方案（架构视角）→ 方案文档：选型对比/风险/回滚 —— 评审通过才开发
③ 开发（后端）→ 小步提交，每提交可运行可测试
④ 代码评审（交叉）→ 对照检查单（正确性/规范/测试覆盖）
⑤ 测试（测试视角）→ 单测+集成+验收用例，报告留档
⑥ 上线（SRE视角）→ 上线检查单：变更范围/回滚预案/观察指标 —— M2 起走流水线
⑦ 观察（SRE视角）→ 大盘/告警确认，STATUS 更新，复盘进登记簿
```

## 4. 演练矩阵（全部本地容器化，零云成本；每次演练=暴露一个真实生产问题的机会）

| 演练 | 里程碑 | 内容 | 预期暴露的真问题 |
|---|---|---|---|
| 水平扩容 1→2 实例 | M2 | Nginx 后动态加应用实例，压测中扩、观察零中断 | @Scheduled 多实例重复执行（L16→必须分布式锁/选主） |
| 蓝绿发布+回滚 | M2 | 绿组起→切流量→注入故障→回蓝组 | 优雅停机、健康检查、迁移与代码兼容性 |
| 框架版本升级 | M2 起常态化 | 流水线跑 Boot 小版本升级+依赖扫描+全量回归 | 回归测试作为升级安全网 |
| MySQL 主从+故障切换 | M4 | 加从库→复制→杀主→提升从库 | 复制延迟读旧数据、切换窗口丢写 |
| 不停机分库迁移 | M4 | 双写搬迁+灰度切读+可回滚 | 双写期 UPDATE 丢更新（数禾真坑） |
| 分库翻倍扩容 2→4 | M4 | "容量不够加机器"全流程 | 数据重分布、路由变更、迁移期双读一致性 |
| Redis 哨兵故障切换 | M4 | 主从+哨兵→杀主→自动选主 | 丢最近写入→库存漂移→对账重建收口（验证 ADR-0006） |

**资源预算**（WSL2，16GB 内存机器可行；必要时调 `.wslconfig`）：M2 全套（应用×2/MySQL/Redis/Nginx/Prometheus/Grafana/Gitea+runner）≈2.6GB；M4 分库演练用 2 容器×4 schema 模拟 8 库 +1GB；M5 RocketMQ +1.5GB。多 schema 共享实例是测试环境常规做法，不影响演练真实性。
