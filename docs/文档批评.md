# 这两份文档的问题与改进方向

## 一、先说结论

这两份文档比“咋咋呼呼甩名词”好，但离“适合你”还差得远。核心问题是：**它自称“教学版”，但骨子里还是“给项目内部人看的备忘录”**。它假设读者已经知道整个系统的架构、黑话和背景，然后在这些假设上“讲原理”。一个真正的教学文档，应该从零开始构建理解，而不是在一堆未解释的概念上跳舞。

* * *

## 二、具体问题（按严重程度排）

### 问题1：满篇内部黑话，第一次出现不解释

文档里到处都是这种词：

> ADR-0009、M1、L2、L5、D1-D9、docs/06、守恒式、对账修复、令牌、在途、恒等式、dbi、ic、pend、REPAIR、uk\_idem、c:dly、c:uld……

这些词在文档里反复出现，但**没有任何一处用大白话解释它们是什么、为什么存在**。文档第0部分说“读完本文再看技术文档会非常顺”，但读者连“本文”都读不懂，怎么顺？

比如“守恒式”这个词，在两份文档里出现了十几次，但从来没解释过它到底是什么。一个外部读者看到“守恒式/DB终审”，完全不知道在说什么。

### 问题2：假设读者是项目内部人

文档里大量引用“答辩 D8 裁定”“ADR-0009 §6”“docs/06 §6.2”“讨论01 七核查”……这些对项目内部人是常识，对外部读者是天书。教学文档不应该依赖读者读过其他内部文档。

更离谱的是角色表：

> | `receive()` | 领券编排方法：过闸 → DB 事务 → confirm/cancel 记账 |  
> | confirm | DB 提交成功后的记账动作（dbi+1、令牌出清，一个 Lua） |

这叫什么解释？“过闸”是什么？“dbi+1”是什么？“令牌出清”是什么？“Lua”在这里干什么？一个解释里塞了三个未解释的新概念。

### 问题4：讲解和代码仍然割裂

你之前要求“讲到哪、贴到哪、解释哪”。文档部分做到了，但很多时候还是：先讲一段原理，然后甩一个代码块，代码块后面再讲一段原理。代码块本身没有逐行解释，读者不知道哪一行对应哪个原理。

比如Bug②的`recoverUncertainOutcome`方法，代码块前面只说“探针定案，三岔口”，代码块后面才解释。读者看代码时是懵的，要读到后面才明白。正确的做法是：先讲“我们要查一下事务到底提交没有”，然后贴查询那两行，解释为什么查`uk_idem`；再讲“查到了怎么办”，贴`confirmQuietly`那行；再讲“没查到怎么办”，贴`cancelQuietly`那行。

### 问题5：“教学版”仍然按技术文档结构走

第3部分“方案为什么长那样”直接对着“D1-D9”讲。D1到D9是技术文档的编号体系，教学版不应该继承这个体系，而应该按读者的认知顺序重新组织。读者不需要知道“D1是什么”，只需要知道“为什么修核销是第一优先”。

### 问题6：缺少完整可复现的演示

文档说“测试里领一张真券，然后直接改数据库把`valid_end`改成两天前”，但：

-   测试代码在哪？
-   怎么跑？
-   环境怎么配？
-   数据库连接信息在哪？
-   改哪个库、哪张表、哪一行？
-   跑完输出长什么样？

一个读者想复现，根本无从下手。教学文档的核心价值是“我能跟着做一遍”，但这两份文档只给了“结论和片段”，没给“完整可执行的路径”。

### 问题7：自测题没答案，难度跳跃

自测题问“为什么 cancel 之后恒等式还是 0、三层对账全瞎”，这个问题需要读者完全理解“恒等式”“三层对账”“cancel的配对回滚机制”才能回答。但文档对这些概念的解释都不够，读者做不出来。而且没有参考答案，读者不知道自己想得对不对。

### 问题8：过度强调“这很重要”

文档里到处是“这是灾难”“这才是关键”“记住它的名字”“这是全系统资损的最后防线”……这种语气像营销文案，不是教学。教学应该让读者自己得出结论，而不是不断告诉读者“这里很重要”。

## 三、怎么写才适合你：一份改进后的提示词

text

复制

下载

你是一名资深工程师，正在带一个【读者】从零理解【任务】。
读者背景：【填写】。读者目标：【填写】。
你手头有内部技术文档、代码、日志，但读者没读过这些，也不懂项目黑话。
写作要求：
1\. 从零构建。假设读者不知道任何项目内部术语。每个术语第一次出现必须用大白话解释：
   “术语（大白话：……；为什么需要：……；举个例子：……）”
   禁止在解释里塞新的未解释术语。
2\. 不引用内部文档编号。不说“ADR-0009”“docs/06”“D1-D9”“答辩D8”。
   需要引用时，用一句话概括那个文档说了什么，然后继续讲。
3\. 代码跟着讲解走，不要攒成块。
   讲到一个点时，先说要做什么，然后贴相关代码（只贴相关的那几行），
   逐行解释关键行为什么这么写、运行会发生什么。
   然后进入下一个点，再贴下一段代码。
   每段代码必须给：文件路径、完整方法名、依赖版本、运行命令。
   如果代码片段依赖上下文，先把上下文用最小示例补全。
4\. 演示要完整可复现。
   从环境准备开始：装什么、配什么、连哪个库、改哪张表、跑什么命令。
   给出预期输出和实际可能输出。
   失败时看什么日志、怎么排查。
5\. 不讲“D1-D9”，按认知顺序重新组织。
   先讲“要解决什么问题”，再讲“为什么这个问题难”，
   然后讲“第一个想法是什么、为什么不行”，
   再讲“第二个想法是什么、为什么也不行”，
   最后讲“最终方案是什么、为什么它行”。
   每一步都贴代码、跑命令、看输出。
6\. 不要过度强调“这很重要”。让读者自己从过程和结果里得出结论。
   不要用“灾难”“关键”“记住”这种词。用事实和因果说话。
7\. 自测题给参考答案或思路提示。
   自测题本身要基于文档里完整演示过的内容，不要考没讲过的背景。
8\. 每一节末尾列“读者可能卡在哪”，并解释。
现在我的任务是：
【填写任务】
请直接开始写。如果信息不足，先问我最多3个关键问题。

## 四、用这个提示词改写“症状②”会是什么样

给你一个直观对比。原文是：

> **为什么这个入口是对的**：锁定的 SQL 当初就写对了——

> sql

> UPDATE user\_coupon SET status \= 1 WHERE id \= ? AND status \= 0 AND valid\_end \> NOW()
> 
> 注意最后的 `AND valid_end > NOW()`……

改写后应该是：

> **先看锁定入口为什么是对的。**
> 
> 券表长这样（简化）：
> 
> sql
> 
> 复制
> 
> 下载
> 
> CREATE TABLE user\_coupon (
>   id BIGINT PRIMARY KEY,
>   user\_id BIGINT,
>   status TINYINT,        \-- 0=待使用，1=已锁定，2=已核销，3=已过期
>   valid\_end DATETIME,    \-- 有效期终点
>   ...
> );
> 
> 用户下单要用券时，系统执行这条 SQL：
> 
> sql
> 
> 复制
> 
> 下载
> 
> UPDATE user\_coupon
> SET status \= 1
> WHERE id \= ?
>   AND status \= 0
>   AND valid\_end \> NOW()
> 
> 逐行看：
> 
> -   `SET status = 1`：把券从“待使用”改成“已锁定”。
> -   `WHERE id = ?`：只改这一张券。
> -   `AND status = 0`：只有当前是“待使用”才改。如果已经锁定或核销，改0行。
> -   `AND valid_end > NOW()`：只有没过期才改。如果过期了，改0行。
> 
> 关键在最后一行。`NOW()`是数据库的当前时间，判断和修改在同一个原子操作里完成。  
> 不会出现“先查时没过期、改的一瞬间过期了”的缝隙。
> 
> 跑一下试试。先插一张过期券：
> 
> sql
> 
> 复制
> 
> 下载
> 
> INSERT INTO user\_coupon (id, user\_id, status, valid\_end)
> VALUES (1, 1001, 0, '2026-09-10 00:00:00');
> 
> 然后执行锁定 SQL：
> 
> sql
> 
> 复制
> 
> 下载
> 
> UPDATE user\_coupon SET status \= 1 WHERE id \= 1 AND status \= 0 AND valid\_end \> NOW();
> 
> 输出：
> 
> text
> 
> 复制
> 
> 下载
> 
> Query OK, 0 rows affected
> 
> 0行被改。因为`valid_end > NOW()`不成立。锁定被拒绝，报4002。
> 
> 现在把有效期改到未来：
> 
> sql
> 
> 复制
> 
> 下载
> 
> UPDATE user\_coupon SET valid\_end \= '2026-09-20 00:00:00' WHERE id \= 1;
> 
> 再跑锁定：
> 
> text
> 
> 复制
> 
> 下载
> 
> Query OK, 1 row affected
> 
> 1行被改。锁定成功。
> 
> 记住这个写法：**把条件写进 UPDATE 的 WHERE 里，让数据库在一个原子动作里同时判断和修改**。  
> 下一节会看到，核销入口少了这个条件，导致了资损。

## 五、一句话总结

这两份文档的问题是：**它以为自己在教学，其实在写内部备忘录**。它假设读者懂黑话、懂架构、懂背景，然后在这些假设上“讲原理”。真正的教学文档应该从零开始，每个术语解释清楚，每段代码给足上下文，每个结论用可复现的演示来支撑，让读者自己得出结论。
