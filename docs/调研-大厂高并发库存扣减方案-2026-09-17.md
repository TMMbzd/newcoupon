## 1. 路线 A：库存分桶（腾讯云 618 实证）

来源：[从雪崩到稳如磐石：电商秒杀热点库存更新的高并发优化实战](https://developer.cloud.tencent.com/article/2623908)

**做法**：1000 件库存拆成 10 个逻辑段（`product_stock_bucket` 表），每段 100 件。扣减时随机选一个非空桶更新：
```sql
UPDATE product_stock_bucket
   SET stock = stock - 1
 WHERE product_id = ? AND bucket_id = ? AND stock > 0
```
锁竞争从 1 行分散到 10 行，**吞吐提升近 10 倍**。

**实证数字**：
| 指标 | 优化前 | 优化后 |
|---|---|---|
| 秒杀 QPS | 12,000 | 15,000+ |
| MySQL CPU | 95%+ | < 30% |
| P99 延迟 | 5.2s | 80ms |
| 超卖率 | 0.7% | 0% |
| 可用性 | 82% | 99.99% |

其他：约 99% 请求在 Redis 层被拦截；MQ 消费 1000 TPS；对账周期 1 分钟。

**注意**：分桶同时用在了 Redis 层（库存拆多个 key 分散单 key 热点）和数据库层（拆多行分散行锁热点）——两层同时分。

## 2. 路线 B：合并提交（阿里"库存合并扣减"方案）

来源：[库存合并扣减：基于分布式缓存的强一致性热点库存扣减方案](https://developer.aliyun.com/article/1704859)（阿里库存团队）

**核心思想**：Redis 分桶扣减计数 + **合并提交扣减 DB**——不是每笔都写 DB，而是攒一批（如 100 笔或固定时间窗口）后一次写：
```
Redis 分桶扣减（每笔实时，原子）→ 扣减明细暂存 → 合并提交（批量写 DB）
```

**与固定步长的区别**：固定步长是"从 DB 申请→Redis 扣→扣完再申请"（拉模式）；合并提交是"Redis 先扣→攒明细→批量写回 DB"（推模式）。两者本质相同：**把 N 次数据库写变成 1 次**。

## 3. 路线 C：数据库内核组提交（阿里 PolarDB-X / 淘宝 RDS）

来源：
- [PolarDB-X 热点更新官方文档](https://help.aliyun.com/zh/polardb/polardb-for-xscale/update-hot-rows)
- [AliSQL Inventory Hint（阿里云 RDS）](https://www.alibabacloud.com/help/zh/rds/apsaradb-rds-for-mysql/inventory-hint)
- [淘宝数据库内核月报：RDS 三节点企业版热点组提交](http://mysql.taobao.org/monthly/2020/02/03/)

**这是最激进的路线：不改应用架构，改数据库内核。**

原理：普通更新 `LOCK → UPDATE → UNLOCK`；热点组提交改为 `LOCK → GROUP UPDATE → UNLOCK`——**数据库内核自己把同一行的多个并发更新合并成一批，只加一次行锁，组内批量更新，一次提交**。

阿里给了一个 SQL Hint（`commit_on_success`），应用侧只改一条 SQL 的注释：
```sql
UPDATE /*+ commit_on_success rollback_on_fail target_affect_row(1) */
    coupon_template SET issued_count = issued_count + 1
 WHERE id = 1 AND issued_count < 100000;
-- 数据库自动：成功→连同之前语句一起提交；失败→自动回滚
```

**性能实测（阿里官方基准，512 并发线程）**：

| 并发线程 | 热点更新 TPS | 普通更新 TPS |
|---|---|---|
| 1 | 298 | 318（单线程无差异） |
| 16 | 3,472 | 409 |
| 64 | 10,138 | 428 |
| 256 | 15,803 | 497 |
| 512 | **23,262** | 615 |

普通更新约 **400 TPS 饱和**；热点更新线性增长到 **23,262 TPS——38 倍**。

**限制**：仅 PolarDB-X 企业版/AliSQL 支持；单分片事务；WHERE 必须主键等值。

## 4. 大厂真实系统里三条路的组合

综合全部调研，大厂（阿里/腾讯/美团量级）**不是选一条，是分层组合**：

```
第一层  客户端+网关限流（验证码/答题/按钮限点/SLB限流）
         ↓ 挡掉 90%+ 无效流量
第二层  Redis Lua 原子扣减（分桶 key）
         ↓ 99% 请求在这层解决，~1% 过闸到下一层
第三层  合并提交 / 固定步长（攒批写 DB，或数据库组提交）
         ↓ DB 热行只被打扰批边界次（或内核自动合并）
第四层  对账兜底（每分钟 Redis↔DB 比对）
```

**关键认知**：大厂"每笔都写数据库"这个假设在 5000+ QPS 时是不成立的——他们用的是"**每笔都过 Redis（原子），但 DB 只在批边界被打扰**"。零超卖不是靠 DB 逐笔验，而是靠 Redis 原子性+对账兜底。

## 5. 与守恒式的兼容性分析

**问题**：守恒式 `stk+pend+dbi+void≡total` 要求 Redis 里有全量库存余量。合并提交/固定步长下 Redis 里只有"当前批的余量"。

**兼容方案——批次分片**（我们自己的推导）：

```
total = 1,000,000（一批大促券）
拆成 100 个批次，每批 10,000

Redis 键结构变为：
  c:stk:{tpl}:{bucket}     批次余量（每个桶独立守恒）
  c:pend:{tpl}:{bucket}    批次在途
  c:dbi:{tpl}:{bucket}     批次已发放
  c:void:{tpl}:{bucket}    批次已撤销

守恒式变为（两层）：
  层1（桶内）：stk_i + pend_i + dbi_i + void_i ≡ bucket_total_i（每桶独立验）
  层2（全局）：Σ(dbi_i) + DB未分配的余量 ≡ total（DB 视角的全局守恒）

DB 交互：
  开新桶时：UPDATE template SET allocated = allocated + 10000 WHERE allocated + 10000 <= total
  （一次行锁，只在批边界发生——热行问题消失）
```

**这样既保住守恒式（每桶独立验证），又解决热行（DB 只在开桶时被打扰）**。
