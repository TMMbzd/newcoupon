# 对标：P2 已实现部分 vs 业界（大厂）做法对照（2026-09-30）

> **这份文档干什么用**：P2 做了一大批"库存闸门 + 对账 + 一致性"的机制。这份文档逐块回答三个问题——**哪些我们做的和业界一致（同款）／哪些我们做得比公开资料更细（超纲）／哪些是业界有而我们没有（该补）**，以及 **哪些我们明确不做**。
> 依据：[对标-大厂能力地图](对标-大厂能力地图-2026-09-30.md)（含全部来源）。结论直接喂给 [ROADMAP-V2](ROADMAP-V2.md) 的 S3（发放链路重做）。
> 2026-10-01 微调：补流量治理对照（块 5 附「三类熔断/开关」、清单 B-9~B-12），S 编号同步重排。
> 诚实声明：对照的是**公开资料**（技术博客/专利/产品文档），不等于大厂内部真实实现；标"未见"只代表公开资料里没找到，不代表大厂没有。

## 一、逐块对照

### 块 1｜库存扣减与防超发（P2b 地基）

| 维度 | 我们（P2 实现） | 业界（公开资料） | 判定 |
|---|---|---|---|
| 扣减原子性 | Redis 一段 Lua：五重校验 + 扣减 + 令牌入队 + 幂等键 | **同款**："Lua 内先检查再 DECR，保证不会扣成负数"；超卖根因被点名为 TOCTOU | ✅ 同款 |
| 热点分散 | 模板拆 16 桶，键 `c:stk:{tpl}:{bucket}:{gen}`，行 `(template_id, bucket_no, generation)` | **同款**：库存分桶/分片——"单热点商品拆 N 个子库存行、复合主键 `(goods_id, bucket_id)`、写路由打散"；专利方案按用户量定 40 片 | ✅ 同款 |
| 数据库兜底 | 条件更新 `used < quota AND status = 0`（+ 模板状态 EXISTS） | **同款**：DB 乐观锁/条件更新兜底 | ✅ 同款 |
| 落库时机 | **同步**：同一请求内完成 DB 事务 | **异步**：Redis 预扣 → MQ → 后台平滑消费落库 | ⚠️ **差异（S3 补异步模式）** |
| 领取幂等 | Redis 幂等键 + DB 唯一索引（uk_idem）+ 令牌单次使用 | **同款**：Redis setnx/唯一索引/防重 key（`USER_ID+GOODS_ID` + TTL） | ✅ 同款 |
| 限领 | 每人累计 + 每日（Redis 计数 + DB `uk_user_seq` 终审 + 计数自愈） | **同款**：`maxCouponsPerProfile` / `maxCouponsPerOrder` 参数化 + 唯一索引 | ✅ 同款 |
| 取消/回滚 | 令牌单次使用 + 三态取消（回加 / 钉零 / 下线退休）+ **世代隔离**（迟到取消落旧代 void） | 延迟消息/定时任务**回滚补回**（INCRBY）；未见"世代"与"按原因分类取消"的公开描述 | 🌟 **超纲**（见清单 A-1、A-2） |
| 崩溃残留 | 在途令牌 ZSET + 180 秒清扫（= DB 锁等待上限 3 倍） | 定时任务补回 | 🌟 更细（在途窗口有硬上界，清扫阈值有推导依据） |

### 块 2｜对账（P2b 第二条腿 + P2e）

| 维度 | 我们 | 业界 | 判定 |
|---|---|---|---|
| 体系分期 | 巡检（验账）→ 三步确认（定罪）→ deep 修复/人工（平账） | **同款三分期**：数据准备 → 轧账 → 平账（美团配送资金对账） | ✅ 同款（术语待对齐，S3 做） |
| 检测目标 | 四条等式（桶内守恒 / Redis 总账 / 镜像口径 / 额度段） | 抓**漏结 / 重复结 / 错结** | ✅ 同款（我们的"额度段"对应"重复结"） |
| 比对算法 | 等式比对（同一系统两个存储） | **集合求差**（哈希 O(N+M)）+ **多级匹配**（精确→模糊时间金额→关联单号）+ 分片并行 | ⚠️ 不同场景：大厂是**两方**对账；我们是**单系统内部**一致性 → 等式更合适（要在文档里讲清这个区别） |
| 差异分级 | 方向判据：Redis 多钱=危险→冻结；少钱=安全→只修 | 长款/短款/单边账/状态不一致 | ✅ 等价（术语待对齐） |
| 实时性 | 60 秒巡检 + **亚秒三步确认** | T+1 → 小时级 → 准实时（"从 T+1 到实时"仍是演进方向） | 🌟 **超纲（实时性领先）** |
| 处置 | 自动冻结止血 + 白名单自动修复 + 影子模式 + 熔断 + 漂移表 | 差异工单、根因分类（有团队用随机森林）、追款闭环、资损三类明细 | ⚠️ **各有侧重**：我们的"自动"更强，大厂的"工单/追款/度量"更强（追款属资金侧，我们不做） |
| 度量 | 心跳/风暴聚合/连续熔断 | 预案覆盖率、MTTR、1-5-10 达成率 | ❌ **该补（后置治理批）** |

### 块 3｜最终一致性链路（P2d 发件箱）

| 维度 | 我们 | 业界 | 判定 |
|---|---|---|---|
| 方案选型 | 本地消息表（outbox）+ 独立投递器 | 三选一：本地消息表（eBay BASE；携程/拼多多）/ RocketMQ 事务消息（阿里、博时基金）/ CDC（Debezium） | ✅ **与携程/拼多多同款**；要在文档写清"为什么不用事务消息"（解耦、可换 MQ、失败可重放、账本自持、不绑架 MQ 集群） |
| 消费幂等 | `coupon_event_consumed` + `INSERT IGNORE` | 同款（唯一消息 ID / 去重表） | ✅ 同款 |
| 重试 | 指数退避 2^retry | 同款 | ✅ 同款 |
| 死信 | status=2 + `OUTBOX_DEAD` 告警（行保留可重放） | DLQ | ✅ 同款 |
| **顺序性** | **无**（未声明事件顺序依赖） | 分区键保证同键有序 | ❌ **该补（S3，或明确"无顺序依赖"）** |
| 对账兜底 | T+1 `issuedEventMinusOutbox` 守恒审计（2026-09-30 接上） | "必备实践"之一 | ✅ 同款（刚补上） |
| MQ 观测 | 无 lag/exporter | rocketmq-exporter + lag 告警 | ❌ 该补（后置监控批） |

### 块 4｜缓存（P2c）

| 维度 | 我们 | 业界 | 判定 |
|---|---|---|---|
| 选型 | Caffeine（W-TinyLFU） | **同款**：企业统一选型 | ✅ 同款 |
| 三兄弟 | 防击穿（refreshAfterWrite）/ 防穿透（负缓存）/ 防雪崩（TTL ±20%） | 同一套（互斥锁/逻辑过期/空值缓存/TTL 抖动） | ✅ 同款 |
| 层级 | 只有本地一级 | **四级**：CDN → Nginx → 本地 → Redis → DB | ⚠️ 该补（后置扩容批） |
| 多实例失效 | 主动失效 + TTL 兜底（单实例够用） | Pub/Sub 广播 / 订阅 binlog → MQ → invalidate | ❌ 该补（已登记 L16，后置） |
| **热点探测** | **无** | JDHotKey：滑动窗口判定 → 自动提升到本地缓存（P99 2.1ms→0.08ms） | ❌ **该补（展示价值高）** |
| 观测 | 命中计数入日志 | 命中率突降告警（5 分钟滑窗）、单 key 延迟告警 | ❌ 后置 |

### 块 5｜止血与降级（P2e）

| 维度 | 我们 | 业界 | 判定 |
|---|---|---|---|
| 止血手段 | 模板冻结牌（危险方向自动置位 + 三通道解除）、售罄牌自续期、假售罄当场急救、影子修复、连续 FORCE 熔断 | **预案平台**：一键降级/开关/切流/限流/熔断/重启；红黄蓝三级预案（按资损风险分级） | ⚠️ **理念不同（互补）**：大厂=人的处置标准化+一键化；我们=已知故障自动化 |
| 决策方式 | 系统自己判（等式破缺 → 方向 → 自动冻结/自动修） | 人/预案平台判（开关 + 演练 + 度量） | 🌟 **超纲（细粒度自愈闭环，公开资料少见）** |
| 灰度/回滚 | 无（模板级冻结是最近似物） | 灰度发布、开关回滚（约 70% 故障源于变更） | ❌ 该补（治理批） |
| 演练 | 故障注入用例（红灯基建）+ 影子模式 | 混沌工程（华为披露 376 个模型、5.9 万次演练） | ✅ 方法相近（我们规模小） |

**补充（2026-10-01）：三类"熔断/开关"要分清——我们只有第三类**

| 类别 | 是什么 | 归属层 | 我们 | 大厂 |
|---|---|---|---|---|
| **调用熔断** | 依赖（Redis/MySQL/MQ）异常或变慢时快速失败 | 技术层 | ❌ 缺（靠超时兜底） | Sentinel / Resilience4j 标准能力 |
| **业务开关** | 关掉某功能/某活动/某接口（Kill Switch） | 产品层 | ⚠️ 只有"模板冻结牌"（近似物） | 开关中心 + 一键降级 + 红黄蓝预案 |
| **修复环熔断** | 自动修复连续失败就停手止损 | 运维层 | ✅ **已有**（连续 FORCE 熔断） | 一般由预案/度量体系覆盖（未见等价公开描述） |

## 二、清单 A：我们超纲的（公开资料少见，作为"设计亮点"写进文档）

| # | 亮点 | 一句话讲清价值 | 文档归属 |
|---|---|---|---|
| A-1 | **世代隔离（批次快照）** | 迟到取消/跨代回滚是分桶后最难的坑；大厂靠补偿与对账兜底，我们把"回滚到哪一代"变成**键寻址**（令牌固化 (桶,世代)，取消按令牌世代落键）——从"事后对齐"变成"结构上不可能错" | S3 文档（术语对齐为"批次快照"） |
| A-2 | **按原因分类的取消（三态）** | 回加 vs 钉零的选择直接决定"过补偿自持环"（反复放量）是否出现；异步链路天然拿不到原因，只能盲回滚——这是我们保留同步模式的**技术理由之一** | S3 文档 |
| A-3 | **等式化的账 + 方向判据** | 把"账对不对"变成可计算（四条等式），并给出方向裁决：多钱=危险→止血，少钱=安全→只修。公开资料多是"比对差异 + 阈值告警"，缺这套"方向性" | S3 文档（术语对齐为轧账/平账） |
| A-4 | **亚秒定罪（三步当场确认）** | 大厂公开的实时对账目标仍在"小时级~准实时"，我们是同一轮内三步确认（新鲜重读 + 200ms 独立快照）→ 亚秒级 | S3 文档 |
| A-5 | **影子模式 + 熔断预算** | 自动修复先"只算不写"观察，再放开；连续失败熔断止损。是"让自动修复敢于上线"的工程手段 | S3 文档 |
| A-6 | **中断自愈协议（差额恢复/孤儿重放/额度段唯一键/封账看在途）** | "运行中开桶"路线的边界处理，等价于大厂"库存预分段"所需人工修复的自动化 | S3 文档（并与"预分段"路线做取舍对比） |
| A-7 | **先红后绿的方法学** | 每条修复先让它红、再让它绿；红灯用例池成为防回归资产（已实锤：修 L44 时旧用例抓住新引入的错误） | 全阶段通用（写进工程流程章） |

## 三、清单 B：该补的（业界有、我们没有，按新路线归位）

| # | 缺什么 | 归到哪 | 优先级 |
|---|---|---|---|
| B-1 | **异步落库模式**（预扣 → MQ → 受理号 → 消费落库 + 回滚策略） | **S3** | 高（S3 正题） |
| B-2 | **消息顺序性**（分区键）或明确声明"无顺序依赖" | **S3** | 高（一行代码 + 一段论证） |

| B-4 | **压测对比数字**（同步 vs 异步：QPS/失败率/P99/DB 峰值；对齐大厂公开数字口径） | **S3 验收** | 高（学习展示价值大） |
| B-5 | **热点 key 探测**（滑动窗口统计 → 提升到本地缓存） | S4/S6 之后（后置批） | 中 |
| B-6 | **多级缓存**（Nginx 层/Redis 层）+ 多实例失效广播 | 后置扩容批（原 L16） | 低 |
| B-7 | **预案/开关平台 + 1-5-10 度量**（一键降级/切流/限流） | 后置治理批 | 低 |

| B-9 | **调用级熔断**（依赖 Redis/MySQL/MQ 异常比例 + 慢调用 + 半开） | **S2**（Resilience4j） | 高（可用性） |

## 四、清单 C：明确不做的（写清理由，避免"看起来漏了"）

| # | 不做 | 理由 |
|---|---|---|
| C-1 | **跨机构对账**（多级模糊匹配、Spark 分片并行、差异工单、追款闭环） | 那是"两个独立主体之间对账"的形态（平台 vs 银行/渠道）；我们是单系统内部两个存储的自洽问题，用等式即可，硬套会变成过度设计 |
| C-2 | **2PC/XA 分布式事务** | 业界共识：同步阻塞、协调者单点、高并发不用；我们选本地消息表 + 对账兜底 |
| C-3 | **CDC 链路**（Debezium 监听 binlog 投递） | 已有 outbox 且已跑通；CDC 引入新组件与新故障面，收益（无侵入）在本项目不成立（我们可以直接改代码） |
| C-4 | **模型类算法**（预算最优分配 MCKP 求解器、Uplift 因果模型、随机森林根因分类） | 需要样本、特征平台与实验设施；我们做**规则版**（预算闸门/速率控制/分位数筛选），并把分配策略抽成接口留扩展点 |
| C-5 | **真 CDP/数仓**（离线标签加工、OneID、实时特征） | 我们做"标签消费方"（通过端口取标签），不做"标签生产方" |
| C-6 | **商用风控模型/人机识别** | 需要外部服务与合规；我们做规则版（设备指纹 + 名单 + 频控 + 验证码位） |
| C-7 | **税务/发票联动**（分账的应税收入调整） | 属财务系统职责；我们只在文档里标注"优惠成本分摊对发票金额有影响，需财务侧联动" |

## 五、结论（一句话）

**P2 的可靠性体系按业界标准看是"同款 + 超纲"，不缺基本功；真正缺的是"业务面"与"异步模式"。** 因此 ROADMAP-V2 的结构是：
**S1 接入（含治理插槽）→ S2 流量治理（瘦身版 + 增量清单）→ S3 发放链路对标重做（补异步 + 术语对齐）→ S4 算钱 → S5 钱的后半程 → S6 运营玩法 → S7 风控 → S8 计与复盘**，
P2 的资产**保留并按大厂术语重整**，"超纲项"作为亮点写进教学文档，"不做项"写进本文档第四节。
