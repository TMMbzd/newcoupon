# 大厂优惠券/秒杀库存的完整做法——资料调研（2026-09-17）

> **调研背景**：用户质询"前端显示已抢完，第一个请求怎么发出来触发当场修？大厂完整做法是什么？"——本文档全部内容来自公开资料（每条带出处），先给结论总表，再逐项展开，最后对照我们的系统标出"已有/已立项/缺失"。

## 0. 先回答触发问题的核心：大厂的"售罄"信号是**短过期的**，不是永久的

调研后最关键的发现：大厂/主流方案的"售罄标记"几乎都带**短过期时间（1~2 秒）**，而不是立一个永久标志。这直接回答了"回补后前端怎么知道又能买了"——标记自己会过期，过期后重新查 Redis，Redis 回补了就恢复按钮。

| 来源 | 售罄信号 | 过期机制 |
|---|---|---|
| [阿里云官方秒杀文档](https://help.aliyun.com/zh/document_detail/2860128.html) | 本地缓存（商品信息+剩余库存） | **1 秒过期**；RocketMQ 消息广播通知集群刷新 |
| [博客园·秒杀场景如何通过Redis减库存](https://www.cnblogs.com/javastack/p/16334831.html) | JVM 内存 Map（isOverMap） | **无过期——是公认缺陷**（文章未讨论，回补后 Map 挡住请求） |
| [腾讯云·高并发防超卖少卖](https://developer.cloud.tencent.com/article/2705635) | Lua 归零返回失败 + 售罄标记 | 回补时 `incrby` + **同时删除售罄标记**让商品重新上架 |

**结论**：大厂的真实做法是"**售罄信号短 TTL + 回补时主动清除**"双保险——短 TTL 保证就算清除消息丢了，1~2 秒后也会自愈。

## 1. 分层拦截链路（阿里云官方文档的完整版）

[打造高性能秒杀系统（阿里云官方）](https://help.aliyun.com/zh/document_detail/2860128.html)给的完整分层：

| 层 | 手段 | 作用 |
|---|---|---|
| 客户端 | 动静分离（CDN 承接静态）/ 活动时间外禁用按钮 / 验证码 / 3 秒限点一次 | 挡掉最大量无效流量 |
| 接入层 | SLB 限流（限流值由 PTS 压测确定） | 超额请求在网关直接拒绝 |
| 应用层 | 秒杀系统独立部署 / 1 秒本地缓存挡读 / Redis 原子预扣挡写 | 读走本地缓存，写走 Redis |
| 数据层 | Lua 原子扣减 / CAS 条件更新 / Redis Cluster / PolarDB | 最后防线 |

**关键细节**：商品动态信息（价格、剩余库存）由**异步 Ajax 获取**（不是页面静态渲染时写死）；本地缓存 1 秒过期 + **RocketMQ 消息广播"通知集群刷新缓存"**——即售罄状态变化通过消息广播推给所有应用节点刷新本地缓存。

## 2. 阿里 Inventory Hint：百万 QPS 级的终极形态

[阿里 Inventory Hint 技术分析](https://www.cnblogs.com/Johny-zhao/p/18914456)（应对秒杀百万 QPS 的"核心法宝"）：

- **逻辑分片**：总库存划分成 N 个逻辑分片（非物理分库），分片 ID 和额度**提前推送缓存到应用层各节点**；
- **本地内存扣减**：应用节点本地的 LocalHint 是"乐观额度"（非实时精确值），扣减是**纯内存操作**——决策权下沉到应用服务器，中心存储访问变成异步批量确认；
- **异步仲裁**：本地扣减后立即返回"抢购排队中"，扣减请求进 RocketMQ/Kafka；库存服务层消费 MQ 做强一致最终扣减（查 ActualStock → DECR），失败通过异步消息**回滚 LocalHint 或使分片失效**（防"超卖幻觉"）；
- **防超卖**：Sum(LocalHint) ≤ ActualTotalStock（保守分配）+ 中心库存强一致仲裁；
- **防少卖**：失败反馈回滚额度 + 按历史成功率动态调整分配。

这是"把 Redis 也变成瓶颈之后"的下一级——我们的路线图 M3 压测后再谈。

## 3. 售罄后的恢复/回补（三个来源拼出完整闭环）

**来源一：[腾讯云·高并发防超卖少卖](https://developer.cloud.tencent.com/article/2705635)（618 项目实证）**
- **兜底查询**："当 Redis 库存为 0 时，再查一次数据库"——**防止 Redis 数据丢失导致误判售罄**（= 我们立项的"假售罄急救"，大厂确实这么干）；
- **取消回补**：Lua `incrby` 回补库存，**同时删除售罄标记让商品重新上架**；
- **超时回滚**：RocketMQ 延迟消息（≈30 分钟）检查未支付订单，原子回滚 Redis 库存并取消订单；
- **多层对账**：凌晨全量核对"订单支付数 vs 库存扣减数" + **每小时增量对账"Redis 库存 = DB 可用库存"，不一致时以 DB 为准修正 Redis**；
- **实时对账**：定时任务每隔几分钟核对 Redis 与 DB 差异，"发现异常丢失立即修复"；
- **库存分片**：1000 件拆 10 个分片 key，一个分片扣完自动尝试下一个——避免单分片售罄造成其他请求误失败。

**来源二：[发券高并发库存扣减方案落地](https://www.cnblogs.com/papering/p/16634825.html)（春节活动 400 万张实证）**
- **固定步长预扣**：不放全部库存进 Redis，从数据库申请固定步长（如 1 万），扣完再申请下一批——400 万张发券只打 400 次 DB；
- 双重检查锁保证"DB 扣 + Redis 加"原子；步长固定，未来按发放量/QPS 动态化。

**来源三：[美团到家商品库存演进](https://juejin.cn/post/7054450547654393870)（美团高级技术专家分享）**
- 三阶段：MySQL 同步扣减（初期）→ Redis 同步扣减 + **监听 AOF 异步同步 MySQL**（万级 TPS）→ 平台化；
- 最终一致性：**双通道流水校验 + 库存校正处理**（应对主从切换丢数据）；"如果 redis、库存异步服务数据丢失，那就**重新加载**"（= 我们的懒重建）；DTS 监听 binlog 双通道保障。

## 4. 前端到底怎么知道"已抢完"

综合全部资料，大厂前端展示的真实做法（不是一个答案，是三种并存）：

| 做法 | 描述 | 出处 |
|---|---|---|
| **点击后告知**（最普遍） | 按钮可点，点了后端返回"已抢完"——服务器是裁判 | 阿里云官方文档（"若 Redis 库存不足则直接返回错误信息"） |
| **短 TTL 本地缓存** | 剩余库存进 1 秒本地缓存，前端 Ajax 异步获取；状态变化时 MQ 广播刷新 | 阿里云官方文档 |
| **轮询** | 前端定时轮询库存/订单状态（间隔与终态设计参考支付宝轮询文档） | 多篇 |

**注意**：调研中**没有找到**"前端按钮基于 Redis 库存数永久置灰"的大厂方案——因为永久置灰会堵死回补后的恢复。置灰主要用于"活动未开始/已结束"（时间驱动，不是库存驱动）和"点击后防重复提交"（3 秒限点）。
