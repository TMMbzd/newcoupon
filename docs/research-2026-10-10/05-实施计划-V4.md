## 三、开工前必须讲透的三个诚实话

### 1. "异步"的正确切口（第 4 条要求的工程修正）

你要库存改异步——方向采纳，但一手证据显示切口要摆对：
- **vivo 官方原话**："领券是实时的（异步的话，不能实时将券发到用户账户下，影响到用户体验和券的转化率）"。字节 13 万 QPS 的券系统主链路也是同步的，扛量靠分库分表而不是异步。
- **真正的异步在两处**：①**落库异步**——用户请求即时返回"受理成功"，券的落库由"发放任务表+消息队列"在后台完成（vivo 库存系统的官方方案，与本项目已有的发件箱模式同构，可靠性机制现成）；②**批量发券全异步**——运营给一万个用户发券，拆任务、限速、批量写。

**V4 的做法**：领券 = Redis 原子预扣（即时返回受理）+ 同一事务写发放任务表 + 消息队列异步落库 + 受理状态查询接口；同时保留"同步/异步"配置开关。**与 vivo 生产形态的差异**（我们让落库异步化以演示完整异步链路，且没有真实转化率约束）会写成一份显式决策记录——这样面试被问"业界明明是同步落库，你为什么异步"时有话可答，而不是自相矛盾。

### 2. 工期真相（第 8、10 条的连带后果）

前端（16~21 天）+ 安全补全（约 10 天分散在各步）叠加后，V3 的 23~29 天不再成立。按本项目真实节奏（每步含测试回归、审查往返、教学文档，历史数据校准）：
- **全天档**（每天 6~8 小时有效投入）：核心 52~68 个有效日 + 15% 缓冲 ≈ **60~78 个有效日**（日历约 3.5~4.5 个月）
- **半天档**（每天 3~4 小时）：约 **5.5~7.5 个月**
- **投简历节点**：第 5 步结束时（第 27~35 个有效日）——那时后端全量能力+证据链已成立，前端与投递并行推进，不必等全部做完。

### 3. "前端分配工程师"的转译

本项目没有真实的前端团队，前端将由**你 + AI 以工程师工作流承担**：契约先行（后端先冻结接口文档）、类型自动生成（接口一变前端立刻编译报错）、组件化、进 CI 门禁。这套工作流恰好就是"如果明天真来一个前端工程师，他第一天就能接手"的形态。工期后果见上一条（诚实话说在前面：真实 SPA 前端约为此前"降级版"估价的 8 倍工作量）。

### 第 0 步：修复地基（1.5~2 天）——一切的前提

**背景**：昨天开工的优惠计算代码留下了一段半失败的数据库迁移脚本（它想把券模板表加五个新列，但执行到一半失败，数据库迁移账本里留了一条失败记录，导致**当前工作区所有依赖数据库的测试全部起不来**），且代码里有一处会算错钱的硬编码。

| # | 工作项 | 详情 |
|---|---|---|
| 0-1 | **撤销坏迁移、恢复测试全绿** | 做什么：删掉那段迁移脚本文件（从未提交过 git）+ 删数据库迁移账本里的失败记录 + 重跑全部测试。怎么做：删文件 → 数据库执行一条 DELETE 清失败登记 → `mvn clean test`。参考：本项目数据库迁移用 Flyway 管理（带编号的建表/改表说明书，失败记录不清除则拒绝启动）。为什么：四个新列与券模板表第一天就有的三列（类型/面额/折扣上限）完全重复，回填语句还把"满 100 元可用"的门槛值当成了"减 100 元"的面额——十倍错误。验收：442 个测试全零失败的输出留档 + 全程截图。 |

### 第 2 步：券模板五维模型 + 算钱闭环（9~12 天）⭐ 业务核心

| # | 工作项 | 详情 |
|---|---|---|
| 2-0 | **小调研：租户接入旅程**（0.5 天） | 做什么：查清企业接入一个开放平台的标准旅程（自助注册还是邀请、审核流、协议条款、接入引导页、对账单形态）。参考：微信支付/支付宝开放平台的商户接入公开流程。为什么：你第 1 条"企业可注册接入并使用"的验收本体，缺了它只能按想象设计。产出：接入旅程图 + 接入指南大纲 + 模拟租户全流程走通脚本（在第 6/8 步的页面里兑现）。 |
| 2-1 | **券模板五维模型** | 做什么：新建迁移（与读写代码同批提交，杜绝"只有表没人用"）：在既有"类型/面额/门槛/折扣上限"之上补四个维度——**作用范围**（全场/品类/指定商品）、**叠加层级**（店铺级/平台级）、**互斥组**（同组只能用一张）、**出资方**（平台出/商家出/按比例共担）；建券表单与引擎同批接通。怎么做：模板三段式字段（领取规则/使用规则/使用效果）+ 五个正交维度列。参考：yudao 开源项目的券模板三段式（一手源码，已核实）+ 京东东券三分类/抖音平台券·商家券分类（官方规则页）。为什么：这是"中台"与"单店券系统"的分界——没有出资方和互斥组，分账与叠加都无从谈起。验收：建一张"平台出 70% 商家出 30%、限食品品类、平台级、互斥组 A"的券，全流程可查。 |
| 2-2 | **计价引擎：分层责任链 + 同层择优 + 分摊** | 做什么：按固定层级顺序编排计算节点（骨架按八层位次建模：单品级→限时折扣→满减→商家券→平台券→积分→运费→收尾；**本期实装商家券+平台券两层+收尾守恒断言**，其余层留接口并写明点亮条件）；同层互斥组内"优惠金额大者胜"；优惠按商品行金额比例分摊，前 n-1 行取整、最后一行反减兜底、断言分摊之和=券面额且每行≥0；金额全程整数"分"。参考：yudao 计价责任链源码（ORDER 常量+择优实现+分摊算法，一手可抄）；有赞官方帮助页的优惠顺序（会员价>满减送>优惠券>积分）；抖音官方叠加规则通知。为什么：一手调研证实分层顺序计价是业界生产主形态，没有任何公司用动态规划求全局最优。验收：多商品订单算出最优券+到手价+每行分摊，与手工核算一致。 |
| 2-3 | **核销由平台算钱** | 做什么：核销请求改为携带商品行明细，平台自己算优惠并落库（金额不再由调用方传入）；老调用方（只传金额）保留过渡兼容。为什么：试算接口只是半成品——核销时钱还是调用方说了算的话，"平台算钱"就是空话（面试一问就穿）。验收：核销后数据库里的优惠金额=平台计算值，可逐笔查证。 |
| 2-4 | **出资拆分 + 申报防线**（中台特有） | 做什么：核销时把每笔优惠按出资方拆成两行（平台 X 元 + 商家 Y 元，X+Y=总优惠的守恒断言）；**申报防线**——门槛由服务端复算（不信调用方的判定）、单笔优惠金额设合理性上限（如不超过订单金额的 N%）、异常申报速率告警、核销前后快照进审计。为什么：批评家抓出的资损级信任边界——接入方虚报订单金额即可放大平台出资；开源样本没有此问题（订单在自己域内），业界无现成参照，必须自建。验收：虚报金额的测试请求被拦 + 出资拆分守恒用例全绿。 |
| 2-5 | **配置期校验** | 做什么：券模板保存/发布时，用与结算同一套计价器对模拟订单重放，输出"为什么不可用"的明文原因清单 + 保底价校验（折后价低于阈值则拦截上线）。参考：yudao 的不可用原因四件套（一手）。为什么：优惠错配是大促资损主因，事前拦截比事后对账便宜。验收：造一个"叠加后击穿保底价"的模板被发布拦截。 |
| 2-6 | **质量与教学收尾** | 10 条黄金用例全绿（先红后绿取证）+ demo 脚本扩展"折扣券建券→试算→核销→分摊查询"端到端 + 设计期 3 视角审查 + 实现后对抗审查 + 教学文档一篇（讲解+面试刁难卡）。 |

|---|---|---|
| 3-1 | **领券异步受理链路** | 做什么：Redis 原子预扣即时返回"受理成功" + 同一数据库事务写发放任务表 + 消息队列异步落库 + 受理状态查询接口（三态：成功/失败/处理中）+ 轮询防风暴（查询接口独立限流、终态写缓存、客户端指数退避）。同步/异步按模板配置开关。怎么做：任务表极简（主键+载荷），消费幂等复用既有唯一索引机制。参考：vivo 库存方案二（官方，与本项目发件箱同构）；第三节诚实话 1 的决策记录。验收：异步模式全生命周期与同步模式结果一致；超发 0；重复发放 0。 |
| 3-2 | **库存简化** | 做什么：默认每模板单 key 扣减；桶退化为纯 key 数组（随机不重复轮询+耗尽跳过），删除世代号；单 key 写入逼近万级 QPS 才按开关开桶。参考：字节实测（Redis 单分片写约 2 万 QPS）+ vivo"低量级不分桶"一手反例。为什么：你判断的过度设计成立——量级判断先于机制堆叠。验收：单 key 模式压测通过 + 开桶开关可演示。 |
| 3-3 | **批量与定时发放 + 预算硬顶** | 做什么：人群名单批量发券（任务分片进队列+消费限速实测选型+按分表归集批量插入+失败重试+进度查询）；定时发放；**预算闸门**——模板挂总预算/日预算，发放前校验、耗尽即拦、超额告警。参考：vivo 亿级定向发券官方复盘、得物"发券四道闸"（规则/预算/幂等/防超发——本项目唯一缺预算这道）。验收：批量发 1000 人幂等只发一批 + 预算耗尽被拦脚本可实跑。 |
| 3-4 | **轻对账三件套** | 做什么：①差错表（场景/批次/错误类型/状态）②准实时配对（发放流水 vs 券记录，残留即漏发，轮询输出告警）③T+1 总数核对（流水数=券记录数=Redis 已扣数）；自动修复只做补发/回收两种，其余告警人工；二次核对防日切误报；新增表的运行时治理（扫描索引、归档清理、水位指标）。参考：美团官方对账体系建设（"漏结/重复结/错结"三分类原文）。为什么：替代守恒巡检的业界标准形态，也是退役的前提。验收：人为注入漏发/重发/错发，对账实抓三类（复制"防线失效必须看得见"的断言模式）。 |
| 3-5 | **旧体系灰度退役** | 做什么：新旧对账在重叠流量上双跑一个账期核对一致 → 关闭守恒巡检 → 删世代/巡检代码（约 1500 行）→ 出退役报告（含被删测试用例清单与理由——测试总数变化属预期，逐条列明不冒充回归）。为什么：直接切换会把"返工红"与"迁移红"混在一起；永久并存则重蹈复杂化覆辙。验收：退役报告 + 三条脚本（demo/反例/演练）全 PASS。 |
| 3-6 | **T+1 出资日账单** | 做什么：定时任务按租户/出资方汇总发放/核销/回退，只读查询接口。参考：美团门店日账单 T+1 可查。验收：账单数字与数据库手工核算一致。 |
