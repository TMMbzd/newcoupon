## 三、开工前必须讲透的三个口径

### 1. "异步"的正确切口（第 4 条要求的工程修正）

一手证据（三家公司官方复盘互证）：
- **vivo 官方原话**："领券是实时的（异步的话，不能实时将券发到用户账户下，影响到用户的体验和券的转化率）"。字节 13 万 QPS 的券系统主链路也是同步的，扛量靠分库分表而不是异步。
- **真正的异步在两处**：①**落库异步**——用户请求即时返回"受理成功"，券的落库由"发放任务表+消息队列"在后台完成（vivo 库存系统的官方方案，与本项目已有的发件箱模式同构，可靠性机制现成）；②**批量发券全异步**——运营给一万个用户发券，拆任务、限速、批量写。

**V4 的做法**：领券 = Redis 原子预扣（即时返回受理）+ 同一事务写发放任务表 + 消息队列异步落库 + 受理状态查询接口；同时保留"同步/异步"配置开关。**与 vivo 生产形态的差异**（我们让落库异步化以演示完整异步链路，且没有真实转化率约束）会写成一份显式决策记录——这样面试被问"业界明明是同步落库，你为什么异步"时有话可答，而不是自相矛盾。

### 2. 执行节奏：两条线分开走（原"工期真相"口径作废）

**原来的工期表假设"你写代码"——现在代码与文档的时间由 AI 连续承担，你的时间只剩"消化文档"**。所以：
- **执行线（AI）**：以"环"为交付单位不间断推进——每环 = 代码完成 + 环文档包交付 + 提交 + 状态同步。总量一环不减（不偷工减料），测试回归、多视角审查、文档撰写全部保留——这些是质量成本，不是人的日历成本。
- **学习线（你）**：对着环文档包按自己的节奏学，**学习进度不阻塞执行线**。每环文档自包含，跳着学或回头学都不影响。
- 投简历节点：第 5 步末（业务闭环+安全账号+可观测与压测证据齐备时），与之前口径一致。

### 3. 前端定位与文档规格（你第 2、10 条的落地方式）

**前端定位**：展示与体验的载体——让你学后端文档时能对着真实界面点（不用抽象想象每个接口），也让外人 clone 即见"成品感"。由 AI 按完整工程标准直接做出来（契约先行、类型自动生成、组件化、进 CI 门禁——这些**工程标准不降**，降的只是"你要花时间学它"）。你从前端得到的是《使用指南》：页面地图、每页对应的后端能力与接口、怎么点、点完数据库里发生了什么。

**环文档包（每环交付的四件套，第 10 条的制度化）**——达到"不翻源码、不猜运行"的标准：

| 件 | 内容 | 验收标准 |
|---|---|---|
| ① 变更说明 | 这环做了什么、为什么这么做（含业界对标与出处链接）、哪些旧内容变了 | 只读这一篇就能向别人复述这一环的设计取舍 |
| ② 可跟跑指南 | 环境准备→命令原文→**真实输出**→怎么读→失败看什么 | 复制粘贴能跑出同样结果；预期输出与真实输出明确区分 |
| ③ 代码走读 | 该环核心路径**完整走读**（小段贴码+逐段讲解+调用时机+每段"为什么"），延续项目"逐段代码讲解"的正典风格 | **读文档 ≈ 读过源码**；源码位置仅作"想深入再去"的指引 |
| ④ 自测卡 | 只考文档讲过的，每题带答案，第一题送分 | 学完即可自检 |

（沿用既有教学硬约束：术语首现即解释、每节末"容易混淆的地方"、禁自造词与强调词、写后机械自查门。）

### 第 2 步：券模板五维模型 + 算钱闭环 ⭐ 业务核心

| # | 工作项 | 详情 |
|---|---|---|
| 2-0 | **小调研：租户接入旅程** | 做什么：查清企业接入一个开放平台的标准旅程（自助注册还是邀请、审核流、协议条款、接入引导页、对账单形态）。参考：微信支付/支付宝开放平台的商户接入公开流程。为什么：你第 1 条"企业可注册接入并使用"的验收本体。产出：接入旅程图 + 接入指南大纲 + 模拟租户全流程走通脚本（在第 4/7 步的页面里兑现）。 |
| 2-1 | **券模板五维模型** | 做什么：新建迁移（与读写代码同批提交，杜绝"只有表没人用"）：在既有"类型/面额/门槛/折扣上限"之上补四个维度——**作用范围**（全场/品类/指定商品）、**叠加层级**（店铺级/平台级）、**互斥组**（同组只能用一张）、**出资方**（平台出/商家出/按比例共担）；建券表单与引擎同批接通。参考：yudao 开源项目的券模板三段式（一手源码，已核实）+ 京东东券三分类/抖音平台券·商家券分类（官方规则页）。为什么：这是"中台"与"单店券系统"的分界——没有出资方和互斥组，分账与叠加都无从谈起。验收：建一张"平台出 70% 商家出 30%、限食品品类、平台级、互斥组 A"的券，全流程可查。 |
| 2-2 | **计价引擎：分层责任链 + 同层择优 + 分摊** | 做什么：按固定层级顺序编排计算节点（骨架按八层位次建模：单品级→限时折扣→满减→商家券→平台券→积分→运费→收尾；**本期实装商家券+平台券两层+收尾守恒断言**，其余层留接口并写明点亮条件）；同层互斥组内"优惠金额大者胜"；优惠按商品行金额比例分摊，前 n-1 行取整、最后一行反减兜底、断言分摊之和=券面额且每行≥0；金额全程整数"分"。参考：yudao 计价责任链源码（ORDER 常量+择优实现+分摊算法，一手可抄）；有赞官方帮助页的优惠顺序；抖音官方叠加规则通知。为什么：一手调研证实分层顺序计价是业界生产主形态，没有任何公司用动态规划求全局最优。验收：多商品订单算出最优券+到手价+每行分摊，与手工核算一致。 |
| 2-3 | **核销由平台算钱** | 做什么：核销请求改为携带商品行明细，平台自己算优惠并落库（金额不再由调用方传入）；老调用方（只传金额）保留过渡兼容。为什么：试算接口只是半成品——核销时钱还是调用方说了算的话，"平台算钱"就是空话。验收：核销后数据库里的优惠金额=平台计算值，可逐笔查证。 |
| 2-4 | **出资拆分 + 申报防线**（中台特有） | 做什么：核销时把每笔优惠按出资方拆成两行（平台 X 元 + 商家 Y 元，X+Y=总优惠的守恒断言）；**申报防线**——门槛由服务端复算（不信调用方的判定）、单笔优惠金额设合理性上限（如不超过订单金额的 N%）、异常申报速率告警、核销前后快照进审计。为什么：批评家抓出的资损级信任边界——接入方虚报订单金额即可放大平台出资；开源样本没有此问题（订单在自己域内），业界无现成参照，必须自建。验收：虚报金额的测试请求被拦 + 出资拆分守恒用例全绿。 |
| 2-5 | **配置期校验** | 做什么：券模板保存/发布时，用与结算同一套计价器对模拟订单重放，输出"为什么不可用"的明文原因清单 + 保底价校验（折后价低于阈值则拦截上线）。参考：yudao 的不可用原因四件套（一手）。为什么：优惠错配是大促资损主因，事前拦截比事后对账便宜。验收：造一个"叠加后击穿保底价"的模板被发布拦截。 |
| 2-6 | **质量与环文档收尾** | 10 条黄金用例全绿（先红后绿取证）+ demo 脚本扩展"折扣券建券→试算→核销→分摊查询"端到端 + 设计期 3 视角审查 + 实现后对抗审查 + **环文档包四件套**（含五维模型与计价链的完整代码走读）。 |

**学习线（你）**：对环文档包自定节奏；文档自包含、可跳读可回读。**投简历节点 = 第 5 环末**（第 5~9 个会话后：业务闭环+安全账号+可观测压测证据齐备）。

**若中途要调整范围**：降序砍第 7 环部分页面 → 第 8-1 风控深度 → 第 6-1 热配置（改冷配置）——**第 0/2/3/5 环不可降**。

## 六、工作纪律（七条）

1. 先红后绿（失败用例先写、输出留档）；2. 每环收尾四件套（提交+状态文件+工作日志+**环文档包**）；3. 设计期 3 视角审查 + 实现后对抗审查（必做）；4. 引用三重门（出处可点开+自己核过+登记）；5. **动钱先审计**；6. **退役走灰度**——删大件必须双跑比对+出退役报告；7. **文档不交付不开下一环**（环文档包是每环的验收项之一，不是事后补充）。
