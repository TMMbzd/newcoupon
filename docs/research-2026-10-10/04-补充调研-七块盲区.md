## 一、七条核心结论（主会话综合裁定版）

### 1. "异步"的正确位置——本轮最重要的反直觉发现

一手证据（三家公司官方复盘互证）：
- **vivo 官方原话**："领券是实时的（异步的话，不能实时将券发到用户账户下，影响到用户的体验还有券的转化率）"；真正全异步的是运营定向发券（亿级批量）。
- **字节 13 万 QPS 券系统官方复盘**：发券主链路是**同步的**（校验→幂等→Redis 扣减→券记录直接写 MySQL 分库分表），RocketMQ 只承担过期延迟等旁路；扛量靠分库分表+库存拆 key+本地二级缓存，不是异步削峰。
- **vivo 库存系统官方对比**：Redis 扣减与"库存任务表 insert"放**同一 DB 事务**，异步任务从任务表搬运到正式表实现最终一致且不丢数据——本质就是本项目已有的发件箱模式。

**本项目裁定**（回应指示④，与用户方向一致、切口修正）：个人领券 = Redis Lua 预扣**即时受理返回** + 同一事务写发放任务表 + MQ 异步落库 + 受理状态查询接口；批量/定时发放 = 全异步任务分片 + 消费限速；保留配置开关可切回同步模式。与 vivo 生产形态的差异（我们让落库异步化以演示完整异步链路；无真实转化率约束）写成显式决策记录。
**分桶量级依据**（回应指示⑥）：字节实测 Redis 单分片写约 2 万 QPS——**默认单模板单 key，单 key 写逼近万级才开桶**（随机不重复轮询+耗尽桶跳过）；vivo 一手反例证明低量级不分桶是正确克制。世代机制退役。

### 2. 轻对账蓝图（美团官方对账体系建设原文）

一致性问题只归三类：**漏结、重复结、错结**。形态：明细对账为主（发放流水 vs 券记录，准实时配对、残留即漏发）+ **总数对账兜底**（T+1 三数核对：流水数 = 券记录数 = Redis 已扣数）+ 统一差错表（场景/批次/错误类型/状态）+ 二次核对防日切误报 + 自动修复只做补发/回收两种、其余告警人工。**世代+守恒巡检+自愈整体退役**（所有一手材料无一用守恒证明做库存对账）；退役路径 = 配置开关双轨 → 故障注入演练证明新对账实抓三类差错 → 双跑核对 → 出退役报告。

### 3. 安全 = 六层纵深（回应指示③，S1 资产零返工）

边界层（TLS 终止于 nginx，/open 与 /console 两入口分流）→ 认证层（机器面沿用 HMAC 签名链；**人工管理面新增 Spring Security 6**——自有过滤器只做认证、授权交框架，密码 BCrypt+失败锁定+渐进验证码）→ 授权层（RBAC 三表管功能权限 + 租户归属管数据权限，SQL 层强制）→ 数据层（敏感字段 AES-GCM+密钥版本路由，复用既有密钥表；展示脱敏）→ 审计层（注解+AOP 六要素：谁/何时/何处/何事+前后快照+traceId/IP，异步落库+哈希链防篡改）→ 业务防线层（OWASP API6 官方把"优惠券薅羊毛"点名为敏感业务流：配额/限流+预算硬顶+异常速率告警）。**OWASP API Security Top 10（2023）十项直接当验收清单逐项对表**。最优先补洞（已一手核实）：管理面令牌过滤器只保护显式列举的两个路径前缀、漏列即无鉴权写口——改为"非 GET 默认必须校验+显式例外"+结构性测试，随修基线顺手关闭。**新纪律：动钱先审计**——算钱闭环开工前先落操作审计最小版。

### 4. 前端 = Vite + React 18 + TS + AntD 5 自组（回应指示②）

不整套采用 Ant Design Pro（umi）：维护者官方 issue 自述"主要就我一个人维护"（一手）、dev server 内存与 WSL 6.6G 真实冲突。权限模式抄 AntD Pro 官方 access 模式（一手文档）；契约层 = springdoc 出 OpenAPI → openapi-typescript 生成类型化请求层进 CI；图表 ECharts；nginx 托管静态包+反代，与后端同 compose。页面清单：**租户后台 8 页**（登录/接入引导/工作台/券模板规则表单/发放管理/券码与核销记录/预算与日账单/成员角色）+ **平台后台 6~7 页**（登录/租户审核与密钥/概览看板/跨租户审计/批次监控/风控命中/治理只读）。工期（计入本项目纪律成本）：**15~20 个有效日**，分两批（租户最小闭环先行 6~8 天早可用）。备选（触发条件明确）：若以国内 B 端就业为唯一导向且接受 Vue，用 soybean-admin（权限/刷新令牌/Docker 全内置，省 2~3 天骨架期）。

### 5. 分布式 = 双实例先行的"决策表"（回应指示⑨）

立即做：Micrometer Tracing + Zipkin（Boot 3.3 官方组合，自研 traceId 对齐 MDC 双轨兼容，压测时采样率调 1.0）；nginx 双实例 + 优雅停机演练（SIGTERM→宽限期→摘流，滚动重启零 5xx 取证）；Caffeine 多实例失效广播（JetCache 官方 BOTH+syncLocal 同款语义，或自研约 50 行 Redis pub/sub）——这是双实例正确性的前置件。**明确不引**（各写触发条件+版本锚点进"分布式决策表"）：Nacos/SCA（触发=拆出第二个可部署单元；届时锚定 SCA 2023.0.3.4+Spring Cloud 2023.0.x，已知坑：HealthIndicator 默认关闭、优雅停机须 ≥2023.0.3.4、用 spring.config.import）、Spring Cloud Gateway（限流鉴权已在应用层闭环）、Seata/TCC（已有发件箱；触发=拆独立账务服务且要同步强一致）、K8s（WSL 跑不动控制面；简历口径"知边界、能迁移"）。**这张决策表 + 演练证据就是指示⑨的交付物，而不是引入更多中间件。**

### 6. 规则引擎与券抽象 = 自研责任链 + 条件引入表达式引擎（回应指示⑤）

- **计价骨架自研责任链**：一手范本 = yudao（ruoyi-vue-pro）的 TradePriceCalculator——ORDER 常量固化层级顺序、每类优惠一个 Bean、同层互斥择优有真实代码实现（"会员折扣和限时折扣冲突，选优惠金额多的"）、分摊算法 dividePrice（按比例、前 n-1 项取整、末项反减兜底、断言非负、全链路用分）。官方顺序锚点：有赞官方帮助页"会员价 > 满减送 > 优惠券 > 粉丝专享价 > 积分抵现"；抖音 2023 新增+2026-09 修订的叠加规则通知（平行/递进满减、层级与优先级）。
- **券模板五维模型**：模板/实例分离 + 三段式字段（领取规则/使用规则/使用效果）+ 五个正交维度：**优惠类型 × 作用范围 × 叠加层级 × 互斥组 × 出资方**——在 yudao 已验证字段之上补齐后三列（开源项目都缺，正是中台差异点）。满折券强制带上限（在途代码踩过的坑）。
- **表达式引擎条件引入**：QLExpress 4（阿里官方场景第一条就是"电商优惠券规则配置"）或 Aviator（decimal 高精度+沙箱）——**仅当结构化规则不够表达时才引**；LiteFlow/Drools 本体不引（Drools 是推理型 40+ 模块全家桶，与本场景错位）。规则=数据：存库+版本+审核+60 秒轮询热刷新（LiteFlow SQL 插件默认值同款）。
- **组合爆炸三件套**（不做全局最优枚举）：限张（默认 1 商家券+1 平台券）+ 层内只比金额不比组合 + 固定层级顺序——组合空间从 2ⁿ 压到线性。

### 7. 上线标准 = 证据物 1~10（回应指示⑧）

测试基线报告（全绿输出绑 commit）→ 覆盖率报告（JaCoCo 门禁：存量 ≥70% 只查不升、**新增资金路径 ≥90%**——Google 官方口径）→ CI 质量门（四项 required checks + 分支保护）→ SLO 声明表（领券/核销/算钱各一行：可用性+P99+测量口径）→ Grafana 四大盘（发放流量/核销成功率/算钱分摊守恒/库存与积压水位）→ **压测报告七模块**（概述/策略/指标/拐点/资源水位/归因/结论——对标美团 Quake 要素，含错误率拐点与降级触发实录，诚实标注单机口径）→ 恢复演练记录（mysqldump 全备+binlog 重放 PITR，记实测 RTO）→ 上线检查单（Google LCE 六主题裁剪约 20 条，每条附证据链接）→ 告警演练记录（多窗口多燃烧率 Page/Ticket 两级，SRE Workbook 参数表）→ 契约回归证据（OpenAPI 快照回归，替代 Pact——官方口径单体场景收益边际）。

## 二、批评家新增发现（两评委均未覆盖，已并入 V4）

1. **算钱申报防线（资损级信任边界）**：本项目是中台——核销时订单明细由接入方申报、而出资方含平台，**接入方虚报订单金额即可放大平台出资**。开源样本（订单在自己域内）不存在此问题，业界无现成参照。V4 算钱步必须新增：门槛服务端复算（不信调用方判定）、单笔优惠合理性上限、异常申报速率告警、核销前后快照入审计。
2. 责任链八层位次建骨架、本期只实装两层（商家券/平台券）+守恒断言，其余层位留接口+触发条件表——避免六个永远空转的扩展点。
3. 受理轮询防风暴（轮询 QPS ≈ 峰值×频率×未完成率，削峰会变二次峰）：独立限流+客户端指数退避抖动+终态写 Redis。
4. 异步化新增表的运行时治理（扫描索引/归档清理/水位指标进压测报告）。
5. 双实例时钟一致性（验签时间窗/对账切日一律取服务端单一时钟）。
6. 三个开工前小调研（各半天）：租户接入旅程（指示①的验收本体）、退款场景矩阵（第 7 步前）、平台/商家按比例共担的自研推导（无一手样本，必须推导+测试自证）。

## 异步库存与轻对账

### 目标架构建议
推荐目标架构（括号内为证据强度）：领券/发券请求 → 开放层签名与限流 → 用户维度幂等（DB 唯一索引）→ Redis Lua 原子预扣：默认单模板单 key，仅当单 key 写 QPS 逼近万级（Redis 单分片写瓶颈约 2w，需留余量）才拆子库存 key+随机不重复轮询+耗尽桶跳过（字节 primary；vivo 反例证明低量级不分桶 primary）→ 预扣成功即受理返回，同一 DB 事务 insert 发放任务表（主键+载荷 json），MQ 通知消费者批量落库，任务表保证消息等价不丢（vivo 方案二 primary，与本项目已有发件箱同构）→ 消费幂等靠唯一索引；失败延迟重试，N 次进死信告警；用户回补同理，阈值后放行不阻断（vivo primary）→ 券模板进本地二级缓存+定时刷新，Redis 万分之 2~3 的超时不再打断发券（字节 primary）→ Redis 整体故障时降级为 DB 多行分桶条件更新（update where 余量>=n），牺牲吞吐保不超发（vivo 方案一改进版 primary）→ 对账轻量三件套：准实时配对（发放流水 vs 券记录，残留即漏发，轮询输出）+ T+1 总数核对（流水数=券记录数；Redis 已扣=流水数）兜底，差异归漏发/重发/错发三类，自动修复限补发/回收两种，其余告警人工，二次核对防日切误报（美团 primary）。MQ 不承担唯一削峰职责，分库分表+批量写才是主削峰（字节/vivo primary 综合）。

### 发现清单
- **字节 10万级QPS 券系统的主链路形态（2022-04 官方复盘）**（primary, https://juejin.cn/post/7087824893831544845）：发券主链路是同步的：参数校验→幂等校验(MySQL)→库存扣减(Redis)，券记录直接写 MySQL（按 user_id 后四位分表），RocketMQ 只用于券过期延迟消息（超长有效期循环投递）。扛 13w QPS 压测、99.9%+ 成功率靠分库分表+库存拆 key+本地二级缓存，不是异步削峰。服务治理：RPC 内部 100ms/接口超时 500ms、Grafana 监控、限流、资源隔离；压测=先找单实例/单主库/单分片瓶颈再估算资源，线上资源=压测数据×1.5。
- **分桶的量级阈值（回答：到多少 QPS 才需要分桶）**（primary, https://juejin.cn/post/7087824893831544845）：字节实测：MySQL 单机写瓶颈约 4000 QPS（超过则 IO 时延剧增）、单表千万级后查询大降；Redis 单分片写约 2w QPS、读约 10w。12w QPS 集中同一券模板时需 ≥6 个 Redis 分片、30 个 MySQL 主库。结论：单 key 写 QPS 数千级以内时，分桶没有必要——这是『默认单 key、按量开桶』的直接依据。
- **热点分桶的正确形态与售罄判定（字节）**（primary, https://juejin.cn/post/7087824893831544845）：建券时对热点模板预拆 N 个子库存 key（key 尾带分片编号）；扣减时生成随机不重复轮询数组把请求打散到不同分片；每请求顺便记录各子库存剩余量，已耗尽的桶直接跳过（售罄判定优化，库存见底时响应不劣化）。文内明确否掉 key 备份方案：只适合读多写少，不适合发券大流量写场景。
- **Redis 扣减到 DB 落库的两种主流形态（vivo 官方对比）**（primary, https://cloud.tencent.com/developer/article/2238920）：方案一：Redis 扣完异步刷 DB——简单，但 Redis 宕机会丢扣减数据。方案二（vivo 秒杀库存实际采用）：Redis 扣减与『库存任务表 insert』放同一 DB 事务（insert 无寻址比 update 快，任务表极简=主键+json），异步任务从任务表搬运到正式库存表实现最终一致且不丢数据；本质=事务性发件箱。逆向回退基于 DB 扣减记录延迟重试，达到重试阈值仍无扣减记录则返回回退成功不阻断。
- **vivo 券系统刻意不用 Redis 扣券库存——避免过度设计的原文证据**（primary, https://www.cnblogs.com/vivotech/p/15117264.html）：vivo 券系统领券采用数据库扣减改进版：单库存字段拆成 M 行库存记录，随机选一行 UPDATE 分散行锁，定时任务同步已领数。理由原话：『从优惠券系统当前及可预见未来的流量峰值、系统维护性、实用性上综合考虑』。同一团队库存一文更直白：『我们目前线上的流量峰值还达不到会造成 redis 单片瓶颈的问题，为避免过度设计，只做了前置限流，没有进行 key 值的打散』。
- **异步发券的业界真实位置：异步在落库与批量，不在 C 端实时领券**（primary, https://www.cnblogs.com/vivotech/p/15117264.html）：vivo 原话：『领券是实时的（异步的话，不能实时将券发到用户账户下，影响到用户的体验还有券的转化率）』。真正全异步的是运营定向发券（亿级）：去事务、轻量化校验、内存预计算分库分表路由后批量插入（最多 M 次）、单次发券量/读库量/峰速参数动态可配。两篇官方复盘均无受理单/受理号状态机的公开描述。阿里云官方秒杀文档有 Redis 扣量→MQ→异步下单入库形态，但那是秒杀订单不是券。
- **轻量对账完整方法论（美团官方，可直接替代守恒巡检的蓝图）**（primary, https://tech.meituan.com/2018/03/21/balance-accounts.html）：一致性问题只归三类：漏结、重复结、错结。对账方式双向优先；粒度明细对账为主+总数对账复核兜底；时机离线 T+1 为主、在线为辅——在线分实时（耦合主链路可拦截）与准实时（binlog→Kafka→Storm，Redis List 配对：单据入 List、回单删 List，定时轮询残留即漏单输出告警，不可拦截但轻）。差错处理=统一差错记录(场景/批次/错误类型/状态)→二次核对防日切误报→自动修复或告警人工两档。背景：该系统 70% 事故是一致性问题。

## 安全全景

### 目标架构建议
六层纵深，每层独立可验证、失败必须可见。①边界层：TLS 终止于 Nginx/网关，仅暴露 /open 开放面与管理面两个入口，跨信任域内部调用重加密；②认证层：机器对机器沿用 S1 HMAC 签名链（不推倒），管理面的人走 Spring Security 6——自有过滤器只管认证、授权交 authorizeHttpRequests DSL，密码 BCrypt+失败锁定+渐进验证码；③授权层：RBAC 管功能权限，AppOwnership/租户条件管数据权限（行级隔离，SQL 层强制而非各处手写）；④数据层：敏感字段 AES-GCM 加密+key_version 路由轮换（S1 密钥表直接复用），展示层统一脱敏；⑤审计层：注解+AOP 记 before/after 快照与 traceId/IP，异步落库+哈希链防篡改，留存≥6 个月；⑥业务防线层：发券按 OWASP API6 定性为敏感业务流——配额/限流（Sentinel 已有）+预算硬顶+异常发放指标告警+风控闸。总原则：认证不重复造轮子（OWASP API2 明令），fail-open 必须带指标，防线条条可实测（本项目既有纪律）。

### 发现清单
- **OWASP API1:2023 BOLA（对象级授权失效，API 安全第一大风险）**（primary, https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/）：每个接收对象 ID 的端点都必须做对象级授权校验；『比对会话用户 ID 与 ID 参数』不足以覆盖 BOLA；对策=基于策略与层级的授权机制+在使用客户端输入访问数据库记录的每个函数里检查+用随机不可预测 GUID+编写授权机制测试（不让授权回归上线的门禁）。本项目 S1 的 AppOwnership 五条路径正是此模式，方向与官方一致。
- **OWASP API2:2023 失效认证**（primary, https://owasp.org/API-Security/editions/2023/en/0xa2-broken-authentication/）：登录端点与『忘记密码/重置密码』同等防护：防撞库限流必须比常规限流更严+账号锁定/验证码+弱口令检查；敏感操作（改邮箱/手机号）要求再认证；禁自造认证/令牌/密码存储（用标准）；API Key 只用于客户端认证、不得用于用户认证；校验 JWT 签名算法与过期时间（防 alg:none）；『OAuth 不是认证，API Key 也不是』。
- **OWASP API6:2023 敏感业务流不受限访问（发券场景的官方定性）**（primary, https://owasp.org/API-Security/editions/2023/en/0xa6-unrestricted-access-to-sensitive-business-flows/）：官方场景三即优惠券/积分薅羊毛（脚本自动注册刷返利）。防护双层：业务层识别敏感流（发券/核销/退款），工程层选机制——设备指纹、人机识别（验证码/生物特征）、非人类模式分析（加购到支付<1 秒）、封锁 Tor 出口与知名代理；机器直接消费的 B2B API（正是本项目开放面）因防护常缺位而更易被攻击，须单独加固。
- **OWASP API Security Top 10 (2023) 官方完整清单与 2019 差异**（primary, https://owasp.org/API-Security/）：2023 版十项：BOLA/失效认证/对象属性级授权失效(新)/不受限资源消耗/函数级授权失效/不受限访问敏感业务流(新)/SSRF(新)/安全配置错误/不当清单管理/第三方 API 不安全消费。对比 2019：过度数据暴露并入 API3，注入被移出（Web Top 10 已覆盖），新增三项直面业务滥用。可用作验收清单逐项对表。
- **Spring Security 6（Boot 3）与自研过滤器的融合而非推倒**（secondary, https://juejin.cn/）：主流融合模式：自定义 OncePerRequestFilter 只做『认证』（解析自有令牌→写入 SecurityContext），『授权』交给框架 authorizeHttpRequests DSL——认证与授权解耦，避免自研整套过滤器链重复造轮子（Boot 3 移除 WebSecurityConfigurerAdapter，SecurityFilterChain Bean 为现状）。对本项目=保留 HMAC/AdminToken 认证逻辑，外面包一层 Spring Security 授权面。注意：Spring 官方文档因网络限制未能直接读取，此条来自头部社区文章（多源一致）。
- **管理后台 JWT vs Session 取舍**（secondary, https://juejin.cn/）：JWT 痛点=注销/吊销困难+权限变更后旧令牌仍有效；补救=Redis jti 黑名单、短有效期 Access Token（5~15min）+Refresh Token 轮换。需要强制下线与权限实时生效的管理后台更推荐 Session，或短 JWT+Redis 状态校验的混合。纯 HMAC 机器面对照此逻辑：本项目签名含时间窗+nonce，机器面无需 JWT。
- **RBAC 与多租户行级数据权限**（secondary, https://juejin.cn/）：功能权限走 RBAC（用户→角色→权限点），数据权限靠共享表加 tenant_id/app_id 列+SQL 自动注入条件（MyBatis 拦截器）实现行级隔离；三种隔离强度（共享表+租户列 / 独立 Schema / 独立库）按租户规模选择。关键纪律：数据权限必须在 SQL 层强制而非每个 Service 手写（漏一处=越权口子——与本项目 L51/L61 的教训同源）。
- **账号安全：密码存储/登录锁定/验证码**（secondary, https://juejin.cn/）：密码 BCrypt/PBKDF2/Argon2 慢哈希（cost≥10），禁 MD5/SHA1；同账号连续失败 N 次（典型 5 次）锁定 15~30 分钟或升级验证码；IP+账号双维度限流防撞库；登录成功后重发会话 ID 防 Session Fixation；验证码渐进路径=图形→行为→风控无感（低风险直登/中风险加码/高风险拦截）。
- **操作审计日志设计（美团官方实践）**（primary, https://tech.meituan.com/2020/07/01/audit-log.html）：美团官方文章核心：四问（Who/When/Where/What）扩展为六要素——加操作前后数据快照（before/after）+上下文（traceId/来源 IP/UA）；审计日志区别于业务日志：面向事后追责与取证，必须防篡改、可回放、长期留存；落地=注解+AOP 自动采集+异步落库不阻塞主链路。注意：全文读取因工具网络错误未成，此条以检索摘要核实（含大段原文引用），未读全文。
- **审计日志防篡改方案对比**（secondary, https://juejin.cn/）：哈希链 H(n)=hash(H(n-1)⊕record)：实现简单、能检测事后篡改，但防不了整段删除重建；WORM 存储（对象存储一次写入不可变）法律效力强；区块链存证成本高适合跨机构。企业内部主流=哈希链+定期快照锚定+审计表权限隔离+备份不可变。
- **敏感数据加密与脱敏（蚂蚁/支付宝一手规范）**（primary, https://opendocs.alipay.com/）：支付宝官方《应用安全开发指南》：页面渲染的敏感数据（身份证/银行卡号/手机号）必须脱敏；证件号等敏感信息存储须 AES-128 加密；口令必须加盐慢哈希。为『脱敏是展示层职责、加密是存储层职责』的一手背书。注意：全文读取未成（工具域名拦截），以检索摘要核实。
- **密钥管理与轮换（多版本共存）**（secondary, https://juejin.cn/）：信封加密：主密钥 CMK 不落应用侧，应用持数据密钥 DEK 加密数据、DEK 本身被 CMK 加密后存储；轮换=新写入用新版本、旧密钥保留解密能力，解密按 key_version 路由——禁止『换密钥就重刷全表』；金融级加码：根密钥物理隔离、密钥使用全程审计、双人授权。本项目 S1 的 AES-GCM 多版本共存密钥表正是 key_version 路由模式，无需返工。

- 【复用——不推倒】S1 开放接入层全套即 OWASP API1/API2 的工程化实现：HMAC 签名链（canonical+恒定时间验签+注入防护）、时间窗+nonce 防重放（先验签再写）、Redis 故障 fail-closed、AppOwnership 五条越权防线、X-Client-Token 接入幂等、appId 配额 429+Retry-After——与官方对策逐条对得上，认证链零返工

- 【新增——结构性补洞，最优先】L61 判据反转：AdminTokenFilter 现保护『显式列举的路径前缀』，漏列=无鉴权写口；改为『/api/** 非 GET 默认必须校验+显式白名单例外』并加结构性测试（遍历所有写映射断言受保护）。半天工作量，随第零步返工顺手关闭；同族 L51（归属校验只覆盖模板/券两类，新增租户资源按清单补）
- 【新增——管理后台账号体系】与用户硬性指示②（前端管理后台）绑定实施：admin_user/admin_role/admin_user_role 三表 RBAC + Spring Security 6 授权面（自有 AdminToken 认证逻辑保留为过滤器写入 SecurityContext）；人用 Session 或短 JWT+Redis 状态校验（可强制下线），机器继续走 HMAC——两套并存不混用；密码 BCrypt cost≥10、连续失败 5 次锁定 15~30 分钟、登录成功重发会话 ID、登录事件入审计
- 【新增——操作审计】@AuditLog 注解+AOP 自动采集，记录六要素（Who/When/Where/What+before/after 快照+traceId/IP/UA），异步落库复用既有发件箱模式（同步落表已登记 L48 有触发条件）；防篡改起步=审计表权限隔离+哈希链（低成本低风险版），WORM 留给真实生产形态；时机=算钱闭环（V3 第一步）必须先有审计再动钱
- 【新增——数据安全】敏感字段加密随真实用户手机号入库时落地（AES-GCM+key_version，复用 S1 密钥表；展示层统一脱敏工具类）；L50 密钥到期自动失效（定时任务扫 status=2 AND expire_time<now）随运营需要；dev 明文 DB 密码外部化+环境矩阵（L20）随 CI 批次
- 【新增——依赖与配置治理】OWASP dependency-check 插件入 CI + Spring Boot 3.3.5 过支持期升级评估（L19），随 V3 第三步（Grafana+CI）同批；CORS 白名单（禁反射任意 Origin+Allow-Credentials 组合）、管理面 CSRF 按会话形态定——写接口默认开、纯 Token 头场景可关但 CORS 必须收紧
- 【新增——发券业务流防护（API6 收尾）】单用户限领与 IP 频控已有，补『租户日预算硬顶+异常发放速率告警』——V3 第二步（预算+异步受理）天然覆盖，把 API6 的双层模型（业务识别+工程机制）作为该步的验收清单
- 【新增——合规底线（知晓级，L26 更新）】个保法：接入指南加『数据采集告知/最小必要/委托处理协议』条款，由接入方承诺；等保不立项（学习项目、无真实用户数据，维持原裁定）但『审计记录留存≥6 个月、记录含时间/用户/事件类型/是否成功』两条国标要求直接吸收进审计表设计，零成本拿合规姿势
- 【顺序建议】①第零步返工时关 L61（越权口子，最优先）；②管理后台开建时同步引入 Spring Security 6 RBAC（防 AdminToken 临时方案长成永久）；③操作审计 AOP 随算钱闭环先行（钱动之前审计必须在）；④敏感字段加密随用户注册流程、密钥自动失效随运营需要；⑤依赖扫描随 CI；⑥合规条款随接入方上线。全部条目均有触发时机，不需要单独立大阶段

## 企业前端

### 目标架构建议
推荐：Vite 6 + React 18 + TypeScript + AntD 5 + @ant-design/pro-components 自组，不整套采用 Ant Design Pro（umi 锁定重、单人维护、dev server 吃内存，WSL 6.6G 下是真实风险）。权限抄 AntD Pro access 模式：src/access.ts 由登录用户生成 canXxx，路由守卫按 access 字段过滤+跳转，按钮用 Access 组件，菜单只渲染有权限项；权限点由后端 RBAC 接口下发（借鉴 RuoYi 权限串与 soybean 静态+动态路由双模式）。鉴权：access token 存内存，refresh token 走 HttpOnly+Secure+SameSite Cookie，请求层统一错误码处理（401 静默刷新、403 页、业务码弹窗）。契约：springdoc /v3/api-docs 经 openapi-typescript+openapi-fetch 生成类型化请求层，纳入 CI。看板 ECharts。部署：vite build 产 dist，nginx 托管+/console-api 反代，与后端同 compose。若唯一目标是国内 B 端就业且接受 Vue，soybean-admin 是更快的合法备选（触发条件已写明）。

### 对本项目的落地建议
- 边界先说死：做不了的是影子表全链路压测的真实形态（ShardingSphere 影子路由可做小范围「压测标记透传+影子表落行」演示，但不压全链路）、多机水平扩容、Rhino 式多地公网注压。不虚做、不虚标。
- 流量模型表（方法真、业务量可自设）：对本项目接口（领券/用券/查券）写「业务量→均值→×3~4 峰值」推算表；公式与口径是业界真实方法，业务曲线数字自设但在表中声明假设——满足『实际数据说话』的模型可追溯半边。
- 阶梯压测找拐点（单机口径）：JMeter 或 k6 在 WSL2 本机跑领券接口，50 并发起、每档+50、每档 5~10 分钟，逐档记录 TPS/P99/错误率/GC，产出拐点。硬约束照旧：压测机与被测应用共享 6.6G，压测工具并发上限保守、两者串行跑、跑前停应用与闲置容器；结论措辞写『相对水位与瓶颈形态』，不冒充生产容量。
- 消费节奏实测（速率控制看得见）：压测同时记录 Redis Lua 扣减 QPS、MySQL 落库 QPS、MQ 消费侧限速后的实际消化速率（张/秒）与积压水位——这是『定时/批量发券按每秒 N 张速率可控』的实测证据，直接回应用户第 6 条发放承受力。
- 三条防线断言（把承受力做成可演示）：①入口流量被 Redis 预扣拦截后 DB 近零写（入口 TPS 与消费落库 TPS 比例断言）；②超量流量被 Sentinel 快速拒绝（现有演练断言延伸到发券入口）；③限速消费下 MQ 积压被安全消化且发件箱零丢失（对账计数断言）。
- 报告按七模块出（概述/策略/指标/拐点/资源水位/归因/结论），附口径声明：单机 WSL2 环境，数字只代表相对水位与瓶颈形态，不代表生产容量；方法论（模型→阶梯→拐点→归因→结论）与业界全链路压测闭环同构——每条结论可追问可复算，面试不虚。

- **缓存多实例一致性（Caffeine 本地缓存失效广播债的偿还范式）**（primary, https://github.com/alibaba/jetcache）：Alibaba JetCache（JDK17+ 于 2.8+、Spring Boot3.x+ 支持）README 明确列出：2.7+ 提供「Invalidate local caches (in all JVM process) after updates」——cacheType=BOTH 两级缓存 + syncLocal(true) + remote.broadcastChannel（Redis 广播）即官方范式。证明项目登记的「失效广播」债方向正确且是业界标准解：实现上要么引 JetCache，要么自研极简版（Redis pub/sub 一条 invalidate 事件，各实例 Caffeine 收到即删）。属低代码量、高面试叙事价值的债。
- **优雅上下线与健康检查**（primary, https://docs.spring.io/spring-boot/reference/web/graceful-shutdown.html）：Boot 官方：三内嵌服务器（Tomcat/Jetty/Netty）默认启用优雅停机——停机时在 SmartLifecycle 最早阶段先在「网络层停止接收新请求」、再等存量请求完成，宽限期 spring.lifecycle.timeout-per-shutdown-phase 控制；server.shutdown=immediate 可关；IDE 直接 kill 不发 SIGTERM 则不优雅。完整上下线闭环=应用优雅停机 + Nginx 侧先摘流/慢启动 + （若引 Nacos）注册表摘除，三段缺一不可。配套证据：SCA 侧 Nacos 客户端停机 bug 2023.0.3.4 才修完。这正是「上线前有实际数据」的可演练点：滚动发布期间断言零 5xx。
- **单体→微服务的演进节奏（官方路径顺序）**（primary, https://sca.aliyun.com/blog/spring-boot-to-spring-cloud-best-practice/）：SCA 官方示例给出的升级顺序就是节奏模板：第一步只加 nacos-discovery（服务名注册）；第二步调用方把域名/SLB 直连改成 OpenFeign/LoadBalancer 服务名调用；第三步才加 Gateway（lb:// 路由）；官方同时承认 DNS/SLB/K8s Service 是合法的长期形态，并未给出「必须拆」的统一触发线。业界公开材料普遍以「团队规模、部署/故障隔离需求」为判据，但这部分属工程判断（标注判断，非官方数字）。对本项目：业务闭环（创建/发放/核销/算钱）在一个部署单元内未遇到拆分压力，先不拆。
- **配置热更新：租户配置中心与 Nacos config 如何共存不重复建设**（unverified, https://github.com/alibaba/spring-cloud-alibaba/releases）：设计分层（工程建议，机制描述本轮未打开 nacos.io 原文页，标注 unverified）：基础设施级可变配置（数据源、线程池、Sentinel 规则兜底值、功能开关）→ Nacos config 动态推送；租户级业务参数（配额、限流阈值、活动开关）→ 保留自研租户配置中心（DB+监听+审计）。二者面向对象不同、变更频率不同、审计要求不同，不构成重复建设；SCA 2023.0.3.2 还在增强 nacos config 注解与序列化（release notes 可证模块活跃，primary）。反例警戒：把租户配置也塞进 Nacos 会丢审计与租户隔离，是把两个问题混成一个。

### 对本项目的落地建议
- 【立即引入·低风险】Micrometer Tracing + Zipkin：加 micrometer-tracing-bridge-otel + opentelemetry-exporter-zipkin + spring-boot-starter-actuator（Boot 3.3 官方组合，零业务代码改动）；把自研 traceId 与 MDC traceId/spanId 对齐（日志 correlation ID 自动生效），验收=Zipkin UI 看到领券→核销全链路；注意默认采样 10%，压测/演示时设 management.tracing.sampling.probability=1.0。不引 SkyWalking：它的 OAP+存储是一套新基础设施，触发条件=将来真拆成 5+ 服务需要拓扑图与全量无侵入插桩时再评估。
- 【立即引入·部署形态定型】学习项目合理形态=Nginx 负载均衡 + Docker Compose 双实例（这正是 SCA 官方承认的 DNS/SLB/K8s 三形态中的低成本等价物）；必须演练完整上下线：SIGTERM → Boot 默认优雅停机（显式设 spring.lifecycle.timeout-per-shutdown-phase）→ Nginx 健康检查摘流，验收=滚动重启期间压测零 5xx 留档。生产形态差异写进文档：生产会把 Nginx 换成云 LB/K8s Ingress、compose 换 K8s Deployment+Service，但应用侧（优雅停机、健康端点、无状态）完全不变，迁移路径=compose→K3s→K8s，Spring Cloud Kubernetes 可在 K8s 内平替注册发现。不上 K8s：WSL2 6.6G 内存跑不动控制面，且学习收益为负；简历口径=『知边界、能迁移』。
- 【偿还登记债·多实例上线前置条件】Caffeine 多实例失效广播：跑双实例那一刻必须完成，两条路线二选一——(a) 自研极简版：Redis pub/sub 一条 invalidate 频道，各实例监听后删本地 Caffeine（约几十行）；(b) 直接用 JetCache BOTH+syncLocal(true)+broadcastChannel（2.8+ 支持 JDK17/Boot3，官方背书的同款语义）。验收=改一个租户配置后断言两个实例的本地缓存在秒级都失效。
- 【条件引入·触发条件明确】Spring Cloud Alibaba + Nacos：当前不引，触发条件=拆出第二个可部署单元需要服务名互调，或需要基础设施级配置热更新时。锚定版本=SCA 2023.0.3.4 + Spring Cloud 2023.0.x（Boot 3.3.x 兼容线，nacos-client 2.4.3），禁止自己拼版本；已知坑必须写进接入文档：Nacos HealthIndicator 默认关闭需显式决策、客户端优雅停机必须 ≥2023.0.3.4、新配置写法用 spring.config.import 不用 bootstrap.yml。若引则按 SCA 官方升级路径顺序：先 nacos-discovery → 再 OpenFeign/LoadBalancer 服务名调用 → 最后才考虑 Gateway。
- 【配置分层·防重复建设】不把自研租户配置中心迁去 Nacos：基础设施配置（数据源/线程池/功能开关兜底值）将来走 Nacos config，租户业务参数（配额/阈值/活动开关）保留自有配置中心——后者需要审计与租户隔离，塞进 Nacos 会丢这两样；两条链路共存不冲突，文档里写清『谁管什么、变更走哪条』。
- 【不引·触发条件明确】Spring Cloud Gateway：限流（Sentinel 单机+集群 Token Server）、鉴权（appId+HMAC+防重放）、熔断（Resilience4j/Sentinel 双层）已在应用层闭环，单应用+两实例下 SCG 净增量≈0，Nginx 静态反代足够。触发条件=出现第二个后端服务需要统一入口与动态路由，或需要边缘横切（SecureHeaders/TokenRelay/边缘限流）时再评估；届时 Boot 3.3 对应 SCG 4.1.x。
- 【不引·触发条件明确】Seata/TCC：outbox+消费幂等已覆盖 DB↔MQ 最终一致性，核销算钱在同一库本地事务；触发条件=拆出独立账务/核销服务且业务要求同步跨服务强一致回滚。届时选 AT 模式但必须写明其全局默认读未提交、需 SELECT FOR UPDATE 才读已提交的语义；TCC 仅在支付级资金场景考虑（成本=每参与方手写三段逻辑）。把这条对比写进 docs 决策表即可，不写代码。
- 【不引·无需动作】分布式 ID（雪花）、三层幂等、无状态会话（appId+HMAC 无服务器会话）：三项均已是业界主流做法且测试覆盖，不更换、不加 Spring Session；文档 checklist 里标注『已满足+证据位置』即可。
- 【文档动作·面试资产】在 docs 新增一页分布式决策表：每个组件（Nacos/网关/Seata/K8s/SkyWalking/JetCache）一行，列『现在引不引、触发条件是什么、届时版本锚点、已知坑』——用户十条指示第⑨条『分布式要点想明白』的交付物就是这张表加上每条的验证/演练证据，而不是引入更多中间件。

## 规则引擎与券抽象

### 目标架构建议
推荐「自研分层计价骨架 + 嵌入式表达式引擎」串联，不整套引入重量级规则引擎。①计价骨架：责任链（一手范本=yudao TradePriceCalculator），按优惠层级分四段顺序执行：单品级→店铺级(商家券)→跨店级(平台券)→服务收尾(运费/积分)，与有赞官方顺序（会员价>满减送>优惠券>积分抵现）和抖音 2026-09 递进式规则同构；层内按互斥组「优惠金额大者胜」（yudao 会员折扣vs限时折扣同款），跨层默认叠加，秒杀等特价单禁用券。②券类型抽象：模板/实例分离+策略注册；模板三段字段（领取/使用/效果）+五个正交维度：优惠类型（满减/折扣封顶）、作用范围（全场/类目/SPU）、叠加层级、互斥组、出资方；新增券类型=新增一个计价策略 Bean，主链零改动。③条件引擎：复杂门槛/资格用 QLExpress4（官方场景第一条即电商优惠券 DSL、默认沙箱、表达式追踪归因）或 Aviator（字节码更快、decimal 高精度）；脚本存库+版本化+轮询热刷新（LiteFlow rule-sql 同款 60 秒轮询即可，不必引入 LiteFlow 本体）。④规则=数据：版本+审核状态+租户灰度；保存时用结算期同一套计价器对模拟订单重放做配置期校验（mismatchReason 四件套/保底价/出资承担额）。⑤算法纪律：限张（1 商家券+1 平台券）+层内择优把组合从 O(2^n) 压到线性；分摊统一「按比例、末位反减兜底、单位为分」。Drools 是推理型 BRMS（40+ 模块），与本场景错位，明确不用。

### 对本项目的落地建议
- 引擎选型建议（拍板版）：计价骨架自研责任链——Spring Bean + ORDER 常量接口（照 yudao TradePriceCalculator 的组织方式，已验证 12 个 calculator 共存协作），不引入 LiteFlow/Drools 本体；条件/资格表达式选 QLExpress 4.x（官方场景第一条=电商优惠券规则配置、默认安全沙箱、表达式追踪可直接做归因），备选 Aviator 5.4.x（更轻、decimal 高精度、超时+沙箱）；LiteFlow 的真正价值是规则存 SQL/注册中心热刷新+多租户过滤（rule-sql 插件，60s 轮询），这一小部分能力自研一张 rule 表+定时轮询即可获得，不必引双引擎
- 券模板模型设计方向：promotion_coupon_template（模板）与 coupon（用户实例）分离；模板字段三段式=领取规则（totalCount/-1 不限、takeLimitCount、takeType）+使用规则（usePrice 门槛、productScope 三级范围 ALL/CATEGORY/SPU+values、validityType 固定日期或领取后 N 天）+使用效果（discountType 满减/折扣、discountPrice、discountPercent、discountLimitPrice 折扣上限——满折券必须带上限，正是 newcoupon 在途代码踩过的'按减 N 元算折扣券'的坑）；在 yudao 已验证字段之上补齐四列：叠加层级 layer（ITEM/SHOP/PLATFORM）、互斥组 mutex_group、出资方 fund_source（平台/商家/按比例共担）、适用订单类型
- 计价链固化顺序（对齐业界官方规则）：单品级(ORDER=8)→限时折扣(10)→满减送(20)→商家券(30)→平台券(35)→积分抵现(40)→运费(50)→赠积分收尾(999)；同层互斥组内按优惠金额择优并落明细，跨层默认叠加；秒杀/特价订单直接拒券（yudao PRICE_CALCULATE_COUPON_NOT_MATCH_NORMAL_ORDER 模式）；每一笔优惠产出 Promotion 明细行（优惠id/类型/出资方/每个 SKU 分摊额）——这直接支撑 Phase 1 要做的'核销由平台算钱+分摊落行+出资方'闭环
- 分摊与尾差硬规则：全链路金额用分（long），禁止 BigDecimal 中途四舍五入；每项优惠按受益 SKU 支付金额比例分摊，前 n-1 项向下取整、最后一项反减兜底并断言≥0（yudao dividePrice 一手实现照抄即可）；分摊结果落行后，退款冲回按原分摊行反向执行，不要再算一遍
- 配置期校验（防错配，进管理后台保存/审核流程）：用结算期同一套计价器对构造的模拟订单重放，输出四类 mismatchReason（未到使用时间/无匹配商品/差X元可用/优惠超订单额——yudao 已实现直接复用）+校验保底价（折后价≥floorPrice 才允许保存）+预估出资方承担额给运营确认；QLExpress 脚本规则开启表达式追踪，配置期即可看条件分支归因
- 组合爆炸三件套（不做全局最优枚举，与此前调研否证动态规划的结论一致）：①限张规则默认 1 商家券+1 平台券（模板可配、抖音/Amazon 同款）；②层内互斥择优只比金额不比组合；③固定层级顺序消除顺序自由度。三者把组合空间从 2^n 压到 O(n)；未来若做'为你推荐最优券'，只做只读推荐（分桶+剪枝），不进结算链路
- 面向多租户接入闭环：规则表带 tenant/app_id 维度（LiteFlow rule-sql 插件的 applicationName 多租户过滤是现成设计参照）；规则=数据：脚本/链配置存库+版本号+审核状态+灰度开关，热刷新用 60 秒轮询（与 LiteFlow SQL 插件默认值一致），配置变更走审核后才进生效版本，灰度按租户切流验证后再全量
- 遗留口径修正：上轮调研的'京东 ZCube 用规则引擎做券展示'本轮未重验，沿用请标 unverified；本轮新增的硬锚点是有赞官方顺序页、抖音 2023 新增+2026-09 修订叠加规则通知、微信跨店每满减分摊规则、QLExpress/LiteFlow/Aviator/Drools 官方 README、yudao 与 mall 全文源码，均可直接写进实施文档的'参考'栏

## 上线标准

### 目标架构建议
上线就绪是一条证据链，不是一次评审：先把测试基线修到全绿并纳入分支保护——PR 必过构建+测试+JaCoCo 门槛+安全扫描四个 required check，覆盖率按 Google 口径分存量（≥70% 只查不升）与新增代码（≥90% 底线），以 jacoco:check 落成部署门禁；再定义 SLI/SLO：领券/核销/算钱三个资金路径接口各定可用性+P99 双目标，配四张业务大盘（发放流量、核销成功率与错误码、算钱分摊守恒、预算与桶库存/MQ 积压水位）；告警按 SRE Workbook 多窗口多燃烧率落成两级——Page（燃烧率 14.4x/1h、6x/6h）映射 P0/P1 响应 1-3-5-10 锚点，Ticket（1x/3d）映射 P2/P3；日志遵循 OWASP：traceId 贯穿、认证失败/鉴权失败/超限尝试必落日志、令牌与密钥绝不落日志；容量用真实流量回放式压测报告说话（极限 QPS、错误率拐点、降级触发实录，对标美团 Quake 要素）；数据侧落实"全备+binlog PITR+恢复到沙箱演练一次并记录 RTO"；最后过一张按 Google LCE 六主题裁剪的上线检查单（架构依赖/容量压测/故障降级/防滥用/手册/回滚），发布走备份→灰度→校验→可验证回滚。每一环都产出带时间戳的证据文件——这才是"实际数据说话"。

### 发现清单
- **测试金字塔与各层比例**（primary, https://martinfowler.com/bliki/TestPyramid.html）：底层单测应远多于高层广栈测试（GUI/端到端），端到端测试脆、慢、贵，倒金字塔（ice-cream cone）是反模式；高层测试是第二道防线，暴露 bug 时应先用单测复现再修；例外：若高层测试快而稳，可减少低层测试。对交易/营销系统的落地含义：库存扣减、算钱、预算等资金路径以单测+集成测试为主，领券→核销全链路只保留少量冒烟级 E2E。
- **覆盖率门槛：反对声音（作为数字目标的滥用）**（primary, https://martinfowler.com/bliki/TestCoverage.html）：覆盖率的价值在于找出『没被测到的部分』，作为数字目标几乎无用：深思式测试自然落在上 80%~90%，低于一半是危险信号，接近 100% 反而说明为凑数而写；充分性应由『生产逃逸 bug 少 + 改代码不心虚』判定，不由数字判定。
- **覆盖率门槛：Google 的可执行口径（区别存量与新增）**（primary, https://testing.googleblog.com/2020/08/code-coverage-best-practices.html）：Google 内部指引：全项目覆盖 60%=可接受、75%=值得表扬、90%=模范；全项目 >90% 大概率不值得追，但『每次提交的新增代码』90% 是好下限、99% 合理；建议把覆盖率并入代码评审（看未覆盖行而非只看总数）；覆盖率不保证断言正确，可用变异测试补验；应设置部署门禁但防『打勾效应』。价值最大处是暴露未覆盖区域。
- **覆盖率『80%』的行业惯例与工具门槛**（secondary, https://launchdarkly.com/blog/on-code-coverage-in-software-testing/）：业界常见约定即『80% 行覆盖』：LaunchDarkly 称 80~90% 为强；JaCoCo 官方通过 jacoco:check 规则设比例门槛（BUNDLE/类级 limit）；SonarQube 默认 80% 且与 JaCoCo 自定义阈值要分别配置；Jenkins 社区常见 70% 门。均由搜索结果页核实，未逐篇抓原文。
- **契约测试何时值得（对本项目的裁剪判断）**（primary, https://docs.pact.io/）：契约测试适合『两个以上需要通信、且各自独立部署的服务』，在多服务微服务环境『大放异彩』；消费驱动契约只测消费方真正用到的字段，未用行为可自由演化；它是替代昂贵易碎集成测试的手段。反向结论：单体应用 + 单一对外开放 API（appId+HMAC）场景，Pact 级 CDC 收益边际，用 OpenAPI 快照回归 + 签名/幂等回归用例即可承担同等职责，不必引入 Pact 全家桶。
- **告警分级与燃烧率（Google SRE Workbook 第5章，含精确参数表）**（primary, https://sre.google/workbook/alerting-on-slos/）：推荐多窗口多燃烧率告警（99.9%/30d SLO）：Page 级=1h 长窗+5m 短窗、燃烧率 14.4（已耗 2% 预算）与 6h+30m、燃烧率 6（5%）；Ticket 级=3d+6h、燃烧率 1（10%）。请求按关键度分桶设差异化目标：CRITICAL 99.99%/100ms、HIGH_FAST 99.9%/100ms、HIGH_SLOW 99.9%/1s、LOW 99%、NO_SLO 不设。低流量服务用合成流量补信号。禁止用 for 持续时长做门限（波动序列可能永不告警）。
- **SLI/SLO/错误预算入门口径（Google SRE 书第4章）**（primary, https://sre.google/sre-book/service-level-objectives/）：用户侧服务三类核心 SLI=可用性、延迟、吞吐；所有系统都该追踪正确性；用 50/99/99.9 分位而非平均值（长尾会被平均掩盖）；只选少数代表性指标，标准化 SLI 模板（窗口/聚集体/采样频率）；内部 SLO 应比对外宣称更紧，留缓冲；错误预算是『允许未达标率』，直接驱动发布节奏决策。
- **日志规范：结构化/traceId/敏感信息不落日志（OWASP）**（primary, https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html）：每条日志记 when/where/who/what + 交互标识（即 traceId 贯穿）；必须记：输入校验失败、认证成败、鉴权失败、会话异常、高危功能使用、可疑业务逻辑（乱序操作、超限尝试——即刷券/薅羊毛行为特征）；严禁直接落日志：会话 ID、访问令牌、密码、数据库连接串、加密密钥、银行卡/持卡人数据（需脱敏/哈希）；要防日志注入（CR/LF）、防日志写满磁盘 DoS、设保留期并保护日志完整性。对资产敏感的券系统，这构成安全日志底线而非可选。
- **券/营销系统压测的监控与安全基线（美团 Quake 全链路压测一手复盘）**（primary, https://tech.meituan.com/2018/09/27/quake-introduction.html）：美团公司级全链路压测平台：压测必须打线上真实环境+回放高峰真实流量（词表=每行一个请求）；写流量用『影子表』隔离防数据污染；压测标识跨线程（ThreadLocal）跨服务（Mtrace）透传；秒级监控 QPS 曲线/错误率/TP 分位/采样日志，预设熔断阈值到限自动降 QPS 或中断，可注入故障验证降级预案；所有核心业务线接入、月均压测上万次。给学习项目的启示：压测报告必须包含『极限 QPS+错误率拐点+降级触发实录』而非只给 TPS 数字。
- **MySQL 备份策略官方标准（8.4 手册第9章）**（primary, https://dev.mysql.com/doc/refman/8.4/en/backup-types.html）：官方口径：物理备份（快、紧凑、适合大而重要的库）vs 逻辑备份（mysqldump --single-transaction 对 InnoDB 在线无锁、跨机器可移植）；增量靠 binlog——FLUSH LOGS 轮转后备份 binlog 即增量，恢复=先全量恢复再按 mysqlbinlog 重放到指定时点（PITR）；可从 replica 备份避免影响主库；官方建议备份调度自动化+压缩+加密。注意：官方文档未给出『定期恢复演练 SOP 与 RTO 记录』的细目，该环节业界惯例（恢复到沙箱+校验+测 RTO）未核实到一手来源。
- **上线评审检查单的公开版本（Google LCE 第28章）**（primary, https://sre.google/sre-book/reliable-product-launches/）：LCE 上线检查单主题：架构评审（请求链路、依赖清单）、容量（发布峰值可达预估 15 倍，需 N+1 冗余）、故障模式（单点、降级模式、load shedding、请求死线）、防滥用客户端（指数退避+抖动、限流配额）、手册化人工流程（『从备份恢复数据』被点名为必须文档化的流程）、版本管理、第三方依赖、发布计划+应急预案。检查单治理原则：每个问题必须被一次真实事故背书、每条指令必须具体可执行；低风险发布走简化快速通道（无新二进制+流量增幅<10%）。
- **发布形态：渐进放量/金丝雀/功能开关是 Google 发布的默认动作**（primary, https://sre.google/sre-book/reliable-product-launches/）：几乎一切变更渐进放量：金丝雀先观察再扩大；feature flag 从 1~10% 用户起逐步放量，出问题立即独立回滚；发布高峰校验失败自动回滚。压测被列为大多数发布的硬性要求（过载行为无法从第一性原理预测）。学习项目最小合理形态：单实例上先跑迁移前备份→停机/滚动替换→冒烟校验→保留一条已验证的回滚命令，即等价于蓝绿的核心承诺（可回滚），无需追求全自动蓝绿基建。
- **CI 质量门的强制机制（GitHub 官方文档）**（primary, https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches）：分支保护可强制：PR 审查数、required status checks（strict=必须先同步基线分支再合并；loose=不强制；检查状态为 successful/skipped/neutral 才放行）、部署到指定环境成功后才可合并（staging 门）、合并队列防基线破坏。已知坑：required check 与 workflow path filter 组合会导致检查挂起阻塞 PR（GitHub 官方 issue 讨论区核实，secondary）。
- **告警响应时限（P0~P3 ↔ 1-3-5-10 的对齐）**（secondary, https://response.pagerduty.com/before/severity_levels/）：SEV/P 级别数字越小越紧急（PagerDuty 官方指南核实到存在与定义句）；第三方通行映射：P1≈15 分钟内响应、P2≈30 分钟、超时自动升级（Xurrent/incident.io 等口径，均未整页核实）；本项目已有 1-3-5-10 响应锚点，可直接作为 P0~P3 的响应时限并与 SRE Workbook 的 Page/Ticket 两级对齐（Page≈P0/P1，Ticket≈P2/P3），无需另造体系。
- **券平台业务大盘应有哪些图（合成结论，无直接一手示例）**（unverified, https://sre.google/workbook/alerting-on-slos/）：未找到任何公司公开到『券平台大盘逐图』级别的一手资料。可由一手方法论合成：四张业务面板=发放（QPS/成功率/错误码分布/限流拒绝数）、核销（核销 TPS/P99/失败原因分布）、算钱（分摊金额守恒校验告警/出资方口径）、预算与库存（预算水位/16 桶库存/发件箱积压/MQ 消费延迟）；技术层叠机械指标（CPU/GC/连接池）。合成部分按 unverified 对待，结构依据 SRE Workbook 请求分桶法与 Quake 监控元素。
- **测试金字塔落地版（Ham Vocke）——部分读取**（unverified, https://martinfowler.com/articles/practical-test-pyramid.html）：该文是金字塔落地最常引用的实践文（强调『别追求完美比例，金字塔只是粗略指引』），本次仅成功读取文章开头，关键段落因抓取超限未完整核实，相关论断不要单独引用此条。
- **恢复演练的常规节奏——未核实到一手**（unverified, https://www.percona.com/blog/）：常见口径：xtrabackup 物理热备+binlog 做 PITR、恢复到隔离沙箱验证行数/checksum 并实测 RTO、备份失败要告警（静默失败常见）、3-2-1 原则。因搜索通道限流未能抓到 Percona/官方一手原文核实，仅作方向参考；工具选型本身已由 MySQL 官方手册一手核实。

### 对本项目的落地建议
- 证据物1·测试基线报告：mvn clean test 完整输出留档（总例数/失败数/跳过数/总耗时），绑定提交 hash——即现有『442 例零红』口径的正式证据文件，放进 docs/evidence/。
- 证据物2·覆盖率报告：JaCoCo XML/HTML 报告 + jacoco:check 门槛配置 diff，附一条决策记录：存量 BUNDLE ≥70%（只查不升）、新增资金路径模块 ≥90%（Google 新代码口径）、为何不设 95%+（Google 原文：全项目>90% 不值得；Fowler：凑数即反模式）。
- 证据物3·CI 质量门配置：GitHub Actions workflow 文件 + main 分支保护规则截图，required checks 四项=build/unit+integration tests/jacoco gate/依赖与代码扫描，注意规避 required check 与 path filter 的挂起坑。
- 证据物4·SLO 声明表：领券/核销/算钱（+异步发放受理）各一行=可用性目标+P99 目标+测量口径（统计窗口、是否含熔断降级响应、分位数而非平均值），并声明内部目标比对外口径更紧。
- 证据物5·Grafana 大盘证据：大盘 JSON 导出+四面板截图（发放 QPS 与限流拒绝数/核销成功率与错误码分布/算钱分摊守恒与预算水位/16 桶库存+发件箱+MQ 积压），每图标注数据来源指标名——大盘逐图构成是合成结论，需在文档中注明依据。

- 证据物9·告警演练记录：至少一条 Page 级规则被真实触发并恢复的截图（含多窗口多燃烧率表达式，如 14.4x/1h+5m），一条 Ticket 级规则同理——证明『告警会响、响了有人接』。
