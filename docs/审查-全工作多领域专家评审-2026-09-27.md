## 2. 确认发现（已去重合并；标注 ✅ 的条目为主控独立复核）

### P1-1 ✅ 开桶者恢复执行时 `openBucket` 缺"世代不回退"护栏 → act 名册被指回已封账旧代，全模板假售罄且四检全绿
- **位置**：`RedisStockGateway.java:162-166`（OPEN_BUCKET_SCRIPT 幂等门）；`StockBucketRouter.java:177`（调用点）
- **证据**：幂等门只挡"同代"：`local cur = redis.call('HGET', KEYS[1], ARGV[2]) / if cur == ARGV[3] and ... then return 0 end / redis.call('HSET', KEYS[1], ARGV[2], ARGV[3])`——名册上是**更新**的世代时照样回写旧代；调用侧 slot/gen 在暂停之前算好，恢复后零复核（对照：孤儿重放路径有 `cur < row.getGeneration()` 护栏）。
- **触发**：开桶者在"行已提交、Redis 未建键"之间被暂停 >5s（锁过期）→ 接管者封空代并开新代 → 恢复者用过期世代调 `openBucket` → act 回退、旧代 stk 被重置为满额。
- **影响**：deduct 过闸、DB `status=0` 守卫拒绝 → cancel → 立模板级售罄牌 → 全模板终态 3001；新代真实库存不可达；四条守恒检查全平，无自动发现手段。
- **建议**：开桶脚本加单调护栏（`cur > 目标代 → 拒绝`）；调用前重读 act 复核世代。

### P1-2 ✅ 批量重开把"未注册的孤儿桶行"当"空代"封账（`stk==null` 与 `stk==0` 混同）→ 孤儿重放被绕过、额度永久搁浅
- **位置**：`StockBucketRouter.java:253-257`（refill ①封账循环）
- **证据**：`Long stk = gateway.bucketStock(...); if (stk == null || stk == 0) { row.setStatus(1); bucketMapper.updateById(row); }`；孤儿重放只遍历活跃行（`selectActive` = `status=0`）→ 被封的孤儿行从此不可达；且 `refill || tryOpen` 短路使重放根本不被触发。
- **触发**：桶行已提交、Redis 未建键之间崩溃/暂停（L37 文档 §5.2 承认的窗口），模板 `allocated < total`（部分分配=大盘模板常态）。
- **影响**：崩溃分支：该段额度永久不可卖且 `c:alloc < Σquota` 永久破缺 → 巡检每轮确认漂移、deep 只修活跃行修不了 → 修复熔断；暂停恢复分支：已封账行被重新注册成全量库存 → 自持环或全模板售罄牌。全程守恒四检全绿。
- **建议**：封账前区分 `stk==null`（先走重放/跳过）与 `stk==0`（才是可安全封的真代）。

### P1-3 ✅ 巡检立售罄牌缺"额度已分完"判据（`allocated>=total`）→ 部分分配模板剩余额度被自续期短路牌锁死
- **位置**：`StockReconcileService.java:325`（`maybeSetSoldout`）
- **证据**：`if (stkSum == 0 && gc.alloc() == stockBucketMapper.sumQuota(templateId)) { stockGateway.setSoldoutWithTtl(templateId, 10); ... }`——条件里没有 total/allocated；牌命中即续期（`DEDUCT` 首段 `EXPIRE so 10`）；请求侧急救分支要求 `!isSoldout` 而不可达；唯一清牌者（deep FORCE 且 stk>0）在该状态不会被触发。
- **触发**：模板 `total > 槽位数×桶额`（生产默认 16 万，如 total=100 万）→ 当前桶卖空、巡检采样落在"全空"瞬间（或流量低谷期）→ 立牌 → 之后 `-3` 短路，`-10` 补开路径永不进入。
- **影响**：剩余额度（可达数十万张）被终态 3001 挡住；流量不断则牌永不过期；单位从可卖池永久退休。**这是本次对业务影响最直接的发现。**
- **建议**：立牌条件加 `allocated>=total`；开桶/回加路径接 B4 清除协议；"命中续期"改为有界。

### P1-4 ✅ 尾段"桶满被拒"被分类为售罄并立模板级牌 → 牌无清除路径、请求侧救援被 `!isSoldout` 挡住
- **位置**：`ReceiveAppService.java:397-401`（`classifyDeductRejectAndCancel` 的 SOLD_OUT 分支）
- **证据**：`if (stockBucketRouter.soldOutInDb(...)) { cancelQuietly(cmd, d, CancelCause.SOLD_OUT); ... }` → CANCEL 脚本 `SET c:so 1 EX 10`；全仓唯一业务清除点在 deep FORCE（`StockReconcileService.java:510-512`）。
- **触发**：`allocated==total` 但桶内仍有未卖余量时任一 DB 扣账被拒（成因可叠加 P1-2 的封账-在途竞态）。
- **影响**：与 P1-3 同族：假售罄终态 + 牌自续期 + 尾段余量不可达。
- **建议**：SOLD_OUT 分类收紧为"确实没有任何可卖/可回加的货"（L38 三条件判据）；清牌协议接入开桶/回加。

### P1-5 ✅ ENSURE 灾后重建只回填活跃行 → 封账代/历史行份额缺失，E2b 与镜像永久破缺、自动修复熔断
- **位置**：`StockBucketRouter.java:191`（`selectActive`）、`RedisStockGateway.java:183-199`（ENSURE 脚本）
- **证据**：`var rows = bucketMapper.selectActive(templateId);`（只传 `status=0`）；`redis.call('SET', KEYS[2], total)` 的 total 只累计传入行；而 E2b 锚是全表 `sumQuota`（`StockBucketMapper.java:58`）、镜像锚含封账真代（`sumUsedBucketed` 仅排除 V10 历史行，注释明确"含已封账的真代"）。
- **触发**：任何发生过换代的模板发生 Redis 数据丢失 → `-7` → ENSURE。
- **影响**：`c:alloc` 比全表 Σquota 少"封账代/历史行 quota"整块 → 每 60s 巡检恒报破缺/confirm-lost → deep 只修活跃行、缺口不可收敛 → 连续 FORCE 熔断（自动修复停摆）。现有 `P2bEnsureRecoveryTest` 覆盖不到含封账代的形态（假绿边界）。
- **建议**：ENSURE 传全世代行并区分代状态（活跃代 stk=q−u、封账代 stk=0/dbi=u/void=q−u），使四口径灾后同时可收敛；补相应用例。

### P1-6 ✅ REBUILD·FORCE 把"未注册世代"按退役推导 → 新鲜额度写成 void、E2a 转危险方向冻结、静默库存丢失
- **位置**：`RedisStockGateway.java:236-242`（REBUILD 的 `isCurrentGen`/retired 判定）
- **证据**：`local retired = ... or not isCurrentGen`——名册里**不存在**该桶（行已提交、注册未执行）时也判 retired → `stkV=0; voidV=quota−used`；deep 侧对名册外的行以 `dbiObs=0,voidObs=0` 调 rebuild，栅栏放行；脚本从不写 act/gens。
- **触发**：(a) 行已提交、openBucket 未执行后巡检先于任何 `-10` 确认 E2b 并提交 deep；(b) Redis 全丢后 60s 内无请求（ENSURE 未跑）。
- **影响**：(a) 整段新鲜额度写成 void → 下一轮 E2a 判危险方向 → 模板冻结、自动解冻不可达（需人工）；(b) 更重：deep 全写 retired 后请求先触发 ENSURE，因 stk 键已存在而跳过 → 四检全平、未售额度静默丢失、此后只收 3001。
- **建议**：区分"旧代"与"未注册"（仅当 `HGET(act,b)` 存在且≠gen 才算 retired）；未注册行走开桶/ENSURE 协议或中止并告警；ENSURE 对已存在的 stk 键做一致性校验。

### P1-7 ✅ V10 历史代行永不进 Redis 镜像，但 E2b 按"全表 Σquota"比对 → 存量在售模板永久误报、自动解冻/售罄重立失效
- **位置**：`V10__p2b_stock_bucket.sql:45-47`（历史行回填）与巡检 `sumQuota`（`StockReconcileService.java:238`）
- **证据**：历史行 `(bucket_no=0, generation=0, quota=issued_count, status=1)` 只存在于 DB；`c:alloc` 只由 OPEN(INCRBY 新行)/ENSURE(SET 传入活跃行合计) 写 → 恒为 `total−issued`；巡检比对用全表 Σquota（=total）→ 恒不等。
- **触发**：任何执行过 V10 回填的库（迁移时刻存在 `publish_status=1 且 issued_count>0` 的模板）。
- **影响**：每个存量模板每 60s 恒判 E2b 破缺 → 漂移日志每轮刷写、≥6 模板触发全局风暴告警；clean 分支永不可达 → 自动解冻/售罄重立对该批模板彻底失效；deep churn。
- **建议**：统一口径（三选一：E2b 排除 (0,0) 历史行 / 历史行也计入 c:alloc 并注册 / 迁移时为其建键）；补存量形态的红灯用例。

### P1-8 ✅ L37 段唯一键残洞：refill 无差额检查，三方交错时 Σquota 仍可 > allocated
- **位置**：`StockBucketRouter.java:268-285`（refill 的 segBase/建行）对照 `132-137`（差额检查只在 tryOpenBucket）
- **证据**：L37 去重前提是"两个建行者算出的段上界相同"；refill 在差额未补时继续 `casAllocate`+建行，其 `allocated_hi = Σquota + n` 与暂停者的 `rowsQuota + n` 不再相等 → 唯一键撞不上。
- **触发**：A 在划款后暂停 >5s → R（refill，尾量 n=5000）先建 hi=95000 → B 差额恢复建 hi=105000 → A 恢复建 hi=100000（不撞）→ Σquota=115000 > allocated=105000。
- **影响**：超发 ≤ 一个桶额（默认 1 万）每次交错；窗口内多出额度可真实售出；仅靠新增的额度段检查在 ~2 个巡检周期后冻结。
- **建议**：refill 建行前先补差额（或有差额时禁止划款/建行）；建行改条件 INSERT（`Σquota + n ≤ allocated` 才插）。

### P1-9 ✅ 封账用整行 `updateById` 回写（无 @Version、无 CAS）→ 并发 `used+1` 被静默回退，账目永久不平且污染修复锚
- **位置**：`StockBucketRouter.java:226-231`（sealOldGenerations）、`253-259`（refill ①）

- **影响**：该代 `used` 永久少记 → 镜像误报 PHANTOM（P0 签名假警报）、deep 守卫矛盾；分代修复以 `used` 为锚（"少记的 used 变成多铸的 stk"）→ 超发方向（默认 shadow 模式只推导不执行，暂未直接超发）。
- **建议**：封账改定值 CAS：`UPDATE stock_bucket SET status=1 WHERE id=? AND status=0`；补"封账 × 扣账并发"回归用例。
