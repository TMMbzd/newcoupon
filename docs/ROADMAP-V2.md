# ROADMAP V2：业务优先 + 对标大厂（2026-09-30 立项）

> **为什么有 V2**：原路线（本文档同目录的 [ROADMAP.md](ROADMAP.md) v4）把"可观测/压测/存储规模化"排在业务前面。用户 2026-09-30 裁定：**先要一个"其它系统能接入、业务完整、算得清钱"的优惠券中台成品**；扩展、观测、治理等**留在后面做**（顺序靠后，不是砍掉）。同时要求**对标大厂技术**（调研见 [对标-大厂能力地图](对标-大厂能力地图-2026-09-30.md)）并作为**可学习的成品**。
> **与 v4 的关系**：**里程碑顺序被本文档取代**；v4 保留作为历史（其 P1/P2 已完成，P3~P9 的内容被重新编排进 S1~S8 与"后置"）。冲突时以本文档为准。
> **2026-10-01 微调**：新增 **S2 流量治理与过载保护**（瘦身版：入口限流 + 调用熔断 + 三级开关），并在 S1 增加**治理插槽**（请求上下文 / 资源命名 / 开关点与降级路径）；其余治理能力列为"随时可插的增量"。
> **2026-10-04 微调**：S2 扩为「**流量治理与租户策略**」——新增**租户配置中心**（把超时 / 限流阈值 / 熔断阈值 / 开关默认值从代码里挪到**按租户的配置**上），并把**舱壁隔离**从「随时可插的增量」提为「**S2 之后紧邻的一步**」。
> **为什么**：租户配置是后续所有租户级能力（熔断阈值、灰度开关、舱壁池大小）的**共同地基**——晚做的话，每做一项租户能力都要回头补一次；而它本身的成本很低（一张配置表 + 一个带缓存的读取服务）。**物理隔离与完整灰度仍然后置**（判断依据见 §3：问"没有它，会发生什么具体的坏事"）。
>
> **确认记录**（用户 2026-09-30）：① 采用"**对标重构 + 业务新建**"（不从零重写）；② 顺序"**先门面（S1 接入层）再骨架（S3 双模式）**"；③ 压测**定目标数字**（见 S3 验收）。

## 0. 总原则（本版本的六条）

1. **业务可用性/完整性/安全性优先**：先把"别的系统接得进来、券发得出、钱算得对、退得回"做出来。
2. **不阉割功能面**：大厂有的能力域，我们都要有对应实现（可以是规则版/模拟端口版），差别只体现在**顺序**与**深度**上。
3. **外部依赖一律走"端口 + 适配器"**：商品系统/画像/触达/设备指纹等外部系统用**模拟适配器**实现，真实适配器留接入位（见 §4）。这是"没有外部系统也能做成成品"的关键手法。
4. **能力对齐 + 术语对齐**：P2 已有的能力保留，但**命名向业界靠**（"守夜人/世代"→"轧账平账/批次快照"），对外沟通无障碍。
5. **每个阶段都产出四件套**：代码 + 教学文档（`study/v2/`）+ 面试刁难卡 + 可跟跑演示脚本/命令。
6. **明确的"不做"要有理由**：见 [对标-P2实现对照](对标-P2实现对照-2026-09-30.md) §4（七条不做项）。

## 2. 路线图 S1~S8（2026-10-01 微调后）

> 每阶段格式：**对标依据 → 做什么 → 模拟什么 → 验收（可演示可测）→ 学习产出 → 债务挂接**。

### S1 开放接入层与契约（对外门面）

- **对标依据**：大厂开放平台规范——appId+AK/SK 签名（时间戳+有效期防重放）、clientToken 幂等、IP/接口/appId 三维度限流与配额（429）、`/v1` 版本化、错误码分段、沙箱→灰度接入流程（来源见能力地图域 ⑥）。
- **做什么**
  1. 应用管理：接入方注册（appId/AK/SK）、密钥轮换、状态启停、调用审计。
  2. 签名网关：`Authorization` 头（版本/时间戳/签名头/签名），参数按 key 升序 + 密钥 HMAC，时间窗校验（如 ±5 分钟）+ nonce 防重放。
  3. 幂等中间件：写接口强制 `clientToken`（同 token 同参返回同结果；同 token 异参返回参数不一致）。
  4. 配额与限流：按 appId 的 QPS/日配额（超限 429）+ 现有 IP 频控保留。
  5. 契约统一：错误码分段（沿用现有 1xxx/2xxx/3xxx/5xxx + 新增 6xxx 接入域）、重试语义（哪些码可重试）、超时建议。
  6. **面向接入方的接口文档**：接口清单 + 签名示例 + 错误码表 + 幂等说明 + 联调示例（curl/脚本）。
  7. **治理插槽（2026-10-01 微调加入：成本极低，但决定后期治理能否"零改动插入"）**：
     - **统一请求上下文** `RequestContext{appId, userId, traceId, deadline, actId, templateId}`——traceId/appId 本阶段本就有，补 **deadline（超时预算的透传位）** 与治理维度；
     - **资源命名规范**：`resource = 接口[:维度[:值]]`（如 `receive:template:123`）——限流 / 熔断 / 监控 / 开关**共用同一套 key**，写进契约文档；
     - **开关点与降级路径约定**：开关命名（如 `sw.receive.enabled`）+ 关键路径位置（收单入口 / Redis 依赖 / DB 依赖 / 发件箱投递 / 触达外呼）+ "开关读取接口 + 默认开启 + 降级分支返回什么"（降级码沿用现有 5001 可重试语义，先空实现）。
- **模拟什么**：无（全部真实实现）。
- **验收（可演示可测）**
  - 一个 demo 客户端（脚本）用签名跑通：建券 → 发布 → 领券 → 锁券 → 核销 → 释放 → 查券。
  - 反例全部可复现：签名错 401、重放被拒、同 clientToken 重放返回同一结果且不重复发券、超配额 429、越权（A 应用操作用户 B 的数据）被拒。
  - 治理插槽可见：请求日志能打出 `appId + resource 命名 + deadline`；开关读取接口能读到一个默认开启的开关；关键路径的降级分支位置在代码里标注清楚。
- **学习产出**：为什么签名要带时间戳与 nonce；幂等键与业务键的区别；配额与限流的三维度；版本化的兼容策略。
- **债务挂接**：L27（管理面鉴权已清）扩展为**接入方鉴权**；L12（"userId 由请求携带"）在此**重新定性**——中台模式下由受信任接入方传 userId 是正常设计，L12 的真实风险由"接入方鉴权"解决。

### S2 流量治理与租户策略（2026-10-01 加入；2026-10-04 扩为含租户配置中心）

> **为什么插在这里**：限流/隔离的对象正是"接入方与接口"，S1 定了身份与契约，治理层才落得下去；而 S3 的"异步削峰"本身就是治理手段，紧挨着讲最顺。

- **对标依据**：Sentinel（阿里开源、双 11 同款）的治理矩阵——流控维度（IP/接口/调用方/热点参数/链路）、流控效果（快速失败 / **Warm Up 冷启动** / **匀速排队**）、熔断降级（异常比例 / 慢调用比例 / 半开探测）、**系统自适应保护**（Load/CPU/RT/入口 QPS；借鉴 TCP BBR：`平均RT × 最大QPS = 预估容量`）、集群流控（Token Server 全局配额）；Boot 3 侧的实现选型用 **Resilience4j**（`resilience4j-spring-boot3`）。来源见 [能力地图](对标-大厂能力地图-2026-09-30.md) 域 ⑦。
- **做什么（瘦身版：只做"直接影响可用性"的部分 + 租户策略地基）**
  0. **租户配置中心（先做——下面三块都要读它）**：把散落在代码与全局配置里的可调参数，收敛成**按租户的一份策略**——
     超时预算、限流阈值与算法参数（窗口大小 / 冷启动时长 / 是否排队）、熔断阈值（异常比例 / 慢调用界线 / 半开探测次数）、该租户的开关默认值。
     做法：`open_app_config` 表（app_id + 配置键 + 值）+ 带缓存的读取服务（与既有的接入方认证缓存同款：防击穿 / 负缓存 / TTL 抖动）+ 管理面读写接口 + 变更审计。
     **读不到配置时回落全局默认值并记日志**——不让"配置缺失"变成"功能不可用"。
     **这一步的意义**：把租户从一个**身份**变成一份**可运营的策略**——这是中台与普通系统的分界线。
  1. **入口限流（多维）**：维度 = IP / appId / 接口 / 链路；效果 = 快速失败 + Warm Up + 匀速排队；实现 = **自研限流器家族**（滑动窗口 / 令牌桶 / 漏桶），挂在 S1 的过滤器链上，按 S1 的资源命名统计。
  2. **熔断与降级（调用级）**：用 **Resilience4j** 给依赖调用加熔断（Redis 闸门 / MySQL / MQ 投递 / 外部触达）——异常比例 + 慢调用比例 + 半开探测；fallback 复用已有语义（5001 可重试降级码 / 只读 / 快速失败）。
  3. **开关中心与三级预案（最小版）**：接口级 / 依赖级 / 模板级 / **租户级**开关（一键降级，默认值来自第 0 块的租户配置）+ **红黄蓝三级预案**（蓝=预热与预防；黄=局部降级；橙红=保命：刚性限流/拒新/只读）+ **演练脚本**（注入故障 → 一键降级 → 验证 → 恢复）。
  4. **把三类"熔断/开关"的区别写进文档（教学点）**：**调用熔断**（技术层：依赖不可用时快速失败）/ **业务开关**（产品层：关掉某功能或某活动）/ **修复环熔断**（运维层：自动修复连续失败止损，P2 已有）。
- **紧随本阶段之后（不再算"增量"，但也不同批做）**：**舱壁隔离**（按接入方 / 按活动分线程池与连接池）。
  排在这里的理由：S2 做完熔断与租户配置后，"按租户分资源"就是顺势一步（池子大小从租户配置读）；
  而它要解决的问题——**一个租户打满连接池、其他租户一起变慢**——是这一堆治理项里**唯一会真实伤到其他租户**的。
- **本阶段不做 → 列入"随时可插的增量清单"（不阻塞业务阶段）**：集群配额（Token Server 思想的配额中心）、热点参数限流（按模板/接入方的 LRU+滑动窗口）、系统自适应保护、超时预算的**实际裁剪**（S1 只留 deadline 透传位，本阶段把它接上）、重试治理细化。**它们都能后续直接插入**（挂载点已在 S1 的插槽里），触发条件 = 业务量级上来、或压测暴露瓶颈。
- **验收（可演示可测）**
  1. 四维度限流可配可演示：造流量 → 429 / 排队 / **预热曲线**（Warm Up 生效）；
  2. 熔断：把 Redis 或 DB 打出异常 → 熔断打开 → 快速失败/降级 → 恢复后半开探测成功（给出状态变化曲线）；
  3. 一键降级演练：关掉一个非核心功能（如触达外呼 / 报表查询），核心领券链路仍可用；
  4. 三类熔断/开关的边界有对照文档与用例；
  5. **租户策略可演示**：给两个租户配不同的限流阈值 → 同样的流量下，一个被限、一个不受影响；
     改一个租户的超时/熔断配置 → 不重启、不影响其他租户；把配置读坏 → 回落默认值且有日志。
- **学习产出**：三种限流算法各自适合什么场景（为什么网关层常用令牌桶、削峰用漏桶）；Warm Up 为什么能保护冷启动；熔断状态机与半开探测；开关与熔断的分工；**"租户身份"与"租户策略"的区别**（前者是认证结果，后者是可运营的配置）。
- **债务挂接**：L18（限流/风控拆债）中的"限流最小版"在此销账；L33（重试预算）与超时预算相关，随本阶段或增量清。

### S3 发放链路对标重做（同步 + 异步双模式 + 对账术语对齐）

- **对标依据**：秒杀标准链路"Redis 预扣 → MQ 异步落库"（Lua 原子扣减、后台平滑消费、消费幂等、DLQ、回滚）；对账"数据准备 → 轧账 → 平账"三阶段与差异分类（长款/短款/单边账/状态不一致）（来源见能力地图域 ⑤⑥）。
- **做什么**
  1. **术语与结构对齐**（不改能力，改命名与文档）：世代 → **批次快照**；巡检 → **轧账**；deep 修复 → **平账/差错处理**；漂移表 → **差错台账**；差异分类补上业界词（长款/短款/单边账/状态不一致）与现有方向判据的映射。
  2. **新增异步模式**（与同步模式并存，按活动配置切换）
     - 受理入口：Redis 预扣 → 入 MQ → 返回**受理号**；配套**结果查询**接口（按受理号/requestId 查券是否到账）。
     - 消费端落库：复用同一段发券事务逻辑（券 + 事件 + 发件箱 + 过期任务），消费幂等（event_no/requestId 双锚）。
     - 回滚策略：能拿到原因（限领/下线）→ 按原因处理；**拿不到原因 → 一律"钉零 + 告警"**（宁可少卖不可超发），并在文档里论证为什么不能盲回滚（过补偿自持环）。
     - 切换开关：按活动配置 `issue_mode = sync|async` + 预估 QPS 阈值建议（文档给出建议规则）。
  3. **消息顺序性**：为发放事件加分区键（券/用户维度），保证同券事件有序；或明确声明"本系统事件无顺序依赖"并说明理由。
  4. **压测对比**（见验收）。
- **模拟什么**：无。
- **验收（可演示可测 + 目标数字）**
  - **功能**：两种模式各跑完整生命周期（领/用/退/过期），结果一致；异步模式的"受理 → 到账"链路可观测。
  - **正确性硬指标**（两种模式都必须满足）：**超发 = 0**（DB `SUM(used) ≤ quota` 且 Redis 与 DB 双口径核对一致）、**重复发券 = 0**、**最终一致收敛 ≤ 60 秒**（用现有对账体系验证）。
  - **性能目标**（WSL2 同机压测，数字为**下限**口径）

    | 模式 | 目标 QPS | 成功率 | P99 | 说明 |
    |---|---|---|---|---|
    | 同步（现状优化后） | ≥ 1000 | ≥ 99% | ≤ 100 ms | 现状实测：2000 并发下 ok=246~1000、大量 DB 资源失败 → 需先解连接池/超时（L31 已外部化），再做压测配平 |
    | 异步（受理路径） | ≥ 3000 | ≥ 99.9% | ≤ 20 ms | Redis 预扣路径；落库端平滑消费不丢 |

    对比表须包含：QPS / 成功率 / P99 / DB 峰值 CPU / **用户语义**（同步=立刻拿券；异步=受理号+稍后到账）。
  - **口径声明**：本机同机压测（应用+MySQL+Redis+压测线程共享资源）→ 数字是**下限不是天花板**；阶梯加压/拐点/soak/容量评估表归后置的压测批。
- **学习产出**：预扣/背压/最终一致；为什么同步的"在途"有硬上界而异步没有；盲回滚为什么会造成自持环；两种模式各自的失败代价。
- **债务挂接**：L36（发件箱索引）、L33（重试预算参数化）、L41②（11c 文档同步）在本阶段顺手清；L28/L29/L32/L35 按"止损清单"**冻结不修**（见 §5）。

### S4 优惠计算引擎（中台的"脑子"）

- **对标依据**：淘宝价格服务（到手价预计算 + 责任链/中介者/适配器）；抖音四层优惠（单品级→店铺级→跨店级→红包）+ 递进式计算（上一层折后价作为下一层门槛）+ 同层择优（按金额取最大）+ 数量上限 + 配置期模拟校验（来源见能力地图域 ①）。
- **做什么**
  1. **规则模型**：券类型（满减/折扣/立减/兑换/运费）、门槛、面额/折扣率/封顶、**适用范围**（全场/品类/品牌/门店/指定 SKU）、有效期、叠加层级、互斥组、优先级、每人限领。
  2. **试算接口**：输入商品行（SKU+数量+价格）→ 返回可用券列表 + **最优券组合** + **到手价**（可指定"允许叠加"策略）。
  3. **核销算钱**：`ConfirmRequest` 改为传"订单/商品行金额"，平台算钱并落 `discountAmt`；旧字段保留过渡期（兼容老调用方）。
  4. **配置期校验**：保存/发布规则时模拟叠加场景，折后价低于阈值（可配置，如原价 50%）→ 告警或阻断上线。
- **模拟什么**：**商品目录端口** `ProductCatalogPort`（模拟商品表：SKU/名称/价格/品类/品牌/门店；适配器：本地模拟表 / 请求内联 / 将来接真实商品系统）。
- **验收（可演示可测）**
  - 一笔多商品订单：给出手到价 + 最优组合，与手工核算一致（黄金用例表 ≥10 条，覆盖满减/折扣/封顶/门槛/互斥/叠加/单品范围）。
  - 配置期校验：造一个"叠加后低于阈值"的规则 → 上线被拦/告警。
  - 兼容性：老调用方（传 discountAmt）不炸。
- **学习产出**：为什么价格计算要"分层 + 递进门槛"；同层择优的算法（组合枚举 vs 贪心的取舍）；扩展点设计（新增玩法不改核心链路）。
- **债务挂接**：docs/05"优惠计算引擎 ❌"销账；L23（usage 侧无 userId 的路由广播）在本阶段评估是否随契约改造顺带解决。

### S5 钱的后半程（优惠成为可对账的钱）

- **对标依据**：优惠**三要素（来源/金额/承担主体）**；券模板配承担规则（比例/固定/阶梯）；**核销后重算分账**；退款按比例回收 + 下期轧差；账单三态（一致自动核销/差异挂账/人工调整留痕）；编号规范；异常场景清单（来源见能力地图域 ④）。
- **做什么**
  1. **主体与承担**：主体（平台/商户/供应商）、券模板承担规则、`coupon_share_detail` 落账（核销触发，按商品行×主体拆分）。
  2. **退款冲销**：退款事件 → 按承担规则回收补贴 → 生成冲销流水；**跨周期自动轧差**。
  3. **预算**：活动预算池 + 超预算闸门 + 发放速率控制（每秒 N 张）+ 简单分配规则（人群优先级/先到先得）。
  4. **结算与对账**：T+1 结算汇总（各方应收应付）、账单三态、差异工单（人工调整留痕，**不修改最终金额**）。
  5. **编号规范**：订单号 / 支付流水号 / 退款单号 / 退款批次号 分离（对齐业界教训）。
- **模拟什么**：无（主体与商户表自建，先 2 个主体：平台 + 商户）。渠道账单（银行/支付渠道）用**导入文件**模拟（对齐大厂"文件上传"接入模式）。
- **验收（可演示可测）**
  - 平台券 + 商户券混合的一笔核销 → 退款全链路：产出各方应收应付变动、日汇总账单、冲销记录，可逐笔追溯。
  - 预算闸门：预算耗尽后发券被拦（可重试/可配置行为）。
  - 账单三态：造三种差异各一条，验证"自动核销/挂账/人工调整留痕"。
- **学习产出**：分账基数为什么不因优惠变化；退款轧差与跨月处理；账单三态与审计留痕；为什么"券核销是成本、过期才是收入"。
- **债务挂接**：L24（退款三矛盾）在此**裁决并实施**；L17（追加库存/下线）在 S6 的运营闭环里做，预算部分在此。

### S6 运营与发放玩法

- **对标依据**：八种投放方式；券码体系（结构化编码 + 签名防伪 + 码池 + BitMap 判状态）；人群包（标签圈选/名单导入/分位数筛选/相关度分配）；触达（多渠道 + 频控 + 免打扰 + 营销画布 + 自动化规则）；运营闭环（追加/下线/停发/复制）（来源见能力地图域 ②③）。
- **做什么**
  1. **运营闭环**：模板追加库存（appendStock：DB 额度 + Redis 回补 + 清停流牌 + 批次快照）、下线/停发/恢复、复制模板、有效期调整；**审批最小版**（关键操作需第二管理令牌复核）。
  2. **发放方式扩展**：主动发券批次（选人群批量发/定时发/触发式发：如"领券后 3 天未使用"）、**券码/兑换码**（生成 + 兑换核销）、分享裂变（邀请码/助力）、口令。
  3. **人群与定向**：标签定义与取值（端口）、**人群包**（规则群组 + 静态名单导入）、定向发券、差异权益（按人群给不同券）、按客单价分位数筛选（对齐大厂做法）。
  4. **触达**：`message_task`（待发→发送中→已发/失败重试）+ 模板管理 + 频控/免打扰 + **营销画布最小版**（定时/条件触发链路：如"券到期前 1 天提醒"）。
- **模拟什么**：**画像端口** `UserProfilePort`（模拟标签表 / 请求内联 / 将来接 CDP）；**触达端口** `MessageChannelPort`（落表通道 / 控制台通道 / 真通道接入位）。
- **验收（可演示可测）**
  - 运营能建活动 → 圈人（规则+名单）→ 发券（立即/定时/触发）→ 在活动详情看到结果。
  - 券码：生成 1 万张、兑换（含防爆破：错误码尝试阈值锁定）、防伪校验。
  - 触达：一条"券到期提醒"自动化链路跑通，触达日志可查，频控生效（同一人当天不重复打扰）。
  - 追加库存：追加后立即可卖，账目自愈（对账干净）。
- **学习产出**：券码为什么需要校验位与签名；人群圈选的两条路（规则 vs 名单）；触达频控为什么必须做；营销画布的触发模型。
- **债务挂接**：L17（appendStock/下线）销账；L1（审批流）做最小版。

### S7 风控与安全

- **对标依据**：设备指纹（Canvas/WebGL 等硬特征哈希）、IP 画像、五道防线（验证码/设备上限/黑名单/注销库/失败封禁）、实时规则（策略即代码）、券码防爆破、审计与脱敏（来源见能力地图域 ⑥）。
- **做什么**
  1. 设备指纹端口 + 本地实现（特征哈希 + Bloom 去重）。
  2. 名单库（黑名单/白名单/注销库）+ 风控规则表（可配：频次/设备数/IP 段/行为特征）+ 规则命中审计。
  3. 领取链路接入风控（现有 IP 频控 → 扩展为多维）；券码兑换的错误尝试锁定与告警。
  4. 安全加固：越权防护（接入方只能操作自己的数据）、敏感字段脱敏、操作审计（谁在什么时候改了什么）。
- **模拟什么**：**设备指纹端口**（本地哈希实现即可，不需外部服务）。
- **验收（可演示可测）**
  - 三类刷券脚本被拦：高频同 IP、多账号同设备、验证码暴力尝试；拦截原因可查、可申诉（白名单）。
  - 越权用例被拒（A 应用查 B 应用的数据）。
- **学习产出**：风控的"规则 vs 模型"边界；为什么会误伤以及怎么留申诉口；设备指纹的稳定性与隐私边界。

### S8 "计"与复盘

- **对标依据**：营销看板 + AB 实验 + 效果归因（来源见能力地图域 ③效果复盘）。
- **做什么**：发/领/用/退/过期/成本/ROI 的日汇总表与看板接口；AB 实验位（两套规则/两个人群对比）；活动效果归因（领券→核销转化、成本回收）。
- **验收（可演示可测）**：一个活动从上线到复盘的完整数据链（造数 → 看板数字与手工核算一致 → AB 对比出结论）。
- **学习产出**：指标口径（发放量/领取量/核销量/核销率/成本/ROI）为什么必须写死定义。
