# 限流选型：业界调研与决策（2026-10-08）

> **这份文档解决什么**：动手改限流之前，先把"业界怎么做"查清楚，再决定"我们该怎么做"。
> 触发它的是用户的一句要求——"先调研业界是怎么做的，对于一切阉割版的功能实现、
> 重复造轮子的实现，都不要了"。
>
> **调研方式**：4 个独立视角并行（业界方案全景 / 接口契约设计 / 场景匹配与迁移代价 /
> 全项目自研盘点），全部要求联网核实到**具体版本、真实 API 签名与出处**。
> 下面凡是"某库怎么做"都有出处，凡是"大厂怎么做"只讲到**可核实的类型分布**。

---

## 一、触发事件：我们那个接口契约，业界七家没有一家这么做

上一版的限流器接口是：

```java
boolean tryAcquire(String key, int limit, Duration ttl);

/**
 * @param key 计数器键（**必须自带窗口标识**，如 ...:1712345678 表示某一秒）——
 *            窗口切换靠换 key 实现，不需要清理旧键（TTL 会收尸）
 */
```

调用方（`OpenApiQuotaFilter`）照着做了——把"当前秒"拼进键：

```java
String key = QPS_KEY_PREFIX + appId + ":" + (System.currentTimeMillis() / 1000);
```

**后果**：滑动窗口会在基础键下面再派生 `:{窗口号}` 子键，与调用方拼的"秒"重复。
于是它想读的"上一窗口"（`...:1699999999:窗口号`）与它实际读的（`...:1700000000:窗口号`）
根本不是同一个键——**`prev` 恒为 0**，滑动退化成"每秒重置的固定窗口"。

**而运维那边看到的是**：给租户配了 `rate_limit.algorithm=sliding_window`，以为解决了
边界双倍问题。**实际上拿到的是和原来一样的行为，而且没有任何东西会告诉他。**

### 调研核实：主流方案怎么表达"限流主体"

| 方案 | 真实 API（核实自官方文档/源码） | 要求调用方传"带时间的键"吗 |
|---|---|---|
| Guava `RateLimiter` | `RateLimiter.create(permitsPerSecond)` / `acquire()` / `tryAcquire()` | 否 |
| Bucket4j | `BucketConfiguration.builder().addLimit(...)` / `bucket.tryConsume(1)`；分布式 `proxyManager.getProxy(key, () -> config)` | 否 |
| Redisson `RRateLimiter` | `trySetRate(RateType, rate, interval)` / `tryAcquire()` | 否 |
| Sentinel | `SphU.entry(resourceName, ...)` / `FlowRule` | 否 |
| Resilience4j | `RateLimiterConfig.custom().limitForPeriod(n).limitRefreshPeriod(d)` | 否 |
| Spring Cloud Gateway | `RedisRateLimiter`（`replenishRate` / `burstCapacity`）+ `KeyResolver` | 否 |
| redis-cell | `CL.THROTTLE key maxBurst tokensPerPeriod period` | 否 |

**七家，0 命中。**

**正确的契约**：调用方只说"**限谁**"（主体，纯标识）；**限多少、限多久是规则（配置侧）；
窗口怎么切、状态怎么存是实现的私有职责。**

## 二、第二个发现：**"三算法可切换"在业界没有对应物**

我们曾有一个配置项 `rate_limit.algorithm`，让租户在
`fixed_window` / `sliding_window` / `token_bucket` 之间选。

调研核实：**主流方案不是"同一接口下三种算法"，而是各自选定的语义**。

| 我们以为在"选算法" | 业界对应的是什么 |
|---|---|
| 固定窗口 | Spring Cloud Gateway 的 `refillStyle=INTERVALLY_ALIGNED`（对齐墙钟补充） |
| 滑动窗口 | Redisson `RRateLimiter` 的**滚动窗口**（Redis 里一个 zset，按时间戳清理） |
| 令牌桶 | Bucket4j 的 `refillGreedy` / redis-cell 的 **GCRA** |

**为什么主流避开另外两个**：

- **固定窗口**：边界处最多放过**两倍**上限（上一个窗口末尾用满 + 下一个窗口开头又用满）。
- **滑动窗口日志**：每个请求一条记录，存储与清理开销大。

**令牌桶**成为主流的理由：允许突发（符合真实流量）、状态极省（令牌数 + 最后补充时间两个字段）、
参数语义清晰（速率 + 容量）。

**结论**：那个配置项是**自造的，而且是坏的** —— 已删。

## 三、选型：为什么是 Bucket4j

| 方案 | 核实到的事实 | 判断 |
|---|---|---|
| **Bucket4j 8.21.0** | Apache-2.0（**"Redis 集成要收费"是误传**——收费的只有 Java 8 构建，作者单独维护老 JDK，约 50€）；471 KB、**零新传递依赖**；官方支持 Lettuce 集成 | ✅ **选它** |
| Redisson `RRateLimiter` | 真实算法是**滚动窗口**（不是令牌桶）；无预热参数；**12 MB 传递依赖**，且必须自带 Redis 客户端 | ❌ 双客户端栈的代价太大；3.x 线已收尾 |
| Sentinel | 预热是它唯一做成官方流控效果的方案（`coldFactor` 默认 3，源自 Guava 算法）；但**集群限流不基于 Redis**（要走 Token Server + Netty） | ❌ 对一个单机项目太重 |
| Resilience4j `RateLimiter` | **单 JVM**；官方 issue 明确回复"不持久化任何东西"，并建议要分布式的去看 Bucket4j | ❌ 保留它做**熔断**（那正是它的强项）；配额不能用它 |
| Guava `RateLimiter` | 单机；有 `warmupPeriod`（我们那个预热装饰器的灵感来源） | ❌ 不能分布式 |

**Bucket4j 的决定性优势**：**可以复用项目现有的 Lettuce 连接**
（`LettuceConnectionFactory.getRequiredNativeClient()` → 自建 `StatefulRedisConnection`），
不引入第二个 Redis 客户端栈。这一点经实测确认（见 `Bucket4jWiringTest`）。

**代价要诚实说**：真正能删掉的自研代码只有约 265 行；"按租户动态改限额"要改用
`replaceConfiguration`。**净收益是"契约正确、不再骗人"，不是"少写代码"。**

## 四、大厂怎么做（只讲可核实的类型分布）

调研能核实的是**做法的类型**，不是"某公司用了某库"：

1. **自建流量防护体系的**（阿里、字节这类）：限流做在接入层/网关，要**全局精确配额**
   （跨机房、跨服务），所以走自研 Token Server 那一套。**阿里开源的 Sentinel** 是这条路的公开版本。
2. **用 Spring 生态的**：**Spring Cloud Gateway 官方的 `RequestRateLimiter`** 就是
   **Redis + Lua 实现的令牌桶**（参数只有 `replenishRate` 与 `burstCapacity`）。
3. **Redis 官方的答案**：7.0 提供的 `redis-cell` 模块用 **GCRA** 算法——
   说明"把限流做进 Redis、用原子脚本"是共识。

**三条路的共同点比选哪个库更重要**：

> **没有人做"N 种算法可切换"。** 每家选**一种**语义做扎实，参数只有"速率 + 容量"这类
> 业务能理解的量。

## 五、这次改造实际踩到的两个坑（都写进了代码注释）

### 5.1 坐标与包名不一致

```
Maven 坐标：com.bucket4j:bucket4j_jdk17-core
Java 包名：io.github.bucket4j.*
```

照官网 groupId 写 import（`import com.bucket4j.Bucket`）会编译失败。
另外制品按 JDK 分档：必须用 `jdk17` 坐标；网上老教程常引用的
`com.bucket4j:bucket4j-redis`（Jedis 版）与 `bucket4j_jdk17-redis` **都已停更**。

### 5.2 配置随桶状态一起持久化在 Redis（分布式限流的固有特性）

桶一旦建出来，**它的容量与补充速率就存在 Redis 里了**。
所以"给某租户把限额从 1000 改成 2"，如果只是下次调用传个新 config，**不会生效**。

**实测**：前面的用例把限额配成 1000 建了桶，清掉配置改回 2 之后，连打 20 次仍然全放行。

**两种解法与我们的选择**：

| 解法 | 说明 | 我们的判断 |
|---|---|---|
| Bucket4j 的隐式替换 `withImplicitConfigurationReplacement(version, strategy)` | 版本号由调用方提供，库比较"存储的版本 < 提供的版本" | ❌ **先试过，不成立**：它要求版本号**单调递增**，而配置哈希不单调——`limit=1000` 的指纹 33961 > `limit=2` 的指纹 3023，**改小限额时不会触发替换** |
| 显式 `bucket.replaceConfiguration(config, strategy)` | 直接替换，无版本约束 | ✅ **采用**，并加一个本地指纹缓存（Caffeine，TTL 30 秒）——只在"本实例观察到配置变了"时才替换，避免每次调用多一次 Redis 写 |

**已知的取舍**：多实例下改限额的传播有延迟（≤ 指纹缓存的 TTL）。
这与项目里租户配置缓存本身的行为一致（那边也是"本实例立即、其他实例等刷新"）。

## 六、顺带修掉的两条"一直在的时序依赖"

换实现之后，两条用例暴露了它们**本来就存在**的时序依赖：

1. `OpenApiQuotaIntegrationTest.tenantConfig_overridesRegisteredThreshold`
   原本"连打 5 次必被拒"——隐含"5 次落在 2 秒内"。旧实现因为键里带"秒"、
   窗口实际只有 1 秒，所以更容易撞上；新的令牌桶窗口是完整的 2 秒，于是暴露。改成连打 20 次。
2. `OpenApiQuotaIntegrationTest.warmUp_throttlesDuringColdStart`
   上一轮已经改成"把阈值降到 1、连打 3 次"，见工作日志。

**共同点**：都是"用不可控的量卡边界"——机器快慢、JVM 运行时长、套件里的位置。

## 七、这次改造**没有**动的东西（附理由）

盘点结论：全项目约 20 个自研点里，真正属于"有成熟库但没去查"的只有 4 处，
限流是其中最硬的一处。其余多数是：

- **模式实现**（没有对位库，或库的收益极小）：发件箱、幂等、签名协议、对账巡检、
  状态机、故障注入。
- **业务必要**（领域专用）：库存桶化、守恒式对账、分片路由。

**明确不推倒它们**——那会把"该换的"和"该留的"一起搅乱。

其余三处（TraceIdFilter → Micrometer Tracing；RedisScanLock → ShedLock；
`IpRateGate` 与固定窗口的实现重复）另行处理。
