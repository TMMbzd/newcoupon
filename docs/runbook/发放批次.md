# 运维手册：发放批次（批量/定时任务、兑换码、预算）

> 面向值班/运营。覆盖 V6 阶段 1 上线的三个能力：批量发放任务域（V39）、兑换码域（V41）、
> 预算账本（V42）。代码提交：f158e5e…b2b9402（2026-11-02/03）；验收测试：
> `GrantTaskIntegrationTest` 12 例、`CouponCodeIntegrationTest` 7 例、`BudgetIntegrationTest` 10 例。

## 1. 开关一览（默认全关，逐个灰度）

| 开关 | 默认 | 作用 | 关掉的后果 |
|---|---|---|---|
| `coupon.grant.worker.enabled`（env `GRANT_WORKER_ENABLED`） | false | 批量任务 worker | 任务受理正常但**永不执行**（受理端点不依赖它） |
| `coupon.code.reap-enabled` | false | 兑换码 LOCKED 残留独立回收 | 崩窗残留码靠 grant worker 顺带回收（没开 grant worker 则需手动调 `BudgetService`/`CouponCodeService.reapStaleLockedCodes`） |
| `coupon_budget_reconcile`（BudgetReconcileJob 的条件装配） | false | 预算对账 | 无小时级钱账巡检；对账可手动触发 runOnce |
| 活动行 `budget_enabled` | 0（DB 列） | 预算闸门 | 该活动发放不过预算，行为与阶段 1 之前完全一致 |
| `coupon.activity.check-enabled` | false | 建券校验活动存在/归属 | 建券不校验 activityId（存量兼容；开启前先补齐活动数据） |

**开启顺序建议**：先开对账（观察一轮绿）→ 开 grant worker → 按活动开预算。

## 2. 值班速查

### 任务卡在 RUNNING / CANCELING 不动
- 判断：`GET /open/v1/grant/tasks/{taskNo}` pending 长时间不变。
- 根因两类：① worker 没开（最常见，看开关表第一行）；② 收尾竞态让路（有 reap 兜底，
  worker 下一轮 5 秒内补收尾；日志关键字 `grant task reap`）。
- 手动驱动：调用 `GrantTaskWorker.runOnce()`（XXL `couponGrantTaskJob` 手动触发一次）。

### 任务失败项多（fail 高）
- `POST /{taskNo}/failures` 导 CSV 看 fail_code 分布：
  - `3001` 售罄 → 走 `stock-adjust` 补库存（内部面），再 `retry-failed`（提醒调用方换新 token）；
  - `3002` 已限领 → 正常现象（用户在别处拿过），SKIP 语义，无需处理；
  - `5000/5001` 瞬时 → retry-failed 重发即可。
- **retry-failed 会按当前失败张数重新预占预算**（防账外超发）——预算不足时会拒绝。

### 兑换码全部 3007
- 先查批次状态（内部面 `GET /api/codes/batches/{batchNo}`… 或 DB `coupon_code_batch.status`；
  2A-2 起内部面 GET 要带 `X-Admin-Token`，见 `管理面认证翻面.md`）
  与该模板是否发布/冻结；3007 是统一文案，真实原因在 `coupon_code_redeem_log.fail_reason`。
- 每身份 10 次/分钟限流也会表现为 3007（fail_reason=`rate_limited`）——正常防探测。

### 明文导出失败/导出资格被烧
- 导出顺序是"读暂存→CAS 一次性闸门"：Redis 瞬断时**可以重试**（资格未消耗）；
  一旦成功过一次，第二次必 4002。崩在"成功后响应未送达"→ 明文已离开系统，
  无法重新导出（明文只在 Redis 暂存 24h，TTL 后彻底不可导）。
- 兜底：24h 内可人工读 Redis 键 `c:code:export:{batchNo}`（需 DBA），此后只能作废批次重建。

### 预算相关
- 3009 报错：`coupon_budget_account` 查该活动 reserved/consumed/total；追加预算=改活动
  `budget_amount` **并**同步改账户行 total（账户 total 是懒建时的快照，不随活动自动更新——
  已知边界，调大时两处一起改）。
- `BUDGET_RECONCILE_*` 漂移告警（stock_drift_log）：等式⑤（consumed vs 已发券Σ成本）出现
  差异≈有过"发券成功但结算未到"的崩窗，方向是多留池子不超发——人工核对后可调账（走
  `BudgetService.adjust` 预留口或 SQL+留痕）。

## 5. 安全纵深登记（2A）

- **Redis 会话序列化**：spring-session 默认 JDK 序列化（`c:session:*`）。攻击前提=攻击者已拿到
  Redis 写权限（届时业务键同样可写，属同层沦陷）；缓解=启动参数加类白名单，例如：
  `JAVA_TOOL_OPTIONS="-Djdk.serialFilter='com.newcoupon.**;org.springframework.security.**;org.springframework.session.**;java.util.*;java.time.*;!*'"`
  （顺序即白名单到黑名单；上线前以实际会话属性类清单校准）。后续可换 Jackson 会话序列化彻底消除该面。
- **登录锁定键=用户名+来源 IP**（`c:admin:auth:fail:{user}:{ip}`）：直连取 remoteAddr——
  **经反向代理部署必须改取受信的 X-Forwarded-For**，否则所有请求同 IP 会让锁定退化成全局。
- 登录节流：每 IP 10 次/分钟（`c:admin:auth:ip:{ip}`，Redis 故障 fail-open）。

## 6. 租户生命周期与沙箱（2B 第一刀，V45）

> 代码：`AppLifecycle`（状态机）/`TenantLifecycleService`+`TenantLifecycleTxService`（编排与事务）/
> `EnvironmentGuard`（资金边界）/`OpenApiAuthFilter` 第 3.5 步（6013）。
> 验收：`TenantLifecycleIntegrationTest` 8 例。

### 6.1 状态机图（唯一合法路径；非法组合一律 4002，报错会带当前状态允许的动作）

```
DRAFT ──submit_review──▶ PENDING_REVIEW ──approve_sandbox──▶ SANDBOX_ACTIVE
                                                               │ activate
ACTIVE ◀──────resume────── SUSPENDED ◀──────suspend──────────┘
   │                              │
   └────────────close─────────────┴──▶ CLOSING ──confirm_close──▶ CLOSED ──delete──▶ DELETED
```

操作一律走内部面：`POST /api/apps/{appId}/lifecycle`，body `{"action":"...","reason":"..."}`
（权限 `tenant:lifecycle`；X-Admin-Token 或控制台会话）。**没有整行更新接口，也不提供租户自助端点**——
生命周期是平台运营动作。入口态裁定：`POST /api/apps` 建的 PROD 应用直接 ACTIVE、SANDBOX 应用直接
SANDBOX_ACTIVE（"内部面建=已审"）；DRAFT/PENDING_REVIEW 留给后续自助注册，运营可 SQL 置入后正常走链。

### 6.2 各状态的业务效果

| 状态 | 开放面（/open/v1） | 密钥 | 数据 | 可逆性 |
|---|---|---|---|---|
| ACTIVE / SANDBOX_ACTIVE | ✅ 正常 | 有效 | 正常 | — |
| SUSPENDED | ❌ 403 + **6013** | 保留 | 保留 | `resume` 即恢复 |
| CLOSING | ❌ 6013（写入先冻结） | 保留 | 保留 | 只能 `confirm_close` 往前走 |
| CLOSED | ❌ 6013 | **已撤**（零窗口轮换，旧 SK 即时作废） | 保留，`closed_at`+`retention_until`（+180 天）落库 | 终态，只能 `delete` |
| DELETED | ❌ 6013 | 无 | **逻辑死**：行与业务数据都保留，仅记录终态 | 不可逆 |

6013 与 6003 的分工：6013=平台停用你（找运营）；6003=签名错（查自己）。二者文案都不区分内部原因（防探测）。

### 6.3 注销最小闭环（值班 SOP）

1. `close`（→CLOSING）：开放面立即 6013，写入冻结；
2. （窗口内）`GET /api/apps/{appId}/data-export` 导出数据——**一次性**，响应头 `X-Data-Sha256` 校完整性；
   二次请求或注销完成后再导都 4002；导出内容=app 行+模板清单+每模板发放计数（券明细全量导出已裁剪，
   需要时按模板 id 找 DBA 离线导）；
3. `confirm_close`（→CLOSED）：撤密钥+落 `closed_at`/`retention_until`；
4. （可选，需另一管理员在场）`delete`：body 另带 `secondApproverUsername` + `secondApproverPassword`
   （另一个 **enabled** 管理员的登录密码）——最小双人实现，完整审批表登记给 2C；
   `legal_hold=1` 时一概拒绝（审计/诉讼冻结，解除需人工清 0）。

### 6.4 沙箱

- 识别：appId 前缀 `sbx-` 或 `open_app.environment='SANDBOX'`（前缀优先——显式传 PROD 也按沙箱）。
- **券能发、钱不动**：建券/发放/核销照常（分账行也照落）；三处资金边界拦截——
  ① 日账单聚合 SQL 直接过滤沙箱模板（模板账单与主体账单同条件，reconcile 口径一致）；
  ② 真实退款（`TradeTxService.refundConfirm` 入口）4002；③ 预算账户懒建（`BudgetTxService.ensureAccount`）4002。
  预算对账任务（等式①②）跳过沙箱账户。
- **手动事项（本刀不做自动化，登记在此）**：沙箱数据 30 天清理是**人工动作**（按 `retention_until`/创建时间
  批量删，删前确认无 `legal_hold`）；沙箱独立配额也未做（沙箱与生产共用租户配额配置）。

### 6.5 排障速查

- 接入方反馈全线 6013：查 `open_app.lifecycle_status`（suspend/close 链）与事件表
  `open_app_lifecycle_event`（谁在何时做的什么动作，operator=会话用户名/旧令牌记 admin）。
- 误停用：SUSPENDED 可 `resume`；**CLOSING 及之后没有回头路**——误注销需重建应用+重新发密钥，
  这正是 confirm_close 两段式设计的目的（close 先冻结留出反悔窗口，confirm_close 才动密钥）。
- `data-export` 报 4002"一次性"但没拿到文件：导出资格已被消耗（事件表有 data_export 行），
  按事件时间查响应是否送达；确未送达走 DBA 离线导出兜底。


## 7. 租户生命周期与沙箱——审查补登记（2B-1 对抗审查后口径）

- **SUSPENDED/CLOSING 不回收已受理任务**：202 是受理承诺——停用时刻已在队列里的异步任务/批量任务会跑完。
  需要立刻止血：先冻结模板（TemplateLifecycleService.freeze）再处理任务，或在 CLOSING 前等队列排空。
- **activate 翻转 environment 的账单口径**：环境对账单聚合是"当下过滤"——沙箱期核销的分账行在 activate
  后重跑**当日**账单会开始计入（历史日不受影响，账单按 bill_date 聚合当日的行）。要绝对口径干净：跨日晋升
  （当日沙箱收尾、次日 PROD 开张）。
- **双人删除**：必须具名管理员会话发起（旧管理令牌被拒）；第二管理员凭据核验接入与登录同一套锁定计数
  （`c:admin:auth:approver:{user}`，5 次/15 分钟，Redis 故障 fail-closed）。
