## 1. 谁在哪里留痕：三张表的分工（覆盖矩阵）

**写动作按"发起面"分账**：同一业务代码挂在 /api（管理面）与 /open（开放面）两个前缀下时，
管理面发起 → `audit_log`（本刀起，`AdminActionAuditor` 闸门：TENANT 跳过不双写）；
开放面发起 → `open_api_audit` 专表全量覆盖。旧管理令牌（共享机器凭据，actor=SYSTEM）
动作照记——"管理面发生了什么"比"具体哪个人"更不可让步，个人身份由控制台会话面补齐。

| 动作 | 落哪张表 | action / 表内标识 |
|---|---|---|
| 核销（动钱） | `audit_log` | `COUPON_CONFIRM`（@AuditLog 切面） |
| 退款（动钱） | `audit_log` | `COUPON_REFUND`（@AuditLog 切面） |
| 登录成功/失败/锁定 | `audit_log` | `ADMIN_AUTH_LOGIN_SUCCESS` / `_FAILED` / `_LOCKED` |
| 登出 / 强制下线 | `audit_log` | `ADMIN_AUTH_LOGOUT` / `ADMIN_AUTH_FORCE_LOGOUT`（actor=操作者，目标进 resourceId/detail） |
| 会话被终止（四道核对任一失败） | `audit_log` | `ADMIN_AUTH_SESSION_TERMINATED` |
| **注册接入方（M3 新增）** | `audit_log` | `APP_CREATE` |
| **接入方启停（M3 新增）** | `audit_log` | `APP_SET_STATUS` |
| **密钥轮换（M3 新增，此前零留痕）** | `audit_log` | `APP_ROTATE_SECRET` |
| **建活动（M3 新增，管理面发起）** | `audit_log` | `ACTIVITY_CREATE`（开放面建活动在 open_api_audit） |
| **模板发布/库存调整/冻结/解冻/下线/重上线（M3 新增，管理面发起）** | `audit_log` | `TEMPLATE_PUBLISH` / `TEMPLATE_STOCK_ADJUST` / `TEMPLATE_FREEZE` / `TEMPLATE_UNFREEZE` / `TEMPLATE_OFFLINE` / `TEMPLATE_REONLINE`（技术明细在 coupon_stock_adjust_log 专表，这里记"谁"） |
| 审计查询 / 详情 | `audit_log` | `AUDIT_QUERY` |
| 审计导出受理 / 下载 | `audit_log` | `AUDIT_EXPORT`（after 快照的 `phase` 区分受理/下载） |
| 开放面每次 API 调用（请求级细节） | `open_api_audit` 专表 | appId/资源/结果码/耗时——高频全量，不进哈希链 |
| 租户生命周期九态迁移 | `open_app_lifecycle_event` 专表 | 状态机事件流，含双人删除与数据导出留痕 |
| 租户配置写入/删除 | `open_app_config_log` 专表 | 键值变更 + operator（audit_log 不重复记） |
| 审计 verify 端点 | **不写审计** | 只读完整性检查、无数据出域（2C 裁定；矩阵在此明示） |

**尚未挂管理面审计的写动作（登记，下刀补齐）**：预案升降级（/api/switch-plans）、
价格异常人工处置（/api/pricing-exceptions/{usageNo}/resolve）、批量任务取消/重试
（/api 侧调用时）。它们是低频治理动作，先登记不静默。

**判据一句话**：动钱/动身份/动密钥/数据出域 → `audit_log`（哈希链防篡改）；高频调用与
技术明细 → 专表；两者是不同问题的答案（"谁动过" vs "流量长什么样"），不是冗余。

## 2. actor 四值口径（V46 起）

| actor_type | actor_id | session_id | 出现时机 |
|---|---|---|---|
| `ADMIN` | 管理员 userId（字符串） | 会话**指纹**（SHA-256 前 16 hex） | 控制台会话请求（AdminPrincipal） |
| `TENANT` | appId | 空 | 开放面 HMAC 验签请求（RequestContext.appId） |
| `USER` | （预留） | 空 | C 端调用审计目前在 open_api_audit 专表，audit_log 尚不产出此值 |
| `SYSTEM` | `SYSTEM` | 空 | 后台任务；旧管理令牌（共享机器凭据，无个人身份） |

- **session_id 列是指纹不是凭据（C2）**：会话 id 原值就是 SESSION Cookie 凭据本身，
  审计行能被持 audit:read 的低权限角色查到——原值入库等于把高权限账号的会话凭据
  递给低权限角色（空闲 30m/绝对 8h 内可当 Cookie 劫持）。所有写入统一过
  `AuditActorResolver.fingerprint`（SHA-256 前 16 hex）：同会话多行可关联、不同会话
  可区分、还原凭据不可行。排查"某会话干了什么"拿原始会话 id 现场算指纹再查即可。

- 解析优先级（`AuditActorResolver`）：管理面会话 → 开放面应用 → 系统，顺序固定不可换。
- **userId 列 ≠ actor**：userId 是"操作对象"维度（核销动的是哪个业务用户的券），
  actor 三列是"谁发起"——审计要同时回答两组问题。
- 存量行（V46 前）actor 三列为 NULL：写入时无 actor 概念，不回填（编造比空白更糟）。

## 3. hash_version 语义

| 版本 | 写入方 | record_hash 拼接口径 | 校验 |
|---|---|---|---|
| 1 | V46 前的存量行 | 六要素 12 字段 + prev_hash（**不含** actor 三列） | 按行版本选 v1 算法 |
| 2 | V46 起所有新写入 | 六要素 + actor 三列 + prev_hash | 按行版本选 v2 算法 |

- 历史链**永不重算**：重算历史哈希等于平台亲手改写防篡改凭证。
- **存量 v1 行的已知盲区（L81，登记）**：v1 时代 createdAt 带纳秒进哈希、而 DATETIME
  列秒级落库四舍五入——v1 行的存储哈希从写入起就不可能从库内数据重算（"重算补验"
  数学上不可行）。verify 因此对 v1 行**豁免内容重算、只做衔接校验**：删行/插行/
  改链头一律可检出；**改 v1 行内容（不动哈希）衔接不破、检测不到**——历史数据的
  永久盲区，兜底=应用层只写不改不删（无 UPDATE/DELETE 路径）+ DB 层审计日志。
  v2 起新写入写时截断到秒，内容+衔接全量可验。

## 4. 查询端点（内部面，全部 POST，`/api` 管理面认证）

权限：query/detail/verify 要 `audit:read`；export 族要 `audit:export`
（V44 种子，PLATFORM_AUDITOR 角色两者皆有；旧管理令牌持全量权限码）。

| 端点 | 请求要点 | 响应要点 |
|---|---|---|
| `POST /api/audit/query` | 过滤 appId/actorType(+actorId)/action/resourceType/resourceId/resultCode + 时间窗（≤31 天，都空=最近 1 天，必须成对给）；`limit`≤200 默认 50；`cursor`=上页 nextCursor | 行按 id 升序；快照只给 200 字摘要；`nextCursor` 空=末页 |
| `POST /api/audit/detail` | `{id}` | 快照全文 + prev/record_hash + hash_version |
| `POST /api/audit/verify` | 无参 | `{ok:true, checked}` 或第一个断点 `{ok:false, breakAtId, reason}` |
| `POST /api/audit/export` | 过滤同 query | `{jobNo}`，构建异步进行 |
| `POST /api/audit/export/status` | `{jobNo}` | PENDING/RUNNING/DONE/FAILED（DONE 带行数+SHA-256） |
| `POST /api/audit/export/download` | `{jobNo}` | CSV 字节流（UTF-8 BOM；**一次性**，二次 4002） |

- 游标分页禁 OFFSET：审计只写不删，游标（=上页末行 id）永不错位，任意翻页深度同价。
- 导出 CSV 首行 manifest：`MANIFEST,<行数>,<SHA-256>,<时间窗>,<过滤描述>`——SHA-256 盖
  "表头+数据行"（manifest 自身除外），收件方可离线复核；公式注入防护与 BOM 同 1A 先例。
- 导出行数上限 `coupon.audit.export.max-rows`（默认 20 万）超限任务落 FAILED，提示缩窗。
- 任务有效期 `coupon.audit.export.expire-hours`（默认 24h）：过期不可下载；**惰性清理**
  （下一次受理导出时删过期行，无独立调度）。构建中实例重启 → 任务停 PENDING/RUNNING，
  不会续跑——重新发起即可（审计只读快照，幂等）。

## 5. verify 断链处置（值班速查）

断链 = 有行被删/被改。**没有"修复"动作**——自动接链等于销毁被篡改的证据；哈希链的
价值就是让篡改留痕。处置顺序：

1. `POST /api/audit/verify` 拿 `{breakAtId, reason}`：
   - `RECORD_HASH_MISMATCH`：该 **v2** 行内容被改（重算对不上存储哈希；v1 行豁免内容重算，见 §3）；
   - `PREV_HASH_MISMATCH`：断在前一行与该行之间——中间有行被删（或被插）；
   - `GENESIS_MISMATCH`：首行 prev 不等于 GENESIS 常量（链头被动过）；
   - `CHAIN_HEAD_MISMATCH`：`audit_chain_head.last_hash` ≠ 全表末条 record_hash——
     典型攻击=删掉末尾 N 行并把 head 同步改成新末行（只走链不核头对此失明，故 verify 收尾必做链头对账）；
   - `CHAIN_HEAD_NON_NULL_ON_EMPTY_CHAIN`：表空但 head 残留非空（行被删光）。
   注：head 对账与末次写入存在毫秒级竞窗（写事务先 insert 后 update head）——
   若 reason 落在 CHAIN_HEAD 族且无其它异常，**先复跑一轮 verify 再定性**。
   链头对账的边界也要知道：它抓的是"删尾行但 head 残留/超前/空表非空"；
   攻击者若**同时**把 head 修成新末行哈希，库内证据无法检出——head 与表同库
   同权限，抗"DB 主体亲自作案"要靠库外锚点（WORM 存储/异地日志投递，未实施）。
2. v1 行的内容篡改本身不报警（§3 盲区）——衔接/链头族报警对 v1、v2 一视同仁。
3. 真·断链：封存现场（导出断点前后窗口的 CSV 留证据）→ 按 actor/时间窗反查谁动过 →
   DBA 查 binlog 定位 DELETE/UPDATE 来源 → 安全事件流程。**不要**手工补行/改哈希。

## 6. 每日巡检任务（AuditChainVerifyJob）

| 开关 | 默认 | 说明 |
|---|---|---|
| `coupon.audit.verify.enabled`（env `AUDIT_CHAIN_VERIFY_ENABLED`） | false | 条件装配；关=任务不存在 |
| `fixed-delay-ms` / `initial-delay-ms` | 86400000 / 3600000 | @Scheduled 降级通道节奏（默认一天一轮） |

- 双通道：XXL `couponAuditChainVerifyJob`（主通道，可手动触发）+ @Scheduled 兜底；
  Redis 锁 `c:lock:audit-chain-verify` 多实例单飞（verify 只读，重复跑无害）。
- 断链输出四连：轮次计数 + 指标 `coupon_audit_chain_broken_total{reason}`（告警按它
  响铃）+ ERROR 日志（关键字 `AUDIT CHAIN BROKEN`）+ 断点详情。处置走 §5。
- **监控告警项（M2）**：
  - `coupon_audit_chain_verify_total{result}` 每轮必增（ok/broken/error 三值）——
    三值全无=巡检根本没在跑（先查 `enabled` 开关与调度器，再谈断链）；
  - `coupon_audit_chain_last_success_epoch_ms`（gauge）超 `fixed-delay-ms`+1 小时
    未动=巡检停摆（默认节奏下即 25 小时告警）；
  - `coupon_audit_chain_broken_total` 出现任何增长=立即按 §5 处置。
- 成本口径：每轮全表扫描 + 每行一次 SHA-256（v1 行免；百万行约几十秒、只读不锁写）
  ——按数据量决定开不开、跑多勤；应急时手动打 verify 端点同效（同一份重算逻辑）。
