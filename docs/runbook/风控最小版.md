## 1. 架构一览（谁在什么时候调谁）

```
调用方（/api 内部面 或 /open 开放面）
  │  POST /api/coupons/receive  （body: requestId/userId/templateId；头: X-Device-Id 可选）
  ▼
RiskContextFilter（HIGHEST+5，所有路径）
  │  X-Device-Id（≤128，超长视为缺失）+ clientIp（容器解析）→ ThreadLocal
  ▼
RiskControlFilter（HIGHEST+10，仅 /receive*）          ←—— 既有 IP 频控，本刀未动（两条防线论）
  ▼
ReceiveAppService.receive（领券同步主入口——4A 唯一接线点）
  │  模板校验后、时间预算/预算租约/库存/落库之前（整段进 mysql 熔断段，审查 C8）：
  │  enabled(RISK_DECISION, appId)? 三层取值
  │    ├─ 关 → 整段跳过（零额外查询，幂等快查也不做）
  │    └─ 开 → ①幂等快查：同 requestId 已发过券=重放旧结果，不做风控（审查 C2：
  │             拉黑后重试旧请求拿回 duplicated，不是 7003——已成立的事实不被风控改写）
  │          ②decide(scene=RECEIVE, appId=模板归属租户, userId, deviceId, ip, requestId)
  │             ├─ 按固定序评估规则（R_LIST_BLACK @Order(100) → R_DEVICE_DAILY @Order(200)）
  │             │    白名单命中→PASS 短路；黑名单→REJECT 终止；灰→REVIEW 继续；设备超阈→REJECT
  │             ├─ 同步写 risk_decision_log（因子快照全量；写失败不挡业务：ERROR+指标）
  │             └─ 指标 coupon_risk_decision_total{action}
  │  REJECT → 抛 7003（HTTP 403）；REVIEW/CHALLENGE/PASS → 放行（REVIEW 留痕）
  ▼
既有领券链路（预算/库存/落库……完全不变）
```

**异步 /receive-async 与兑换码 redeem 本刀不接**（避免一刀改所有热路径；刀 2 按场景逐个
评估接线——注意异步受理同样创建库存预扣，接风控的理由与 RiskControlFilter 拦它同源）。

## 2. 决策框架语义

### 2.1 四态动作与合成

| 动作 | 语义 | 领券场景的处置 |
|---|---|---|
| PASS | 放行（无规则命中，或**白名单命中短路**——两种来源靠 matched_rules 区分） | 正常走业务 |
| CHALLENGE | 人机挑战（**本刀保留位**：无规则产出；挑战页/一次性 token/通过后重决策属 4C，登记 §7） | 未产出 |
| REVIEW | 放行但复核：日志 + 指标（灰名单命中） | 正常走业务，事后人工看日志 |
| REJECT | 拒绝 | 抛 7003（HTTP 403） |

**合成规则**：多规则命中取**最严**（REJECT > REVIEW > CHALLENGE > PASS）；白名单 PASS 与
REJECT 终止评估（短路省 IO）。评估顺序=Spring 注入序（@Order），固定不可配——
两三条规则时优先级引擎是负担。

**REJECT 的处置由场景决定，不在框架里**：领券=直接拒绝；退款（刀 2）=**照做+打标**
（合规红线：不能拒绝消费者退款）；核销/锁券（刀 2）按各自风险定。所以 `decide()`
只返回结果不抛异常。

### 2.2 规则清单（最小规则集=代码规则+配置阈值）

| ruleId | 场景 | 判定 | 可回放 | 因子/阈值 |
|---|---|---|---|---|
| `R_LIST_BLACK` | 任意 | 用户/设备/IP 三查名单（等值+平台级/租户级两层+ACTIVE 未过期）：任一维 WHITE→PASS 短路；否则任一 BLACK→REJECT；否则任一 GRAY→REVIEW | ✅（只读当前名单） | `list.user`/`list.device`/`list.ip` =命中的类型串或 `none`；`list.scope` |
| `R_DEVICE_DAILY` | 仅 RECEIVE | 同设备当日领券**尝试**数 > 阈值 → REJECT | ❌（INCR 是副作用，回放跳过并列出） | `device.count`/`device.maxPerDay`/`device.skipped` |

- 设备阈值：`coupon.risk.device-daily.max-per-day`（默认 10，环境变量
  `RISK_DEVICE_DAILY_MAX_PER_DAY`）。**改阈值=改配置+重启生效**（构造期 @Value 单值，
  非租户热更——想验证新阈值的影响，拿历史 REJECT 行回放，见 §2.4）；热更/按租户阈值
  的升级路径=挪进 TenantConfigKey 词表（登记 §7）。
  **计数=受理尝试**（决策时点递增，被拒也计）；**幂等重放不计数**——同 requestId
  已成功发过券的重试在风控之前被豁免（审查 C2），拉黑后重试旧请求拿回旧结果
  （duplicated）而不是 7003。
- Redis 键：`c:risk:dev:{appId}:{deviceId}:{yyyyMMdd}`（INCR + 首次写 EXPIRE 2 天；
  日界靠键名切换）。运维排查命令与 IP 频控同族：`redis-cli --scan 'c:risk:dev:*'`。

### 2.3 开关与租户灰度

- 开关键：`SwitchKey.RISK_DECISION`（`switch.risk.decision.enabled`）。**默认关**——
  全站层 application.yml 显式 `false`（环境变量 `RISK_DECISION_ENABLED`）。
- 三层取值：租户 `open_app_config.switch.risk.decision.enabled` → 全站
  `coupon.switch.risk.decision.enabled` → 默认关。**灰度开法**：先给一个租户配
  `switch.risk.decision.enabled=true`（管理面配置接口），观察
  `coupon_risk_decision_total{action}` 与决策日志，再扩大。
- **关=零变化**：decide 直接 PASS、不写决策日志、热路径零额外 IO（唯一成本是
  RiskContextFilter 的两个 ThreadLocal 操作；含幂等快查在内的一切风控查询都被
  enabled 前置门跳过）。用例钉住（RiskSwitchOffIntegrationTest）。
- **开闸=立即执法，不是观察模式**：名单是存量语义——开闸前建好的 ACTIVE 条目（含
  平台级）在该租户**立即全部生效**，没有"只记录不拦截"的预览期。开闸前先核对：
  `POST /api/risk/lists/query`（status=ACTIVE）过一遍条目数与 expiresAt，确认没有
  建错的/过宽的条目会瞬间放大拦截面；想先观察就用 GRAY（REVIEW 放行留痕）过渡。
- 三级预案（蓝/黄/红）对该开关统一 `false`：预案不做灰度开闸的决策人；已灰度开的租户
  套用预案后会被覆盖回 false（预案全量物化的既定取舍），需要时预案外手工恢复。
  "攻击在途时预案该不该自动开它"留给 4B 接线核销/退款后再定。

### 2.4 决策日志（回放的根基）与回放端点

- **同步写**：异步丢日志=回放失真（"可回放"会静默退化成"部分可解释"且无人知道缺哪段）。
  写失败**不挡业务**：ERROR + `coupon_risk_decision_log_write_fail_total`（涨=这段时间
  不可回放，追存储）。与审计"可丢"语义的差别就在这里：审计丢一行少一行追责线索，
  决策日志丢一行坏的是整段回放口径。
- **行内容**：scene/appId/userId/deviceId/ip + `factors_json`（所有被评估规则的输入与
  结果，LinkedHashMap 序=决策过程回放稿）+ `matched_rules`（产出动作的规则）+ action +
  degraded + trace_id + request_id（幂等键）。
- **degraded=1 的两类原因**（fail-open 且可见）：`device.skipped=missing-header`
  （接入方没接设备头）/ `device.skipped=counter-unavailable`（Redis down，同时
  `coupon_ratelimit_failopen_total{dimension=risk_device}` 计数）。
- **查询**：`POST /api/risk/decisions/query`（risk:read）——过滤分两组：态度过滤
  （scene/action/appId）与**定位键**（userId/traceId/requestId——误杀工单的真实入口）；
  时间窗不传=**默认最近 1 天**（决策日志无归档任务，无界扫描的护栏），传则成对且
  ≤31 天；游标分页。定位键均有索引（idx_user/idx_request/idx_trace）。
- **回放**：`POST /api/risk/decisions/{id}/replay`（risk:read）——按日志行重建上下文，
  用**当前**规则集只读重算，返回 `{originalAction, replayAction, ruleDiff, replayedRules,
  skippedRules}`。**不改原行、不写新行、不产生规则副作用**。规则的重算方式两类：
  纯规则（名单）=按当前数据重查；有副作用的规则（设备日限）=**日志因子×当前配置**
  的纯内存重算（当时的 count 对**当前阈值**重新比较，不碰 Redis 计数器）。用途：
  ①误杀复盘（申诉：现在还拦吗？为什么不拦了？）；②调参验证（改名单/改阈值后回放
  历史 REJECT 行，量化影响再上线）。diff 粒度=命中与否+最终动作（逐规则的当时动作
  在 factors_json 里读）；被跳过的规则如实标"未评估（有副作用且日志因子不足以重算）"，
  **不会**被渲染成"命中→未命中"。

## 3. 设备频控透传约定（给接入方）

- 请求头 `X-Device-Id`：可选，≤128 字符，超长/空白视为缺失（不截断——截断会把两个
  长设备号错误聚成同一设备）。
- **它是透传维度不是可信指纹**：客户端可换头绕过（测试 R7 也如实断言了"换设备头=
  新计数桶"）。价值在挡"不换头的脚本"与"多账号同设备"的可观测性；商用设备指纹 SDK
  只留端口（§7）。
- 不带头的后果：设备日限跳过、决策行 degraded=1，**不挡请求**。
- 详见接入指南 §2（请求头总览）与 §7（7003）。

## 4. 名单管理口径（管理面）

- 端点（全 POST，`risk:write` 写 / `risk:read` 读；V44 既有种子：ADMIN 全量、OPERATOR
  读写、AUDITOR 只读）：`POST /api/risk/lists`（增）、`/api/risk/lists/disable`（停用）、
  `/api/risk/lists/query`（查）。
- **自然键** =（list_type, value_type, value, app_id）：同键已有 **ACTIVE** 行时重放幂等
  返回已存在行（duplicated=true）；已有 **DISABLED** 行时同键 add = **复活**（审查 A 簇
  修复）：DISABLED→ACTIVE 并覆盖 reason/expires_at/created_by，响应 `reactivated=true`。
  复活是"停用后重建"的唯一路径——停用行占着自然键唯一约束，不做复活这个工作流就走不通
  （黑名单静默缺失且无信号）。reason 不参与身份，改 reason=停用后同键重建（新 reason 生效）。
- **平台级 vs 租户级**：`appId` 缺省=平台级（对所有租户生效；存储为空串——MySQL 唯一
  索引对 NULL 互不相等，空串才让唯一键对平台级条目成立）；传了则要求 app 真实存在
  （挂到拼错租户上永远命不中，入口就拒 1002）。
- **value 存明文**：管理面要显示给运营看拉黑的是谁、等值查询即业务查询；名单不是
  凭据（与兑换码存哈希不同），泄漏面=名单本身。**HMAC 化升级路径**（拖库风险下）：
  value 列加哈希影子列（或直接换 HMAC(value, 租户盐)），等值查询改查哈希列，管理面
  显示走"创建时留存的掩码"；列宽 128 已够 HMAC 摘要。
- **IP 型名单=精确匹配**：逐 IP 等值比对——攻击者用代理轮换 IP 可绕过（与所有精确
  IP 防线同限）；CIDR/网段匹配是升级路径（规则升级为区间判定时做，登记 §7）。
- **过期与停用**：`expiresAt` 空=永久；过期后命中自动失效（查询侧过滤，行保留）。
  停用=软删（DISABLED），行保留=申诉/复核的第一现场。
- **白名单优先**：任一维度命中 WHITE 盖过所有 BLACK（跨维度）——运营放行是明确的意思
  表示。写操作审计：`RISK_LIST_ADD`/`RISK_LIST_DISABLE`/`RISK_LIST_REACTIVATE`
  （AdminActionAuditor，2C 模式）。

## 5. 错误码与指标

| 项 | 值 | 说明 |
|---|---|---|
| 7003 RISK_REJECTED | HTTP **403** | 领券被拒（文案不泄漏命中规则——详情查决策日志）；不可重试（重试还会被拦，除非换行为）。**幂等重放例外**：同 requestId 已成功发过券的重试拿回旧结果（1001/duplicated），不吃 7003 |
| `coupon_risk_decision_total{action}` | 四值有界 | 决策分布：REJECT 占比=拦截率、REVIEW 占比=复核队列压力 |
| `coupon_risk_decision_degraded_total{reason}` | 两值有界 | 降级决策：missing-header=租户没发设备头（唯一自动化规则静默归零的盘面信号）/ counter-unavailable=设备计数 Redis 故障 |
| `coupon_risk_decision_log_write_fail_total` | — | 决策日志写失败（不挡业务但不可回放），涨=追存储 |
| `coupon_ratelimit_failopen_total{dimension=risk_device}` | — | 设备计数 Redis 故障放行（与 risk_ip 同族不同维度，不合并计数） |

## 6. 值班速查

- **说"被风控拦了"怎么查**：拿响应头 X-Trace-Id → `POST /api/risk/decisions/query`
  （按 traceId/userId/requestId 定位键过滤）或 SQL
  `SELECT * FROM risk_decision_log WHERE trace_id='...'`
  → 看 action/matched_rules/factors_json（哪条规则、什么输入、为什么）。
- **误杀申诉（名单类）**：查到该行 → `POST /api/risk/decisions/{id}/replay`——重放仍
  REJECT=现行名单还会拦（看 factors 定位证据）；重放 PASS=拦它的名单已变。放人：
  白名单加条目（盖过黑名单）或停用对应黑名单条目。
- **误杀申诉（设备日限类，看 factors 不看 replayAction）**：matched_rules=
  R_DEVICE_DAILY 的行，回放的设备判定=**当时 count×当前阈值**——若用户当天确实领满
  10 次，重放永远 REJECT（这不是误杀是事实）；确认是正常重度用户就调大阈值（改配置
  重启）或给该设备加白名单。回放翻成 PASS 只有两种可能：阈值调大了，或该行是
  无头的 degraded 行（当时就没算）。
- **要调整拦截面**：加/停名单条目即时生效（决策时直查，无缓存）；**停用后重建=同键
  再 add 一次（复活，reactivated=true）**；改设备阈值=改配置重启（非热更，§2.2）。
  改完拿历史行回放量化影响。
- **Redis 故障期间**：设备日限整体失效（放行+degraded+failopen 指标）——IP 频控同款
  哲学：可用性防线不因依赖故障误杀全量，资损另有库存/DB 双防线。看
  `coupon_ratelimit_failopen_total{dimension=risk_device}` 与
  `coupon_risk_decision_degraded_total{reason=counter-unavailable}` 是否停止增长判断恢复。
- **`coupon_risk_decision_degraded_total{reason=missing-header}` 持续增长**：该租户的
  接入方没发 X-Device-Id——设备防线对它没生效，找接入方按接入指南 §2 补头。
- **上线/回滚**：开闸=租户配置 `switch.risk.decision.enabled=true`；回滚=删该配置
  （回落全站 false）。两向都不动数据、不停服务。

## 7. 裁剪登记（本刀明确不做——原因与升级路径）

| 裁剪项 | 为什么不做 | 升级路径（谁触发） |
|---|---|---|
| 规则引擎六表（risk_scene/ruleset/rule/factor/rule_factor/action）+版本灰度热更新 | 两三条规则时引擎是负担：决策路径可审计性（代码规则=看得见的判定）优先于配置灵活 | 规则数明显增长（>5 条）或多环境差异化时上 V6 原文方案：不可变版本+DRAFT→CANARY→ACTIVE+回滚切指针；ruleId 命名与 matched_rules 结构已按可迁移设计 |
| risk_list_hit（名单命中表） | 决策日志的 factors_json 已含命中明细，单独表是重复账 | 需要按名单条目反查"拦过谁"的高频运营动作时再加（或先用日志 SQL 聚合） |
| 人机挑战完整版（CHALLENGE） | 枚举/日志/指标已支持，但挑战页+验证+token+通过重决策是一整个交互闭环 | 4C：一次性 token 返回占位已留（RiskAction 注释）；候选 tianai-captcha（Apache-2.0；AJ-Captcha 停维护不选） |
| risk_review_task 复核表 | REVIEW 的消费方（复核队列）还没建立——先让灰名单日志可查 | 4B：列表/通过/拒绝/证据/操作人+复核人/高金额双人复核 |
| 反作弊日任务 + risk_signal 表 | 信号（退款率/核销率/聚集）需要先有量：日志都没积累就跑任务是空转 | 刀 2 之后：日任务从决策日志+业务表聚合出信号，证据 CSV 导出 |
| 商用设备指纹 SDK | 付费外部依赖，且透传维度已够最小版防守 | 只留端口（X-Device-Id 之外将来加 `deviceCorrelationId`+`source=LOCAL_SIMULATED/confidence`，弱信号不作唯一拒绝证据） |
| 名单查询缓存（Caffeine+Redis 失效） | 名单量级小、等值查询走索引（每决策 ≤3 次）；缓存的失效复杂度不值 | 名单行数过万或决策 QPS 上量后加：本地缓存+名单变更广播失效（V6 原文方案） |
| IP 型名单 CIDR/网段匹配 | 精确匹配已覆盖"拉黑单个出口 IP"的主场景；区间判定需要专门的存储与查询形态（前缀树/范围表） | 代理轮换成为实际攻击形态时做（§4 的既有限制） |
| 设备阈值租户化/热更 | 构造期 @Value 全局单值——两三条规则阶段全局阈值够用，热更需要配置中心联动 | 挪进 TenantConfigKey 词表（rate_limit.* 同款读写校验与缓存），按租户取 |
| 决策日志归档/清理任务 | 开关默认关、灰度租户少量时增长缓慢；先积累可回放历史（回放价值依赖历史在） | 日志过千万行或存储吃紧时：按月归档到冷表/对象存储 + 保留策略（对齐 audit_export 的任务形态） |
| 名单 value HMAC 化 | 管理面可读性+等值查询是当前第一需求 | §4 的影子列方案（拖库风险实际发生或等保要求时） |
| ML 模型 | 边界裁定：不做完整风控引擎/ML（kernel 07 §4.7） | 无（明确不做） |

**刀 2 范围（本刀不做，防混淆）**：核销/退款场景接线（退款 REJECT 降级照做+打标的
合规红线）、预算燃烧信号规则、结算冻结接线（REJECT→place hold，调
`SettlementHoldService.place(source=RISK_RULE)`）、攻击脚本（`scripts/risk/`）。
