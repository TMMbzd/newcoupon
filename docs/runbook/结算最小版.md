## 1. 质量位掩码（quality_flags）语义表

两张明细表（`coupon_share_detail` / `coupon_refund_detail`）各加
`quality_flags INT`（位掩码，0=CLEAN）与 `settle_eligible TINYINT`（1=进真实结算口径）。
**两张日账单聚合同步只取 `settle_eligible=1`**——被排除的行任何一张真实账单都不进，
"主体合计=模板账单"的对账等式因此不破。

| 位 | 名称 | 语义 | settle_eligible | 产生点 |
|---|---|---|---|---|
| bit0=1 | LEGACY_DEFAULT | 商家/共担出资的钱落在 `__default__` 主体（灰度关期间的写入 / V22 前老行 / 行缺主体）——主体丢失 | **0（排除）** | 写入打标 + V47 回填（两张明细表） |
| bit1=2 | NO_ITEMS | 老式订单级分账行（`order_line_no IS NULL`，无行级 items），与 `coupon_refund_order.funding_known=0` 同族的"粗粒度"标记 | 1（**不排除**——出资拆分真实，只是没有行级明细） | 写入打标 + V47 回填 |
| bit2=4 | FUNDING_UNKNOWN | 出资方不明的退款明细（关联退款单 `funding_known=0`） | **0（排除）** | V47 回填（当前老式退款不写明细行，此位是防御口径） |
| bit3=8 | ORPHAN_TEMPLATE | 模板主数据缺失（写入路径防御位，正常不可达——核销前链路要求模板存在） | 0 | 仅写入防御 |
| bit4=16 | NEGATIVE_ADJUSTMENT | 负账单调整（保留位——3B 调整单的领域，本刀不做） | — | 未接线 |

**怎么用**：想知道某天为什么账少了一截 → 查主体账单的 `ineligible_share_count`/
`ineligible_refund_count`（当日被排除行数，一条聚合算齐）；再按位掩查明细：

```sql
SELECT quality_flags, COUNT(*) FROM coupon_share_detail
WHERE create_time >= ? AND create_time < ? AND settle_eligible = 0
GROUP BY quality_flags;   -- 位值含义查上表，或代码 SettleQualityFlags.describe()
```

**L76 清偿说明**：历史 `__default__` 行里"平台券合法空主体"与"商家主体丢失"终于可区分——
后者被回填打 LEGACY_DEFAULT 并排除出真实结算。回填判定 JOIN `coupon_template.funder_type`
（1 平台 / 2 商家 / 3 共担），平台券 `__default__` 不动。回填 SQL 的 Java 副本在
`SettleBackfillSql`（供解释性测试复验判定口径；**改迁移必须同步改副本**——测试能抓住
语义漂移，抓不住纯文本漂移）。

## 2. 主体账单四列（hold / payable / 质量桶）

`coupon_settle_party_daily_bill` 新增四列，生成时（T+1 任务）算好存列、重跑幂等覆盖：

| 列 | 语义 |
|---|---|
| `hold_amount` | 生成时命中的 ACTIVE hold 扣减额（分）。**主体级 hold（template_id 为空）对该主体的每个模板行全额扣减**——主体跨多模板时合计扣减=行数×金额（过度扣减；精确分摊属 3B 批次/结算单，已裁剪）；模板级 hold 只扣对应模板行 |
| `payable_amount` | 应付净额 = `discount_total`（已含退款冲回的净额）− `hold_amount`。**负数允许并如实展示**：负 payable=该主体有未释放 hold 超过当期净额，财务需人工关注——不钳制，钳制会掩盖问题本身 |
| `ineligible_share_count` | 当日被质量排除的分账行数（可观测；金额不计入本行） |
| `ineligible_refund_count` | 当日被质量排除的退款明细行数 |

**存量账单行**：V47 之前已生成的行四列是默认 0——补数重跑该日即可刷新
（`generateAll(date)` 幂等，upsert 覆盖）。

**hold 语义边界（重要）**：hold 只改账单 payable 口径，**不动真实资金、不影响用户退款**。
释放/作废后重跑当日账单，hold_amount 归零、payable 恢复。

## 3. settlement_hold 生命周期（4B 风控挂点）

状态机（服务层条件 UPDATE 强制；并发 release/void 只有一个能改中）：

```text
          release()                    void()
 ACTIVE ────────────▶ RELEASED（终态：下期账单恢复扣减前口径）
   │
   └────────────────▶ VOIDED（终态：判定建错）
 终态重放 = 幂等成功返回原状态；RELEASED ↔ VOIDED 互斥拒绝（4002）
```

端点（内部面 POST；权限码用 V44 既有种子——settlement:write 写 / settlement:read 查，
PLATFORM_OPERATOR 双码、PLATFORM_AUDITOR 只读，无需补种）：

| 端点 | 权限 | 说明 |
|---|---|---|
| `POST /api/settlement/holds` | settlement:write | 建冻结：`holdNo`（幂等，同号重放返回已存在）、`appId`（必须真实存在）、`settlePartyId`、`templateId`（空=主体级；非空校验模板存在）、`amount>0`（分）、`reason` 必填 ≤255、`source`=RISK_RULE/MANUAL |
| `POST /api/settlement/holds/release` | settlement:write | ACTIVE→RELEASED；重放幂等 |
| `POST /api/settlement/holds/void` | settlement:write | ACTIVE→VOIDED；重放幂等 |
| `POST /api/settlement/holds/query` | settlement:read | 游标分页（主键倒序 + cursor，禁 OFFSET）；过滤 appId/settlePartyId/status |

**审计**：建/释/作废在**服务层**挂 `AdminActionAuditor`（action=SETTLEMENT_HOLD_CREATE/
RELEASE/VOID；写入是异步的，秒级落地）；query 不记。操作人从认证上下文解析
（会话→登录名 / 令牌或任务→SYSTEM），不由请求自报。

**4B 接入说明（风控规则的挂点用法）**：阶段 4B 的风控规则直接调
`SettlementHoldService.place(...)` / `release(...)`（`source=RISK_RULE`，非 HTTP 上下文
actor=SYSTEM 同样留审计）——命中风控时 place、申诉通过后 release，下一轮 T+1 账单
自动反映。不需要绕道 HTTP 端点。

**裁定：hold 不接 EnvironmentGuard**——EnvironmentGuard 是"真钱动作"的资金边界
（退款/预算账本/账单聚合），hold 是账单口径的记号：沙箱租户建 hold 动不了任何真钱，
保留现场反而更好排查。若 4B 接入后出现"沙箱 hold 干扰生产账单"的实际风险再收紧。
同理不做余额校验（hold 总额可超主体净额）：超额后果=负 payable 如实展示，
负数本身就是"需人工关注"的信号。

## 4. 对账差异落表与指标

`reconcile`（每日账单任务生成后自动跑，也可手动调 `DailyBillService.reconcile(date)`）
现状差异只打 ERROR 日志——V47 起三连留痕：

- **stock_drift_log**：`action=SETTLE_BILL_RECONCILE`，`detail` 是两侧五项读数的紧凑 JSON
  （`{date, templateId, type, template:{confirm,refund,discount,platform,merchant}, partySum:{...}}`，
  512 列宽内）——复用预算对账（BUDGET_RECONCILE_*）的既有告警通道；
- **指标**：`coupon_settle_reconcile_diff_total{type}`，type 有界两值：
  `PARTY_VS_TEMPLATE`（主体合计≠模板账单）/ `PARTY_ORPHAN_TEMPLATE`（主体账单有行、模板账单没有）；
- **ERROR 日志**照旧（`SETTLE_PARTY_BILL_RECONCILE_MISMATCH/_ORPHAN`）。

处置：差异落表≠自动修复。两段生成事务之间恰有退款提交会产生瞬时差异（重跑即收敛）；
持续差异按 detail 里的两侧读数定位哪张账单错了，重跑该日 `generateAll(date)` 前先人工判断
是否数据损坏（对账失败的根因没消，重跑还会红）。

## 5. 值班速查

### 账单金额比预期少
1. 查主体账单 `ineligible_share_count/refund_count` 是否>0 → §1 的 SQL 按位查明细；
2. 常见来源：商家/共担券在灰度关期间核销（合法排除，业务上应开灰度或迁移模板）。

### payable 是负数
- 不是 bug：该主体 ACTIVE hold 总额超过当期净额。查 `coupon_settlement_hold WHERE
  status='ACTIVE' AND app_id=? AND settle_party_id=?`，逐条判断 release（放行）或 void（建错）。
- 释放后重跑当日账单（`generateAll`）恢复。

### hold 建错了想删
- 不能删（追加型事实）：建错走 `void`；真要生效走 `release`——两个终态财务含义不同，
  已终态的不可再迁移。

### 对账告警（SETTLE_BILL_RECONCILE）
- 见 §4；瞬时差异重跑收敛，持续差异按 detail 定位。

### 上线/回滚
- V47 全部是加列/新表/新端点，无行为回滚开关需要——账单口径变化（排除质量行）与
  hold 扣减都是**期望中的口径变化**；如需临时回退账单口径，属破坏性变更须单独裁定
  （没有配置开关，登记为已知边界）。
- 生产 DDL 纪律（照 V28 先例）：`coupon_share_detail`/`coupon_refund_detail` 是核销/退款
  热路径写入表，加列（INSTANT）低风险，但 V47 的回填 UPDATE 全表扫描——预发演练 +
  低峰窗口执行。

## 6. 裁剪登记（本版明确不做）

| 裁剪项 | 说明 | 归属 |
|---|---|---|
| 门店/业务单元维度（storeId/businessUnitId） | 分账/退款/账单都不加列 | V6 计划 3A 后续 |
| `coupon_settle_party` 主数据快照表 | 主体 ID 仍由订单行/模板自带，无主数据管理 | 3A 后续 |
| 3B 日事实（coupon_settle_daily_fact）/结算批次/结算单全套 | 本版止步于"日账单+payable 口径" | 3B |
| 3C 调整单/导出 | 跨日/跨月退款调整、CSV/Excel 导出未做 | 3C |
| 币种列 | 单币种（分） | 3A 后续 |
| hold 精确分摊（主体级 hold 跨模板的额度分配/结转） | 主体级 hold 在每个模板行全额扣减（会过度扣减，负 payable 兜底可见） | 3B 批次/结算单 |
| 回填的端到端可测 | 迁移先于测试数据执行；改为解释性测试（SettleBackfillSql 副本复验判定口径） | 已知边界 |
| 账单口径回退开关 | 未提供（口径变化是本版目的本身） | 已知边界 |
