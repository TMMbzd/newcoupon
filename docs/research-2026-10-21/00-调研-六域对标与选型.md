# 调研：六域对标与选型（2026-10-21）

> **用途**：为 [实施计划 V6](01-实施计划-V6-从券交易内核到券能力中台.md) 提供外部依据。不是技术文档，不重复实现细节。
> **方法**：六个并行调研（发放域、租户治理、结算、风控、稳定性、前端/管理台）+ 一个本地集成点只读审计；外部资料优先官方文档/工程博客/产品规则页，其次行业文章。
> **分级**：**公开事实** = 官方文档/工程博客可点开；**产品规则** = 公开规则页；**推断** = 我们的判断，不冒充事实。
> **纪律**：不把目标写成现状；来源可点开；实施前按项目“引用三重门”复核。
>
> **库存模型补充（2026-10-22）**：本文 §1 讨论的是发放域；库存扣减模型的独立调研与 C1 决策见 [ADR-0018](../adr/ADR-0018-stock-model-c1-fixed-shards.md)（DB 固定分片条件更新、Redis 退出库存权威，含未来演化与完整链接）。

## 0. 结论速览

| 域 | 业界共同模式 | 我们的选择 | 明确不选 |
|---|---|---|---|
| 发放 | 同步受理+异步落库、批次+任务+分片+限速+重试、预算预占/确认/释放、兑换码一次一码 | 任务表即队列 + XXL-JOB + RedisScanLock；`issueOne` 复用；预算激活既有 `coupon_activity` + 台账 | Spring Batch、命令 MQ、Redis 计数器做预算权威 |
| 治理 | 机器面与人工面分离；Session+Redis 或短 JWT；路径/头版本；Pact/OpenAPI；test 模式 | Spring Security 6 + Session Redis + RBAC；`/console` 独立；`/open/v2`；OpenAPI 契约；同库沙箱 | 完整 IAM/SSO、JWT 无状态、Pact Broker（暂） |
| 结算 | 主体+门店+周期+模板；核销/售后时点；退款调整批次；差异分类 | 日账单（会计视图）+ 结算批次/结算单（应付视图）+ hold/调整；CSV 导出 | 支付/打款/发票、完整清分引擎 |
| 风控 | 频控→名单→设备/行为→规则决策→人工审核→结算 hold | 表驱动规则 + 名单 + 设备端口 + 四态决策 + hold + 日信号 | Drools、ML、商用指纹唯一方案 |
| 稳定性 | SLO/错误预算、Prometheus/Grafana、Tracing、混沌、备份恢复、阶梯压测 | 业务 SLI + Micrometer/Prometheus/Grafana + OTel/OTLP + k6 + mysqldump/binlog + JaCoCo/Trivy | K8s/Nacos/微服务、自研大盘 |
| 前端 | 管理台 + 租户自助 + 看板 | Vite+React+TS+AntD+OpenAPI 类型生成 | 自研组件库、手写 API 类型 |

## 1. 发放域

### 1.1 公开资料里的做法

- **vivo 优惠券系统**公开分享过“同步受理 + 异步落库”的领取链路：先快速受理，再异步完成落库，查询接口给最终状态；批量/定向发放按任务分片、限速消费、失败重试、进度可查（来源见 §8）。
- **美团开放平台**提供商家券的批量新增、活动类 API、券状态查询、核销/退款/结算类接口；开放平台把“券模板/批次、发放、核销、结算”拆成不同能力面（来源见 §8）。
- **京东云权益中心**公开文章把优惠券模块做成配置化能力（模板、规则、发放、核销），强调配置与执行分离（来源见 §8）。
- **Stripe** 的 Coupons/Promotion Codes 文档把“优惠定义”和“兑换码”分开；Idempotent Requests 文档明确用幂等键保证重试不重复（来源见 §8）。
- **Shopify** 的 Refund 对象支持按订单行/数量退款，退款与订单行关联（来源见 §8）。
- **有赞**公开分享过跨平台订单优惠计算，强调优惠顺序、分摊与可追溯（来源见 §8）。

> 以上是公开资料中的做法，不代表这些公司全部实现细节；我们只借用模式，不复制业务规则。

### 1.2 我们的选择

**任务/分片/明细三层，DB 是事实源**：

- `coupon_grant_task`（批次头）+ `coupon_grant_chunk`（执行单元）+ `coupon_grant_item`（按用户明细）。
- 任务状态 `PENDING_APPROVAL/APPROVED/SCHEDULED/RUNNING/PAUSED/SUCCEEDED/PARTIAL_FAILED/FAILED/CANCELING/CANCELED`；chunk 有 `lease_owner/lease_until`；item 有 `SUCCESS/FAILED/SKIPPED/CANCELED`。
- worker 用 `SELECT ... FOR UPDATE SKIP LOCKED` 领取 chunk；`@XxlJob` 只做时钟/扫描，`@Scheduled` 降级；`RedisScanLock` 仲裁。
- **RocketMQ 只做唤醒/缓冲**（消息体 `{taskNo, chunkNo}`，不放名单），事实源仍是 DB；MVP 可以先用 DB 轮询 + `SKIP LOCKED`，压测证明需要再补 MQ 唤醒。
- 进度用 task/chunk 计数 + Redis hash 实时汇总；取消是 `CANCELING→CANCELED` 异步语义，已发出的券不回滚，召回走独立高风险任务。
- item 表 MVP 先单表 + `(task_id, chunk_no, status)` 索引；>10M 行或需要按用户查询时再按 `user_id%64` 分片。不要按 `task_id` 扫 64 张 `user_coupon` 做进度。

**一份发放逻辑（先重构再批量）**：

- 从 `ReceiveAppService` 抽出 `StockGateService`（deduct/confirm/cancel/分类）与 `IssueService.issueOne(IssueCommand)`；显式传 `appId/templateId/userId/requestId/seq/source/bizType/bizId`。
- HTTP 领券、批量、定时、兑换码、异步单发全部走同一库存闸门 + DB 事务（桶 CAS → user_coupon → event → outbox → expire task）。
- **不要循环调用 `ReceiveAppService.receive`**：它带请求上下文、DeadlineGuard、单请求幂等语义，批量会误判超时/降级；也不要直接 INSERT user_coupon 绕过 Redis/桶，否则线上余量与 DB 桶不一致。
- 批量消费者用独立线程池/连接池 + 限速；线上 P99 升高时暂停批量（开关/系统自适应）。

**预算闸门（三张账本表）**：

- `coupon_budget_account`：`scope_type/scope_id/app_id/period_type/period_key/total/reserved/consumed/version`；支持活动/租户/模板、总/日/月预算；到期用 `period_key` 自然切换，不要每天清零可变单行。
- `coupon_budget_reservation`：`reserve_no/account_id/biz_type/biz_id/amount/confirmed/released/status/expire_time`；chunk 级预占。
- `coupon_budget_ledger`：只追加的 RESERVE/CONFIRM/RELEASE/ADJUST 流水，任何余额都能回放。
- 单张成本：满减/无门槛=`face_value`，折扣=`discount_cap`（不能用门槛拍脑袋）；共享预算按 `budget_ratio` 拆平台/商家（MVP 先活动级单账户）。
- 顺序：先预算预占，再库存扣减；库存失败释放预算，预算失败不碰库存；chunk 结束确认成功金额、释放失败金额；僵尸预占用 `expire_time` + reaper。
- 对账：`reserved+consumed <= total`；ledger 汇总=account；task 计数=item 状态；Redis 已扣=DB 桶行；差异告警不自动删券。

**兑换码**：

- 码批次 + 码明细 + 兑换日志；Crockford Base32（去掉 I/L/O/U）+ 校验位；手工码 16 位（约 80 bit）+ 限流，二维码 26 位（约 130 bit）。
- 库中只存 `HMAC-SHA256(pepper, normalized_code)`，不存明文；日志/审计只打 mask；需要二次导出才存 AES-GCM 密文。
- 核销：码 CAS `ACTIVE→LOCKED→USED`，失败回 ACTIVE；崩溃恢复先按 request 查 user_coupon 幂等键；统一错误文案防枚举；IP/用户/码限流。
- 码池库存：`coupon_template.code_reserved`，激活预占、兑换扣减、作废释放；守恒 `allocated + code_reserved <= total_count`。
- 批量生成/导出异步化；CSV 加 BOM、防公式注入；一次性下载、短 TTL、审计。

**事件与审批**：

- `coupon_event` 加 `app_id/biz_type/biz_id/operator`；批量事件按 `(biz_type,biz_id)` 查，不广播 64 张 user_coupon。
- outbox 百万级任务不要逐张发 MQ：事件表每张写，outbox 只发需要下游通知的事件 + 一条 `GRANT_TASK_COMPLETED`。
- 审批用最小 `coupon_approval_request/action` 状态机；默认自动通过，高风险（追加库存、绕限领、大批量码、召回）人工；提交人不能自批。

### 1.3 不选/为什么

| 方案 | 不选理由 | 重评触发 |
|---|---|---|
| Spring Batch | JobRepository/Step 面向离线批处理；在线进度、取消、按用户幂等、多租户隔离都要另写一层 | 纯离线、无需在线语义 |
| 命令 MQ 当事实源 | DB 任务表才是事实源；MQ 只做唤醒/缓冲，消息体只放 taskNo/chunkNo | 有跨服务消费方/削峰需求时可加唤醒 |
| Redis 计数器做预算权威 | 预算必须可对账；Redis 丢数/漂移会超支 | 只做读缓存，不做权威 |
| 为每个用户建定时任务 | 任务数爆炸、调度中心压力大 | 不做 |
| 自研分布式调度 | 已有 XXL-JOB + RedisScanLock | 不做 |
| Hashids/Sqids 当码安全 | 官方明确是混淆/编码，不是加密 | 不做 |
| Flowable/Activiti | 一步审批用状态机 + 两张表足够；BPMN 引擎过重 | 多级会签/条件分支/SLA 时重评 |

### 1.4 关键坑

- 任务/分片/明细不要一开始按 `user_id` 分片；item 先单表，>10M 再评估。分片表的唯一键必须含分片键。
- `request_id` 必须含 `appId`（服务层或独立 app_id 列），不要复制 L73。
- 预算预占必须在库存闸门之前；任何失败路径都必须 release；ledger + reaper + 对账兜底。
- 批量取消/重试与 worker 的竞态用状态 CAS + lease；不要只靠内存标志。
- 兑换码明文不能落库/落日志；导出文件一次性/加密；核销限流；CSV 防公式注入。
- 时区统一 Asia/Shanghai；定时任务用 DB `NOW(3)` 判断到期，不用应用机器时间。
- 批量消费者不要和线上领券抢连接池；独立线程池/连接池 + 限速 + 开关。

## 2. 租户治理、身份权限、API 版本与契约

### 2.1 公开资料里的做法

- **Spring Security 6** 官方文档推荐用 `SecurityFilterChain` 配置、`AuthenticationManager`/`DaoAuthenticationProvider` 做认证、`@EnableMethodSecurity` + `@PreAuthorize` 做授权；密码用 `PasswordEncoder`（BCrypt/Argon2/Delegating）。
- **Spring Session** 官方文档支持 Redis 存储会话，适合多实例、强制下线、权限即时生效。
- **Stripe API Versioning** 用请求头 `Stripe-Version` 锁定账户版本；**GitHub API Versions** 用 `X-GitHub-Api-Version` 日期版本；路径版本（`/v1`、`/v2`）也是常见做法。
- **Stripe Test Mode** 用独立 test key + 独立数据，和 live 模式分开；这是“沙箱”的产品化做法。
- **Pact** 是消费者驱动契约测试的标准实现；**OpenAPI** 是 provider 侧 schema 契约的通用标准；**Spring Cloud Contract** 是 Spring 生态的另一种选择。
- **NIST RBAC** 给出用户-角色-权限的标准模型；企业平台通常在其上做租户隔离和数据权限。

> 版本策略没有唯一正确答案；我们按“现有 `/open/v1` + 单体 + 少量接入方”选择路径版本，不声称这是所有公司的最佳实践。

### 2.2 我们的选择

**信任面分离（不是三套认证混用）**：

| 面 | 认证 | 授权 | 用途 |
|---|---|---|---|
| `/open/**` | HMAC + 时间窗 + nonce（Servlet Filter，在 Security 链前） | Security 单独链 `permitAll` + appId 归属 + 配额 + 开关 | 产品/租户机器调用 |
| `/api/**` | Spring Security：旧 `X-Admin-Token` 作为兼容认证过滤器 + 后续 Session/PAT | `authorizeHttpRequests` + `@PreAuthorize` | 平台运营/运维脚本 |
| `/console/**`、`/tenant/**` | Spring Security Session + Redis | RBAC + `tenant_scope` | 管理后台/租户自助 |
| `/actuator/**` | 独立链；health 公开，其余 `ROLE_ACTUATOR` | 不裸奔 | 运维/健康检查 |

- **旧 `AdminTokenFilter` 改成只认证的 `LegacyAdminTokenAuthenticationFilter`**：去掉 `@Component`/`@Order`（防 Boot 自动注册两次），由 `SecurityConfig` 手动 `new` + `addFilterBefore`；保留一个发布周期，统计使用量后删除；脚本长期用 `admin_api_token`（PAT，SHA-256/scopes/过期）。
- **授权交给框架**：删除 `BUSINESS_WRITE_PATHS`/`isProtected` 路径白名单；`authorizeHttpRequests` 粗粒度 + `@PreAuthorize` 细粒度；`/api` GET 全部要求认证（破坏性变更，公告 + 更新脚本 + 结构测试）。
- **RBAC**：五表 + `admin_user_role.tenant_scope`（空=平台级，非空=该 appId）；权限码 `resource:action`；角色种子平台管理员/运营/审批/审计 + 租户管理员/查看者；不按页面建角色。
- **密码/会话**：`DelegatingPasswordEncoder` + `BCrypt(12)`（Argon2id 可选，需 BouncyCastle）；失败 5 次/15 分钟锁定；`RedisIndexedSessionRepository` + `SpringSessionBackedSessionRegistry`；CSRF Cookie；空闲 30 分钟/绝对 8 小时；登录后轮换 session id；强制下线。
- **权限即时生效**：会话只存 `AdminPrincipal(userId, username)`；`AdminAuthorityRefreshFilter` 每请求从 DB 重载权限；角色变更/停用/改密触发删会话 + `auth_version`。
- **租户隔离必须到数据层**：`user_coupon.uk_idem` 改为 `(user_id, app_id, idempotent_key)`（64 张分表）；`coupon_usage` 加 `app_id`（64 张分表 + 回填）；`coupon_event` 加 `app_id`。**不要**把 appId 前缀拼进 64 字符幂等键（会截断/冲突）。

**API 版本**：

- `/open/v1` 冻结：只增字段、不删字段、枚举可扩展、未知字段忽略；破坏性变更开 `/open/v2`。
- 路径版本天然进 HMAC canonical；**不加请求头版本**（否则版本头也要签，老客户端全失败）。
- 响应加 `X-API-Version`；废弃加 `Deprecation`（RFC 9745）、`Sunset`（RFC 8594）、`Link`；v2 GA 后 v1 至少支持 12 个月；不做 per-tenant 版本矩阵。
- 版本注册表解析 `/open/v1`、`/open/v2`；未知/未启用版本 6010（HTTP 400），`data.supportedVersions` 只新增；`/open/v1/unknown` 是接口写错，可以 404。

**契约测试**：

- **OpenAPI 契约 + 提供方校验 + 破坏性变更门禁**：`docs/open-api/openapi-v1.yaml`（OpenAPI 3.0.3，匹配 springdoc 2.6）；`springdoc` 生成 spec + 测试 diff 防漂移；`swagger-request-validator` 校验真实请求/响应；`openapi-diff --fail-on-incompatible` 基线取 `origin/main`；Spectral lint；黄金样例覆盖错误码/未知字段/枚举扩展。
- CI 增加 `contract` job；前端用 `openapi-typescript` 生成类型，接口变更导致类型 diff 可见。
- Pact 暂不引入：单仓库、少量接入方、外部伙伴不会写 consumer test；出现“多个独立发布节奏的消费方 + can-i-deploy”时再上 Pact Broker。

**沙箱**：

- `open_app.environment=PROD|SANDBOX`；沙箱 appId 用 `sbx-` 前缀；同库逻辑隔离，所有业务按 appId 过滤；`EnvironmentGuard.assertProd` 在结算/账单/真实退款/Webhook 等资金边界拒绝沙箱；定时任务跳过沙箱；独立配额/配置；每日清理 30 天前沙箱数据。
- 不做第二套数据源/独立环境：成本高、与当前单库分片架构冲突；合规要求物理隔离时再评估。
- 文档明确“逻辑沙箱不是生产隔离”，避免虚假安全感。

**租户生命周期**：

- `open_app.lifecycle_status` 独立于 `status`；状态机 `DRAFT→PENDING_REVIEW→SANDBOX_ACTIVE→ACTIVE⇄SUSPENDED→CLOSING→CLOSED→DELETED`；`open_app_lifecycle_event` 留痕；只允许 `POST /lifecycle {action,reason}` 走迁移表。
- 注销：冻结写入、撤密钥、收场未终结占用/退款、出账单；导出 `tenant_data_export_job`（NDJSON+CSV+manifest+SHA-256，一次性下载，过期清理）；财务/结算/审计按保留期保留，非财务数据删除/匿名化；`tenant_deletion_request` + 双人审批 + 删除证明；`legal_hold` 阻止删除。
- 开通/审核/沙箱验收/启用/停用/注销；高风险租户留 KYC/合同字段，但不接自动 KYC。

**审计**：

- `audit_log` 加 `actor_type/actor_id/session_id/approval_id/hash_version`；`AuditAspect` 从 `SecurityContext`/`RequestContext` 取 actor，不再用“第一个 Long 参数”猜 userId。
- 多实例：`audit_chain_head` 单行表，事务内 `SELECT ... FOR UPDATE` 串行 append；老记录 v1、新记录 v2，不重算历史链；每日校验任务重算并告警。
- 查询 `POST /api/audit/query`（游标、日期≤31 天、limit≤200）；导出异步 CSV/NDJSON + manifest；`POST /api/audit/verify` 返回第一个断点；查询/导出本身也写审计。
- 双人复核 `approval_request`：MVP 范围=租户删除、手工结算调整；请求人≠审批人；双方审计。

### 2.3 不选/为什么

| 方案 | 不选理由 | 重评触发 |
|---|---|---|
| 完整 IAM/SSO/MFA | 当前是单体平台，本地 RBAC 足够；接入企业身份是另一条工程 | 企业统一身份/合规要求 |
| JWT 无状态 | 强制下线、权限即时生效、会话审计更难；Session+Redis 更直接 | 跨域多端/无状态要求 |
| 把 `/api` 改成多租户面 | 会破坏现有机器面/脚本/测试；控制台独立前缀更安全 | 平台运营面需要租户身份 |
| Pact Broker（现在） | 没有外部消费方 CI；维护成本高 | 外部团队要求消费者驱动契约 |
| 物理独立沙箱 | 成本高、与单库分片冲突 | 合规要求物理隔离 |
| 自研认证/授权 | Spring Security 是标准件 | 不做 |

### 2.4 关键坑

- `AdminTokenFilter` 是 `@Component` + `HIGHEST_PRECEDENCE+20`，在 Security 链之前；直接叠加会把会话登录请求挡掉，且会被 Boot 自动注册两次。必须去掉 `@Component`/`@Order`，改成只认证的 `LegacyAdminTokenAuthenticationFilter`，由 `SecurityConfig` 手动 `new` + `addFilterBefore`。
- `/api` GET 目前不设防；新 Security 链必须保护全部 `/api`（除 `/api/ping`/login），否则 RBAC 只保护了写接口，租户列表/配置早就泄露。
- 三套身份不能互推：HMAC 是租户应用，Session 是管理员，`X-Admin-Token` 是机器；RBAC 管功能权限，`tenant_scope`/`CallerContext` 管对象权限，二者缺一不可。
- 权限不要长期信任在 Session 里：会话只存 userId，每请求重载权限；否则角色变更不生效。
- Session 多实例必须 Redis + `RedisIndexedSessionRepository`；CSRF Cookie 要配 SPA 读取；登录接口 CSRF 要单独处理；Redis 故障管理面 fail-closed + break-glass。
- 审计哈希链多实例不能只靠 `synchronized`；用 `audit_chain_head` 行锁/分链；动钱/管理审计同事务或 outbox；actor 从 `SecurityContext`/`CallerContext` 取，不猜第一个 Long。
- 版本兼容要测“旧客户端 + 新服务”：新增字段、枚举扩展、未知字段、错误码不变；路径版本天然进 HMAC，不要加未签名的请求头版本。
- `audit_log`/`AuditAspect` 目前 `app_id NOT NULL` 且无 actor 字段；管理审计要么扩列 + hash_version，要么用独立表，不能把管理员 ID 硬塞进 `user_id`。
- 沙箱漏一个 `environment` 过滤就会串场；资金边界用 `EnvironmentGuard`，不要依赖每个查询都记得加条件。
- `coupon_usage` 没有 `app_id`；注销/导出/按租户审计会跨 64 表，应在 V27 补列 + 回填。

## 3. 结算深化

### 3.1 公开资料里的做法

- **美团**的商家券/结算类开放能力把券的核销、退款、结算数据分面提供；商家侧通常按门店/主体/周期看账（来源见 §8）。
- **Stripe** 的 Balance Transactions/Payouts 把“交易流水 → 余额 → 打款”分层；退款会产生负向余额交易；结算与支付通道分离（来源见 §8）。
- **Shopify** 的 Payouts/Refunds 也把“订单退款”和“商家打款”分开，退款影响后续结算（来源见 §8）。
- 行业常见结算时点：核销即结、T+N、售后期结束；退款冲回已结算账单通常用调整单/负账单，不重开历史账单（推断/行业模式）。

> 券平台的边界：只提供券侧结算数据（分摊、退款、主体、门店、周期），不做支付打款/发票税务。

### 3.2 我们的选择

- **日账单 = 会计视图**：新增/扩展 `coupon_settle_daily_fact`，按日期+appId+主体+门店/BU+模板，**gross/refund/net 分列**；`confirm_count` 是分账行数，另给 `usage_count = COUNT(DISTINCT usage_no)`；带 `run_id/source_max_id/generated_at/currency`。
- **结算批次 = 应付视图**：`coupon_settle_batch` + `coupon_settle_statement` + `coupon_settle_statement_line`；状态 `DRAFT→CALCULATING→CALCULATED→PENDING_CONFIRM→CONFIRMED→CLOSED`，另 `VOID/SUPERSEDED/ADJUSTED`；确认后金额/行/主体/期间冻结，只能新版本或调整单。
- **调整单**：`coupon_settle_adjustment`；已确认后退款走下一期负向调整；负账单允许结转，不能 `GREATEST(0,...)` 截断。
- **结算主体主数据快照**：`coupon_settle_party`（party_type/parent/status/source_version/quality）；只存主体 ID/名称/层级/状态，不存完整银行卡/身份证/KYC；账户引用用 token。
- **门店/业务单元**：订单行可选 `storeId/businessUnitId`；分账/退款复制；日事实/结算单按维度汇总；旧数据标记 `data_quality`，不猜门店。
- **结算周期/时点/方式**：`settle_cycle`（T+1/T+N/WEEKLY/MONTHLY/MANUAL）、`settle_point`（CONFIRM/AFTER_SALE_END）、`after_sale_days`、`holdback_ratio`、`min_settle_amount`、`settle_mode=NET`；默认“T+1 净额账单 + 售后期 holdback”。
- **历史质量**：`quality_flags` 位掩码（LEGACY_DEFAULT/APP_MISMATCH/NO_ITEMS/FUNDING_UNKNOWN/ORPHAN_TEMPLATE/NEGATIVE_ADJUSTMENT/MANUAL）+ `settle_eligible`；真实结算默认排除不可结算行；提供质量报表。
- **重跑**：带 `run_id`；不能只 upsert，要删除/替换本次 run 的旧行；`source_max_id` 支持增量/全量。
- **对账**：`coupon_recon_run` + `coupon_recon_diff`；券侧内部恒等式全做（行/单券/退款/主体=模板/单头=行/批次=单）；订单侧有数据再做；支付/财务外部。差异分类 + 自动修复只修派生/精确重复，已确认单/主体/外部差异人工。
- **导出**：异步 `coupon_export_job` + 游标分批 + 流式写；CSV 用 OpenCSV，Excel 用 POI SXSSF/FESOD（EasyExcel 已归档，新项目不主选）；UTF-8 BOM、防 CSV 公式注入、一次性短链、权限 + 审计、文件 SHA-256。
- **账单任务**：`@XxlJob` + `RedisScanLock`/单实例路由 + 失败指标/告警；重跑幂等；`accounting_time` 统一为退款明细 create_time，保留 `original_bill_date`。

### 3.3 不选/为什么

| 方案 | 不选理由 | 重评触发 |
|---|---|---|
| 支付/打款/发票/税务 | 外部系统边界；平台不做资金执行 | 平台要做出款时接外部 |
| 完整清分/结算引擎 | 当前是券侧结算数据，不是资金清算 | 多主体分账/资金池要求 |
| 把日账单当结算单 | 会计视图含未结算/hold，直接打款会错 | 不做 |
| 重开历史账单 | 破坏已结算账；用调整批次 | 不做 |
| 手写 CSV 转义 | 容易漏引号/换行/BOM/公式注入 | 不做 |
| EasyExcel 作为主选 | 已归档/维护模式；新项目用 OpenCSV/POI SXSSF/FESOD | 已有代码再评估 |

### 3.4 关键坑

- 跨日/跨月退款：账单按明细日，结算按批次；已结算走调整。
- 时区/日切：固定 Asia/Shanghai；DB session 时区是部署前置。
- `__default__` 不能用于真实商家结算；历史质量必须显式标记。
- 主体/门店大小写：结算表用 `utf8mb4_bin`；单号 collation 仍是已知边界（L77）。
- 账单任务多实例：唯一键幂等 + Redis 锁/XXL；失败要可见。
- hold：日账单可以有，结算批次必须扣；放行后进下一批。

## 4. 风控与反作弊

### 4.1 公开资料里的做法

- **OWASP API Security Top 10 (2023) API6: Unrestricted Access to Sensitive Business Flows** 明确把“优惠券/抢购/评论”等敏感业务流列为需要防自动化滥用的对象（官方文档）。
- 美团等公开分享的风控体系通常分层：入口频控、名单、设备指纹、行为规则、关系网络、人工审核/处置（行业模式/公开分享）。
- 规则引擎常见“场景→规则→因子→动作”，识别与处置分离；重引擎（Drools）适合规则多/复杂，轻量场景用表驱动 + 表达式。
- 设备指纹/人机验证通常接商用服务（同盾/数美/极验等）；自建只做端口 + 本地模拟（推断/工程边界）。
- 券平台只能提供券侧证据与约束；订单/支付/物流真实性由外部系统判定（行业边界）。

### 4.2 我们的选择

- **表驱动 + 规则集版本**：`risk_scene/risk_ruleset/risk_rule/risk_factor/risk_rule_factor/risk_action`；规则集不可变，`DRAFT→CANARY→ACTIVE→ARCHIVED`，回滚=切 active 指针；决策日志记录 ruleset_version/definition_hash/engine_version。
- **决策四态**：`PASS/CHALLENGE/REVIEW/REJECT`；`CHALLENGE` 通过后重新决策；`REVIEW` 业务可继续但打 `risk_state=REVIEW` 并挂 hold；**退款场景的 REJECT 必须降级为“退款照做 + 打标/退券挂起”**，不能拒绝消费者退款。
- **决策日志/回放**：`risk_decision_log` 记录因子快照、所有被评估规则（不只命中）、动作/分数/耗时；`POST /api/risk/decisions/{id}/replay` 只读回放；决策缓存与 HTTP 幂等缓存分开（不要复用 24h 响应缓存）。
- **名单**：黑/白/灰，维度 USER/DEVICE/IP/PHONE/OPENID；值 HMAC + 租户盐，不存明文；时效/原因/操作人/申诉；Caffeine+Redis，DB 权威；变更失效 + TTL 兜底；命中审计。
- **设备**：叫 **`WeakDeviceSignalProvider`/`deviceCorrelationId`**，不叫“真设备指纹”；UA/canvas/屏幕/时区哈希 + `stableClientId`，带 `source=LOCAL_SIMULATED/confidence`；只作信号，不作唯一拒绝证据；商用 SDK 只留端口。
- **人机验证**：Phase 2 接 `tianai-captcha`（Apache-2.0，滑块/点选/PoW）；AJ-Captcha 已停维护不选；挑战一次性 token、绑定 requestId+subject、短 TTL、失败计数。
- **风险资产状态**：`risk_asset_state(asset_type, asset_id, risk_state, decision_id)` 独立非分片表；不要给 64 张 user_coupon/coupon_usage 加风险列。lock/confirm 前查风险状态。
- **复核**：`risk_review_task` 独立于 `coupon_confirm_exception`；列表/通过/拒绝/证据；操作人+复核人；审计同步落业务表。
- **结算冻结**：`coupon_settlement_hold` 非分片；hold 券侧应付，不冻结用户退款/资金；日账单加 `hold_amount/held_count`，`payable = discount - hold`；释放/作废走下一期调整；拒绝后 `VOIDED` + 必要时作废券/退券调整。
- **反作弊信号**：退款率、核销率、券占比、同设备/同用户聚集、短时多次退款、预算燃烧率、库存消耗速度；日任务/事件聚合写 `risk_signal`；阈值用 P95/P99/MAD，分租户基线；先影子运行再灰度。
- **失败策略**：按场景矩阵；低风险 fail-open + 指标，高风险 CHALLENGE/REVIEW；任何降级可见；风控总开关默认关、按租户灰度；错误码 7003 REVIEW/7004 CHALLENGE/7005 UNAVAILABLE。

### 4.3 不选/为什么

| 方案 | 不选理由 | 重评触发 |
|---|---|---|
| Drools/完整规则引擎 | 规则少、要可解释可回放；重引擎维护成本高 | 规则数 >50 且结构化表达不了 |
| ML 评分 | 无标签数据；无法解释/回放 | 有标注数据且规则误杀不可接受 |
| 商用设备指纹唯一方案 | 无采购/无法本地演示 | 有商用合同/准确率要求 |
| 把订单真实性判断写进券平台 | 越界；券平台只有券侧证据 | 外部证据契约建立后 |
| 全自动封禁 | 误杀成本高；先复核/挑战 | 规则成熟/人工审核数据充足 |

### 4.4 关键坑

- 误杀：规则默认宽松、灰度、可回放；hold 可放行；不要一上来全拦截。
- 规则热更新：Caffeine + 版本；变更审计；回滚。
- 名单 PII：值哈希/脱敏；权限；审计。
- 设备指纹可伪造：只作信号；结合 IP/UA/行为。
- 结算 hold 与账单：hold 在结算批次扣，不在日账单删；放行后下一批。
- 性能：规则评估在请求路径，必须 <5ms；缓存；无阻塞 IO。

## 5. 稳定性、可观测、容量与演练

### 5.1 公开资料里的做法

- **Google SRE Workbook** 的 “Alerting on SLOs” 给出多窗口、多燃烧率告警方法；错误预算把“可靠性”变成可管理的预算。
- **Prometheus** 官方推荐 recording rules + alerting rules；**Grafana** 支持 provisioning 管理大盘。
- **Micrometer Tracing** 是 Spring Boot 3 的原生 tracing 门面，支持 Brave/OTel bridge；**OTLP + Tempo/Jaeger** 是更中立的现代组合，Zipkin/Brave 是旧路线。
- **Testcontainers ToxiProxy** 可在测试里注入网络延迟/故障；**ChaosBlade/Litmus** 适合更重的混沌工程。
- **k6/Gatling/JMeter** 是常见压测工具；阶梯加压、拐点、soak、故障注入压测是标准报告要素。
- **MySQL** 官方 `mysqldump --single-transaction` + binlog 是常见逻辑备份/恢复组合；**JaCoCo** 覆盖率、**Trivy** 依赖/镜像扫描是常见 CI 门禁。

### 5.2 我们的选择

- **SLI/SLO**：新增 `coupon_sli_events_total{journey,outcome,reason}`；在服务边界按业务码判定 good/bad/excluded，**不用 HTTP 200/`TradeMetrics.failed` 当 SLI**；领券 99.9%/P99 300ms、试算 99.9%/150ms、核销退款 99.95%/500ms；28 天 + 错误预算 + 14.4/6/1 多窗口；单机口径 `coupon_deployment_info` 明确标注。
- **指标**：复用 Micrometer/Prometheus；新增发放/预算/风控/结算/账单任务；标签有界 + `MeterFilter` 硬防线；直方图用 `publishPercentileHistogram`，不用客户端 percentile 跨实例聚合。
- **大盘**：Grafana 四张盘（SLO/预算、领券、资金链路、运行时/依赖）；provisioning JSON；低流量/无数据/up==0 告警。
- **Tracing**：**Micrometer Tracing + OpenTelemetry bridge + OTLP**；后端 Tempo（Grafana）或 Jaeger v2；不在新项目主选 Brave/Zipkin；dev 100%、prod 5~10%；`X-Trace-Id` 保留为业务关联号。
- **故障演练**：ToxiProxy + `docker pause/stop`；`pause` 测超时/熔断，`stop` 测快速失败；Redis/MySQL/MQ 各硬故障 + 网络故障；独立 compose project/network、`CONFIRM=yes`、trap cleanup；断言熔断/fail-open/outbox/守恒。
- **备份恢复**：compose MySQL 开 binlog；`mysqldump --single-transaction --source-data=2` 同一次 dump `newcoupon+xxl_job`；恢复到 `newcoupon_restore` + Flyway validate + 行数/校验和/中文/时区核对；本地 RPO≤15min/RTO≤30min，生产 RPO≤5min/RTO≤60min。
- **容量**：k6 开放模型（`ramping-arrival-rate`）四场景；阶梯/soak/故障注入；独立 schema/Redis DB/MQ topic；`loadtest` profile 护栏；WSL2 `.wslconfig` + 停 Grafana/Tempo/XXL/IDE，结果只作相对基线。
- **双实例**：compose profile + nginx；readiness/drain + SIGTERM；不同 `WORKER_ID`；Redis pub/sub + 版本 + TTL 缓存失效；`audit_chain_head`；滚动重启零 5xx；`proxy_next_upstream` 不对非幂等 POST 开 `non_idempotent`。
- **CI**：构建/测试/覆盖率/依赖扫描四门；JaCoCo + diff-cover（存量 ratchet、新增资金路径 ≥85~90%）、dependency-review/OWASP/Trivy + SBOM；Dockerfile 多阶段；不做 CD 到生产。

### 5.3 不选/为什么

| 方案 | 不选理由 | 重评触发 |
|---|---|---|
| K8s/Nacos/网关/微服务 | 单体阶段，增加运维复杂度 | 团队/流量/部署要求 |
| 自研大盘/Tracing | Grafana/Micrometer/OTel 是标准件 | 不做 |
| Brave/Zipkin 作为新主链路 | OTel bridge + OTLP 更中立，换 Tempo/Jaeger 不改代码；Zipkin 只作旧后端兼容 | 已有 Zipkin 且不迁移 |
| XtraBackup | 当前数据量小；mysqldump 够用 | >100GB/热备要求 |
| ChaosBlade/Litmus | 单机 `docker pause/stop` + ToxiProxy 覆盖测试；Litmus 需要 K8s | 节点级混沌需求 |
| CD 到生产 | 没有生产环境；先做可重复构建/CI | 有真实环境 |

### 5.4 关键坑

- **HTTP 200 伪成功**：业务失败大量返回 200；SLI 必须看业务码。`TradeMetrics.failed` 混入业务拒绝，不能直接当可用性；`duplicated` 要算 good。
- 指标标签爆炸：userId/单号/路径参数不做标签；用 result/status/type；`MeterFilter` 硬防线；客户端 percentile 不能跨实例聚合，用 histogram + `histogram_quantile`。
- 压测污染测试库：独立 schema/Redis DB/MQ topic；`lt-` 前缀；`loadtest` profile 护栏；WSL 资源串行；记录 dropped iterations。
- 备份恢复：compose 没开 binlog 先补；`--source-data=2`；`newcoupon+xxl_job` 同一次 dump；时区/字符集/分片表/Flyway 账本；恢复到独立库；核对行数/校验和；RPO≈0 单机做不到。
- 演练误伤：`CONFIRM=yes`；独立 compose project/network；`trap cleanup`；`pause` 与 `stop` 测两种防线；记录窗口。
- Tracing 采样：dev 100% 可演示；prod 5~10%；错误/慢请求 tail sampling；OTLP 导出器队列上限，不能拖垮业务。
- 双实例：Snowflake `WORKER_ID` 必须不同；nginx keepalive 需先摘流量再 SIGTERM；`proxy_next_upstream` 不对非幂等 POST 开 `non_idempotent`；缓存广播/审计链/调度锁都要多实例验证。
- 分片表数量：V6 3×64 + V7 64 = 256；以 `SHOW TABLES` 为准，STATUS 的 192 只指 V6 段。

## 9. 调研结论对计划的直接影响

1. **不做 Spring Batch/命令 MQ**：任务表 + XXL-JOB 已能覆盖在线发放语义（§1.3）。
2. **控制台独立 `/console` + Spring Security**：不碰 `/api` 机器面；必须收窄 `AdminTokenFilter`（§2.2）。
3. **API 路径版本 v2 + OpenAPI 契约**：不上 Pact Broker（§2.3）。
4. **结算分“会计视图/应付视图”**：日账单不直接当结算单（§3.2）。
5. **风控表驱动 + 设备端口 + hold**：不上 Drools/ML（§4.3）。
6. **稳定性标准件组合**：SRE/Prometheus/Grafana/Tracing/k6/备份/CI（§5.2）。
7. **前端标准件**：React+AntD+OpenAPI 类型（§6）。

## 10. 本地集成点审计（摘要）

> 只读审计结论，用于“不要重复造轮子”；详细路径/行号见本轮审计报告（会话内）。

### 10.1 可直接复用

- 发件箱/MQ：`OutboxDispatcher` + `EventPublisher` + `coupon_event_consumed` 已有退避/死信/消费幂等；但当前只有 `ISSUED` 事件有完整链路，`topicOf()`/消费者要扩展。
- 调度：`@XxlJob` + `@Scheduled` + `RedisScanLock` 是现成的“持久化待办 + 多实例互斥”骨架；新任务照抄。
- 租户策略：`open_app_config` + `TenantConfigKey` + `CachedTenantConfigService` 已有校验/审计/缓存/热推送；新策略键直接加。
- 开放面：`OpenApiAuthFilter`/`OpenApiIdempotentFilter`/`OpenApiQuotaFilter`/`AppOwnership`/`@OpenResource` 已覆盖签名/时间窗/nonce/幂等/配额/归属；新接口复用。
- 限流/熔断/开关/预案：`RateLimiter`/`Bucket4jRateLimiter`/`TenantFlowRuleDataSource`/`DependencyCircuitBreakers`/`SwitchKey`/`SwitchPlan` 已可用。
- 缓存：`CacheTtl` + `CachedTemplateReader`/`CachedOpenAppReader`/`CachedTenantConfigService` 的三兄弟模式；新热读照抄。
- ID/键：`SnowflakeIdGenerator`、`BoundedKey`、`uk_*` + 撞键重放。
- 审计：`@AuditLog` + `AuditAspect` + `AuditService` 哈希链。
- 测试：`ShardedIntegrationTestSupport`、`OpenApiTestClient`、`FaultHooks`。

### 10.2 沉睡资产（先盘点再新建）

- `coupon_activity`（V9）有表/PO/Mapper，但**没有任何 Service 引用**；`TemplateCreateRequest.activityId` 只透传，不校验活动存在/预算/状态。预算闸门应激活它，而不是新建一套活动表。
- `coupon_event.activity_id/source`（V9）列已建，但 domain/PO 未映射；发放事件归因要补上。
- `coupon_template.approve_status`（V1）已有 `PENDING/APPROVED/REJECTED`，但 `create` 硬编码 `APPROVED`；审批流应激活状态机，不引入 Flowable。
- `coupon_template.stacking_group`（V9）列已建但未使用；当前叠加靠 `stacking_layer` + `exclusion_group`。同组叠加/热配置可作为阶段 6 可选。
- `coupon_usage.refund_no`（V9）列已建但未接线（L71）；退款权威仍是 `coupon_refund_order.refund_no`，不要重复造。
- `open_app_plan_apply`/`open_app_config_log` 已有操作者/快照/审计字段，可复用。

### 10.3 已知边界（必须在新功能里避开）

- **64 张分表**：`user_coupon`/`coupon_usage`/过期任务/超时任务按 `user_id%64`；新领域表优先未分片，不轻易动 64 表。`coupon_usage` 按 `usage_no` 查询不带 `user_id` 会广播（L23）。
- **Flyway 手工触发**：迁移在 `ShardingDataSourceConfig` 内、构造 ShardingSphere 前执行；迁移半失败会让应用起不来。新迁移从 V25 开始，连续编号。
- **`AdminTokenFilter`**：当前保护 `/api/**` 和 `/console` 非 GET；控制台登录会被它挡住，必须收窄为只保护 `/api/**`。`AdminSurfaceProtectionTest` 要同步。
- **`/api` 不是多租户面**：内部面 `appId=null`，新建资源归内置应用 `'1'`；租户自助必须走 `/open` 或新 `/tenant`。
- **L73**：`uk_idem(user_id, idempotent_key)` 不含 appId；新发放幂等键从一开始带 appId。
- **时区**：业务 Asia/Shanghai；JDBC URL/容器/CI/JVM 都要对齐；`LocalDate.now()` 依赖 JVM 默认时区。
- **Sentinel 全局状态**：`FlowRuleManager` 只有一个属性位；新维度复用 `TenantFlowRuleDataSource`，不要再挂第二个 property；自定义 Slot 的 `install` 必须在首次访问前。
- **审计哈希链**：单机 `synchronized`，多实例会断；用 `audit_chain_head` 单行 `FOR UPDATE` 或单写者。
- **Caffeine 无广播**：多实例最长约 60s 不一致；双实例阶段加 Redis pub/sub，保留 TTL 兜底。
- **日账单任务**：只有 `@Scheduled`，无 XXL/Redis 锁/失败指标；阶段 3 补。
- **发件箱 payload 2048**：新事件体大要扩宽或只放 ID；`topicOf()` 只有 ISSUED。
- **WSL 资源**：全量测试/压测/observability 串行；测试共享容器，MySQL `max-connections=500`；不要裸连 dev 库。

### 10.4 审计给出的 8 条集成建议

1. 新业务事件走 `coupon_event` + `coupon_outbox` 同事务，扩展 `topicOf()`/消费者，不在业务代码直接发 MQ。
2. 批量/定时/预算对账复用“任务表 + XXL 双通道 + RedisScanLock”，分片广播时锁键按分片号拆。
3. 租户策略统一 `TenantConfigKey` + `open_app_config`，不新建第二套配置表/缓存。
4. 新租户接口走 `/open/v1`，复用签名/幂等/配额/归属；管理写走 `/api` 非 GET，自动受保护。
5. 审计/指标复用 `@AuditLog`/`GovernanceMetrics`，不新建第二套；管理审计补操作者身份。
6. 新领域表优先未分片；需要按用户查询时加索引/异步宽表，不轻易进 64 分片族。
7. 新 ID/单号用雪花 + `BoundedKey`，幂等键从一开始带 appId。
8. 新测试复用 `ShardedIntegrationTestSupport`/`OpenApiTestClient`/`FaultHooks`；全量 `mvn clean test`。
