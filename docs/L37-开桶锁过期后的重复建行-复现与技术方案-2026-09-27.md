## 0. 一句话问题

开桶要往数据库写两处：先在模板行上把额度加进 `allocated`（一条条件 UPDATE），再往 `stock_bucket` 插一行桶行。两处之间如果执行线程被暂停、且暂停时间超过开桶锁的有效期（5 秒）——来源可以是长 GC、数据库阻塞、虚拟机挂起——锁会被别的请求接管；那个请求会把这笔"已划出、还没建行"的额度**补建一行**（差额恢复）；被暂停的线程恢复后又插一行，**同一段额度建了两行**。多出来的额度可以真实卖出去（超发），而对账的前三条等式都看不出来（重复建的行让各合计同步变大），第四条（Σquota ≡ allocated）此前只在数据库迁移脚本里检查过一次、运行时没有。

## 1. 背景：开桶的两步、锁、三道防线

### 1.1 开桶做什么（`StockBucketRouter`，行号核对自磁盘）

单桶版 `tryOpenBucket`（`src/main/java/com/newcoupon/application/service/StockBucketRouter.java` L110-166）的骨架：

```
① 抢锁             L110  在 Redis 上 SET NX PX 5000 抢锁键 c:opening:{tpl}，值=本线程的 UUID
② 读模板行         读 allocated（已划出额度）/ total（总库存）
③ 孤儿桶重放       数据库有桶行、Redis 名册里没有 → 重新执行一遍 Redis 开桶（幂等）
④ 读 Σquota       L130  已建桶行的 quota 合计
⑤ 三选一：
   - Σquota < allocated  → 差额恢复：把这笔"已划出、还没建行"的额度补建一行【不划款】
   - allocated >= total  → 真售罄，直接返回
   - 其余               → 正常开桶：先从模板行划走一段额度（casAllocate L140），再建行
⑥ 【故障注入缝】   L145-146  位置=额度已划出、桶行还没插
⑦ 选槽位 + 算世代   （有空闲槽位用空闲的；全忙则复用编号最小的活跃槽位，世代 +1）
⑧ 封旧代           （仅在复用槽位时：把该槽位旧世代的行标记为已封账 status=1）
⑨ 插桶行           L160  quota = 这段额度的大小
⑩ Redis 开桶 Lua   L161  登记活跃名册 + 建这个世代的四个键 + 把 c:alloc 加上这段额度
⑪ 释放锁           L166  只删自己 UUID 的锁（防止误删别人的）
```

批量版 `refillExhaustedBuckets`（L225-291）把 ⑤-⑩ 放进一个循环，一次把槽位补满。

### 1.2 三道防线各防什么、漏什么

| 防线 | 实现 | 防住的形态 | **漏掉的形态** |
|---|---|---|---|
| 开桶锁 | `setIfAbsent(c:opening, UUID, 5秒)`（RedisStockGateway L427-432）；释放前比对 UUID（L434） | 正常并发下重复开桶；持锁者**进程结束**后，锁 5 秒自动过期、他人接管 | 持锁者**被暂停**（没结束）超过 5 秒：锁被接管，但持锁者恢复后继续执行 ⑦-⑩，没人拦 |
| 唯一键 `uk_tpl_bucket_gen` | `(template_id, bucket_no, generation)` | 同一个槽位同一个世代的重复行 | 恢复执行的开桶者会在 ⑦ **重新选槽位**——换了槽位或世代，这个键不冲突 |
| Redis 幂等门 | 开桶 Lua 首段：`HGET(act,槽位)==世代 且 库存键存在 → 返回 0` | 同一个世代重复执行开桶（孤儿桶重放场景：行已建、Redis 没建，重放时不会把 c:alloc 加两次） | 换过世代的恢复者（`HGET(act,槽位) != 世代`）→ 照常执行，c:alloc 照加 |

三道防线各自有一个前提：锁假定"持锁者不会恢复执行"；唯一键假定"重复的行落在同一个槽位/世代"；幂等门假定"重复执行发生在同一个世代"。本次的问题恰好三个前提都不成立。

### 1.3 差额恢复的语义（问题的一半在这里）

`tryOpenBucket` L130-135：`Σquota < allocated` 时，补建 `allocated - Σquota` 这么一行（不超过一个桶额），**不执行划款**——因为钱已经划出来了，只是还没建行。它的语义是"把已划出、还没建行的额度补上"——**它无法区分这笔额度属于"进程已经结束的开桶人"还是"只是被暂停、还会恢复执行的开桶人"**。锁的有效期把前者放心地交给接管者，但管不住后者。这就是问题的根。

### 1.4 业界对照：锁的有效期保证什么、不保证什么

锁的过期时间只能保证"结束了的持锁者不会永远占着锁"（进程没了，5 秒后别人能接管），**不能保证"被暂停的持锁者恢复后不再写"**。分布式锁的经典解法叫 fencing token：写操作携带一个单调递增的编号，存储侧拒绝过期的编号。本系统的锁有 UUID，但只用于**释放时比对**（防止误删别人的锁），不用于**写入校验**——所以恢复者的写入不受任何约束。

**系统内对照**：六个定时任务也用分布式锁（RedisScanLock），但它们的正确性由幂等的 CAS 保证、锁只用于减少重复扫描——恢复者顶多多跑一遍，没有副作用。**开桶是全系统唯一一个"在锁保护下往数据库和 Redis 写钱"的地方**，所以只有它会被这个问题伤到。

## 2. 复现：时间线推演

### 2.1 触发条件（三条同时满足）

1. 一个开桶线程在"额度已划出、桶行还没插"之间被暂停，暂停超过 5 秒（锁的有效期）；
2. 暂停期间有请求走进了差额恢复分支（路径：领券撞 -10 → 批量重开先返回 false（额度已分完）→ 单桶开桶看到差额）；
3. 被暂停的线程恢复后继续执行——代码在故障注入缝之后**没有任何重新检查**，它不知道自己已失去锁、也不知道那笔额度已被补建。

暂停的现实来源：长 GC 停顿、插入语句被数据库阻塞（等元数据锁/行锁、磁盘 IO 卡顿）、虚拟机或容器挂起、线程 dump。

### 2.2 时间线（配置=故障注入测试档：桶额 5、2 个槽位、total=15）

```
初始：发布开了 2 个槽位（0/1 各 5 张），allocated=10，Σquota=10
     10 个用户把两桶领光（used=5/5，Redis 库存键=0）

① 开桶人 A（一个撞 -10 的领券请求线程）走批量重开 refillExhaustedBuckets：
   - 抢到锁（有效期 5 秒开始计时）
   - ① 把库存为 0 的两个旧世代封账（status=1）
   - ② 循环第 1 轮：allocated(10) < total(15) → n = min(5, 15-10) = 5
   - casAllocate(5) → allocated = 15                    ← 已提交
   - FaultHooks.fire(OPEN_BUCKET_SEAM)                   ← A 在这里被暂停 7 秒
     此刻：allocated=15，Σquota=10（差 5 = A 已划出、还没建行的那一段），c:alloc=10

② B（5.5 秒后，另一个撞 -10 的领券请求）：批量重开第一步返回 false（allocated>=total）
   → 落到单桶开桶 tryOpenBucket：
   - 抢到锁（A 的锁已在第 5 秒过期）
   - 孤儿桶重放：活跃行为空（旧世代被 A 封了、A 的行还没插）→ 无
   - Σquota(10) < allocated(15) → 差额恢复：n = 5，不划款
   - 插行 (槽位0, 世代2, quota=5) → Σquota = 15        ← B 补建的正是 A 那一段
   - Redis 开桶：名册 槽0→世代2，c:alloc = 15
   - 返回 true → 调用方重扣 → 领到 1 张
     此刻：allocated=15，Σquota=15，c:alloc=15 —— 三本账全平（正确的中间态）

③ A 恢复（约第 7 秒）：从缝继续，没有任何检查：
   - 选槽位：活跃行={(0,2)}（B 那行）→ 槽位 1 空闲（它的旧世代已被 A 自己封账）→ 选槽位 1
   - 世代 = 2；封旧代无操作
   - 插行 (槽位1, 世代2, quota=5) → 唯一键 (tpl,1,2) 不冲突 → 插入成功
   - Redis 开桶：名册 槽1→世代2，c:alloc = 20
   - 循环条件 15<15 不成立 → 退出

终态：allocated=15，Σquota=20，c:alloc=20
      —— A 那 5 张被建了两行（B 的行 + A 的行）
```

### 2.3 两个变体（取决于 A 恢复时选到哪个槽位）

- **变体一：A 选到空闲槽位（如上）**——B 的行和 A 的行都是活跃、都有货 → 可卖 10 张而账上只支持 5 张 → 继续领券 10 张全部成功 → **总发放 20 > total 15 = 真超发 5 张**。为什么真能卖出去：数据库的逐笔条件扣账守卫是 `used < quota AND status = 0`——只看**行内**额度，不看 allocated/total；Redis 侧名册指向两行、库存键都大于 0。两道防线都放行。
- **变体二：A 复用 B 的槽位**——A 的封旧代会把 B 那行封账（status=1）→ B 的 5 张卖不出去（少卖），A 的多余行顶替 → 账破（Σquota > allocated）但可卖量近似不变。

方向裁决：变体一 = 超发方向（危险）；变体二 = 少卖方向（安全）。**两个变体都破坏账目。**

## 3. 为什么现有检查看不见

终态（allocated=15，Σquota=20，c:alloc=20）下，巡检 `conservationCheckOne` 的检查逐条过一遍：

| 检查 | 读数 | 结果 |
|---|---|---|
| 各世代桶内守恒（Redis 四个键之和 ≡ quota） | 两行都是全新世代（库存=quota、其余=0） | 自洽 |
| Σ四键 ≡ c:alloc | 20 ≡ 20 | 平 |
| c:alloc ≡ Σquota | 20 ≡ 20 | 平 |

唯一被破坏的是第四条：**Σquota ≡ 模板行的 allocated（20 ≠ 15）**。全仓库核查（2026-09-27）：这条不变量只出现在
- V10 迁移脚本的一次性断言（迁移时检查，之后不再运行）；
- `StockBucketMapper.sumQuota` 的注释里（写着"巡检 E3a 侧证"——但代码里没有这条检查）。

运行时的巡检、日审、修复流程都不读 `template.allocated`。所以账被破坏后**没有任何现有机制会报告**。

## 5. 修复方案（已批准→已实施）

### 5.1 第一层（根治）：额度段上界 + 唯一键

**一句话**：每一行桶行记下"它覆盖的是模板 allocated 的哪一段的末端位置"，同一模板内同一个末端位置只允许一行——重复建行会在唯一键上失败，由应用层挡下。

- **列与键**（V13 迁移）：`stock_bucket.allocated_hi BIGINT`（本行覆盖的额度段上界），唯一键 `uk_tpl_allocated_hi (template_id, allocated_hi)`。

- **取值规则（单一公式）**：`allocated_hi = 建行前读到的 Σquota + 本行 quota`。正常开桶行与差额恢复行同一公式。

- **关键纪律**：这个值必须用**进入暂停窗口之前读到的 Σquota** 来算，插行时**绝不能重新读一次**。原因：恢复执行的开桶者如果重新读，读到的是"别人已经补建之后"的合计，算出的上界会落在下一段上——唯一键撞不上，重复建行照样发生。两条写入路径的实现：
  - `tryOpenBucket`：L130 读到的 `rowsQuota` 本来就在划款之前 → `row.setAllocatedHi(rowsQuota + n)`（差额恢复分支与正常分支同式）；
  - `refillExhaustedBuckets`：在循环体顶部（划款之前）增加一次 `sumQuota` 读，`row.setAllocatedHi(segBase + n)`。

- **为什么两个开桶者会算出同一个上界**（碰撞的来源）：
  - A 读 Σquota=10、划款 5 → 上界 10+5=15；
  - B 差额恢复读 Σquota=10、补建 5 → 上界 10+5=15；
  - 谁先插谁成功；后插的撞唯一键。**同一段额度（10→15）只可能有一行**。

- **撞键后的处理**：插行处捕获 `DuplicateKeyException` → 记一条 warn 日志（"重复建行已拦截"）→ **返回 true**。返回 true 的含义是"这段额度已经被别人建好行了，调用方去重扣即可"——调用方重扣时要么直接命中对方建的行（已注册进 Redis），要么先经过孤儿桶重放把它登记进去（行在、名册无的场景有兜底）。批量重开路径撞键时停止本轮、返回 true，尚未建完的段由后续请求的差额恢复补齐（安全方向，不会超发）。

- **迁移 V13 的回填**：历史行的精确段位置无法还原，按模板内固定顺序（桶号、世代、id）用窗口函数累加 quota 作为段上界。安全依据：回填后同模板内的值互不相同，且最大值恰好等于"当前已建行额度合计"；而以后新建行的段上界 = 当时的合计 + 新额度 > 全部历史值，不会误撞。加唯一键放在回填之后——**如果存量数据里已有重复（历史上发生过重复建行），加键会失败并中止迁移，这本身就是一条断言**。

- **两个顺序的正确性对照**（谁先谁后都恰好一行入账）：
  - 恢复者先插：它的行（上界 15）成功 → 差额恢复行撞键 → 恢复方返回 true → Σquota=15=allocated；
  - 差额恢复先插：它的行（上界 15）成功 → 恢复者撞键 → 恢复者放弃 → 同样 Σquota=15=allocated。
  - 两个方向都收敛到同一状态；未建完的段（比一个桶额大的差额）由后续开桶逐段补齐。

### 5.2 实施期调整：封账挪到建行之后

原代码顺序是"封旧代 → 建行"。这样在"插行被唯一键挡下"的路径上，可能先把并发者刚建的那行封掉（status=1），造成它的库存在数据库侧卖不出去（变体二的少卖）。实施时把封旧代挪到**建行成功之后**：撞键返回的路径上没有任何行被误封。两次数据库写之间多出的"同槽位两代都活跃"的窗口无法避免（两处写本来就不在一个事务里），但它是瞬时的、且旧世代库存为 0，不影响正确性；若进程恰好在该窗口结束，遗留的旧世代行会被下一次复用槽位或批量重开的封账步骤收掉。

### 5.3 第二层（检测兜底）：巡检加第四条不变量

`conservationCheckOne` 增加 `Σquota ≡ allocated` 这一条（`StockReconcileService`，读法：`templateMapper.selectById` 取 `allocated`，读不到就跳过这条检查）：

- 三段确认（首读 → 新鲜重读 → 200ms 复读）与既有检查共用；
- 方向裁决：
  - **Σquota > allocated**：危险方向（同一段额度建了两行 = 超发方向）→ 冻结 + 告警；
  - **Σquota < allocated**：安全方向（已划出、还没建行——可能是开桶动作正在被暂停，也可能是补建没跑完）→ 只告警不冻结。运行时这条差值在"划款到建行之间"是正常的毫秒级瞬态，会被 200ms 复读滤掉；持续存在才告警。

## 8. 诚实记录：为什么之前几轮审查没抓到

- 三视角审查（P2b 收口）：发现都来自"并发交错、边界值、状态机"的枚举；本次问题需要挑战的是**锁的时间语义**（"被暂停、还会恢复"这种状态），不在当时的枚举维度里。
- 故障注入三连：开桶夹缝用例模拟的是"进程结束"（异常透出、不再回来）——差额恢复和孤儿桶重放正是它的设计对偶；**没有任何用例模拟"暂停后恢复执行"**。这个状态恰好落在"结束了"和"正常在跑"之间。
- 终审：覆盖的是安全/可靠性/性能的惯例清单，没有涉及锁的有效期与执行暂停之间的关系。
- 教训一句话：**"锁 5 秒过期"背后有一条从未被写下来的假设——"持锁者要么正常在跑、要么结束了不再回来"。没写下来的假设不会被审查。**
