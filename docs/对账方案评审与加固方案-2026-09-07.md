## 二、外部 R1-R11 逐条详解（裁定 + 机制 + 我的修正）

> 每条按"裁定 → 为什么（具体过程，用数字推演）→ 与外部评审的分歧点"讲。代码行号以当前 HEAD 为准。

### R1 多实例失效 —— 确认（"未提"改判"已声明但后果定量不足+无运行时防护"）

**机制（失配公式）**：流量稳态下 `diff ≈ 全局在途 F`（每个在途请求的 DECR 已进 Redis、提交未进 issued_count）；本机计数器只数到 `F/N`（N 实例均分）。误判条件：`F − F/N > 5`，即 **N=2 时 F>10、N=3 时 F>7.5**——按 5000 QPS、DB 事务 10-20ms 估算 F≈50-100，**每小时每实例必然误判**，二次复核救不了（F 是平台不是毛刺，且复核读同一个偏小的本机计数器）。

**与外部评审的分歧（两处）**：
1. "文档未提"不成立——ADR-0007 认账段、StockReconcileService 类注释、ROADMAP L16+M2 三处明示单实例口径与 M2 前置计划。正确的批评是：**后果只写到"需换汇总"，定量后果（每小时假重建、DB 拒绝风暴、1h 震荡）没写，且纯靠流程纪律没有任何运行时防护**（无锁依赖、无启动断言），M2 前一次误扩容就静默触发。
2. "三实例互覆 SET"是次生现象（双方都来自 DB 快照，后 SET 者更新鲜，近似良性）；**主害是每次假 rebuild 的无条件 SET 抹掉（DB读→SET落地）窗口内过闸请求的 DECR**，把 F 个在途当作已结算 → Redis 偏高 ≈ F+窗口扣减 → 闸门超放 → DB 拒绝+补偿风暴。

**修法（上多实例前必须，M2 门禁）**：①`@Scheduled` 加分布式锁（ShedLock）或选主；②计数器 Redis 化（`c:inf:{tplId}` 挂同 hash tag，deduct/compensate Lua 内原子 INCR/DECR + 滑动 TTL 防泄漏）或 Micrometer 汇总；③**不等 M2 的便宜保险（建议现在做）**：启动断言——检测到多实例（如 Spring Cloud 实例数/环境变量）时拒绝启用对账并告警，一行成本消除对运维纪律的依赖。

### R2 计数器全局不分模板 —— 确认（我的设计盲区）

**机制**：`ReceiveInFlightCounter` 是单个无模板维度的 AtomicLong（ReceiveInFlightCounter.java:20）；任意模板过闸都 inc 到同一个数；measure() 用它对**每个模板各自的** diff 构造容忍带。模板 A 的 diff 精确等于 A 的在途，但容忍带混进了 B/C 的在途——B 大促在途 200 时，A 的真漂移 ≤208 全部隐形，**一小时又一小时**。
**单实例也成立**（同一 JVM 多模板并发领取），不需要多实例触发。
**修法**：计数器改按模板维度 `Map<templateId, AtomicLong>`（单实例）；Redis 化方案（`c:inf:{tplId}`）天然按模板，与 R1 一并解决。

### R3 容差 5 在流量下不够 —— 确认（机制修正：泄漏项不是新请求，是提交者）

**外部评审的推导不精确，真实机制更系统性**。量测次序 T1=读DB issued → T2=读Redis → T3=读计数器：

- 外部说"读间隔内的新请求抬高 diff"——错一半：新请求 DECR 后**微秒级**就 inc（两行代码之间无 IO），inc 必然先于 T3，diff+1 与 F+1 对冲，**大多被覆盖**。
- 真正的系统性泄漏是 **DB 提交落在 (T1,T3) 窗口内的请求**：它的 DECR 已进 R(T2)（diff+1），它的提交未进 expected(T1)（快照偏旧），而它的 finally dec 又先于 T3 完成——**计数器已经把它放走**。每个提交者贡献 +1 无覆盖 diff。
- 量级 = 成功速率 × (T3−T1) = 速率 × (DB SELECT + Redis GET + **连接池排队**)。健康链路 2-5ms ⇒ **1000-2500 QPS 破 5**；池排队放大跨度（代码注释自证 2000 并发撞池）后**几百 QPS 即破**。
- **5s 二次复核救不了**：该偏差是稳态比例量（∝ 持续速率），两次量测同等偏置——double-confirm 形同虚设。
- 后果链延伸到 N1：假修复 SET 抹掉在途 DECR → 偏高 ≈ 在途数 → 模板售罄即进入自持环——**不是一次性误修，是闸门在售罄热点上被持续击穿**。

**修法**：①量测前后各读一次计数器取 max + 容忍带动态化 `max(5, 速率×跨度估计)`；②**高峰压测专项（M3 必做）验证容差公式**——当前所有测试都在低 QPS 下跑，这个假设从未被压测。

### R4 循环无异常隔离 —— 确认

**机制**：`reconcileAll` 的 for 循环无 try/catch；measure 里 DB/Redis 调用都可能抛（连接抖动、超时 1s）。第 17 个模板抛异常 → 本轮剩余全部跳过 → Spring 调度器吞掉异常 → 若某模板有真漂移，要等下一个整点。**Redis 是每次必经的远端读，是最现实的触发源**（这吸收了 R8 的担忧能量）。
**修法**：循环体 try/catch，单模板失败记日志+计数+继续；整轮失败率有指标告警（M2）。

### R5 从库读旧值 —— 部分成立（当前不触发，M4 变现实）

**机制成立且比外部更糟**：从库延迟下 issued 偏小 → expected 偏大 → diff 系统性为正；在途计数器**救不了**（从库延迟是"主库已提交、从库不可见"——inc/dec 已配对归零，diff 仍虚高）；5s 复核也救不了（复测走同一从库）。外部说"震荡"——**稳态延迟下更糟：不震荡，偏高被烧进基线后下一轮 diff≈0 判"一致"，永久隐形**。
**当前核实**：单 JDBC URL、无任何读写分离依赖——今天恒读主库。**M4 的主从+切读落地（演练矩阵明列）使其变现实**。
**修法（现在就立约束，不等 M4）**：ADR-0007 追加架构约束"**对账读（measure/rebuildStock 的模板读）禁止从库、禁止缓存，必须强制主库**（专用数据源或路由 hint）"，并把"对账读走主库"列入 M4 切读演练验收项。

### R6 修复暴露窗 1h —— 确认并升级（售罄时无界）

非售罄模板：残余偏高 ≈ 修复时刻在途数（5000QPS×30ms≈150），放行者被 DB 正常受理属合法发放，损害递延到售罄瞬间——**与 N1 组合后，售罄模板上暴露窗无界**（对账 SET 0 被迟到补偿顶回，永不收敛）。
**修法**：N1 的修复（售罄钉零）根治；另加"rebuild 后 60s 快速复查"把非售罄场景的收敛窗从 1h 压到 1min。

### R7 调度线程阻塞 —— 确认（今天零影响，M1 即爆发）

Spring @Scheduled 默认**单线程**调度器（全仓库无覆盖配置）；当前全库只有对账 1 个 @Scheduled——**今天 sleep 只拖延对账自己**（外部评审此处不准）。但 **M1 将新增券过期+锁定超时两个定时任务**：K 个疑似模板 ×5s 串行睡眠 = 调度器黑洞（K=30 时约 3 分钟），期间**M1 自己要交付的过期/释放任务停摆**——过期券继续可用、锁死券 SLA 违约。
**修法**：`spring.task.scheduling.pool.size≥2` 一行配置（或复核改调度器外的一次性延迟任务）。

### R8 null 语义混淆 —— 反驳

**核实**：`remaining()` 用 `opsForValue().get()`；Lettuce 在连接失败/命令超时下**抛异常**（包装为 DataAccessException 上抛），**不会静默返回 null**——项目未配置任何吞异常的组件。null 的唯一语义是"Redis 可达且 key 不存在"，恰好是 KEY_MISSING 的正确设计输入。方向也相反：抖动时系统是**不重建**（fail-safe）不是误重建。R8 的合理担忧（抖动→异常→报废整轮）完全落在 R4 机制内，已并入 R4 修法。
**残余极小项**：人工往 key 写非数值时 `Long.parseLong` 抛 NumberFormatException 走 R4 路径——运维纪律项（R11c 已覆盖"c:stk 只准网关写"）。

### R9 只守 stock 一扇门 —— 确认（时长精确化）

今天偏高计数的主要源头：kill -9 在途残余（Lua 已 INCR 三计数、DB 未提交）——**对账修了 stock，同批请求的 ul/uld/dly 偏高永久留存**（旧源头"双补偿"已被幂等门控关闭）。后果按 key：
- ul 偏高 → 闸门 -2 直接拒绝（不核对 DB 实领数）→ 最长 **7 天**（TTL 604800，且被拒不再续期）；
- uld 偏高 → 拒绝到**当日 24 点**（key 含日期，"至 TTL"说法不准确）；
- dly 偏高 → **全模板所有用户**被拒到午夜——半径最大，但幅度受崩溃瞬间在途数限制。

**兜底方向不对称**（核心论点成立）：uk_user_seq 只兜 ul **偏低**方向；L3 计划的自愈也是偏低方向；偏高方向两个都不管。
**修法（M1 顺带，L3/L4 扩展）**：dly 与 DB 当日 issued 增量互证；ul 撞索引自愈（见 N3 修法，两个方向都要）；uld 先告警不重建（逐用户核对成本高）。

### R10 计数器泄漏 —— 确认

测试断言防"现在写错"，防不了"将来改坏"（inc 挪进 try / 中间插抛异常行 / DB 调用异步化——dec 不再与 inc 同生命周期）。泄漏 = 虚假在途永久撑大容忍带 = 真漂移被掩盖（与 R2 同机理）且无报错。
**修法**：运行时守卫——静默期（QPS≈0 持续 60s）计数器仍 >0 → 告警；绝对上限熔断（inFlight > 连接池×2 时告警）。依赖 M2 的 metrics 通道，先做上限告警。

### R11 五个低危项 —— 确认

①initialDelay=1h：上线首小时无对账 → 改 5min（冷启动安全）；②rebuilt 数无消费 → 差异落表（M2，并入 novel-M2 修复）；③手工 SET 运维纪律 → 写进网关注释与演练 checklist；④**06d"3s 论据"勘误成立**：connection-timeout 只管拿连接，行锁等待默认 50s——结论侥幸正确（任意时长在途都被计数器精确跟踪，恒等式不破），论据错误，06d 已列勘误；⑤多实例日期 key 跨零点分裂 → M2 多实例门禁项（统一时区+时钟同步检查）。

## 三、我方新发现详解（全部经对抗核实，这是比外部清单更重要的部分）

### N1【高·已核实】售罄模板的过补偿自持环——闸门在最需要它的时刻被击穿

**触发**：模板售罄（DB issued=total）时仍有持续流量，且 Redis stock 存在任意幅度偏高 δ。δ 的来源全部是现实路径：R3 高峰假修复、N2 懒重建风暴、双重补偿、人工误 SET。**单实例即可触发**。

**逐步推演**：
1. 售罄时 expected=0，Redis 实际 R=δ>0。入口校验不查售罄（assertReceivable 只查审批/发布/窗口），Lua 只查 stock≤0 → **每个请求照样过闸**：DECR → R=δ−1；
2. DB 侧 casDeductStock 影响 0 行（issued=total）→ 抛信号 → 编排层**先无条件补偿**：INCR → R 回 δ。用户拿到正确的 STOCK_OUT，但**每个请求付出 3 次远程操作**（扣减 Lua + DB 事务尝试 + 补偿 Lua），DECR 与 INCR 互相抵消，**δ 永不耗尽**；
3. 整点对账测得 diff=0−δ<0 → 复核仍 <0 → rebuild **SET 0**；
4. SET 落地瞬间，管线内已过闸的请求（5000QPS 下数百个）陆续被 DB 拒绝并补偿 INCR——**只要有一个迟到 INCR 落在 SET 之后，R≥1** → 下个请求 DECR→0→DB 拒→INCR→1 → **自持**。一个迟到补偿就够；
5. 下一小时重复③④，**永远收不了口**；只有流量回落才自愈。

**后果定性**：不资损（DB 双防线 + 用户拿到正确 STOCK_OUT），但**售罄热点模板上 Redis 闸门被完全击穿——它存在的全部意义（售罄后替 DB 挡流量）恰在最高峰时刻失效，DB 以约 3 倍放大承接全量请求**。

**修法（设计）**：**分类先行**——StockDeductRejectedException 先在事务外取新快照分类（现有 classifyDeductReject 前移），**售罄分支的补偿不再 INCR stock**，改为"stock 直接 SET 0（幂等钉零）+ 只回滚三个计数 + DEL 幂等键"；非售罄分支（模板下线）同样跳过 stock。次选（不推荐）：rebuild 后短窗熔断等管线排空——引入新时序复杂度。

### N2【高·已核实】-7 懒重建风暴——Redis 清库瞬间的并发 SET 雷击

**触发**：Redis 重启/FLUSH/故障切换导致 c:stk key 消失的瞬间仍有流量（大促中 Redis 抖动与高流量强相关）。单实例即触发。

**逐步推演**：①key 缺失 → 所有 deduct 返回 -7（早退，未写任何 key）；②**每个**收到 -7 的请求都各自同步执行 rebuildStock（无锁、无 single-flight、无退避）——每次 = 一条 DB SELECT + 一个**无条件 SET**。5000QPS 下等于瞬间向 20 连接的池子注入全量额外读，重建请求互相排队拉长风暴窗口，同时这批请求挂起占用 Tomcat 线程；③第一个 SET 落地后，后续 deduct 开始正常过闸并 DECR；**但风暴中其余请求的 SET（各自持有可能更旧的 DB 快照）陆续落地、无条件覆盖——先过闸请求的 DECR 被整批抹掉**；④管线落定后 Redis 偏高 ≈ 速率×(DB事务+风暴时长)，高峰量级上百；若期间售罄 → 直接点燃 N1。
**ADR-0007 曾认账"懒重建毫秒级竞态量级极小（key 缺失时本就无扣减流量）"——该 dismissal 的前提在风暴场景不成立**（第一个 SET 落地扣减流量即刻恢复，而排队中的 SET 数秒后才落地），已在 ADR 勘误。

**修法（设计）**：懒重建路径改**条件 SET**（新 Lua：`if EXISTS stock then return 0 end; SET ...`）——首个 SET 生效后其余风暴 SET 全部 no-op，其后的 DECR 天然保留；且首个 SET 之前 key 不存在、无人能过闸，**该路径做到零竞态**。对账的漂移重建（key 存在）保留无条件 SET，**两个方法分开治理**。另：-7 重试前随机退避 50-200ms 削平 DB 雷击。

### N3【高·已核实】ul 计数的 7 天 TTL 是"计划性失忆"——部分领取用户被永久误拒

**触发**：perUserLimit≥2 的模板 + 用户两次领取间隔≥7 天（长周期活动的常态人群）。部署形态无关。

**逐步推演**（perUserLimit=3，活动 30 天）：Day1 用户领第 1 张：DB 落 (uid,tpl,seq=1)，Redis c:ul=1 且 EXPIRE 7天（硬编码，仅成功扣减时刷新）；Day8 起静默 → key 过期归零；Day10 领第 2 张：①Lua 读 c:ul=nil → 按 0 算，过闸，INCR→1，返回 seq=0+1=**1**；②DB INSERT (uid,tpl,seq=1) **撞 uk_user_seq 历史首行** → DuplicateKey；③补偿把 c:ul DECR 回 0；④分类：幂等键查无 → 抛"已达限领上限"（**实际才领 1/3，错误语义为假**）。此后**每次串行重试完全复现**：ul 永远停在 0，seq 永远=1——**无限期拒绝**。唯一逃生通道是并发（两个请求同时进，第二个读到 ul=1 → seq=2 若空槽则成功）——**"并发能解、串行锁死"的倒挂**。

**根因**：docs/03"所有计数 key 强制 TTL"的内存策略被机械套用到**无日期维度的全生命周期累计 key**上——TTL 在这里不是清理，是**数据模型失忆**。STATUS L3 把成因框成偶发"漂移"，没意识到 7 天 TTL 让它成为每个长活动的**必然事件**。

**修法（设计，M1 L3 扩展）**：①撞索引自愈两个方向都做：uk_user_seq 碰撞且幂等键不存在时，从 DB 回填 c:ul=COUNT(实领行数) 再重试一次；②**c:ul 的 TTL 绑定模板有效期**（deduct 的 ARGV 传模板剩余有效期+缓冲），内存回收由活动生命周期驱动而非失忆驱动；③ul 抽样对账（Redis 计数 vs DB 行数）纳入对账告警。

### 中低危新发现（摘要，全文见 workflow 归档）

- **M1 偏高方向高峰被掩盖**：R3 同项"提交泄漏 u"会把真偏高 m≤u 压进一致区间——**"Redis 偏高零容忍"的承诺高峰不成立**，与 R3 同根同治（动态容忍带 + 紧凑次序复测）。
- **M2 差异零持久化**：重建只有日志痕迹；"同模板连续重建"（漂移源未死的最强信号）无检测；docs/01 要求的"差异落表供财务复核"未实现 → 建 stock_drift_log 表 + 连续 2 次重建升级告警并冻结自动重建转人工。
- **M3 issued_count 单点盲信**：对账与 DB 双防线信任同一列——账本错（M4 双写丢更新/人工修数）时**两者同时失效成超发放大器** → 对账加第二不变式：issued_count 与 COUNT(user_coupon) 互证，差超容忍 → 冻结重建+告警先修账本；M4 演练加"故意丢一条 UPDATE→对账必须告警"验收用例。
- **L1 appendStock 三写者**（M6）：定死协议——DB 先行 + Redis 用 INCRBY（非 SET）+ stock_epoch 版本号 CAS，写进 M6 开题约束。
- **L2 M3 缓存架空对账**：L6 实施时给对账留 findByIdFresh 强一致通道，与 R5 合并成同一条架构约束"**对账读禁止从库、禁止缓存**"。

### D 级：接受的残余（写明理由）
