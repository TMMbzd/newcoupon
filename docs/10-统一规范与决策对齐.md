# 第十章 统一规范与决策对齐（冲突裁决，以本章为准）

> 背景：01~09 章由 9 个独立领域专家基于同一批素材撰写，审查发现存在命名、时序步数、Redis 结构、落库方式等口径出入。真实团队里这叫"文档腐化"，必须在动工前收敛。本章是**唯一规范**：任何章节与本章冲突，以本章为准。每条裁决附理由。

## 10.1 命名与表结构规范（Canonical Schema）

各章曾出现 `coupon_batch`/`coupon_template`、`coupon_stock_segment`/`coupon_stock_ledger`/`coupon_stock`、`coupon_event`/`coupon_consume_record` 混用。统一如下：

| 规范名 | 含义 | 关键约束 |
|---|---|---|
| `coupon_template` | 券模板/批次（同义词，统一叫模板） | 双状态机字段 + 四层限额 + total_count 只增 |
| `user_coupon_{0000..}` | 用户券实例，按 user_id 分库分表 | 快照字段 + `UNIQUE(user_id, request_id)` + `KEY(user_id,status)` + `KEY(status,valid_end)` |
| `coupon_stock` | 库存底账（DB 账本） | 三字段不变式载体：`total_amount`(审批量,不可变) / `pushed_amount`(已推 Redis) / `issued_amount`(已落券)，恒有 issued ≤ pushed ≤ total；含 `bucket_count/low_water/replenish_step` 分桶增补参数 |
| `coupon_usage` | 占用单（锁券/核销单） | `UNIQUE(usage_no)`，usage_no = orderNo + couponId |
| `coupon_event` | **全域唯一事实源** | event_type: 1发放 2锁定 3核销 4释放 5过期 6作废；核销事件的 amount = 分摊后实际抵扣额。**不另设 coupon_consume_record**——核销明细就是 event_type=3 的记录（统计/对账全部回放本表） |
| `coupon_grant_txn` | 发券本地事务表（outbox） | 仅异步落库模式启用；status: 0待发 1已发MQ 2已落库 3已回补 |
| `coupon_expire_task` | 过期任务表 | 窄行三业务字段 + `uk(coupon_code)` + `KEY(expire_time, task_status)` |

用户券状态枚举统一（终态加 ★）：`0 待使用 / 1 已锁定 / 2 已核销★ / 3 已过期★ / 4 已作废★`，可选扩展 `5 待激活`（任务券）、`6 已回收`（活动资格取消，语义=作废的审计变体，不推荐单独设）。**不设"已退回/已取消"独立态**——回退是回到 0（未过期时），由占用单+事件承载追溯。

## 10.2 库存 Redis 结构规范

各章曾出现 String / Hash 两种选型。**裁决：常规批次用 Hash + hash tag，热点批次分桶后每桶一个 Hash**：

- `c:stk:{tplId}:b{bucketNo}` → Hash：field `left` = 桶余量，field `{yyyyMMdd}` = 当日已发（日期做 field 天然按天滚动，无跨天重置任务——腾讯云方案）。
- **hash tag `{tplId}` 的意义**：Redis Cluster 要求 Lua 涉及的所有 Key 同 slot，同批次 key 共用 tag 才能单脚本全原子；代价是单批次吞吐 = 单分片 ≈ 2 万 QPS——这就是必须分桶的原因，分桶后 tag 变 `{tplId:b3}`。
- 用户计数**不用批次大 Hash**（防大 Key），用独立小 Key：`c:ul:{tplId}:{uid}`（总限领）、`c:uld:{yyyyMMdd}:{tplId}:{uid}`（日限领），**强制 TTL + 随机抖动**。
- 幂等：`c:idem:{uid}:{requestId}` SET NX EX 600 前置；**弃用批次级 ZSET 防重**（百万 member 大 Key 风险），DB 唯一索引终审。

## 10.3 五重校验顺序规范

统一为：**幂等 → 库存（售罄）→ 批次日限 → 用户总限 → 用户日限**，全部在同一 Lua 内原子执行，失败路径回滚已 INCR 的计数（对称性）。说明：顺序只影响"先报哪个错"，不影响正确性；把售罄放校验最前是为了让最大量的失败请求（售罄后）最快返回。

## 10.4 落库方式规范（同步 vs 异步）

各章最终形态结论相反（01=同步+补偿，02/03=outbox 异步）。**裁决：做成开关，默认同步，热点脉冲批次切异步**：

- 同步模式（默认）：Lua 扣减 → 本地事务 insert user_coupon + insert event → 失败投补偿队列回滚 Redis。正确性便宜、读己之写即时、唯一索引即时兜底。
- 异步模式（配置切换）：Lua 扣减 → insert coupon_grant_txn（outbox）→ MQ 消费者落库。用于红包雨型脉冲或单批次流量逼近 DB 分片写能力。
- **两种模式共用同一套补偿/回滚/对账底座**，切换只是配置项，不是两套代码。

## 10.5 分库分表路由规范

统一采用 vivo 两段式（**不采用字节的 user_id 后四位**——尾号定向活动会造成倾斜）：

```
表后缀 tableSuffix = hash(user_id) % M          // M=表总数
库后缀 dbSuffix    = hash(user_id) / M % N      // N=库总数
```

进阶（可选，数禾基因法）：`couponId = user_id 前 15 位 + 雪花 18 位`，使 couponId 可独立路由。**若启用基因法，hash 输入必须与上式一致（都取 user_id 前 15 位或都用完整 user_id）**——否则按 couponId 路由与按 user_id 路由会落到不同分片，破坏"任一 ID 可路由"。

幂等唯一索引规范：`(biz_id, request_id)` 全局语义 + 分片内 `(user_id, request_id)` 物理约束（中台多租户下两者都要；单业务阶段只需后者）。批量领券（券包）：一次请求 N 张券 = N 个独立领券意图，子幂等键 = `requestId:itemIndex`，逐券独立事务，单券失败不影响其他券，返回逐券结果明细。

## 10.6 库存扣减选型决策树（收敛 03/07 章的相反结论）

```
单批次预期峰值 QPS？
├─ < 2000  → DB 分段库存（vivo 式）：M 段随机扣 + 定时汇总，强一致免对账
├─ 2000 ~ 20000 → Redis+Lua 单 key（hash tag 同 slot 全原子）
└─ > 20000 → Redis 分桶（桶数 = 峰值/2万 向上取整）+ 随机不重复轮询 + 售罄桶跳过
              └─ 所有档位共用：DB coupon_stock 三字段不变式 + 唯一索引 + 对账
```

理由：vivo 的 DB 分段在低量级是**更理性的选择**（无 Redis 一致性复杂度），字节量级下才必须 Redis——这不是谁对谁错，是量级决定方案。DB 分段的段间不均衡在低量级可容忍（对账再平衡），高量级无解。

## 10.7 优惠计算规范（收敛 01/05 章）

- 跨类别四级**递进**（单品券 > 折扣券 > 满减券 > 无门槛券），每层门槛按前序优惠后金额判定；
- 同类别内多张券**平行**（共同基数 = 进入该层时的金额）；
- **只做贪心自动勾选，不做穷举全局最优**（教学级幂集枚举仅 n≤10 可行；"递进+最优把 4 位开发干跑"是真实教训）；
- 金额全链路 long 分 + BigDecimal 中间值；分摊按比例 + **尾行倒挤**（is_tail 标记），sum(shares) == discount 恒等式进单测。

## 10.8 事实源与统计口径

`coupon_event` 是全域唯一事实源（含核销明细语义）。统计 9 指标、三层报表、库存对账、占用单交叉核对**全部从本表回放**；跨维度运营查询走 binlog→MQ→ES 宽表。报表口径警告：当天领券张数与用券张数天然错配（当天用的券来自之前 N 天）。

## 10.10 二轮审查发现的技术错误修正（重要）

**02 章 hash tag 表述自相矛盾，以本节为准**：02 章一处宣称"`cs:{tplId}:{slot}` 的 slot 可把热点模板拆到多分片"，另一处又要求"Lua 所有 KEYS 同槽（hash tag `{tplId}`）"。Redis Cluster 的事实是：**二者不可兼得**——四类 key（库存/幂等/用户计数）共用 `{tplId}` tag 才能单脚本全原子，但它们必然落同一 slot，"拆到多分片"不成立；若把 slot 编号放进 tag，key 落不同槽，Lua 直接 **CROSSSLOT 报错**，且用户计数按桶分裂后五重校验不再原子。正确做法即 10.2 节与 03 章的表述：**常规批次同 tag 全原子（吞吐上限=单分片 2 万）；热点批次分桶（tag=`{tplId:bN}`）+ 两段式**（先 check_user 只读脚本 → 再 deduct_bucket 扣桶 → 再 incr_user 写计数，中间不原子的窗口由 DB 唯一索引兜底）。这是"原子性 vs 横向扩展"的刚性权衡，没有两全解，任何声称两全的方案都隐藏了正确性漏洞。

**幂等载体统一裁决**（08 章推荐独立幂等表 vs 02/03/09 章 user_coupon 唯一索引）：
- 单业务阶段：user_coupon 表 `UNIQUE(user_id, request_id)` 即可（少一张表，vivo 论证：新建表多一层关联、对性能和现有逻辑影响大）；
- 中台多租户阶段：升级为**独立 issue_idempotent 表，`UNIQUE(biz_id, request_id)`，记录处理中/成功状态与 couponId 结果**（不依赖分片路由、可表达状态机、跨业务防撞号）——08 章的理由成立；
- 两阶段共存时的铁律：幂等键语义 = **业务身份 + 请求意图**；批量券包一次请求 N 张 = N 个子意图（`requestId:itemIndex`）。

## 10.11 二轮审查遗漏补遗（简则）

1. **"展"域（商品/门店反查）**：商详页/门店页"该商品可领哪些券"是与结算页并列的前三大读流量，方向与"查我的券"相反，需**倒排索引**：`String key = 券ID+门店ID+商品ID`，由分布式任务系统预热（京东到家：500 万任务 10 分钟内构建，MySQL 任务表持久化 + 按门店拆队列 + Worker 横向扩容 + 权重优先级）。商品预估到手价是 IO 放大器（50 商品 × 每券 5 类校验），必须缓存化 + 批量 mget。
2. **自动发券事件引擎**：第三种发放模式（除主动领/定向发外）——注册/实名/首购/复购/邀请/回归等事件触发返券，做成通用事件订阅配置。注意产品反模式：全量推券致用户囤券上百张、拉低用券率；建券客群与发券客群不一致会"领了用不了"，需领券侧可见性控制。
3. **M 端与客服工具**：中台一半开发量在 M 端——建券表单工程化（口径强校验/复制券/查询条件按频次）、运营与财务角色权限分离（运营=活动/配置/查询，财务=预算/核销/平账）、客服操作台（按券码/订单号/手机号查全生命周期流水——走 ES 异构宽表，跨分片禁止广播；补发/作废/冻结走统一 Facade + 双人复核 + 审计，严禁旁路直插 DB）。
4. **上线与迁移工程**：绿地按路线图分阶段；存量替换用 vivo 七步不停机迁移（停后台静态操作→单写→迁静态→双写→迁动态→切源可回滚→关双写）或数禾双读四步法（适用前提：存量百万级且多为终态无 UPDATE）；双写期 UPDATE 必须条件写（分表已有该行才更新，否则回写旧表——数禾实踩的丢更新坑）；Lua/Redis 结构变更同样走双写过渡 + 按 appId 灰度。
5. **时区与日切**：日期入 Key 的限领计数（`{yyyyMMdd}`）必须显式声明日切时区（多时区/海外业务会静默出错），凌晨边界以"先写先得 + Key 自然滚动"处理，无需跨天重置任务。
