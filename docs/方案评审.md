# 优惠券发放系统：一个替代方案的完整设计

**先给结论**：作者修复后的方案（A1-A8）是"在坏架构上打补丁打得很好"——它把每个已知病灶都处理了，但保留了三个架构级根源：①"量测→容差→自动 SET"的对账范式；②在途请求无显式标记，只能靠"估算"；③Redis 单 key 单点。我的方案用三个设计决策从根上消除这三个根源：**预留令牌（显式在途标记）+ 事件驱动自愈（拒绝即分类即修复）+ 恒等式校验（无时间窗的只读对账）**。下面从原理讲到落地，最后做逐场景对抗验证和方案对比。

* * *

## 一、三条设计原则（以及为什么）

### 原则 1：**"在途"必须是一等公民，显式可查，而非可估算**

作者方案最大的根源问题：Redis 扣减成功后到 DB 提交前，这个状态在系统里**没有任何显式记录**——只能靠 JVM 计数器去"数"（R1/R2/R3 一系列问题的共同起点）。没有标记，对账只能"测量"——而测量必有时间窗，时间窗必有偏置（R3 的提交泄漏），偏置逼出了"容忍带"这个补丁，容忍带又逼出了 R2（不分模板）和 R10（泄漏撑大）的连锁问题。

**我的解法**：每次 Lua 扣减时，**必须**先写入一个预留令牌 `rsv:{requestId}`（TTL 30 秒）。这个令牌就是"在途"的物理存在——系统随时可以准确数出"此刻有多少请求已扣 Redis、未落 DB"，不需要估算。

### 原则 2：**修复发生在事件路径上，对账只读**

作者方案让对账每小时带着写权限跑一次（这是 N1、R1 假修复的元凶——审计员自己动手就会跟正常流量打架）。即使 A1 加了"售罄钉零"，对账的自动 SET 权限还在，只是限制了场景。

**我的解法**：**所有修复都由事件触发**——DB 拒绝的那一瞬间，请求自己分类、自己修复（售罄钉零、下线钉零、异常恢复计数）。后台对账**永远只读**：发现不一致就告警、就落审计表、就冻结自动重建，**从不 SET**。危险动作从架构上不存在，而不是被条件限制。

### 原则 3：**用恒等式校验，不用时间窗测量**

作者方案的对账是"在 T1 读 DB、T2 读 Redis、T3 读计数器，差值和容忍带比"——三个时刻之间的流量变化全靠估算。作者 A4 的"动态容忍带"依然是在优化这个估算公式。

**我的解法**：让系统里存在一个**在任意时刻都成立的恒等式**，校验就退化为一次 O(1) 读：

复制

```
Redis 侧 issued（per bucket） = DB 侧 issued（per bucket） + 预留令牌数（per bucket）
```

这个等式**与时间窗无关**——因为每一笔成功扣减都会同时写入 Redis issued（+1）和预留令牌（+1）；每一笔成功发放会同时写入 DB（+1）和删除令牌（-1）。任何时刻读这个等式，都应该精确为 0。**不等 → 必然是 bug 或人工干预 → 告警**，不存在"高峰期偏置"这种模糊地带。

## 二、方案架构

### 2.1 数据模型

**Redis 侧（Cluster，hash tag 按 bucket 分片）：**

复制

```
# 库存分桶：把单模板库存拆成 N 桶，N = max(4, 峰值QPS/5000)
stock:{tplId}:b{0..N-1}      # 各桶剩余库存
issued:{tplId}:b{0..N-1}     # 各桶 Redis 侧已发放计数（恒等式的一侧）

# 限领计数（key 设计原则：TTL 绑定业务生命周期，不是拍脑袋 7 天）
ul:{tplId}:{uid}             # TTL = 模板有效期 + 24h 缓冲
uld:{tplId}:{date}:{uid}     # TTL = 25h
dly:{tplId}:{date}           # TTL = 25h

# 预留令牌（在途标记）
rsv:{requestId} = bucket_id  # TTL 30s
idem:{requestId} = OK/FAILED # TTL 1h，幂等结果缓存

# 售罄标志（设计上的一等公民）
soldout:{tplId} = 1          # DB 判定售罄时设置，入口短路用
```

**MySQL 侧（分库分表）：**

复制

```
user_coupon 表（按 uid % 16 分库，uid % 64 分表）
├── 唯一索引 (uid, tpl_id, seq)        # 幂等兜底
├── 唯一索引                  # 消息/MQ 重试幂等
└── 字段 bucket_id                     # 关键：让对账能按桶精确归因

template_agg 表（按 tpl_id % 8 分库）
├── issued_count                       # 汇总缓存（非真相源）
└── total

# 第二不变式：issued_count 与 COUNT(user_coupon) 互证
```

**为什么要 bucket 分桶**：单 key 单分片的理论上限约 10 万 ops/s，5000 QPS 单 key 勉强够，但：①大促万级 QPS 必然打爆单分片；②Redis Cluster 扩容时单 key 无法水平切分；③一个 key 丢失 = 全模板库存失效（作者 N2 风暴的根源就是"整个 key 没了"）。分桶后这三个问题都消解。

**为什么要 issued 侧计数器**：这是恒等式的一侧。没有它，对账只能拿 `stock` 和 `total` 做减法，无法区分"在途"和"漂移"。

### 2.2 扣减主流程（带完整 Lua）

lua

复制

```
-- KEYS: stock_key, issued_key, ul_key, uld_key, dly_key, rsv_key, idem_key, soldout_key
-- ARGV: requestId, perUserLimit, perUserDailyLimit, perDayLimit, tplExpireTs

-- ① 入口短路：售罄直接拒绝，不碰任何桶
if redis.call('EXISTS', KEYS[8]) == 1 then return {-1, 'SOLD_OUT'} end

-- ② 幂等检查：重复请求直接返回缓存结果
local cached = redis.call('GET', KEYS[7])
if cached then return {0, cached} end

-- ③ 限领检查
if tonumber(redis.call('GET', KEYS[3]) or 0) >= tonumber(ARGV[2]) then return {-2, 'USER_LIMIT'} end
if tonumber(redis.call('GET', KEYS[4]) or 0) >= tonumber(ARGV[3]) then return {-3, 'USER_DAILY_LIMIT'} end
if tonumber(redis.call('GET', KEYS[5]) or 0) >= tonumber(ARGV[4]) then return {-4, 'DAY_LIMIT'} end

-- ④ 预留令牌（原子抢占，防并发重复）
if redis.call('SET', KEYS[6], ARGV[1], 'EX', 30, 'NX') == false then 
    return {-5, 'IN_FLIGHT'} 
end

-- ⑤ 库存校验+扣减
local stock = tonumber(redis.call('GET', KEYS[1]))
if not stock or stock <= 0 then
    redis.call('DEL', KEYS[6])  -- 释放令牌
    return {-6, 'BUCKET_EMPTY'}  -- 调用方切换到下一个桶
end

-- ⑥ 应用所有变更
redis.call('DECR', KEYS[1])
redis.call('INCR', KEYS[2])
redis.call('INCR', KEYS[3]); redis.call('EXPIRE', KEYS[3], tonumber(ARGV[5]))
redis.call('INCR', KEYS[4]); redis.call('EXPIRE', KEYS[4], 90000)
redis.call('INCR', KEYS[5]); redis.call('EXPIRE', KEYS[5], 90000)

return {0, 'OK'}
```

**关键设计点逐个解释**：

-   **令牌在扣减之前 SETNX**：这是关键时序。若令牌已存在，说明同一 request 在途，直接返回 IN\_FLIGHT 而非二次扣减。作者方案用 JVM AtomicLong 计数，它只能"数"，不能"识别是谁"。
-   **令牌 TTL 30 秒**：覆盖 DB 事务最坏时长。进程崩溃（kill -9）后令牌自动过期，无需清理任务——**在途状态的清理是自洽的**。
-   **所有变更原子**：作者 R2（计数器不分模板）、R3（窗口内泄漏）在 Lua 单次执行中根本不存在——Lua 内没有"时间窗"。

### 2.3 DB 事务与确认/取消

java

复制

```
@Transactional
public void insertCoupon(Request r) {
    // 唯一索引 幂等，DuplicateKeyException 捕获后走查询返回已有结果
    userCouponMapper.insert(r.uid, r.tplId, r.seq, r.requestId, r.bucketId);
    int affected = templateAggMapper.deduct(r.tplId);
    if (affected == 0) throw new SoldOutException(); // 售罄
}

// DB 成功后（异步或同步均可）
public void confirm(Request r) {
    redis.eval("SET idem:{r}='OK' EX 3600; DEL rsv:{r}");
}

// DB 失败后（拒绝分类 → 一等公民修复）
public void cancel(Request r, RejectReason reason) {
    switch (reason) {
        case SOLD_OUT:
            // 售罄：钉零（幂等，任意次执行结果都是 0）+ 标志位 + 回滚用户计数
            redis.eval("""
                SET stock:{tpl}:b{bucket} 0
                SET soldout:{tpl} 1
                DECR issued:{tpl}:b{bucket}
                DECR ul:{tpl}:{uid}; DECR uld:...; DECR dly:...
                DEL rsv:{r}; SET idem:{r}='SOLD_OUT' EX 3600
            """);
            break;
        case TEMPLATE_OFFLINE:
            // 下线：同样钉零，但不设置 soldout（模板可能重新上线）
            redis.eval("SET stock:{tpl}:b{bucket} 0; DECR issued:...; DECR ul/uld/dly; DEL rsv");
            break;
        default:
            // 其他异常（DB 超时等）：恢复计数，但不钉零（库存未真正耗尽）
            redis.eval("INCR stock:...; DECR issued:...; DECR ul/uld/dly; DEL rsv");
    }
}
```

**为什么这样设计**：作者 A1 修法是"DB 拒绝后先取新快照分类再决定补偿"——我的方案把这个分类**前置到 Lua 层**（入口判 soldout），加上 DB 拒绝时的二次分类，双保险。钉零和 INCRBY 恢复是不同分支的**一等路径**而非"修复逻辑"。

### 2.4 对账：恒等式校验（只读）

这是方案最核心的部分。

**每分钟增量校验（近实时，O(buckets)）：**

复制

```
# 对每个 bucket 执行（一次 Redis pipeline 读 2 个 key + SCARD pending）
redis_issued = GET issued:{tpl}:b{k}
pending      = SCARD pending_set:{tpl}:b{k}  # 30s 内的令牌集合（用 SADD/SREM 维护）
db_issued    = GET db_issued_mirror:{tpl}:b{k}  # 由 binlog 驱动的物化计数器

delta = redis_issued - pending - db_issued
# 恒等式：delta 应精确为 0
# 不为 0 = 有变更未被任何机制追踪 → 真 bug → 告警 + 落 stock_drift_log 表 + 冻结自动重建（没有自动重建可冻结，冻结的是 bucket 自动补位）
```

**binlog 驱动的物化镜像**：Canal 监听 `user_coupon` 表 INSERT 和 `template_agg` 表 UPDATE，按 汇总后写入 Redis `db_issued_mirror:{tpl}:b{k}`。这让 DB 侧的"真相"也变成一个可 O(1) 读的计数器，对账从"每小时扫全量"变成"每分钟做 2 次 Redis GET"。

**每日全量审计（T+1）：**

复制

```
# 冷启动跑：COUNT(user_coupon WHERE tpl_id=X AND bucket_id=k) vs db_issued_mirror
# 双重验证 issued_count 和明细行数（第二不变式，作者 M3 风险的根治）
# 任何差异 → 只写 stock_drift_log + 告警，不修复
```

**为什么这样**：作者的对账是"测量"，任何测量都有时间窗和偏置；我的对账是"校验恒等式"，等式在任意瞬间成立或失败，没有中间态。作者 A4 的"动态容忍带"在我的方案里**不存在**——因为恒等式的期望值精确为 0，不需要容忍。

### 2.6 多实例与集群安全性

作者方案的多实例问题是 R1（JVM 本地计数器失配）和 C1 门禁（M2 才做 Redis 化）。我的方案**从设计上就没有 JVM 本地状态**：

-   所有计数都在 Redis（Cluster），天然多实例共享；
-   Lua 原子性替代分布式锁；
-   无 `@Scheduled` 后台任务 → 不存在调度线程阻塞（作者 R7）问题；
-   多实例水平扩容**不需要任何前置门禁**，加机器就能加。

这是架构红利而非修复项——作者 C1 需要在 M2 才能做到的事情，在方案设计阶段就完成了。

| **对账写权限** | 有（每小时 SET），靠 A1/A2 限制场景 | 无（只读+告警） | 作者：审计员会做手术；我：审计员只报告。N1/R1 类事故架构上不存在 |
| **修复触发** | 定时 + 事件混合 | 纯事件驱动（DB 拒绝时分类修复） | 作者：定时任务与流量打架；我：每个请求自己负责自己 |
| **DB 一致性验证** | issued\\_count ↔ COUNT 互证（A8，纳入 M3） | 第二不变式作为一等设计 + binlog 物化镜像 | 作者：补救；我：原生 |
| **Redis key 热点** | 单 key（模板粒度） | bucket 分桶 | 作者：5000 QPS 够用但不可扩展；我：水平扩展原生支持 |
| **多实例就绪度** | C1 门禁在 M2 | 设计即多实例安全 | 作者：依赖流程纪律和断言；我：架构上无此问题 |
| **售罄处理** | A1 修复（分类先行 + 钉零） | 入口 soldout 标志短路 + 拒绝路径一等公民钉零 | 作者：售罄时 Redis 仍承担流量然后修复；我：售罄时 Redis 层直接毫秒级拒绝 |
| **计数器 TTL** | A6 修复（绑定模板有效期） | 设计时绑定 | 同上  |
| **后台任务** | 对账 cron（+R7 修复调度线程池） | binlog 消费 + 分钟级增量校验（无 @Scheduled 轮询） | 作者：调度器会成为新瓶颈；我：无调度器依赖 |

**对作者修复后方案的批判（分三点）**：

**批判 1：A4 的动态容忍带是把"估算"优化得更好，而不是消灭估算。** 作者公式 `max(5, 速率×跨度估计)` 里的"速率"和"跨度"依然是估算值，需要"高峰压测专项"验证——这说明公式的正确性无法离线证明，只能靠压测兜底。我的恒等式期望值恒为 0，**不需要验证公式，只需要验证系统行为符合设计**。前者是经验工程，后者是正确性工程。

**批判 2：A1-A8 是"点修"，架构范式的三个隐患还在。** ①每小时自动 SET 权限还在（只是场景被限制）——未来某个新场景（比如"模板配置错误"）仍可能触发 N1 同类问题；②JVM 计数器仍在（C1 Redis 化推迟到 M2）——R1 的失配公式在 M1-M2 之间仍然成立；③对账仍是定时任务——R7 的调度线程池问题只是从"卡死"变成"变慢"，形态改变但存在。

**批判 3：单 key 设计在 Redis Cluster 下的水平扩展是死锁。** 5000 QPS 时单 key 单分片够用，但大促万级 QPS 或未来多活动叠加时，单分片会成为物理瓶颈——Redis Cluster 无法拆分单个 key 的流量。作者方案要扩容就必须在 M 系列之外新做 bucket 分桶（一次架构迁移），我的方案从第一天就是水平扩展的。**这是"现在够用"和"永远够用"的区别**。

## 四、对抗验证：用作者的故障场景逐一测试

### 场景 1：N1 售罄 + Redis 偏高 δ

**作者修复后（A1）**：售罄类拒绝时钉零 → δ 被每个迟到补偿"往 0 拉"→ 环断。**修复有效，但依赖**：拒绝分类必须正确（如果 DB 返回"售罄"的原因被误判为其他），且需要等到第一次 DB 拒绝才能触发修复。

**我的方案**：入口 soldout 标志在**第一次 DB 售罄拒绝时**就被设置。之后所有请求在 Lua 第 ① 步就被拦截，**根本不会过闸、不会走 DB、不会产生补偿**。DB 在售罄场景下的 QPS = 1（那第一个触发 soldout 的请求）。**δ 无论多大都会被第一个请求"钉零"吸收**，因为 soldout 标志独立于 stock 值。

### 场景 2：N2 Redis 清库瞬间

**作者修复后（A2）**：条件 SET，首个生效其余 no-op。**修复有效**。

**我的方案**：同样用条件 SET（继承这个优秀修复），但多了版本号——对账能看到"这个桶被重建过几次"。此外 bucket 化后，一次清库只影响 1/N 的容量（比如 N=8 时只损失 1/8 闸门），其他 7 个桶正常工作，**风暴半径减半以上**。

### 场景 3：R3 高峰期测量偏差

**作者修复后（A4）**：紧凑次序 + 动态容忍带 + 前后双读计数器。**部分缓解**，但公式仍需压测验证，且存在"高峰期真偏高被掩盖进容忍带"（M1 风险）。

**我的方案**：恒等式无时间窗，`redis_issued - pending - db_issued` 在任意时刻都应精确为 0。**偏差项不存在，容忍带不存在，M1 类风险不存在**。高峰期唯一的动态量是 `pending`（令牌数），它由 Redis 自己精确维护，不需要估算。

### 场景 4：R1 多实例部署

**作者修复后**：C1 门禁在 M2，A3 把计数器改 Map<tplId, AtomicLong>——但 M2 之前仍是 JVM 本地，多实例仍然失配。启动断言（B3）只是"拒绝启用对账"，不是"支持多实例"。

**我的方案**：**没有 JVM 本地状态，设计即多实例就绪**。加机器就直接生效，不需要任何 M 系列门禁。预留令牌、issued 计数、售罄标志全在 Redis Cluster，所有实例看到的是同一个真相。

### 场景 5：R5 主从延迟 + 缓存（M4/M3 的未来场景）

**作者修复后**：B1 架构约束"对账读禁止从库、禁止缓存"——**用架构文档防未来踩雷**，合理但仍是"约束"。

**我的方案**：对账只读 Redis 侧计数器 + 消费 binlog，**根本不读业务库**——不存在从库/缓存路径。Binlog 是主库的物理日志，天然强一致。

### 场景 6：R9 kill -9 导致 ul/uld/dly 偏高

**作者修复后（A6）**：撞索引自愈 + TTL 绑定模板有效期 + 抽样对账告警。

**我的方案**：TTL 设计就绑定生命周期（不是修复项）；抽样对账升级为**每分钟增量恒等式校验**——`ul 计数 vs COUNT(user_coupon WHERE uid=X AND tpl_id=Y)` 的偏差会在 1 分钟内被发现（作者方案要等抽样轮到 + 整点对账）。此外，进程崩溃后 `rsv:{requestId}` 令牌 30s 过期，期间对账会把这 30 秒的不一致归因到 pending 而非误报——**作者 R10 的"泄漏撑大容忍带"问题在我的方案里表现为"pending 临时虚高"，会在 30s 内自然消解**。

## 五、权衡与残余风险

诚实列出我的方案不如作者方案的地方：

1.  **预留令牌增加了 Redis 写放大**：每次扣减多 1 次 SET NX + 1 次 DEL + 1 次 SADD/SREM（约 4 次额外 Redis 操作）。在 5000 QPS 下增加约 20000 ops/s，Redis Cluster 轻松承受，但确实是成本。**如果实际峰值只有几百 QPS，这套预留机制可以简化为"不做预留，直接靠 DB 唯一索引兜底"**——这是作者在元批评里值得被夸的地方：**量级决定复杂度**。
2.  **binlog 消费链路引入新组件**：需要 Canal/Flink CDC + MQ + 消费者，运维成本高于作者的"每小时 SELECT"。换来的是对账从"小时级"到"分钟级"的时效性和零时间窗的正确性。
3.  **拒绝分类依赖 DB 错误码语义稳定**：如果 DB 抛异常的类型不明确（比如连接超时 vs 售罄），我的方案会走 default 分支（恢复计数不钉零），**比作者方案保守**——宁可 Redis 偏低让下个请求过闸被 DB 拒绝，也不冒险钉错。这是牺牲少量"售罄短路效率"换取"绝不误钉零"。
4.  **恒等式校验对"双重补偿"这类 bug 的探测**：作者 R9 提到的"双重补偿"（已被幂等门控关闭）在我的方案里表现为 `redis_issued` 减少 2、`pending` 减少 1、`db_issued` 不变 → delta = -1 → 告警。**能抓到**，但需要人工修复，作者方案的对账自动 SET 也许能修——但自动 SET 也会在判断错误时制造 N1。**我选择慢但稳，作者选择快但有险**。

## 六、一句话总结

作者修复后的方案是把一台"每小时自动做手术的机器"打磨得尽量安全（A1-A8 每一项都很精湛）；我的方案是让"手术"从架构上不存在——每个请求自己负责自己的正确性（预留令牌 + 事件分类 + 一等公民钉零），对账退回到它本来的角色：**诚实地观察、大声地报警、绝不越权动手**。如果你要选：**当峰值 QPS < 1000 且团队规模小时，作者方案够用且实现成本低；当峰值 QPS > 3000 或未来必然水平扩展时，预留令牌 + 恒等式校验是正确的架构投资**。
