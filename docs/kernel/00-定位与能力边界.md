> **状态**：v0.3（2026-10-18，环 1 结算主体已实施）。
> **读者**：产品/技术负责人、内核开发、准备接入的产品团队、面试/作品集读者。

## 0. 一句话定位

**券能力内核（Coupon Kernel）**：为多个产品/租户提供券的通用能力——模板、发放、试算、锁券、核销、释放、退款、分摊、出资归属、结算数据——**产品自己决定规则政策、营销玩法和界面**。

对外可以叫“优惠券能力平台”；在文档和代码里统一用“券能力内核”，避免和“业务平台/营销中台”混在一起。

---

## 1. 为什么需要这份文档

没有定位文档，系统会自然漂移：

- 今天加一个“双 11 活动页”，明天加一个“商家招商”，后天加一个“会员积分兑换”——最后变成一个什么都做、谁都接不动的业务系统；
- 产品团队不知道“哪些该找内核、哪些该自己做”，每个产品都来提定制；
- API 没有边界，字段越加越多，旧接入方不敢升级；
- 面试/对外讲不清“你们到底做的是中台还是某个产品的营销后台”。

这份文档的作用是：**先定边界，再谈实现**。

## 2. 系统是什么

### 2.1 两类服务对象

| 类型 | 例子 | 与内核的关系 |
|---|---|---|
| 企业内部产品 | 视频会员、电商、到店、金融 App、内部福利平台 | **需要隔离的产品走开放面 `/open/v1`**（分配 appId）；`/api` 只作为平台运营面 |
| 外部企业产品 | 其他企业的商城、SaaS、银行/车企权益平台 | 通过开放面 `/open/v1`（appId + 签名）接入；租户 = 企业 |

**内部面的边界**：当前 `/api` 没有租户身份，`AppOwnership` 把内部面当作“平台自己”放行，多个内部产品走 `/api` 时**没有 appId 隔离**。因此：

- 需要数据隔离、配额、审计、结算边界的内部产品，必须走开放面 `/open/v1`；
- `/api` 用于平台自己的运营/运维动作，以及**可信平台调用方的业务写接口**（lock/confirm/release/refund 白名单）；它是单租户、可信环境，不构成多租户隔离面；
- 如果未来要让内部产品继续用 `/api`，需要先补“内部应用身份 + 归属校验”，否则不要把 `/api` 当作多租户接入面。

两类对象的共同点：**都不想为优惠券重新造一套系统**，但各自的规则、营销、界面不同。

### 2.2 内核与业务平台的分工

| 能力 | 内核（我们做） | 产品（调用方做） |
|---|---|---|
| 券模板、用户券、占用单 | 提供模型、状态机、生命周期 | 决定建什么券、什么时候发 |
| 试算、锁券、核销、释放、退款 | 提供原语、金额计算、幂等、分摊 | 决定在哪个环节调用、失败怎么处理 |
| 金额与分摊 | 保证守恒、逐行分摊、出资归属 | 决定券类型、门槛、力度、叠加规则 |
| 适用范围 | 提供全场/品类/SKU/结算主体等维度 | 配具体范围值 |
| 退款政策 | 提供配置项并强制执行 | 决定最多退几次、整单退是否退券 |
| 结算数据 | 按租户/结算主体/模板出日汇总与明细 | 决定怎么打款、开票、和财务对账 |
| 风控/反作弊 | 提供频控、限额、信号、审计、结算 hold | 决定业务规则、是否人工审核、是否终止合作 |
| 营销 | 不做 | 活动编排、人群、页面、投放、触达 |
| 商家运营 | 不做 | 入驻、招商、店铺、结算账户 |

一句话：**内核管“怎么正确地算、锁、核、退、记账、留证据”，产品管“为什么发、发给谁、怎么营销”。**

### 2.3 同一套内核怎么服务不同产品

| 产品形态 | 范围维度 | 出资/结算 | 内核怎么支持 |
|---|---|---|---|
| 视频/会员 | 套餐、会员等级 | 平台出资，无商家 | 租户级券，结算主体留空，落 `__default__` 桶 |
| 电商/外卖 | 品类、SKU、商家/门店 | 平台/商家/共担，按商家结算 | 结算主体可选；商家出资券必须绑定主体；按主体出日汇总 |
| 银行/信用卡 | 商户类别、地区、卡等级 | 银行/商户出资，按商户结算 | 范围 + 结算主体；扩展点接会员/地区资格 |
| SaaS | 套餐、版本、坐席数 | 租户自己出资 | 租户级券；无实物商品；结算主体留空 |
| 车企/经销商 | 门店、车型、地区 | 厂商/经销商出资 | 结算主体 = 门店/经销商；扩展点接车型/地区 |

共同点：**模板、实例、锁/核销/退款、分摊、出资、审计**是同一套；差异在范围维度、出资方、政策和扩展点。

### 2.4 三个具体例子：同一套内核怎么落

**例子一：视频会员产品**

- 产品：视频 App 想发“年卡立减 30 元”；
- 券：平台出资、全场券、范围是“年卡套餐”、无结算主体；
- 内核做：建模板、发券、试算、锁/核销、退款；分账记“平台承担 30”，落 `__default__` 桶；
- 产品做：决定发给哪些用户、活动页、投放、会员资格校验（可走扩展点）。

**例子二：电商平台**

- 产品：平台下有商家 A、B；
- 券：商家 A 出资的“满 100 减 20”，范围是“商家 A + 食品品类”；
- 内核做：只在 A 的食品行上判门槛、分摊、记 A 承担 20；退款按 A 的原分账行冲回；日汇总按 A 出；
- 产品做：商家入驻、活动报名、店铺页；决定 A 是否参加活动。

**例子三：银行信用卡**

- 产品：银行发“周五餐饮满 50 减 10”；
- 券：银行出资、范围是“餐饮类商户”、结算主体是具体商户；
- 内核做：按餐饮行判门槛/分摊，记银行承担 10；按商户出结算数据；
- 产品做：卡等级/地区资格、活动页、和商户的商务合同；可走资格扩展点。

三个例子的共同点：模板、实例、锁/核销/退款、分摊、出资、审计都是同一套；差异在范围、出资方、政策和扩展点。

### 2.5 一个需求该不该进内核

用五个问题判断：

1. 它是**通用机制**，还是某个产品的**政策/玩法**？
2. 现有原语 + 配置能不能表达？能，就不加新代码；
3. 它是否需要订单、支付、物流等**外部证据**？需要，就留在产品/外部系统；
4. 其他产品是否也会用？只有一个产品用，优先放产品层或扩展点；
5. 加进内核后，会不会让 API/状态机/数据模型变得不可维护？会，就拒绝或降级为扩展。

结论：**通用机制进内核，产品政策进配置，长尾玩法进扩展或产品层。**

### 2.6 系统不是什么

明确不做，避免边界漂移：

- **不是营销活动平台**：不做活动编排、人群圈选、页面搭建、投放、触达；
- **不是商家营销 SaaS**：不做商家入驻、招商报名、店铺装修、广告；
- **不是支付/结算执行系统**：不做收款、打款、发票、税务；只提供结算所需的数据；
- **不是万能规则引擎**：不追求表达所有产品的所有玩法；标准原语 + 配置 + 扩展点，长尾留在产品层；
- **不是风控大脑/反作弊判决系统**：提供券侧信号、限额、审计、结算 hold；订单真实性、支付流水、物流签收等证据来自外部系统；
- **不是合规认证机构**：不替代 ISO/等保/隐私合规；内核提供审计、权限、数据保留的基础能力。

## 3. 核心概念与边界

### 3.1 租户（Tenant）

- **定义**：一个接入方。租户键 = `appId`；一个企业可以有多个 appId；一个业务线只有被分配独立 appId 时才算租户。
- **作用**：数据隔离、配额、配置、审计、结算的边界。
- **内部面说明**：`/api` 当前不携带 appId，不构成多租户隔离面；需要隔离的内部产品走 `/open/v1`。
- **不是什么**：租户不一定是“商家”。它可能是视频产品、银行 App、SaaS 企业，也可能是一个含多个商家的平台。

### 3.2 结算主体（Settlement Party）与出资方

**这是两个正交维度，不能混为一谈：**

- **出资方**回答“这笔优惠的成本由谁承担”：平台、非平台（商家/租户）、或按比例共担；
- **结算主体**回答“平台和谁结算”：商家、门店、经销商、业务单元，或租户自己。

例子：平台出 10 元补贴、和商家 M 结算。

- 成本承担：平台 10、商家 M 0；
- 结算应付：平台应付 M 10；
- 如果只看“商家承担 0”，会误以为平台不用付钱；实际上平台要补 M 10。

因此：

- **定义**：结算主体 = 优惠最终算到谁头上、平台和谁结算；可以是商家、门店、经销商、业务单元，也可以就是租户自己。
- **为什么需要**：平台券跨多个主体时，平台补贴要按主体拆分；商家出资/共担券必须知道扣谁的钱。
- **可选**：没有细分主体的产品不传，落到 `__default__` 桶；不强迫所有产品都有“商家”。
- **命名**：文档/契约统一用 `settlePartyId`（推荐名，最终待拍板）；`merchantId` 只是电商场景的领域别名，不作为契约字段。
- **字段命名的坑**：现有 `merchant_burden` 字段表示“非平台出资方承担的成本”，**不是**“平台应付商家的钱”；平台应付要按 `platform_burden` 和结算主体另行汇总，且**是条件公式**——结算模式（商家收款平台补差 vs 平台代收再结算）未拍板前，不对外承诺具体应付口径。

### 3.3 模板（Template）

- **定义**：一类券的规则：类型、面额/折扣、门槛、范围、叠加层级、互斥组、出资方、有效期、限领、政策。
- **边界**：模板是“规则”，不是“发给某个人的券”；模板可以改的字段要受控，核心规则（面额、门槛、范围、出资、结算主体）发布后不可变或必须版本化。

### 3.4 用户券实例（User Coupon）

- **定义**：某个用户持有的某一张券；领取时固化面额、门槛、折扣上限、有效期等快照。
- **边界**：实例的可用性由状态机、时间、范围、门槛决定；模板后续变更是否影响实例，按“快照字段 vs 动态字段”规则处理。

### 3.5 占用单（Usage）

- **定义**：一次“券 × 订单”的合同：哪个用户、哪张券、哪个订单、锁了多久、核销/释放/退款到什么状态。
- **作用**：幂等锚点、回退裁判、金额载体。
- **边界**：一张券可以一生签多份占用单（锁→释放→再锁）；一份占用单对应一个订单里的一张券。

### 3.6 分账（Share）

- **定义**：核销时按商品行记录的两组信息：
  1. **成本承担**：平台承担多少、非平台（商家/租户）承担多少；
  2. **结算归属**：这一行属于哪个结算主体。
- **作用**：退款按行冲回、结算按主体汇总、审计追溯。
- **平台应付怎么来**：默认“商家自己收款、平台补差额”模式下，平台应付某结算主体 ≈ 该主体行上的平台承担净额；商家承担是商家自己少收的钱，不是平台现金支出。
- **边界**：分账是“这笔优惠怎么分、和谁结算”，不是“平台已经把钱打给谁”。

### 3.7 退款（Refund）

- **定义**：已核销后的冲回：按行 + 数量、退款单号幂等、退款明细、券处置政策。
- **边界**：内核返回“冲回了多少优惠”，不负责“用户实际收到多少钱”；后者由订单/支付系统按行实付计算。

### 3.8 政策（Policy）

- **定义**：产品可配置的业务规则：最多退款次数、一券最多退券次数、整单退是否退券、叠加/互斥、限领、范围等。
- **边界**：内核提供**机制**（怎么执行、怎么校验、怎么审计），产品提供**政策值**；内核不替产品决定“满多少减多少”。

### 3.9 扩展点（Extension）

- **定义**：标准原语覆盖不了的产品特殊逻辑的受控入口：资格校验、范围解析、特殊定价、出资解析、结算适配、通知。
- **边界**：扩展点不是“让产品改内核代码”；内部产品可用 SPI/插件，外部产品用 Webhook/API；扩展必须有版本、超时、降级和审计。

## 5. 内核保证什么、不保证什么

### 5.1 目标态下内核保证

- **金额正确（仅带 items 的行级链路）**：行分摊合计 = 券优惠；平台承担 + 非平台承担 = 行优惠；退款累计不超原分账；老式核销/退款不写行级明细，不能按行/按主体结算；
- **状态正确**：锁/核销/释放/退款只走合法状态迁移，重复请求幂等（按原语分别定义，见 01）；
- **价格一致**：**使用有效 `pricingId` 的调用方**，试算价 = 核销价（目标态）；不带快照的旧调用方不保证；
- **归属正确**：优惠记到正确的租户/结算主体；退款只冲回原主体（目标态）；
- **隔离**：开放面租户（appId）之间资源归属隔离；**严格隔离未成立**——`uk_idem` 不含 appId（L73），且 `/api` 是平台运营面，不构成多租户隔离；
- **可审计**：核销/退款已有前后快照 + 哈希链；动钱/改状态/管理动作全覆盖、可查询是目标态；
- **可恢复**：依赖故障时有超时/熔断/降级；有备份恢复与故障演练（目标态）；
- **可接入**：API 版本化、字段兼容、错误码稳定、契约测试（目标态）。

### 5.2 内核不保证

- **产品政策正确**：产品把门槛配成“满 0 减 100”，内核会按配置执行；政策合理性由产品/运营负责；
- **终端用户身份**：内核只认证应用（appId），不认证终端用户；`userId` 由调用方提供并信任，调用方必须保证其真实性和归属；
- **订单真实性**：内核无法判断订单是不是假的、用户是不是和商家串通；这需要订单、支付、物流等外部证据；
- **营销效果**：发多少券、转化多少、ROI 多少，不是内核的职责；
- **支付/结算执行**：内核不碰钱、不转账、不开票；
- **外部系统正确性**：订单系统传错金额、传错商家，内核只能在契约内校验，不能替它修数据；
- **完整合规**：内核提供审计/权限/保留的基础能力，但不替代企业的合规认证与法律审查；
- **老式核销/退款的行级完整性**：不带 `items` 的核销不写行级分账，老式退款不写退款明细，不能进入按行/按主体的结算数据；
- **事件顺序与恰好一次**：目标至少一次 + 消费方幂等；当前对外 Webhook 未实现；
- **`/api` 的多租户隔离与 token 幂等**：`/api` 只用于平台运营；需要隔离的产品走 `/open/v1`。

### 5.3 为什么这样切

- **机制与政策分离**：内核保证“怎么正确地执行”，产品保证“执行什么”；
- **诚实边界**：不把“防自产自销”“保证订单真实”这类需要外部证据的事说成内核能独立完成；
- **可演进**：标准原语覆盖大多数产品；长尾用扩展点；不为某个产品把内核改成万能系统。

## 6. 成功标准

| 维度 | 指标 | 目标 |
|---|---|---|
| 接入成本 | 新产品质量从试算到退款接入所需时间 | 有 SDK/文档/沙箱后，核心链路可在数天内完成（具体目标待定） |
| 金额正确 | 黄金用例、并发用例、退款用例的金额/守恒失败数 | 0 |
| 兼容性 | 破坏性 API 变更数 | 0；必须变更时走新版本 + 废弃期 |
| 隔离 | 跨租户越权成功数 | 0 |
| 可审计 | 动钱/状态/管理动作审计覆盖率 | 100% |
| 可运维 | 核心链路是否有指标/告警/Runbook | 每条关键链路都有 |
| 韧性 | 依赖故障演练中核心链路是否雪崩 | 不雪崩，可降级/可恢复 |
| 容量 | 是否有可重复的容量基线 | 有四类核心场景的压测报告 |
| 产品体验 | 产品团队是否需要改内核代码才能接入 | 标准需求 0 改代码；长尾走扩展点 |

> 具体数值（SLO、P95、QPS）在容量压测和试点后填，不在定位文档里拍脑袋。

## 10. 开放问题

1. **结算模式**：商家自己收款、平台补差额，还是平台代收再结算？这决定结算数据的字段和口径。
2. **结算主体命名**：推荐对外用 `settlePartyId`，`merchantId` 只作电商场景别名；最终命名在环 1 开工前拍板。
3. **产品接入方式**：内部产品用 SDK/SPI，外部产品用 REST/Webhook；是否需要沙箱租户？
4. **默认结算主体**：旧订单/单商户产品统一落 `__default__`，是否需要提供“默认主体映射”配置？
5. **管理面角色**：查看/操作/审批三角色是否第一版就做？
6. **SLO/容量目标**：等压测基线出来再填。
