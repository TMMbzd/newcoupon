# 06 · 能力对照与大厂实践

> **状态**：v0.2（2026-10-18，已按对抗审查修订）。
> **读者**：项目 owner、内核开发、准备接入的产品团队、面试/作品集读者。
> **前置阅读**：[00 定位与能力边界](00-定位与能力边界.md)、[01 内核能力契约](01-内核能力契约.md)、[05 路线图与验收](05-路线图与验收.md)、[07 信任与韧性能力地图](07-信任与韧性能力地图.md)。
> **这份文档回答三个问题**：
> 1. 成熟企业和公开产品在券/优惠能力上**公开可见**的做法是什么；
> 2. 我们当前做到哪一步，哪些是同层可比的，哪些还差关键件；
> 3. 差距挂到哪一环、本周期做不做、验收是什么。
> **不是这份文档的内容**：某家公司的内部架构还原、实现细节、流量/组织/合规对标。大厂内部系统大多不公开，本文不编造。

## 1. 先说清楚：大厂的内部系统，公开资料能看到什么

### 1.1 四级证据

| 级别 | 是什么 | 本文怎么用 | 例子 |
|---|---|---|---|
| A 官方文档 | 厂商公开的 API/产品文档 | 可以直接引用，作为“该产品确实支持”的证据 | Voucherify、Stripe、Shopify、SAP 的官方文档 |
| B 公开工程分享 | 技术博客、大会演讲、专利、公开论文 | 可以引用，但要注明“公开分享口径”，不等于当前实现 | 阿里/京东技术博客、美团风控博客、专利/论文 |
| C 产品可观察行为 | 帮助中心、商家规则、接口返回、实测 | 只能说明“产品规则长这样”，不能说明内部架构 | 淘宝/京东/美团的券使用与退款规则 |
| D 行业通行模式 | 多个公开方案共同出现的模式 | 只能标“行业常见/推断”，不能写成某公司事实 | 下单快照、按行分摊、幂等键 |

### 1.2 四条纪律

1. **不把产品规则当内部架构**：看到“部分退款不退券”，只能说明产品规则，不能推断它内部怎么记账；
2. **不把行业模式当某公司事实**：没有 A/B 级来源时，写“行业常见做法”，不写“美团就是这么做的”；
3. **不把目标态当现状**：我们的缺口明确写“未做/目标”，不用“规划中”模糊；
4. **不拿规模对标**：本文比较的是**能力形状**，不是 QPS、数据量、组织规模、合规等级。大厂的能力是业务规模和组织分工的产物，不是一个小项目“补几个功能”就能等价；
5. **不跨业务线合并**：美团外卖/闪购/到店、京东零售/到家/科技、阿里淘宝/天猫/支付宝/阿里云是不同业务线；一条业务线的公开材料，不能拿来证明另一条业务线或整个集团的内部实现。

> 一句话：**能公开验证的，写成事实；只能从产品行为观察的，写成规则；只能从多个方案归纳的，写成模式；不知道的，写“不知道”。**

## 2. 大厂优惠券能力的真实分层

### 2.1 一张能力分层图

```text
┌─────────────────────────────────────────────────────────────┐
│ 活动/营销层                                                  │
│ 活动编排、人群圈选、预算、玩法、页面、投放、触达              │
│ 典型归属：营销平台/增长团队/业务产品                          │
└───────────────────────────┬─────────────────────────────────┘
                            │ 规则、权益、预算
┌───────────────────────────▼─────────────────────────────────┐
│ 计价/优惠层                                                  │
│ 券可用性、叠加/互斥、门槛/范围、最优组合、金额分摊            │
│ 典型归属：交易/计价中心，或营销中台的算价模块                 │
└───────────────────────────┬─────────────────────────────────┘
                            │ 券资产、状态
┌───────────────────────────▼─────────────────────────────────┐
│ 券资产层                                                    │
│ 模板、实例、券码、锁/核销/释放/退款、状态机、有效期           │
│ 典型归属：券平台/营销资产系统                                 │
└───────────────────────────┬─────────────────────────────────┘
                            │ 订单、支付、售后
┌───────────────────────────▼─────────────────────────────────┐
│ 交易层                                                      │
│ 订单、支付、售后、逆向；决定何时锁券/核销/退款                │
│ 典型归属：订单中心/支付系统/售后系统                          │
└───────────────────────────┬─────────────────────────────────┘
                            │ 结算数据
┌───────────────────────────▼─────────────────────────────────┐
│ 结算层                                                      │
│ 商家应收、平台补贴、对账、打款、发票、税务                    │
│ 典型归属：财务结算中心/商家结算系统                           │
└─────────────────────────────────────────────────────────────┘
```

**这张图是能力分层，不是某家公司的组织架构。** 不同公司边界不同：有的把计价放在交易中心，有的把券资产和计价合并，有的把结算放在财务中台。分层的目的，是让我们能说清楚“我们在哪一层、和谁比”。

### 2.2 为什么大厂的“优惠券系统”看起来什么都有

因为人们常把**整个业务平台**叫成“优惠券系统”：

- 活动、人群、预算、页面、投放——是营销平台；
- 券模板、发券、锁/核/退——是券资产系统；
- 门槛、叠加、分摊、订单金额——是交易/计价链路；
- 商家应收、平台补贴、打款——是结算系统；
- 设备指纹、黑名单、假单识别——是风控/反作弊系统。

**拿我们的内核去对比别人的整个平台，结论永远是“缺很多”；正确的比法是同层比。**

### 2.3 我们的切片

| 层 | 我们做不做 | 说明 |
|---|---|---|
| 活动/营销层 | ❌ 不做 | 活动编排、人群、页面、投放属于产品/营销平台 |
| 计价/优惠层 | ✅ 做一部分 | 试算、叠加/互斥、门槛/范围、行级分摊；不做“最优组合搜索” |
| 券资产层 | ✅ 做 | 模板、实例、锁/核/退、状态机、幂等、审计 |
| 交易层 | ❌ 不做 | 订单、支付、售后由产品/交易系统负责；我们提供原语 |
| 结算层 | ◐ 只做数据 | 日账单/结算数据；不做打款、发票、税务、逐笔对账执行 |

一句话：**我们做“券资产 + 计价 + 结算数据”，不做“营销玩法 + 交易执行 + 资金结算执行”。**

## 3. 对照对象与选择理由

| 对象 | 主要像我们哪一层 | 为什么选它 | 公开资料类型 |
|---|---|---|---|
| 美团 | 活动/计价/券资产/结算（业务平台） | 本地生活多商家、平台券/商家券、核销后售后，业务形状最接近“多商家租户” | 开放平台/商家文档、产品规则、风控技术博客 |
| 京东 | 计价/券资产/结算（自营+POP） | 券类型、叠加、限品类门槛、退款规则公开可见 | 公开技术分享、产品规则、帮助中心 |
| 阿里/淘宝/天猫 | 计价/券资产/结算（平台+商家） | 平台券/店铺券/跨店满减、退款与退券规则，是中文电商的典型样本 | 公开技术分享、产品规则、帮助中心 |
| Voucherify | 券能力 API | 最接近“券能力内核”的公开产品：validation/redemption/rollback、叠加、Webhook；公开的幂等契约较弱 | 官方 API 文档 |
| Stripe / Shopify | 计价/退款/分摊 | 行级折扣分摊、退款冲正、幂等键有公开且可验证的文档 | 官方文档 |
| SAP / Salesforce / Talon.One / Infosys Equinox | 企业促销/规则引擎 | 规则建模、多租户、促销优先级、企业级扩展 | 官方文档/产品页 |

> **关于 Infosys**：公开的券专项资料相对少，本文只把它作为“企业促销引擎”的补充样本，不为了凑齐名单而编造细节。若找不到可验证材料，就在 §10 标“未找到公开券专项文档”。

### 3.1 几个公开样本的关键差异

> 下表只写官方文档/公开产品规则能支撑的差异；不写内部实现。完整链接见 §10。

| 样本 | 校验/核销 | 分摊/退款 | 快照/版本 | 对我们的启示 |
|---|---|---|---|---|
| Voucherify | `validations` 只校验/算价，`redemptions` 才消耗；两者分开 | 折扣可按行金额/数量比例分摊；退款/回滚只支持整笔或整栈，不支持按行部分退 | 公开文档没有“校验→核销”的价格快照；只有可选的 LOCK session | 校验/核销分离一致；我们的按行退款比其公开能力更细；其 Webhook/版本/规则引擎比我们成熟 |
| 淘宝/天猫 | 券有门槛、叠加层级、互斥择优；部分退款不退券，整单退在有效期内退券 | 按单品优惠价比例分摊；退款按分摊后的实付；公开规则给了 A/B 两件商品的算例 | 活动报名有价格校验窗口/普惠券后价；不是订单级价格快照 | 行级分摊/退款方向一致；我们缺商家/门店维度和结算主体 |
| 京东 | 京券/东券不能混用；全品类东券每单一张；店铺→品类→全品类顺序扣减；平行门槛 | 逆向按分摊实付；东券整单退才返，拆单不退；红包按子单分摊返 | 价保按下单时基准金额，不是当前标价 | 出资/结算语义按业务线不同；我们缺结算主体和结算时点 |
| 美团 | 闪购券活动最多三层优惠；券状态未使用/已使用/已撤销/已退款/已冻结；整单优惠最多一个且与其他营销互斥；外卖红包一单一张、不可叠加/拆分 | 闪购按 SKU 原价比例分摊，尾差最后一项吸收；部分退款读分摊后金额；团购未消费随时退/过期自动退 | 团购验券 prepare→consume→cancel，重复幂等键返回首次结果；没有公开的订单级价格快照 API | 我们的行级分摊/退款方向与其公开 API 一致；缺商家/门店/结算主体 |
| 支付宝 | 退款用 `out_request_no` 做幂等键；多次部分退用不同号，重试复用同号 | 退款接口只处理支付金额，不处理券分摊 | — | 我们的 `refundNo` 与其一致；还缺租户作用域 |
| SAP Commerce | 券有 `CONSUME`/`CONSUME_PER_ITEM`/`NOT_CONSUMED`；下单最后一步对失效券是静默忽略 | 按 entry price share 分摊，最后一行拿余数；退货复用原交易促销并比例冲回 | 购物车/订单保存促销规则版本快照 | 我们的快照目标与 SAP 一致；SAP 的“静默忽略”是我们不想要的 |
| Talon.One | 规则效果返回给集成层，由商户应用；退货触发 `rollbackDiscount` | 按 item/pro rata/bundle 分摊；退货可选按当前规则重算 | 退货重算使用当前规则 | 我们选择“退货读原分摊”，比“按当前规则重算”更稳定；代价是规则变更不能追溯修正 |
| Infosys Equinox | `preview` 不提交、`evaluate` 提交；部分失败进 `failedCommits[]` | 公开资料未找到退款分摊细节 | 促销组、审批、版本、审计 | 校验/核销分离与我们的 `pricingId` 目标一致；其事件 fire-and-forget，不能当可靠事件 |
| Salesforce Loyalty | voucher 支持 redeem/reserve/reinstate + `reservationKey` | 部分核销用 `RedeemedValue`/`RemainingValue` | 平台级多租户/API 版本退休 | 两阶段预留可参照；它不是券内核的完整替代 |

**读表结论**：

- “校验/核销分离”是公开产品的共同做法；我们缺 `pricingId`（环 2）。
- “退款读原分摊/原交易”与“按当前规则重算”两种做法都存在。我们选择前者，和淘宝/天猫、SAP 的公开口径一致；Talon.One 公开文档提供的是后者（可选），说明这不是唯一标准，而是**产品取舍**。
- “结算/出资”在公开的券产品里普遍不是重点：Talon.One、Infosys、SAP 的公开券文档都没有完整的平台/商家结算模型；淘宝/天猫把它放在平台规则和分账服务里。这反过来说明：**券内核和结算系统是两层**。

## 4. 能力对照总表

> **读表说明**：
> - “行业公开做法”是多个公开方案的共同模式，不指某一家公司的内部实现；具体来源见 §10。
> - 差距符号：**●** 同层接近或已对齐；**◐** 有主体能力但缺关键件；**○** 未做；**—** 非目标/不做。
> - “本周期”指 05 路线图的六个环；“—”表示不在本周期。

| # | 能力 | 行业公开做法（共同模式） | 我们当前（2026-10-18） | 差距 | 本周期 |
|---|---|---|---|---|---|
| 1 | 模板与版本 | 模板/活动/批次分离；发布后核心规则不可变或版本化；券码池独立 | 五维模板（类型/范围/叠加层/互斥组/出资）+ 门槛/面额等规则字段；发布后无更新接口；无版本、无券码池 | ◐ 缺版本化/更新/码池 | 待评估（05 未列模板版本化） |
| 2 | 发券 | 领取、批量、定向、兑换码；库存、限领、预算闸门 | 仅单个领取；Redis 分桶库存、限领 N、日限；无批量/定向/码 | ◐ 缺批量/定向/码/预算 | 环 5（预算）；批量按 V5 |
| 3 | 券实例与状态机 | 模板→实例→占用/核销；状态机；过期/冻结/作废 | 状态机主体完整；锁/核/释/退/过期/超时关闭；退款回退 `REFUND_RETURN`；作废（INVALIDATED）当前无产生点 | ◐ 作废无产生点 | 待评估（05 未列） |
| 4 | 查询 | 按用户/状态/订单/退款单/账单查询；分页 | 券包查询；无订单占用、退款明细、账单查询 | ◐ 缺查询 API | 退款查询环 3；订单/账单查询/导出 05 未列 |
| 5 | 试算/校验 | validation 不消耗、redemption 才消耗；相邻机制有规则版本快照/LOCK session；公开样本未见到订单级报价 token | 整栈试算（层序/互斥/递进门槛/范围金额/逐行分摊）；无 `pricingId`、无最优组合搜索 | ◐ 缺价格快照/最优组合 | 环 2（快照） |
| 6 | 锁券/占用 | 下单占用、TTL、超时释放；业务键幂等 | 30 分钟锁窗；超时关闭；锁券按 `(orderNo, couponId)` 幂等；`usageNo` 由服务端生成，供核销/释放使用；释放守卫 | ● 主体对齐 | — |
| 7 | 核销 | 支付后核销；幂等；订单级上下文复算 | 核销幂等；L64 按 `(user_id, order_no)` 找回已锁/已核销占用单整栈复算；订单售后守卫；依赖接入方支付前把订单券全部锁完（L70） | ●/◐ 依赖全锁契约 | — |
| 8 | 释放/取消 | 取消/超时释放；终态幂等 | 释放幂等；已核销/已退款拒绝释放；超时关闭 | ● 主体对齐 | — |
| 9 | 退款 | 整单/按行+数量；退款单号幂等；冲回原分摊；部分退款通常不退券 | 按行+数量（仅带 `items` 的行级链路）；`refundNo` 幂等；累计上限；部分退不退券；整单退有效期内回可用；一券限退 3 次；老式核销只能整单退、无明细/不进日账单 | ●/◐ 核心对齐；老式链路是过渡边界 | 环 3（政策/查询） |
| 10 | 行级分摊 | 按行比例分摊；取整与尾差；单行上限；退款按原分摊冲回 | 按“进入本层前行剩余金额”比例；前 n−1 取整、末行兜底；单行上限；溢出再分配；三条守恒校验 | ●/◐ 商品金额对齐；缺税费/运费/多币种 | 环 1（主体）；税费/运费待评估 |
| 11 | 门槛/范围 | 全场/品类/SKU/商家/门店/地区；门槛按“可用券商品金额” | ALL/CATEGORY/SKU；门槛/折扣基数按券范围内金额；无商家/门店/地区 | ◐ 缺商家/门店/地区 | 环 1（商家/门店） |

## 5. 关键能力逐项对照

### 5.1 行级分摊与按行退款：我们最接近行业标准的一块

**行业公开做法**

- 订单级折扣要落到商品行：按行金额比例分摊，处理取整和尾差；单行不能分到超过该行金额；
- 退款按“原分摊”冲回，不按退款时的活动重算；
- 部分退款通常不退券；整单退是否退券看政策和有效期；
- 退款要有业务单号做幂等，重试复用同一单号；
- 部分退款后剩余金额跌破门槛，是否追回优惠是**政策**，行业常见“不追回”。

**公开样本的细节**

- **Shopify**：订单行/运费行有 `DiscountAllocation`，字段含义是“该行实际被折扣的金额”；`allocationMethod` 区分 `ACROSS`（分摊到所有行）和 `EACH`（每行都拿全额）；按件分摊除不尽时，用 `[0.01, 0.01, 0.02]` 这种方式让一个单位吸收尾差，`approximateAllocatedAmountPerItem` 返回最高份额；
- **Stripe**：发票行有 `discount_amounts`，行级折扣先于发票级折扣；信用票据按比例冲减折扣——10 行各 10 美元、50% 折扣，退一行减 5 美元而不是 10 美元；
- **Voucherify**：订单行区分 `discount_amount`（行级折扣）和 `applied_discount_amount`（订单级分摊到该行），两类折扣分开记；回滚是整笔/整栈粒度，最长 3 个月；公开文档没有按行/按金额的部分回滚；折扣券一次核销消耗一次，部分核销只对礼品卡/积分余额。
- **淘宝/天猫**：合并付款时，订单级优惠按各商品“单品优惠价”比例分摊；发生逆向退款，按各商品分摊后的实付款退。公开商家规则/解读给出的算例（数字仅示意）：A 100 元、B 200 元，店铺满 100−10、跨店满 300−50，最终实付 240；50 元按 1:2 分成 A 16.67、B 33.33；退 B 时退 200−50×200/300。
- **淘宝店铺券**：确认收货前全额退款、且退款完成时券仍在有效期 → 退券；部分退款、或退款完成时券已失效 → 不退。
- **天猫购物券**：一单只能用一张、不可拆分；交易在券有效期内关闭才退回，退回后有效期不变。
- **京东东券**：取消未拆分订单自动返券；订单已拆分时，即使取消全部子订单也不返；使用券的商品全部退货后才返券；过期券不补发；红包按子单/退货商品分摊额返还。
- **京东外卖“随心囤”事故（2025-12）**：用户买 100 张券后申请全额退款，平台只收回 1 张、99 张仍可用；京东确认短时系统故障并承担已出餐商家损失（公开报道未披露根因）。无论根因是什么，事故表现说明：**退款与券回收必须有原子性或有明确补偿**，否则一次故障就是资损。
- **美团闪购分摊**：`sku_benefit_detail` 把订单级优惠 N 按各 SKU 原价 M 比例分摊——份额 `M/ΣM×N`，SKU 实付 `M−份额`；只有实际作用到该 SKU 的优惠参与，配送费减免/买赠/满赠/退券不参与；餐盒费进分摊基数，配送费/包装袋不进；小数截断，最后一项吸收尾差；部分退款按分摊后金额。
- **美团部分退款**：`order/applyPartRefund` 是商家发起的部分退款；未接单/已取消/过退款窗口/只有一件商品时拒绝，不能整单退；可多次部分退；用户+商家部分退合计每单最多 10 次；可退 SKU 价按优惠等比例分摊，餐盒/配送费单列。
- **美团团购核销**：验券准备（prepare）→ 执行验券（consume）→ 撤销（cancel）；重复幂等键返回首次结果；撤销后生成新码、旧码失效。
- **美团服务零售退款**：按实付退；红包/券/积分/立减按各自使用规则；未消费“随时退”、过期“自动退”；已核销 1–3 天内可申请，商家确认/平台争议；已核销不可退/欺诈除外。
- **美团 2025-08 “退款不到账”事件**：公开报道称多数是退款信息展示更新不及时/错误，少部分是原支付渠道异常；平台成立专项客服追溯。说明退款不仅要“账做对”，还要“状态查得到、展示对”。
- **SAP**：退货复用原交易的促销，按原促销规则比例冲回；订单级折扣按 entry price share 分摊，最后一行拿余数，避免丢分。
- **Talon.One**：退货触发 `rollbackDiscount`，回滚折扣和预算影响；如果开启退货重算，则用**当前规则**重算。

**我们当前**

- `lineNo` 贯穿试算、核销、退款；同一订单的试算/核销/退款保持相同行序；
- 每层按“进入本层前的行剩余金额”比例分摊；前 n−1 行向下取整、末行拿余数；单行不超过行剩余金额；末行溢出再分配给有余量的行；
- 三条守恒：行分摊合计 = 券优惠；平台承担 + 非平台承担 = 行优惠；退款累计 ≤ 原分账；
- 退款读核销快照，不重算；`refundNo` 幂等；按行+数量累计上限；部分退不退券、整单退有效期内回可用、一券限退 3 次；
- 退款明细从原分账行复制结算主体（目标态；当前无主体列）。

**差距**

- 只分摊商品金额，不分摊税费/运费；多币种、汇率、舍入策略配置未做；淘宝/京东的公开规则明确把运费/税费/赠品排除在门槛和分摊之外，我们目前只接收商品行，调用方不传就不会参与——但内核没有显式的“不可分摊金额”字段；
- 尾差策略不同：淘宝/天猫的公开商家解读把尾差补到单价最高的 SKU；我们是“前 n−1 行向下取整、末行拿余数”。两者都守恒，但逐行金额会差几分钱；若要严格对齐某平台，需要把尾差策略做成配置；
- 退款查询 API、租户级退款政策未做（环 3）；
- 结算主体维度未落（环 1）；
- 老式核销（无 `items`）不写行级分账，不能按行退/按主体结算——这是过渡兼容边界，不是行业标准形态。

**与公开样本的一致/差异**

- 一致：退款读原分摊、部分退款不退券、整单退在有效期内退券，和淘宝/天猫、SAP 的公开口径一致；美团闪购也是“按原价比例、截断、最后一项吸收尾差”，我们的“末行兜底”是同一类做法；
- 差异：淘宝/天猫有商家/门店维度，我们缺（环 1）；美团把餐盒费纳入分摊基数、配送费/包装袋不纳入，我们只接收商品行；Talon.One 可选“按当前规则重算”，我们固定“读原分摊”，因为后者更稳定；代价是规则变更不能追溯修正历史订单；
- **退券不是公开产品的默认**：Voucherify 要显式 rollback，Shopify/Stripe 的公开文档没有说“完成订单退款会自动恢复券次数”；我们的“整单退自动回可用”是产品政策，不是行业标准，必须有租户政策/审计（环 3）；
- 我们多做的：把“退款累计数量/金额上限”“一券限退次数”“退款单号幂等”写成显式契约；公开产品不一定把这些放在券系统里。

**怎么判断“够了”**

对商品金额的按行分摊/退款，已经能支撑电商售后闭环；对税费/运费/多币种/跨境，还不够。**不要对外说“所有场景的行级分摊都做完了”**，要说“商品金额的行级分摊与按行退款已闭环，税费/运费/多币种是后续”。

### 5.2 价格快照（`pricingId`）：试算价必须等于核销价

**行业公开做法**

- 券产品通常把“校验/试算”和“核销/兑换”分开：校验不消耗券，兑换才消耗；
- 交易链路常用“报价/下单快照/试算凭证”把价格、优惠、分摊冻结到订单；
- 支付成功后核销按快照，不按当前模板/活动重算；
- 快照要绑定用户、订单、券集合、有效期；带快照但校验失败时拒绝，不静默改价。

> **一个关键结论**：公开样本里没有一个能证明“订单级价格快照 token 绑定试算与核销”。Voucherify 的 LOCK session、SAP 的规则版本快照、美团 prepare→consume、淘宝活动价格校验、京东价保，都是**相邻机制**，不能等同于 `pricingId`。我们的 `pricingId` 是目标态，不是“照着某一家抄”。

**公开样本的细节**

- **Voucherify**：公开文档没有“校验→核销”的价格快照 token；validation 返回 `valid_...` id，但 redemption 请求不引用它；可选的 LOCK session 只锁定用量，不保证价格；校验后规则/价格变了会怎样，公开文档没写。
- **SAP**：购物车/订单保存促销规则版本快照，`PromotionResult` 带规则版本与 KIE 模块版本，后续改规则不影响已存在的购物车/订单；
- **Infosys Equinox**：`preview` 跑同样的折扣计算但不提交核销，`evaluate` 才提交；多码核销的部分失败进 `failedCommits[]`，不是全部回滚；
- **SAP**：公开文档描述下单最后一步对失效券“静默忽略”——这是校验/核销分离的已知缺口，体验平滑但可能价不对；
- **淘宝/天猫**：活动报名有价格校验窗口/普惠券后价，但那是**活动级价格校验**，不是订单级快照，不能替代 `pricingId`；
- **京东价保**：按“下单时基准金额”算，不是当前标价；使用品类东券的订单要扣掉券支付部分，已价保金额也要扣减；价保过的订单再退款，退款额要减去已价保金额，防止重复退差；
- **美团**：团购核销是 prepare→consume→cancel 两阶段，重复幂等键返回首次结果；但公开文档没有订单级价格快照 API，不能把“两阶段核销”等同于 `pricingId`。

**我们当前**

- 试算有整栈计算和行级分摊，但没有 `pricingId`；
- 核销会按订单上下文整栈复算（L64），但只能找回已锁/已核销的占用单，依赖接入方支付前把订单券全部锁完（L70）；如果模板在试算后、核销前变更，复算结果也可能变；
- 扩展点上线后，如果核销重新调用资格/范围/出资扩展，结果也可能变。

**差距**

- 环 2：快照表、`pricingId`、绑定校验、TTL、fail-closed、旧调用方回退；
- 快照必须包含每行结算主体、每券每行分摊，以及**必需扩展的结果**；
- 支付后核销失败要有异常态（如 `CONFIRM_EXCEPTION`），不能走普通释放/超时回 `USABLE`，否则“用户已付款 + 券回可用 = 双重优惠”。

**为什么这块必须做**

不是“技术洁癖”：用户看到的价格、支付金额、核销记账必须是同一套数；模板改一次、活动换一档，就可能出现“试算 20、核销 15”或“试算不可用、核销可用”的客诉和资损。

### 5.3 叠加/互斥/门槛/范围：标准原语，不做万能规则引擎

**行业公开做法**

- 平台券/店铺券/品类券/跨店满减按层叠加；互斥组限制同组券不能一起用；
- 有优先级/计算顺序；有的产品会做“最优组合”搜索；
- 门槛按“可用券商品金额”判断，不按整单金额；
- 范围按品类/SKU/商家/门店/地区等维度。

**公开样本的细节**

- **Voucherify**：项目级 stacking rules——`ALL`/`PARTIAL`（一个无效是否整单失败）、`REQUESTED_ORDER`/`CATEGORY_HIERARCHY`（排序）、`STACK`/`ONCE`（商品重复应用）、`NEVER`/`ALWAYS` stackable 分类；上限 30 个 redeemable、5 个 never-stackable；
- **Shopify**：商品折扣先、订单折扣按商品折扣后的 subtotal、运费折扣最后；最多 5 个商品/订单码 + 1 个运费码，运费折扣不能叠加；叠加的百分比订单折扣都按同一个原 subtotal 算，不复合；
- **淘宝/天猫“平行式满减”**：以单品优惠价作为所有优惠的门槛参照；同层不叠加，不同层叠加；个人资产最后；
- **2026-03-10 起**：店铺级优惠改为“互斥择优”（店铺券与多件优惠不再叠加，系统按实际购物情况择优一个），平台用带日期的公告通知 ISV，并给出“升级前 170 元、升级后 180 元”的算例；
- **京东**：京券（无门槛、类现金）和东券（有门槛）不能同时用；全品类东券每单一张、同一商品一张；多个券满足时选优惠最大的；扣减顺序是店铺东券 → 品类东券 → 全品类东券；门槛按“券扣减前的可用商品金额”判，运费不计；
- **京东平行优惠**：SKU 标准价 = 京东价 − 单品促销；各门槛按标准价平行判断，不按逐层扣减后的金额；官方例子：400 元商品叠加 20 元总价促销 + 20 元店铺券 + 50 元品类券，实付 310；
- **美团外卖**：整单优惠最多一个，除积分抵扣配料外与其他营销互斥；商品行优惠不含整单优惠，用其他优惠的商品不参与整单分摊；首单红包与首减/满减/满赠/套餐赠/折扣菜互斥；一单一张红包、每天最多两张；满减每天最多两单；门槛按商品价+餐盒费、不含配送费；
- **Infosys Equinox**：评估组策略 `priority`/`first_match`/`best_discount`，组级 `maxAppliedPerCart`/`maxDiscountPerCart`；
- **Talon.One**：评估组 `Stackable`/`First Campaign`/`Highest Discount`；
- **SAP**：独占/非独占规则组 + 优先级 + 最大执行次数。

**我们当前**

- 两层：店铺层、平台层；互斥组；递进门槛；范围金额口径；
- 固定层序，不做“最优组合”搜索；
- 范围只有 ALL/CATEGORY/SKU；没有商家/门店/地区；
- 门槛口径是**递进式**（进入本层前的行剩余金额），淘宝/天猫和京东的公开规则都是**平行式**（单品优惠价/标准价）。两种口径都存在，我们当前不可配——这是“口径差异”，不是简单的功能缺失，需产品政策决定。

**差距**

- 环 1 补商家/门店维度；
- 环 5 补预算闸门；
- 最优组合本周期不做；通用优先级/任意规则表达式按 00 的边界不做——它们会把内核变成不可维护的规则引擎，测试组合爆炸，产品也说不清“为什么这单用了这张券”。最优组合如果确有产品需要，单独评估，不默认承诺。

**边界**

标准原语 + 配置覆盖大多数场景；长尾玩法走扩展点或产品层。**“不做万能规则引擎”是定位，不是偷懒。**

### 5.4 出资拆分 vs 结算主体：两个正交维度

**行业公开做法**

- 平台补贴、商家出资、平台/商家共担是“成本承担”；
- 平台和商家/门店/业务单元结算是“结算归属”；
- 两者不是一回事：平台出 10 元补贴、和商家 M 结算，成本是平台 10、商家 0，但平台应付 M 10；
- 多商家平台按商家/门店出结算数据；没有商家概念的产品（视频会员、SaaS）可以不传主体。

**公开样本的细节**

- **淘宝/天猫**：官方立减中消费者少付的部分由商家承担，商家不能获得等值现金；平台发放的消费券/红包，除另有约定外由平台承担，不得转嫁给商家（该出资归属来自 2026 天猫 618 招商规则，是**活动范围**，不是全平台通用规则）；
- **淘宝开放平台 OC 分账**：可按父订单/子订单粒度、按金额或比例分账，T+0/T+1，分账方需支付宝账号——这是**结算执行**，不是券内核；该公开文档较旧，只作能力形状参考；
- **京东**：零售券在结算时“轧差”——只把用户实付结算给商家，优惠由商家承担；科技权益（支付券、白条补贴）在收银台后发生，按“用户实付 + 权益金额”结算给商家，再通过预算/结算平台回收营销成本。同一个“券”在不同位置，结算语义相反；
- **美团外卖**：到店自取只能享受非美团补贴的活动，美团补贴活动仅限美团配送订单——**出资方和履约方式绑定**；平台红包与商家红包的退款返还规则也不同（第三方教程称平台红包按比例返、商家红包不退，官方以券面为准）；
- **美团结算**：技术服务费 6–8% 是佣金，配送/履约费单列；折扣是商家自愿营销、商家承担，平台不收费；团购按“实际核销券数 × 团购价 × 佣金比例”结算；收款周期 2 周自动/1 周手动/4 周自动；核销后 T+1（1–3 个工作日）到账；对账 API 按 `clearDate` 查券码/团购/服务费/结算额/退款/门店/订单号；结算信息不全则延期，收益日期 = 收款日 − 1；
- **Talon.One/Infosys/SAP**：公开券文档没有完整的平台/商家出资与结算模型；Talon.One 的预算只限制花费，不做成本分摊。

**我们当前**

- `funder_type`：平台/商家/共担；共担有平台比例；
- 行级 `platform_burden` / `merchant_burden`；
- 没有 `settle_party_id`；`merchant_burden` 只表示“非平台承担的成本”，**不是**“平台应付商家的钱”。

**差距**

- 环 1：订单行可选 `settlePartyId`，不传落 `__default__`；商家出资/共担券必须绑定主体；分账/退款明细加 `app_id + settle_party_id`；退款从原分账复制主体；
- 环 3：按主体日汇总，正行−退款；平台应付按主体汇总；
- 存量订单没有真实主体，只能 `__default__`，不能猜。

**为什么这是多商家租户的关键**

一个租户下多个商家时，券必须知道“这笔优惠算到谁头上、和谁结算”。只记“商家承担”不够：平台补贴也要按主体拆，否则财务无法按商家对账。

京东的例子还说明：**出资方、结算方、结算时点/方式必须分开建模**。同一个券在零售链路是“轧差”（少结算），在科技权益链路是“全额结算再回收”，两者的账务处理相反。我们当前只有 `funder_type` 和平台/商家承担，结算主体、结算时点、结算方式都没有建模；环 1/3 不是“加一个字段”，而是补结算语义。

### 5.5 幂等与一致性：业务键比请求 token 更重要

**行业公开做法**

- API 层有幂等键（同键同参重放、异参冲突）；
- 业务层还有业务键（订单号、退款单号、批次号）；两层都要有；
- 消息至少一次 + 消费方幂等；
- 对账/守恒校验发现差异，不靠“应该没问题”。

**公开样本的细节**

- **Stripe**：所有 `POST` 接受 `Idempotency-Key`；同键重试返回首次响应（包括 500）；参数不一致会报错；键至少保留 24 小时；客户端生成、建议 UUID、最长 255 字符；
- **Shopify**：2025-12 给 `refundCreate` 加 `@idempotent(key)`，同键重试返回原结果；并发重复与“同键异参”有不同错误码；官方说明计划在 2026-04 版本强制（以当前版本为准）；
- **Voucherify**：公开 API 文档里没有 `Idempotency-Key`；术语表声称“重复调用不会重复核销”，但 API 契约没有给出可验证的幂等键；LOCK session 用 `multiple_requests` 错误串行化，`409 duplicate_found` 只用于资源创建；
- **支付宝退款** `out_request_no`：失败重试必须复用同一号；同一笔交易多次部分退用不同号；已成功则幂等返回；
- **Talon.One**：只在退货接口提供 `Idempotency-Key`（v26.05）；重复键、重试、响应重放的完整语义公开文档没写全；
- **Infosys、SAP**：公开券文档里没有找到通用幂等键契约；
- **京东**：JOS/宙斯公开参数里没有统一 `requestId`；京东用专门的“营销权益防重系统” + 业务唯一键；京东健康开放文档要求接收方按源时间排序/去重。大厂也不一定有一个统一幂等头，但一定有业务键或防重系统；
- **美团**：团购核销 prepare/consume/cancel，重复幂等键返回首次结果；撤销后生成新码、旧码失效——业务键与状态机一起保证“不会核销两次”；
- **SAP**：公开文档描述下单最后一步对失效券静默忽略——说明“校验通过 ≠ 核销成功”是行业常见缺口。

**我们当前**

- 开放面 `X-Client-Token`（Redis 不可用时按设计 fail-open，业务键仍生效）；锁券 `(orderNo, couponId)`；核销/释放 `usageNo`；退款 `refundNo`；
- 核销/退款守恒校验；日账单重跑幂等；库存守恒巡检；
- 缺口：模板创建没有业务幂等键——换新 token 重复建会建两张，同 token 在 Redis 故障 fail-open 时也会重复；`refundNo` 全局唯一、不按租户；`uk_idem(user_id, idempotent_key)` 不含 appId（L73）；审计无幂等键。

**差距**

- 环 4：L73 待 05 拍板（改 64 张分表或 requestId 加 appId 前缀并迁移）；模板创建业务幂等、审计幂等是候选，05 未列；
- 这些不是“再加一个 token”能解决的：业务键必须稳定、可重放、能区分“同号同参”和“同号异参”。

### 5.6 多租户与配置：开放面是隔离面，`/api` 不是

**行业公开做法**

- 券产品/企业促销引擎通常有项目/环境/租户隔离；配额、配置、审计按租户；
- 租户有生命周期：开通、停用、轮换密钥、注销、导出/删除；
- 管理面有角色/权限，不是一把万能令牌。

**公开样本的细节**

- **Voucherify**：以 project 为租户边界，项目间数据不共享；API key、Webhook、metadata schema、stacking rules、固定的 API 版本都按 project；项目区域创建后固定；Areas/Stores 做子范围，restricted key 只能访问分配范围；
- **Infosys Equinox**：每个请求带 `instanceId`（平台租户）/`businessId`（商家）/`storeId`，repository 按这三个维度过滤；
- **京东到家**：公开分享称业务中台与技术中台用 Token 鉴权并携带业务身份，Token 绑定到券记录；领券时校验调用方 Token 与券记录 Token 一致；用户券存 MySQL 8 库 × 1024 表 + Redis Hash；发券平时 15 万/分钟、大促 45 万/分钟，约 5000 万/天、40 亿总量、归档 15 亿。公开材料描述的是业务线隔离，不是 `tenant_id` 行级租户隔离；
- **美团**：多业务授权用 `appAuthToken`（绑定授权主账号）+ `businessId`（业务线）+ `opBizCode`（门店/客户）三层；每次调用传 `realOpBizCode` 选择门店/客户；`accessToken` 约 30 天、`refreshToken` 35 天；授权可按门店/客户撤销。这是授权/业务线范围，不是物理租户隔离；
- **我们**：`appId` 类似 project，但没有环境/沙箱、没有 restricted key、没有区域概念；`/api` 不是隔离面。

**我们当前**

- 开放面 `/open/v1` 用 `appId` + HMAC + nonce + 时间窗；模板/用户券带 `app_id`；配额/限流/配置按租户；
- 占用单没有 `app_id` 列，经 `user_coupon.app_id` 追溯；
- `/api` 是平台运营面，没有 appId 隔离；GET 不鉴权；没有 RBAC；没有注销/导出/删除；L73 幂等键不含 appId；
- 配置：QPS/超时/开关可用；退款政策全局；熔断配置只在租户熔断器首次创建时读取、改配置需重启；warmup 与 `REDIS_DEPENDENCY`/`MESSAGE_CHANNEL` 两个 `wired=false` 开关没有执行点。

**差距**

- 环 4：RBAC、租户生命周期、隔离测试；L73 待 05 拍板；
- 环 3：租户级退款政策；
- 配置要“写了就生效”，不能“登记了但没有执行点”；不能热更的要写清楚。

### 5.7 扩展与规则：能力内核的边界，也是最大的风险点

**行业公开做法**

- 券产品有验证规则（客户、订单、商品、时间、次数）；企业促销引擎有规则模型和优先级；
- 外部集成常用 Webhook/事件；内部扩展用 SPI/插件；
- 扩展有版本、超时、降级、审计；扩展结果要能回放。

**公开样本的细节**

- **Voucherify**：validation rules 是可组合规则树（人群/购物车/金额/数量/元数据/核销人/预算），错误消息可定制；金额语义对叠加顺序敏感——“折前总额”在更早的优惠把购物车金额降下来后可能不满足；
- **Voucherify Webhook**：HMAC-SHA256 签名、10 秒超时、1 分钟到 24 小时退避、最多 12 次；堆叠核销每个 redeemable 一条事件 + 整栈一条，消费方必须去重；
- **Infosys Equinox**：`preview`/`evaluate` 分离，多码核销部分失败进 `failedCommits[]`；事件 fire-and-forget，可能丢。

**我们当前**

- 扩展点设计完成（资格、范围、定价、出资、结算、通知），但未实现；
- 没有 SPI、没有对外 Webhook、没有扩展注册/版本/审计；
- 扩展结果进 `pricingId`、支付后核销异常态还是目标。

**差距**

- 环 4：扩展公共契约、注册/版本/required/顺序/decisionId/错误码/沙箱；Webhook 安全（URL 审批、私网拦截、签名、重试、死信）；
- 扩展点上线前必须先有快照冻结和核销异常态，否则支付后核销失败会把券放回可用，造成双重优惠。

**边界**

扩展不是“让产品改内核代码”；也不是“所有逻辑都能扩展”。标准原语 + 少量扩展点，长尾留在产品层。

### 5.8 风控/反作弊/审计/韧性：大厂强在体系，我们刚起步

**行业公开做法**

- 风控/反作弊是跨系统证据链：账号、设备、IP、订单、支付、物流、售后；券系统只是其中一个信号源；
- 审计覆盖动钱/状态/管理动作，可查询、可校验、保留策略；
- 韧性有 SLO、故障演练、舱壁、降级矩阵、容量基线。

**公开样本的细节**

- **Voucherify**：反作弊是规则+限额，不做风险评分；明确把 IP rate limit 推给后端/网关；审计记录 dashboard/API/SDK 请求，但 Management API 动作不记录；共享区日志保留 6 个月、专用区 12 个月；
- **美团风控**：策略按“场景→规则→因子”组织，同步决策 + 异步采集，维护事件快照/聚合事实/衍生信号/黑白灰名单；关键动作返回放行/拒绝/增强验证；规则与决策分离、多决策可配优先级；把“薅羊毛”定义为下单/支付/购买/验券全链路的作弊；
- **美团预算分配论文**（arXiv 2406.05987）：券预算实时分配用 XGBoost + 等渗回归 + 拉格朗日对偶 + PID，公开摘要称预算误差 <1%——这是预算分配模型，不是券内核数据模型；说明大厂把“预算怎么分”做成独立能力；
- **京东风控**：“查杀分离”——前端做基础防护与实时风险探测，云端用大数据模型做对抗；违规订单规则封禁批量注册、爬虫、刷单、拆单套优惠等行为；
- **京东审计/对账**：开放平台要求 ISV 上传登录、订单访问、转第三方、数据库操作、批量上传五类日志，并规定时效（登录实时、订单访问 ≤5 分钟、转第三方 ≤60 分钟、数据库操作 ≤24 小时）；这是**合规日志义务**，不是券事件审计；
- **阿里云风险识别**在领券场景的公开案例：单日 800 万+ 请求、实时拦截 15%+ 恶意用户、行为分析召回 40%+ 垃圾用户、单日营销预算损失降到 5 万元以下——这是厂商案例，不是淘宝/天猫的具体实现；
- **阿里营销 DataCheck 对账**：DB、Tair 等多数据源比对，增量+全量，DRC 消息触发实时对账，告警+修复；
- **Talon.One**：预算可挂 campaign/profile/IP/coupon 等维度，多个预算取最严格；审计日志记录 Management API 变更；
- **Infosys**：促销有审批、版本比较、变更日志；**SAP**：购物车/订单保留规则版本快照。

**我们当前**

- 风控：IP 频控、单笔优惠占比上限、核销速率告警、审计；没有设备指纹、名单、预算闸门、风险决策钩子、结算 hold；
- 审计：核销/退款哈希链；异步写入失败只记 ERROR、无重试/告警，JVM 崩溃可能丢；无审计幂等键，重试可能重复；`record` 取不到 userId 时为空；没有查询/覆盖矩阵/保留/校验任务；
- 韧性：超时、熔断、限流、开关预案、发件箱；熔断主要覆盖领券链路，MQ 无熔断，发件箱默认只 `log` 兜底；有 Redis/限流降级演练脚本（DRILL PASS）；没有 SLO、容量基线、重试预算、舱壁，缺 MySQL/MQ 全依赖与系统化演练。

**差距**

- 环 5：规则 v1、风险决策钩子、反作弊信号、结算 hold、人工审核；
- 环 6：SLO、故障演练、压测四场景、容量表；
- 环 4：审计查询/覆盖/保留/校验，以及“不丢、不重”的可靠性。

**边界**

券内核无法单独判断“订单是不是假的、用户是不是和商家串通”；这需要订单、支付、物流等外部证据。我们能做的是：券侧信号、限额、审计、结算 hold，以及与外部证据的契约。**不要把“反作弊”说成券系统能独立完成的事。**

## 6. 中国企业公开实践的共同模式（对照公开产品）

> 以下每条都标了证据类型；没有 A/B 级来源的，只能当“产品规则/行业模式”，不能当内部实现。

### 6.1 券资产与营销活动分离

- **证据类型：B（公开工程分享）+ C（产品规则）+ D（行业模式）**。
- 活动、人群、预算、页面通常属于营销平台；券模板、发券、锁/核/退属于券资产系统。
- 公开样本：阿里 UMP 把营销活动拆成可复用元数据块；京东把券分成 `batchId`（批次静态属性）+ `couponId`（领取时实例），资格是独立的“券→SKU/品类/店铺”倒排索引。
- 对我们的意义：不要为了一个活动把活动编排、页面、投放做进内核；内核只提供券资产和计价原语。

### 6.2 平台券/商家券/共担 + 商家结算

- **证据类型：C（产品规则）+ D（行业模式）**。
- 电商/本地生活平台常见平台补贴、商家出资、共担；结算按商家/门店。
- 公开样本：淘宝/天猫官方立减由商家承担、平台消费券由平台承担；京东零售券“轧差”结算（只结算用户实付），科技权益“全额结算再回收”（结算用户实付+权益金额）。
- 对我们的意义：`funder_type` 只是成本承担；结算主体/结算时点是另外的维度，必须补（环 1/3）。

### 6.3 下单快照、退款按原分摊

- **证据类型：D（行业模式）+ A（SAP/Voucherify 公开文档）+ C（产品规则）**。
- 下单时冻结价格/优惠/分摊；退款读取原分摊，不按退款时活动重算。
- 公开样本：SAP 购物车/订单保存促销规则版本快照；淘宝按单品优惠价分摊、退款按分摊实付；京东价保按下单时基准金额。
- 对我们的意义：`pricingId` 不是可选优化，是“试算=核销”的必要条件（环 2）。

### 6.4 部分退款通常不退券，整单退有条件退券

- **证据类型：C（产品规则）+ D（行业模式）**。
- 部分退款通常不退券；整单退是否退券看平台政策和有效期；门槛是否追回是政策，常见“不追回”。
- 公开样本：淘宝店铺券部分退不退、确认收货前全额退且券有效才退；天猫购物券交易在有效期内关闭才退；京东东券拆单不退、全部退货才返、过期不补发；Voucherify 的回滚是整笔/整栈，不是按行。
- 对我们的意义：我们的政策（部分不退、整单退有效期内回可用、门槛不追回）是行业常见选择之一，不是唯一标准；租户级政策是环 3。

### 6.5 叠加有边界，不是万能规则引擎

- **证据类型：D（行业模式）+ A（Voucherify/SAP/Talon.One/Infosys 公开文档）+ C（产品规则）**。
- 叠加组、互斥组、优先级、层序是常见能力；但很少有平台把“任意规则表达式”开放给所有业务方。
- 公开样本：淘宝“平行式满减”+2026-03-10 店铺级“互斥择优”；京东京券/东券不能混用、店铺→品类→全品类顺序扣减；SAP 独占/非独占规则组；Talon.One/Infosys 评估组策略（可叠加/首个/最高折扣/优先级）。
- 对我们的意义：标准原语 + 配置 + 少量扩展点；最优组合本周期不做，通用规则引擎按 00 的边界不做。

### 6.6 风控/反作弊是跨系统证据链

- **证据类型：D（行业模式）+ B/C（公开分享/规则）**。
- 假单、套现、自产自销需要订单、支付、物流、设备等证据；券系统只能提供券侧信号和约束。
- 公开样本：京东风控“查杀分离”（前端基础防护+实时探测，云端大数据模型）、违规订单规则封禁批量注册/爬虫/刷单/拆单；阿里云风险识别在领券场景的厂商案例（单日 800 万+ 请求、拦截 15%+ 恶意用户）。
- 对我们的意义：环 5 做“信号 + 限额 + 结算 hold + 人工审核”，不冒充“反作弊大脑”。

## 7. 我们的真实水平

### 7.1 分维度

| 维度 | 当前水平 | 证据 | 不能声称 |
|---|---|---|---|
| 业务闭环 | 算钱域 + 行级售后达到“可试点”的业务内核 | 试算/锁/核/释/退/分摊/日账单；受影响链路 81 例 + 状态机 16 例全绿；全量最近一次除 1 例已知高负载偶发与 6 例门控跳过外全绿 | “结算完整”“所有售后场景都覆盖” |
| 多租户 | 开放面可试点；`/api` 不是隔离面 | appId + HMAC + 配额；`/api` 无 appId；L73 | “多租户生产级”“内部产品可直接用 `/api`” |
| 信任/安全 | L1~L2 之间，部分能力有 | HMAC、管理令牌、审计、限流、密钥轮换 | “等保/合规”“完整 IAM” |
| 风控/反作弊 | L1（最小防线） | IP 频控、占比上限、审计 | “能识别假单/套现” |
| 韧性/容量 | L1（组件有，体系未成） | 超时/熔断/限流/开关/发件箱；有 Redis/限流降级演练脚本（DRILL PASS）；无 SLO/容量基线，缺 MySQL/MQ 全依赖与系统化演练 | “高可用”“能扛大促” |
| 文档/契约 | 较强：目标态/真实态分开、错误码/幂等/边界明确 | 00~07 文档包 + STATUS 债台账 | “文档写完就等于实现” |

### 7.2 离大厂还有多远

- **不是“差一个功能”**：05 的六个环——结算主体、价格快照、结算-lite/政策/查询、信任边界、风控反作弊、韧性容量——目前都未完成（注意：这是 05 的六个环，不是已经完成的“第 2 环算钱域/行级售后”）；
- **已经完成的是“算钱域 + 行级售后”**：这是业务内核的地基，不是整栋楼；
- **最关键的三个缺口**：
  1. 结算主体（多商家租户无法按商家结算）；
  2. `pricingId`（试算价可能≠核销价）；
  3. 信任边界（RBAC/租户生命周期/API 版本/审计覆盖）。
- **不能拿规模对标**：我们没有大厂流量、组织、合规证据；本文只比能力形状，不比“谁更强”。

一句话：**业务内核到了“可试点”，信任/风险/韧性还在 L1；离大厂不是差一个功能，而是差结算主体、价格快照、信任边界三个体系件。**

## 9. 面试/作品集怎么讲

### 9.1 三个主故事 + 一个加分故事

**故事一：一笔按行退款，怎么保证不把钱算错**

- 背景：原来只能整单退，部分退款没有行级依据；退款金额如果按当前活动重算，会和用户下单时看到的不一致。
- 做法：行号贯穿试算/核销/退款；按行剩余金额分摊；三条守恒；退款读核销快照；`refundNo` 幂等；累计退款数量/金额上限；部分退不退券、整单退有条件退券。
- 证据：退款集成测试 R1~R8、L64 三例、状态机 16 例；日账单正行−退款明细。
- 边界：只覆盖商品金额；税费/运费/多币种未做；老式无 items 核销只能整单退。

**故事二：为什么要做 `pricingId`（目标态）**

- 背景：试算和核销是两次调用；模板/活动可能在中途变更；扩展点上线后，资格/范围/出资结果也可能变。
- 做法：一次试算=一个快照；绑定 appId/userId/orderNo/券集合；TTL；fail-closed；核销读快照；必需扩展结果冻结；支付后核销失败进异常态，不把券放回可用。
- 对比：SAP 的规则版本快照、Voucherify 的 validation/redemption 分离、电商的下单快照，都是同一类问题的不同解法；Stripe 的幂等键解决的是“重试安全”，是配套问题。
- 边界：未实现；`CalculateRequest` 当前没有 `orderNo`，契约要加字段。

**故事三：为什么做能力内核，而不是营销平台**

- 背景：多个产品都需要券，但活动、人群、页面、投放各不相同；如果每个产品都改内核，内核会变成不可维护的业务系统。
- 做法：内核只做模板/实例/锁/核/退/分摊/结算数据；产品做活动/营销/界面；标准原语+配置+扩展点；开放面 appId 隔离；结算主体可选。
- 对比：美团/京东/淘宝的“优惠券系统”其实是业务平台的一组能力，横跨营销、计价、券资产、交易、结算；Voucherify 是更接近“券能力 API”的公开样本。
- 边界：我们不做活动编排、商家入驻、支付结算执行；也不声称达到大厂规模。

**故事四（加分）：多租户隔离的边界**

- 开放面 `/open/v1` 有 appId + HMAC + 配额；`/api` 是平台运营面，没有 appId 隔离；`uk_idem` 不含 appId（L73）；退款单号全局唯一。
- 讲法：不回避缺口，说明“哪些场景必须走开放面、哪些要等环 4”；这比“我们多租户做得很好”更可信。

### 9.2 不要这么说

- ❌ “我们对标美团/淘宝”——除非你能说清同层比什么、规模证据是什么；
- ❌ “我们自研了规则引擎”——我们没有通用规则引擎，只有标准原语+配置+扩展点；
- ❌ “我们结算完整”——我们只有日账单/结算数据，不做打款/发票/税务/逐笔对账；
- ❌ “我们能防作弊”——我们只有券侧信号和限额，订单真实性靠外部系统；
- ❌ “我们高并发/高可用”——没有容量基线、SLO；只有 Redis/限流降级的有限演练证据，不要这么说；
- ❌ “所有行级场景都覆盖”——税费/运费/多币种/跨境未做。

### 9.3 可以量化的证据（只说测过的）

- 受影响链路 81 例零红；状态机 16 例零红；全量最近一次：除 1 例已知高负载偶发（单跑绿）与 6 例门控跳过外全绿；
- 行级分摊三条守恒；退款累计上限；L64 订单级复算三例；退款 R1~R8；
- 这些是**测试证据**，不是生产流量证据。

- **美团/京东/阿里的内部实现**：数据库表结构、状态机、精确分摊/舍入算法、幂等键格式、结算内部流程，公开资料不足；本文只写产品规则和公开分享，不还原内部。

- **美团平台/商家红包的退款返还**：官方页面只给了部分使用/退款规则；“平台红包按比例返、商家红包不退”来自第三方教程，未在官方页面逐条复核，引用时已标注。

- **淘宝/天猫规则页**：部分帮助页客户端渲染/需要登录，未能全文抓取；引用来自页面标题、搜索摘要和商家解读，具体数字以官方页面为准。
- **Voucherify**：公开文档没有价格快照、没有 `Idempotency-Key`、回滚只到整笔/整栈；这不代表企业版没有，只是公开文档没写。
- **SAP**：help.sap.com 是 SPA，部分细节来自索引摘要；Promotion Calculation Engine 指南是 6.0.0，线上 Commerce Cloud 行为可能不同。
- **Talon.One**：没有公开的出资/结算模型；`Idempotency-Key` 只在退货接口，重复键/重试/响应重放语义未写全。
- **Infosys Equinox**：公开资料是概念/FAQ/事件级别，没有公开 REST schema、幂等键、按行退款细节、结算模型。
- **Salesforce Loyalty**：帮助页返回 403/JS 壳，部分细节来自 Trailhead 和发布说明摘要；它是忠诚度券，不是通用券内核。
- **平台级幂等契约**：公开材料只支持“流水线级”幂等（支付宝退款、美团验券、Shopify `refundCreate`、Talon.One 退货），不支持“所有券操作统一幂等头”；京东没有统一 `requestId`，Voucherify/Infosys/SAP 公开文档没有通用幂等键契约。
- **租户隔离内部实现**：美团的 `appAuthToken`/`businessId`/`opBizCode`、京东 Token/业务身份、阿里 TMF2/单元化，都是逻辑范围/业务隔离；物理隔离、行级 `tenant_id`、配额、吵闹邻居没有公开。
- **审计**：美团结算对账 API、京东 ISV 日志、阿里 DataCheck、SAP 版本快照，都是相邻证据，不是“每张券的完整审计轨迹”。
- **API 废弃**：美团固定 `version=2` + 字段回收通知、阿里 TOP `v=2.0` + 公告、京东 `v=1.0/2.0`，都是协议版本/公告，不是完整的 per-API 语义版本/废弃策略。
- **容量/韧性/扩展点**：公开材料没有可比的 SLO、RTO/RPO、故障演练、插件/扩展 API；本文只把它们标为差距，不拿零散分享当容量证明。
- **风控**：公开材料只支持规则/限额/名单/决策钩子；没有公开的 ML 评分细节；阿里云数字是厂商案例，美团 arXiv 是预算分配，不是券风控。
- **我们的生产证据**：没有真实流量、SLO、容量基线；只有 Redis/限流降级演练脚本（DRILL PASS），没有 MySQL/MQ 全依赖与系统化故障演练；本文的“我们当前”只到测试/代码证据，不能当生产证明。
