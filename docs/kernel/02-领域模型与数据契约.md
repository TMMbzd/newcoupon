## 1. 模型总览

```text
appId（租户）
  │
  └─ coupon_template（一类券的规则；结算主体可选）
       │
       └─ user_coupon（用户持有的一张券；领取时快照）
            │
            └─ coupon_usage（一次“券 × 订单”的合同；usage_no 唯一）
                 │
                 ├─ coupon_share_detail（核销时按商品行的分账）
                 │     └─ app_id + settle_party_id + 行号/行金额/行数量/优惠/出资
                 │
                 ├─ coupon_refund_order（一次退款；refund_no 唯一）
                 │     └─ coupon_refund_detail（按商品行的退款明细）
                 │           └─ settle_party_id 从分账行复制
                 │
                 └─ coupon_event（发放/锁定/核销/释放/过期/退款事件）

coupon_pricing_snapshot（试算价格快照；pricing_id 唯一）  ← 已有（V23）
coupon_pricing_usage（占用单 ↔ 快照绑定）                 ← 已有（V23）
coupon_confirm_exception（支付后核销异常）                ← 已有（V23）
coupon_daily_bill（按模板的 T+1 日账单）                  ← 已有
coupon_settle_party_daily_bill（按结算主体的日汇总）       ← 目标态
open_app_config（租户级配置/退款政策）                    ← 已有配置中心
audit_log（动钱/状态/管理动作审计，哈希链）                ← 已有
```

**读图要点**：

- 模板是“规则”，用户券是“一张券”，占用单是“一次使用合同”；
- 分账/退款明细是“钱怎么分”，日账单是“按维度汇总”；
- 结算主体是可选维度：没有细分主体的产品，分账/退款/日汇总落 `__default__` 桶；
- 价格快照已由 V23 落地（灰度默认关），用来保证试算价 = 核销价；绑定表记录锁券用了哪份快照；异常表记录支付后核销失败。

## 2. 实体与职责

### 2.1 租户（OpenApp / appId）✅

| 项 | 说明 |
|---|---|
| 是什么 | 一个接入方；开放面用 `appId` 标识 |
| 负责 | 数据隔离、配额、配置、审计、结算边界 |
| 关键字段 | `app_id`、名称、状态、QPS/日配额、联系方式 |
| 不负责 | 商家入驻、结算账户、支付；这些是产品/财务系统的事 |

### 2.2 结算主体（Settlement Party）◐（V22 已落字段）

| 项 | 说明 |
|---|---|
| 是什么 | 优惠最终算到谁头上、平台和谁结算；可以是商家、门店、经销商、业务单元，或租户自己 |
| 为什么 | 平台券跨主体时要拆分补贴；商家出资/共担券必须知道扣谁的钱 |
| 关键字段 | `settle_party_id`（或 `merchant_id`，命名待定）、`app_id` |
| 默认 | 不传落 `__default__`；不冒充真实主体 |
| 约束 | 商家出资/共担券必须绑定；平台券可空（全租户）或指定 |
| 不负责 | 商家主数据、入驻、结算账户、打款 |

> 命名：文档/契约统一用 `settlePartyId`（推荐名，最终待拍板）；`merchantId` 只作电商场景别名，不作为契约字段。

### 2.3 券模板 CouponTemplate ✅

| 项 | 说明 |
|---|---|
| 是什么 | 一类券的规则 |
| 关键字段 | `id`、`template_code`、`activity_id`、`name`、`coupon_type`、`face_value`、`discount_cap`、`threshold`、`total_count`、`per_user_limit`、`daily_limit`、`per_user_daily_limit`、`valid_type/start/end/days`、`approve_status`、`publish_status`、`issued_count`、`app_id`、`scope_type`、`scope_ids`、`stacking_layer`、`exclusion_group`、`funder_type`、`budget_ratio`、`settle_party_id` |
| 目标新增 | `rule_version`（模板规则版本，可选） |
| 不变量 | 满减面额 ≤ 门槛；满折有上限；SPLIT 有比例；范围一致性；**商家出资/共担券必须绑一个结算主体**；**平台券可空（全租户）或指定主体**；模板绑定主体只对商家/共担券必填、发布后不可变；平台券的行主体按行解析 |
| 可变性 | 面额/门槛/范围/出资/结算主体/有效期发布后不可变；要改走新模板/新版本 |
| 不负责 | 发券、锁券、核销；这些是实例/占用单 |

### 2.4 用户券 UserCoupon ✅

| 项 | 说明 |
|---|---|
| 是什么 | 某个用户持有的一张券 |
| 关键字段 | `id`、`user_id`、`template_id`、`template_code`、`face_value`、`threshold`、`discount_cap`、`valid_end`、`status`、`receive_time`、`idempotent_key`、`seq`、`app_id` |
| 快照 | 面额、门槛、折扣上限、有效期在领取时固化；模板后续变更不影响这些字段 |
| 动态字段 | 范围/层级/互斥组目前实时读模板；目标是用价格快照/模板版本控制（见 §6） |
| 不变量 | 同一用户同一模板的序号唯一；同一幂等键只发一次；有效期归一化到当日 23:59:59 |
| 分片 | 按 `user_id` 分 64 张物理表；不要随便加宽表 |

### 2.5 占用单 CouponUsage ✅

| 项 | 说明 |
|---|---|
| 是什么 | 一次“券 × 订单”的合同 |
| 关键字段 | `id`、`usage_no`、`user_id`、`user_coupon_id`、`order_no`、`status`、`discount_amt`、`occupy_time`、`use_time`、`release_time` |
| 唯一键 | `usage_no` 全表唯一（`orderNo:couponId` 的有界形式） |
| 作用 | 幂等锚点、回退裁判、金额载体 |
| 不变量 | 一个订单+一张券只有一份占用单；`discount_amt` 只在核销时写；状态只走合法迁移 |
| 分片 | 按 `user_id` 分 64 张物理表；**不加结算主体/价格快照列**，避免动 64 张表 |

### 2.6 分账明细 CouponShareDetail ✅/◐

| 项 | 说明 |
|---|---|
| 是什么 | 核销时按商品行记录的优惠与出资归属 |
| 关键字段 | `id`、`user_coupon_id`、`user_id`、`template_id`、`app_id`、`settle_party_id`、`pricing_id`、`usage_no`、`order_no`、`order_line_no`、`order_line_amount`、`order_line_quantity`、`platform_burden`、`merchant_burden`、`share_total`、`create_time` |
| 新增 | `pricing_id`（V23，可空）：核销用的价格快照，审计追溯用；老式核销/未启用快照为 NULL |
| 唯一键 | `(usage_no, order_line_no)`：同一占用单同一行一条正分账 |
| 守恒 | `share_total = platform_burden + merchant_burden`；`share_total ≤ order_line_amount`；同一 `usage_no` 的 `Σ share_total = 占用单优惠` |
| 字段含义 | `platform_burden` = 平台承担的成本；`merchant_burden` 是历史字段名，实际表示“**非平台出资方承担的成本**”，**不是“平台应付商家的钱”**；平台应付某主体 ≈ 该主体行上的 `platform_burden` 净额（默认商家收款模式） |
| 归属 | 每行的 `settle_party_id` 是该行商品所属主体；退款从这里复制，不重算；`app_id`/`settle_party_id` 已由 V22 落列 |
| 不负责 | 汇总；汇总是日账单/结算数据 |

### 2.7 退款单 CouponRefundOrder ✅/◐

| 项 | 说明 |
|---|---|
| 是什么 | 一次退款请求的汇总单据 |
| 关键字段 | `id`、`refund_no`、`usage_no`、`user_coupon_id`、`user_id`、`template_id`、`app_id`、`order_no`、`refund_type`、`refund_discount_amt`、`refund_platform_amt`、`refund_merchant_amt`、`request_digest`、`item_count`、`coupon_returned`、`coupon_status`、`usage_status`、`create_time` |
| 目标新增 | 无（`app_id` 已由 V22 落） |
| 唯一键 | `refund_no` 全局唯一 |
| 不变量 | 同号同参重放返回首次结果；同号异参冲突；同号跨占用单拒绝；金额 = 明细之和 |
| 不负责 | 用户实际收款、支付渠道退款；这些是订单/支付系统 |
| 状态 | 当前只有“已退款成功”一种业务结果；没有打款状态（目标也不做，除非未来接结算引擎） |

### 2.8 退款明细 CouponRefundDetail ✅/◐

| 项 | 说明 |
|---|---|
| 是什么 | 一次退款里，每一行退多少数量、冲回多少优惠与出资 |
| 关键字段 | `id`、`refund_no`、`usage_no`、`order_line_no`、`user_coupon_id`、`user_id`、`template_id`、`app_id`、`settle_party_id`、`refund_qty`、`refund_discount_amt`、`refund_platform_amt`、`refund_merchant_amt`、`create_time` |
| 目标新增 | 无（`app_id`/`settle_party_id` 已由 V22 落） |
| 唯一键 | `(refund_no, order_line_no)` |
| 不变量 | 累计退款数量 ≤ 原行数量；累计冲回金额 ≤ 原行分账；`退优惠 = 退平台 + 退非平台`（`refund_merchant_amt` 是历史字段名，表示非平台出资方冲回，不是平台应付）；`settle_party_id = 原分账行` |
| 老式退款 | 不带 items 的老式退款只写退款单、不写退款明细；不能进入按行/按主体结算 |
| 不负责 | 重新计算优惠；只从分账快照按数量拆分 |

### 2.9 退券留痕 CouponReturnLog ✅

| 项 | 说明 |
|---|---|
| 是什么 | 整单退款把券退回可用时的留痕 |
| 关键字段 | `id`、`user_coupon_id`、`refund_no`、`return_time` |
| 唯一键 | `refund_no` |
| 作用 | 一券限退 N 次、审计追溯 |
| 不变量 | 一次退款最多一条退券留痕；只对整单退完且券在有效期内的场景 |

### 2.10 价格快照 CouponPricingSnapshot ✅

| 项 | 说明 |
|---|---|
| 是什么 | 试算时冻结的一单价格与分摊（V23 已实施，独立非分片表） |
| 关键字段 | `pricing_id`（P+128 位随机串）、`app_id`、`user_id`、`order_no`、`coupon_set`、`request_digest`、`live_digest`、`payload`（MEDIUMTEXT JSON：商品行/券规则/每券每行分摊/结算主体/引擎版本/冻结配置/扩展决策占位）、`payload_version`、`engine_version`、`payload_bytes`、`line_count`、`applied_coupon_count`、`original_amount`、`discount_amount`、`final_amount`、`expires_at`、`last_bound_at`、`create_time` |
| 唯一键 | `pricing_id`；`(app_id,user_id,order_no,live_digest)`——ACTIVE 时 `live_digest=request_digest`，过期置 NULL，允许同摘要重建且保留历史行 |
| 粒度 | 一次试算 = 一个快照，覆盖商品行、券集合、每张券每行分摊；同一订单多张券可共用，不能跨订单复用 |
| 绑定 | `app_id + user_id + order_no + 券集合` 必须匹配；锁券带 ID 时同事务写 `coupon_pricing_usage` |
| TTL | 默认 120 分钟；锁券时续期到“锁窗 + 10 分钟宽限”；过期后带 ID 拒绝；清理保留 7 天 |
| 不变量 | 归属必须匹配；过期/撤销拒绝；券集合与订单占用单一致；快照不可改；带 ID 的问题一律 fail-closed，不静默改价；payload ≤ 1 MiB |
| 生命周期 | 创建 → 锁券绑定/续期 → 核销使用 → 过期置空 `live_digest` → 7 天后物理删除 |
| 不负责 | 替代分账；核销后仍以分账明细为准 |

### 2.10.1 快照绑定 CouponPricingUsage ✅

| 项 | 说明 |
|---|---|
| 是什么 | 占用单与价格快照的绑定（V23，独立非分片表） |
| 关键字段 | `usage_no`、`pricing_id`、`app_id`、`user_id`、`order_no`、`coupon_id`、`bound_at` |
| 唯一键 | `usage_no`：一份占用单只能绑定一份快照 |
| 写入 | 锁券事务内写；快照续期失败则整个锁券回滚 |
| 作用 | 核销漏传 `pricingId` 时按绑定自动解析；传了不同 ID → 4007；回滚/审计可回答“这次锁券用了哪份快照” |
| 生命周期 | 随占用单保留；不随快照清理删除（审计用） |

### 2.10.2 核销异常 CouponConfirmException ✅

| 项 | 说明 |
|---|---|
| 是什么 | 用户已支付但带 `pricingId` 的核销无法完成时的异常记录（V23） |
| 关键字段 | `usage_no`、`app_id`、`user_id`、`user_coupon_id`、`order_no`、`pricing_id`、`reason`、`resolve_status`（PENDING/CONFIRMED/RELEASED）、`resolve_reason`、`resolve_time`、`create_time` |

## 3. 状态机

### 3.1 用户券状态 CouponStatus

| 当前状态 | 动作 | 目标状态 | 守卫/说明 |
|---|---|---|---|
| 不存在 | 领取/发放 | `USABLE` | 模板可领、库存/限领、幂等 |
| `USABLE` | 锁券 | `LOCKED` | 未过期、归属正确 |
| `LOCKED` | 核销 | `USED` | 占用单占用中、券未过期 |
| `LOCKED` | 释放/超时 | `USABLE` 或 `EXPIRED` | 未过期回可用，已过期转过期 |
| `LOCKED` | 锁定期过期收场 | `EXPIRED` | 确已过期 |
| `USABLE` | 到期 | `EXPIRED` | 定时/惰性判断 |
| `USABLE`/`LOCKED` | 作废 | `INVALID` | 风控/运营 |
| `USED` | 整单退款退券 | `USABLE` 或 `EXPIRED` | 政策例外；有效期内回可用，已过期转过期；一券限退 N 次 |
| 其他 | 非法动作 | 拒绝 | 返回状态冲突 |

> `USED` 不是绝对终态：唯一出边是“整单退款退券”；部分退款不退券。

### 3.2 占用单状态 UsageStatus

| 当前状态 | 动作 | 目标状态 | 说明 |
|---|---|---|---|
| 不存在 | 锁券 | `OCCUPYING` | 建占用单，唯一 `usage_no` |
| `OCCUPYING` | 核销 | `CONFIRMED` | 写 `discount_amt`、核销时间 |
| `OCCUPYING` | 释放 | `RELEASED` | 取消/超时 |
| `OCCUPYING` | 锁定期间过期 | `EXPIRED` | 过期收场 |
| `OCCUPYING` | 锁定超时 | `TIMEOUT_CLOSED` | 系统收场 |
| `CONFIRMED` | 部分退款 | `PARTIALLY_REFUNDED` | 按行+数量 |
| `CONFIRMED`/`PARTIALLY_REFUNDED` | 再部分退款 | `PARTIALLY_REFUNDED` | 累计未退满 |
| `CONFIRMED`/`PARTIALLY_REFUNDED` | 全部退完 | `REFUNDED` | 所有正分账行退满 |
| `OCCUPYING` | 支付后快照核销失败 | `CONFIRM_EXCEPTION` | 4007/快照校验失败；暂停 30 分钟超时释放；券保持 `LOCKED`，不得回 `USABLE` |
| `CONFIRM_EXCEPTION` | 人工按快照核销 | `CONFIRMED` | 管理面 CONFIRM；按冻结金额/分摊记账；不可重复核销 |
| `CONFIRM_EXCEPTION` | 人工确认退款后释放 | `RELEASED` | 管理面 RELEASE；券 LOCKED→USABLE/EXPIRED；券已过期时保持 EXPIRED |
| 其他 | 非法动作 | 拒绝 | 返回 4004/4006 等 |

> **实现说明**：`CONFIRM_EXCEPTION(7)` 已由 V23/环 2 落地。`timeoutClose` 只 CAS `status=0`，因此异常单天然跳过 30 分钟超时释放；普通 `release`/`refund` 遇到 7 返回 4004；只有管理面 `/api/pricing-exceptions/{usageNo}/resolve` 能解除。

### 3.3 退款单/快照

- 退款单没有“待支付/已打款”状态：它是券平台的冲回记录，资金执行在订单/财务系统；
- 价格快照没有复杂状态机：`expires_at` 到期即失效；读取时判断归属/过期/券集合。

## 4. 不变量

> 不变量 = 任何代码路径、并发、重试、迁移都必须保持的规则；破坏它就会出现错账/错状态。

### 4.1 模板

- 满减：`face_value ≤ threshold`；满折：`discount_cap > 0`；无门槛：`threshold = 0`；
- `SPLIT`：`budget_ratio` 1~99；非 SPLIT 不设比例；
- 范围：`ALL` 不设 `scope_ids`；非 ALL 必须有范围值；
- 商家出资/共担：`settle_party_id` 必须非空（V22 起，灰度开启时强制）；
- 核心规则（面额/门槛/范围/出资/结算主体/有效期）发布后不可变或版本化。

### 4.2 用户券

- 领取时快照面额/门槛/折扣上限/有效期；
- `valid_end` 归一化到当日 23:59:59；
- 同一用户同一模板的 `seq` 唯一；同一幂等键只发一次；
- 状态迁移只走 §3.1。

### 4.3 占用单

- `usage_no` 唯一；同一订单+券只有一份；
- `discount_amt` 只在核销时写；
- 状态迁移只走 §3.2；
- 已核销/已退款不可释放。

### 4.4 分账

- 同一 `usage_no + order_line_no` 只有一条正分账；
- `share_total = platform_burden + merchant_burden`（`merchant_burden` 实际是“非平台承担”）；
- `share_total ≤ order_line_amount`；
- 同一 `usage_no`：`Σ share_total = usage.discount_amt`；
- 同一 `usage_no`：`Σ platform_burden = 平台总成本`，`Σ merchant_burden = 非平台总成本`；
- **结算应付是条件公式**：在“商家收款、平台补差”模式下，按结算主体汇总 `platform_burden` 得到平台应付；平台代收再结算的口径不同（可能含服务费/全额结算/退款冲正），结算模式未拍板前不对外承诺；非平台承担不是平台现金支出；
- 每行 `settle_party_id` 非空（目标）；商家出资/共担券的行必须属于模板绑定的主体；
- 以上仅对带 `items` 的行级核销成立；老式核销不写分账，不适用。

### 4.5 退款

- `refund_no` 全局唯一（不按租户隔离）；不传时生成 `AUTO:<usageNo>`；`(refund_no, order_line_no)` 唯一；
- 同号同参重放返回首次结果；同号异参返回 `1000`；同号跨占用单拒绝；
- 累计退款数量 ≤ 原行数量；
- 累计冲回优惠 ≤ 原行 `share_total`；累计冲回平台/非平台 ≤ 原行对应出资；
- `refund_discount_amt = refund_platform_amt + refund_merchant_amt`（后者是非平台冲回，不是平台应付）；
- `refund_detail.settle_party_id = share.settle_party_id`（精确复制，不重算）；
- 全退判定：所有正分账行退满才转 `REFUNDED`；
- 部分退款不退券（券保持 `USED`）；整单退券：券在有效期内回 `USABLE`，已过期转 `EXPIRED`；一券限退 N 次（当前全局 3）；
- 同一占用单最多 50 次退款（当前全局）；
- 老式退款（不带 items）只能整单退、无退款明细，不能进入按行/按主体结算。

### 4.6 价格快照（目标）

- `pricing_id` 唯一；归属（appId/userId/orderNo）匹配；
- 一次试算 = 一个快照，覆盖整单券集合；同一订单多张券可共用，不能跨订单复用；
- 快照不可改；过期拒绝；TTL 与锁券/支付窗口对齐（具体值待定）；
- 快照里的券集合与订单占用单一致；不一致一律拒绝（fail-closed），不静默改价；
- 核销带快照时，金额/分摊以快照为准，不按模板当前值重算；
- 不带 `pricingId` 的旧调用方：带 items 走整栈复算；不带 items 按调用方金额记账（见 4.4 限定）。

### 4.7 账单

- 模板日账单：`净额 = 正分账 − 退款明细`；重跑幂等；**只覆盖带 items 的行级核销/退款**；
- 老式核销/退款没有正分账/退款明细，**在日账单中不可见**；不能按日账单净额对老式链路做结算；
- 结算主体日账单：同一模板多主体相加 = 模板日账单；退款日负数；
- `confirm_count`/`refund_count` 是行数，不是订单数/退款请求数。

### 4.8 金额与时间口径

- **金额单位**：分，整数；不使用浮点；
- **取整**：满折按四舍五入到分；分摊前 n−1 行向下取整、末行兜底；退款按累计差；
- **时区**：`Asia/Shanghai`；日切 00:00；
- **日账单**：T+1 00:30 生成昨日账单；重跑幂等；跨日退款记退款日；
- **锁窗**：默认 30 分钟，与订单取消/支付超时契约对齐；超时收场后迟到核销返回 4006；
- **多券订单**：支付前应把订单全部券锁完；核销按订单号整栈复算；订单进入售后后拒绝再核销其他券（当前实现见 01/05）。

### 4.9 跨实体

- `usage.discount_amt = Σ share.share_total`（**仅行级核销**；老式核销 0 行，不适用）；
- `refund_order` 金额 = `Σ refund_detail`（**仅行级退款**；老式退款无明细，不适用）；
- 用户券状态与占用单状态一致：券 `USED` 对应占用单 `CONFIRMED/PARTIALLY_REFUNDED/REFUNDED`；券 `USABLE` 对应占用单 `RELEASED/超时/过期`（或未使用）；**券 `USABLE/EXPIRED` 也可对应占用单 `REFUNDED`**（整单退款退券路径：券按有效期回可用/转过期）；
- 事件：目标至少一次 + 消费方按 `eventId` 幂等；当前对外 Webhook 未实现；
- 审计：当前 best-effort（异步写入、失败只记 ERROR、可能丢/重，见 §2.14/01 G7）；“不丢不重、全覆盖、可查询”是目标态，不是当前不变量。

## 5. 数据归属与写入规则

| 数据 | 谁写 | 谁读 | 规则 |

## 7. 迁移与兼容规则

1. **只加不删**：新列有默认值或按语义可空；不删旧列、不改旧列语义；
2. **存量归属**：
   - 分账/退款明细的 `app_id` 从 `coupon_template.app_id` 回填；
   - `settle_party_id` 存量统一 `__default__`，不猜真实商家；
   - 旧式核销（无行数据）没有分账，退款只能整单退，不伪造行级归属；
3. **新写入必填**：
   - 分账/退款明细写 `app_id`、`settle_party_id`；`settle_party_id` 非空，默认哨兵 `__default__` 只用于平台券/无商家产品；
   - 商家出资/共担券命中的行必须有真实主体；缺失时不可用/报错，禁止用 `__default__` 兜底；
4. **索引**：
   - `idx_share_party (app_id, settle_party_id, create_time)`：按主体日汇总/查询；
   - `idx_share_tpl_party (template_id, settle_party_id, create_time)`：按模板+主体查退款/对账；
   - `pricing_id` 唯一索引属于 V23（环 2），不在 V22；
5. **唯一键**：不改已有唯一键；新增表用自己的唯一键；
6. **回滚**：新表独立、新列有默认值或可空；关闭开关即可回退新路径，旧路径不受影响；
7. **64 张分表**：不因商家/快照加列；所有主体/快照信息放在单表分账/退款/快照里；
8. **老式链路**：不补行级分账/退款明细，不伪造主体；历史数据只能标 `__default__/未归属`；要按行结算，接入方必须改用 items 核销/退款。

## 8. 数据保留与隐私（最低基线）

- 内核不存姓名、手机号、银行卡、支付流水；只存 `user_id`、`order_no`、`usage_no`、金额、状态；
- 日志不打印敏感明文；审计的 before/after 只包含业务字段；
- 保留策略：业务/审计/财务按租户合同与法规配置；目标支持导出/删除；
- 数据隔离：按 `app_id` 过滤；管理面按角色授权（目标）；
- 不把外部订单/支付/物流的敏感数据复制进内核，只存引用/摘要。
