## 0. 怎么用这份文档

1. 先看 §1 的完成定义和 §2 的当前基线；
2. §3 是环计划：每环的范围、交付物、验收、风险、状态；
3. §4 是依赖关系：哪些环必须串行、哪些可以并行；
4. §5 是验收证据模板：每环结束时必须留下什么；
5. §6 是迁移/兼容/回滚纪律；§7 是风险与触发条件；
6. §8 是明确不做；§9 是待拍板。

**目标态 vs 真实态**：本路线图描述目标态；`docs/STATUS.md` 与代码/测试是真实态。每环开始前用 STATUS 核对“上一环真的完成了吗”，不靠记忆。

## 1. 完成定义

一个环算“完成”，必须同时满足：

| 项 | 要求 |
|---|---|
| 代码 | 功能实现 + 开关/降级；不破坏旧调用方 |
| 迁移 | Flyway 迁移可重复执行；存量数据有回填/默认值；回滚方案明确 |
| 测试 | 先红后绿；单元/集成/兼容/负例覆盖；受影响链路全绿 |
| 文档 | 环文档包（变更说明/可跟跑/代码走读/自测）+ 01~04 相关章节同步 |
| 证据 | 测试报告、curl/SQL 输出、关键日志/指标；不口头声称 |
| STATUS | 债台账更新；完成项关闭；新边界登记 |
| 回滚 | 关闭开关/回退代码后旧路径仍可用 |

**“做了”不等于“完成”**：没有验收证据、没有兼容用例、没有回滚方案，只能算“在途”。

## 3. 环计划

> 环号是内核能力视角，不等同于 V5 实施计划的步骤号；与 V5 的关系见 §4.3。

### 环 1：结算主体可选 + 行级归属

**目标**：多商家租户的优惠能记到正确主体，退款只冲回原主体；没有主体的产品不受影响。

**范围**：

- 订单行可选 `settlePartyId`（或 `merchantId`，命名待定）；不传落 `__default__`；
- 模板可选绑定主体：商家出资/共担券必填，平台券可空/可指定；
- `coupon_share_detail`/`coupon_refund_detail` 增加 `app_id + settle_party_id`；退款单头只加 `app_id`；
- 退款从原分账行复制主体，不读退款请求；
- 范围过滤在门槛/分摊之前：先按主体过滤，再按品类/SKU；
- V22 迁移：加列/索引；存量 `app_id` 从模板回填、`settle_party_id=__default__`；不动 64 张 `coupon_usage`；
- 旧调用方兼容：不传主体仍成功；老式核销/退款不伪造行级归属。

**交付物**：代码 + V22 + 集成测试 + 环文档包 + 01/02/03 同步。

**验收**：

- 一单 A/B 两个主体，分账/退款主体正确；
- A 商家券只命中 A，B 不能帮凑门槛；
- 退 A 只冲 A；平台券跨主体按行拆分应付；
- 旧调用方不传主体仍成功，落 `__default__`；
- 隔离测试：跨租户读写拒绝。

**风险**：

- 存量数据没有真实主体，只能 `__default__`；
- 模板无更新接口，主体不可变只能新建模板；
- 商家主数据/结算账户不在内核，主体 ID 由订单系统提供。

**状态**：○ 未开始。

---

### 环 2：`pricingId` 价格快照

**目标**：试算时冻结价格与分摊；锁券/核销/退款按快照，模板中途变更不影响已下单。

**范围**：

- 快照表 V23：`pricing_id`、appId、userId、orderNo、payload、expiresAt；
- `calculate` 返回 `pricingId`；请求增加 `orderNo`（或等价绑定键）；
- `lock`/`confirm` 可选带 `pricingId`；快照绑定 appId+userId+orderNo+券集合；
- 带 ID 但过期/归属不符/券集合不一致 → fail-closed；不带 ID 旧调用方回退；
- 同单多券可共用一个快照，不能跨订单复用；
- TTL 与锁窗/支付窗口对齐；过期清理；开关默认关灰度；
- 快照包含每行 `settlePartyId`、每券每行分摊。

**交付物**：代码 + V23 + 契约测试 + 环文档包 + 01/02/03 同步。

**验收**：

- 试算后改模板，带 `pricingId` 核销金额不变；
- 过期/跨租户/券集合不一致拒绝；
- 重复核销结果不变；
- 不带 `pricingId` 的旧调用方行为不变；
- 试算请求没有 `orderNo` 时，`pricingId` 不可用（明确报错或返回空）。

**风险**：

- `CalculateRequest` 当前没有 `orderNo`，契约要加字段；
- 快照存储/清理/大小；大订单/多券；
- 快照与占用单的券集合一致性校验。

**状态**：○ 未开始。

---

### 环 3：结算-lite + 租户政策 + 查询/指标

**目标**：财务能按主体看账、客服能查退款、租户能配退款政策；不做打款状态/完整结算引擎。

**范围**：

- V24 新表 `coupon_settle_party_daily_bill`：日期+app_id+主体+模板；正行-退款明细；T+1 幂等；
- 租户退款政策：`open_app_config` 加键（最多退款次数/退券次数/整单退券），缺省回落全局；
- 退款查询只读 API（按 usageNo/refundNo/主体/日期）；内部面用 POST + 管理令牌；
- 最小指标：退款成功/失败/重放/金额；核销/退款业务大盘；
- 旧模板日账单不动；新表独立可回滚。

**交付物**：代码 + V24 + 查询 API + 指标 + 环文档包 + 01/02/03/04 同步。

**验收**：

- 同一模板多主体金额相加 = 模板日账单；
- 跨日退款记退款日，允许负数；
- 两个租户可配不同退款次数/退券次数/整单退券；
- 按订单/退款单能查明细；
- 重跑账单结果不变。

**风险**：

- `confirm_count/refund_count` 语义（行数）；
- 租户配置缓存/审计；
- 查询 API 的权限与租户隔离；
- 老式链路不进账单，财务要知道。

**状态**：○ 未开始。

---

### 环 4：信任边界（RBAC、租户生命周期、API 版本/契约、审计）

**目标**：产品敢接、运营敢用、出事能查。

**范围**：

- 管理面角色：查看/操作/审批；权限矩阵；高风险操作双人复核；
- 租户生命周期：注销/导出/删除/沙箱（至少注销与导出）；
- API 版本/废弃策略/契约测试/未知字段兼容；SDK/沙箱（可选）；
- 审计覆盖矩阵、查询/导出、失败告警/补偿、哈希链校验；
- L73：领券幂等键含 appId（如确认要做严格多租户隔离）。

**验收**：

- 角色矩阵用例；跨租户越权拒绝；
- 注销后数据导出/删除按策略执行；
- 契约测试通过；旧版本兼容；
- 动钱/状态/管理动作审计覆盖；篡改可发现。

**风险**：动 64 张分表（L73）；RBAC 与现有单令牌兼容；注销涉及财务/合规。

**状态**：○ 未开始。

---

### 环 5：风控安全与反作弊

**目标**：异常领券/核销/退款能被拦或告警；假单/套现能留证据、结算前可审核。

**范围**：

- 规则 v1：用户/IP/设备/订单/退款维度；黑名单；预算闸门；
- 风险决策钩子：放行/复核/拒绝；命中日志/回放；
- 反作弊信号：退款率、核销率、券占比、同设备/同用户聚集；风险标签；证据导出；
- 结算 hold/人工审核接口；
- 明确边界：内核只提供券侧证据与约束，订单/支付/物流真实性由外部系统。

**验收**：合成作弊场景被标记；证据可导出；审核可放行/拒绝；规则单测；误报可复盘。

**风险**：误杀、规则维护、外部证据契约。

**状态**：○ 未开始。

---

### 环 6：韧性与容量

**目标**：知道能扛多少、依赖故障时不雪崩、告警能定位。

**范围**：

- SLO/SLI/错误预算；核心链路指标/告警/Runbook；
- 依赖故障演练（Redis/MySQL/MQ）；重试预算；舱壁（按依赖/租户）；
- 压测四场景（领券/试算/锁+核销/退款）；容量基线；调优；
- 回归阈值；压测数据隔离。

**验收**：故障注入下核心链路可控降级；恢复收敛；压测报告 P95/P99/容量表；告警/手册可执行。

**风险**：WSL 资源限制；压测环境与数据；调优影响功能。

**状态**：○ 未开始。

## 4. 依赖与并行

### 4.1 串行依赖

```text
环 1 结算主体/行级归属
   ↓
环 2 pricingId（快照里要带主体）
   ↓
环 3 结算-lite/租户政策/查询
```

- 环 1 是环 2/3 的数据基础；先做主体，再做快照/结算；
- 环 2 的快照必须包含主体，所以不宜先于环 1；
- 环 3 的结算数据依赖环 1 的 `settle_party_id` 和环 2 的价格快照。

### 4.2 可并行

- 环 4 信任边界可在环 1 后开始（不依赖 2/3 的业务数据）；
- 环 5 风控/反作弊可在环 2/3 后开始（需要分账/退款数据）；
- 环 6 韧性/容量可在环 3 后开始（需要稳定场景）。

### 4.3 与 V5 实施计划的关系

- 本路线图是**内核能力视角**，V5 是项目整体步骤；两者不是一套编号；
- V5 的 Phase 2 发放域（异步发放/批量/预算闸门/轻对账）与本路线图的环 5（预算闸门/反作弊）有交集，排期时合并评审；
- 本路线图不替代 V5；每环开始前用 V5/STATUS 核对当前优先级。

## 5. 验收证据模板

每环结束时，必须留下：

| 证据 | 形式 |
|---|---|
| 变更说明 | 环文档包：改了什么、为什么、影响面 |
| 可跟跑 | 环境准备、SQL/curl、真实输出、失败看什么 |
| 代码走读 | 关键方法全文 + 调用链 + 边界 |
| 测试 | 先红后绿记录；单元/集成/兼容/负例；受影响链路全绿 |
| 迁移 | Flyway 版本、回填 SQL、回滚步骤 |
| 观测 | 指标/日志/告警截图或查询输出 |
| 债台账 | STATUS 更新；完成项关闭；新边界登记 |

**没有证据 = 没完成**；不接受“代码写了、应该没问题”。

## 6. 迁移、兼容与回滚纪律

1. **只加不删**：新列可空/有默认值；不删旧列、不改旧语义；
2. **存量默认**：主体 `__default__`，不猜真实商家；老式核销/退款不伪造行级数据；
3. **旧调用方**：字段可选；不带 `pricingId`/主体仍可用；老式路径行为不变；
4. **开关**：新路径默认关或灰度；关闭即回退旧路径；
5. **双跑**：高风险环（结算/退款）先双跑对账，再切主路径；
6. **回滚**：新表独立、新列可空；回滚不删数据，只停用新路径；
7. **64 张分表**：不因主体/快照加列；L73 若要改幂等键，单独评估迁移；
8. **测试**：每环先红后绿；全量回归在合并前跑；已知偶发要单跑复核并记录。

## 7. 风险与触发条件

| 风险 | 影响 | 缓解 | 触发条件 |
|---|---|---|---|
| 存量订单没有真实主体 | 只能 `__default__`，财务无法按商家结算 | 接入方新订单必须传主体；历史订单标注未归属 | 接入方要求历史按商家结算 |
| 模板无更新接口 | 主体/规则变更只能新建模板 | 模板版本化；文档写明不可变 | 运营需要改已发布模板 |
| `CalculateRequest` 无 orderNo | `pricingId` 无法绑定订单 | 契约加 `orderNo`/绑定键；旧调用方不启用 | 启用 `pricingId` |
| 快照存储/清理 | 数据膨胀/过期读 | TTL + 清理任务 + 监控 | 快照量上来 |
| L73 幂等键不含 appId | 跨租户撞键 | 改 64 张分表或 requestId 加前缀 | 严格多租户隔离 |
| 租户政策缓存 | 配置不生效/延迟 | 缓存刷新上界 + 审计 | 多租户政策上线 |
| 反作弊误杀 | 客诉 | 先告警/人工复核，后自动拦截 | 规则命中率/误报率超阈值 |
| 压测影响 WSL | 环境不稳定 | 串行、限资源、压测后清理 | 容量环开始 |
| 全量偶发 | 假红 | 单跑复核；记录 L62 | 全量出现 |

## 8. 明确不做（本路线图周期内）

- 完整结算引擎（结算单/待确认/已确认/已打款/跨期冲正）；
- 打款/发票/税务/三方逐笔对账；
- 商家入驻/招商/店铺/广告/营销页面；
- 多地域双活/7×24 值班/合规认证；
- 万能规则引擎/特殊定价全面开放；
- 每租户独立数据库/独立部署（除非大租户/合规触发）；
- 完整数据仓库/BI/成本分摊。

这些不是“永远不做”，是本周期不做；触发条件见 07 或 STATUS。
