> **状态**：v0.5（2026-10-18，环 3 结算-lite 已支持）。
> **读者**：内核开发、架构师、产品接入方。
> **前置阅读**：[00 定位与能力边界](00-定位与能力边界.md)、[01 内核能力契约](01-内核能力契约.md)、[02 领域模型与数据契约](02-领域模型与数据契约.md)、[03 API 与事件契约](03-API与事件契约.md)。

**状态标记**：✅ 当前可用；◐ 部分；○ 目标态，未实现。

## 0. 怎么读这份文档

1. §1 是租户模型和隔离边界：先确认“谁能看/改谁的数据”；
2. §2 是租户生命周期：开通、启用/停用、轮换密钥、注销；
3. §3 是配置层级：哪些配置放全站、租户、模板；
4. §4 是扩展点清单：产品特殊逻辑从哪进；
5. §5 是扩展的执行与信任边界：失败怎么办、能不能改钱；
6. §6 是产品接入清单；§7 是当前 vs 目标。

**两个词先定义**：

- **租户**：一个接入方，开放面用 `appId` 标识；是数据隔离、配额、配置、审计、结算的边界。
- **扩展点**：标准原语覆盖不了的产品特殊逻辑的受控入口；不是“让产品改内核代码”。

## 1. 多租户模型与隔离

### 1.1 两类接入面

| 面 | 身份 | 隔离 | 用途 |
|---|---|---|---|
| `/open/v1` | appId + HMAC | ✅ 按 appId 隔离数据/配额/配置/审计 | 产品接入（内部产品也走这里） |
| `/api` | 写接口 X-Admin-Token（业务写白名单除外）；**GET 不鉴权** | ❌ 没有 appId，平台运营面 | 平台自己的运营/运维 |

**结论**：需要多租户隔离的产品，一律走 `/open/v1`；`/api` 不能被当作“内部多产品接入面”。

### 1.2 隔离的三个层次

| 层次 | 当前做法 | 目标 |
|---|---|---|
| 逻辑隔离 | 模板/用户券带 `app_id`；**占用单没有 app_id 列**，归属经 `user_coupon.app_id` 追溯；查询/写入做归属校验 | 保持；补更多隔离测试 |
| 数据分片 | `user_coupon`/`coupon_usage` 等按 `user_id` 分 64 表 | 不按租户物理分库；大租户可评估独立库 |
| 资源隔离 | 租户 QPS/日配额、限流、熔断 | 补舱壁（按租户/依赖隔离线程/连接池）、按租户指标 |

**明确不做**：当前不做“每个租户一个数据库/一套部署”；先逻辑隔离 + 分片 + 配额，等大租户/合规要求再评估物理隔离。

### 1.3 隔离的边界与已知缺口

- `OpenApiAuthFilter` 把 appId 写进 `RequestContext`；`AppOwnership` 校验模板/用户券归属；**占用单无 app_id 列**，归属经 `user_coupon.app_id` 追溯；
- `/api` 不携带 appId，`AppOwnership` 视为平台自己；**它没有多租户隔离**；
- `user_coupon` 的领券幂等键是 `uk_idem(user_id, idempotent_key)`，**不含 appId**：不同租户同一 userId+requestId 会撞键（STATUS L73）；严格隔离需要把 appId 纳入幂等键或给 requestId 加租户前缀；
- 管理面只有单一令牌，没有租户级 RBAC；按租户的查看/操作权限是目标态。

## 2. 租户生命周期

### 2.1 状态

| 状态 | 含义 | 当前 |
|---|---|---|
| 开通 | 注册 appId、发放密钥、设配额/联系人 | ✅ `OpenAppService.create` |
| 启用 | 正常调用 | ✅ 默认启用 |
| 停用 | 拒绝请求（6002），数据保留 | ✅ `setStatus` |
| 密钥轮换 | 新旧密钥并存，旧密钥到期失效 | ✅ `rotate`（`POST /api/apps/{appId}/rotate`），旧钥并存默认 168h（不是自动轮换） |
| 注销 | 停用 + 导出 + 删除/匿名化 + 撤销密钥 | ○ 未做 |
| 沙箱 | 独立 appId/环境，合成数据 | ○ 未做 |

### 2.2 开通（当前）

`CreateAppRequest`：`appId`（可空，系统生成）、`appName`、`qpsLimit`（可空）、`dailyQuota`（可空）、`contact`。

- 返回 `AppWithSecret`：appId、appName、**明文 secret 只返回这一次**、status、qpsLimit、dailyQuota；
- 密钥加密存储；视图只返回 `SecretView`（状态/到期时间/是否可用），不返回明文；
- 配额缺省用建表默认值；后续可用租户配置覆盖。

### 2.3 停用与轮换（当前）

- 停用：`setStatus(appId, 0)`；开放面认证拒绝（6002）；数据保留；
- 启用：`setStatus(appId, 1)`；
- 轮换：`rotate` / `POST /api/apps/{appId}/rotate`；生成新 secret，旧 secret 进入 `ROTATING`，到期失效（默认并存 168 小时）；验签时逐个尝试可用 secret；
- **多实例延迟**：认证信息是进程内缓存（TTL 60s、refresh 30s、负缓存 30s），`setStatus`/`rotate` 只失效本实例缓存；其他实例最长约 60 秒仍可能接受旧状态/旧密钥。密钥泄漏后的“立即止血”要配合入口封禁/网关封 IP，不能只靠轮换。

### 2.4 注销（目标）

注销不是“删一行”：

1. 停用应用，撤销全部密钥；
2. 导出该租户的业务数据（模板/券/占用单/分账/退款/账单）；
3. 按合同/法规保留必要审计与财务数据，其余删除或匿名化；
4. 记录注销审计，保留操作人/时间/原因；
5. 处理未终结的占用单/退款（先收场或转人工）。

**当前没有注销接口**；这是目标态，也是合规最低基线的一部分。

## 3. 配置层级

### 3.1 三层配置

| 层 | 载体 | 例子 | 谁改 | 当前 |
|---|---|---|---|---|
| 全站默认 | `application.yml` / 环境变量 | 全局锁窗、全局退款次数、全局开关默认值 | 平台运维 | ✅ |
| 租户配置 | `open_app_config`（按 appId） | QPS/日配额、超时、租户开关（✅）；熔断阈值（◐ 首次创建时读）；预热（○ 已登记未接线）；退款政策（✅ V24 租户级） | 平台运营（`/api` + X-Admin-Token）；租户自助 ○ 目标 | ◐ 部分键 |
| 模板配置 | `coupon_template` | 面额/门槛/范围/叠加/出资/有效期 | 产品/运营 | ✅ |
| 结算主体配置 | ✅ 模板/订单行（V22）+ 主体日账单（V24） | 门店/业务单元、结算周期/方式 | 产品/运营 | ◐ |

### 3.2 优先级与回落

**按配置键分别回落，不是一条统一的“全站默认”**：

| 配置 | 优先级/回落 |
|---|---|
| 租户 QPS/日配额 | 租户配置 → `open_app.qps_limit` / `open_app.daily_quota`（每租户登记行；0=不限） |
| 超时 | 租户 `timeout.default_ms` → 3000ms |
| 开关 | 租户 `switch.*` → 全站 `coupon.switch.*` → 默认 true |
| 模板规则 | 模板显式值（创建时固化/快照） |
| 退款政策 | ✅ V24 租户级：`trade.refund.max_times` / `max_return_times` / `full_return_coupon`，未配置回落全站 50/3/true |

- 写入校验：类型 + 范围（2026-10-18 补：QPS/日配额/预热/熔断三键都有 min/max；`timeout.default_ms` 1200~30000）；负值/越界在写入时拒绝；
- 读取宽容：坏数据回落/钳制，不炸服务；
- 配置变更写审计日志（`open_app_config_log`）；
- 缓存有刷新上界；Redis 故障时不能把“读不到”当成“关闭安全功能”。

**一个例子**：租户 B 的登记行 `qps_limit=50`，没有租户配置 `rate_limit.qps`；则 B 生效 50，而不是某个“全站 QPS=50”。租户 A 配了 `rate_limit.qps=100`，A 生效 100。配了 `abc` 写入拒绝；库里已有坏数据则读取回落/钳制。

### 3.3 哪些配置该放哪

| 配置 | 建议层 | 理由 |
|---|---|---|
| 券面额/门槛/范围/叠加/出资 | 模板 | 产品自己的活动规则 |
| 退款次数/退券次数/整单退券 | 租户（目标）；模板可覆盖未裁定 | 不同租户售后政策不同；模板级粒度待拍板 |
| QPS/日配额/超时/熔断 | 租户 | 资源与稳定性策略 |
| 锁窗 30 分钟 | 全站 | 与订单取消契约对齐，租户改会让契约漂移 |
| 单笔优惠占比 80% | 全站（当前 env；租户可调是目标，未实现） | 资损防线，不能由产品随意放开 |
| 功能开关 | 全站 + 租户 | 出事时按租户/全站降级 |

### 3.4 当前配置词表

- `TenantConfigKey`：`rate_limit.qps`、`rate_limit.daily_quota`、`rate_limit.warmup_seconds`、`timeout.default_ms`、`circuit_breaker.failure_rate`、`circuit_breaker.slow_call_ms`、`circuit_breaker.open_seconds`；除 warmup 未接线外，其余键有类型+范围校验（2026-10-18 补）；
- `rate_limit.warmup_seconds` **已登记但没有按租户的执行点**（只有全站接口维度预热消费全站属性）；`SwitchPlan` 写它不会改变行为；
- `circuit_breaker.*` 只在租户熔断器**首次创建**时读取并缓存；`evictTenant` 没有调用方，改配置要重启；目前只覆盖领券链路的 Redis/MySQL 调用，交易链路没有租户级熔断；
- `SwitchKey`：领券/锁/核销/释放/退款/模板发布/发件箱已接线；`REDIS_DEPENDENCY`、`MESSAGE_CHANNEL` 是 `wired=false`（登记但无执行点）；
- 退款政策已租户级（V24）：三个键走 `open_app_config`，未配置/配错回落全站；多实例缓存最长约 60s。

## 4. 扩展点清单

> 产品特殊逻辑从这里进；标准原语能表达的不走扩展。

### 4.0 扩展公共契约

| 项 | 约定 |
|---|---|
| 注册 | `appId + extensionKey + extensionVersion + required + config`；注册走管理面，写审计 |
| 必需/可选 | `required=true` 的扩展缺失/失败 → 拒绝业务；`required=false` 缺失 → 跳过并记录；**不能静默放行 required** |
| 顺序 | 资格 → 范围 → 定价 → 出资；结算/通知在核销/退款后异步 |
| 幂等 | 每个业务动作生成 `decisionId`/`extensionCallId`；扩展按它幂等；重试不重复产生副作用 |
| 超时 | 同步扩展共享请求 deadline；余额不足返回 5003 或专用码；不无限等待 |
| 错误码 | 扩展失败映射成稳定业务码；不允许把内部异常直接透传 |
| 输入 | 只传最小字段；不传姓名/手机号/支付流水；appId/userId 由内核注入 |
| 输出 | 资格 allow/deny；范围 ID 列表；定价候选金额/参数；出资方案；不能直接改最终金额 |
| 版本 | 扩展契约有版本；新版本先沙箱/灰度；旧版本保留废弃期 |
| 沙箱 | 新扩展先在沙箱 appId 跑通；不能直接上生产 |
| 审计 | 记录 extensionId/version/decisionId/appId/usageNo/pricingId/输入摘要/结果/耗时/错误码 |

### 4.1 资格校验（Eligibility）

| 项 | 说明 |
|---|---|
| 用途 | 判断用户/订单是否有资格用券（会员等级、地区、渠道、白名单等） |
| 输入 | appId、userId、模板/券、订单摘要（最小字段） |
| 输出 | allow / deny + 原因码 |
| 调用时机 | 试算/锁券/核销前；至少试算与核销各一次 |
| 失败语义 | **fail-closed**：超时/异常 → 拒绝用券，不静默放行 |
| 机制 | 内部产品 SPI；外部产品 Webhook |
| 当前 | ○ 未实现 |

### 4.2 范围解析（Scope Resolver）

| 项 | 说明 |
|---|---|
| 用途 | 把产品的品类/门店/会员等级/地区映射成内核范围值 |
| 输入 | appId、商品行/订单摘要 |
| 输出 | 命中的范围 ID 列表 |
| 调用时机 | 试算/核销的 scope 过滤前 |
| 失败语义 | fail-closed |
| 机制 | 内部 SPI/配置；外部 Webhook |
| 当前 | ○ 未实现；当前只用模板 `scopeIds` 静态匹配 |

### 4.3 特殊定价（Pricing Policy）

| 项 | 说明 |
|---|---|
| 用途 | 标准满减/满折表达不了的价格逻辑 |
| 输入 | 券、订单行、上下文 |
| 输出 | 候选优惠金额/参数，**不能直接作为最终金额** |
| 约束 | 内核复核守恒；不能超过行金额/订单金额；不能绕过状态机 |
| 失败语义 | fail-closed；不回退到“另一个价格” |
| 机制 | 第一版不做；确需时白名单 SPI |
| 当前 | ○ 未实现；建议优先用标准策略组合 |

### 4.4 出资解析（Funding Resolver）

| 项 | 说明 |
|---|---|
| 用途 | 多预算账户/多主体出资：平台预算 A、商家预充值 B、共担比例 |
| 输入 | 模板、订单行、结算主体 |
| 输出 | 平台/非平台承担、可选账户 ID |
| 失败语义 | fail-closed；不默认“平台全出” |
| 机制 | 内部 SPI/配置；外部 Webhook |
| 当前 | ○ 未实现；当前只按模板 `budgetOwner/budgetRatio` 固定拆分 |

### 4.5 结算适配（Settlement Adapter）

| 项 | 说明 |
|---|---|
| 用途 | 把结算数据推给产品/财务系统（文件/API/Webhook） |
| 输入 | 日汇总/明细、租户/结算主体/模板 |
| 输出 | 接收确认/失败原因 |
| 调用时机 | T+1 账单生成后，异步 |
| 失败语义 | 重试 + 对账；不阻塞主链路 |
| 机制 | 文件/API/Webhook |
| 当前 | ○ 未实现；只有模板日账单表和定时任务 |

### 4.6 通知（Notification）

| 项 | 说明 |
|---|---|
| 用途 | 发券/锁定/核销/退款/过期事件通知 |
| 输入 | 事件信封（03 §10） |
| 输出 | 消费确认 |
| 调用时机 | 事件产生后，异步 |
| 失败语义 | 至少一次、消费方幂等、重试/死信 |
| 机制 | Webhook/MQ |
| 当前 | ◐ 内部事件；发件箱仅 ISSUED；对外 Webhook ○ |

### 4.7 扩展结果与价格快照

**核心规则**：**试算/锁券时调用的必需扩展，结果要冻结进 `pricingId` 快照；核销读冻结结果，不再重新调用同一个必需扩展。**

为什么：

- 支付成功后的核销是“记账”，不是“重新审批”；如果核销时资格扩展超时，fail-closed 会把已支付订单卡住；
- 核销时重新调用扩展，可能出现“试算 allow、核销 deny”或“试算金额 A、核销金额 B”，价格/资格不一致；
- 扩展结果不冻结，`pricingId` 只冻结了金额，没冻结“为什么允许”，快照不完整。

**当前实现（环 2）**：快照 payload 已冻结 `extensionDecisions[]` 结构与读取路径（`extensionId/version/decisionId/result`），当前为空列表——扩展框架尚未接线。扩展点上线的第一步就是把必需扩展结果写进这里；核销只读它，不重新调用。

快照里的扩展结果：

```json
{
  "extensions": [
    {"extensionKey": "vip-eligibility", "version": 1, "decisionId": "dec-1", "result": "ALLOW"},
    {"extensionKey": "merchant-scope", "version": 1, "decisionId": "dec-2", "result": ["M1"]}
  ]
}
```

- 试算/锁券：调用必需扩展，结果进快照；
- 核销：只校验快照归属/券集合/过期，**不重新调用**必需资格/范围/出资扩展；如需复检，只做确定性、无外部依赖的校验；
- 若核销时发现快照与当前状态不一致（如快照券集合与占用单不一致）→ fail-closed，进异常处置（见 4.8），不静默改价；
- 可选扩展（如通知、非关键标签）可以在核销时异步执行，失败不影响主链路。

### 4.8 支付后核销失败的处置

**问题**：支付已经成功，但核销因为扩展/快照/状态失败，不能简单 `return false` 或走普通释放：

- 占用单停在 `OCCUPYING`，30 分钟后超时收场会把券退回 `USABLE`；
- 用户已经付了钱，券又回可用，可能再次使用 → 双重优惠/资损；
- 订单侧可能已经按“用了券”收了钱。

**正确处置（目标态）**：

1. 核销失败分类：可重试（临时依赖故障）vs 不可重试（快照不一致/必需扩展 deny/数据错误）；
2. 可重试：保持占用单 `OCCUPYING`，**暂停该单的超时释放**（或把 deadline 延长），告警，调用方用同一 `usageNo` 重试；
3. 不可重试：占用单进入**核销异常/待人工处理**状态（新增状态，如 `CONFIRM_EXCEPTION`），券**不得回 `USABLE`**；生成异常单/告警；订单侧走退款/补券/人工裁决；
4. 任何情况下都不允许“核销失败 → 超时释放 → 券回可用 → 再次使用”；
5. 异常处置要审计：usageNo、orderNo、原因、扩展 decisionId、处理人/结果。

> 当前没有 `CONFIRM_EXCEPTION` 状态和暂停超时释放的机制；这是目标态，必须在扩展点上线前完成（见 05 环 2/5）。

### 4.9 Webhook 安全

- URL 白名单/审批：只允许 https、已登记域名；禁止私网/回环/云元数据地址；禁止任意重定向；
- 出站请求带 HMAC 签名、时间戳、nonce；响应校验签名/内容类型/大小上限；
- 超时/重试/退避/死信；按 `extensionCallId` 幂等；
- 密钥按租户/扩展轮换；失败告警；
- 不允许 Webhook 返回“直接改钱”的指令；只接收决策/确认；
- 出站流量走统一代理/白名单，防 SSRF。

### 4.10 扩展调用预算

- 同步扩展共享请求 deadline（`X-Timeout-Ms`）；不要每个扩展各等 500ms 叠成几秒；
- 限制每单扩展数/并发；试算最多 10 券 × 100 行时不能对每行每券都远程调用；
- 余额不足返回 5003 或专用码；不无限重试；
- 按 appId+扩展点熔断；熔断打开时按 required 语义处理（必需 → fail-closed，可选 → 跳过）；
- 批量接口优先于逐行调用。

### 4.11 结算适配契约

- 批次：`batchId`、`schemaVersion`、`checksum`、`itemCount`、`totalAmount`；
- 幂等：按 `batchId` 幂等；重复推送返回同一结果；
- ACK：接收方明确确认；失败返回可重试/不可重试原因；
- 重试/死信：指数退避 + 上限 + 死信；对账兜底；
- 对账：以结算数据与退款明细为准，不以“调用成功”作为账平；
- 范围：老式核销/退款（无行级明细）不进入结算适配。

### 4.12 扩展审计字段

| 字段 | 说明 |
|---|---|
| `extensionId/extensionKey/version` | 哪个扩展、哪个版本 |
| `decisionId/extensionCallId` | 本次决策/调用幂等键 |
| `appId/userId/usageNo/pricingId` | 关联业务 |
| `inputDigest` | 输入摘要（不存敏感明文） |
| `result` | allow/deny/候选/错误码 |
| `amount/settlePartyId` | 涉及金额/主体（如有） |
| `durationMs` | 耗时 |
| `errorCode` | 失败码 |
| `createdAt` | 时间 |

> 动钱扩展的审计与业务同事务或走 outbox；重试要能按 `extensionCallId` 去重。

## 5. 扩展的执行与信任边界

### 5.1 SPI vs Webhook

| 方式 | 适用 | 优点 | 风险/约束 |
|---|---|---|---|
| 内部 SPI | 同一进程内的内部产品 | 低延迟、强类型 | 代码与内核一起部署；版本必须兼容；只给可信内部团队 |
| Webhook/API | 外部租户/跨团队 | 不把外部代码装进内核 | 超时/重试/签名/幂等/熔断；失败必须可降级 |
| 配置 | 标准原语能表达 | 最简单、可审计 | 表达力有限；不能写复杂逻辑 |

**原则**：能用配置就不用扩展；能用 Webhook 就不把外部代码装进内核；SPI 只给可信内部产品。

### 5.2 同步扩展的失败语义

**先分时点**：试算/锁券（支付前）vs 核销（支付后）。

- **试算/锁券（支付前）**：资格/范围/出资 fail-closed，超时/异常 → 拒绝用券；特殊定价 fail-closed，不回退到另一个价格；调用方可以改单/换券后重试；
- **核销（支付后）**：读 `pricingId` 里冻结的扩展结果，**不重新调用必需扩展**；快照不一致/必需结果缺失 → 4007 并进入 `CONFIRM_EXCEPTION`（V23 已实现），**不能走普通释放/超时回 `USABLE`**；不能把“支付后核销失败”当成“调用方重试整个业务”；
- 超时：同步扩展共享请求 deadline，默认 200~500ms/个（按类型配置），总额不能超过请求预算；余额不足返回 5003/专用码；
- 重试：同步扩展不无限重试；支付前由调用方按幂等键重试整个业务；支付后按 4.8；
- 熔断：按 appId+扩展点熔断；必需扩展打开时 fail-closed（支付前拒绝；支付后进异常处置），可选扩展跳过；
- 审计：记录扩展调用（谁、哪个扩展、耗时、结果、错误码），不记录敏感明文。

### 5.3 异步扩展的失败语义

- 通知/结算：至少一次、消费方按事件唯一号幂等（当前 `event_no`，目标 `eventId`）；
- 重试：指数退避 + 上限 + 死信；
- 顺序：不保证；需要顺序的消费方自己按业务键排序；
- 失败不阻塞主链路；失败进死信/人工处理；
- 对账：结算适配失败以对账为准，不以“调用成功”作为账平依据。

### 5.4 扩展不能做什么

- 不能改状态机（锁/核销/退款状态只能走内核）；
- 不能改金额守恒（扩展只提供输入/候选，内核复核后落账）；
- 不能绕过租户隔离/权限；
- 不能直接写内核表；
- 不能把外部 PII/支付数据复制进内核；
- 不能在同步扩展里做长时间阻塞/批量操作；
- 不能把“支付后核销失败”变成普通释放/超时关闭——那会把券退回可用，造成双重优惠（见 4.8）。

### 5.5 三个扩展例子

**例子一：视频产品的“仅 VIP 可用年卡券”**

- 产品在试算/核销前调用资格扩展；
- 扩展查会员系统，返回 `allow` 或 `deny + 原因`；
- 超时/异常 → fail-closed，券不可用，返回“会员资格校验失败”；
- 内核记录扩展调用耗时/结果；不把会员等级复制进券表；
- 产品自己做会员页/活动页，内核只做资格闸门。

**例子二：电商的“门店/商家范围”**

- 产品把订单行映射成 `settlePartyId`，模板绑定商家；
- 范围解析扩展把“门店 ID”映射成内核范围值；失败 → 券不可用；
- 平台券可跨商家，商家出资券只作用于绑定商家；
- 退款按原分账行的商家冲回，不重新解析。

**例子三：银行的“多预算出资”**

- 产品在核销前调用出资解析扩展，返回“平台预算 A 出 70%、商户补贴 B 出 30%”；
- 内核复核比例/守恒后落账；扩展失败 → fail-closed，不允许默认平台全出；
- 结算数据按结算主体汇总，产品/财务系统做打款；
- 内核不直接扣预算账户，账户余额由产品/财务系统维护（除非未来做出资账本）。

## 8. 反模式

- **把 `/api` 当多产品接入面**：没有 appId，租户之间不隔离；
- **让扩展直接返回最终优惠金额**：内核无法保证守恒；
- **同步扩展无限重试/长阻塞**：拖垮主链路；
- **外部产品代码装进内核**：升级/隔离/安全都不可控；
- **所有配置都做成租户可调**：资损防线（占比、锁窗）会被产品放开；
- **为了一个产品把内核改成万能规则引擎**：维护成本失控；
- **把 PII/支付数据复制进内核**：合规与泄露风险；
- **把 SPI 当安全边界**：SPI 与内核同进程，能读内存/绕过接口；它只用于可信内部产品，外部一律 Webhook；
- **支付后核销失败直接释放/超时关闭**：券回可用 + 用户已付款 = 双重优惠；
- **配置写了但没有执行点**：warmup、`wired=false` 开关、首次创建后不再读取的熔断配置，都是“看起来能降级，实际没效果”。

## 9. 开放问题

1. 内部产品的扩展用 SPI 还是也走 Webhook？SPI 的插件版本/加载/隔离怎么做？
2. 扩展点第一版做哪些：资格、范围、出资，还是先只做配置？
3. 租户注销的数据保留/删除策略：按合同还是统一默认？审计保留多久？
4. 沙箱是独立 appId 还是独立环境？合成数据怎么隔离？
5. 结算主体已落模板/订单行（V22）+ 主体日账单（V24）；商家级退款政策已租户级；门店/业务单元、结算时点/方式仍待环 3 后续或环 4。
6. 特殊定价扩展是否永远不做，还是只给白名单大客户？
7. 管理面 RBAC 的角色与审批范围。
8. 是否把领券幂等键改成含 appId（L73），代价是改 64 张分表。
9. 扩展结果进 `pricingId` 快照的 Schema；核销异常态是否新增 `CONFIRM_EXCEPTION`，以及它如何暂停超时释放、如何人工处理。
10. Webhook 的 URL 审批/私网拦截/出站代理/签名/响应校验/密钥轮换具体方案。
11. 结算适配的 `batchId/schemaVersion/checksum/ack` 契约与对账口径。
12. 租户配置热生效：熔断器实例淘汰、warmup 接线、wired=false 开关是否补齐。
13. 租户注销后 appId 是否永久保留、不允许复用；匿名化如何不破坏审计哈希链。
