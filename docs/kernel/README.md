## 1. 五分钟了解

### 1.1 它是什么

- **券资产层**：模板、用户券、占用单、状态机、锁/核/释/退/过期/超时；
- **计价层**：试算、叠加/互斥、门槛/范围、行级分摊、出资拆分；
- **结算数据**：模板日账单、退款明细、按结算主体的日汇总（目标态）；
- **不做**：活动编排、人群、页面、投放、商家入驻、支付/打款/发票/税务。

### 1.2 原语链（10 个）

`建模板/发布` → `发券` → `试算` → `锁券` → `核销` → `释放` → `退款` → `查询` → `事件` → `结算数据`。

每个原语的边界、幂等键、失败语义见 [01 内核能力契约](01-内核能力契约.md) §2/§3；接口字段见 [03 API 与事件契约](03-API与事件契约.md)。

### 1.3 当前 vs 目标

- **目标态**：00~07 描述“应该是什么样”；
- **真实态**：`docs/STATUS.md` 的能力矩阵、债台账、测试基线；
- **一句话现状**：业务链路可演示/可内测（算钱域 + 行级售后 + 结算主体/价格快照）；按 07 的成熟度仍在 **L1**，未达 **L2 试点级**——缺 RBAC、契约测试、SLO、系统化故障演练、容量基线、备份恢复等；主体日汇总/结算、信任边界、扩展框架、风控、韧性/容量还没完成。

### 1.4 三个最关键缺口

1. **主体日汇总/结算**：主体字段已落，但财务还不能按商家/门店看日账、结算时点未建模（05 环 3）；
2. **信任边界**：RBAC、租户生命周期、API 版本/契约、审计覆盖（05 环 4）；
3. **扩展框架/风控**：扩展点未接线、无风控/反作弊与预算闸门（05 环 5）。

### 1.5 不能说什么

- ❌ “我们对标美团/淘宝”——只能同层比能力形状，不能比规模；
- ❌ “我们结算完整”——只有结算数据，不做打款/发票/税务；
- ❌ “我们高并发/高可用”——没有容量基线/SLO；只有有限的 Redis/限流演练证据。

完整“不要这么说”清单见 [06 §9.2](06-能力对照与大厂实践.md#92-不要这么说)。

## 3. 权威顺序

发生冲突时，按这个顺序判断：

1. **代码 + 测试**：实际行为是什么；
2. **`docs/STATUS.md`**：当前能力、债、测试基线、已知缺口；顶部“交接快照”是当前排期的唯一权威；
3. **ADR 的已决策部分**：同一主题上，ADR 已拍板的决策优先于 00~07 的描述；ADR 的“待拍板”项**不是定论**，统一登记到 05 §9 / 各 ADR 文末；
4. **00~07**：目标态设计；其中 01/03 是契约，02 是数据模型；
5. **06**：公开资料对照；只用于解释“行业怎么做/我们差多少”，不作为我们行为的契约；
6. **README**：只是入口/索引，不承载状态；与上述冲突时，以 1~5 为准。

**处理规则**：发现文档与代码不一致，先记录差距（哪一项、影响什么、下一步），把目标改成“已完成”是最后一步，不是第一步。

**开放决策**：ADR-0014/0015/0016 的核心参数（字段名、结算模式、TTL、错误码、迁移期等）仍是待拍板项；在拍板前，相关文档只能写“推荐/条件公式”，不能写成已承诺。

## 4. 维护规则

### 4.1 每次代码变更

- **先红后绿**：先写失败用例并留证据，再修；
- 涉及契约/模型：同步 01/02/03/04 的相关章节；
- 涉及路线图：同步 05 的环状态与验收；
- 改动公共配置/新增必填项：跑受影响既有用例；
- 每次提交后：更新 `docs/STATUS.md`（能力矩阵、债台账、测试基线）+ 追加 `study/工作日志.md`（不入 git）；
- 需要不可逆决策：新增 ADR，不把理由埋在 commit message 里；
- 设计/实现后：至少一轮多视角对抗审查（用户长期要求）。

### 4.2 每次文档变更

- **目标态 vs 真实态分开**：目标态写“应该”，真实态写“当前”；不把计划写成已完成；
- **证据**：涉及金额/状态/并发的承诺，必须能指向测试或代码；没有证据的写成“目标”；
- **来源**：行业事实按 06 §1 的 A/B/C/D 分级；没有来源的写“行业常见/推断”；
- **不跨业务线合并**：美团外卖/闪购/到店、京东零售/到家/科技、阿里淘宝/天猫/支付宝/阿里云是不同业务线，公开材料不能互相证明；
- **版本**：00~07 是 living docs，版本记录在各文档“变更记录”；对外定稿/交付版本按 STATUS 的“定稿类文档出新版本文件”规矩另存。

### 4.3 每个环结束时

按 [05 §5 的验收证据模板](05-路线图与验收.md#5-验收证据模板)执行：变更说明、可跟跑、代码走读、先红后绿测试、迁移/回滚、观测、STATUS 债台账。**没有证据 = 没完成。**

## 5. 怎么验证文档里的说法

**前置**：本机已 `make up`（MySQL/Redis）；应用已 `make run`。跨进程脚本会起多实例/暂停 Redis，**只在本机跑，会改动本地状态**。

```bash
# 全量测试（必须 clean，防增量假绿）
mvn clean test

# 开放面演示/反例（需应用已启动；真实签名 + 幂等 + 错误码）
bash scripts/open-api/demo.sh
bash scripts/open-api/negative.sh

# 集群/配额/降级演练（仅限本机；会起 2 个应用 + Token Server / 暂停 Redis）
CONFIRM=yes bash scripts/cluster/verify-cluster.sh
CONFIRM=yes bash scripts/open-api/drill.sh
```

测试数字、已知偶发、债编号以 `docs/STATUS.md` 为准；脚本输出以实际运行为准，文档不替代证据。

## 6. 术语速查

| 术语 | 一句话 |
|---|---|
| 券能力内核 | 提供券通用能力的共享系统，不负责产品营销 |
| 租户 | 一个接入方，开放面用 `appId` 标识 |
| 结算主体 | 优惠最终算到谁头上、平台和谁结算；可以是商家/门店/业务单元/租户自己 |
| `settlePartyId` | 结算主体的推荐字段名（最终待拍板）；`merchantId` 只作电商场景别名 |
| `__default__` | 没有商家概念/未归属的哨兵主体；不表示真实商家 |
| `merchant_burden` | 历史字段名，表示“非平台出资方承担的成本”，**不是平台应付** |
| `pricingId` | 试算价格快照 ID（环 2 已实施，V23，灰度默认关）；核销带它即按冻结价 |
| 模板 | 一类券的规则 |
| 用户券实例 | 某个用户持有的一张券 |
| 占用单 | 一次“券 × 订单”的合同，幂等与回退的锚点 |
| 分账 | 按商品行记录优惠与出资归属 |
| 退款 | 已核销后的按行冲回 |
| 政策 | 产品可配置的业务规则值 |
| 扩展点 | 标准原语覆盖不了时的受控定制入口 |
| `Lnn` | `docs/STATUS.md` §3 的债编号（如 L73） |
| 环 | 05 的内核能力环（环 1~6），**不是** V5 实施步骤 |

完整术语表见 [00 §9](00-定位与能力边界.md#9-术语表)。
