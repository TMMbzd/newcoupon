# 07 · 信任与韧性能力地图（骨架 v0.1）

> **状态**：骨架，待评审后补细节。
> **目标态与真实态**：本文写“内核应该具备什么、我们准备做到哪一档”，是**目标态**；`docs/STATUS.md` 与代码/测试是**真实态**。两边冲突时，先如实记录差距，不把目标写成已完成。
> **读者**：内核开发、产品接入方、面试/作品集读者。
> **范围**：券能力内核。业务平台（活动编排、页面、投放、商家入驻、营销玩法）不在本文范围。
> **范围依据**：2026-10-18 与用户确认的十个方向——业务需求、身份认证、风控安全、反作弊、权限与隔离、API 安全、审计、韧性、一致性、容量压测；可观测性作为支撑能力，不单列为第十一项。

---

## 0. 这份文档回答什么

1. 一个“能算对钱”的券内核，离“企业敢用”还差哪些能力；
2. 每个能力：目标是什么、内核提供什么机制、我们现在有什么、缺什么、下一步做什么、怎么验收；
3. 成熟度 L1/L2/L3：这个项目应该做到哪一档，哪些只做最低基线；
4. 每个能力挂到哪一环，避免“知道要做但永远排不上”。

本文不重复 00 定位、01 契约、02 领域模型、03 API 契约的细节；它负责**把非业务能力讲全、排序、定验收**。

## 1. 范围与组织方式

### 1.1 十个方向分四层

| 层 | 方向 | 回答的问题 |
|---|---|---|
| 业务正确性 | 1 业务需求、2 一致性 | 算得对吗？状态和钱对得上吗？ |
| 信任边界 | 3 身份认证、4 权限与隔离、5 API 安全、6 审计 | 谁在调用？能看/改什么？请求可信吗？事后查得到吗？ |
| 风险与滥用 | 7 风控安全、8 反作弊 | 会不会被刷、被套、被自产自销？ |
| 运行韧性 | 9 韧性、10 容量压测 | 依赖挂了还能用吗？能扛多少？ |

**支撑能力**：可观测性（指标、日志、告警、Runbook）。它不单列，但 2/3/6/7/8/9/10 都依赖它；没有它，这些能力无法证明、无法运行。

### 1.2 三条原则

- **内核管机制，产品管政策**：内核保证“怎么正确地算、锁、核、退、记账、审计”；产品决定“发给谁、什么力度、怎么营销”。
- **默认拒绝、最小权限、证据留痕**：认证失败拒绝、越权拒绝、状态不合法拒绝；只给必需的权限；动钱和改状态的动作必须有审计。
- **目标态与真实态分开**：本文可以写“应该做”，但每项必须标出“现在有什么/缺什么”，不把计划写成现状。

## 2. 成熟度阶梯

| 档位 | 含义 | 要满足的最低能力 |
|---|---|---|
| **L1 演示级** | 能讲清、能演示业务闭环 | 业务主链路正确；基础测试；基础身份认证；基础审计；文档齐全 |
| **L2 试点级（建议目标）** | 小规模真实租户可以用 | L1 + 管理面角色/权限；API 版本与契约测试；风控规则与反作弊信号；SLO/告警/Runbook；依赖故障演练；容量基线；备份恢复演练；密钥外置；依赖/镜像扫描 |
| **L3 生产级** | 多租户、7×24、可审计 | L2 + 完整 IAM/SSO；WAF/DDoS；渗透测试；多地域/容灾；7×24 值班；合规认证；完整结算/对账；成本分摊 |

**本项目建议**：关键链路做到 **L2**；L3 只选做能讲清楚、能演示的少数项（如一次备份恢复演练、一次依赖故障演练、一次压测基线）。不追求全面 L3。

## 4. 逐项骨架

> 每项先给“目标/现状/差距/下一步/验收/边界”，细节待评审后补。文件引用只列代表性位置，不追求穷举。

### 4.1 业务需求

- **目标**：券模板、发放、锁券、核销、释放、退款、分摊、出资、结算数据全链路可用；产品通过配置表达规则，不改内核。
- **现在有什么**：
  - Phase 1 算钱域：模板五维、叠加互斥、范围券、逐行分摊、出资拆分、日账单；
  - 2026-10-18 行级退款：按行+数量、`refundNo` 幂等、退款单/明细、整单退券政策。
- **缺什么**：
  - `pricingId` 试算价格快照；
  - 结算主体可选（商家/门店/业务单元）；
  - 租户级退款政策（当前全局配置）；
  - 按结算主体的日汇总/结算数据；
  - 产品接入的配置 API/SDK/沙箱。
- **下一步**：
  - 内核 v1 第 1 环：结算主体可选 + 行级归属；
  - 第 2 环：`pricingId`；
  - 第 3 环：政策配置 + 结算数据 + 查询/指标。
- **验收**：端到端场景（建券→试算→锁→核销→部分退→全退→账单）；黄金用例；旧调用方兼容用例。
- **边界**：不做活动编排、页面、投放、商家入驻、营销玩法。

### 4.2 一致性

- **目标**：任何并发、重试、消息重复、依赖故障下，券状态、占用单、分账、退款、账单不出现“半截”或“多算/少算”。
- **现在有什么**：
  - 状态机 + CAS 条件更新；
  - 事务边界、发件箱、幂等键、退款 `refundNo` 幂等；
  - 核销/退款分账守恒校验；
  - T+1 日账单；
  - 锁定超时、过期收场、死锁顺序测试。
- **缺什么**：
  - 试算价格与核销价格的一致性（`pricingId`）；
  - 跨系统/跨日自动对账；
  - 结算主体维度的守恒校验；
  - 对账差异的自动修复边界（只修安全项）。
- **下一步**：快照一致性；订单/支付/券/结算的对账任务；不变量测试集；并发与重复消息回归。
- **验收**：并发锁券/核销/退款用例；重复消息用例；守恒断言；对账差异报告。
- **边界**：不追求跨系统强一致；用“本地事务 + 幂等 + 补偿 + 对账”达成最终一致。

### 4.3 身份认证

- **目标**：开放面知道是哪个应用，管理面知道是谁；拒绝伪造、重放、过期请求。
- **现在有什么**：
  - 开放面 HMAC 签名、时间窗、nonce 防重放、应用密钥；
  - 管理面 `X-Admin-Token`，非 GET 默认拒绝 + 业务写白名单；
  - appId 归属校验。
- **缺什么**：
  - 密钥外置与轮换（当前配置/环境变量）；
  - 管理面更强认证（OAuth2/mTLS/MFA，可选）；
  - 环境隔离（dev/staging/prod 密钥不混用）；
  - 认证失败的可观测与告警。
- **下一步**：密钥管理方案；轮换演练；认证负例测试集；管理面认证增强评估。
- **验收**：篡改 body、错误密钥、过期时间戳、重放 nonce、跨应用访问全部拒绝；轮换后旧密钥按策略失效。
- **边界**：不建完整 IdP/SSO；内部产品可先用管理令牌/网关身份。

### 4.4 权限与隔离

- **目标**：租户之间数据互不可见；管理面按角色授权；高风险操作有审批/双人复核。
- **现在有什么**：
  - appId 归属校验（模板、券、占用单）；
  - 用户维度分片；
  - 租户配置、配额、限流；
  - 管理面单一令牌 + 业务写白名单。
- **缺什么**：
  - 管理面角色（查看/操作/审批）与权限矩阵；
  - 租户生命周期（开通、停用、注销、数据导出/删除）；
  - 隔离的自动化测试；
  - 每租户用量/错误/成本可观测。
- **下一步**：RBAC 最小模型；权限矩阵测试；租户生命周期；隔离测试集。
- **验收**：跨租户读写全部拒绝；角色矩阵用例；注销后数据导出/删除可按策略执行。
- **边界**：不做完整 IAM/SSO；不按租户物理隔离数据库（先逻辑隔离 + 分片）。

### 4.5 API 安全

- **目标**：请求可信、参数合法、不可重放、不可越权、错误不泄露内部信息；版本演进不破坏接入方。
- **现在有什么**：
  - JSR-303 输入校验；
  - HMAC/时间窗/nonce；
  - `X-Client-Token` 幂等；
  - 限流/配额；
  - 统一错误码。
- **缺什么**：
  - API 版本与废弃策略；
  - 契约测试（提供方/消费方）；
  - 请求体大小/字段长度/数组长度上限；
  - 安全响应头、CORS/CSRF（若有浏览器端）；
  - 依赖/镜像扫描、SBOM；
  - SDK/沙箱/错误码手册。
- **下一步**：版本策略；契约测试；输入上限；OWASP 检查清单；安全扫描进 CI。
- **验收**：篡改/重放/越权/注入/超限/错误版本用例；契约测试通过；扫描无高危。
- **边界**：WAF/DDoS 属入口/运维层，不在内核代码内实现。

### 4.6 审计

- **目标**：所有动钱、改状态、管理配置的动作都有“谁、何时、对什么、改前、改后、结果”的记录，且可查询、可验证未被篡改。
- **现在有什么**：
  - `@AuditLog` 切面、异步写入、哈希链；
  - 核销/退款等动钱路径已挂审计；
  - 管理面鉴权失败/配置变更日志（部分）。
- **缺什么**：
  - 审计查询/导出 API；
  - 审计覆盖矩阵（哪些动作必须审计）；
  - 保留策略与归档；
  - 哈希链校验任务；
  - 高风险操作的双人复核/审批。
- **下一步**：查询 API；覆盖矩阵；校验任务；保留策略；双人复核（按需要）。
- **验收**：动钱/状态/管理动作全覆盖；篡改可发现；按订单/用户/时间可查。
- **边界**：审计不是业务分析/BI；不记录无必要的敏感明文。

### 4.7 风控安全

- **目标**：异常领券、核销、退款、预算消耗能被拦截或告警；规则可配置、可解释、可回放。
- **现在有什么**：
  - IP 频控；
  - 核销速率告警（fail-open）；
  - 单笔优惠占比上限；
  - 租户配额/限流；
  - 开关/预案。
- **缺什么**：
  - 用户/设备维度频控；
  - 黑名单/白名单；
  - 预算闸门（活动/租户/模板）；
  - 风险决策钩子（放行/复核/拒绝）；
  - 规则配置与命中日志；
  - 异常告警与大盘。
- **下一步**：规则 v1（用户/IP/设备/订单/退款）；决策钩子；预算闸门；命中日志；告警。
- **验收**：脚本刷券、高频核销、短时间多次退款等场景被拦或告警；规则单测；误杀可回放。
- **边界**：不做完整风控引擎/ML 模型；规则先少而准。

### 4.8 反作弊

- **目标**：识别假单、套现、刷券、自产自销等行为，提供证据、限制和人工审核入口；**不冒充订单/支付/物流的真实性判定**。
- **现在有什么**：
  - 限速/限额；
  - 审计；
  - 退款/核销数据；
  - 结算窗口概念（未实现）。
- **缺什么**：
  - 异常指标（退款率、核销率、券占比、同设备/同用户聚集）；
  - 风险标签与证据导出；
  - 结算前审核/延迟结算；
  - 人工复核工作流；
  - 与订单/支付/物流证据的对接契约。
- **下一步**：信号 v1（规则 + 阈值）；风险标签；证据报告；结算 hold；人工审核接口。
- **验收**：合成作弊场景被标记；证据可导出；审核可放行/拒绝；误报可复盘。
- **边界**：内核只能提供券侧证据与约束；订单真实性、支付流水、物流签收等证据必须来自外部系统；“自产自销”无法靠券平台单独根治。

### 4.9 韧性

- **目标**：Redis/MySQL/MQ 等依赖变慢或挂掉时，核心链路不雪崩；能降级、能恢复、能定位。
- **现在有什么**：
  - 超时/时间预算；
  - 熔断器（Redis/MySQL）；
  - 限流/配额；
  - 开关/三级预案；
  - 发件箱、幂等、重试；
  - 优雅停机（Spring）。
- **缺什么**：
  - SLO/SLI/错误预算；
  - 依赖故障演练（Redis/MySQL/MQ）；
  - 重试预算/退避策略统一；
  - 舱壁（按依赖/租户隔离线程/连接池）；
  - 降级矩阵（哪些功能可降、降级后语义）；
  - Runbook/告警联动。
- **下一步**：SLO；故障演练；重试预算；舱壁；降级矩阵；Runbook。
- **验收**：依赖故障注入下核心链路可用/可控降级；恢复后自动收敛；告警与手册可执行。
- **边界**：不做多地域双活/自动故障转移（L3）。

### 4.10 容量压测

- **目标**：知道四类核心场景能扛多少、瓶颈在哪、扩容/调参依据是什么。
- **现在有什么**：
  - 单元/集成测试；
  - 部分并发测试；
  - 连接池参数外部化；
  - 分片/索引基础。
- **缺什么**：
  - 压测场景与数据模型；
  - SLI（吞吐、P95/P99、错误率）；
  - 容量基线；
  - 瓶颈分析（DB/Redis/锁/GC）；
  - 回归阈值；
  - 压测环境与数据隔离。
- **下一步**：四类场景（领券、试算、锁+核销、退款）压测；容量表；调优；回归阈值。
- **验收**：可重复压测报告；P95/P99/错误率；容量上限与扩容建议；压测后无数据污染。
- **边界**：不做 7×24 容量团队；先做一次基线 + 定期复跑。

### 4.11 可观测性（支撑）

- **目标**：每条关键链路都有指标、日志、告警、Runbook；出问题能在用户投诉前发现。
- **现在有什么**：
  - Micrometer 指标；
  - Actuator；
  - 结构化日志 + traceId；
  - 审计表。
- **缺什么**：
  - 业务大盘（发券/核销/退款/预算/结算）；
  - 告警规则与分级；
  - Runbook；
  - 分布式链路追踪（若多服务）；
  - 日志脱敏/集中收集/保留。
- **下一步**：最小大盘；告警；Runbook；日志治理。
- **验收**：每条关键链路有指标/告警/手册；演练时能按手册定位。
- **边界**：不建完整 APM/可观测平台；先用现有 Micrometer/日志栈。

## 5. 不做专项与最低基线

| 不做的专项 | 为什么现在不做 | 最低基线（仍要做） |
|---|---|---|
| ISO/等保等合规认证 | 组织级投入，学习项目不现实 | 审计、权限、密钥外置、日志脱敏、保留/删除策略 |
| 多地域双活/自动容灾 | 成本高，当前单地域足够 | 数据库备份 + 一次恢复演练；RPO/RTO 写清 |
| 7×24 值班/完整事故体系 | 无真实值班团队 | 告警 + Runbook + 故障复盘模板 |
| 完整结算引擎/打款/发票 | 依赖财务系统与商务合同 | 按结算主体的日汇总/明细，供财务手工结算 |
| 商家入驻/招商/店铺/广告 | 属业务平台，不是内核 | 内核只提供租户/结算主体维度 |
| 完整数据仓库/BI/成本分摊 | 数据量与组织需求未到 | 核心业务指标 + 日账单/结算数据 |
| 完整混沌工程平台 | 工具与时间成本高 | 依赖故障注入 + 手工演练脚本 |
| 万能规则引擎 | 容易变成不可维护的黑盒 | 标准原语 + 配置 + 少量扩展点 |

## 7. 待拍板事项

1. **SLO 目标**：核心链路可用性、P95/P99、错误率目标定多少？需要先有压测基线。
2. **管理面 RBAC 范围**：只做查看/操作两角色，还是一次做到查看/操作/审批三角色？
3. **反作弊边界**：内核只做券侧信号与结算 hold，还是还要接订单/支付/物流证据？后者需要外部契约。
4. **结算模式**：商家自己收款、平台补差额，还是平台代收再结算？影响结算数据字段。
5. **容量目标**：目标租户数、QPS、单租户峰值是多少？决定压测场景与容量表。
6. **最低合规基线**：PII 分类、日志脱敏、保留/删除策略做到什么程度？
7. **可观测性是否单列**：当前作为支撑线；若要做完整大盘/告警体系，可升级为独立方向。
