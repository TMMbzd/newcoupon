# S1 开放接入层与契约 —— 需求清单与设计（2026-10-01）

> **本文档的位置**：ROADMAP V2 的 S1 阶段，工序 = **需求清单 → 设计文档 → 用户批准 → 红绿灯实施**。本文档是前两步的产物，**当前状态：待批准**。
> **上游依据**：[ROADMAP-V2](ROADMAP-V2.md) §2 S1；[对标-大厂能力地图](对标-大厂能力地图-2026-09-30.md) 域⑥（开放平台规范）；[对标-P2实现对照](对标-P2实现对照-2026-09-30.md) 清单 B-9~B-12（治理项挂载点）。
> **一句话**：把现在"谁都能调、userId 随便传、没有配额"的内部接口，变成**一个外部系统能安全接入的开放平台**——接入方拿 appId/AK/SK 签名调用，有幂等、有配额、有审计，并且**为 S2 的流量治理预留好挂载点**。

---

## 1. 起点：现状盘点（V2 的 S1 从哪儿出发）

| 维度 | 现状 | 缺口 |
|---|---|---|
| 入口 | `POST /api/coupons/receive`、`/api/coupons/{lock,confirm,release}`、`GET /api/coupons`、`/api/templates*`（[ReceiveController.java](../src/main/java/com/newcoupon/controller/ReceiveController.java) 等四个 Controller） | 无版本前缀；无"开放面 / 内部面"的区分 |
| 身份 | **只有 IP**（`RiskControlFilter` 频控）与**管理令牌**（`AdminTokenFilter`，拦 `POST /api/templates*`） | **没有接入方身份**：任何人都能调领券/用券接口；无法区分调用方、无法计量、无法审计 |
| 幂等 | 业务层：领券 `requestId`（Redis + DB `uk_idem`）；用券三段 `usageNo` | **契约层无幂等**：接入方超时重试"建券/发布"这类接口会重复执行；重试拿到的响应体与首次不同（`duplicated` 标志位不同） |
| 限流 | IP 固定窗口频控（`IpRateGate`，60 秒 30 次，fail-open） | 无 appId 维度配额（QPS / 日配额）；无接口/链路维度 |
| 错误码 | 1xxx 参数 / 2xxx 模板 / 3xxx 领券 / 4xxx 用券 / 5xxx 系统 / 7xxx 安全（风控 7001、管理 7002） | **无接入域段**（签名/配额/幂等失败无码可归） |
| 审计 | 只有 `AdminTokenFilter` 的一行日志 | 无调用审计（谁在什么时候调了什么、结果如何） |
| 数据归属 | 券/模板**没有归属方**概念 | **越权无防线**：A 应用能读 B 应用的模板与用户的券 |
| 治理 | 分散的开关（`coupon.risk.ip-rate.enabled`、`coupon.outbox.transport`、`coupon.reconcile.auto-repair.mode`） | 无统一开关点；无请求上下文（deadline/资源名）；S2 的限流/熔断**没有可挂的 key** |

**结论**：S1 不是"加个签名"，而是**把入口这一层从"内部调试接口"升级成"开放平台契约"**，同时把 S2 需要的四个挂载点（上下文 / 资源命名 / 开关点 / 依赖包装位）一次性预留出来。

## 2. 决策点（需要你拍板；每条给了推荐与理由）

### D1｜入口形态：双面并存，还是全量改造？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）** | **双面并存**：`/api/**` 保持原样（内部/管理面，走现有鉴权）；新增 `/open/v1/**` 开放面（签名 + 幂等 + 配额）。**Controller 用 `@RequestMapping({"/api/coupons", "/open/v1/coupons"})` 复用同一份代码**，不是两套实现 | 一个 Controller 挂两个前缀，读代码时需注意"哪个前缀走哪条过滤链"（文档与注释写清即可） |
| B | 把 `/api/**` 全量改造成签名制 | **214 例测试与全部演示脚本要重写**；`/api` 是管理面（建券/发布），用签名不合适 |
| C | 开放面独立 Controller（`OpenApiController` 复制 8 个方法委托同一应用服务） | 零风险，但两份协议转换代码会长期漂移（改一个忘一个） |

**推荐 A**。理由：收益最大、破坏为零；且"同一份业务代码、两个契约面"本身就是大厂的常见形态（内部 RPC 面 / 开放 HTTP 面），教学价值高。

### D2｜数据归属：越权防线怎么建？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）** | **券与模板加 `app_id` 冗余列**（写时从模板带过来），查询与操作按 `app_id` 过滤；**分片键仍是 `user_id`** | 要给 64 张 `user_coupon` 分表各加一列（V14 迁移，V9 已有 64 条 `ALTER` 的先例） |
| B | 分片键改成 `hash(appId, userId)` | 彻底物理隔离，但要**重迁 192 张表 + 改所有路由代码**，与"L39 不扩列"同一个理由：伤筋动骨 |
| C | 不加列，靠 `template_id → 模板 → appId` 反查 | 每次领券/核销多一跳；`lock/confirm/release` 只拿得到 `usageNo`，**根本拿不到模板上下文**，这条走不通 |

**推荐 A**。这就是多租户的"共享表 + 租户列"形态（成本最低、业界主流）；B 作为**将来某个租户数据量特别大时**的演进路径写进文档，不现在做。
**注意**：(appId, userId) 才是"一个逻辑用户"——不同应用传相同 userId 是**不同的两个人**，隔离靠 `app_id` 过滤。

### D3｜密钥（SK）如何存储？

| 选项 | 说明 |
|---|---|
| C1 | **只存哈希**（像密码一样）——**不可行**：HMAC 验签需要**原密钥**，服务端必须能拿到明文 |
| B | 明文存 DB | 拖库即全部接入方失守 |
| **A（推荐）** | **AES-GCM 加密存 DB**，主密钥来自环境变量（生产应接 KMS，本地实现讲清边界）；支持**轮换期双密钥共存**（旧密钥仍可验签，到期自动失效） |

**推荐 A**。C1 的"不可行"本身就是最好的教学点：**不是所有敏感数据都能哈希——只有"验证"语义能哈希，"使用"语义必须可解密**。

### D4｜审计落库时机？

| 选项 | 说明 |
|---|---|
| **A（推荐）** | **同步落表**——数据可信、可测、可演示；性能代价（每请求一次 INSERT）登记为 S2/S3 优化项，触发条件写死（S3 压测若审计成为瓶颈则改异步） |
| B | 有界队列 + 单线程批量 flush（大厂常见） | 性能好，但立刻引入"队列满了丢审计怎么办""进程崩了丢审计怎么办"两个新问题——**在 S1 引入，会稀释本阶段的教学主题** |

**推荐 A**。

### D5｜幂等快照缓存什么？

| 选项 | 说明 |
|---|---|
| **A（推荐）** | **缓存完整响应体**：同 `clientToken` 重放 → 返回**同一结果**（字节级一致）+ 响应头 `X-Idempotent-Replay: true` |
| B | 只缓存"参数指纹" | 重放只能回一个"重复请求"错误——**不满足 ROADMAP 验收**"同 clientToken 重放返回同一结果且不重复发券" |

**推荐 A**。

### D6｜开放面包含哪些接口？

| 选项 | 说明 |
|---|---|
| **A（推荐）** | **全链路**：模板创建/发布/查询 + 领券 + 锁券/核销/释放 + 查券包——demo 脚本一条命令跑通"建券→发布→领券→锁券→核销→释放→查券" |
| B | 只有 C 端（领/用/查），建券留在管理面 | 演示要两个脚本（一个带管理令牌、一个带签名），故事不完整 |

**推荐 A**。

|---|---|---|---|

## 4. 详细设计

### 4.1 一次开放面调用穿过什么（总览）

```
客户端（接入方）
  │  Authorization: NC-HMAC-SHA256 Credential=demo-app, Timestamp=..., Nonce=..., Signature=...
  │  X-Client-Token: <写接口必填>      X-Timeout-Ms: 300（可选）
  ▼
[1] TraceIdFilter            （已有）生成/透传 X-Trace-Id → MDC
[2] OpenApiAuthFilter        （新，仅 /open/**）解析头 → 查应用+密钥 → 时间窗 → 验签 → nonce
                              → 填 RequestContext（appId/userId/traceId/deadline/resource）
[3] OpenApiQuotaFilter       （新，仅 /open/**）appId 维度 QPS + 日配额 → 超限 429
[4] OpenApiIdempotentFilter  （新，仅 /open/** 的 POST）X-Client-Token → 占位/快照/重放
[5] RiskControlFilter        （已有）IP 频控（领券路径）
[6] AdminTokenFilter         （已有）管理面 /api/templates POST
[7] Spring MVC → Controller（同一份 Controller，两个前缀映射）
      → AppService（应用服务层：查开关、记资源维度、业务逻辑不变）
      → 领域 / 基础设施（Redis 闸门 / DB / 发件箱）
  ▲
[8] OpenApiAuditRecorder     （新）在 [2] 的 finally 里落审计（成功与失败都落）
```

**为什么拆成三个 Filter 而不是一个大的**：职责单一（认证 / 配额 / 幂等），S2 要替换的只有 [3]（换成限流器家族），S7 要加的只有 [2] 里的一段（风控规则）——**每个都能独立单测**。

### 4.2 数据模型（V14 迁移）

> 约定沿用现有迁移：`utf8mb4` / 每个字段带 COMMENT / 主键与索引起名规范 / 分片表逐张 ALTER。

**① `open_app`（接入方）**

```sql
CREATE TABLE open_app (
  id           BIGINT UNSIGNED AUTO_INCREMENT COMMENT '主键',
  app_id       VARCHAR(32)  NOT NULL COMMENT '接入方标识（对外公开，签名头里明文传）',
  app_name     VARCHAR(128) NOT NULL COMMENT '接入方名称',
  status       TINYINT      NOT NULL DEFAULT 1 COMMENT '0停用 1启用',
  qps_limit    INT          NOT NULL DEFAULT 100 COMMENT '每秒请求上限（0=不限）',
  daily_quota  INT          NOT NULL DEFAULT 1000000 COMMENT '每日请求配额（0=不限）',
  contact      VARCHAR(128) DEFAULT NULL COMMENT '联系人/联系方式（运营用）',
  create_time  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_app_id (app_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='开放平台接入方';
```

**② `open_app_secret`（密钥，多版本共存）**

```sql
CREATE TABLE open_app_secret (
  id            BIGINT UNSIGNED AUTO_INCREMENT COMMENT '主键',
  app_id        VARCHAR(32)  NOT NULL COMMENT '接入方标识',
  secret_cipher VARCHAR(256) NOT NULL COMMENT 'SK 密文（AES-GCM：Base64(iv||ciphertext||tag)）',
  status        TINYINT      NOT NULL DEFAULT 1 COMMENT '0已失效 1当前 2轮换期旧密钥（仍可验签）',
  expire_time   DATETIME     DEFAULT NULL COMMENT '轮换期旧密钥的失效时刻（NULL=不自动失效）',
  create_time   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_app_status (app_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='接入方密钥（多版本共存支撑轮换）';
```

**为什么密钥要单独一张表、还要多版本**：轮换的**本质**是"新旧并存一段时间"——接入方换密钥需要发版/重启，一刀切会让对方在切换瞬间全部请求 401。业界叫**双密钥轮换期**（AWS/GitHub 的 access key 都是这个模型）。`status=2` 的旧密钥在 `expire_time` 之前仍可验签，之后由管理动作（或定时任务）置为 0。

**③ `open_api_audit`（调用审计）**

```sql
CREATE TABLE open_api_audit (
  id          BIGINT UNSIGNED AUTO_INCREMENT COMMENT '主键',
  trace_id    VARCHAR(32)  DEFAULT NULL COMMENT '链路 id（与响应头 X-Trace-Id 同值）',
  app_id      VARCHAR(32)  DEFAULT NULL COMMENT '接入方（验签失败时取头里的声明值，不全信）',
  verified    TINYINT      NOT NULL DEFAULT 0 COMMENT '0未通过验签 1已通过（审计要区分"谁在敲门"和"谁进了门"）',
  resource    VARCHAR(128) DEFAULT NULL COMMENT '资源名 接口[:维度[:值]]，如 receive:template:2001',
  method      VARCHAR(8)   DEFAULT NULL,
  path        VARCHAR(128) DEFAULT NULL,
  http_status INT          DEFAULT NULL COMMENT 'HTTP 状态码',
  code        INT          DEFAULT NULL COMMENT '业务错误码（Result.code）',
  cost_ms     INT          DEFAULT NULL COMMENT '耗时（毫秒）',
  client_ip   VARCHAR(64)  DEFAULT NULL,
  user_id     BIGINT       DEFAULT NULL COMMENT '业务用户（验签通过且解析到才有）',
  create_time DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  KEY idx_app_time (app_id, create_time),
  KEY idx_time (create_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='开放接口调用审计（每次 /open/** 调用一行）';
```

**④ 归属列（越权防线的数据基础）**

```sql
-- 模板表（单表，直接 ALTER）；存量数据回填为 1 = 内置应用/默认租户
ALTER TABLE coupon_template
  ADD COLUMN app_id VARCHAR(32) NOT NULL DEFAULT '1' COMMENT '归属接入方（多租户隔离维度；V14 前存量=1）';

-- 券表（64 张分表逐张 ALTER；写入时从模板冗余，读时不 join）
ALTER TABLE user_coupon_0
  ADD COLUMN app_id VARCHAR(32) NOT NULL DEFAULT '1' COMMENT '归属接入方（写时从模板冗余；查询/操作的隔离维度）';
-- … user_coupon_1 .. user_coupon_63 同（共 64 条）
```

**为什么不给券表加 `(user_id, app_id, status)` 索引**：现有 `idx_user_status(user_id, status)` 已经能把结果集收得很小（一个用户在一个 app 下的券本来就不多），`app_id` 作为**过滤条件**而不是索引前缀足够；贸然加索引会拖慢写入（领券是写热点）。**这一条要写进文档的"取舍"里**：索引不是越多越好，热点写表的索引成本要单独算。

### 4.3 签名协议（S1 的核心，逐字节定死）

**请求头格式**（自定义方案，参考 AWS SigV4 与阿里云 RPC 签名的简化版）：

```
Authorization: NC-HMAC-SHA256 Credential=demo-app, Timestamp=1759280400000, Nonce=abc123, Signature=786b25f5...ec67
```

| 字段 | 说明 |
|---|---|
| `Credential` | appId（明文传，不是秘密——**秘密是 SK**） |
| `Timestamp` | 毫秒时间戳（`System.currentTimeMillis()`） |
| `Nonce` | 一次性随机串，`[A-Za-z0-9_-]{8,64}`（防时间窗内的重放） |
| `Signature` | HMAC-SHA256 的小写十六进制（64 字符） |

**待签串（canonical string）**——7 行，用 `\n` 连接，**最后一行后不加换行**：

```
{HTTP_METHOD}               大写，如 POST
{CanonicalPath}             requestURI 的原始值（不含 query，不做 URL 解码）
{CanonicalQuery}            query 参数按 key 字典序升序、`k=v` 用 `&` 连接；无 query 则为空行
{BodySha256Hex}            请求体的 SHA-256 小写十六进制；无 body 时为 空串的 SHA-256（e3b0c442...b7852b855）
{appId}
{timestamp}
{nonce}
```

**黄金用例（本文档的向量，实施时测试逐字节比对）**：

```
method    = POST
path      = /open/v1/coupons/receive
query     = （无）
body      = {"requestId":"req-1","userId":1001,"templateId":2001}
appId     = demo-app
timestamp = 1759280400000
nonce     = abc123
SK        = demo-secret-key

bodySha256 = 8c4a865ff382d9a73dca622cd8151648183d79839b3ae132f9347caf5f618d38
canonical  = "POST\n/open/v1/coupons/receive\n\n8c4a865f...8d38\ndemo-app\n1759280400000\nabc123"
signature  = 786b25f54b296c7d79cd97b757e92ecaddc299a0576c1260b4315f9f5c4aec67
```

> 上面 3 个值是用 `printf` + `sha256sum` + `openssl dgst -sha256 -hmac` 实算出来的（2026-10-01），不是手写示意——实施时如果算不出同样的值，**是实现错了，不是文档错了**。

**四个"为什么"**（面试会问）：

1. **为什么签 body 的哈希、而不是 body 本身**：① body 可能很大，HMAC 直接吃大输入浪费；② body 里若含换行会与分隔符歧义。哈希把任意长度压成 64 字符定长，**同时保住"完整性"语义**（改一个字节哈希就变）。
2. **为什么 query 要排序**：两端拼接顺序必须**确定性**一致，排序是最简单的确定性方案（Map 遍历顺序在语言间/版本间不保证）。
3. **为什么要有 Timestamp**：没有它，抓到一个合法请求就能**永久重放**。时间窗把重放的可用期压到 ±5 分钟。
4. **为什么有了 Timestamp 还要 Nonce**：时间窗内仍可重放（5 分钟内可以打一万次）。Nonce 是"窗口内一次性的凭证"，服务端记住用过的 nonce → 第二次直接拒。**两者是互补的，不是二选一**。

**Nonce 的写入顺序（一个容易做错的点）**：**必须先验签，再写 nonce**。如果先写 nonce 再验签，攻击者可以用**垃圾签名**刷 nonce 键：① 把 Redis 写爆；② 更糟——**预占**合法客户端接下来要用的 nonce，让正常请求被判"重放"。这就是"检查顺序决定安全性"的典型例子。

**时间窗**：`|now - timestamp| ≤ 300_000 ms`（±5 分钟）。**未来时间也拒**（否则攻击者用一个"很远的未来"的时间戳，配合 nonce 过期时间就能绕过窗口）。nonce 的 Redis TTL 取 **600 秒**（= 2 × 窗口，覆盖窗口边界）。

### 4.4 认证与上下文（`OpenApiAuthFilter`）

**处理顺序**（任一失败即拒绝，**并落审计**）：

| # | 步骤 | 失败码 | HTTP |
|---|---|---|---|
| 1 | 解析 `Authorization` 头（前缀/字段/格式） | 6001 签名头缺失或格式错误 | 401 |
| 2 | 查应用（Caffeine 缓存 + 负缓存，命中 DB 一次） | 6002 应用不存在或已停用 | 401 |
| 3 | 校验时间窗 | 6004 时间戳超出允许窗口 | 401 |
| 4 | 计算 canonical + HMAC，与 `Signature` 比对（**恒定时间比较**，`MessageDigest.isEqual`） | 6003 签名不匹配 | 401 |
| 5 | Redis `SET c:open:nonce:{appId}:{nonce} 1 NX EX 600` | 6005 nonce 已被使用（重放） | 401 |
| 6 | 填充 `RequestContext`，放行 | — | — |

**应用信息的缓存**：复用 P2c 的"三兄弟"经验——Caffeine `refreshAfterWrite`（防击穿）+ 负缓存（防穿透，应用不存在时缓存 60 秒，避免拿随机 appId 打库）+ TTL 抖动（防雪崩）。**密钥轮换后要主动失效缓存**（与模板缓存的 `create/publish` 主动失效同一手法）。

**恒定的比较**：签名字符串用 `MessageDigest.isEqual(byte[], byte[])` 而不是 `String.equals`——后者短路返回，理论上可被时序侧信道逐字节猜签名（与 `AdminTokenFilter` 同款处理，保持一致性）。

**失败响应**：`401 + Result{code, message}`（**沿用统一响应体**，不裸写 JSON——与 `RiskControlFilter` 手写体的历史做法不同，S1 统一收敛到 `Result`，顺带避免 L43 那类乱码问题）。

### 4.5 配额（`OpenApiQuotaFilter`，S1 最小版 + S2 插槽）

| 维度 | 键 | 上限来源 | 窗口 |
|---|---|---|---|
| QPS | `c:open:qps:{appId}:{epochSecond}` | `open_app.qps_limit` | 1 秒（固定窗口，EXPIRE 2 秒） |
| 日配额 | `c:open:quota:{appId}:{yyyyMMdd}` | `open_app.daily_quota` | 自然日（EXPIRE 到次日 00:05，留 5 分钟余量给跨天边界） |

- 超限：HTTP **429** + 码 **6006/6007** + 响应头 `Retry-After`（QPS 超限给 1 秒；日配额超限给到次日 00:00 的秒数）。
- **fail-open**（沿用 `IpRateGate` 的裁决）：Redis 故障时**放行**——配额是可用性防线，不是资损防线（资损由库存闸门 + DB 双防线独立保障）。这条要在文档里重复强调，因为"限流为什么可以 fail-open"是高频面试题。
- **抽象成接口**：`RateLimiter#tryAcquire(key, limit, windowSeconds)`。S1 的实现是 `FixedWindowRateLimiter`；**S2 会实现令牌桶/漏桶/滑动窗口并替换它**（Warm Up 与匀速排队需要"等待时长"这个返回值，接口那时会演进——本阶段不提前设计，避免过度设计）。

**固定窗口的边界问题（要写进文档）**：窗口边界处最多可通过 2× 上限（前一秒末尾 + 这一秒开头）。对"保护系统"够用；对"精确计费"不够——精确限流要用滑动窗口/令牌桶。这是 S2 的正题。

### 4.6 幂等（`OpenApiIdempotentFilter`）

**适用范围**：`/open/**` 且 `POST`（写操作）。`GET` 不参与。

**键与状态机**：

```
key = c:open:idem:{appId}:{clientToken}
  ├─ SET key "PENDING" NX EX 60        ← 第一个请求抢到（处理中窗口 60 秒）
  ├─ 成功 → SET key <快照JSON> EX 86400 ← 完成后覆盖（24 小时可重放）
  └─ SET 失败 → GET key
        ├─ "PENDING"  → 6009 请求处理中，请稍后用同一 clientToken 重试（409）
        └─ 快照       → 比对参数指纹
              ├─ 相同 → 直接回放快照（响应头 X-Idempotent-Replay: true）
              └─ 不同 → 6008 clientToken 重复但参数不一致（409）
```

**快照内容**：`{fingerprint, httpStatus, bodyBase64或原文}`。`fingerprint = SHA-256(canonical string 的后 4 行：bodySha256 + appId + path + method)`——**复用签名协议已经算好的 body 哈希，不重复读 body**。

**哪些结果会被缓存**：HTTP 200 且业务码 **不是** 5xxx（系统繁忙/降级）——5xxx 是"这次没成、下次可能成"，缓存它等于把一次抖动变成 24 小时的确定性失败。**可缓存 vs 不可缓存是一张显式的表**，写进契约文档。

**三层幂等的分工（重要，容易讲混）**：

| 层 | 键 | 保证什么 | 现有/新增 |
|---|---|---|---|
| 契约层 | `X-Client-Token` | **同一个 token 重放返回同一个响应体**（面向接入方的承诺） | S1 新增 |
| 业务层 | `requestId`（领券） | 同一个领取意图**不重复发券**（DB `uk_idem` 终审） | 已有 |
| 资源层 | `usageNo`（用券三段） | 同一张券的锁/核销/释放**单次生效** | 已有 |

三层**不是冗余**：契约层让接入方的重试逻辑简单（拿到什么就是什么）；业务层保证不换 token 也重放不坏数据。**"契约幂等"与"业务幂等"的区别**是 S1 的核心教学点之一。

**技术实现要点（踩坑预警，实施时必看）**：

- 需要包装请求（可重复读 body）与响应（可重复读响应体）：`ContentCachingRequestWrapper` + `ContentCachingResponseWrapper`。
- **坑 1**：`ContentCachingRequestWrapper.getContentAsByteArray()` 在 body **尚未被读取**时返回空数组——必须在算指纹前先读一次（`StreamUtils.copyToByteArray`）再往下传，否则指纹恒为"空 body 的哈希"，**同 token 异参永远判不出来**（这是个会静默失效的坑）。
- **坑 2**：`ContentCachingResponseWrapper` 用完必须 `copyBodyToResponse()`，否则**客户端收到空 body**（响应被包装器吞了）。
- **坑 3**：重放命中时**不调用 `filterChain.doFilter`**，直接把快照写进响应（并 `copyBodyToResponse`）。

### 4.7 数据归属与越权防护

**判定规则（三条，全部在应用服务层实现）**：

1. **模板归属**：模板创建时写入 `app_id`；`publish`/详情查询校验 `template.app_id == ctx.appId`，否则 **6003/越权拒绝**（用 4xxx 还是新码？**裁决：用 6003 的独立码 6011 "无权访问该资源"**，让接入方能区分"签名错"和"越权"）。
2. **券归属**：领券时把模板的 `app_id` 冗余进券行；`lock/confirm/release/myCoupons` 校验券的 `app_id == ctx.appId`。
3. **管理员例外**：管理面（`/api/**`，X-Admin-Token）不受 appId 限制（运营要能看全局）。

**为什么越权检查放在应用服务层而不是 Filter**：Filter 阶段还不知道"要操作的是哪个模板/哪张券"（那要解析 body 甚至查库）。**Filter 管"你是谁"，服务层管"你能碰什么"**——这条边界要写清楚。

**新增错误码**：`6011 无权访问该资源`（HTTP 403）。

### 4.8 三个治理插槽（S1 的低成本、高杠杆部分）

**插槽① 统一请求上下文 `RequestContext`**

```java
public final class RequestContext {          // com.newcoupon.common.context
    private static final ThreadLocal<RequestContext> HOLDER = new ThreadLocal<>();
    // appId（签名得来，可信）/ userId（接入方声明）/ traceId / deadlineMs（超时预算）/
    // actId / templateId / resource / dimensions（如 template:2001）
    public static RequestContext current();            // 未设置时返回 EMPTY（不是 null——调用方少一层判空）
    public static void set(RequestContext ctx);        // Filter 入口设置
    public static void clear();                        // Filter finally 清理（线程池复用必清）
    public static Deadline deadline();                 // S2 用它裁剪下游超时；S1 只透传
    public static void dimension(String k, Object v);  // 补资源维度 → resource = "receive:template:2001"
}
```

- `deadline` 来源：请求头 `X-Timeout-Ms`（正整数，上限 30000）；未带 → `now + 3000ms`（服务端默认预算），并标记 `explicit=false`。
- **S1 只透传不裁剪**（写进日志与审计）；S2 用它给 Redis/DB 调用设超时，S8 之后可以用它做"快到期就别做非必要工作"。

**插槽② 资源命名规范**

```java
@OpenResource("receive")   // 标在 Controller 方法上
```

- 规则：`resource = 接口[:维度[:值]]`，例：`receive`、`receive:template:2001`、`template:publish`。
- **为什么要显式注解而不是从 URL 推导**：限流/熔断/监控/开关要**共用同一套 key**，这套 key 必须稳定——URL 会随版本演进（`/v2`）和重构变化，资源名不能跟着变。
- 维度由应用服务层补（那时才知道 templateId）：`RequestContext.dimension("template", id)`。

**插槽③ 开关点与降级路径**

```java
public interface SwitchService {
    boolean isOn(String key);              // 默认 true；配置 coupon.switch.<key>=false 即关闭
    Map<String, SwitchView> all();         // 读取接口 GET /api/switches 用
}
```

| 开关 | 埋点位置 | 关闭后的行为 |
|---|---|---|
| `receive.enabled` | 领券入口 | 5001 DEGRADED（可重试） |
| `trade.lock/confirm/release.enabled` | 用券三段入口 | 5001 |
| `template.publish.enabled` | 发布入口 | 5001 |
| `redis.dependency.enabled` | Redis 闸门调用前 | 5001（S2 接线熔断降级） |
| `outbox.dispatch.enabled` | 发件箱投递循环 | 跳过本轮投递（消息不丢，恢复后补投） |
| `message.channel.enabled` | 触达外呼（S6） | 跳过外呼，落表标记"未发送" |

- **默认开启**（`isOn` 缺省返回 true）：开关是"出事时关"，不是"上线时开"。
- 读取接口 `GET /api/switches`（管理面）返回：key / 当前值 / 默认值 / 来源（配置文件 or 默认）。
- **S1 实现为"配置读取 + 真实生效"**（不是空壳）：把 `coupon.switch.receive.enabled` 配成 `false`，领券接口真的返回 5001——**可演示**。S2 会把它升级为"开关中心 + 三级预案"。

### 4.9 审计

- **写在哪**：`OpenApiAuditRecorder`，在 `OpenApiAuthFilter` 的 `finally` 里调用（**成功与失败都落**——审计的价值一半在失败调用上：谁在敲门、敲了多少次）。
- **记录什么**：见 §4.2 的表。`verified` 字段区分"验签通过"与"未通过"：未通过时 `app_id` 记录的是头里的**声明值**（不可信，仅用于排查），`user_id` 为空。
- **不记录什么**：请求体与响应体（**可能含用户隐私**；要查内容用 traceId 去应用日志找，而日志有脱敏规范）。这是一个明确的合规取舍。
- 🔶 **同步落表的代价**：每次开放面调用一次 INSERT。S1 接受（简单、可测）；**登记为 S2/S3 优化项**，触发条件：S3 压测显示审计写入成为瓶颈。

### 4.10 错误码 6xxx 段与重试语义

| 码 | 含义 | HTTP | 可重试？ | 接入方应该怎么做 |
|---|---|---|---|---|
| 6001 | 签名头缺失或格式错误 | 401 | ❌ | 检查签名实现 |
| 6002 | 应用不存在或已停用 | 401 | ❌ | 联系平台确认应用状态 |
| 6003 | 签名不匹配 | 401 | ❌ | 检查 SK 与待签串拼接 |
| 6004 | 时间戳超出允许窗口 | 401 | ❌ | 校准本机时钟（NTP） |
| 6005 | nonce 已被使用（重放） | 401 | ❌ | 每次请求用新的 nonce |
| 6006 | QPS 超限 | 429 | ✅ 退避重试 | 按 `Retry-After` 退避 |
| 6007 | 日配额超限 | 429 | ⏳ 次日 | 联系平台提额 |
| 6008 | clientToken 重复但参数不一致 | 409 | ❌ | 换新 token 或复用原参数 |
| 6009 | clientToken 处理中 | 409 | ✅ 短退避重试 | 用**同一 token**重试 |
| 6010 | 不支持的接口版本 | 400 | ❌ | 升级调用方 |
| 6011 | 无权访问该资源（越权） | 403 | ❌ | 检查 appId 与资源归属 |

**为什么这些码要单独一段（6xxx）而不是混进 1xxx**：接入方的重试逻辑、告警规则、监控看板都要按段处理；且 6xxx 表示"**还没进业务**就被拦下"（请求连业务逻辑都没跑到），与 1~5xxx 的"业务内失败"是不同层面的语义——**这个区分对定位问题极其重要**（看到 6xxx 就知道不该查业务日志）。

**错误码段的完整地图**（V14 后）：

```
0      成功
1xxx   参数与通用          1000 参数错误 / 1001 重复请求
2xxx   模板域              2001~2003
3xxx   领券域              3001~3003
4xxx   用券域              4001~4006
5xxx   系统与依赖          5000 系统繁忙 / 5001 降级 / 5002 冻结
6xxx   接入域（S1 新增）    6001~6011（签名/配额/幂等/版本/越权）
7xxx   安全域              7001 风控频控 / 7002 管理令牌
```

## 9. 实施期实测发现（第 1~3 步，2026-10-01）

> 这一节记录**只有真正动手才会暴露**的问题。它们全部由"先写用例、跑红、再实现"的流程抓出——
> 如果没有红灯这一步，前两条会直接被写进代码、然后在某次线上排查中被重新发现。

### 发现 1｜MySQL 往秒精度列写带小数的时刻是**四舍五入**，不是截断

- **现象**：零窗口轮换（"立刻让旧密钥失效"）后，旧密钥**仍然可用**。
- **根因**：`LocalDateTime.now()` = `16:10:04.6` 写进 `DATETIME`（秒精度）被存成 **`16:10:05`**——
  失效时刻被悄悄**推后最多 0.5 秒**。对 7 天的轮换期毫无影响，但对"密钥疑似泄漏、立刻止血"是真实窗口。
- **修法**：列改 `DATETIME(3)`（毫秒精度），并把这条写进迁移脚本注释。
- **教训**：**任何"到点生效/到点失效"的判据，都要先问一句"这个时间列存得下我要的精度吗"**。
  同族的坑在本项目已有先例（容器 UTC 与 JVM +08 差 8 小时，见测试基座的 TZ 注释）——
  时间问题永远不是"逻辑问题"，是"时间源与精度问题"。

### 发现 2｜appId 生成器违反了自己定的 appId 格式

- **现象**：`create_withoutAppId_generatesOne` 报"appId 需满足 `[a-z0-9][a-z0-9-]{2,31}`"。
- **根因**：生成的是 `app_` + 12 位十六进制，而白名单里**没有下划线**——自己写的生成器过不了自己的校验。
- **修法**：生成器改用 `app-` 前缀（连字符在白名单内）。
- **教训**：**"生成规则"和"校验规则"必须是同一份真相**。两者分开写时，测试就是唯一的对账机制——
  这也是为什么"新功能先写用例"不只是流程洁癖：**它就是那个对账机制**。

### 发现 3｜fail-fast 的代价：新增的必填配置会打破**所有没配它的环境**

- **现象**：`P2cAdminAuthTest`（既有用例，与 S1 无关）**4 例全红**：ApplicationContext 加载失败。
- **根因**：新的 `SecretCipher` 在主密钥未配置时**直接抛异常**（fail-fast，这是设计里明确要的），
  但我只在**新测试类**里配了密钥，忘了给 **dev 环境**配默认值——
  也就是说：**照当时的工作区状态，本地 `make run` 会直接启动失败**。
- **修法**：`application-dev.yml` 加 dev 默认密钥（并注明"生产靠 `OPEN_SECRET_MASTER_KEY`"），
  `application.yml` 显式留空 + 注释说明 fail-fast 语义。
- **教训**：**fail-fast 不是免费的**。它的收益是"不静默降级成不安全的默认值"，
  代价是"配置项变成必填，必须同批更新每一套环境（dev / test / prod / 每个测试类的 properties）"。
  本次是**既有回归用例**抓出来的——如果当时只跑新用例就提交，坏的是整个开发环境。
  **改动公共配置/新增必填项后，必须跑一遍受影响的既有用例**（这条已作为流程写进本项目的收尾约定）。

### 发现 4｜"在 Filter 里回写响应头"想当然会生效，实际做不到

- **现象**：设计里打算回写 `X-Request-Resource`（让接入方自助确认"我的请求算到哪个资源"），实测**读到的永远是 null**。
- **根因**：Tomcat 在消息转换器写完响应体时就 flush 了 buffer——**filter chain 返回时响应已经提交**，
  按 Servlet 规范提交后设置响应头无效。同一个方法的日志却打出来了（证明代码执行了、内容也对）。
- **替代方案也堵死**：唯一"业务异常时也会执行"的时机本来就少——Spring 在 handler 抛异常时
  **跳过 postHandle**，而业务失败恰恰最需要看资源名。
- **修法**：放弃响应头，改走**访问日志 + traceId 查询**（审计接口在第 10 步）。
- **教训**：**"响应头能不能设"取决于时机，而时机取决于容器什么时候提交响应**——
  这类问题只能靠实测，读代码推不出来。凡是"想当然能生效"的地方，写一条用例钉住。

### 发现 5｜`@TestInstance(PER_CLASS)` 会让 Spring 上下文**先于 Testcontainers 启动**加载

- **现象**：新加的集成测试类一上来就 `Failed to load ApplicationContext`，根因
  `Mapped port can only be obtained after the container is started`。
- **根因**：PER_CLASS 让测试实例在 `@BeforeAll` **之前**创建，而 Spring 的上下文加载挂在
  "实例后处理"阶段 → 上下文在 Testcontainers 启动容器之前就开始加载 → `@ServiceConnection`
  拿不到映射端口。默认的 PER_METHOD 则把实例创建推迟到容器就绪之后，所以别的测试类都没事。
- **修法**：改回 PER_METHOD，用 `@BeforeEach` + `AtomicBoolean.compareAndSet` 做"只建一次"的幂等初始化。
- **教训**：**测试生命周期扩展之间的顺序是有语义的**——换个生命周期模式，可能悄悄改变了
  "谁先谁后"，而报错信息（端口拿不到）完全不指向真正的原因。

### 发现 6｜IDE 的后台构建会污染 Maven 的增量编译（"改了代码却跑的是旧 class"）

- **现象**：改完代码跑测试，报的却是**上一版**代码的行为；更迷惑的是**编译不报错**——
  明明有一个未导入的注解（`@BeforeEach` 而 import 是 `BeforeAll`）。
- **根因**：VSCode 的 Java 扩展在后台自动构建，产出的 class 文件时间戳比源文件新 →
  **Maven 的增量编译判定"已是最新"直接跳过编译** → surefire 跑的是 IDE 编译出来的旧 class。
- **修法**：跑测试**一律 `mvn clean test`**（本项目的 STATUS 里早就写着"必须 clean（增量假绿）"——
  这次是那条纪律第二次救场：第一次是假绿，这次是**假红**）。
- **教训**：增量编译的前提是"class 只由这一个构建器产生"。**装了 IDE 插件之后这个前提就不成立了**。
