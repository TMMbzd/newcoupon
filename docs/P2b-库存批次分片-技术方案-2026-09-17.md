# P2b 库存批次分片——技术方案（2026-09-17 待批准）

> **工序 v2**：本方案属于"结构性变更"——改 Redis 键结构+守恒式验证粒度+DB 交互模式，影响全局。先文档后实施。
> **依据**：背景 5000 QPS vs DB 热行 ~400 TPS（[腾讯云 618](https://developer.cloud.tencent.com/article/2623908) 实证普通更新 ~400 TPS 饱和）——数学已定，不等压测。
> **设计原则**：守恒式不推翻——从"全量单级验证"升级为"桶内+全局"两级验证。

---

## 1. 问题

当前每次领券事务执行 `UPDATE coupon_template SET issued_count=issued_count+1 WHERE issued_count<total_count`——所有请求打同一行，行锁串行，实测上限约 200~500 TPS。5000 QPS 下数据库先死。

## 2. 方案总图（2026-09-17 用户追问后重写——澄清"桶在哪、怎么并发"）

**桶在 Redis 里，多个桶同时活跃，用户被路由到不同桶并发扣减。**

```
DB（总投放量 100 万，allocated 列跟踪"已分出多少"）
  │ ← 开桶时才碰 DB（每 1 万笔领券发生一次，一次行锁）
  │    UPDATE template SET allocated = allocated + 10000
  │     WHERE id=? AND allocated + 10000 <= total_count
  ▼
Redis（10 个桶同时活跃，各自独立扣减——真正的并发）
  ├── c:stk:{tpl}:0  ← 10000 张 ← userId hash%10==0 的用户
  ├── c:stk:{tpl}:1  ← 10000 张 ← userId hash%10==1 的用户
  ├── ...
  └── c:stk:{tpl}:9  ← 10000 张 ← userId hash%10==9 的用户

某桶扣完 10000 张 → DB 开新桶补货 → 该桶号重置为新额度
```

**改造前后对比**：
```
改造前：5000 QPS → Redis 扣减(1个key) → DB UPDATE(每笔，同一行，~400 TPS 饱和)
改造后：5000 QPS → Redis 扣减(10个key 各~500 QPS，并发) → DB 开桶(每2秒1次)
```

**两层收益分开看**：
- BUCKET_SIZE=10000 解决 **DB 热行**（从每笔碰变成每万笔碰）
- BUCKET_COUNT=10 解决 **Redis 热 key**（从 1 个 key 变 10 个，Redis Cluster 可散不同节点）

## 3. 参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| BUCKET_SIZE | 10000 | 每桶额度——DB 每 1 万笔领券被打扰一次 |
| BUCKET_COUNT | 10 | 最大同时活跃桶数（Redis 单分片热 key 分散） |
| 桶路由 | hash(userId)%BUCKET_COUNT | 同用户同桶（限领计数天然隔离） |

## 5. 桶耗尽切换协议

```
DEDUCT 尝试桶 i → stk_i=0 且其他桶有余 → 切换到下一个非空桶 → 重试（Redis 内完成，无 DB）
DEDUCT 所有活跃桶耗尽 → 返回新码 -10（桶耗尽）
编排层收到 -10 → 调 StockBucketRouter.openBucket() → DB 开新桶
  → 成功：新桶 Redis 键初始化 → 重试 deduct → 成功
  → 失败（allocated+BUCKET_SIZE > total）：真售罄 → cancel sold_out 路径
```

## 6. 与守恒巡检的兼容（2026-09-17 用户追问"全局读数不原子"后重写）

**用户抓到的洞**：跨系统读数（DB allocated + Redis 桶值）不原子——开桶瞬间全局等式必然假性破缺（两种交错都破，见追问原文）。

**解法**：Redis 加 `c:alloc:{tpl}` 键（DB allocated 列的 Redis 镜像），开桶 Lua **原子地同时更新 c:alloc 和建新桶**。全局等式变为纯 Redis 验证：

```
层1（桶内，纯 Redis 原子）：每桶独立验 stk_i + pend_i + dbi_i + void_i ≡ bucket_total_i
层2（全局，纯 Redis 原子）：Σ(各桶四键之和) + c:alloc ≡ total_count
                           ↑ 所有读数都是 Redis 键 → 一条 Lua 原子读 → 无跨系统窗口
```

**跨系统残留（c:alloc vs DB allocated 的镜像一致性）**：处理方式与现有 dbi↔issued_count 完全同构——镜像臂（新鲜重读+两轮确认+修复）：
- c:alloc > DB allocated → 幻影分配（开桶 DB 失败但 Redis 已建）→ 重置 c:alloc + 删幽灵桶
- c:alloc < DB allocated → confirm-lost 同构（DB 分了 Redis 桶没建）→ 补建桶
- 两者相等但某桶内部漂移 → 逐桶修复

REBUILD FORCE：按桶推导（活跃桶 stk=max(0,bucket_total-ic_i)；非活跃桶 stk=0）；c:alloc 重置为 DB allocated 口径。

## 9. 实时性三改进（2026-09-17 用户追问"大厂不可忍受分钟级"后追加）

**改进 1：守恒巡检两轮确认改当场重读**——发现 sum≠total 后不等下一轮 60 秒，当场再读一次 Redis 原子快照确认。发现时间从 120 秒降到毫秒级。防假阳性的原理不变（同一次巡检内的两次独立原子读数，中间过期的慢请求在清扫线后已暴露）。

**改进 2：模板冻结标志（c:fz）提前到 P2b 实施**——DEDUCT Lua 首行加冻结短路键（与售罄牌同款）。巡检确认漂移 → 自动 SET c:fz → 后续请求全部被 Redis 挡住。发现+止血从"120秒+人工"变成"毫秒+自动"。解冻人工（P7 升双人复核）。

**改进 3：假售罄当场修提前到 P2b**——领券发现 -3 且无停流牌 → 当场查 DB → 有货即重建重试。用户零感知。

改进后时间线：发现毫秒/止血毫秒/修复可慢（大厂同样慢修复，但已止血不持续伤害）。

**冻结的假阳性代价有界设计**：当场重读仍破缺 → 冻结。但下一轮巡检（60 秒后）若干净且无修复动作 → 自动解冻——误冻结最多挡 60 秒，把"敢不敢自动冻结"的顾虑压到可接受。真漂移则维持冻结等修复。破坏性修复（FORCE）不因此提速，仍走两轮确认——**分层恢复原则：粗动作快（冻结可逆所以敢快），精修复慢（FORCE 不可逆所以保守）**。
