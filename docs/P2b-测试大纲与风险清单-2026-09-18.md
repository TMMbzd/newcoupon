## 3. 测试总监盲区批判

#### CONC-4 [P1/可能性高] 桶号复用导致代际混合：桶耗尽重开同号时，跨代的在途 pend 令牌、迟到 confirm 与迟到 cancel 全部落到新代账上

- **场景**：§6 镜像处理：『c:alloc > DB allocated → 重置 c:alloc + 删幽灵桶』。两个洞：(1) dbi 镜像的修复从不删除数据（FORCE 有 ZCARD 门+双键 CAS 栅栏兜底），而删桶是破坏性动作，方案未给栅栏——读数与 DEL 之间混入 deduct/confirm 时直接毁账。(2) 方向性判据『>为危险』隐含『DB 永远是幸存真相』：dbi/ic 满足（DB 行是事实源），allocated 不满足——DB 备份恢复/回滚场景里 Redis 才是幸存方，按 doctrine 删 Redis 等于销毁唯一完整的账。另外巡检若沿用 findPublished 列表快照读 allocated（同今日 ic 的做法），高频开桶窗口（5000 QPS 下每 2 秒一次）内 stale allocated < c:alloc 会反复误触『幻影分配』——修复又是删桶。
- **爆炸半径**：一次误判即物理删除活桶：已过闸令牌的归属键消失，allocated 回退腾出的额度被再次分配——同额度两卖；同时全局守恒因两侧同降而保持绿色，零告警。
- **接缝**：新增 c:alloc 镜像臂（对标 dbi↔issued_count 同构 claim）；REBUILD FORCE 的 ZCARD 门+双键栅栏（该修复没有对应物）；P3-⑭ 备份恢复演练；巡检 findPublished 列表快照陈旧窗
- 用例1：**幻影分配臂删除带在途令牌的活桶**
  - 前置：桶5 有 stk=8000、pend=37（用户 DB 事务在途）；模拟误判源：手工 SET c:alloc:{tpl} 为 DB allocated+10000（或恢复一个旧备份使 DB allocated 落后）
  - 步骤：1) 制造上述 c:alloc > DB allocated 状态。2) 触发巡检镜像臂。3) 检查桶5 四键是否被删除、c:alloc 是否被重置。4) 等在途 37 笔中 DB 提交成功者落库后，再开新桶放行同额度。5) 全程跑守恒巡检。
  - 预期：镜像臂修复拒绝在 pend>0 或读数漂移的桶上执行删除（须有 ZCARD 门+双键 CAS 栅栏的同款守卫）；只落人工告警
  - 红信号：c:stk:{tpl}:5/c:pend:{tpl}:5 等四键被 DEL 而 pend 曾为 37；随后同额度再次放行，出现同额度两卖且守恒绿

#### CONS-5 [P0/可能性低] 回滚协议本身超发：丢桶键 + issued_count 未回填，旧代码以冻结 ic 为基线放行全套库存
- **场景**：方案 §8 回滚：『删 V10 列+还原 Gateway 代码；旧键 c:stk:{tpl} 不冲突（桶键带后缀）』。问题：P2b 期间发出的 N 张券，issued_count 冻结不包含它们；回滚后旧 casDeductStock（UPDATE ... - **爆炸半径**：P2b 期间发出的每一张券都成为 DB 账外资产：回滚当刻起可超发 N 张（N=P2b 期间实发数），T+1 才发现、资损已实现。
- **接缝**：V10 迁移与回滚章节；旧 DEDUCT -7→lazyRebuildStock 路径（回滚后首个请求即触发，用冻结 ic 整本重建）；T+1 dailyAudit（最迟次日 03:47 才可能发现）
- **核验**：设计缺陷（docs/P2b-库存批次分片-技术方案-2026-09-17.md:100（§8回滚仅'删V10列+还原Gateway代码'，无任何数据回填步骤）；docs/ROADMAP.md:98（2b改造后'领券不再逐笔UPDATE issued_count'→ic冻结）；旧防线以冻结ic为基线：src/m）
- 用例1：**回滚演练：P2b 发券后还原旧代码**

  - 步骤：1) P2b 形态下发 500 张（ic 保持 0）。2) 按方案回滚：删 V10 列、还原 Gateway 代码（不做任何数据回填——按方案原文）。3) 旧代码继续领券压测直到 STOCK_OUT。4) 终态 COUNT(user_coupon) 与 total 比对。

#### CONS-6 [P1/可能性高] 层2 公式在两份文档里给出两个版本且按字面都不可满足——c:alloc 语义（allocated 镜像）与方程（Σ+c:alloc≡total）矛盾；bucket_total 键不在改动清单
- **场景**：P2b 文档 §6：『c:alloc:{tpl}（DB allocated 列的 Redis 镜像）』且『层2：Σ(各桶四键之和)+c:alloc≡total_count』——代入数字：total=100000，开一桶 10000，Σ=10000，c:alloc=10000，左式=20000≠100000；全分配后左式=200000≠100000。任何桶存在后该式永不成立。ROADMAP 2b 给的另一式『Σ(dbi_i)+DB未分配余量≡total』同样不满足（dbi=50000、未分配=0 时左式 50000）。数学上成立的只能是 Σ(各桶四键)≡c:alloc（配合 allocated≤total 与镜像臂），即 c:alloc 应记『未分配余量』或公式应改写。另外层1右端 bucket_total_i 需要 Redis 键承载，§4 改动清单的键族列表里没有它——实现者只能各自发明。
- **爆炸半径**：按字面实现则任何桶建立后层2永远破缺：巡检永动、deep 每轮空转、ESCALATE 周期性刷屏；被迫『修正』实现又无验收基准，两条岔路（永动 vs 恒绿）都毁掉这层对账。
- **接缝**：StockReconcileService 层1/层2 新巡检；StockBucketRouter 桶元数据；docs 与实现的对齐验收（项目自身纪律：先文档后实施）
- 用例1：**层2公式日一不满足（字面实现）**
  - 前置：total=100000；发布开桶0（bucket_total=10000，c:alloc=10000）；已发 4000 确认 3900、在途 100
  - 步骤：1) 按文档字面实现层2（Σ四键+c:alloc 对比 total）并执行。2) 再等 60s 重复。3) 检查是否进入 suspected→confirmed 流程。
  - 预期：层2在任意稳态（含刚开首桶、全分配、部分发放）都可判定为成立，且实现与文档公式一一对应（文档必须先改对一个）
  - 红信号：层2 Lua 返回 20000 != 100000（或实现侧的反例形态）——刚发布 2 秒就进入两轮确认流程
- 用例2：**bucket_total 键存在性与开桶原子性**

  - 步骤：1) 执行一次开桶。2) KEYS/SCAN 检查 c:btot（或等价桶额度键）是否存在。3) 在开桶 Lua 前后各跑一次层1，观察是否出现短暂不一致。
  - 预期：开桶 Lua 原子写入桶额度键，层1检查不依赖 Java 侧多命令拼装
  - 红信号：查不到桶额度键（实现者各自发明）；或额度键与四键非同 Lua 写入，巡检可观察到中间态

#### CONS-7 [P1/可能性高] -10 桶耗尽惊群无去重协议：并发 openBucket 把 allocated 一次推满、桶位爆炸、DB 热行以惊群形式回潮
- **场景**：§5：『DEDUCT 所有活跃桶耗尽→返回 -10→编排层调 openBucket()』。5000 QPS 下全桶耗尽瞬间会有数千并发 -10 同时进 openBucket，条件 UPDATE allocated+N<=total 只封顶不去重：剩余额度充足时（如 total=100 万、allocated=0），数百次 UPDATE 全部成功——一次『每万笔碰一次 DB』直接变成惊群打满行锁 + 开出远超 BUCKET_COUNT=10 的桶位 + allocated 被推到接近 total（提前锁死全部库存的设计意图）。方案没有任何开桶互斥/去重/CAS-再查机制。同时镜像追赶臂（c:alloc<allocated→补建桶）与在途 openBucket 竞争：追赶臂按 stale 读数补建，可能与正主各建一个。
- **爆炸半径**：热行问题以惊群形式回潮（一次边界打满 DB 行锁）；allocated 被提前推到 total 造成大范围『假性售罄』库存被提前锁死；BUCKET_COUNT 上限被击穿；追赶臂与在途开桶互踩产生持续破缺。
- **接缝**：ReceiveAppService 的 -10 新分支；StockBucketRouter.openBucket（新）；TemplateMapper 条件 UPDATE（复用形态）；c:lock 类 RedisScanLock 既有惯例
- 用例1：**全桶耗尽瞬间的 2000 并发 -10**
  - 前置：total=1000000，allocated=0，首桶 stk=1，bucket-count=10，无开桶去重（按方案字面）
  - 步骤：1) 2000 线程并发领券。2) 断言只有 1 笔成功、其余收到 -10 并各自调用 openBucket。3) 检查 DB allocated 增量、Redis 桶键个数、c:alloc 读数。4) 再跑一轮巡检观察是否出现新破缺。
  - 预期：allocated 恰好 +10000，新桶恰 +1，全部请求要么成功要么收到确定性 STOCK_OUT/限流，无重复开桶
  - 红信号：DB allocated 一步跳到 900000/990000；桶键数量 >10；或追赶臂随后重复建桶产生 c:alloc 与桶内容失配
- 用例2：**追赶臂与在途开桶互踩**
  - 前置：已制造 allocated 领先 c:alloc 30000（三次开桶的 Lua 阶段全部崩溃）
  - 步骤：1) 触发镜像臂（c:alloc<allocated 分支）。2) 同时人工再执行一次 openBucket。3) 检查桶建了几个、c:alloc 终值、层2是否成立。
  - 预期：追赶修复收敛为恰好补建缺失额度且幂等（重复触发不产生额外桶/额度）
  - 红信号：补建后 Σ(桶)!=allocated 或产生 2/3 个重复额度，层2持续破缺进入修复环

#### CONS-8 [P1/可能性中] 三步当场确认的『两次读数不变』前提被清扫的进度效应证伪——危险方向盈余可被窗口内 token 到期吸收成『第二次读数干净』而遭压制
- **场景**：§9/2e-① 的论证『正常流量全是恒等变换 Lua，两次读数不会变，会变的只有非原子管理操作』对 CONSERVATION 不成立：CONSERVATION 自带清扫（ZREMRANGEBYSCORE，时间单调），两次独立 EVAL 相隔 200ms，凡 TTL 落在窗口内的 token 都会让第二次读数变小——这正是三步要抓的清扫破缺类本身。致命组合：桶呈危险盈余 sum>total（如 dbi 被双计 +1），窗口内同桶恰好一个 token 到期被第二次 EVAL 清扫，读数回落为 ==total『干净』→按『第二次干净=管理窗口』规则不升级、不冻结。crash 风暴（漂移高发期）与 token 密集到期高度相关，吸收概率被流量放大。另外步骤(1)『主键新鲜重读 DB total』滤的是 total 侧列表陈旧，而层2破缺的真rhs 变量是 allocated——重读对象没跟上分桶后的方程。
- **爆炸半径**：危险方向漂移恰逢邻 token 到期即被静默放行——2e 引以为傲的『亚秒发现+止血』对超发方向出现概率性失明；另 total 重读对 allocated 侧窗口无过滤力，误升级走 deep 空转。
- **接缝**：2e-① 三步当场确认（依赖『两次读数不变』公理）；CONSERVATION_SCRIPT 的 ZREMRANGEBYSCORE 副作用；c:fz 绑定条件（sum>total）；开桶协议的 DB/Redis 两段窗口
- 用例1：**危险盈余被窗口内 token 到期吸收**
  - 前置：单桶 bucket_total=100，稳态和=100；注入 INCR c:dbi:{tpl}:0（+1，危险）；预置一个 score=now-(TTL-100ms) 的 pend token 使其恰在两次 EVAL 之间到期
  - 步骤：1) 注入上述状态。2) 执行三步确认（步骤2 延迟 200ms 的独立 EVAL）。3) 检查是否升级/deep 是否被提交、c:fz 是否置位。
  - 预期：第二次读数仍判危险（对危险方向的判定不得被同桶对向变化洗白）；c:fz 应被置位
  - 红信号：第二次读数 sum==total 被判『管理窗口』不升级，c:fz 未置位——三步确认放走了超发方向漂移
- 用例2：**步骤(1) 重读对象在桶世界错位**
  - 前置：制造『DB UPDATE allocated 已提交、开桶 Lua 尚未执行』的窗口（可通过断点/延迟注入）
  - 步骤：1) 在开桶事务的 DB 提交与 Lua 之间人为停顿 300ms。2) 期间触发巡检三步确认。3) 观察是否确认漂移/进入 deep。
  - 预期：层2相关漂移的『新鲜重读』覆盖 DB allocated（或证明 RHS 全在 Redis 内无需重读）；模拟开桶窗口不产生确认漂移
  - 红信号：巡检在窗口内确认漂移并提交 deep，且 deep 无能力收敛（反复 DEFERRED/ALARM_ONLY）——过滤步骤对象错误的证据

#### CONS-9 [P1/可能性高] 清扫故意破缺的修复闭环断裂+逐桶告警无风暴聚合——『告警永动』在桶维度重演：REPAIR_LOOP 熔断后 ESCALATE 24/7

#### CONS-10 [P1/可能性中] 管理面与桶协议缺位：total 调小触发 sum>total 自动冻结每 60s 抖动；appendStock/重新上线无桶化补充协议——永久破缺或冻结震荡
- **场景**：两个接缝：(1) 『先 DB 后 Redis 窗口偏差永远良性（sum<total）』的铁律对 total 调小方向不成立：DB 先减 total，Redis Σ 未动，立刻 sum>total——正是 2e 自动冻结绑定的危险方向。若巡检在窗口内三步确认成立（窗口持续存在，第二次读数仍破缺），c:fz 置位；之后每轮『干净即解冻』不可能干净（total 永久小了）→冻结-解冻-再冻结每 60s 抖动，模板间歇停卖。现有 deep 只告警清单里『total 调小』分支（L322）说明这类操作真实存在。(2) appendStock（P5/P7 计划内）只加 total 不开桶：正确形态层2（Σ≡allocated）依旧绿（追加量未分配本就不在 Redis），但字面形态层2永久破缺；且发布 resetAll 改『开首个桶』后，重新上线的 RESET 审计行 before 读数要跨 10 桶逐桶读——非原子撕裂快照写进审计表。
- **爆炸半径**：total 调小后模板每 60s 冻结/解冻抖动，间歇性 -11 拒单；appendStock 加的量永远巡检报破缺；RESET 审计行的前读数不可信——管理面操作全部变成对账噪音源。
- **接缝**：deepReconcile『total 被调小→只告警』分支（L322）；c:maint 维护豁免键；TemplateAppService.publish 的 RESET 审计行（L97-105，单次 conservation 前读数）；2e 自动冻结+60s 自动解冻

#### CHAO-1 [P0/可能性高] 开桶跨系统半完成：DB allocated 已提交、Redis EVAL 未执行——补建与重试竞态双开桶
- **场景**：开桶协议是两段式：先 DB `UPDATE allocated=allocated+N WHERE allocated+N<=total`，再 Redis Lua 原子建桶+INCRBY c:alloc。5000 QPS 下每 ~2 秒开一次桶，任何一次发布/崩溃/网络抖动落在两步之间必然产生撕裂。时序：T1 应用 A 执行 DB UPDATE 提交（allocated=510000）；T2 A 进程 kill -9（或 EVAL 超时）；T3 应用 B 的请求再撞 -10 重新 openBucket，DB 条件更新再次通过（allocated=520000，又一个 10000）；T4 巡检镜像臂也发现 c:alloc(500000)<DB allocated，触发『confirm-lost 同构→补建桶』——T3 与 T4 同时补建。方案 §6 只定义了方向判据，没定义补建与开桶路径之间的互斥与幂等锚（allocated 目标值 CAS 或开桶幂等键）。
- **爆炸半径**：双开桶=Redis 里凭空多出 10000 张可卖额度，DB 侧 allocated 只记了一次——超发 10000 张券（资损）；或 allocated 被反复推进直达 total，模板『纸面售罄』但实际没卖出几张，需人工改 DB 恢复。
- **接缝**：ReceiveAppService 桶耗尽(-10)分支 / 新 StockBucketRouter.openBucket / StockReconcileService 镜像臂 c:alloc<allocated 补建 / 多实例部署 / 优雅停机 30s 窗口(application.yml shutdown: graceful)

#### CHAO-3 [P1/可能性高] -10 惊群：多实例并发开桶，败者立售罄牌，2e-④ 自续期把假牌焊死

#### CHAO-8 [P1/可能性中] noeviction OOM 恰逢开桶 EVAL：全或无失败进入补建重试循环，allocated 被纸面推满；键数×10 逼近 1gb
- **场景**：桶化把状态键从 4 族/模板放大到 4×BUCKET_COUNT+alloc+fz≈42 键/模板（hash tag 同 slot，单分片内存不分散）。maxmemory 1gb+noeviction：内存满时写命令报 OOM——开桶 EVAL 会整段失败（Lua 原子性保住不产生半桶），但 DB UPDATE 已经提交→c:alloc<allocated→补建路径被反复触发。若补建实现里含任何『再走一次 openBucket』的成分（CHAO-1 同源），每次重试 +10000，N 次后 allocated==total 而零桶存活——模板纸面售罄、实际无券可卖，且要人工改 DB 才能恢复。另外 noeviction 下 OOM 命中是随机的：可能先打死 DEDUCT（全站领券 500）也可能先打死开桶，故障形态不稳定。
- **爆炸半径**：热模板被 OOM 循环推满 allocated→功能不可用需人工修 DB；OOM 期间所有领券报错（P1 级可用性事故）；长期看键数增长无回收（桶键无 TTL）逼近容量。
- **接缝**：docker/redis/redis.conf(maxmemory 1gb/noeviction) / 开桶 EVAL / c:alloc<allocated 补建路径 / P3-⑤ 库存余量 per-bucket 指标(尚未实装，OOM 无预警) / 心跳键 c:hb:patrol 也可能被 OOM 拒写→假一级告警
- 用例1：**CHAOS-压内存触发开桶OOM**
  - 前置：测试 Redis 保持 noeviction；用 redis-benchmark 或脚本灌键至接近 maxmemory（或 `CONFIG SET maxmemory` 降到当前用量+10KB）；高流量模板将耗尽最后一桶。
  - 步骤：1) `CONFIG SET maxmemory` 压到临界；2) 触发桶耗尽→openBucket（DB UPDATE 成功，EVAL 返回 OOM command not allowed）；3) 观察编排层异常分类与后续补建行为（等 2 轮巡检）；4) 记录 DB allocated 变化曲线与 c:alloc、桶键状态；5) 释放内存后看是否自愈。

#### SECU-2 [P0/可能性中] 桶内成分平移攻击：stk+1/void-1（或dbi+1/void-1）对倒使两层守恒全绿，超发零检测零痕迹

#### SECU-6 [P1/可能性高] 开桶条件更新无尾桶语义：total%BUCKET_SIZE≠0时尾量永久囚禁，-10假售罄风暴叠加so牌/拆牌自持环
- **场景**：开桶SQL是UPDATE allocated=allocated+10000 WHERE allocated+10000<=total_count——当剩余额度<BUCKET_SIZE（如total=25000，已allocated=20000，剩5000）时UPDATE恒0行，方案§5把openBucket失败一律判『真售罄→cancel sold_out路径』。确定性触发条件：total不能被BUCKET_SIZE整除（业务建券total=88888这类数字很常见）。后果链：尾量5000张永不可发（需人工改配置或total对齐）；且在售罄临界的高并发下，大量请求同时收到-10→全部涌向openBucket→DB行锁串行→只有1个成功其余全判售罄→若实现沿用classifyDeductRejectAndCancel形态会SET c:so=1（售罄牌）→刚开出的新桶被牌挡住→§9改进3『-3且无so才急救』因so已立而不触发→模板假死直到牌TTL（改进4的10秒自续期期间还在被DEDUCT命中续期）。
- **爆炸半径**：尾量部分永久卖不出（面额×尾量=直接少卖损失+客诉『有库存却抢不到』）；竞态窗口内-10风暴反复打DB热行（正是P2b要消灭的那行），最坏情形新桶开出却被售罄牌压住，模板假死到人工介入。
- **接缝**：StockBucketRouter.openBucket（新）、coupon_template.allocated条件更新、CANCEL sold_out的SET so、§9改进3假售罄急救的『无so』前置、改进4售罄牌自续期、ReceiveAppService.handleGateRejected

#### SECU-7 [P1/可能性中] 冻结键c:fz管辖面缺口：只拦DEDUCT不拦开桶/REBUILD/管理面，键自身可被无痕DEL，自动解冻条件可被伪造
- **场景**：方案§9改进2把c:fz并入DEDUCT首行（-11），但止血语义需要覆盖所有『让库存往外走』的路径：(a)编排层收到-10后的openBucket不受fz管辖——冻结期间（sum>total超发止血中）DB allocated仍被推进，配额被烧掉；(b)REBUILD NX（-7懒重建路径）不检查fz——冻结中的模板仍可被重建改写桶键（冻结期间证据被修复动作覆盖）；(c)c:fz是普通键，持Redis权限者DEL即解冻，无任何审计行、无双人复核（P7才做）；(d)自动解冻条件『下一轮巡检干净且无修复动作』——攻击者在冻结后做一次反向篡改让sum==total（伪造干净），60秒后系统自动解冻，攻击恢复——自动解冻信任的『干净』本身是可篡改读数；(e)换桶重试路径中-11/-10若未进handleGateRejected的switch，落入default分支报SYSTEM_ERROR『库存闸门未知返回』（现状代码只认-1/-2/-3/-6/-8）。
- **爆炸半径**：冻结是P2b之后唯一的亚秒级止血手段（DB防线已撤，见SECU-1）——它有任何绕过路径，等于止血开关是纸糊的：超发持续进行而监控面板显示『已冻结』，给人错误的安全感，比没有冻结更危险。
- **接缝**：RedisStockGateway DEDUCT脚本首行（新c:fz检查）、ReceiveAppService.handleGateRejected的switch（无-10/-11分支）、StockBucketRouter.openBucket、StockReconcileService.lazyRebuildStock（NX路径）、巡检自动解冻逻辑（2e）、Redis ACL缺失
- 用例1：**冻结期间开桶与懒重建穿透测试**

#### SECU-8 [P1/可能性低] appendStock/回补与bucket_total、c:alloc的三写者不同步：良性追加触发超发方向冻结误伤，或烧光FORCE熔断额度
- **场景**：appendStock（M6规划，§9已把它列为巡检过滤对象）在P2b后从『改total+INCR c:stk』变成三处联动：DB total+、c:alloc口径、bucket_total_i（若回补当前桶）。两个失效形态：(A)appendStock只加DB total不动Redis——层2 Σ(桶)+c:alloc<total（良性方向，不冻结只deep慢修）→deep走FORCE按桶推导+『c:alloc重置为DB allocated口径』→allocated没变重置无效→层2仍破→连续两轮FORCE→c:frce计数到2，REPAIR_LOOP熔断——此后24小时该模板真漂移也不再自动修复，只剩告警；(B)appendStock直接INCR c:stk:{tpl}:{i}回补当前桶但不同步bucket_total_i——层1变sum>bucket_total（超发方向）→三步确认后自动SET c:fz——一次正常的运营加量把模板冻结，卖券中断（与『冻结只绑危险方向』的设计意图相反，因为回补把危险方向造出来了）。
- **爆炸半径**：形态A：追加库存后模板失去自动修复能力24小时（熔断窗口），期间发生的真实漂移只能人工；形态B：大促运营加量瞬间模板被冻结，卖券中断，运营与研发互相甩锅『我加了库存怎么卖不了』。
- **接缝**：appendStock（M6/L17，含B4清除协议DEL so）、bucket_total元数据、c:alloc、c:frce连续FORCE熔断（24h TTL）、巡检冻结方向判据、REBUILD FORCE按桶推导
- 用例1：**appendStock只动DB烧熔断额度测试**

#### SECU-9 [P2/可能性低] bucket参数伪造/越界打错桶：内部调用面无白名单校验，key拼接与跨桶路由缺少防线
- **场景**：桶号进入两个信任边界：(1)key拼接——c:stk:{tpl}:{bucket}中bucket若来自配置反序列化、管理接口或未来运维工具的参数，无0≤i<BUCKET_COUNT白名单校验与整型校验，越界值（负数、超大数、字符串注入如'0:evil'）会创建幽灵键族——幽灵桶不在巡检清单里（活跃桶列表来自StockBucketRouter元数据），形成永久不可见的账外库存；(2)路由来源——deduct的桶必须由服务端以userId计算，若未来DTO/内部RPC透传bucket字段（性能优化常见借口），上游可指定任意桶，绕过hash路由把流量集中打到余量最多的桶（桶间负载攻击）或打到已被冻结退化的桶。同族：CANCEL/CONFIRM的桶号来自固化cmd，但L3自愈setUserCount与镜像臂修复等『重建命令』的代码路径若重算桶号，与SECU-5的漂移窗口叠加。
- **爆炸半径**：幽灵桶键族游离于两层守恒与巡检清单之外——在里面发生的任何扣减/污染无人看见（审计盲区被人为扩大）；跨桶指定路由可被用于薅羊毛侧的集中突破（配合无登录态现状）。当前为内部调用面，暴露度取决于后续运维工具的实现纪律。
- **接缝**：StockBucketRouter（新，桶号计算与元数据）、RedisStockGateway键构造（stockKey等private方法改带bucket后缀）、活跃桶列表（巡检枚举依据）、未来运维/客服工具（M6）、无鉴权管理面（L12已登记）

#### SECU-10 [P2/可能性高] 痕迹留存不足以事后定责：开桶/删幽灵桶/补建桶/逐桶FORCE无审计承诺，drift表无bucket维度与操作人，Redis无ACL无命令级审计，日审计数读数在分桶后会说谎
- **场景**：现状唯一有完整留档的整本操作是publish的RESET行（TemplateAppService.publish前读五键落表）。P2b新增的高危写操作均无审计承诺：openBucket（allocated+10000——DB配额变更无coupon_event/drift行）、镜像臂的删幽灵桶与补建桶（会被记成REPAIRED——与攻击触发的修复不可区分）、逐桶FORCE（drift表结构无bucket列，多桶模板修复后无法回答『哪个桶被动过』）、c:fz置位/解冻（SECU-7）。环境面：application-dev.yml的Redis无密码无ACL（生产profile同构风险），MySQL root/root123456——直改Redis/DB在应用侧零痕迹，唯一可能的痕迹是drift_log，而成分平移（SECU-2）连drift行都不会产生。另有一处『审计行自身说谎』：StockReconcileService.dailyAudit的AUDIT_FAILED行里stockGateway.remaining(t)与conservation(t)读的是单键c:stk:{tpl}（RedisStockGateway.java:322/267）——分桶后该键恒为null/0，落表的stk/void字段是假数据，误导事后排查方向。
- **爆炸半径**：出现资损事件后无法回答三个基本问题：谁动的（无操作人/来源维度）、动了哪个桶（无bucket维度）、动了多少（部分行读数是假的）——定责不能、复盘不能、同类攻击无法预防。对内部作恶的威慑为零：所有高危动作要么无行、要么伪装成系统自愈。

#### USAB-2 [P1/可能性高] -10/-11 新返回码没有 ErrorCode 映射——冻结期用户收到裸'库存闸门未知返回: -11'
- **场景**：ErrorCode 是给上游做程序化分支的契约（枚举头注释自述），但方案通篇没有为 -10（桶耗尽）和 -11（冻结）定义错误码段位、HTTP 语义与文案。现状 ReceiveAppService.handleGateRejected 的 default 分支是 new BizException(ErrorCode.SYSTEM_ERROR, "库存闸门未知返回: " + d.code())——GlobalExceptionHandler 会把 detail 原样透出。时序：巡检冻结模板→用户 POST 领券→Lua 返回 -11→编排层未接线（或漏改一个实例）→用户看到 code=5000 + 文案'库存闸门未知返回: -11'。上游无法区分'冻结(可重试,≤60s 自动解)'与'售罄(不可重试)'与'真系统错误'，订单侧只能统一兜底成失败页。
- **爆炸半径**：冻结期 100% 请求拿到带内部负数码的 5000；用户在 App 里看到'系统繁忙+一串负数'，客服无法给出重试指引；若有人图省事把 -11 映射成 STOCK_OUT(3001)，则变成谎报售罄，用户直接流失——两种映射都是体验事故。
- **接缝**：ReceiveAppService.handleGateRejected default 分支、ErrorCode 分段规范（3xxx 领券域/5xxx 系统域）、GlobalExceptionHandler detailOf 透传
- 用例1：**冻结期领券返回专用降级码且不泄漏内部负数**
  - 前置：模板已发布有货；Redis SET c:fz:{tplId} 1 模拟冻结
  - 步骤：1) POST /api/receive（userId 未达限领，带新 requestId）；2) 断言响应 code 与 message；3) grep 响应体中的 '-11' 字样；4) DEL c:fz 后重试同一请求
  - 预期：返回专用错误码（如 5xxx FROZEN 段），文案含'活动暂停发放，请稍后重试'类明确指引且可重试语义标注（如 retryable=true）；响应体不含'-11'；解冻后同一请求成功。验收指标：冻结期错误码分布 100% 落在专用码，0 条 SYSTEM_ERROR
  - 红信号：code=5000 且 message 含'库存闸门未知返回: -11'，或 code=3001 谎报售罄
- 用例2：**-10 未接线时不得以未知码透出**
  - 前置：全桶耗尽且 allocated+BUCKET_SIZE<=total（应开桶）；构造编排层未处理 -10 的旧实例（灰度期两版本并存是常态）
  - 步骤：1) 把全部桶打到 stk=0（保留 DB 余量）；2) POST 领券打到旧编排层；3) 检查响应码
  - 预期：旧实例把 -10 兜底为可重试 DEGRADED(5001) 而非 SYSTEM_ERROR+负数码泄漏——即 Lua 返回码集合变更时 default 分支的安全兜底必须先改
  - 红信号：出现'库存闸门未知返回: -10'——灰度期用户撞见内部码泄漏

#### USAB-3 [P1/可能性高] 桶耗尽 -10 无单飞（single-flight）——500 并发同时 openBucket 把热行问题原样搬回来，边界瞬间错误簇
- **场景**：方案 §5：编排层收到 -10 → 调 openBucket() → DB UPDATE allocated。按方案自己的数字：5000 QPS/10 桶=每桶 ~500 QPS，桶在某一毫秒内耗尽，同一瞬间约几十~几百个在途请求全收到 -10。方案没有规定 openBucket 的单飞/去重（对比：-7 路径有'随机退避+条件 SET 只让一个请求重建'的 A2' 设计）。时序：桶 3 余额 1→N 个并发 DEDUCT 只有 1 个成功，其余 -10→全部调 openBucket→模板行 N 并发 UPDATE 行锁排队——这恰是分桶号称消灭的 DB 热行，在每次开桶时刻（5000 QPS 下每 2 秒一次）周期性复发。用户侧：开桶瞬间 P99 从 <200ms 跳到锁等待超时，DB 抖动时整簇请求被分类成 DEGRADED。
- **爆炸半径**：P99<200ms SLA 在每个开桶边界被击穿；5000 QPS 峰值下 DB 行锁排队可能级联成连接池耗尽——'每 2 秒一次'的微事故节拍器。验收指标（方案承诺'桶耗尽切换无丢请求'但无实现路径）：边界 500 并发下非业务错误=0、openBucket 每 iPad 桶代际只执行 1 次。
- **接缝**：ReceiveAppService 的 -7 backoffQuietly 惯例（-10 无对应物）、openBucket 行锁与 casDeductStock 同一行（coupon_template）、TRANSIENT_BURST 熔断计数（会被边界风暴刷高）
- 用例1：**桶边界单飞与零丢单**
  - 前置：BUCKET_SIZE=50，单桶；200 并发压测客户端；开启 SQL 慢日志或 openBucket 指标计数
  - 步骤：1) 预热桶至 stk=1；2) 200 并发 POST 领券（各自新 requestId）；3) 统计：openBucket 的 DB UPDATE 执行次数、响应分类（成功/3001/5000/5001）、P99
  - 预期：UPDATE ... allocated 执行次数=1（或 ≤2 含一次竞态重试）；200 个请求结果=成功+业务拒绝，SYSTEM_ERROR/DEGRADED=0；边界 P99 增量 <100ms。验收指标：切换零丢单、开桶次数=1
  - 红信号：UPDATE 次数 >2，或出现 5000/5001 错误簇，或 P99 超 200ms SLA——雷群未单飞
- 用例2：**开桶时 DB 抖动的降级路径**
  - 前置：toxiproxy（P4 已规划，可提前用）给 MySQL 注 500ms 延迟；桶将耗尽
  - 步骤：1) 打空桶触发 -10→openBucket；2) 收集该窗口用户响应；3) 解除延迟后立即再发一个请求
  - 预期：窗口内用户拿到可重试 DEGRADED（不是 STOCK_OUT 谎报，不是 5000）；DB 恢复后下一个请求开桶成功领到券——用户重试即得
  - 红信号：任何 STOCK_OUT 谎报（DB 只是慢不是没货），或恢复后仍需人工干预

#### USAB-4 [P1/可能性中] 真冻结修好后没有可执行的解冻路径——c:fz 无 TTL、'无修复动作'条件排除自动解、解冻工具 P7 才有
- **场景**：方案自己的恢复逻辑分两支：误冻=下轮干净自动解（≤60s）；真冻=人工。但三处接缝叠加：(a) '下一轮巡检若干净且无修复动作→自动解冻'——真漂移触发 deep FORCE 修复成功后，'有修复动作'成立，即使账已修平也不自动解冻；(b) c:fz 未定义 TTL（对比：so 牌在 2e-④ 有 10s 自续期）——巡检线程死亡/锁持有者僵死（PATROL_LOCK TTL 10 分钟）期间，误冻结也永不清除；(c) 人工解冻的管理面鉴权与客服工具排在 P7，P2e 上线自动冻结到 P7 之间是空窗——SRE 唯一手艺是 redis-cli 直连生产 DEL c:fz，无双人复核、无审计、步骤全凭口口相传。
- **爆炸半径**：一次真冻结（超发方向漂移，正是大促夜最可能发生的那种）修平后模板继续锁死，每多锁一分钟都是直接发券损失；redis-cli 裸删生产键一旦删错模板/删错键无回溯。可用性验收指标应写死：解冻 ≤3 步（查 drift 表确认 REPAIRED→双人复核→一键解冻口），frozen_duration_seconds 有 gauge 且 >5min 告警。
- **接缝**：§9 改进2 自动解冻条件、REBUILD FORCE 修复（clearSoldout 的 B4 清除协议不认识 fz）、PATROL_LOCK/HEARTBEAT 存活机制、P7 管理面解冻口=双人复核
- 用例1：**误冻结自动解冻时长有界**
  - 前置：模板健康，无真实漂移；模拟误冻结：直接 SET c:fz:{tplId} 1（不注入漂移）
  - 步骤：1) SET c:fz；2) 连续触发 conservationCheckAll() 两轮（或等 60s×2 调度）；3) 每轮记录 fz 是否存在与时间戳；4) 期间持续发领券请求
  - 预期：首轮巡检发现干净→自动 DEL fz；从置位到清除 ≤2 个巡检周期（p100 ≤120s）；期间领券返回专用冻结码，解冻后自动恢复成功。验收指标：误冻结用户侧恢复时间 p100 ≤120s，无需任何人工
  - 红信号：fz 持续 >5 分钟未清（巡检活着却不清），或清除后领券仍被拒
- 用例2：**修复完成后解冻 runbook 演练（MTTR 度量）**
  - 前置：注入 sum>total 漂移→三步确认→fz 置位→deep FORCE 修复成功（drift 表有 REPAIRED 行）；两名 SRE + 计时器 + runbook 草稿
  - 步骤：1) 值班 SRE 按告警（'模板冻结'）进场，从告警到确认'修复已完成可解冻'计时；2) 执行解冻（当前形态：查 drift 表→复核→redis-cli DEL c:fz:{tplId}）；3) 验证领券恢复；4) 数步骤并检查是否留审计痕迹
  - 预期：≤3 步且全程有审计记录（谁/何时/为何解冻）；MTTR（告警→恢复）演练值 ≤5 分钟。正式验收：解冻口有带鉴权的管理端点或脚本，双人复核留痕
  - 红信号：步骤 >3（如需要先找文档确认键名、再人工算 hash tag 拼键名），或解冻无任何留痕——runbook 不存在或不可执行
- 用例3：**巡检死亡时冻结不无限期延续**
  - 前置：SET c:fz:{tplId} 1；停掉巡检线程/持有 PATROL_LOCK 不放（模拟实例僵死）
  - 步骤：1) 冻结后停巡检；2) 观察 15 分钟：fz 是否存在、HEARTBEAT EXPIRED 告警是否触发、冻结持续时长指标是否可查；3) 恢复巡检
  - 预期：巡检心跳缺失触发一级告警（现有机制）；告警内容/文档把'巡检死+冻结在'关联为一条处置路径（恢复巡检即自动解）；冻结时长 gauge 可查。方案需补：fz 带兜底 TTL（如 10 分钟自续期，同 so 牌）或至少把该场景写进 runbook
  - 红信号：fz 无 TTL 且巡检死亡期间无任何告警把两者关联——冻结无限期，只有用户投诉才发现

#### USAB-5 [P1/可能性中] resetAll 改'开首桶'但没说清理旧桶键——重新上线残留键让 Σ>total 落进危险方向，发布即自动冻结
- **场景**：现 resetAll 只 SET/DEL 四个无桶键（连发 4 条命令，方案 §9 自己点名'非原子管理窗口'）。分桶后改为'开首个桶'，但全文未规定：重新发布（下线后再上线，现有 publish 路径的正当场景——囚禁告警注释里就有'重新上线未走协议？'前科）时，上一生命周期残留的 bucket 1..9 四族键与 c:alloc 是否清除。时序：发布→发放多桶→OFFLINE（offline cancel 吸收存量）→再 publish→新口径 total/ic 从 DB 读，但 Redis 里旧桶 dbi_i/void_i 残留→层2 Σ(桶)+c:alloc>total→'危险方向'→三步确认（读数稳定，滤不掉）→自动冻结。新模板上线第一秒就被自己的守恒巡检锁死。
- **爆炸半径**：重新上线的模板（运营补货/活动返场的标准动作）对用户表现为'上线即不可领'，且冻结告警指向守恒破缺而非真问题——SRE 排障方向被带偏（先查超发，实际是残留键）。
- **接缝**：TemplateAppService.publish→resetAll、CANCEL(OFFLINE) 的 void 吸收、层2 全局守恒与自动冻结方向判定、c:alloc 重置口径（REBUILD FORCE 段落提了，resetAll 段落没提）
- 用例1：**重新发布后旧桶键清理与层2守恒绿**
  - 前置：total=1000；发布→跨多桶健康发放 300 张→OFFLINE→Redis 中保留全部桶键现状（不清库）
  - 步骤：1) 再次调用 publish（重新上线）；2) SCAN c:stk/c:pend/c:dbi/c:void/c:alloc 的 {tplId} 全部桶键，记录；3) 触发巡检 checkOne 两轮；4) GET c:fz；5) 立即领券一次
  - 预期：旧生命周期桶键全部消失（或按文档化口径归零并入 c:alloc 重置）；层2 Σ+alloc≡total 绿；c:fz 不存在；首个领券成功。验收指标：再发布场景冻结次数=0
  - 红信号：Σ>total 破缺确认、c:fz 被置位、或领券被 -11 拒绝——残留键把新发布锁死

#### USAB-6 [P1/可能性中] 假售罄急救的'有货'判定口径未定义——错用 issued_count 旧口径会把单键 REBUILD 和桶键并存，修复路径自己触发冻结
- **场景**：§9 改进3：'领券发现 -3 且无停流牌→当场查 DB→有货即重建重试'。分桶后'查 DB 有货'有两个候选口径：旧 issued_count<total_count（ic 滞后，见 USAB-1）与新 allocated<total。若急救路径沿用旧口径/旧 REBUILD（现有 lazyRebuildStock 走 REBUILD·NX 操作无桶键），时序：全桶真耗尽（allocated<total，应开桶）→用户撞 -3→急救查 ic<total 判'有货'→执行单键 REBUILD 写出 c:stk:{tpl} 旧键→旧键不在任何桶的守恒式里但 remaining()/部分工具还读它→层2 口径混乱；更糟方向：真售罄（allocated=total）被 ic 滞后误判'有货'→重建出一个 Redis 有货、DB 无货的假库存→过闸→DB 双防线逐笔拒绝→N1 自持环回加/拒绝震荡。
- **爆炸半径**：急救机制在最需要它的售罄边界（大促收尾时刻）给出两种坏结果：假库存引发 DB 拒绝风暴（用户反复'系统繁忙'），或新旧键并存让巡检口径分裂。用户侧'零感知修复'承诺落空成'零感知加伤'。

- 用例1：**真售罄态急救不误判有货**
  - 前置：allocated=total（DB 无余量），全部桶 stk=0，c:so 不存在；drift 表清空
  - 步骤：1) POST 领券；2) 断言响应=3001 STOCK_OUT；3) SCAN 检查 c:stk:{tplId}（无桶旧键）是否被创建；4) 检查 DB 是否有开桶 UPDATE 痕迹
  - 预期：返回 3001；无桶旧键被创建；无开桶尝试；后续请求稳定 3001（不震荡）。验收指标：真售罄误触发急救率=0
  - 红信号：创建了 c:stk:{tplId} 单键，或响应在 3001/5001 间震荡（重建→DB 拒→取消→再重建的自持环签名）
- 用例2：**需开桶态急救走开桶且用户零感知**
  - 前置：allocated+BUCKET_SIZE<=total，全桶空，无 so
  - 步骤：1) POST 领券（带耗时打点）；2) 断言最终 HTTP 结果与该请求 RT；3) 检查 Redis 新桶键已建立
  - 预期：单次请求内完成'识别-3→判 allocated→开桶→重试'链路并返回成功券；RT 增量 <200ms（SLA 内）；新桶四键就位且守恒绿。验收指标：急救路径用户可见错误率=0、P99 增量<200ms
  - 红信号：返回 5001/5000 让用户自己重试（'零感知'承诺失败），或开桶成功但层1/层2巡检随后报破缺

#### USAB-7 [P2/可能性高] 分桶(2b)先行、每桶水位监控(2e-⑤)后到——窗口期桶级盲飞，且 dailyAudit 的 remaining() 还在读无桶旧键
- **场景**：ROADMAP 顺序 2b→2c→2d→2e：桶键上线到 per-bucket gauge 交付之间是观测真空。同时现有代码 dailyAudit 落 DriftEvent 时调 stockGateway.remaining(t.getId())——读 c:stk:{tpl} 无桶键，分桶后恒 null；审计表 stk 列从此是空/陈旧值。SRE 视角的完整断链：某桶被清/漂移时，(a) 无 gauge 看不到是哪个桶；(b) drift 表 stk 列误导（显示 null 或上辈子的单键值）；(c) 层1逐桶告警若只报模板不报桶号，排障第一步就卡住。'每桶水位在监控里可见'是分桶方案的可验收承诺，但方案正文只在 2e-⑤ 一行带过。

- **接缝**：RedisStockGateway.remaining()/confirmedCount()（无桶读数）、dailyAudit DriftEvent、2e-⑤ per-bucket gauge、开桶水位低告警（缺位）
- 用例1：**打光单桶可观测且可定位**
  - 前置：分桶版运行（BUCKET_COUNT=10）；Prometheus 可达；模拟 2e 未完成的窗口期（无 gauge）与完成后（有 gauge）两种形态
  - 步骤：1) 把桶 3 的 c:stk:{tplId}:3 置 0（其余桶有货）；2) T+5s 查询 per-bucket 指标（或窗口期模拟：执行 dailyAudit 后查 drift 表 stk 列）；3) 触发层1巡检看告警内容
  - 预期：有 gauge 形态：指标 5 秒内反映桶 3=0 且其余桶不变；层1 告警/drift 行包含 bucket=3 维度；drift 表不再出现来自无桶键的 null stk。窗口期形态（红，作为基线证据留存）：无任何渠道能区分是哪个桶
  - 红信号：指标不存在或值不变；层1 告警只有 templateId 没有桶号；drift 表 stk 列为 null——SRE 拿到告警后第一步就得手工 SCAN

#### USAB-8 [P2/可能性低] bucket_count 是实例本地 yml——滚动发布两代配置并存期间路由分裂，假全局漂移告警+cancel 跨桶落空
- **场景**：application.yml 的 coupon.sharding.bucket-count 没有多实例一致性机制。滚动发布/水平扩容（P3 演练项）窗口内实例 A=10 桶、实例 B=8 桶：同一 userId 在 A 路由桶 3、在 B 路由桶 3%8 之外；领券令牌落在 A 的 pend_3，取消请求打到 B 时 ZREM 桶错→no-op（幂等保住了不崩）→令牌在桶 3 泄漏到 180s 清扫（sum<total 良性方向，不冻结但层1两轮确认会提 deep）；同时两实例巡检按各自 count 读桶集合，全局 Σ 口径不一致→漂移告警在发布窗口随机响。运维没有任何'修改桶数'的 runbook 与顺序规定。
- **爆炸半径**：每次调整桶数的发布窗口伴随 3~10 分钟的假漂移告警噪音与一批 180s 自愈的 pend 泄漏；SRE 若不知道因果，会在大促前夜对着假告警人肉排查。用户侧基本无感（cancel 幂等兜住），代价主要是运维信任度。
- **接缝**：StockBucketRouter 路由、CANCEL Lua 的 ZREM==0 no-op 幂等、层2 全局 Σ（按 count 枚举桶）、P3 水平扩容/蓝绿演练、@Value 配置加载
- 用例1：**双实例不同 bucket_count 的取消幂等与守恒收敛**
  - 前置：两套应用配置 bucket-count=10 与 8 指向同一 Redis/DB（或单测内模拟两个 Router 实例）；模板 total 足够
  - 步骤：1) 用 count=10 的路由领券 1 张（记录 userId 落桶 i）；2) 用 count=8 的路由对同一 DeductCommand 执行 cancel(TRANSIENT)；3) 断言 cancel 返回 no-op（0）且不抛错；4) 等待/模拟 180s 清扫后触发层1+层2 巡检两轮
  - 预期：cancel 幂等无异常；清扫后层1 各桶绿、层2 绿（良性方向自愈）；期间无 sum>total 方向冻结。运维侧：文档化'改 bucket_count 必须停写/全实例同步'或路由版本化
  - 红信号：cancel 抛异常，或层1/层2 报 sum>total 危险方向导致冻结，或泄漏 pend 清扫后守恒仍长期破缺

#### USAB-9 [P2/可能性中] 桶号复用的代际语义未定义——跨代在途令牌让层1永假破缺，告警疲劳淹没真漂移
- **场景**：§2：'某桶扣完→DB 开新桶补货→该桶号重置为新额度'。桶号 i 被复用时，上一代残留的 pend_i 令牌（在途未 confirm/cancel）如何计入 bucket_total_i？若 bucket_total 按'当代额度'解释，跨代令牌使 stk_i+pend_i+dbi_i+void_i 恒差 1~N；按'代际累计'解释则需要累计口径的存储与文档。方案没写。时序：桶 i 余 1 张→用户 U 领到（令牌入 pend_i）→同秒其他并发打空桶 i→开新桶重置桶 i→U 的 DB 事务随后失败→cancel 回到桶 i（按 cmd 固化桶号，能找到）→正常；但若 U 的实例崩溃→令牌残留→新代层1 每轮巡检都破缺→两轮确认→deep 提交→DEFERRED_PENDING 循环（在途未清）直到 180s 清扫。高频大促下每次开桶都伴 1~2 个跨代令牌=层1告警成为常态白噪音。
- **爆炸半径**：守恒告警从'响=出事'退化成'响=日常'，MTTD 指标失真；deep 单线程被代际假案占用，真超发方向漂移的确认被排队延迟——安全机制的信噪比被自己设计的桶复用侵蚀。
- **接缝**：层1逐桶守恒（StockReconcileService 巡检改造）、pend 180s TTL 清扫与'故意破缺'口径（清扫后 sum<total 不冻结但 deep 慢修）、deduct 桶号随 DeductCommand 固化（§8）
- 用例1：**跨代在途令牌下新桶层1巡检绿**
  - 前置：BUCKET_SIZE=10；桶 i 上一代残留 1 个未决 pend 令牌（手工 ZADD 模拟崩溃残留，score 设为当前时间避免被立即清扫）；随后该桶被打空并开新桶（复用桶号 i）
  - 步骤：1) 开新桶（重置桶 i 额度）后立即触发 checkOne；2) 记录层1对该桶的读数与判定；3) 快进 180s（或调小 inflightTtlMs 模拟）令跨代令牌被清扫；4) 再触发 checkOne 两轮
  - 预期：方案文档化代际口径（推荐：bucket_total_i 为代际累计，或开桶时把跨代 pend 一次性折算入 dbi/void），实现后：清扫前后层1 均不产生'确认漂移→deep 提交'；跨代令牌清扫走既有的'故意破缺/崩溃残留'通道（deep 慢修或不冻结路径）
  - 红信号：每次开桶复用后层1 稳定产出 CONSERVATION DRIFT confirmed/deep 提交（哪怕随后自愈）——告警噪音的代际签名

#### USAB-10 [P2/可能性高] 测试可跟跑性：无桶帮助方法会静默读旧键假绿，路由不公开则桶级断言写不了
- **场景**：现有 RedisStockGateway 的测试/运维读数 remaining()/confirmedCount()/pendingCount()/userCount() 全部操作无桶键；现有集成测（RedisStockIntegrationTest 等）大量依赖它们断言库存。分桶后这些方法读不存在的键：remaining() 返回 null（断言处 NPE，算红）但 pendingCount() 返回 0、Long.parseLong(null) 之前的各种路径里 0 是合法值——部分断言会静默通过（假绿）。同时若桶路由只藏在编排层私有逻辑里、StockBucketRouter.route() 不公开纯函数，测试无法预知 userId 落哪个桶，'桶内四键守恒'断言无从下手，只能做全局黑盒断言——分桶方案自己的红灯测试①②（§7）都需要'指定某桶扣到 0'的能力。
- **爆炸半径**：分桶改造的回归网失效：旧套件要么全红没人细看（红=正常被当成噪音），要么局部假绿给出错误信心；新桶级行为（耗尽切换/单桶守恒）没有可跟跑的断言入口，红灯测试变成手工 redis-cli 表演——开发侧验证成本翻倍。
- **接缝**：RedisStockGateway 帮助方法族、src/test/java/com/newcoupon/integration 全套、方案 §7 红灯测试①②的可执行性、ShardedIntegrationTestSupport 造数支撑
- 用例1：**分桶改造提交后旧套件必须红（检测力存在性证明）**
  - 前置：分桶改造分支 checkout；本地 Redis/MySQL 测试容器可用
  - 步骤：1) mvn test -Dtest='RedisStockIntegrationTest,ReceiveIntegrationTest,ConservationRedLightIntegrationTest'；2) 统计失败分类：编译失败/断言失败/NPE/通过
  - 预期：失败集中在'键结构变更'的明确断言上（编译错或断言差值），且失败信息指明'读数应带桶参数'——改造者被迫同步升级帮助方法（remaining(tpl,bucket)/Σ聚合读数 allBuckets(tpl)），而不是删断言了事
  - 红信号：全套件全绿通过——证明旧断言在读不存在的键时静默取 0/null 通过，回归网已失效（此时打光一个桶旧测试毫无反应）
- 用例2：**路由纯函数公开且分布均匀可断言**

  - 步骤：1) 单测：route(userId) 调用两次结果相同；10 万个随机 userId 落 10 桶分布 max/min 比 <1.2；route 对 null/负数 userId 的兜底有定义；2) 集成测：领券后按 route(userId) 直接 GET c:stk:{tplId}:{bucket} 等四键，断言四键之和=桶总额（桶级守恒可跟跑）
  - 预期：route() 是公开纯函数（无 Redis 依赖）；测试能预计算桶号并直连桶键断言——方案 §7 红灯①（指定桶扣到 0）有程序化前置手段；桶耗尽注入可用'置 stk_i=0'单命令完成
  - 红信号：route 不可注入/不可访问，或测试只能靠 SCAN 全键猜桶——红灯测试退化成手工操作，无法进 CI

### 性能与容量（10 条）

#### PERF-1 [P1/可能性高] 0点开抢前几秒只有1个桶有货——"10桶并发"在脉冲峰值期不存在，且每~2秒串联一次开桶雷击
- **场景**：方案§4定死"发布 resetAll 改为开首个桶（不再全量入 Redis）"，§5桶生命周期是"耗尽→开下一桶"。发布瞬间仅桶0有10000张：hash(uid)%10==k的90%用户请求落到空桶k，DEDUCT内走"切换下一个非空桶"全部收敛到桶0——5000 QPS脉冲峰值（恰是0点开抢最疼的前2-10秒）100%挤在单桶（且同slot串行，见PERF-2）；桶0每2秒耗尽一次，每次触发全局限流点（-10→openBucket→重试）。§2图"10个桶同时活跃"与§4/§5的开桶时序自相矛盾，除非预热开满10桶（方案未写）。

- **接缝**：ReceiveAppService.doReceive的-10分支、StockBucketRouter.openBucket、DEDUCT桶扫描、TemplateAppService.publish/resetAll、Redis单线程（同slot）

#### PERF-3 [P1/可能性高] 桶耗尽雷鸣畜群无单飞——-10到openBucket无并发闸门，最坏QPS级并发UPDATE打DB热行、allocated多开、hikari 20连接被打满拖死无辜流量

- **接缝**：ReceiveAppService -10分支、StockBucketRouter.openBucket、hikari连接池、CouponIssueTxService剩余INSERT流量、多实例部署、层2守恒/镜像臂（c:alloc vs allocated）
- 用例1：**耗尽事件单飞计数（核心验收）**

  - 红信号：模板Y RT P99>200ms或出现DEGRADED/超时——局部桶耗尽放大成全局故障。

#### PERF-4 [P1/可能性中] 开桶同步串在领券RT内——每2秒一次DB行锁等待是常态路径，P99预算被周期性收割
- **场景**：BUCKET_SIZE=10000×5000 QPS=开桶每2秒一次（方案§2自己的算术）。开桶是同步链：-10→openBucket（DB条件UPDATE行锁+Redis建桶Lua）→重试deduct→返回。正常DB RT 1-5ms时雷击窗口请求多付10-30ms；DB轻微劣化（20-50ms）时窗口内请求RT翻倍。SLA P99<200ms的分位预算被一个每2秒必然发生的事件周期性收割——P99曲线梳齿化，"平均RT好看、P99长期贴线"。方案无预开（水位低于阈值后台开下一桶）或异步化设计，把本可后台化的补货放进了用户RT。
- **爆炸半径**：用户侧每2秒一批"领取慢"；SRE侧P99告警反复触发放狼来了；2小时大促=3600次雷击抽奖，DB每次IO尖刺都传导给当批用户。
- **接缝**：ReceiveAppService -10重试、DB行锁（与user_coupon/coupon_event INSERT、expire task注册争IO）、2e-⑤ RT指标、SLA P99<200ms、2d MQ削峰（尚未到位）
- 用例1：**稳态开桶雷击的RT梳齿量化**
  - 前置：5000 QPS稳态压测5分钟；10ms桶聚合RT直方图；开桶事件时间线可查（日志打点）。
  - 步骤：对齐开桶时间戳与RT直方图，计算"开桶后50ms窗口P99"对比"无开桶窗口P99"的比值。
  - 预期：比值<1.5×且整体P99<200ms；若实现了预开/异步开桶则雷击窗口消失（用户路径-10率趋近0）。
  - 红信号：开桶窗口P99/平常P99≥2×，或整体P99>200ms且毛刺周期≈BUCKET_SIZE/QPS秒。
- 用例2：**预开桶水位验收**
  - 前置：实现了"桶水位低于阈值后台预开下一桶"。
  - 步骤：稳态压测中统计用户路径-10命中率与后台预开成功率、后台开桶时的DB连接占用。
  - 预期：用户路径-10率<0.01%；后台预开成功率100%；预开不与领券争抢DB连接产生尖峰。
  - 红信号：用户路径-10率>1%（预开跟不上耗尽速度）或预开把DB CPU打出周期尖峰。

#### PERF-5 [P1/可能性中] hash(user_id)路由倾斜——活跃用户扎堆同桶把"10桶"退化成"1个热桶+9个围观桶"，倾斜桶提前耗尽后该用户群反复撞切换/-10
- **场景**：路由隐含假设"userId均匀→桶均匀"，但QPS分布由用户行为决定：0点开抢流量=活跃用户/社群导流/羊毛党段，注册潮形成的自增userId连续段对%10取模会聚到少数桶。倾斜40-60%到桶k时：(a)桶k以2000-3000 QPS单桶扣减且同slot串行（PERF-2），Redis排队；(b)桶k以5-10倍速耗尽，其用户全体走"切换下一非空桶"长脚本或直接-10进开桶等待——同批用户RT系统性劣化；(c)开桶频率从0.5/s上升（倾斜桶反复耗尽），雷击密度升；(d)"同用户同桶"被切换打破后，若ul限领键随桶拆则限领被绕过（正确性组主责，性能连带）。方案无倾斜探测与再平衡设计，且压测惯用均匀随机userId——实验室永远复现不了，线上才爆。
- **爆炸半径**：大促主推券在真实流量形状下SLA失守；桶水位分布无告警的话连"为什么慢"都查不到；羊毛党段用户体验劣化引发客诉。
- **接缝**：StockBucketRouter路由、DEDUCT桶切换路径、ul/uld限领键语义、2e-⑤ per-bucket gauge、P4压测流量模型（必须加倾斜场景）
- 用例1：**倾斜流量注入与检测时延**
  - 前置：已发布多桶模板；离线算10万个userId的hash%10分布，选出映射桶3的子集（约1万）。
  - 步骤：3000 QPS其中90%来自桶3子集、10%均匀，压5分钟；观察per-bucket水位下降速率与倾斜告警（单桶份额>25%持续30s）。
  - 预期：桶3消耗速率≈其他桶9倍被指标捕获；1分钟内触发倾斜告警；其余桶有余量兜住切换，-10错误为0。
  - 红信号：无per-bucket指标或告警不触发（倾斜不可见=红线）；倾斜期间桶3用户RT P99>均匀基线3×。
- 用例2：**极端倾斜兜底（100%单桶）**
  - 前置：全部压测userId映射到同一桶，其余桶有余量。
  - 步骤：单桶打至耗尽后继续压1分钟。
  - 预期：切换路径兜住：-10错误为0（其他桶有余量时不得误判全空），RT增幅<50%。
  - 红信号：返回-10（"全桶耗尽"误判——切换逻辑只看了本桶）或RT P99翻倍以上。

#### PERF-6 [P2/可能性中] bucket-size/bucket-count配置错位——调小=开桶频率回升热行复活；大于total=开桶永假直接拒发；热变更=路由漂移
- **场景**：参数进application.yml（coupon.sharding.bucket-size/bucket-count）但无与total的联动校验。三个坑：(a)bucket-size被调小（如100，为"并行度"或照抄配置），5000 QPS→50次开桶/s，DB行锁50 TPS+每秒50次雷击，比分桶前的400 TPS好不了多少且RT打穿；(b)小盘券total=5000<bucket-size=10000，开桶条件allocated+10000<=total永假→发布后第一笔领券即"真售罄"；(c)bucket-count运行中热变更（多实例滚动配置不一致），hash(uid)%N的N变了→同一用户路由漂移，pend令牌桶号（cmd固化，§8）与新路由错位；2c本地缓存生效后bucket_count来自缓存，刷新延迟窗口内多实例路由不一致加剧。
- **爆炸半径**：运维一次参数调整可直接终结大促（拒发）或让DB提前阵亡；配置漂移是最难排障的一类故障。
- **接缝**：application.yml、StockBucketRouter路由参数、2c Caffeine模板缓存（bucket_count缓存一致性）、多实例滚动发布、P7 appendStock（追加库存时bucket-size语义）
- 用例1：**bucket-size调小的开桶频率红线**
  - 前置：压测环境bucket-size=100、bucket-count=10、total=100万。
  - 步骤：1000 QPS压30s，统计UPDATE allocated TPS、开桶事件数、RT P99。
  - 预期：验收阈值落为告警规则：UPDATE allocated≥2/s持续10s触发；本用例应触发告警且RT P99<200ms（有预开/合批时）。
  - 红信号：UPDATE TPS≈10/s（=QPS/100）无任何告警，RT P99>500ms——"调参复活热行"无人发现。
- 用例2：**小盘券发布冒烟**
  - 前置：bucket-size=10000默认未改；建total=5000模板并发布。
  - 步骤：发布后发第一笔领券请求。
  - 预期：要么自动收敛bucket-size=min(bucket-size,total)，要么发布接口明确拒绝并报错可读。
  - 红信号：第一笔领券返回售罄/DEGRADED（开桶条件永假）。
- 用例3：**bucket-count滚动变更路由一致性**
  - 前置：双实例（或双线程模拟）：实例A用N=10、B用N=5模拟滚动发布窗口。
  - 步骤：同一userId交替经A/B领券产生pend令牌，再cancel/confirm。
  - 预期：cmd固化桶号使confirm/cancel找回正确桶（§8承诺成立）；配置不一致期只影响路由分布，不产生错误码。
  - 红信号：cancel找错桶致令牌悬挂（错桶ZREM=0）或-7/-10错误率>0。

#### PERF-7 [P2/可能性中] 桶切换重试放大——最坏1个用户请求=2×DEDUCT+1×DB开桶+1×CANCEL，叠加-7退避sleep挤占Tomcat线程，名义5000 QPS实际后端1.5-3×
- **场景**：-10分支在编排层重试deduct（§4"换桶重试"）；叠现有机制：-7懒重建随机退避50-200ms（Thread.sleep占住请求线程）、L3自愈retryOnce透明重试、recoverUncertainOutcome探针DB读、2e-③假售罄当场修（-3后当查DB再重建重试）。错误路径请求的后端命令数从正常~6条（1 DB读+2 Lua+DB事务4 SQL）膨胀到12+；雷击窗口内几百线程同时sleep/等开桶，Tomcat默认200线程被错误路径挤占，正常请求排队。若-10→openBucket→重试仍-10（开桶未完成）无重试上界，形成循环。容量规划按名义QPS配池，错误率5%时实际负载已超预算30%+。
- **爆炸半径**：大促错误路径占比升高时（恰是DB/Redis最脆弱时）线程池连锁打满，正常流量被错误流量的重试挤死——"越忙越重试、越重试越忙"。
- **接缝**：ReceiveAppService.doReceive（-7退避/retryOnce/-10重试/假售罄急救）、Tomcat线程池（默认200未覆写）、hikari、Redis连接池、P4-⑤池参数配平
- 用例1：**错误路径命令数预算断言**
  - 前置：集成环境开Redis MONITOR或Lettuce命令打点；能构造-10（全桶耗尽+可开桶）、-7（清库）、-3+急救（假售罄）三种错误。
  - 步骤：各错误路径发100个请求，统计每请求Redis命令数、DB SQL数、含sleep的线程占用时长。
  - 预期：每请求Redis命令≤8、DB SQL≤6、-10重试≤1次、总耗时≤500ms；写成集成测断言常驻。
  - 红信号：任一错误路径Redis命令≥12，或出现-10→openBucket→-10循环（重试无上界）。
- 用例2：**错误流量占比对正常RT的挤占**
  - 前置：压测环境4000 QPS正常流量稳态。
  - 步骤：叠加5%错误注入流量（持续制造-10+开桶+退避），观察正常流量RT P99与Tomcat busy threads 5分钟。
  - 预期：正常流量RT P99劣化<10%，busy threads<80%。
  - 红信号：busy threads触顶200、正常流量P99翻倍——重试放大击穿线程池。

#### PERF-8 [P2/可能性中] 每请求KEYS与脚本膨胀——DEDUCT从7键到20+键（c:fz+桶扫描），单实例Redis在5000 QPS进入非线性排队区
- **场景**：现状DEDUCT 7 KEYS约12次redis.call。分桶后：+c:fz首行检查（§9改进2）、桶扫描（Lua内找非空桶需把全部桶stk键进KEYS——Cluster下Lua只能碰声明键）→KEYS 20-30个、redis.call 15-25次、EVALSHA包体约3×。Redis单线程：5000 QPS×20 call=100k ops/s，再加CONFIRM/CANCEL/idem，逼近单核舒适水位；利用率过半后M/M/1排队延迟非线性上升，P99由队列决定。巡检层2"一条Lua读41键"与DEDUCT同slot互斥（PERF-2），60s一次不致命但计入预算。
- **爆炸半径**：P4压测拐点比预期提前；Redis CPU告警与大促流量叠加时P99抖动放大；每请求带宽×3在内网可承受但会吃掉Redis网卡预算。
- **接缝**：RedisStockGateway五段Lua、c:fz（2e-②）、层2全局守恒Lua、Redis单实例（P6前）、SLOWLOG/latency monitor、INFO commandstats
- 用例1：**脚本膨胀基线对比**
  - 前置：改造前后同环境；压测机；SLOWLOG已配置。
  - 步骤：分别以改造前（单桶键）与改造后（桶版含fz+扫描）各压3000 QPS 5分钟，记录instantaneous_ops_per_sec、Redis CPU%、SLOWLOG条数、Lua段p99。
  - 预期：验收阈值：Redis ops≤70k/s、CPU≤60%、SLOWLOG无>1ms条目、Lua段P99≤2ms；ops/QPS比值增幅≤1.5×。
  - 红信号：改造后ops/QPS比值>改造前1.5×，或CPU>60%且Lua p99>5ms。
- 用例2：**桶扫描最坏路径**
  - 前置：构造9个桶空、1个桶有余，流量路由命中空桶。
  - 步骤：1000 QPS全部走"路由桶空→扫描切换"路径1分钟，量该路径Lua p99与SLOWLOG。
  - 预期：扫描路径Lua p99≤3ms；实现上应一次算出目标桶而非逐桶试扣（审Lua源码确认无O(BUCKET_COUNT)次DECR尝试）。
  - 红信号：扫描路径p99≥直达路径3×，或脚本对每个候选桶都执行完整扣减尝试。

#### PERF-9 [P2/可能性低] c:alloc全局键护栏——当前低频无害（每开桶1次≈0.5/s），但任何"把全局余量判断塞进DEDUCT"的演化都会让5000 QPS重新砸回单键热点
- **场景**：方案里c:alloc只在开桶Lua（INCR）与层2巡检（读）出现——0.5写/s完全不热。风险在未来演化：一旦有人为"提前感知全局售罄"在DEDUCT里GET c:alloc，或2e-①三步确认被改成高频执行，c:alloc立刻变5000 QPS读热点且与桶键同slot（PERF-2）互斥——它天然是全模板串行点，只能靠低频访问纪律保平安。P3-③热key探测（单键>3000 QPS预警）应显式覆盖此键。
- **爆炸半径**：未来一次"顺手优化"复活全局热key，且因同slot互斥拖慢所有桶的DEDUCT——无per-key QPS告警时性能退化无声。
- **接缝**：c:alloc键、开桶Lua、DEDUCT脚本演进、2e-①三步确认、P3-③热key探测
- 用例1：**c:alloc访问频率红线（静态+运行时双保险）**
  - 前置：改造后代码与压测环境。
  - 步骤：(静态)单测断言DEDUCT/CANCEL/CONFIRM脚本源码字符串不含c:alloc键名，进CI常驻；(运行时)3000 QPS压测中用INFO commandstats或redis-cli --hotkeys抽样5分钟统计c:alloc命中QPS。
  - 预期：静态断言通过；c:alloc命中频率≤开桶频率量级（个位数/s）。
  - 红信号：c:alloc QPS与领券QPS同量级（>100/s）——全局读被塞进了请求路径；或静态断言被人绕过。

#### PERF-10 [P2/可能性中] 巡检按桶放大+心跳假告警——每模板从1条Lua变11+条，模板数增长后巡检一轮逼近心跳TTL 180s，HEARTBEAT EXPIRED误报风暴
- **场景**：守恒巡检改造为"层1逐桶+层2全局"：每发布模板每60s从1次conservation Lua变10桶级+1全局（读41键）；2e-①三步确认再加~200ms延迟。HEARTBEAT_KEY TTL=180s（3×周期）按"一轮≤60s"设计——已发布模板数涨到几百、或Redis/DB变慢时一轮耗时逼近180s，心跳键过期→"HEARTBEAT EXPIRED立即叫醒级告警"误报；大促夜模板多+巡检慢=告警风暴，真故障（巡检真挂了）被淹没。层2的41键大脚本与DEDUCT同slot互斥，也计入Redis预算（PERF-8）。
- **爆炸半径**：告警疲劳：真巡检静默（最危险故障）被假心跳告警淹没；巡检自身放大Redis压力，大促夜雪上加霜。
- **接缝**：StockReconcileService.conservationCheckAll、HEARTBEAT 180s TTL、findPublished全表、2e-①三步确认200ms、PERF-2同slot互斥
- 用例1：**模板规模下巡检一轮时长**
  - 前置：造200个已发布模板（每个10桶），压测环境巡检开启。
  - 步骤：触发一轮conservationCheckAll计时；观察期间心跳键存活与层2脚本p99。
  - 预期：一轮≤60s；心跳无EXPIRED告警；层2脚本p99≤5ms；巡检期间DEDUCT RT毛刺<10%。
  - 红信号：一轮>120s或出现HEARTBEAT EXPIRED日志（假阳性）；或单轮巡检使DEDUCT RT P99抬升>10%。

## 6. 好用性验收指标（USAB 域提炼，进 P2b 验收标准）

**用户侧**：
- 桶耗尽切换**零丢单**；边界瞬间 P99 增量 <100ms（USAB-3）
- 冻结期返回**专用降级码**（FROZEN 段，retryable=true，文案"活动暂停发放，请稍后重试"），**响应体不得泄漏内部负数码 -10/-11**；旧实例 default 分支兜底为可重试 DEGRADED 而非 SYSTEM_ERROR（USAB-2）
- 假售罄急救：真售罄误触发急救率=0；急救路径用户可见错误率=0、P99 增量<200ms（USAB-6）
- 误冻结自动解冻 p100 ≤120s（两个巡检周期内），无需人工（USAB-4）

**运营/SRE 侧**：
- 解冻 runbook ≤3 步、全程审计留痕（谁/何时/为何）；MTTR（告警→恢复）演练 ≤5 分钟；解冻口双人复核（USAB-4）
