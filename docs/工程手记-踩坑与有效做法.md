## 一、多 agent 工作方式（用户 2026-10-05 要求）

**为什么要多 agent**：单线程推进的盲区是**视角问题，不是注意力问题**。S2 第 9 步的实证——
单 agent 写完的实现，经三个独立视角审查后找出 **15 个缺陷**，其中 4 个是"实现了但没人守"的代码；
设计阶段的那一轮更是**直接推翻了原方案**（详见 [S2 设计文档](S2-流量治理与租户策略-需求与设计-2026-10-04.md) §附一/附二）。

### 1.1 什么阶段该起几个 agent

| 阶段 | 做法 | 视角设计 |
|---|---|---|
| **设计前** | 3 个独立视角并行 | **可行性**（技术核实在这个栈上做不做得到）/ **风险**（会怎么坏）/ **可测性**（怎么证明它有效） |
| **实现后** | 3 个独立视角并行 | **正确性与边界** / **与既有机制的交互** / **测试可信度（找假绿）** |
| 小改动（一两行、纯机械） | 不必起 | 自己 + 回归用例足够 |

**规模**：默认 3 个视角（medium 档），够覆盖盲区，不必更多。

### 1.2 prompt 怎么写才有效（实测）

**有效的写法**：
- **给具体文件路径**，并要求"**先实际读代码再回答**"——否则会收到泛泛而谈的架构建议；
- **明确要求"列出做不到的事"**——这一条比"列出可行的做法"更有价值：
  说不清"做不到什么"，方案就会在实施时被静默打折；
- **要求 confidence（high/medium/low）**——便于判断哪些结论值得直接采信；
- **给具体的失败场景让其推演**（如"如果这个判断错了会发生什么"），比"请审查"有效得多；
- **要求"文件:行号"级别的证据**，并**允许标注"推测"**——把猜测和事实分开。

**审查类 prompt 的关键**：**明确说"默认假设它有 bug，你的任务是找出来"**。
说"请审查代码"会得到一份礼貌的总结；说"默认它有 bug"会得到 15 条带证据的发现。

### 1.3 Workflow 脚本的坑（踩过）

- **prompt 正文里不能出现反引号**：脚本是 JS 模板字符串，`` ` `` 会提前结束字符串，
  报错是 `ReferenceError: xxx is not defined`（指向毫不相干的地方）。行内代码用单引号。
- **agent 数量与耗时**：3 个 agent 一轮约 6~9 分钟、30~45 万 subagent tokens（2026-10-05 实测）。
  它在后台跑，期间**不要开工重活**（WSL 资源纪律），可以做文档类的轻量工作。
- **结果可能不完整**：`journal.jsonl` 里每个 agent 一行 `{"type":"result",...}`；
  若某视角没产出，别假设它是空的——先读 journal 确认。

### 1.4 审查结果怎么处置

- **"实现了但没人守"是最高优先级**：审查说"删掉这一行用例也不会红"时，**代码等于没写**——
  下次改动会静默破坏它。必须补上能区分行为的用例。
- **分清"真缺陷"与"可选优化"**：前者当场修，后者登记并写清触发条件。
- **审查也会有错**：本项目的做法是"审查提发现 → 自己验证 → 才动手"，
  验证方式就是**把它说的那一行删掉，看用例红不红**。

## 二、测试设计的四条铁律（S2 期间同一类问题出现 4 次）

**四条都来自真实返工**，不是理论：

| 铁律 | 反例（本项目真实发生过） |
|---|---|
| ① **用例的数据自己建，不共享** | "异参"用例给同一个用户又发了一张券；"整体为空"的断言被别的用例写脏 |
| ② **有状态组件要复位** | 熔断器是**进程级**的，一条压力用例把它打开后，同批其他用例全报"系统繁忙" |
| ③ **不要用不可控的量卡边界** | 预热用例"连打 20 次"卡在有效阈值附近——有效阈值取决于"JVM 已经跑了多久"，单跑绿、同批跑红；另有"千并发成功数 98~100 波动" |
| ④ **只断言外部行为，不依赖实现细节** | 用例预填内部的 Redis 键，换一种限流算法（键格式变了）后 5 条用例集体变红 |

**推论**：
- **测试可以依赖契约，不该依赖实现**（"超过上限会被拒"是契约，"内部键长什么样"不是）；
- **断言失败时，先问"用例自己有没有问题"**——S2 里至少 4 次失败是用例的错，不是实现的错；
- **让失败自带证据**：把关键读数（如失败分布）**打进断言消息**。
  同一个千并发用例，之前有一次 `98 != 100` 完全没有线索；加了分布之后，一眼就看出是"连接池打满"而不是"发券逻辑错了"。

**关于"红"的两种来源**：环境敏感（压力、资源竞争）与真实缺陷。区分方法：
**单跑**。单跑绿、批量红 → 环境敏感；单跑也红 → 真实缺陷。**不要用"环境问题"一句话糊过去。**

## 三、工具与环境的坑

| 坑 | 触发条件 | 做法 |
|---|---|---|
| **增量编译假绿/假红** | 同一秒内改文件，Maven 按时间戳粒度跳过重编译 | **跑测试一律 `mvn clean test`**（本项目 STATUS 早就写着"必须 clean"） |
| **IDE 后台构建污染** | VSCode 的 Java 扩展编译产物比源文件新 → Maven 跳过重编译 → 跑的是旧 class，**且编译不报错** | 同上：必须 clean |
| **`mvn ... \| grep` 的退出码** | 管道取的是**末尾命令**的退出码 | 用 `${PIPESTATUS[0]}`，或不用管道 |
| **`min-calls > window-size` 是无效配置** | 想把熔断阈值配得"永不触发"时 | **两个参数必须一起调**（Resilience4j 要求最小样本数 ≤ 滑动窗口） |
| **`setQueryTimeout(0)` 表示"无超时"** | 想按剩余预算收紧 SQL 超时 | 必须**钳到 ≥1 秒**（写反比不写更糟） |
| **Spring 自带 `ContentCachingRequestWrapper` 不重放 body** | Filter 读完 body 后 Controller 读不到 | 自己写可重放的 wrapper（一次性读进内存，之后每次返回新流） |
| **响应在 filter chain 返回前就已提交** | 想在 filter 里回写响应头 | 做不到（Tomcat 写完 body 就 flush）；改走日志/traceId |
| **断言服务端日志要轮询** | "发请求→立刻查日志" | 响应早于日志落盘，存在竞态窗口；轮询等待（且在 detach appender **之前**等） |
| **测试容器偶发"appId 已存在"** | 新写的测试类首次运行（出现 3 次，未定位） | **把准备动作写成幂等的**（存在就轮换密钥 / 每用例用独有 appId），不去猜根因 |

## 四、本项目的四条长期约定（与 STATUS 同步）

1. **先红后绿**：每条修复/新功能都先写用例、跑出失败、再实现、跑出通过。**红灯输出留档**。
   新功能写不出失败就先建骨架（方法体抛异常）让用例能编译。
2. **收尾三件套**：git 提交 + `docs/STATUS.md` 同步 + `study/工作日志.md` 追加。
3. **改动公共配置或新增必填项后，必须跑一遍受影响的既有用例**
   （教训：`SecretCipher` 的 fail-fast 让本地 dev 直接起不来，靠既有用例抓出）。
   **"受影响的用例"要按"改动会被谁感知到"推，而不是按"我改了哪个功能"**
   （教训：新增一个横切所有写接口的过滤器，破坏了前面步骤写的用例，潜伏两步才暴露）。
   **加了构造依赖后，单测与集成测试都要跑**（教训：`@InjectMocks` 不会自动补新依赖，
   20 例单测里 19 例 NPE 却没人发现）。
4. **多 agent 讨论与观察**（见第一节）。

## 五、一条工作节奏上的经验

**"查根因"与"消除依赖"之间要会切换**：S2 第 7 步遇到两个查不清的现象
（复用 appId 偶发"已存在"、共享字段莫名为 null），最后的处置是**消除对它的依赖**
（每用例自建独有数据），两个现象同时消失。

**判断依据**：当"查清根因"的成本已明显高于"消除对它的依赖"时，选后者——
而**消除依赖通常本身就是更好的设计**。但要用**单跑**先把"环境敏感"与"真实缺陷"区分开，
不要把真实缺陷也当成"环境问题"糊过去。
