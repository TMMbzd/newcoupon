## 〇、动手前先调研（用户 2026-10-08 要求，优先级最高）

**用户原话**：「先调研业界是怎么做的，对于一切你之前阉割版的功能实现，重复造轮子的实现，都不要了。
你经常在原来阉割版的实现中小修小改，不肯废除惯性思维和动作。」

**触发事件**：限流器的接口契约是从**第一个实现**（固定窗口）身上长出来的——它要求调用方
传"自带窗口标识"的键。后来加滑动窗口与令牌桶时沿用了这个签名，于是滑动窗口的"上一窗口"
永远读不到（调用方给的键每秒就换），**配了滑动窗口的租户实际拿到的是退化的固定窗口**，
而且没有任何东西会告诉他。业界的做法是用成熟库，我做的是重复造轮子、然后在轮子上打补丁。

**流程（每次实质性工作都走）**：

1. **调研**（并行多视角，不是一个人想）：业界主流方案是什么？它们解决了什么问题？
   接口契约怎么设计的？有没有现成库？—— **不要在现有实现上"顺着改"**。
2. **讨论**：把调研结果与取舍摆出来和用户对一下，不要直接开工。
3. **实施**：结论确定后再动手；**该废除的就废除**，不以"改起来省事"为标准。

**判断"该不该自己写"**：默认用成熟库。要自研必须显式说出理由（教学价值 / 库不满足的特定需求），
并让用户拍板——但**绝不能因为"已经写了"就保留**。这个项目是学习项目，自研确实有教学价值，
所以这条例外要摆到台面上讲清楚，而不是默默沿用。

**这条与"多 agent"是配套的**：调研阶段本来就是多视角的天然场景（业界方案 / 契约设计 /
场景匹配 / 迁移代价），比一个人想完就动手稳得多。

## 一、多 agent 工作方式（用户 2026-10-05 要求）

**为什么要多 agent**：单线程推进的盲区是**视角问题，不是注意力问题**。S2 第 9 步的实证——
单 agent 写完的实现，经三个独立视角审查后找出 **15 个缺陷**，其中 4 个是"实现了但没人守"的代码；
设计阶段的那一轮更是**直接推翻了原方案**（详见 [S2 设计文档](S2-流量治理与租户策略-需求与设计-2026-10-04.md) §附一/附二）。

### 1.1 什么阶段该起几个 agent

| 阶段 | 做法 | 视角设计 |
|---|---|---|
| **设计前** | 3 个独立视角并行 | **可行性**（技术核实在这个栈上做不做得到）/ **风险**（会怎么坏）/ **可测性**（怎么证明它有效） |
| **实现后** | 3 个独立视角并行 | **正确性与边界** / **与既有机制的交互** / **测试可信度（找假绿）** |
| 小改动（一两行、纯机械） | 不必起 | 自己 + 回归用例足够 |

**规模**：默认 3 个视角（medium 档），够覆盖盲区，不必更多。

### 1.2 prompt 怎么写才有效（实测）

**有效的写法**：
- **给具体文件路径**，并要求"**先实际读代码再回答**"——否则会收到泛泛而谈的架构建议；
- **明确要求"列出做不到的事"**——这一条比"列出可行的做法"更有价值：
  说不清"做不到什么"，方案就会在实施时被静默打折；
- **要求 confidence（high/medium/low）**——便于判断哪些结论值得直接采信；
- **给具体的失败场景让其推演**（如"如果这个判断错了会发生什么"），比"请审查"有效得多；
- **要求"文件:行号"级别的证据**，并**允许标注"推测"**——把猜测和事实分开。

**审查类 prompt 的关键**：**明确说"默认假设它有 bug，你的任务是找出来"**。
说"请审查代码"会得到一份礼貌的总结；说"默认它有 bug"会得到 15 条带证据的发现。

### 1.3 Workflow 脚本的坑（踩过）

- **prompt 正文里不能出现反引号**：脚本是 JS 模板字符串，`` ` `` 会提前结束字符串，
  报错是 `ReferenceError: xxx is not defined`（指向毫不相干的地方）。行内代码用单引号。
- **agent 数量与耗时**：3 个 agent 一轮约 6~9 分钟、30~45 万 subagent tokens（2026-10-05 实测）。
  它在后台跑，期间**不要开工重活**（WSL 资源纪律），可以做文档类的轻量工作。
- **结果可能不完整**：`journal.jsonl` 里每个 agent 一行 `{"type":"result",...}`；
  若某视角没产出，别假设它是空的——先读 journal 确认。

### 1.4 审查结果怎么处置

- **"实现了但没人守"是最高优先级**：审查说"删掉这一行用例也不会红"时，**代码等于没写**——
  下次改动会静默破坏它。必须补上能区分行为的用例。
- **分清"真缺陷"与"可选优化"**：前者当场修，后者登记并写清触发条件。
- **审查也会有错**：本项目的做法是"审查提发现 → 自己验证 → 才动手"，
  验证方式就是**把它说的那一行删掉，看用例红不红**。

## 二、测试设计的四条铁律（S2 期间同一类问题出现 4 次）

**四条都来自真实返工**，不是理论：

| 铁律 | 反例（本项目真实发生过） |
|---|---|
| ① **用例的数据自己建，不共享** | "异参"用例给同一个用户又发了一张券；"整体为空"的断言被别的用例写脏 |
| ② **有状态组件要复位** | 熔断器是**进程级**的，一条压力用例把它打开后，同批其他用例全报"系统繁忙" |
| ③ **不要用不可控的量卡边界** | 预热用例"连打 20 次"卡在有效阈值附近——有效阈值取决于"JVM 已经跑了多久"，单跑绿、同批跑红；另有"千并发成功数 98~100 波动" |
| ④ **只断言外部行为，不依赖实现细节** | 用例预填内部的 Redis 键，换一种限流算法（键格式变了）后 5 条用例集体变红 |

**推论**：
- **测试可以依赖契约，不该依赖实现**（"超过上限会被拒"是契约，"内部键长什么样"不是）；
- **断言失败时，先问"用例自己有没有问题"**——S2 里至少 4 次失败是用例的错，不是实现的错；
- **让失败自带证据**：把关键读数（如失败分布）**打进断言消息**。
  同一个千并发用例，之前有一次 `98 != 100` 完全没有线索；加了分布之后，一眼就看出是"连接池打满"而不是"发券逻辑错了"。

**关于"红"的两种来源**：环境敏感（压力、资源竞争）与真实缺陷。区分方法：
**单跑**。单跑绿、批量红 → 环境敏感；单跑也红 → 真实缺陷。**不要用"环境问题"一句话糊过去。**

### 2.1 怎么证明"用例真的能守"——**变异验证**（2026-10-05 新增）

**问题**：写了一条绿灯用例，怎么知道它不是摆设？审查最常报的一类问题是
"删掉这一行实现，用例照样绿"——那种用例**等于没写**，下次改动会静默破坏契约。

**做法（变异验证）**：把刚写好的**关键实现**临时改坏一处，跑用例，**确认对应用例真的红了**，
再恢复实现。一次可以同时改坏几处，跑一遍就能看到"哪几条用例抓住了哪个变异"。

**本项目第 10 步的实操**：砍掉 `put` 的幂等跳过、砍掉 `revert` 的 CAS 判断与快照恢复 →
跑一次 → 恰好 `p3`（审计噪音）/`p4`（快照没还回来）/`p5`（冲突没报出来）三条红，
其余四条保持绿。**这比形式上的红灯更有说服力**：它同时证明了"用例有效"与"变异定位精确"。

**什么时候用**：新写的关键契约用例（幂等、回滚、边界、安全判据）。
纯展示层或一行 getter 不值得。

**恢复实现用 `git checkout -- <file>`**：所以变异前**先提交**，恢复才干净
（否则会把实现一起丢掉）。

### 2.2 "不可控的量"的四种伪装（2026-10-05 起，逐次补充）

铁律③说"不要用不可控的量卡边界"，但**不可控的量常常伪装成可控的样子**。下面每一条都是真实案例（按发现的顺序）：

| 伪装 | 真相 | 症状 |
|---|---|---|
| "连打 35 次一定超过上限 30" | **QPS 限流的 key 里带"当前秒"**——每秒一个新桶，所以 35 次必须**全部落在同一秒内**才有意义 | 单跑绿、全量红：机器忙时 35 次横跨两个秒桶，每桶都不超 30 → 全部放行 |
| "预热 600 秒，整个用例都处于冷启动期" | 有效阈值取决于 **JVM 已运行时长**，套件里排得越后越接近预热结束 | 实际测的是"普通限流"而不是预热，断言的意义早已漂移 |

**第三种伪装（2026-10-08 新增）：「连打 N 次」**。

在集成测试里用"连打 N 次，断言至少被拦一次"验证限流——看起来是可控的（N 是我自己定的），
实际上**依赖"这 N 次落在同一个统计窗口内"**。而集成测试的请求**很慢**：
实测 `POST /api/coupons/receive` **每次约 1.3 秒**（要走完 Spring + 数据库整条链路），
于是"连打 20 次"跨了 **26 秒**——对一条 `1 QPS` 的规则来说，每秒放行一个，
**永远不超限**，用例必红，而链路其实是通的。

**我为此花了三轮才定位**（先是怀疑拦截器没装、再是怀疑资源名不对、最后才量耗时）。
**正确做法**：用**与时间无关**的判据——
· 要验"规则能不能拦" → 用 `count=0`（Sentinel 里 0 = 全拒，一发就拦）；
· 要验"统计在不在工作" → 直接读统计（反射读 `ClusterNode`），而不是靠"打够多次"。

**第四种伪装（2026-10-08 第 6 步新增）：「顺序连打」在**连续补充**的限流器下一定打不出超限**。

令牌桶不是"每个窗口补满一次"，而是**连续补充**（capacity 个令牌摊在整个周期里匀速放出来）。
于是判据还多一个隐含前提：**"请求要比补充间隔更快"**。实测：IP 维度配 2 QPS（每 0.5 秒补一个），
而一发请求要走 1 秒多——**顺序连打，每次之间补的令牌早就够下一次用了**，
无论打多少次都不会超限。换成"8 发并发"之后才是可控的量（同一瞬间抢那 2 个令牌）。

**同一个坑这已经是第 4 次**，所以记一条更实用的判据：
**凡是"打 N 次应该被限"的用例，先问"这 N 次之间流逝的时间能补回多少额度"。**

**识别方法**：问一句"**这个断言成立依赖什么没被写出来的前提？**"——
如果答案是"机器够快"、"上一步刚跑完"、"JVM 刚启动"、"请求够快"，那就是不可控的量。
**"连打 N 次"的隐含前提是"请求够快"，这一条最容易漏。**

**修法**：把它变成**给定输入**（本例：给 `WarmUpRateLimiter` 的构造器传 `startMs`，
用假时钟指定预热进度），或者**换一个不受该量影响的判据**（本例：改用日配额——key 是"当天"，不跨秒）。

**另一个方向的经验**：第 10 步 P1 把熔断判据改宽（沿 cause 链匹配）之后，
一处**既有的测试配置遗漏**被照了出来——某个 2000 并发的压力用例没配宽松熔断阈值
（"谁需要谁配"时漏了它），于是压力触发的异常把熔断打开、成功数从 1000 掉到 76。
**判据变正确可能会让沉睡的配置问题显形**；遇到这种"改动后别处红了"，
先分清是**新引入的错误**还是**被照出来的旧账**——两者的修法完全不同。

### 2.2b 共享测试容器之后：断言必须"自包含"（2026-10-08 补充）

为提速，测试基座从"每个测试类起一对容器"改成"整个 JVM 共用一个容器单例"
（全量 50:48 → **5:31**，省 89%）。代价是**数据不再按类隔离**，于是两条断言当场红了：

| 断言 | 为什么在共享环境下不成立 |
|---|---|
| `identityCheckAll() == 0`（**全库**巡检） | 它是全局的，会被**别的测试类留下的在途令牌**污染（实测报了 4） |
| `dbi == 1000`（已发放 = 库存数） | 压力下有请求以依赖故障失败（从未发放），另有 confirm 失败被静默兜底的路径 |

**共同教训**：断言必须**只依赖自己造的数据**——这是铁律①（用例数据自己建）的延伸，
只是"数据"现在也包括"**别人留下的中间状态**"。

具体做法：把"全库巡检"换成"单模板巡检"（`checkOne(tplId)`——它的注释本来就写着
"集成测试/运维精确断言用"）；把"已发放 = 库存数"换成**真正的守恒式**
"**已发放 + 在途 = 成功数**"（与压力无关，必然成立）。

**一条反复出现的信号**：`dbi == 库存数` 这个断言我改了三版才对
（库存数 → 成功数 → 成功数−在途）。**每改一版我都跑了单跑，而单跑每次都绿**——
真正的判据只有全量。**"单跑绿"在涉及并发/共享状态的用例上几乎不提供信息。**

### 2.3 "注释声称有、实际没有"是最隐蔽的一类债（2026-10-05 补充）

第 12 步的教学文档审查（要求审查者**对照真实代码逐条核对**）抓出两处：

| 声称 | 实际 |
|---|---|
| 代码注释：`WiredSwitchKeysTest` 会扫描所有 `@SwitchGuard` 断言开关标记一致 | **该测试从未存在**（git 全历史零命中） |
| 设计文档：预案的全量物化约束"配错直接启动失败" | 静态初始化块只在**类首次被使用时**执行，而那个类只在方法体里被引用 → 实际是"首次套用预案时才失败" |

**为什么这类债最隐蔽**：它不会报错、不会让测试红、也不影响运行。
后来者读到注释会**信以为真**，于是基于一个不存在的前提做判断——
比如"有测试守着，我改这里应该没问题"。**注释里的承诺比代码里的 bug 更难发现**，
因为没人会去验证一句注释。

**怎么防**：
- 写注释时，凡是"有 X 在守"这类**承诺性表述**，当场确认 X 真的存在；不确认就别写。
- 审查时专门留一个视角**对照代码核对文档里的每个断言**——不是看文档写得通不通顺，
  而是"这句话说的那件事，代码里真的是这样吗"。这一条比语言层面的审查值钱得多。
- 判据能收紧就收紧：把"靠一条测试守"改成"类初始化就断言"，
  或者反过来——**如果一件事真的重要到要写进注释，就让它真的被执行到**。

### 2.4 教学文档的自查门要机械跑（同上）

`study/` 的文档有一套硬约束（术语首现三件套、代码四件套、禁比喻词与强调词、
每节末"容易混淆的地方"等）。写完**必须跑机械检查**，因为人眼会漏：

```bash
grep -nE "ADR-[0-9]|docs/[0-9]|§[0-9]|答辩|讨论0[0-9]" study/<file>.md   # 应为空
grep -nE "灾难|致命|关键|红线|这才是" study/<file>.md                      # 应为空
```

外加人眼补查两类机械查不到的：**术语首现有没有解释**（"装饰器""幂等""CAS""基数"这种
我们习以为常的词，零基础读者未必知道）与**每节末有没有"容易混淆的地方"**。
这两项在 2026-10-05 的审查里各查出十几处——**它们不会出现在 grep 结果里**。

### 2.5 布尔守卫写反：行为与意图**正好相反**，而且不报错（2026-10-08 补充）

写测试基座里那种"只建一次"的守卫时，把
`if (!CAS) { return; } 建();` 写成了 `if (!CAS) { 建(); }`——
于是**第一次不建、之后每次都建**，与意图正好相反。

**症状极具迷惑性**：第一条用例里 `client` 是 `null`（NPE），后面每条都撞
`appId 已存在`。这两条现象看起来毫无关联，我一开始怀疑的是
"容器没清理干净 / 共享容器的数据污染"，而真相只是一处取反。

**两条可复用的经验**：
- **静默的反逻辑最难查**：它不报错、不抛异常，只是把行为翻转。写守卫、开关、极性判断时
  **读一遍它的"第一次"语义**（第一次该走哪支？）比读整段逻辑更有效。
- **两个不相干的症状同时出现，先找共同的上游**（本例共同上游 = 守卫取反：
  "没建" 与 "重复建" 是同一个错误的两个面）。

## 二·补：写"可跟跑脚本"（demo / 反例 / 演练）的坑

这类脚本（`scripts/open-api/*.sh`）是交付物，但它们的正确性**只能靠实跑验证**——
shell 没有编译期检查，逻辑错误往往表现为"远端返回了一个看不懂的码"。
2026-10-05 写演练脚本时，同一类问题连踩三次，模式高度一致：

| 坑 | 症状 | 根因 | 做法 |
|---|---|---|---|
| **对照组的资源不完整** | 断言"B 不受影响"，实际拿到越权码 6011 | 拿 A 的资源去测 B 的隔离 → **测的是越权，不是隔离** | 对照组要有**自己完整的资源**（自己建券、自己发布） |
| **状态在步骤间隐式传递** | 断言"A 领券成功"，报错说"不属于应用 drill-b" | 上一步末尾切换过凭据，这一步**默默继承了** | 每个会用到状态的动作前**显式切换**（`use_app A`），不依赖"上一步结束时是谁" |
| **对照动作不可重复** | 期望 code=0，实际 2003"已发布不可再发布" | 选了一个**非幂等**的动作做对照 | 对照动作要选**可重复**且与被对照动作**同构**的 |

**共同的教训**：脚本里的"隐式上下文"（当前凭据、上一步的状态）是最容易出错的地方，
而且**报错位置离根因很远**（报的是权限错，根因是凭据没切）。
解法是让上下文**显式化**：写出来、每次重设，而不是"继承"。

**断言要对着"契约"而不是"某个恰好可用的值"**：例如"恢复后开关不再拦截"，
判据应是**不是 5001**，而不是**等于 0**——后者会因为"模板已发布"这类无关的业务校验而失败，
把一个正确的实现判成红的。

## 三、工具与环境的坑

| 坑 | 触发条件 | 做法 |
|---|---|---|
| **增量编译假绿/假红** | 同一秒内改文件，Maven 按时间戳粒度跳过重编译 | **跑测试一律 `mvn clean test`**（本项目 STATUS 早就写着"必须 clean"） |
| **IDE 后台构建污染** | VSCode 的 Java 扩展编译产物比源文件新 → Maven 跳过重编译 → 跑的是旧 class，**且编译不报错** | 同上：必须 clean |
| **`mvn ... \| grep` 的退出码** | 管道取的是**末尾命令**的退出码 | 用 `${PIPESTATUS[0]}`，或不用管道 |
| **`min-calls > window-size` 是无效配置** | 想把熔断阈值配得"永不触发"时 | **两个参数必须一起调**（Resilience4j 要求最小样本数 ≤ 滑动窗口） |
| **`setQueryTimeout(0)` 表示"无超时"** | 想按剩余预算收紧 SQL 超时 | 必须**钳到 ≥1 秒**（写反比不写更糟） |
| **Spring 自带 `ContentCachingRequestWrapper` 不重放 body** | Filter 读完 body 后 Controller 读不到 | 自己写可重放的 wrapper（一次性读进内存，之后每次返回新流） |
| **响应在 filter chain 返回前就已提交** | 想在 filter 里回写响应头 | 做不到（Tomcat 写完 body 就 flush）；改走日志/traceId |
| **断言服务端日志要轮询** | "发请求→立刻查日志" | 响应早于日志落盘，存在竞态窗口；轮询等待（且在 detach appender **之前**等） |
| **测试基座偶发"appId 已存在"**（出现 3 次、未定位；**2026-10-08 找到根因**） | 静态守卫 `if (!CAS) { return; } 建()` **取反写反成** `if (!CAS) { 建 }`——"第一次不建、之后每次都建"。同款症状：首条用例里 `client` 为 null（NPE），后面每条都撞"appId 已存在" | 修法见 **§2.5**；全仓 grep `PROVISIONED.compareAndSet` 复查过一遍（`GovernanceMetricsIntegrationTest` 里还留着一处，已修）。**幂等兜底仍然要做**（每用例用独有 appId），但别再把它当成"根因未知" |
| **`pkill -f "<pattern>"` 会杀掉执行它的 shell 自己** | 命令行的字符串里含该 pattern（如 `pkill -f "spring-boot:run"` 写在含这个词的命令里） | 命令返回 144、后续步骤全部没跑。改用更精确的匹配（进程号 / `pgrep` 先查），或把 pkill 单独一条命令执行 |
| **`@SpringBootTest` 默认禁用指标导出** | 测试里访问 `/actuator/prometheus` 得 404，而应用真跑起来完全正常 | 测试类加 `@AutoConfigureObservability`。排查此类"只在测试里出现"的问题，**先启动真实应用访问同一地址**——一步就能把范围缩到"测试环境特有" |
| **Spring 创建 `MeterRegistry` 前会先收集所有 `MeterFilter` bean** | 把 `MeterFilter` 与"需要注入 `MeterRegistry` 的绑定配置"写在同一个类里 | 形成 `MeterRegistry → MeterFilter → … → MeterRegistry` 的环，启动直接失败。**拆成两个类**（过滤器那个不依赖任何东西） |
| **Micrometer 的计数器首次自增前不产生时间序列** | 写"指标应该存在"的断言 | 先触发真实行为再断言。这是对的行为（否则每个可能的标签组合都会有一条恒为 0 的序列），但用例必须知道 |

## 四、本项目的四条长期约定（与 STATUS 同步）

1. **先红后绿**：每条修复/新功能都先写用例、跑出失败、再实现、跑出通过。**红灯输出留档**。
   新功能写不出失败就先建骨架（方法体抛异常）让用例能编译。
2. **收尾三件套**：git 提交 + `docs/STATUS.md` 同步 + `study/工作日志.md` 追加。
3. **改动公共配置或新增必填项后，必须跑一遍受影响的既有用例**
   （教训：`SecretCipher` 的 fail-fast 让本地 dev 直接起不来，靠既有用例抓出）。
   **"受影响的用例"要按"改动会被谁感知到"推，而不是按"我改了哪个功能"**
   （教训：新增一个横切所有写接口的过滤器，破坏了前面步骤写的用例，潜伏两步才暴露）。
   **加了构造依赖后，单测与集成测试都要跑**（教训：`@InjectMocks` 不会自动补新依赖，
   20 例单测里 19 例 NPE 却没人发现）。
4. **多 agent 讨论与观察**（见第一节）。

## 五、一条工作节奏上的经验

**"查根因"与"消除依赖"之间要会切换**：S2 第 7 步遇到两个查不清的现象
（复用 appId 偶发"已存在"、共享字段莫名为 null），最后的处置是**消除对它的依赖**
（每用例自建独有数据），两个现象同时消失。

**判断依据**：当"查清根因"的成本已明显高于"消除对它的依赖"时，选后者——
而**消除依赖通常本身就是更好的设计**。但要用**单跑**先把"环境敏感"与"真实缺陷"区分开，
不要把真实缺陷也当成"环境问题"糊过去。
