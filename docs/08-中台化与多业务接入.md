# 第 8 章 中台化与多业务接入

> 领域定位：本章回答"券系统如何从服务单一业务，演进为服务 N 个业务方的中台平台"。创/发/用/计/控各域能力在前几章已展开，本章专讲**多租户隔离、接入治理、能力复用与业务定制的边界**——这是决定券系统是"一个部门的模块"还是"公司级基础设施"的一章。

## 8.1 解决什么业务问题，在券系统全局中的位置

集团型公司（对标字节/美团/京东到家）的业务现实是：电商、外卖、打车、加油充电、酒店、金融还款……每条业务线都需要券做拉新、促活、转化。券的本质规则高度相似（模板+库存+发放+核销+统计），但每条业务又有自己的"变"：加油券要看油站与供应商，还款券要看借款合同，门店券要看 LBS 围栏。

如果不做中台，就是 N 条业务线 × 各自建一套券系统；做了中台，就是 1 套核心 + N 个薄适配层。中台化要同时兑现三个承诺：

1. **研发效率**：新券玩法从"排期开发"变成"运营自助配置"（汽车之家的目标是"0 开发成本新增优惠券玩法"）；
2. **数据与管控统一**：用户跨业务看到统一券资产，公司层面对券成本统一管控——数禾踩过"各上游业务线的成本分析独立维护、无统一管控"的坑，明确列为短板；
3. **资源与技术复用**：一套高并发发券能力（字节实测 12w~13w QPS）被所有业务共享，而不是每条线各自踩一遍库存热点、超发、幂等的坑。

在券系统全局中的位置：

```
  业务方（玩法与决策层：什么时候、发给谁、发什么）
  ┌─────────┬─────────┬─────────┬─────────┐
  │ 电商大促 │ 外卖门店 │ 加油/充电│ 金融还款 │  ...N 条业务线
  └────┬────┴────┬────┴────┬────┴────┬────┘
       │  app_id + sign + reqId + token
  ╔════╪═════════════════════════════╧══════════════╗
  ║  接入网关层（本章核心之一）                       ║
  ║  验签 / 防重放 / 按上游限流配额 / 业务身份识别      ║
  ╠═════════════════════════════════════════════════╣
  ║  业务中台层（adapter：玩法编排、业务定制）          ║
  ║  券包组合 / 平台券转发商家券 / 跨活动互斥 / 圈人    ║
  ╠═════════════════════════════════════════════════╣
  ║  技术中台层（券核心能力，业务无关）                 ║
  ║  创(模板/组件/表达式) 发(幂等/限领/库存)            ║
  ║  用(锁券/核销/退券) 计(统计) 控(监控/风控/成本)     ║
  ╠═════════════════════════════════════════════════╣
  ║  存储层：MySQL 分库分表 + Redis + MQ + 数仓        ║
  ╚═════════════════════════════════════════════════╝
```

能力地图建议采用"创、发、用、计、控"五字诀（vivo 提出"创发用计"，数禾补充了"控"——监控、策略、告警、成本管控；多租户场景下"控"必须升级为一等公民，因为配额、限流、成本分摊都挂在它上面）。

## 8.2 朴素实现（v1）会怎么挂

v1 有两种朴素形态，**都会挂，且挂法不同**：

**形态 A：垂直复制**——每条业务线复制一套券模块、一套库。京东到家对中台化前的复盘原话是四个问题：每新增一种玩法就垂直拆分式编码，重复逻辑代码多、不易维护；系统与业务代码耦合度太高，难以抽象通用逻辑，测试成本大；复杂度到了一定程度后"不敢随意修改核心业务代码"；新员工学习成本高。vivo 在单体时代 additionally 踩到：海量发券达到单库单表瓶颈、券模块与商城高耦合直接拖累整站接口性能、券迭代被商城版本发布节奏绑架。具体故障形态：业务 A 修一个超领 bug，业务 B 的同款 bug 还在，因为代码已分叉；全公司算不出"今年券花了多少钱"，因为数据散在 N 套库里。

**形态 B：无业务身份的共享服务**——所有业务方调同一个券服务、写同一批表，但没有贯穿的业务身份（biz_id）。这个形态更隐蔽也更致命，挂法非常具体：

- **共享模板串台**：没有按 biz_id 隔离模板，外卖的运营在后台能搜到打车业务配置中的券模板并误发。资损形态：A 业务的高额券被 B 业务的用户领取。
- **无按上游限流的 noisy neighbor**：春节红包雨 12w QPS 全部打在共享的 MySQL/Redis 上（字节实测单 MySQL 写约 4000 QPS、单 Redis 分片写约 2w QPS 就到瓶颈），同一时刻电商结算页的"查可用券"超时 → 下单失败 → 直接 GMV 资损。京东到家的同类教训是"高流量 C 端应用与结算页用券流程未隔离，互相影响"。
- **接口契约各自为政**：A 业务传 `userId`，B 业务传 `uid`；没有统一的 reqId 幂等契约，业务方超时重试直接超发——vivo 明确把"接口不幂等 + 业务方重试 = 超发"列为资损级教训。
- **字段膨胀死循环**：每接一个新业务就往模板表加字段（`oil_station_limit`、`loan_contract_type`……），加字段要 DDL、要发版、要全量回归，接入速度反而不如各自建——中台名存实亡。

一句话总结 v1 的死因：**没有"业务身份"这个第一公民，就没有隔离、配额、幂等和计费的锚点**。

## 8.3 方案演进：v1 → v2 → v3

**v1（垂直复制/裸共享）**：解决"能用了"，问题是 8.2 的全部。

**v2（共享券服务 + biz_id 字段 + 统一接口）**：在共享服务上引入业务身份，统一"创发用计"四个标准接口，表里都带上 biz_id。解决了串台与数据统一，但引入三个新问题：

1. **发布列车问题**：N 个业务方共用一个服务，任何一个业务的需求都要全量回归、全量发布；一个业务触发的 bug 全体买单。迭代速度被最慢的业务拖住（vivo 独立前"迭代受商城版本发布安排限制"就是这个问题的单业务版）。
2. **规则无法收敛**：各业务的用券条件差异大，固定字段模型装不下，每变一次条件就要扩表字段 + 改映射 + 改校验代码（汽车之家原话：笨拙粗放、难维护）。
3. **隔离仍不彻底**：biz_id 只是过滤字段，不是资源边界；限流、配额、监控若不按 biz 维度建设，大促依然互相打死。

**v3（双层中台 + 可装配模型，大厂最终形态）**：对应京东到家的方案——业务层与服务层水平合并成两层：**业务中台**承接玩法差异（券包、互斥、平台券转发商家券、圈人定向），保证业务隔离性；**技术中台**以 RPC 提供建券/领券/展示/用券等最通用能力，风控这类通用逻辑下沉，"一处修改，到处受用"。再叠加汽车之家的**可装配四层模型（组件 → 模板 → 批次 → 活动）**与**规则条件表达式**，让 80% 的长尾玩法由运营配置产出而非研发排期。

v3 引入的新问题（必须正面回答，否则中台会退化）：

- **复杂度税**：组件库、表达式引擎、双层架构本身就是研发负担，业务量小的时候是负资产；
- **优先级冲突**：所有业务都是"客户"，资源紧张时先保谁？必须有配额 + 降级优先级机制，否则靠人情排序；
- **adapter 层腐化风险**：业务中台如果界限不清，会变成"分布式单体"——改一个玩法要同时改业务中台和技术中台，回到 v1；
- **配置治理**：配置化把权力交给运营，一次错配（库存多打一个零）就是全量资损，必须配审批、灰度与审计。

## 8.4 大厂最终形态设计

### 8.4.1 多租户核心表 DDL

业务身份是一切的锚点，先建租户表与幂等表，再改造模板/记录表（均为核心骨架字段，可按需扩展）：

```sql
-- 1. 业务方接入注册表（多租户根表）
CREATE TABLE `biz_app` (
  `id`           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `app_id`       VARCHAR(32)  NOT NULL COMMENT '业务身份，如 ec/ride/oil/loan',
  `app_name`     VARCHAR(64)  NOT NULL,
  `app_secret`   VARCHAR(128) NOT NULL COMMENT 'HMAC 签名密钥，加密存储',
  `status`       TINYINT NOT NULL DEFAULT 1 COMMENT '1启用 0禁用 2沙箱',
  `quota_qps`    INT NOT NULL DEFAULT 500 COMMENT '网关令牌桶容量（配额）',
  `priority`     TINYINT NOT NULL DEFAULT 5 COMMENT '1最高；过载降级时先拒低优先级',
  `callback_url` VARCHAR(256) DEFAULT NULL COMMENT '核销/过期/发放结果事件回调',
  `owner`        VARCHAR(64) NOT NULL COMMENT '业务方接口人，治理用',
  `created_at`   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
                 ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_app_id` (`app_id`)
) ENGINE=InnoDB COMMENT='业务方接入注册表';

-- 2. 发券幂等表（幂等键必须含业务维度！）
CREATE TABLE `issue_idempotent` (
  `id`         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `biz_id`     VARCHAR(32) NOT NULL,
  `req_id`     VARCHAR(64) NOT NULL COMMENT '业务方请求唯一ID',
  `coupon_id`  BIGINT      DEFAULT NULL COMMENT '成功后回填，幂等命中时直接返回',
  `state`      TINYINT NOT NULL DEFAULT 1 COMMENT '1处理中 2成功 3失败可重试',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_biz_req` (`biz_id`, `req_id`)
) ENGINE=InnoDB COMMENT='发券幂等控制表';

-- 3. 券模板表（biz 维度唯一 + 规则表达式承载长尾差异）
CREATE TABLE `coupon_template` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `biz_id`        VARCHAR(32)  NOT NULL,
  `template_code` VARCHAR(64)  NOT NULL,
  `name`          VARCHAR(128) NOT NULL,
  `type`          TINYINT NOT NULL COMMENT '1满减 2折扣 3立减 4兑换',
  `face_value`    INT NOT NULL COMMENT '面额，分',
  `total_stock`   BIGINT NOT NULL DEFAULT 0,
  `stock_seg`     INT NOT NULL DEFAULT 8 COMMENT '库存分段数（热点模板调大）',
  `rule_expr`     VARCHAR(1024) DEFAULT NULL COMMENT '用券规则表达式，见8.4.5',
  `bind_token`    VARCHAR(64) NOT NULL COMMENT '模板级领取令牌，C端领券校验',
  `valid_type`    TINYINT NOT NULL COMMENT '1绝对时间 2领取后N天',
  `valid_start`   DATETIME DEFAULT NULL,
  `valid_end`     DATETIME DEFAULT NULL,
  `valid_days`    INT DEFAULT NULL,
  `limit_per_user` INT NOT NULL DEFAULT 1,
  `limit_per_day`  INT NOT NULL DEFAULT 0 COMMENT '0不限',
  `status`        TINYINT NOT NULL DEFAULT 0 COMMENT '0草稿 1生效 2停用',
  `version`       INT NOT NULL DEFAULT 0 COMMENT '乐观锁，模板变更加1',
  `created_at`    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_biz_code` (`biz_id`, `template_code`)
) ENGINE=InnoDB COMMENT='券模板表';

-- 4. 用户券记录表（分库分表，uid 路由；couponId 内嵌路由因子，借鉴数禾）
--    couponId = uid前15位 + '-' + 雪花18位 → 任一ID可独立路由，免维护映射表
CREATE TABLE `coupon_record_0007` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `coupon_id`   VARCHAR(40) NOT NULL COMMENT 'uid前15位+雪花，全局唯一且内嵌路由',
  `uid`         VARCHAR(64) NOT NULL,
  `biz_id`      VARCHAR(32) NOT NULL COMMENT '业务身份，必须贯穿，禁止NULL',
  `template_id` BIGINT NOT NULL,
  `status`      TINYINT NOT NULL COMMENT '1待使用 2锁定 3已使用 4已过期 5已回收 6待激活',
  `order_id`    VARCHAR(64) DEFAULT NULL COMMENT '核销/锁定的订单号',
  `received_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `expire_at`   DATETIME NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_coupon` (`coupon_id`),
  KEY `idx_uid_status` (`uid`, `status`)
) ENGINE=InnoDB COMMENT='用户券记录表，按 uid 分库分表';
```

要点说明：记录表按 uid（而非 biz_id）路由——同一用户在全业务的券资产落同一分片，"我的卡包"一次路由查全；biz_id 只做过滤字段。京东到家用 8 库 × 1024 表扛 40 亿条记录（归档后 15 亿），证明 uid 路由 + 冷热归档的路线在超大规模成立。

### 8.4.2 Redis key 设计与数据结构选型

| key | 结构 | 说明 | 选型理由 |
|---|---|---|---|
| `c:tpl:{biz}:{tplCode}` | String(JSON) | 模板快照 | 读多写极少、整对象读取，无需 field 级操作；配合本地缓存二级缓存（字节方案：根除 Redis 超时万分之2~3的固有失败） |
| `c:stock:{biz}:{tplId}:{seg}` | String(int) | 分段库存 | DECRBY 对纯字符串原子扣减；分段打散写热点，每段可落不同 Redis 分片 |
| `c:uc:{biz}:{uid}` | Hash | 用户券包，field=couponId | 单用户券的增删改天然是 field 级操作（京东到家同款），避免大 key 整体序列化 |
| `rl:{appId}:{api}` | Hash(tk,ts) | 令牌桶 | 一次 Lua 完成补充+扣减，支持突发流量整形，见 8.4.4 |
| `idem:{biz}:{reqId}` | String, EX=300 | 幂等防抖前置 | 高频重复请求在 Redis 层拦截，DB 唯一索引兜底（双层幂等） |
| `nonce:{appId}:{nonce}` | String, EX=300 | 防重放 | SET NX EX，重复 nonce 直接拒绝 |

注意 `c:uc` 建议按 biz 拆 key（`c:uc:{biz}:{uid}`）而不是把多业务塞进一个 Hash：一是遵循"按业务拆数据源"原则（京东到家把门店券/运费券/红包拆三套数据源，把 1.5GB/s 出流量降下来），二是避免单个用户 key 膨胀成大 key。

### 8.4.3 接入与鉴权设计

参考京东到家的 Token 双重绑定（业务身份 Token 同时绑定到券信息上，领券时校验请求 Token 与券上 Token 一致，防越权/伪造领券），并补齐它没展开的防重放。分两类调用方：

- **服务间调用（业务后端 → 中台）**：HMAC 签名。`sign = HMAC-SHA256(appSecret, appId|uid|templateCode|reqId|ts|nonce)`，网关校验签名 + `|now - ts| ≤ 300s` + `SETNX nonce` 防重放。
- **C 端直领（用户在活动页领券）**：模板级 bind_token。领券请求携带的活动 token 必须与模板的 bind_token 一致——A 业务投放的活动页拿不到 B 业务模板的 token，从入口上杜绝跨业务刷券。

### 8.4.4 按上游限流（配额）的 Lua 实现

```lua
-- KEYS[1] = rl:{appId}:{api}
-- ARGV[1]=capacity(桶容量=配额*突发倍数) ARGV[2]=rate(每毫秒补充=配额/1000)
-- ARGV[3]=now(ms)
local key      = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate     = tonumber(ARGV[2])
local now      = tonumber(ARGV[3])
local last  = tonumber(redis.call('HGET', key, 'ts')) or now
local tokens= tonumber(redis.call('HGET', key, 'tk')) or capacity
local filled = math.min(capacity, tokens + math.max(0, now - last) * rate)
local pass = 0
if filled >= 1 then
  redis.call('HSET', key, 'tk', filled - 1, 'ts', now)
  pass = 1
else
  redis.call('HSET', key, 'ts', now)   -- 空桶也要推进时间戳，否则会欠账
end
redis.call('PEXPIRE', key, 60000)
return pass
```

部署在两处：接入网关（粗粒度，按 appId 总配额）+ 发券服务内（细粒度，按 appId × 接口）。配额来自 `biz_app.quota_qps`，控制台可动态调整——大促前给电商业务调高、给低优先级业务调低，这就是"资源紧张时先拒谁"的机械化答案，替代人情排序。

### 8.4.5 可装配模板与规则表达式（承接业务差异的关键）

四层模型（组件→模板→批次→活动）中，模板拆**固定区**（券共有属性：标题、面额、库存、有效期、承担比例）与**可变区**（业务限制组件：限城市、限门店、限供应商、限油品……）。可变区的条件不落固定字段，而是编译成一行**规则条件表达式**存 `rule_expr`，例如汽车之家的实例：

```
[coupon_city]_in(111010,120000) && ([coupon_order]>10 && [coupon_order]<100) && [coupon_tag]_in(123)
```

语义：北京或天津、订单金额 10~100、品类标签 123 可用。用券时把订单上下文（金额、城市、商家、商品标签等）组装成 Map，正则替换占位符后求值，**一次表达式求值替代 N 次字段循环校验**——这是"业务无关的通用验券接口"得以成立的核心。

工程上必须做的安全加固（原素材未覆盖，属于必须补齐的部分）：

1. **编译而非每次解析**：templateId → AST 缓存在本地 ConcurrentHashMap，模板 version 变更时失效重编译；
2. **白名单语法**：只允许 `_in / = / > / < / >= / <= / && / ||` 与数字、占位符，禁止任意函数调用（汽车之家用 `EvalExpr` 这类动态求值，在多租户开放环境下有表达式注入风险）；
3. **长度限制**（≤1024）+ **求值超时/节点数上限**，防慢表达式打满 CPU；
4. 高频核心条件（有效期、限领、面额）仍走固定字段索引，表达式只承接长尾——性能与灵活兼顾。

### 8.4.6 发券接口契约与时序

```java
public interface CouponIssueService {
    /** 统一发券（同步，单张） */
    IssueCouponResp issue(IssueCouponReq req);
    /** 定向批量发券（异步，走 MQ，亿级人群） */
    String batchIssue(BatchIssueReq req);          // 返回 taskId
    /** 查询用户券（跨业务或单业务） */
    List<CouponDTO> listUserCoupons(long uid, String bizId, int status, PageParam page);
    /** 锁券/核销/退券（用券域，见对应章节） */
    UseResult use(String couponId, String orderId, UseContext ctx);
    void giveBack(String couponId, String orderId);
}

public class IssueCouponReq {
    private String appId;        // 业务身份
    private long   uid;
    private String templateCode; // 模板编码（biz 内唯一）
    private String reqId;        // 业务方请求唯一ID —— 幂等键
    private String token;        // C端领券场景必填，模板 bind_token
    private long   ts;
    private String nonce;
    private String sign;         // HMAC(appSecret, appId|uid|templateCode|reqId|ts|nonce)
}
public class IssueCouponResp {
    private String couponId;     // uid前15位+雪花，内嵌路由因子
    private int    status;       // 券初始状态：待使用/待激活
    private boolean duplicated;  // true=幂等命中，返回上次结果
}
```

同步发券时序（编号步骤）：

1. 业务方构造请求，生成全局唯一 `reqId` 并签名；
2. 接入网关：验签 → 校验 ts 偏移 ≤ 300s → `SETNX nonce:{appId}:{nonce} EX 300` 防重放 → Lua 令牌桶按 appId 限流，超额直接 429（不消耗下游资源）；
3. （可选）路由到业务中台 adapter 做玩法编排：券包拆单、平台券转商家券预校验；
4. 技术中台发券服务：本地缓存→Redis 读模板（二级缓存），校验状态、有效期、`template.biz_id == appId`；
5. C 端领券场景校验请求 token 与 `template.bind_token` 一致（防跨业务越权）；
6. 幂等：`INSERT issue_idempotent(biz_id, req_id)`；唯一键冲突→查回 couponId，置 `duplicated=true` 返回。同时可先查 `idem:{biz}:{reqId}` 做前置防抖；
7. 用户限领校验：`limit_per_user / limit_per_day`（京东到地的三层校验：总库存+用户限领+每日限领）；
8. 库存扣减：分段库存 + 随机不重复轮询 + 售罄分片跳过（细节见库存章节）；
9. 写 `coupon_record`（uid 路由分片），状态机初始化为"待使用/待激活/待激活条件"；
10. 发 MQ 发券结果事件：计（统计）、控（监控告警）、业务方 callback（带签名）三路消费；
11. 返回 couponId。第 8~9 步失败的补偿：处理中状态的幂等记录由对账任务扫描重试或反向回补库存，保证最终一致。

### 8.4.7 新业务接入流程（编号）

1. 控制台提交接入申请：业务背景、预估日常/峰值 QPS、券类型、预算归属、接口人；
2. 平台审核，分配 app_id/app_secret，设定 `quota_qps` 与 `priority`，登记 callback_url；
3. 沙箱环境（status=2）联调：强制通过"签名错误、重放、幂等重试、限流拒绝"四类用例才准出；
4. 生产灰度：配额从 10% 起步，观察按 appId 维度的成功率/RT/库存监控大盘；
5. 逐步放量至约定配额，签署 SLA（可用性、RT、故障响应）；
6. 纳入日常治理：变更审批、配额复核（每季度）、成本分摊报表。

### 8.4.8 治理与容量

- **按 appId 的监控大盘**：QPS、成功率、tp99、库存水位、限流拒绝数——"控"域在多租户下的具体形态；
- **资源隔离**：高流量 C 端展示类应用与结算页核销链路分开部署（京东到家教训：混部会互相拖垮）；字节的做法补充了跨物理区域分布实例防集群级故障；
- **容量规划**：按压测值的 1.5 倍冗余申请线上资源（字节经验数字：MySQL 单机写约 4000 QPS、Redis 单分片写约 2w/读约 10w，先自底向上压单点瓶颈再整体压）；
- **成本分摊**：按 biz_id 汇总计"发券量×面额×承担比例"，月度出账给各业务线——数禾把"成本管控散落"列为体系短板，中台的机会就是把这件事一次做对。

## 8.5 素材间方案分歧与推荐

1. **业务逻辑的归属**：数禾主张"发不发、发给谁"的决策完全归上游，券系统只做执行（风控/黑名单/幂等/扣库存）；京东到家主张建业务中台承接玩法逻辑；汽车之家则把玩法做进券系统的可装配组件里。**推荐：三层切分——决策归业务方，玩法编排归业务中台 adapter，纯执行与原子能力归技术中台**。理由：把玩法做进技术中台（汽车之家路线）在单一业务线内效率最高，但多租户下中台会被某一个业务的特有概念污染（加油券的"供应商"对还款券毫无意义），最终回到字段膨胀；adapter 层让业务差异止步于 adapter，核心保持业务无关。
2. **能力地图四字还是五字**：vivo"创发用计" vs 数禾"创发用计控"。**推荐五字**：多租户下"控"（配额/限流/监控/成本）是平台活命的域，不是可选项。
3. **规则承载方式**：汽车之家全表达式化 vs 传统固定字段。**推荐混合**：高频核心字段（面额/有效期/限领）固定列+索引，长尾条件进表达式。纯表达式让每次校验都多一层解析，且热点查询（按城市筛可用券）无法下推索引。
4. **多业务数据路由**：按 biz 分库（物理强隔离）vs 按 uid 路由 + biz 过滤（本文方案）。**推荐后者，超大业务再独库/独集群**：uid 路由保住"跨业务统一卡包"这一中台核心体验；个别业务量级够大时以独立部署集群（应用层隔离）解决，而非把路由键改成 biz。
5. **存储演进终点**：数禾在 10 亿+ 行后计划用 TiDB 替换分表（换"秒级变更字段、逻辑表、动态扩缩节点"）；京东到家/vivo/字节继续 MySQL 分库分表 + 冷热归档。**推荐 MySQL 分库分表起步**：中台前期最痛的是字段频繁变更，先用"扩展 JSON + 表达式"化解，真到数十亿行且扩容频繁时再评估分布式数据库——且注意数禾当时是规划表述而非已落地结论。
6. **鉴权深度**：京东到家 Token 只做"一定安全拦截"（无防重放讨论）vs 通用开放平台规范。**推荐 HMAC 签名 + 时间戳 + nonce 三件套**：多业务接入后，重放攻击（截获一次合法领券请求重发 N 次）是真实资损向量，Token 静态校验挡不住。

## 8.6 踩坑清单（按严重程度排列）

1. **biz_id 未贯穿全链路（串券/数据污染，资损级）**：某张表、某个 Redis key、某条 MQ 消息漏带业务身份，A 业务的券进了 B 业务的账。怎么发现：按 biz_id 的日终对账（各 biz 发券量 vs 总量恒等式）、用户投诉"卡包里出现没用过的券"。怎么防：所有表 DDL 强制 `biz_id NOT NULL`、Redis key 模板强制带 `{biz}` 段、用 ORM 拦截器在写入层自动注入、code review checklist 固定检查项。
2. **无按上游限流（noisy neighbor 打挂全平台）**：一个业务的大促把共享 MySQL/Redis 打穿，其他业务的结算页用券超时，直接 GMV 损失。怎么发现：按 appId 维度的监控大盘（没有大盘就先建大盘）、故障时看"谁涨了"。怎么防：网关+服务双层令牌桶、配额动态可调、过载时按 priority 先拒低优先级、C 端展示与核销链路应用隔离。
3. **幂等键设计错误（重试超发，资损级）**：幂等唯一键只用了 reqId 没含 biz_id——两个业务方各自的自增 reqId 撞号，B 业务命中 A 业务的幂等记录直接拿到券返回。怎么发现：幂等命中但 couponId 属于另一 biz 的告警。怎么防：唯一索引 `(biz_id, req_id)`，接口文档强制 reqId 语义（业务方内唯一），Redis 防抖 + DB 唯一索引双层兜底。
4. **签名无防重放（盗刷资损）**：只验静态 token/sign，抓包重放领券接口刷库存。怎么发现：同 nonce/同签名请求重复出现的风控告警、单 IP/单设备异常领取。怎么防：timestamp 窗口 + nonce SETNX + 风控埋点。
5. **模板 bind_token 不校验（跨业务越权领券）**：A 业务的活动页改 URL 参数就能领 B 业务的高额券。怎么发现：领取来源 biz 与模板归属 biz 的交叉对账。怎么防：领券入口强制 token 与模板 bind_token 一致（京东到家方案），模板后台按 biz 隔离可见性。
6. **接入靠加字段迁就新业务（架构腐化）**：模板表三年膨胀出上百个业务字段，DDL 越来越慢，最终没人敢动。怎么发现：schema diff 审查中"为单一业务加列"的占比。怎么防：固定区/可变区分离，长尾差异一律走组件 + 表达式，核心表列数设硬上限。
7. **表达式注入与慢表达式（稳定性）**：开放配置的表达式把服务 CPU 打满，或恶意表达式调用危险函数。怎么发现：求值耗时 P99 监控、CPU 异常告警。怎么防：白名单语法编译成 AST、编译缓存、节点数/长度上限、沙箱求值。
8. **业务方绕过中台直连 DB/缓存**：业务方为图方便直接查券库"做报表"，写入侧一旦也绕过，缓存与 DB 不一致且无审计。怎么发现：DB 慢日志中出现非中台服务的来源、账号权限审计。怎么防：账号权限只授给中台应用，数据需求一律走统一查询 API/数仓镜像。
9. **配置/模板变更无灰度（错配全量事故）**：运营把库存多打一个零、把面额配错，直接全量资损。怎么发现：变更 diff 审批时人工核对 + 关键指标（面额×发放量）预算告警。怎么防：变更双人审批、先灰度小批次放量、成本管控域的预算硬上限自动熔断。
10. **不停机迁移双写期的 UPDATE 丢失**：从单库迁分库分表时，迁移期 UPDATE 打到"分表还没有该数据"的行上丢失（数禾明确处理过：UPDATE 前判断分表是否已有数据，没有则回写单表）。怎么发现：双写期两边数据量/校验和对账。怎么防：迁移期 UPDATE 走"分表存在才更新，否则更新单表"的条件写，收尾前全量对账。

## 8.7 本章小结

中台化的本质不是"把服务做大"，而是**把业务身份做成第一公民，把变与不变分层**：不变的原子能力（幂等、库存、状态机、风控）沉到技术中台一处修改到处受用；易变的玩法（券包、互斥、转发、圈人）隔离在业务中台 adapter 各自演进；难以预测的长尾规则交给组件装配与表达式让运营自助。接入网关的"验签+防重放+按上游限流"三件套与贯穿全链路的 biz_id，是这一切的地基——地基上再谈 12w QPS 的发券能力才有意义。
