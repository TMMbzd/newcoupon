# 第 9 章 幂等、一致性、资损防控与稳定性

> 领域定位：券系统里"钱"的安全带。前面章节讲的模板、发放、核销是"把事做成"，本章讲的是"在任何故障、任何并发、任何重试下都不多花钱、不丢数据、不雪崩"。

---

## 9.1 这个领域解决什么业务问题，在全局中的位置

优惠券不是虚拟道具，是**记账凭证**。每一张未核销的券都是一笔或有负债：100 万张 10 元券就是 1000 万元的负债挂账。因此这个领域的四个关键词，本质上对应四类线上事故：

| 关键词 | 对应的业务问题 | 对应的事故形态 |
|---|---|---|
| 幂等 | 同一个发券/核销请求被执行多次 | 用户重试、MQ 重投、网络超时重发 → 一人多券、重复核销 → **直接资损** |
| 一致性 | 库存在 Redis、券记录在 MySQL、通知走 MQ，三处数据对不上 | "抢到了但券包看不到"、Redis 余量与 DB 脱钩 → 超发 |
| 资损防控 | 即使前两层全部失效，系统仍有最后防线 | 对账发现超发时已损失千万；运营配错库存一键放出自伤 |
| 稳定性 | 万级~十万级 QPS 毛刺下系统不倒 | 单行热点打满 DB、大 Key 阻塞整个 Redis 集群、Redis 抖动拖垮全链路 |

在券系统中台的全局位置（本章防线贯穿所有写路径）：

```
  B端运营 ──建券──► ┌───────────────────────────────────────────┐
                   │  优惠券系统中台                              │
                   │                                           │
  上游业务方        │   模板域 ◄────┐                            │
  (App/活动页)      │   (规则/库存)  │                            │
      │            │              │  本章防线覆盖所有写路径：       │   C端查询/展示
      ├─发券/领券──►│   发放域 ──────┤  · 幂等：一个请求一张券      │ ────────────►
      │            │              │  · 一致性：Redis/DB/MQ 对齐   │
  交易/订单系统     │   核销域 ──────┤  · 资损防控：防超发+对账+熔断 │   结算页用券
      ├─用券核销───►│   (用券/退券)  │  · 稳定性：热点/大Key/降级    │ ────────────►
      └─退款退券───►│              │                              │
                   │   生命周期域 ◄─┘                             │
                   │   (过期/作废)                                │
                   └───────────────────────────────────────────┘
                        │              │              │
                        ▼              ▼              ▼
                     MySQL 分库      Redis 集群      RocketMQ
                    (事实源/兜底)   (库存/热点缓冲)  (异步/削峰/延时)
```

一句话概括本章的设计哲学：**Redis 负责"快"，MySQL 负责"对"，MQ 负责"稳"，对账负责"兜底**。任何一层都可能坏，但四层串起来后，单点故障不再等于资损。

## 9.2 朴素实现（v1）会怎么挂：五个具体故障场景

v1 的典型形态（几乎所有没做过高并发营销系统的团队第一次都这么写）：

```java
// v1：先查后插做幂等 + MySQL 直接扣库存
@Transactional
public void grant(long templateId, long userId) {
    int cnt = userDao.countCoupon(templateId, userId);
    if (cnt >= template.getUserLimit()) throw new BizException("超出限领");
    int left = stockDao.getleft(templateId);
    if (left <= 0) throw new BizException("已抢光");
    couponDao.insert(buildCoupon(templateId, userId));   // 直接 INSERT
    stockDao.decrease(templateId);                        // UPDATE stock SET left = left - 1
}
```

这段代码在压测环境毫无问题，上线大促会在四个方向同时挂：

**场景 A：并发超领（先查后插的竞态窗口）**
大促 0 点开抢，用户双击领券按钮（或黄脚本报文重放），同一 uid 两个请求相差 3ms 到达两个服务实例。两个事务都执行 `countCoupon` 得到 0（对方尚未提交），都通过校验，各插一张券。限领 1 张的 100 元无门槛券被同一人领走 2 张。并发 500 时该竞态几乎必现；面向脚本的活动中，攻击者刻意并发打这个窗口，一个 UID 可以领走上百张。这是**最直接的资损**。

**场景 B：库存行锁热点打垮整个库**
单批次 10w QPS 抢券，所有 UPDATE 落在 stock 表同一行上串行排队。字节跳动团队的实测数据是**单 MySQL 写入约 4000 QPS，超过后 I/O 时延急剧增长**。10w QPS 打一行意味着 96% 的请求在等行锁，连接池被占满，`too many connections` 之后**同库的订单、支付全部一起挂**——这就是从"券系统故障"升级成"整站故障"的雪崩路径。

**场景 C：上游重试导致超发**
领券接口超时 500ms，上游按框架默认重试 3 次。第一次请求实际成功了（只是响应没来得及回），后两次又各发一张。vivo 商城的文章明确记录了这个坑：网络超时/异常下领券结果未及时返回，业务方重试，接口不幂等造成超发。按 0.1% 的超时率、1000 万次领券估算，就是 1~2 万张多发。

**场景 D：只信 Redis 的库存，主从切换丢写**
意识到场景 B 后很多人直接把库存搬到 Redis 用 `INCRBY`，但不维护与 DB 的任何不变式。Redis 主从切换瞬间，未同步到从库的扣减结果丢失（已扣到 -3000 的计数回退到 0 附近），继续放量，实际发放量超过 DB 记录的总库存。**超发在事后对账才被发现，钱已经流出去了。**

**场景 E：大 Key 把整个 Redis 集群拖慢**
门店券场景：`Key = CouponId`，`Value = 适用门店 ID 集合`，接近上万家门店。京东到家团队踩过的真实事故：高峰期所有接口都变慢，问题分片每天漂移，Redis 无慢日志，降级和限流都无效——因为根因是每次读这个 Key 就要拉出上万元素的 Value，单分片流出量达到几百 MB/s，Redis 主线程被单次大 Value 操作拖长，**该分片上所有 Key 集体变慢**。流量侧手段救不了存储侧结构问题。

五个场景的后果排序：A/C/D 是**资损**（多发券=多花钱），B/E 是**可用性事故**（整站雪崩），但 B 的雪崩会诱发 C（超时重试洪峰），形成复合事故。

## 9.3 方案演进：v1 → v2 → v3

### v2：原子化——把"查 + 判 + 扣"收进一个原子操作

v2 针对 A、B 两个问题做两件事：

1. **库存扣减与限领校验全部收进一段 Lua 脚本**，在 Redis 侧原子执行。腾讯云 MALL 团队的方案是教科书式的：一个 Lua 内完成"幂等 → 库存 → 批次日上限 → 用户日限 → 用户总限"五重校验加五次计数写入，任一校验失败直接返回语义化错误码（-1 ~ -7），全程一次网络往返、天然无锁。
2. **幂等改为数据库唯一索引兜底**：用户券表上加唯一字段，`INSERT` 撞唯一索引即捕获 `DuplicateKeyException`，查出已发的券按成功返回。这是 vivo 商城的选择——他们在"现有表加唯一字段"和"新建幂等表"之间选了前者（避免表关联的性能与改造代价），代价是要用脚本给历史数据刷唯一值、并为不传唯一编码的业务方服务端代生成。

v2 解决了竞态与行锁，但引入**三个新问题**：

- **Redis 与 MySQL 的一致性问题浮出水面**：Redis 扣成功后券怎么落库？同步写怕打垮 DB（场景 B 的变体），异步写就有"扣了但没发出去"的窗口。
- **Redis 故障 = 库存丢失**：纯 Redis 计数没有 DB 侧不变式，回到场景 D。
- **热点 Key**：一个爆款批次的所有请求打同一个 stockKey，Redis 单分片写瓶颈约 2w QPS（字节实测），单批次理论上限被锁死。

### v3：最终形态——异步化、分段化、可对账、可降级

v3 在 v2 之上补四块拼图，每块都对应一个新问题的解法：

1. **库存异步分段增补**（腾讯云 MALL）：Redis 余量低于 M 时异步从 DB 增补 N 个，维持"Redis 余量 ≤ DB 未放出量"的不变量。Redis 崩溃最多丢 N×段数个额度，DB 是最后防线——把场景 D 的"无界超发"变成"有界少发"。
2. **分段库存打散热点**（字节跳动）：建模板时把库存拆成多个子 Key，扣减时按"随机不重复数组"轮询尝试，售罄的分片本地记下来直接跳过。单批次 12w QPS 均摊到 6+ 个 Redis 分片。
3. **落库路径分场景**：C 端主动领券同步双 INSERT（用户券 + 发券流水，同库同事务，天然强一致且只花一次 DB 往返——字节方案里"单次发券对 MySQL 是一次非事务性写入"正是 12w QPS 容量估算的依据）；定向发券/批量券包走 MQ 异步 + 消费端幂等（vivo 的亿级定向发券：去事务 + 轻校验 + 归集批量插入 + 动态调速）。
4. **对账与降级**：准实时对账 Redis 余量 vs DB 流水，差异即告警；Redis 故障时切换到 DB 分段库存模式降级放量（vivo 的主方案在这里反过来成为降级路径）。

演进脉络一张表：

| 版本 | 核心手段 | 解决 | 引入的新问题 |
|---|---|---|---|
| v1 | 先查后插 + DB 直扣 | 能跑 | 竞态超领、行锁雪崩、重试超发 |
| v2 | Redis Lua 原子扣减 + 唯一索引幂等 | 竞态、DB 热点 | Redis/DB 一致性、Redis 故障丢库存、单 Key 热点 |
| v3 | 分段库存 + 分段增补 + 分场景落库 + 对账降级 | 热点、故障资损、一致性 | 复杂度上升：段间倾斜、段间调拨、对账修复逻辑本身要幂等 |

## 9.4 大厂最终形态：可直接落地的设计

### 9.4.1 总体链路

```
C端领券请求
  │ ①接入层：鉴权/按上游限流/提取幂等号
  ▼
②模板校验 ◄──── 二级缓存(本地Caffeine + Redis，定时刷新+分布式锁保护回写)
  ▼
③Redis幂等前置 SETNX c:idem:{no}  ──命中──► 读终态结果直接返回（快速幂等）
  ▼ miss
④分段扣减：随机不重复段序 → 逐段执行Lua（-3换段，其余码直接返回）
  ▼ 成功
⑤同库本地事务：INSERT user_coupon_xx(唯一索引) + INSERT grant_flow(记录段号)
  │ 成功                          │ DuplicateKey → 查已有券，幂等成功返回
  ▼                              │ 其它异常 → Lua反向回补段库存 + 释放幂等标记
⑥写幂等终态结果(TTL 24h)，返回券信息   （回补失败落补偿表，对账修复）

旁路A：增补Job   段left < M → DB原子转移N到Redis
旁路B：对账Job   每5min增量 + T+1全量，Redis余量 vs (总量-db_left-流水数)
旁路C：熔断      单位时间发放量超阈值 → 自动下架模板
```

### 9.4.2 表结构 DDL

```sql
-- 1. 券模板表（B端写入，读多写少，二级缓存承载）
CREATE TABLE coupon_template (
  id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  template_id   BIGINT NOT NULL COMMENT '分布式ID，对外暴露',
  name          VARCHAR(64) NOT NULL,
  type          TINYINT NOT NULL COMMENT '1满减 2折扣 3无门槛 4兑换',
  total_amount  INT NOT NULL COMMENT '总库存（不变，追加发券另起批次或走调增流程）',
  shard_num     INT NOT NULL DEFAULT 1 COMMENT '库存分段数，热点模板>1',
  user_limit    INT NOT NULL DEFAULT 1 COMMENT '每人总限领',
  daily_user_limit INT NOT NULL DEFAULT 1 COMMENT '每人每日限领',
  daily_batch_limit INT NOT NULL DEFAULT 0 COMMENT '批次每日发放上限，0=不限',
  valid_type    TINYINT NOT NULL COMMENT '1固定区间 2领后N天',
  valid_start   DATETIME, valid_end DATETIME, valid_days INT,
  rule_snapshot VARCHAR(1024) COMMENT '规则快照，冗余给用户券表',
  status        TINYINT NOT NULL DEFAULT 0 COMMENT '0草稿 1上架 2下架 3售罄',
  UNIQUE KEY uk_template (template_id)
) ENGINE=InnoDB;

-- 2. 库存分段表（DB侧总闸，Redis的增补来源，也是降级路径的扣减表）
CREATE TABLE coupon_stock_shard (
  id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  template_id BIGINT NOT NULL,
  shard_no    INT NOT NULL COMMENT '段号 0..shard_num-1',
  db_left     INT NOT NULL COMMENT '该段未同步至Redis的余量（增补即从这里原子转移）',
  UNIQUE KEY uk_shard (template_id, shard_no)
) ENGINE=InnoDB;

-- 3. 用户券表（按 user_id 分库分表：库=hash(uid)/M%N，表=hash(uid)%M）
CREATE TABLE user_coupon_{0000..N} (
  id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  coupon_id     BIGINT NOT NULL COMMENT '分布式ID，全局唯一',
  template_id   BIGINT NOT NULL,
  user_id       BIGINT NOT NULL,
  status        TINYINT NOT NULL DEFAULT 1
                COMMENT '1未使用 2已使用 3已退回 4已过期 5已作废',
  idempotent_no VARCHAR(64) NOT NULL COMMENT '幂等号，唯一索引兜底防超发',
  order_id      BIGINT DEFAULT NULL COMMENT '核销订单',
  name_snapshot VARCHAR(64), amount INT COMMENT '冗余模板字段，分表后无法join',
  receive_time  DATETIME NOT NULL,
  use_time      DATETIME, expire_time DATETIME NOT NULL,
  UNIQUE KEY uk_idem (idempotent_no),      -- 幂等的最终事实源
  KEY idx_user_status (user_id, status),
  KEY idx_expire (expire_time)
) ENGINE=InnoDB;

-- 4. 发券流水表（对账的事实源，必须记录段号）
CREATE TABLE coupon_grant_flow (
  id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  coupon_id   BIGINT NOT NULL,
  template_id BIGINT NOT NULL,
  shard_no    INT NOT NULL COMMENT '从哪个库存段扣的，重建/对账依赖',
  user_id     BIGINT NOT NULL,
  source      VARCHAR(32) COMMENT '来源：C端领券/定向发券/券包',
  create_time DATETIME NOT NULL,
  UNIQUE KEY uk_coupon (coupon_id),
  KEY idx_tmpl_time (template_id, create_time)
) ENGINE=InnoDB;

-- 5. 退券流水表（退券幂等 + 库存回补幂等的事实源）
CREATE TABLE coupon_refund_flow (
  id           BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  refund_no    VARCHAR(64) NOT NULL COMMENT '退款单号，幂等键',
  coupon_id    BIGINT NOT NULL,
  order_id     BIGINT NOT NULL,
  stock_back   TINYINT NOT NULL DEFAULT 0 COMMENT '是否回补了库存',
  create_time  DATETIME NOT NULL,
  UNIQUE KEY uk_refund (refund_no)
) ENGINE=InnoDB;

-- 6. 本地事务表（异步发放场景的可靠投递，与异步消费者配套）
CREATE TABLE local_txn (
  id           BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  biz_no       VARCHAR(64) NOT NULL COMMENT '业务单号，防重复投递',
  payload      VARCHAR(2048) NOT NULL,
  state        TINYINT NOT NULL DEFAULT 0 COMMENT '0待发送 1已发送 2已完成 3死信',
  retry_count  INT NOT NULL DEFAULT 0,
  next_retry_time DATETIME,
  UNIQUE KEY uk_biz (biz_no)
) ENGINE=InnoDB;
```

设计要点说明：
- **幂等唯一索引建在现有 user_coupon 表上**（vivo 的决策），不新建幂等表——避免发券主链路多一次表关联；代价是分了多少张表就要保证分布式 ID 的全局唯一 + 幂等号全局唯一，二者都由雪花类算法保证。
- **grant_flow 独立于 user_coupon**，因为对账要按 `(template_id, shard_no)` 聚合计数，放在分表里没法全局聚合。
- **stock_shard 表的 `db_left` 是防超发不变式的锚点**：增补走 `UPDATE ... SET db_left = db_left - N WHERE template_id=? AND shard_no=? AND db_left >= N`，affected=0 则增补失败，绝不出现"DB 明明没了还往 Redis 放量"。

### 9.4.3 Redis Key 设计与数据结构选型

| Key | 结构 | 字段/成员 | 用途 | 选型理由 |
|---|---|---|---|---|
| `c:t:{tid}:s:{n}` | Hash | `left`=段剩余；`{yyyyMMdd}`=段当日发放量 | 段库存+日限 | Hash 把"余量+按天滚动计数"收进一个 Key，日期做 field 天然按天滚动，不用跨天重置逻辑；Lua 内一次原子操作 |
| `c:t:{tid}:u` | Hash | field=uid，value=用户总领取数 | 总限领校验 | 计数型 Hash，HINCRBY 原子；避免 per-user String 造成 Key 总量爆炸 |
| `c:t:{tid}:u:{yyyyMMdd}` | Hash | field=uid，value=当日领取数 | 日限领校验 | 日期进 Key，过期即可整 Key 删除，避免 Hash 内无限膨胀 |
| `c:idem:{no}` | String | `"1"`，TTL 30s | 幂等前置拦截 | SETNX 一次 O(1)；TTL 短，防"处理中"卡死重试 |
| `c:idem:r:{no}` | String | 结果 JSON，TTL 24h | 幂等终态结果 | 让重试拿到上次结果而不是"处理中" |
| `c:t:{tid}:soldout` | String | 1，TTL 60s | 售罄快速失败 | 短 TTL 防止 DB 补货/回补后售罄标记滞留 |

两条重要的取舍说明：

1. **腾讯云 MALL 方案用 ZSet（member=couponId, score=uid）做幂等去重**。它的优点是校验与扣减同脚本原子完成；但 member 数随发放量线性增长，一个发放千万张的批次就是千万 member 的 ZSet——按京东到家的经验阈值（集合类元素 > 8000 即算大 Key），这本身就是自己制造大 Key。**推荐做法：主幂等用"SETNX 前置 + DB 唯一索引兜底"，ZSet 方案只用于白名单预分配型的小量发放**（先批量 ZADD 预生成的券码，领取时 ZPOPMIN，量级可控）。
2. **用户领取计数 Hash（`c:t:{tid}:u`）也会膨胀**（uid 数 = 领取人数）。治理：以 grant_flow 为事实源，低峰期重建；模板结束后整 Key 设置 TTL 回收；活跃模板的计数 Hash 控制在单 Key 限流阈值内（超过说明该模板量级应再分段）。

### 9.4.4 核心 Lua 脚本（段内扣减）

```lua
-- DEDUCT_SCRIPT
-- KEYS[1] = c:t:{tid}:s:{n}      段库存 Hash
-- KEYS[2] = c:t:{tid}:u          用户总领取 Hash
-- KEYS[3] = c:t:{tid}:u:{ymd}    用户当日领取 Hash
-- ARGV[1] = uid
-- ARGV[2] = ymd            当天日期串
-- ARGV[3] = userLimit      每人总限领
-- ARGV[4] = dailyUserLimit 每人每日限领
-- ARGV[5] = dailyBatchLimit 批次每日发放上限（0=不限）
-- 返回：正数=扣减后段余量；负数为错误码

local stockKey, userKey, userDayKey = KEYS[1], KEYS[2], KEYS[3]
local uid, ymd = ARGV[1], ARGV[2]

if redis.call('EXISTS', stockKey) == 0 then return '-9' end  -- 段未初始化

-- 校验顺序：便宜的、终态的放前面，尽快失败
local uTotal = tonumber(redis.call('HGET', userKey, uid)) or 0
if uTotal >= tonumber(ARGV[3]) then return '-2' end          -- 超每人总限
local uDay = tonumber(redis.call('HGET', userDayKey, uid)) or 0
if uDay >= tonumber(ARGV[4]) then return '-7' end            -- 超每人日限
if tonumber(ARGV[5]) > 0 then
  local daySent = tonumber(redis.call('HGET', stockKey, ymd)) or 0
  if daySent >= tonumber(ARGV[5]) then return '-1' end       -- 超批次日上限
end
local left = tonumber(redis.call('HGET', stockKey, 'left')) or -1
if left <= 0 then return '-3' end                            -- 本段售罄(换下一段)

redis.call('HINCRBY', stockKey, 'left', -1)                  -- 四次写原子完成
redis.call('HINCRBY', stockKey, ymd, 1)
redis.call('HINCRBY', userKey, uid, 1)
redis.call('HINCRBY', userDayKey, uid, 1)
return left - 1
```

错误码语义与腾讯云 MALL 方案对齐（-1 批次日限 / -2 用户总限 / -3 段售罄 / -7 用户日限 / -9 段未初始化），`-3` 是唯一需要调用方换段重试的码。库存回补脚本就是反向的 `HINCRBY left +1`（配以补偿表防丢）。

### 9.4.5 Java 核心代码

```java
@Service
public class CouponGrantService {

    /** 本地记录已耗尽的段（字节方案：售罄分片跳过，避免无效轮询） */
    private final Set<String> localSoldOut = ConcurrentHashMap.newKeySet();

    public GrantResult grant(GrantCmd cmd) {
        // ② 模板：本地缓存 -> Redis -> DB（二级缓存，根除Redis万分之2~3的固有超时失败）
        Template t = templateCache.get(cmd.getTemplateId());
        Asserts.isTrue(t != null && t.isActive(), Err.TEMPLATE_INVALID);

        // ③ 幂等前置：30s 处理中标记
        Boolean first = redis.setIfAbsent(
                "c:idem:" + cmd.getIdempotentNo(), "1", Duration.ofSeconds(30));
        if (Boolean.FALSE.equals(first)) return loadFinalResult(cmd.getIdempotentNo());

        DeductResult d;
        try {
            // ④ 分段扣减：随机不重复轮询
            d = deductWithShards(t, cmd.getUserId());
            if (!d.success()) {
                saveFinalResult(cmd.getIdempotentNo(), GrantResult.fail(d.code()));
                return GrantResult.fail(d.code());
            }
            // ⑤ 同库同事务：用户券 + 发券流水（一次DB往返）
            long couponId = idGen.next();
            couponRepo.saveCouponAndFlow(t, cmd, d.getShardNo(), couponId);
            // ⑥ 终态结果
            saveFinalResult(cmd.getIdempotentNo(), GrantResult.ok(couponId));
            return GrantResult.ok(couponId);

        } catch (DuplicateKeyException e) {
            // 唯一索引兜底命中：并发重复请求，查出已发券按成功返回（幂等语义）
            return couponRepo.findByIdemNo(cmd.getIdempotentNo())
                    .map(c -> GrantResult.ok(c.getCouponId()))
                    .orElseThrow(() -> new IllegalStateException("幂等冲突但查无记录", e));
        } catch (Exception e) {
            // DB失败：必须回补Redis段库存，否则库存虚耗（少卖事故）
            if (d != null && d.success()) compensate(t, d, cmd.getIdempotentNo());
            redis.delete("c:idem:" + cmd.getIdempotentNo());   // 释放标记允许重试
            throw e;
        }
    }

    private DeductResult deductWithShards(Template t, long uid) {
        String ymd = LocalDate.now().format(BASIC_ISO_DATE);
        for (int shardNo : RandomNonRepeat.of(t.getShardNum())) {  // 随机不重复数组
            String tag = t.getTemplateId() + ":" + shardNo;
            if (localSoldOut.contains(tag)) continue;               // 跳过已知耗尽段
            Object r = redisLua.execute(DEDUCT_SCRIPT,
                    List.of(stockKey(t.getTemplateId(), shardNo),
                            userKey(t.getTemplateId()),
                            userDayKey(t.getTemplateId(), ymd)),
                    List.of(String.valueOf(uid), ymd,
                            String.valueOf(t.getUserLimit()),
                            String.valueOf(t.getDailyUserLimit()),
                            String.valueOf(t.getDailyBatchLimit())));
            int code = Integer.parseInt(String.valueOf(r));
            if (code == -3) { localSoldOut.add(tag); continue; }    // 本段空，换下一段
            if (code < 0) return DeductResult.fail(code);
            return DeductResult.ok(shardNo, code);
        }
        return DeductResult.fail(Err.SOLD_OUT);
    }

    /** 回补：反向Lua +1；失败则落补偿表交给对账Job修复 */
    private void compensate(Template t, DeductResult d, String no) {
        try {
            redisLua.execute(BACK_SCRIPT, List.of(stockKey(t.getTemplateId(), d.getShardNo())));
        } catch (Exception ex) {
            compensateLog.save(new CompensateLog(no, t.getTemplateId(), d.getShardNo()));
        }
    }
}
```

**库存增补 Job（不变式的守护者）**：

```java
// 每10s扫描：段 left < M(如200) 时，从DB原子转移N(如1000)到Redis
@Scheduled(fixedDelay = 10_000)
public void supplement() {
    for (ShardView s : hotShards()) {                    // 从Redis批量HGET left
        if (s.getLeft() >= SUPPLEMENT_M) continue;
        // DB侧原子转移：db_left >= N 才允许
        int affected = jdbc.update(
            "UPDATE coupon_stock_shard SET db_left = db_left - ? " +
            "WHERE template_id = ? AND shard_no = ? AND db_left >= ?",
            N, s.getTemplateId(), s.getShardNo(), N);
        if (affected == 1) {
            redisLua.execute(SUPPLEMENT_SCRIPT,          -- HINCRBY left N
                List.of(stockKey(s.getTemplateId(), s.getShardNo())));
        } else {
            markTemplateSoldOutIfAllDrained(s);          // DB也没了 → 置售罄
        }
    }
}
```

由此得到防超发不变式：**任意时刻，`Σ段Redis余量 + Σ段db_left + DB已确认发放流水数 = 模板总量`**。Redis 整体崩溃最多丢失"已增补未发放"的量（≤ N×段数），且重建时按 `(total - db_left) - flow_count(shard)` 重算余量、先重建再放量——宁可少发，不可超发。M、N 是运营旋钮：M 决定"发得快补得慢"时提前提示无库存的阈值，N 决定极端故障下的最大损失上限（腾讯云 MALL 的参数化设计）。

### 9.4.6 C 端领券完整时序（编号步骤）

1. 接入层鉴权，按上游业务方限流（券系统是被多方调用的底层服务，必须按上游维度配额），提取幂等号——上游传 `idempotentNo` 则用之，未传则以 `hash(source + userId + templateId + 活动期次)` 生成。
2. 读模板：本地 Caffeine → Redis →（仅冷启动穿透）DB；本地缓存由定时任务刷新，刷 Redis 时加分布式锁防止多实例重复写。
3. 校验模板状态、有效期、人群资格。
4. Redis 幂等前置 `SETNX c:idem:{no}`（TTL 30s）；命中则读 `c:idem:r:{no}` 返回终态结果，miss 则返回"处理中，请勿重复提交"。
5. 生成分段随机不重复数组，跳过本地耗尽段标记，逐段执行 DEDUCT Lua；`-3` 换段，`-2/-7/-1/-9` 直接失败并落终态结果。
6. 扣减成功后，**同一本地事务**内 `INSERT user_coupon_XX`（带 uk_idem）+ `INSERT coupon_grant_flow`（带 shard_no）。
7. 成功：写终态结果键（TTL 24h），返回券信息；用户立即查券包走从库（主从延迟正常 1ms 以内，用户无感知；强一致诉求场景读主）。
8. `DuplicateKeyException`：并发重复，查已有记录按原结果返回（对外幂等成功）。
9. 其它 DB 异常：反向 Lua 回补段库存、删除幂等处理中标记、向上游抛错允许重试；回补失败落补偿表。
10. 旁路：增补 Job 维持不变式；对账 Job 五分钟增量比对；发放速率熔断监控。

**定向发券（亿级异步路径）**：运营圈人 → 生成发券任务分片 → 写 local_txn → MQ 投递（消息体含批量用户，参数动态可调控制峰值速度）→ 消费者逐条以幂等号 INSERT（撞唯一索引即跳过并确认消息，**消费天然幂等**）→ 内存计算库表后缀归集、按表分组批量 INSERT（最多 M 次 DB IO）→ 校验只做轻量版（去重事务、去强校验，失败记录可重试）。

### 9.4.7 核销、退券、过期的一致性设计

**核销（用券）**——与订单系统的一致性靠"单条 UPDATE 的乐观状态机"而不是分布式事务：

```sql
UPDATE user_coupon_0007
SET status = 2, order_id = #{orderId}, use_time = NOW()
WHERE coupon_id = #{couponId} AND status = 1;
-- affected = 1：核销成功
-- affected = 0：查当前状态——若 status=2 且 order_id 相同 → 幂等重入，返回成功
--              若 status=2 且 order_id 不同 → 一券多单，拒绝并告警
--              若 status=4/5    → 已过期/作废，返回业务错误
```

订单侧若使用本地消息表/事务消息驱动核销，MQ 重投由上面的幂等重入语义吸收。核销成功后发核销流水消息（供统计与对账），消费失败只影响报表不影响资金。

**退券（退款回退）**——退券的幂等键是退款单号，库存回补必须与退券记录绑定：

1. `INSERT coupon_refund_flow(refund_no, ...)` 撞 `uk_refund` → 已处理过，直接返回成功（幂等）。
2. `UPDATE user_coupon SET status = 3 WHERE coupon_id = ? AND status = 2`（乐观，只在"已使用"态回退）。
3. 若业务配置允许回补库存：执行回补 Lua `HINCRBY left +1`。回补动作只在第 1 步 INSERT 成功（首次）时执行，天然只做一次；若第 2 步失败则整单回滚，第 3 步不会执行。
4. 注意方向性：回补使 Redis 余量增大，**必须同步 `db_left += 1`**（或走增补通道记一笔正向流水），否则不变式被打破——对账会把这笔"多出来的量"误判为异常。

**过期**——RocketMQ 延时消息的时长有上限而券有效期不固定，字节的做法是**循环投递**：发券时投递 `min(过期时间, now + 延时上限)` 的延时消息，消费时检查券是否真的到期，没到则计算剩余时长再次投递，到期则执行 `UPDATE ... SET status = 4 WHERE coupon_id = ? AND status = 1`——乐观条件防止把"临过期前一毫秒核销"的券改成已过期（affected=0 直接跳过）。

### 9.4.8 对账与资损防控（最后防线）

三层对账，全部以 MySQL 流水为事实源：

1. **准实时（5 分钟）**：按模板按段比对 `Redis left` vs `(total - db_left - flow_count)`。Redis 偏多（可能超发前兆）→ **最高级告警 + 立即按 DB 值修正 Redis（HSET 调小）+ 视情况下架**；Redis 偏少（DB 失败未回补）→ 自动补偿回正。
2. **T+1 全量**：`Σ模板 total` vs `Σ流水数` vs `Σ用户券状态分布`；核销金额 vs 订单优惠金额双向核对。
3. **资损熔断**：单模板单位时间发放量超过配置阈值（运营配错或 bug 型超发的特征是速率异常）→ 自动下架 + 通知值班；上线新发放链路必须配置影子阈值。

配套监控指标：发券成功率（字节按 0.01% 的量级抠成功率）、错误码分布（-3 占比飙升=售罄进程、-2 飙升=疑似重复请求攻击）、Redis 余量下降斜率、段间 QPS 均衡度（发现轮询倾斜）、DB 慢查询数。

### 9.4.9 稳定性设计

**容量估算先行**（字节数字可直接复用）：单 MySQL 写 ~4000 QPS、单表千万级后查询明显劣化、Redis 单分片写 ~2w/读 ~10w。目标 12w 发券 QPS → 30 个 MySQL 主库分片、至少 6 个 Redis 分片（假设全打一个模板）。**线上资源 = 压测值的 1.5 倍**。压测自底向上：单实例 → MySQL 主库读/写 → Redis 单分片读/写，逐层找瓶颈再做整体压测。

**热点治理**（写热点与读热点手段不同，选错等于没做）：
- 写热点（库存扣减）：分段库存 + 随机不重复数组轮询 + 售罄段本地跳过。**必须随机起点**，固定从 1 号段开始轮询等于没拆（字节踩过）。"Key 备份/散列多份"只适合读多写少，套在发券上是错误选型。
- 读热点（模板）：本地缓存 + Redis 二级缓存，根除 Redis 万分之 2~3 的固有超时失败；本地缓存选**小且不常变**的数据，否则 GC 压力反噬。
- 极端单 Key 写热点（百万级 QPS）：再上聚合扣减（前端聚合同批次请求合并扣减），但要处理聚合窗口与时延、临界库存与聚合批量的适配，复杂度高，非必要不引入。

**大 Key 治理**：结构上首选业务拆散——京东到家把 `CouponId → 万级门店集合` 打平成 `CouponId+门店Id` 单 Key，C 端从拉大 Value 变成 `EXISTS` 判存在，流出量从 G/s 降到几十 M/s。配套规范：Key/字段名缩写、整数优先、冷热字段分离、清理用 Scan 渐进或 4.0+ `UNLINK`（直接 `DEL` 大 Key 本身就会阻塞）、**所有 Key 尽量设 TTL 且加随机值**（集中过期会打满 Redis 定期删除的 CPU 时间片，Redis 的过期清理是惰性+定期删除、只在主库删再同步从库）。发现手段五件套：业务经验、客户端代理收集、慢日志、从库 Scan、主从切换观察流出量/QPS（最笨但一定能定位）。

**隔离与降级**：
- Redis 按数据域拆多集群（京东到家拆了打标/门店券/用户券/活动/已使用 5 个集群），故障隔离 + 独立扩容。
- C 端"展示系统"与"用券核心交易系统"分离，展示洪峰不影响结算。
- 外部依赖（风控、用户中心）熔断 + 线程池/信号量隔离，防连锁雪崩。
- **Redis 整体故障的降级路径**：模板读走本地缓存；库存扣减降级为 DB 分段库存模式（vivo 的主方案在此充当降级位，随机段 + 单段 UPDATE 天然抗并发），配合收紧限流阈值——宁可吞吐从 12w 掉到几千，也不能停止服务或切到无校验直发。
- 超时预算：发券接口内部执行预算 100ms、对外超时 500ms，超时即拒绝，防止被上游拖垮；实例跨物理区域分布防集群级故障。

## 9.5 素材间的方案分歧与推荐

1. **库存扣减放 DB 还是 Redis**。vivo 商城明确放弃了 Redis `INCRBY` 方案（理由：缓存丢失/宕机后的恢复与不一致处理复杂），选了 **DB 分段库存**（库存拆 M 份、随机段扣减、定时汇总同步）；腾讯云 MALL 与字节跳动都选 **Redis + Lua**。**推荐：按峰值分层。** 峰值几千 QPS 且团队 Redis 运维能力一般，DB 分段是低复杂度的正确答案（vivo 稳定支撑了商城数年）；峰值万级以上没有选择——MySQL 单机写 4000 QPS 是物理上限，必须 Redis + Lua 承接。但两者不是二选一：**最终形态以 Redis + Lua 为主路径、DB 分段库存为降级路径**，"分段"思想通用，切换成本最低。

2. **幂等的载体**。vivo 用 DB 唯一索引（建在现有表 + 刷历史数据）；字节只说"幂等校验（MySQL）"未展开；腾讯云 MALL 用批次维度 ZSet（member=couponId）。**推荐：DB 唯一索引是唯一可信的事实源兜底，前面加 Redis SETNX 做快速拦截；不推荐 ZSet 做主幂等**——member 随发放量线性膨胀，与京东到家给出的大 Key 阈值（集合元素 > 8000）正面冲突，等于把幂等问题转换成了大 Key 问题。ZSet 仅适合白名单预分配型小量场景。

3. **防同一用户并发超领**。vivo 用 Redis 分布式锁（锁 key = uid + 券模板 id，批量领券逐券加锁 + 自旋等待）；腾讯云 MALL 把用户限领计数放进 Lua 原子校验，无锁。**推荐：Lua 计数为主**——一次网络往返、无锁、无超时歧义；分布式锁有三个固有坑（组合 key 不互斥、业务超时锁提前释放后并发进入、自旋耗 CPU），只在批量领券这类"一次请求锁多资源"的场景作为补充，且锁内仍必须有唯一索引兜底。

4. **领券落库同步还是异步**。vivo 强调领券必须实时（异步发券用户账户看不到券，影响体验和转化率），用同库批量 INSERT 把 IO 次数压到与券数无关；腾讯云 MALL 选异步生成 + 本地事务表 + 最大努力通知。**推荐：分场景。** C 端主动领券同步（用户在等结果，且"同库事务双 INSERT"的成本字节的容量估算已证明可承受 12w QPS）；定向发券、券包、亿级批量走异步 MQ + 消费幂等。"同步 = 强一致 + 实时性，异步 = 削峰 + 吞吐"，按调用方是谁选，不按个人偏好选。

5. **热点打散手段**。字节：分段 + 随机不重复轮询 + 售罄跳过（写热点）；京东到家：散列多份随机读 + 本地前置缓存（读热点）；腾讯云 MALL：列举了资源分桶/聚合扣减/数据库热点更新三条路但未定论。**推荐：写热点用分段（字节的完整落地细节最成熟），读热点用二级缓存 + 多副本散列，聚合扣减只在百万级单 Key 写热点时作为最后手段**（聚合窗口、临界库存适配的复杂度和次生问题显著）。

## 9.6 踩坑清单（按严重程度排列）

1. **先查后插做幂等**（资损，最高危）。并发窗口内两个请求都通过 SELECT 校验，各发一张券。**发现**：对账出现同一幂等号多条流水、客诉一人多券、风控发现单 UID 券数异常。**防**：唯一索引 + 捕获 `DuplicateKeyException` 按成功返回；团队规范里直接禁止"先 SELECT 判断再 INSERT"的幂等写法，code review 一票否决。

2. **Redis 余量与 DB 无不变式，Redis 故障后超发**（资损）。主从切换丢写后继续放量，实际发放超出总量，事后才发现。**发现**：Redis 故障恢复后对账 `总量 - 发放流水 < 0`。**防**：db_left 原子转移式增补（`WHERE db_left >= N`），维持"Redis 余量 + db_left + 流水数 = 总量"不变式；故障后先按 DB 重建余量再放量，宁少发不超发。

3. **核销/退券非幂等，一券多单、重复回补库存**（资损）。订单重试/消息重投触发二次核销或二次回补。**发现**：同 couponId 多个 order_id、库存无发放却余量上升。**防**：单条乐观 UPDATE 状态机（`WHERE status = X`）+ affected=0 的语义分支；退券以 refund_no 唯一索引为首步，回补只在首次 INSERT 成功时执行。

4. **MQ 消费者不幂等，重投重复发券**（资损）。**发现**：消息轨迹显示同消息多次消费、幂等号重复流水。**防**：消费逻辑以唯一索引 INSERT 为准，撞索引即确认消息（ack）跳过；禁止"先查后插"式消费。

5. **扣减成功但 DB 写失败不回补**（少卖事故，收入损失）。Redis 扣了 1 个库存，券没落库，库存虚耗直至售罄。**发现**：对账 Redis 偏少（DB 失败未回补类 diff）。**防**：异常分支反向 Lua 回补 + 回补失败落补偿表 + 对账 Job 自动修复。

6. **分布式锁三连坑**（资损+稳定性）：批量领券把锁 key 拼成 `uid+A+B+C+D` 与单券请求的 `uid+A` 不互斥，超领照旧（vivo 实际踩过）；业务未执行完锁超时自动释放，第二个请求进入；自旋等待打满 CPU。**发现**：批量+单券并发场景偶发超领、锁监控显示大量超时。**防**：逐券独立锁 key、锁续期（watchdog）、锁内唯一索引兜底；能用 Lua 计数替代就不用锁。

7. **分段库存固定顺序轮询，热点根本没消除**（稳定性）。所有请求仍从 1 号段开始尝试，1 号分片 QPS 一枝独秀。**发现**：Redis 分片 QPS 监控严重不均、1 号分片率先达到写瓶颈。**防**：每次请求生成随机不重复段序数组；售罄段本地内存标记直接跳过（字节两处实战教训）。

8. **段间倾斜导致假售罄**（收入损失）。某段扣尽而其它段有余，用户被误提示售罄。**发现**：售罄告警时 `Σdb_left + ΣRedis余量 > 0`。**防**：段间调拨（低峰小步再平衡）或售罄判定以 DB 侧余量为最终裁决。

9. **大 Key 拖垮整个 Redis 集群，且降级限流无效**（稳定性，京东到家真实事故）。万级元素 Value 使单分片流出量 G/s 级，主线程单次操作时间变长，同分片所有 Key 集体变慢，问题分片还随数据分布每天漂移。**发现**：五件套——业务经验、客户端代理收集、慢日志、从库 Scan、主从切换观察流出量（最后的兜底笨办法，一定能定位）。**防**：设计期就按"元素 < 8000"审 Key 结构（打平 + EXISTS、缩写、冷热分离）；清理用 Scan/UNLINK；幂等 ZSet、计数 Hash 这类随量增长的结构必须有重建与 TTL 机制。

10. **过期时间集中或不设 TTL**（稳定性+成本）。大量 Key 同刻过期打满 Redis 定期删除的 CPU 时间片；不设过期则内存无限涨。**防**：TTL 加随机抖动；规范要求所有业务 Key 必须带 TTL；低峰期对主节点 Scan 顺带触发惰性清理。

11. **无降级路径 + 不压测上线**（可用性）。Redis 万分之 2~3 的固有超时直接体现为成功率损失（字节用二级缓存根除）；没压测就不知道单 MySQL 4000 QPS、Redis 单分片 2w 写的墙在哪。**防**：模板二级缓存、库存 DB 分段降级模式、按上游限流、熔断隔离；上线前自底向上压测，线上资源按 1.5 倍冗余。

## 9.7 小结

这一章的所有设计可以压缩成四条不变式，任何一行代码提交前都值得对照一遍：

1. **一个幂等号，最多一张券**——Redis SETNX 只是加速，DB 唯一索引才是事实。
2. **Redis 余量 + db_left + 流水数 = 模板总量**——任何写路径（增补、回补、退款）都不能打破它，打破它的那天就是对账告警资损的那天。
3. **状态机单向推进，一次 UPDATE 定胜负**——核销、退券、过期全部乐观并发控制，affected=0 就查态分支，不搞跨服务分布式事务。
4. **每一层都快坏了的时候，下一层还能接住**——Redis 坏有 DB 分段降级，DB 坏有对账修复，代码坏有速率熔断，运营配错有阈值兜底。

幂等靠"唯一索引"而不是"小心编程"，一致性靠"不变式 + 对账"而不是"分布式事务"，资损防控靠"分层防线"而不是"测试充分"，稳定性靠"容量估算 + 降级预案"而不是"机器堆够"——这四句话，就是本章想留给实现者的全部。
