# 第三章 库存扣减与防超发

## 3.1 这个领域解决什么问题，在券系统全局中的位置

优惠券中台有四件事：**创、发、用、计**。本章讲的是"发"这个动作里最核心、也最容易出资损事故的子域——**库存扣减**。它要同时回答五个问题，任何一个答错都会出事故：

1. **还剩多少券可以发？**（剩余库存校验）
2. **这个批次今天最多发多少？**（批次日发放上限）
3. **这个人今天领了几张？**（用户日限领）
4. **这个人累计领了几张？**（用户总限领）
5. **这个请求是不是重复请求？**（幂等）

这五重校验在京东到家的文章里被明确列为库存校验的五个维度（原文：剩余库存校验、每日领取数量校验、总领券数量校验、用户每日领取库存、用户总领取库存），在腾讯云 MALL 的 Lua 脚本里被原子化成一次执行——两家的口径是一致的，这就是本域的完整需求边界。

业务上要防三类事故，严重度递减：

- **超发（资损）**：发了 10500 张，库存只有 10000 张。多出的 500 张如果每张面额 50 元，就是 2.5 万元的直接营销资损，且要逐单追回，客诉极大。
- **少发/库存泄漏（营销事故）**：库存 10000，实际只发出去 9600 就显示售罄，400 张额度凭空消失。活动没打完就"售罄"，运营会直接找上门。
- **慢/挂（稳定性事故）**：大促 10 点开抢，瞬时流量打穿库存层，连带拖垮整个券系统甚至交易链路。

在全局链路中的位置（ASCII）：

```

                        │                优惠券中台                       │
                        │                                                │
 用户请求 ──► 接入层 ──► │  活动资格校验 ──► 【库存扣减中心】 ──► 发券落库   │

                        │   黑白名单)      + 原子扣减)       唯一索引)    │
                        │                      │                         │
                        │              ┌───────┴────────┐                │
                        │              ▼                ▼                │
                        │         Redis 集群        MySQL 分片           │
                        │      (热库存/计数层)   (批次/流水/券记录)        │
                        │              ▲                │                │
                        │              │ 异步增补N       │ MQ 异步落库    │
                        │              └── 库存分段源 ───┘                │
                        │           (Redis可扣 ≤ DB总量 不变式)           │
```

一句话概括本章的架构哲学，来自腾讯云 MALL 的实践并被字节跳动压测验证：**热路径上只碰 Redis（单分片写约 2 万 QPS），MySQL 只做"分段增补的源头 + 最后防线 + 对账事实源"，两者之间用"Redis 可扣减额度 ≤ 数据库已推送额度 ≤ 数据库总量"这条不变式锁死超发的可能。**

## 3.2 朴素实现（v1）会怎么挂：具体故障复盘

### 3.2.1 v1 代码长什么样

绝大多数人第一次写领券，代码是这样的：

```java
// v1：先查后扣 + 同步落库
public GrantResult grant(long batchId, long userId) {
    Batch b = batchMapper.selectById(batchId);          // 1. 查库存
    if (b.getStock() <= 0) return SOLD_OUT;
    if (b.getIssued() >= b.getLimitPerUser()) return OVER_LIMIT; // 2. 查限领(不准)
    batchMapper.update("UPDATE batch SET stock=stock-1, issued=issued+1 WHERE id=?", batchId); // 3. 扣库存(无守卫)
    couponMapper.insert(newCoupon(batchId, userId));    // 4. 落库
    return OK;
}
```

### 3.2.2 故障场景一：超发（资损）

**量级**：某爆款券批次，大促 10:00:00 开抢，瞬时 3000 QPS。步骤 1 和步骤 3 之间不是原子的：T1 时刻 100 个并发请求都读到 `stock=1`，都判断"还有"，都执行 UPDATE，库存被扣成 **-99**，发出 100 张，超发 99 张。这就是经典的 check-then-act 竞态。如果 UPDATE 加上 `AND stock > 0` 守卫，超发堵住了，但换来的问题是故障场景二。

**错误现象**：压测或上线后 `SELECT stock FROM batch` 出现负数；财务对账发现发放量 > 审批量。

**资损后果**：超发 N 张 × 券面额。营销券是真金白银，追回需要逐个用户发站内信+强制失效，公关成本远超面值。

### 3.2.3 故障场景二：热行锁把数据库打挂（雪崩）

**量级**：加了 `AND stock>0` 守卫后，所有扣减串行排队在**同一行的行锁**上。字节跳动的实测数据是单 MySQL 实例写吞吐约 4000 QPS（普通分散写），而热点行更新的实际吞吐只剩几百 QPS。vivo 的文章描述了同样的现象：单行单字段的所有更新请求等待行锁，并发大时大量请求阻塞导致超时甚至系统雪崩。

**错误现象**：10:00:00 开抢，10:00:03 数据库连接池（比如 200 个连接）全部 BLOCKED 在 `waiting for row lock`，RT 从 5ms 涨到 30s；上游 Tomcat/Netty 工作线程被占满，**整个券系统的其他接口（查券、用券）一起无响应**——这是最恶性的部分：一个营销活动拖垮核心交易。

**后果**：故障升级为 P0，影响面从"这一个活动"扩大到"全站交易"。

### 3.2.4 故障场景三：无幂等 + 用户超领

用户端弱网点一下"领取"没收到响应，SDK 自动重试 3 次 → 同一个用户领到 3 张限领 1 张的券。vivo 的文章记录了另一个变体：用户并发发出两个领券请求，第一次通过了数量校验但券还没落库，第二次校验也通过，领了两张。错误现象：运营投诉"限领 1 张的用户券包里有 2 张"。后果：单用户资损小，但规则失信，风控介入。

**v1 的结论**：数据库不是不能做库存（vivo 用"分段库存"证明低复杂度场景可行），而是**单行热点 + 非原子校验**这两个结构性问题，在万级 QPS 下必然挂。

## 3.3 方案演进：v1 → v2 → v3

### v3.1 v1：数据库直扣（如上）

- 解决：无。它只是起点。
- 遗留：热行锁瓶颈、check-then-act 超发、无幂等。
- **演进动机**：把扣减从"磁盘上的单行"挪到"内存里的单线程"。

### v3.2 v2：Redis 原子扣减 + 同步落库

把库存放进 Redis，用 Lua 脚本把"查余量 → 判上限 → 扣减 → 计数"合并成一次原子执行（Redis 单线程执行 Lua，天然串行，无锁也无竞态）：

```java
Long left = redis.execute(deductLua, keys(batchId), args(uid, limits));
if (left < 0) return mapError(left);   // -1/-2/-3... 错误码
couponMapper.insert(newCoupon());      // 仍然同步落库
```

- **解决了**：单批次扣减吞吐从几百 QPS 提到约 2 万 QPS（字节实测 Redis 单分片写瓶颈）；Lua 原子性消灭 check-then-act 超发；五重校验可以塞进同一个脚本（腾讯云 MALL 的做法）。
- **引入的新问题**：
  1. **Redis 与 DB 谁是事实源？** Redis 主从异步复制，failover 丢最近写入：丢一次扣减 → 余量虚高 → 可能超发；丢一次回补 → 少发。
  2. **扣减成功、落库失败**（应用重启/DB 抖动）→ 库存泄漏，永远少发一张。
  3. **热点单 Key**：12 万 QPS 打同一个批次 Key 还是落在同一个 Redis 分片（写上限 2 万），字节的文章明确说"严重时拖垮整个 Redis 集群"——因为该分片阻塞会连带影响同分片其他业务 Key（京东到家称之为"单点阻塞表现为该集群所有缓存都变慢"）。
  4. 落库仍是同步写，DB 侧 4000 QPS/实例的天花板还在。
- **演进动机**：需要一条不变式把 Redis 的故障面罩住（防超发），需要削掉 DB 的同步写峰值（防拖垮），需要把热点 Key 摊开（防单分片）。

### v3.3 v3：大厂最终形态

四件套组合，本章 3.4 展开：

1. **Redis + Lua 原子扣减**（热路径只碰 Redis，校验全在脚本内）；
2. **数据库分段增补**：Redis 余量低于水位 M 时，异步从 DB 条件式地"领取"N 个额度推入 Redis，保证 **Redis 可扣 ≤ DB 已推送 ≤ DB 总量**——Redis 整个宕机也最多"少发 N 张"，绝不超发（DB 是最后防线）；
3. **异步落库 + 本地事务表 + MQ**（腾讯云选型：不追求强一致，用"本地事务表 + 最大努力通知"达成最终一致），同时用 DB 唯一索引做幂等终审（vivo/字节做法）；
4. **热点分桶 + 随机不重复轮询 + 售罄跳过**（字节方案），把单批次写吞吐从 2 万扩到 2 万×桶数。

- **v3 仍然引入新问题**（要认账）：
  - **最终一致窗口**：扣减成功到券包可见有 1~2 秒延迟，前端必须文案兜底（"领取成功，稍后到账"），否则客诉；
  - **系统复杂度暴涨**：增补 Worker、补偿任务、对账系统、降级开关，都要人维护；
  - **分桶的代价**：桶间余量不均衡，全局售罄判断只能是近似的（字节方案靠"跳过已空桶"缓解，腾讯云文章也承认临界库存与分桶的适配是遗留难题）；
  - **对账成为必需品**：没有对账，库存泄漏和超发都发现不了。

### 3.4.2 Redis Key 设计与数据结构选型

| Key | 结构 | 内容 | TTL | 选型理由 |
|---|---|---|---|---|
| `cb:{B}:stock:{bucketNo}` | HASH | field `left`=桶余量；field `20260902`=当日已发 | 无(批次结束再清 | HASH 把"余量+按天计数"收进一个 Key，日期做 field **天然按天滚动**，无需跨天重置任务（腾讯云方案） |
| `cb:{B}:dedup` | SET | member=couponId | 批次结束 | 券 ID 防重，SISMEMBER O(1)。**限制**：百万级以上 member 有大 Key 风险，大批次弃用、只靠 DB 唯一索引 |
| `cb:{B}:u:{uid}` | STRING | 用户总领取数 | 批次结束+7d | 计数器 INCRBY 原子；拆成 per-user 小 Key 而非腾讯云的批次大 HASH，规避京东到家文章的大 Key 教训（百万 field 的 HASH 会阻塞分片） |
| `cb:{B}:ud:{uid}:{day}` | STRING | 用户当日领取数 | 2 天 | 日期入 Key 自然滚动，**必须设 TTL**：否则海量用户×天数无限堆积 |
| `idem:{uid}:{requestId}` | STRING | "P"/结果码 | 10 分钟 | 请求级幂等快速拦截，SET NX EX 原子 |

**Hash Tag 策略（Redis Cluster 关键决策）**：`{B}` 是 hash tag，强制同一批次的所有 Key 落同一 slot——这是"一个 Lua 原子操作五重校验五次写入"的前提（Cluster 要求 Lua 涉及的所有 Key 同 slot）。代价是单批次吞吐上限 = 单分片写上限 ≈ 2 万 QPS。**热点批次启用分桶后**，tag 变为 `{B:bkt3}`，按桶分 slot，吞吐 ×桶数；此时用户限领 Key 无法与库存 Key 同 slot，五重校验拆两段（见 3.4.4）。这是"原子性 vs 横向扩展"的刚性权衡，没有两全解。

### 3.4.3 核心 Lua 脚本（常规批次，单 slot 全原子）

```lua
-- deduct.lua  KEYS 全部含 hash tag {B}
-- KEYS[1]=cb:{B}:stock:0   KEYS[2]=cb:{B}:dedup
-- KEYS[3]=cb:{B}:u:{uid}   KEYS[4]=cb:{B}:ud:{uid}:{day}
-- ARGV[1]=couponId ARGV[2]=day ARGV[3]=maxPerUser
-- ARGV[4]=maxPerUserDaily ARGV[5]=batchDailyMax ARGV[6]=ttlSec
local left = redis.call('HGET', KEYS[1], 'left')
if not left then return {-3, 0} end                       -- 库存未初始化
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return {-6, 0} end  -- 券ID重复
left = tonumber(left)
if left <= 0 then return {-3, 0} end                      -- 售罄
local u = tonumber(redis.call('GET', KEYS[3]) or '0')
if u >= tonumber(ARGV[3]) then return {-2, 0} end         -- 用户总限领
local ud = tonumber(redis.call('GET', KEYS[4]) or '0')
if ud >= tonumber(ARGV[4]) then return {-7, 0} end        -- 用户日限领
local dayUsed = tonumber(redis.call('HGET', KEYS[1], ARGV[2]) or '0')
if dayUsed >= tonumber(ARGV[5]) then return {-1, 0} end   -- 批次日上限
-- ===== 校验全过，五次写原子提交 =====
redis.call('HINCRBY', KEYS[1], 'left', -1)
redis.call('HINCRBY', KEYS[1], ARGV[2], 1)
redis.call('INCRBY', KEYS[3], 1);  redis.call('EXPIRE', KEYS[3], ARGV[6])
redis.call('INCRBY', KEYS[4], 1);  redis.call('EXPIRE', KEYS[4], ARGV[6])
redis.call('SADD', KEYS[2], ARGV[1])
return {0, left - 1, dayUsed + 1}
```

脚本结构与腾讯云 MALL 的实现同构（幂等→库存→日上限→用户日限→用户总限 + 五次写），错误码也沿用它的语义：`-3` 售罄、`-2` 总限领、`-7` 日限领、`-1` 批次日上限、`-6` 券 ID 重复。**注意脚本必须严格 O(1)**：Redis 执行 Lua 期间整个分片阻塞，脚本里出现 KEYS/大集合扫描等于自己制造单点阻塞。

**热点批次的两段式变体**：库存 Key 按 `{B:bkt i}` 分桶，用户限领 Key 保持 `{B}` tag（或按 `{uid}` tag 摊开）。流程：先执行 `check_user.lua`（读用户两个计数，不写）→ 通过后执行 `deduct_bucket.lua`（只扣库存+批次日计数）→ 再执行 `incr_user.lua` 写用户计数；若扣库存失败则不必写计数，若写计数超时则补偿回滚。两段之间不原子，超领由 DB 侧"查后插+唯一索引"兜底（vivo 的做法变成这里的防线）。字节跳动的轮询细节照搬：**每次扣减生成桶编号的随机不重复数组（如 [3,1,2]），按序尝试，请求天然散到不同分片；本地记录各桶余量，已空桶直接从数组中剔除**——否则售罄阶段大量请求在空桶上空转，拉高 RT。

### 3.4.4 核心 Java 代码骨架

```java
public interface CouponGrantService {
    /** 同步领券入口；幂等键=userId+requestId */
    GrantResult grant(GrantCommand cmd);
}
public record GrantCommand(long batchId, long userId, String requestId,
                           String source, Map<String,String> ext) {}

@Service
public class CouponGrantServiceImpl implements CouponGrantService {
    public GrantResult grant(GrantCommand cmd) {
        Batch b = batchCache.get(cmd.batchId());          // 本地缓存+Redis 二级缓存(字节方案)
        checkTimeAndStatus(b);
        // 1. 请求级幂等快速拦截(独立小Key,不影响主脚本)
        if (!idempotent.tryLock(cmd.userId(), cmd.requestId())) return DUPLICATED;
        // 2. 分布式ID生成券ID
        long couponId = idGenerator.nextId();
        // 3. Lua 原子扣减(常规批次单脚本;热点批次走两段式+随机桶轮询)
        long[] r = stockGateway.deduct(b, cmd.userId(), couponId);
        if (r[0] != 0) return GrantResult.ofCode(r[0]);
        // 4. 写本地事务表(本服务唯一的MySQL同步写)并投递MQ
        try {
            grantTxnDao.insertTxnAndPublish(new GrantTxn(couponId, cmd)); // 本地事务表+outbox
        } catch (Exception e) {
            stockGateway.restore(b, couponId);           // 5. 回补库存(见回补脚本)
            idempotent.release(cmd.userId(), cmd.requestId());
            throw new RetryableException(e);
        }
        return GrantResult.accepted(couponId);           // 语义:受理成功,券稍后可见
    }
}

@Component
public class StockReplenishWorker {                       // 增补Worker,按batch分片调度
    @Scheduled(fixedDelay = 200)
    public void replenish() {
        for (BatchMeta m : hotBatches()) {                // 只扫低水位批次
            long left = stockGateway.leftTotal(m.batchId());
            if (left >= m.lowWater()) continue;
            // 条件UPDATE原子领取N个额度:pushed+N<=total 不满足则影响行数=0(真售罄)
            int n = stockDao.claimPush(m.batchId(), m.step());
            if (n > 0) stockGateway.addBucket(m.batchId(), chooseBucket(m), n);
        }
    }
}
```

增补的核心 SQL（防"并发双 Worker 重复增补导致超发"的关键）：

```sql
UPDATE coupon_stock SET pushed_amount = pushed_amount + #{n},
       updated_at = NOW()
 WHERE batch_id = #{batchId} AND pushed_amount + #{n} <= total_amount;
```

MQ 消费者伪代码：`INSERT user_coupon`（唯一索引冲突=已处理，直接 ACK）；成功后 `UPDATE coupon_stock SET issued_amount = issued_amount + 1`、事务表置"已落库"；重试超限进死信，由回补任务 `restore`（Lua：`HINCRBY left 1` + `SREM dedup` + 事务表置"已回补"）把库存还回去。

### 3.4.5 领券全链路时序（常规批次）

1. 用户点击领券，网关生成 `requestId`（或透传上游的），先过限流/风控。
2. 服务读批次信息：本地内存缓存 → 未命中读 Redis → 再未命中回源 DB 并回填（字节的二级缓存：定时任务刷新 + 刷 Redis 加分布式锁防多实例重复写）。
3. 校验批次状态、领取时间窗、人群。
4. `SET idem:{uid}:{requestId} P NX EX 600`，失败直接返回"重复请求"。
5. 生成分布式 `couponId`。
6. 执行 `deduct.lua`：五重校验 + 五次写，一次网络往返原子完成。
7. 返回非 0 错误码 → 映射成"已售罄/已达领取上限"等文案，流程终止（幂等 Key 等待自然过期）。
8. 返回 0 → 写本地事务表 `coupon_grant_txn`（status=待发）。
9. Outbox 投递 MQ（与步骤 8 同本地事务，保证"记录必达"）。
10. 消费者消费：`INSERT user_coupon_xxxx`，唯一索引 `uk_user_request` 冲突则视为重复，ACK 跳过（幂等终审）。
11. 消费者推进 `issued_amount+1`，事务表置"已落库"，更新幂等 Key 为最终结果。
12. 前端立即返回"领取成功"（受理语义），券包列表允许 1~2 秒延迟可见，或前端轮询一次。
13. 并行支线：增补 Worker 发现 `left < M`，条件 UPDATE 领取 N，推入随机桶。
14. 兜底支线：投递失败由定时任务扫 `status=待发 && next_retry_time < now` 重推；重试耗尽进死信并触发库存回补。
15. 对账支线：小时级比对 `Redis 扣减累计 = pushed - left`、`issued_amount`、事务表条数、user_coupon 行数，四者不一致即告警并冻结该批次增补。

### 3.4.6 接口签名与错误码

```java
public interface CouponStockGateway {                    // 领域网关(可换实现)
    DeductResult deduct(BatchMeta b, long userId, long couponId);
    void restore(BatchMeta b, long couponId);            // 回补(扣减成功但落库失败)
    long leftTotal(long batchId);                        // 增补Worker用
    void addBucket(long batchId, int bucketNo, int n);   // 增补入桶
}
public record DeductResult(int code, long leftAfter, long dayUsed) {}
```

统一错误码（对齐 Lua 返回）：`0` 成功；`-1` 批次日上限；`-2` 用户总限领；`-3` 售罄/库存未初始化；`-6` 券 ID 重复（幂等命中）；`-7` 用户日限领；`-8` 请求重复（idem Key 拦截）；`-9` 系统降级中。对外 API 层把这些映射为用户可读文案 + 指示前端是否可重试（`-3/-1/-2/-7` 不可重试，`-9` 可稍后重试）。

### 3.4.7 容量估算（压测先行）

沿用字节的实测口径做推演：MySQL 单实例写 ≈ 4000 QPS；Redis 单分片写 ≈ 2 万 QPS、读 ≈ 10 万 QPS；单表千万行后查询效率明显下降。

以目标 12 万发券 QPS 为例：Redis 分片数 ≥ 120000/20000 = 6（若是单一热点批次还需分桶 ≥6 才能吃满）；MySQL 写入只剩"事务表一条 + 券记录一条"，分摊到读多写少常态后主库分片约 8~10 个即可；线上资源 = 压测数据的 1.5 倍冗余。vivo 与腾讯云的量级（万级 TPS、亿级定向发券）用同一公式缩小即可。**每上线一个新形态（分桶、两段式）都要重新压测**——字节的经验：压测暴露的问题就是线上会遇到的问题。

## 3.5 素材间的方案分歧与推荐

**分歧一：库存主存储——vivo 选"数据库分段库存"，腾讯云/字节选"Redis 扣减"。**
这是四篇素材里最根本的分歧。vivo 明确否决了 Redis incrby（理由：要处理缓存丢失/宕机恢复与不一致，复杂），把库存拆成 M 份子库存字段随机扣，保留 DB 的事务与简单性；腾讯云则否决了 DB 直扣（行锁瓶颈）和纯缓存（一致性），用"Redis+Lua+DB 分段增补"组合。**推荐：以 Redis+Lua 为主、DB 分段增补为防线，但吸收 vivo 的洞察。**理由：vivo 方案的吞吐天花板是"M 个 DB 行的热点更新"，M 要开到很大才能对标 2 万+ QPS，且它自己承认段间不均衡无解；而字节用 Redis 方案实打实压到 13 万 QPS。但 vivo"DB 是不丢数据的事实源"这一点必须保留——落地形态就是 `coupon_stock.pushed_amount` 不变式，Redis 整个蒸发也只少发不超发。若你的业务峰值单批次 < 2000 QPS 且团队 Redis 运维弱，vivo 方案是合理降级。

**分歧二：幂等放哪——Redis 集合（腾讯云 ZSET）/ MySQL 幂等前置校验（字节）/ DB 唯一索引（vivo）。**
腾讯云在 Lua 里用 ZSET（member=couponId, score=uid）防重；字节在链路前置做 MySQL 幂等校验；vivo 在用户券表上加唯一索引字段兜底。**推荐：两级——Redis 请求级幂等（`idem:{uid}:{requestId}`，短 TTL 快速拦截）+ DB 唯一索引终审，放弃大批次的批次级 ZSET。**理由：ZSET 挂在批次 hash tag 下，百万张券就是百万 member 的大 Key（京东到家的大 Key 教训：单分片阻塞、全集群变慢），而唯一索引是零成本、不依赖任何中间件的最后防线；vivo 的配套经验（历史数据脚本刷唯一值、为未传码的业务方代生成）直接照抄。

**分歧三：防同一用户并发超领——分布式锁（vivo）vs Lua 原子计数（腾讯云）。**
vivo 用"Redis 分布式锁 + 批量领券逐券加锁自旋等待"；腾讯云把用户计数放进同一个 Lua 原子增减。**推荐：Lua 原子计数。**理由：vivo 自己踩的坑证明了锁的脆弱——组合 key（用户id+四张券id 拼接）与单券请求的锁 key 不互斥，超领照旧，只能改成逐券加锁+自旋，而逐券加锁有顺序死锁风险、锁超时误释放有并发窗口、自旋烧线程。原子计数把"读-判-写"压成一次脚本执行，根本没有窗口。锁保留给真正需要互斥的临界区（如增补 Worker 选主）。

**分歧四：扣减成功后同步落库还是异步落库。**
字节是同步单条非事务写入 + 大量 MySQL 分片扛 13 万 QPS；腾讯云明确否决同步写（打垮 DB），选异步 + 本地事务表 + 最大努力通知。**推荐：做成开关，默认同步、大促热点批次切异步。**理由：同步链路代码简单、失败即回补、一致性窗口为零，中小流量下是更便宜的正确；但当单批次流量逼近 DB 分片写能力或活动是"红包雨"型脉冲，异步是唯一的活路。两者共用同一套事务表/回补/对账底座，切换只是配置。

**分歧五：热点 Key 打散手段——分桶（字节/腾讯云）、Key 备份散列多份（京东到家）、聚合扣减（腾讯云列举）、DB 热点更新（腾讯云列举 TDSQL）。**
**推荐：写热点必用分桶**（拆的是库存本身，逻辑自洽）；**Key 备份（同数据多份随机读）只适合读多写少**——字节明确指出把它套到发券写场景是错误选型，京东到家用它解决的也恰是读场景（券适用门店判断）；聚合扣减（窗口内合并 N 次扣减为一次批量）适合极端脉冲，但要处理聚合窗口延迟与临界库存适配，作为分桶之上的二级手段；DB 热点更新绑定具体数据库（TDSQL），通用中台不应形成硬依赖。

## 3.6 踩坑清单（按严重程度排列）

1. **先查后扣的非原子校验 → 超发资损**。怎么发现：对账任务发现 `issued_amount > total_amount`、库存字段出现负数、财务结算金额对不上。怎么防：所有校验与扣减收敛进一个 Lua 原子脚本；代码评审禁止单独的 GET 库存后再 DEC 的两步写；上线前用并发压测（同一批次 1000 并发领 100 张）验证零超发。

2. **增补链路自身不原子 → 重复增补 → 超发**。多个 Worker 同时看到低水位、都去推 N 个额度，可扣额度超过 DB 总量。怎么发现：`pushed_amount > total_amount`（这条 SQL 应作为分钟级巡检告警）。怎么防：增补必须用条件 UPDATE（`pushed + N <= total`，影响行数为 0 即放弃），且同一批次同一时刻只允许一个 Worker（分布式锁/任务分片），Worker 幂等。

3. **扣减成功但落库失败无补偿 → 库存泄漏（少发）**。怎么发现：对账发现 `pushed - left > issued`（Redis 已扣但 DB 没落券）持续增长。怎么防：本地事务表（outbox）保证"扣减结果必有一条待处理记录"；补偿任务重试落库；重试耗尽执行 Lua 回补（`HINCRBY left 1` + `SREM dedup`）；批次结束前跑终态对账。

4. **热点批次单 Key 打满单分片，拖垮整个 Redis 集群 → 全站缓存集体变慢**。怎么发现：分片级 QPS/网卡流出量监控（不是集群总量！）；京东到家的笨办法兜底：逐个主从切换观察分片流量变化定位问题 Key。怎么防：建券时对预测热点批次预分桶 + 随机不重复轮询 + 记录空桶直接跳过；热点批次隔离到独立 Redis 集群（京东到家的"缓存隔离"，按数据域拆集群）。

5. **Redis 主从切换丢写 → 余量虚高 → 超发几张**。异步复制下 failover 可能丢最近的扣减写。怎么发现：对账 diff（Redis 扣减累计 vs DB 落库数）出现小额度正偏差。怎么防：开启 `min-replicas-to-write` + AOF everysec 缩小窗口；接受残余万分之几概率，用"DB 条件式增补 + 对账冻结批次 + 多发券强制失效+补偿"运营兜底——工程上无法归零，只能把概率和金额敞口压到可接受（这要写进架构决策记录，别假装它不存在）。

6. **批次维度的用户限领大 Hash/ZSET → 大 Key 阻塞分片**。百万用户 × 一个批次 HASH，HINCRBY 本身 O(1) 但 Key 迁移/过期/删除是 O(N)，删除瞬间阻塞整个分片。怎么发现：从库 SCAN + `redis-cli --bigkeys`、分片流出量监控（京东到家案例：流出量 G/s 级）。怎么防：per-user 小 Key 替代批次大 Hash；大批次弃用 dedup ZSET 改 DB 唯一索引；清理大 Key 用 UNLINK/SCAN 渐进，禁 DEL。

7. **分布式锁粒度错误/超时误释放 → 并发超领**。组合 key 不互斥（vivo 实锤的坑）、业务未完成锁先超时被他人抢走。怎么发现：用户券包中同批次券数 > 限领数的投诉/风控报表。怎么防：优先用 Lua 原子计数替代锁；必须用锁时逐资源加锁+固定顺序获取+看门狗续期+加锁人校验（token）。

8. **Lua 脚本里做非 O(1) 操作 → 自己阻塞整个分片**。脚本内 KEYS、SMEMBERS 全量、大范围 LRANGE，执行期间该分片所有请求排队。怎么发现：分片 CPU 100%、慢日志中出现脚本命令、同分片无关业务变慢。怎么防：脚本评审只允许 O(1) 命令；脚本静态扫描进 CI；压测覆盖脚本路径。

9. **日限领 Key 无 TTL / 集中过期 → 内存堆积与定期删除打满 CPU**。日期 Key 不设过期，海量用户×天数无限增长；或所有 Key 同一秒过期，Redis 定期删除被占满时间片（京东到家源码分析：慢周期最多占 CPU 25%，过期键占比超 10% 会持续循环）。怎么发现：Redis 内存单调上涨、CPU 在无流量时段也高。怎么防：所有计数 Key 强制 TTL 且加随机抖动（如 2 天 + 0~1 小时随机）；巡检脚本扫描无 TTL Key。

10. **不做压测直接上线 / 线上资源贴着压测值部署**。压测暴露的问题就是线上会遇到的问题；线上容量刚好等于预估，大促必挂。怎么防：自底向上压（单实例→MySQL 读写→Redis 单分片）再整体压；线上资源 = 压测值 × 1.5；大促前全链路压测 + 盯盘（字节四件套：超时、监控报警、上游限流、跨机房部署，缺一不可）。

本章给出的形态可以总结成一句：**用 Redis+Lua 把五重校验压成一次原子操作，用"Redis 可扣 ≤ DB 已推送 ≤ DB 总量"的不变式锁死超发，用本地事务表+MQ+唯一索引完成最终一致，用分桶+随机轮询吃掉写热点，最后用对账把所有假设变成可验证的事实。**下一章（发券链路与消息一致性）将在本章的库存原语之上展开落库、状态机与核销回退。
