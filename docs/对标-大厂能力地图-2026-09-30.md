## 域 ① 优惠规则与算钱（中台的"脑子"）

### 大厂做法

**淘宝（价格服务）**：营销域有独立的**价格服务**，职责是提前算出每个商品在大促期间的**消费者到手价**＝活动价 − 叠加在商品上的各种优惠。优惠工具包括商品优惠券、满 N 件打折、跨店满减、品类券、消费券、预售直降券、官方立减等；系统需要**算出最省钱的优惠工具组合**。架构上用**责任链、中介者、适配器**等模式组织，新增玩法尽量"扩展而非改核心计算链路"，以降低测试范围。

**抖音电商（四层优惠 + 递进式叠加）**：
- **分层**：单品级（限时优惠价等）→ 店铺级（店铺券/满减/礼金/满返/赠品）→ 跨店级（平台券/达人券/官方立减/加补券）→ 其他（达人/店铺/平台购物红包）。
- **递进式计算**：按优先级依次叠加，且**以上一层优惠后的价格作为下一层的门槛**（官方示例：200 元商品 → 秒杀价 180 → 店铺券满150-30 → 官方立减 10% 与达人券各自计算 → 平台消费券/限时券/加补券 → 会员折扣 → 红包，逐层落到 54.15 元）。
- **同层择优**：同层互斥的优惠按**优惠金额取最大**生效（例："店铺券 30 元 vs 店铺满减 10 元"取券）。
- **数量上限**：单个商品/子订单对每类优惠有张数上限（例：1 张店铺券 + 1 张达人券 + 1 张平台券 + 1 张加补券；红包累计上限 10 个）。
- **配置期风控**：商家配置叠加规则时，系统**自动模拟所有叠加场景**校验最终力度；若折后价低于阈值（如原价 50%，可配置）**阻断活动上线**。

**阿里（预算与权益分配）**：预算分配建模为"渠道效能饱和度"下的**最优化问题**（连续情形用 primal-dual 对偶求解，离散情形用**分组背包 MCKP**）；权益设计基于渠道画像/权益画像/**权益影响力**（券门槛、面额、可覆盖人群）；权益分配用 **Uplift 增量模型**（估计"发券带来的因果增量"而非"会不会买"）+ 用户生命周期价值 + 用户意图识别，并做**发放速率控制**与实时特征。

### 我们现状

**零**。核销时的抵扣金额由调用方传入（`ConfirmRequest.discountAmt` 必填），平台不算钱、没有规则模型、没有试算、没有配置期校验。券类型只有满减/满折/无门槛三种，无适用范围（全场/品类/品牌/门店/单品）概念。

## 域 ② 券的形态与生命周期

### 大厂做法

- **类型齐全**：满减券、折扣券、随机金额券、商品兑换券、运费券（有赞分账文档列举）；品类/品牌/门店/新人/限时券（美团买菜侧）。
- **券码体系**：结构化编码（范围位/顺序位/随机位/**校验位**）+ 签名防伪（`HMAC-SHA256` 截断后嵌入，防客户端伪造；自增序列加密混淆 + Base32/Base64 转码，10 位码可支撑 20 亿以上唯一码）；**码池预生成**（按区间生成，用到 50% 触发缓冲，异步预申请下一区间；定时补充码池）；**BitMap 判核销状态**（不查库即可判断已兑换）；字符集排除易混淆字符，随机数用 `SecureRandom`。
- **状态机**：未使用 → 已锁定 → 已使用；分支：已过期、已作废；用唯一索引防重复领取，核销防重用 CAS + 数据库约束。

### 我们现状

三种类型（满减/满折/无门槛）；有完整状态机（待使用/锁定/已使用/已过期/作废）与三段用券、过期任务表、超时收口；**无券码/兑换码体系**、无运费券、无单品/品类/品牌/门店适用范围（表里也没有 scope 字段）。

## 域 ③ 发放：领、送、兑、定向、触达

### 大厂做法

- **投放方式**（掘金综述）：主动发券、会员领取、手动领取、**优惠码领取**、消费返券、分享发券、活动送券、主动触发送券。
- **高并发领取**：预生成带唯一 ticket_id 的加密券码写入 Redis Hash，领取时用 **Lua 脚本原子执行 `LPOP + HDEL`**（实测平均延迟 2.3ms、超发率 0%）；或 Redis 预扣 + MQ 异步落库（下述域 ⑤ 的一致性话题）。
- **额度与限领**：`maxCouponsPerProfile` / `maxCouponsPerOrder` 等参数化限制；领取用 `setnx` 原子占位 + 唯一索引 + 预扣库存。
- **秒杀公平性**：把券编号散列分布到多队列，合法请求出队后异步处理，先返回"结果统计中"（专利 CN110322280A）。
- **人群与定向**：CDP/DMP 统一 **OneID**，标签分 7 类（自定义/事件统计/事件属性/静态/SQL/档案属性/事件偏好）；**人群包**=标签组合/规则群组/静态名单（可导入名单、可推荐人群）；**权益匹配**用分位数筛选（例："过去 52 周客单价 25 分位数 > 券后金额 299"才发）+ 按相关度排序分配；**差异权益**按等级/生命周期（新人礼包/生日关怀/分层折扣）。规模参考：绝味 1.2 亿会员资产打通、150+ 标签、1000+ 分群。
- **触达**：短信（含彩信/超信）、APP PUSH、企微 1v1、公众号/小程序、广告平台；统一经消息中心；**触达策略管控**：频控、黑白名单、免打扰、跨渠道频控；**营销画布**：拖拽式编排（开始→判断分流→触点/数据操作→结束，支持属性/标签/群组/事件判断、A/B、定时等待）；自动化规则（定时触发/条件触发/完成 A 未完成 B 触发、天气时段等特殊规则）。
- **效果复盘**：统一看板看不同人群的消费表现/复购/响应/转化，形成"打标—分层—运营—复盘"闭环，配合 A/B。

### 我们现状

只有"C 端领取"一种（`POST /api/coupons/receive`），带幂等、限领（每人/每日）、IP 频控；**无人群/标签/定向**、**无触达**、**无主动发券批次**、**无券码兑换**、**无分享裂变**、**无自动化营销**。

## 域 ④ 核销与逆向（用、退、过期）

### 大厂做法

- **核销防重**：CAS + 数据库唯一约束；状态机单向流转。
- **退款冲销与分账**（有赞分账 + 电商财务实践）：
  - 优惠券在交易里有**三种角色**：平台券（平台承担）、商户券（商户承担）、混合券（按约定比例，如双11跨店满减平台/商户各 50%）。
  - 每笔优惠至少拆**三个字段：优惠来源 / 优惠金额 / 成本承担主体**（主体可以是平台/总部/店铺/供应商）。
  - **核销后重算分账**：分账在前、核销在后会导致商户未扣券成本就收到结算款，平台被迫事后追回 → 正确做法是核销事件触发后按承担规则重算各方应收应付。
  - **三个常见误区**：① 直接按券后实付算各方金额（错，基数不应变、只做承担方加减）；② 忽略税务影响（应税收入与发票金额需同步调整）；③ 把优惠券当平台收入（核销时是成本、过期时才是收入）。
  - **规则配置**：券模板上配承担比例/固定额/阶梯；按日/按月自动算账分账；**退款轧差**（下周期自动轧差、按比例回收补贴）。
  - **账单三态**：完全一致自动核销；有差异可解释的挂账；人工调整必须留操作人/时间/原因/审批，且**不得直接修改最终金额**（保留原始金额与调整记录）。
  - **编号规范**：订单号与支付流水号不可共用字段；退款保留原订单号/原支付流水号/退款单号/退款批次号；部分退款需记录商品明细。
  - **异常场景清单**：支付成功但订单取消、一个支付单对应多店铺订单、部分退款、跨月退款、平台券与商家券同时使用、会员合并后查历史订单、积分抵扣后订单关闭、线下补发无支付订单。

### 我们现状

三段用券（锁定/核销/释放）+ 过期 + 超时收口 ✓；**退款冲销零**、**成本分摊零**（`coupon_share_detail` 表已建但没人写）、无账单、无结算。

## 域 ⑤ 钱的后半程：预算、结算、对账

### 大厂做法

- **对账三阶段**（美团配送资金对账体系）：**数据准备 → 数据核对（轧账）→ 差错处理（平账）**；数据准备支持"拉取/推送(ETL)/文件上传"三种接入；核对目标是发现**漏结、重复结、错结**；需明确对账方式、制度、口径、时机。
- **演进路径**：T+1 批处理 → 小时级 → **准实时/流式**（目标分钟级发现差异）；对账被定位为"柔性事务（Saga/TCC/本地消息表）之后的**最后一道防线**"。
- **核对算法**：本质是**集合求差**（我方集合 A、渠道集合 B：A∩B 状态不一致、A−B、B−A）；朴素 O(N×M) 不可行，用哈希表优化到 **O(N+M)**；超内存用外部排序归并；**多级匹配**（一级精确流水号 → 二级模糊"时间+金额"（偏差≤5 分钟）→ 三级关联业务单号）+ 责任链 + 配置化；分布式按"交易日期+渠道"分片（128 片）用 Spark 并行。
- **差异分类与处置**：长款（渠道多给/重复扣）、短款（渠道已扣商户回调丢失）、单边账、状态不一致；有团队用差异特征库 + 随机森林自动分类根因并分派核查主体；核销数据闭环（长短款 → 核销数据）。
- **资损防控平台**（专利 CN116245623A）：配置化取数（对账结果 + binlog）→ 检测规则（小时级对账、重复交易检查）→ 输出**资损/疑似资损/非资损**三类明细 → 告警 + 追款闭环（已追回/未追回金额计算）。
- **基础设施原则**：三栏余额（可用/冻结/总额）、**流水只追加不可修改**、复式记账；"正确性先于性能、可追溯先于简洁"。

### 我们现状

**已有**：守恒式对账（四条等式）、60 秒巡检 + 亚秒三步确认、方向判据（Redis 多钱→冻结 / 少钱→只修）、独立线程修复（白名单+影子模式）、熔断、漂移表、T+1 审计（库存/过期/超时/发件箱守恒）。
**缺**：面向**资金**的结算对账（两方/多方核对、差异工单、长短款核销）、配置化数据接入、多级匹配、差异的智能分类与追款闭环。

## 域 ⑥ 平台能力：接入、多租户、灰度、风控、治理

### 大厂做法

- **开放平台接入规范**（百度/京东/华为/银行规范综述）：
  - **鉴权**：应用唯一标识（appId/AK）+ 密钥（SK）签名；`Authorization` 头携带版本/时间戳/有效期/签名头/签名；服务端用同样机制重算比对。
  - **签名**：参数 + 时间戳 + 密钥哈希生成 sign（防篡改 + **防重放**，有效期如 15 分钟）；参数按 key 字母升序；时间戳格式与误差（京东：误差 10 分钟内）。
  - **幂等**：`clientToken`（≤64 位，24 小时内同 token 同参返回同结果，参数不同返回 `IdempotentParameterMismatch`）；或业务流水号 + 幂等表；区分**可重试错误码（5xx/超时）与不可重试错误码（4xx 业务错）**。
  - **限流与配额**：三维度（IP / 接口 / 调用方），配额超出直接 **429**；本地限流 + 队列削峰；盲目重试会放大调用量触发降权。
  - **版本化**：URI 前缀（`/v1`）或 Header 协商；加字段兼容、删改字段走新版本。
  - **接入流程**：沙箱压测 → 灰度上线（1 家测试 → 3 家小流量 → 逐步放量）；回调接口快速返回 + MQ 异步消费 + 去重 + 定时轮询兜底。
- **多租户与灰度**：`X-Tenant-ID` 强制隔离数据域；`X-Gray-Strategy` + 设备指纹哈希保证灰度流量一致性。
- **业务风控**：设备指纹（Canvas/WebGL/Font/AudioContext 硬特征哈希）、IP 画像（ASN/地理围栏/代理与 IDC 标识/历史风险标签）、行为时序（首屏时间/滚动深度/鼠标轨迹熵）；`SHA256(IP+UA+Canvas+GeoRegion)` + Redis BloomFilter 去重；**五道防线**（同 IP 多注册→验证码；单设备账号上限→拒绝；设备指纹拉黑；手机号注销库；验证码连续失败封 IP）；实时规则引擎（OPA/Rego"策略即代码"）；身份绑定 + 卡券交易登记（降低二次交易）；实测拦截 97%+ 刷券行为。
- **应急预案与止血**：**预案平台**（一键降级/开关/切流/限流/熔断/重启；华为"1 分钟发现-5 分钟定界-10 分钟恢复"、B站"1-3-5-10"）；**红黄蓝三级预案**（按对业务与**资损**的影响分级）；Feature Flag / Kill Switch；熔断（失败率阈值 + 半开探测）；"止损三板斧=回滚/降级/切流"；度量：预案覆盖率、MTTR、演练次数。
- **缓存体系**：多级缓存（CDN → Nginx → 本地 JVM（Caffeine，W-TinyLFU）→ Redis → DB）；本地命中率 70~90%、Redis QPS 降 60~80%；**热点 key 探测**（京东 JDHotKey：滑动窗口"5 秒 10 次"判定 → 自动提升到本地缓存，P99 从 2.1ms 降至 0.08ms、Redis QPS −63%）；一致性用延迟双删 / 订阅 binlog→MQ→invalidate。
- **最终一致性**：本地消息表（eBay BASE 论文；携程/拼多多实践）/ RocketMQ **事务消息**（半消息→本地事务→提交/回查）/ CDC（Debezium 监听 binlog）；落地必备：消费幂等、指数退避、死信 DLQ、顺序性（分区键）、对账兜底。

### 我们现状

**已有**：管理面 admin token、IP 频控（fail-open）、本地缓存 Caffeine（三兄弟防护）、本地消息表 + RocketMQ + 消费幂等 + 退避 + 死信 + T+1 守恒审计、模板冻结/售罄牌/影子修复/熔断（自愈向）。
**缺**：appId/签名/配额（开放平台），多租户、灰度、设备指纹与名单、实时规则引擎、预案/开关平台与 1-5-10 度量、多级缓存与热点探测、消息顺序性、跨机构对账与差异工单。

## 域 ⑦ 流量治理与过载保护

### 大厂做法

- **Sentinel（阿里开源，源自 2012 年内部系统保护需求，承接近 10 年双 11 核心流量场景）**四大能力：**流量控制**（QPS / 线程数）、**熔断降级**（异常比例 / 响应时间 / 异常数）、**系统自适应保护**（Load、CPU 使用率、入口 QPS、RT、并发量；借鉴 TCP BBR 思想，核心公式 `平均RT × 最大QPS = 预估容量`）、实时监控 Dashboard（秒级）。
- **流控维度与效果**：维度 = 资源 / 调用关系 / 链路（直接、关联、链路策略）；效果 = **快速失败 / Warm Up（冷启动慢启动）/ 匀速排队（漏桶削峰）**。
- **热点参数限流**：LRU（社区演进 LFU/ARC）+ 滑动窗口识别热点参数，**按参数值分别限流**（典型场景：网关层限频繁访问的客户端 IP 防爬、写服务防热点数据抢锁）。
- **集群流控**：Token Server 提供全局配额（阿里云 MSE 集群限流基于此）；与 Envoy/Istio（RLS、WASM 插件）、MOSN 集成。
- **规则持久化（生产必做）**：Sentinel 规则默认存内存、**重启即丢**；生产用 Nacos/Apollo 数据源持久化（Dashboard 改规则 → 推送配置中心 → 应用监听热更新）。
- **隔离方式**：Sentinel 用**信号量隔离**（Hystrix 的线程池隔离随 Hystrix 停维护退出主流）。
- **选型（JavaGuide 等综述）**：Spring Cloud Alibaba 生态 → **Sentinel**；**Spring Boot 3 + JDK 17 且不依赖 SCA 生态 → Resilience4j**（`resilience4j-spring-boot3`，模块化：CircuitBreaker/RateLimiter/Retry/Bulkhead/TimeLimiter；轻量 ~10MB，但无内置 Dashboard、规则需自行接配置中心）；混合方案：网关层 Sentinel、内部调用 Resilience4j。
- **最佳实践**：服务提供方按压测容量配 QPS 限流自保；调用方对不稳定依赖做隔离 + 熔断；冷启动用 Warm Up；削峰用匀速排队；网关层按用户/IP 限频。

### 我们现状

**已有**：IP 频控（fail-open）、管理面 admin token、DB 连接池超时快速失败（L31 已外部化）、**修复环熔断**（连续 FORCE 止损，运维层）、故障注入钩子（演练基建）。
**缺**：入口多维度限流（appId/接口/链路/热点参数）、Warm Up 与匀速排队、**调用级熔断**（依赖 Redis/MySQL/MQ）、舱壁隔离、系统自适应保护、集群配额、**开关中心与三级预案**。
