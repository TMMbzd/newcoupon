## 0. 一句话问题

用户下单锁了券之后，订单侧的"取消"或"支付成功"**再也没有传来**（进程崩溃、调用超时被丢弃、调用方违约）——券永久停在"已锁定"，用户资产悬挂。本方案给 LOCKED 状态补第四个出口：**锁定超时，系统自己收场**。

## 1. 现状：券和占用单的状态机（本方案的改动对象）

**两张表的全部状态清单**（左边今天已实现；"← L5"是本方案新增、待批准）：

| 券（user_coupon.status，5 个） | | 占用单（coupon_usage.status，今天 4 个 + L5 的第 5 个） | |
|---|---|---|---|
| 0 待使用 | 活（→锁定/→过期） | 0 占用中 | 活（唯一的活合同） |
| 1 已锁定 | 活（→核销/→释放/→过期） | 1 已核销 | 终态（财务凭证：用了） |
| 2 已核销 | **终态** | 2 已释放 | 终态（退了） |
| 3 已过期 | **终态** | 3 过期关闭 | 终态（拖着拖死，L2 加） |
| 4 已作废 | **终态**（M6 才实现） | 4 超时关闭 ← **L5** | 终态（订单死了系统收场） |

对应关系：**活配对只有一种**——券=已锁定 ⇔ 占用单=占用中；占用单终态更多是因为一张券能签多份合同，每份合同的死法都要留凭证。唯一不经占用单的边：券"待使用→已过期"（从没签过合同）。

**用券三段**（阶段0实现，至今未变）：

```
下单   → lock()    ：券 0待使用→1已锁定；插占用单（status=0占用中）
支付成功 → confirm() ：占用单 0→1已核销（写抵扣金额）；券 1→2已核销（终态）
订单取消 → release() ：占用单 0→2已释放；券 1→0待使用（已过期则→3，见下）
```

### 1.1 券与占用单的分工：资产 vs 合同（本方案的地基，先立稳）

- **用户券 = 资产本体**。它只有一个 `status` 字段，回答不了"现在**是哪个订单**在用我""这条消息**处理过没有**"。
- **占用单 = 一份"某订单占用某张券"的合同**（`usage_no = 订单号:券id` 唯一）。它补上这两个答案：谁在用（行里记着订单号）、处理到哪了（status 即进度）——所以它是**幂等锚点**（重复消息查它定案）与**回退裁判**（核销/释放前先看它）。

**关键认知一：占用单的 0（占用中）是唯一的"活合同"状态**。离开 0 的每条路（1/2/3，加本次的 4）都是合同终结——关了就是关了，不存在复活一份关掉的合同。
**关键认知二：合同关闭 ≠ 券死了**。一张券的一生可以签多份合同：

```
10:00  订单A锁券   券 0→1          占用单A诞生(0)
10:31  超时收场   占用单A 0→4【A合同关闭】  券 1→0【资产回池，用户无损】
11:00  新单B锁券   券 0→1          占用单B诞生(0)   ← 新订单=新合同
11:20  B支付成功   占用单B 0→1(金额) 券 1→2(终态)
这张券的一生 = 1 份资产，2 份合同（A 关闭 / B 履行完毕）
```

四种占用单终态 = 财务四种账目形态（用了/退了/拖着拖死/订单死了系统收场）——合同行**不删**，留给对账与客服归因。用户从不直接"使用"占用单：它是订单与券系统之间的内部凭证，每份合同恰好被推进一次（0→某终态），此后只读。

### 1.2 背景知识：现实中"用券支付"的完整流程（三个系统的分工与三方资金流）

"支付成功"与"核销成功"是**两个系统、两个时刻的独立判定**——支付系统（微信/支付宝）不知道券的存在，只管钱到没到。以美团点外卖为例（45 元外卖、满 40 减 8 的券）：

```
   用户            订单系统              券系统             微信支付
   |  下单，勾选券   |                   |                   |
   |──────────────→|  ①锁券（预留优惠）    |                   |
   |               |──────────────────→| 券 待使用→已锁定    |
   |  看到"应付37元" |                   |                   |
   |  点"去支付"     |                   |                   |
   |───────────────────────────────────────────────────────→|
   |               |                   |      ②扣 37 元      |
   |               |  ←──── ③"钱到了"（支付回调）──────────────|
   |               |  ④核销（把锁定的券正式花掉）               |
   |               |──────────────────→| 券 已锁定→已核销     |
```

- **①下单锁券（不是花掉，是预留）**：订单系统算价 45−8=37，同时锁券。为什么锁不直接花：用户可能不付款，"已核销"是终态不可逆（要能退就得可逆）；不付款取消订单时释放回池。用户视角的体验即"订单超时未支付，优惠券自动退回"。
- **②支付**：微信只收到"付 37 元"，不知道也不需要知道这 37 怎么算出来的。
- **③支付回调**：支付系统反向调用订单系统通知"钱到账"。支付天生异步（用户掏手机输密码要几分钟）、消息会丢会重试——**回调天然可能迟到**，这是"迟到核销"的物理来源，不依赖恶意。
- **④核销**：订单系统收到"钱到了"之后，才调券系统正式花券。
- **推论**：核销失败可以发生在支付成功之后（钱已走、券这边出问题）——这就是 D4 场景的资金背景。

**三方资金流——优惠的那 8 元是谁出的**：商家交出 45 元的货，只从用户收到 37 元；差的 8 元由**平台**补给商家（券=平台替用户垫付部分价格的营销支出；本项目设定平台承担，商家券同理只是出钱方不同）。平台补钱的**付款凭证是核销记录**（占用单 CONFIRMED + 核销事件的真实抵扣金额——CouponEvent"核销事件才记金额"注释的财务含义，事件表=事实源）。因此核销失败的财务含义是：**用户侧优惠已发生（少付了），资金侧补贴没有凭证（结算系统看不到该为这笔订单补钱），缺口悬在商家头上**。"优惠"是两半的合成：用户少付 + 平台补差，后者以核销为凭证。

L2（2026-09-12）已补的出口：**锁定期间券到期**——核销时被 SQL 谓词拒绝后收场为"占用单 3=过期关闭、券 3=已过期"；过期任务扫描器也会对"锁定中且到期"的券做同样收场。

## 2. Bug 复现：静态穷举证明

### 2.1 为什么这个 Bug 写不出红灯测试（工序 v2 诚实声明）

L2 的 Bug 是**谓词缺失**：`casConfirm` 少了 `valid_end > NOW()` 条件——用现有接口就能演示"过期券居然核销成功"，红灯测试写得出来。

L5 的 Bug 是**子系统缺失**：不存在任何会拯救超时锁的代码。测试没有可调用的入口去暴露"不存在的东西"（调用一个不存在的扫描器，测试根本编译不过）。所以按工序 v2 的规则退而求其次：**穷举所有出口 + 时序推演**，证明存在"三出口同时关闭"的场景。以下每个出口都给到代码行号，可打开对照。

### 2.2 穷举：券 LOCKED 状态的全部写者

改 `user_coupon.status` 的代码全在 [UserCouponMapper.java](../src/main/java/com/newcoupon/infrastructure/persistence/mapper/UserCouponMapper.java) 的 CAS 里（`CouponStateMachine` 只是内存校验不写库；领券只写 status=0 不涉及 LOCKED）：

| # | 出口 | 代码位置 | SQL 谓词（打开条件） | 去向 |
|---|---|---|---|---|
| 1 | 核销 | [casConfirm, 行41](../src/main/java/com/newcoupon/infrastructure/persistence/mapper/UserCouponMapper.java#L41) | `status=1 AND valid_end > NOW()` | 2 已核销 |
| 2 | 释放 | [casRelease, 行59](../src/main/java/com/newcoupon/infrastructure/persistence/mapper/UserCouponMapper.java#L59) | `status=1` | 0/3 |
| 3 | 锁定中过期 | [casExpireOnLock, 行51](../src/main/java/com/newcoupon/infrastructure/persistence/mapper/UserCouponMapper.java#L51) | `status=1 AND valid_end <= NOW()` | 3 已过期 |

三个出口的打开条件分别是：**①②要"有人来调"**（订单侧 confirm/release），**③要"时间到"**（valid_end 过期，且被过期任务表扫到）。

### 2.3 时间线推演（具体数字）

```
2026-09-13 10:00:00  lock 成功：
    user_coupon:        status=1(已锁定), valid_end=2027-03-01（还有半年）
    coupon_usage:       status=0(占用中), occupy_time=10:00:00
    coupon_expire_task: next_scan_time=2027-03-01（半年后才到期，扫不到它）

10:20  用户放弃支付，订单服务决定取消订单
       → 按契约它该调我们的 release 接口
       → 调用丢失：订单服务恰好崩溃 / HTTP 超时被它丢弃 / 它的代码漏了调
10:20 起出口检查：
    ① 需要 confirm 被调用 —— 没人再调（订单已死）
    ② 需要 release 被调用 —— 没人再调（这就是丢失本身）
    ③ 需要 valid_end 到点 —— 还差半年
    ⇒ 三出口同时关闭

任意时刻查库：券 status=1，占用单 status=0，永远不变。
用户视角：券包里这张券永远显示"已锁定"——不能核销（不是他的调用）、
         不能释放（没有入口）、不能再用于别的订单（锁着）。
```

### 2.4 影响评估

- **性质**：不是超发也不是少发，是**用户资产悬挂**——券的使用权被一次丢失的调用永久扣押。投诉与客服工单源头；客服今天没有任何工具解救（无作废/强制释放功能）。
- **频率**：同步调用阶段=订单服务的崩溃窗口（低）；M5 上 MQ 后=极端消息丢失（更低）。**本方案不为频率设计，为正确性设计**——与"优雅停机 30s"同一原则：每一个"等对方回话"的中间态都必须有超时自愈，否则中间态就是悬挂态。
- **规模放大**：券量 10 亿级（M4 后），任何万分之一概率的悬挂都是上万张券的客诉。

### 2.5 顺带发现：L2 扫描器的半收场窗口（穷举的额外收益）

穷举出口时发现 [CouponExpireService.processOne, 行131-136](../src/main/java/com/newcoupon/application/service/CouponExpireService.java#L131-L136) 的收场链**没有事务包裹**：

```java
transitioned = userCouponRepository.casExpireOnLock(couponId);  // 第一步：券 1→3
if (transitioned) {
    couponUsageRepository.casExpireByCouponId(couponId);         // 第二步：占用单 0→3
}
```

两步之间进程崩溃 → 券已终态(3)、占用单仍占用中(0)、无事件。重扫时券不再是 LOCKED → 直接 `finish`，**占用单永远悬挂**。更糟的连锁：此时迟到核销到来，`casConfirm(usage)`（谓词只查占用单 `status=0`）**成功置 1 并写金额**，随后 `casConfirm(coupon)` 因券已终态失败回滚——但占用单的 UPDATE 和券的 UPDATE 在**同一个事务**里（TradeTxService.confirm @Transactional），所以会一起回滚。核实结论：**无账实不符**（事务救了它），残余问题是占用单悬挂 0 的统计口径虚高（"在途占用"数不准）与无事件可审计。
**处置**：登记为 F1，随 L5 实施一并修（L5 的收场链以事务方法落地，同时给 expire 扫描器补"券已终态但占用单仍占用中"的补刀分支——CAS 幂等，安全）。

## 4. 设计裁决（六项）

### D1 超时窗口：可配置，默认 30 分钟

`coupon.trade.lock-timeout-minutes`（application.yml，默认 30）。

- **为什么 30**：与电商"订单 30 分钟未支付自动取消"的通用契约对齐——券的锁定窗口必须 ≤ 订单支付窗口，否则会出现"订单已取消、券还锁着"的正常路径摩擦。窗口值是**与订单域的业务契约**，不是券系统单方面拍的。
- **为什么必须可配置**：验收测试要能把它缩到毫秒级——否则每个回归用例真等 30 分钟。
- **否了**：写死常量（测试不可缩）；把窗口塞进模板配置（每张券不同窗口是无证据的灵活，M6 有需求再说）。

### D2 任务登记与发现：新窄表 coupon_release_task，锁券同事务注册

三个候选：

| 方案 | 内容 | 裁决 |
|---|---|---|
| A 新窄表 | 照抄 V5 遗憾骨架建 `coupon_release_task`，锁券事务内注册 | **✅ 采纳** |
| B 复用过期任务表 | `coupon_expire_task` 加 `task_type` 列区分两种任务 | ❌ 扫描条件从单值 `status=0` 变组合 `status=0 AND type=x`，违背 L2 "扫描条件永远单值，无漏扫死角"的纪律；退避/死信两套语义混一表 |
| C 直接扫业务表 | 定时扫 `coupon_usage WHERE status=0 AND occupy_time<...` | ❌ 宽表（金额/订单号/三个时间列）千万级扫描；无退避/死信字段，失败重试节奏无处记——L2 立项前复盘的三起真实事故（IO 打满/长锁卡死支付/中断不可判定）全是"在业务大表上跑定时任务" |

**"同一骨架换谓词换动作"的精确含义**（与 V5 逐项对照）：

| 骨架要素 | coupon_expire_task（L2） | coupon_release_task（L5） |
|---|---|---|
| 列结构 | id/coupon_id/user_id/shard/next_scan_time/status/retry_count | **完全相同** |
| 唯一索引 | uk_coupon(coupon_id) | 相同 |
| 扫描索引 | idx_scan(status, next_scan_time) | 相同 |
| 退避公式 | `min(2^retry, 30min)`，8 次死信(3) | 相同 |
| 注册点 | 领券事务内（"发了必有任务"） | **锁券事务内**（"锁了必有任务"） |
| next_scan_time 初值 | valid_end（到期该处理） | **occupy_time + 锁定窗口**（到时该处理） |
| 到点动作 | 过期收场（券→3） | 超时收场（券→0/3，占用单→4） |

同事务注册的原子性保证：任务 INSERT 失败 → 锁券整体回滚 → 不存在"有锁无任务"（与 L2 同构，审计只防未来旁路产生锁定）。

**"怎么判定超时"而不误伤正常锁定——两道守卫（评审追问补记）**：系统判断的不是"订单死没死"（沉默无法区分死亡与犹豫，不可知），而是"契约窗口内办完没"。守卫①**时间守卫**：deadline=occupy_time+窗口，锁券时固化写库；扫描条件 `next_scan_time <= NOW()`——不到点任务物理上不可见，锁定 29 分钟的占用单与扫描器无关。守卫②**状态守卫**：到点后收场 SQL 自带裁判 `WHERE status=0`——订单窗口内已 confirm/release 的，占用单已离开 0，影响 0 行 no-op；仍挂 0 的才收场为 4。判断与执行在同一条 SQL 内原子，无需预知世界状态。慢用户（29:59 支付页）的误伤由窗口与订单域支付超时契约对齐压到最窄，残余由 D4 的 4006 路径承接。

**分片纪律（批次二起的新规矩）**：V7 直接建 64 张物理分表（`coupon_release_task_0..63`，user_id%64 路由），加入 ShardingSphere 绑定表组——**新表生而分片，杜绝"先单表后拆"**。

### D3 收场后的状态：占用单第四终结态；券回可用或过期

**占用单**：`UsageStatus.TIMEOUT_CLOSED(4, "超时关闭")`。四种终结对财务是四种账目形态——用了(1)/退了(2)/拖着拖死(3)/订单死了系统收场(4)——客服归因"券为什么被释放"必须可分辨。
**否了**复用 RELEASED(2)：省一个枚举值，换来审计不可分辨。

**券**：`LOCKED → 未过期? USABLE : EXPIRED`——与 `casRelease` 的 IF 语义完全一致（[UserCouponMapper.java:59](../src/main/java/com/newcoupon/infrastructure/persistence/mapper/UserCouponMapper.java#L59)）。对资产而言"订单取消"和"订单超时死亡"结果相同（券回来）；差异只在占用单终态与事件类型（审计事实）。

新 CAS（各一行，谓词即状态机边）：

```sql
-- 券：锁定超时收场（未过期回可用，已过期收终态）
UPDATE user_coupon SET status = IF(valid_end > NOW(), 0, 3)
 WHERE id = #{id} AND status = 1;
-- 占用单（扫描器路径，按券id）
UPDATE coupon_usage SET status = 4 WHERE user_coupon_id = #{couponId} AND status = 0;
```

状态机加一条边 `LOCK_TIMEOUT(LOCKED → USABLE, "锁定超时释放")`——过期分流在 SQL 的 IF 里，与 RELEASE 边的先例完全一致（状态机表达主路径，IF 是 SQL 层的落地细节）。事件类型 `EventType.LOCK_TIMEOUT(7, "锁定超时释放")`，事件含订单号（对账归因"哪个订单的死锁被收了场"）。

### D4 迟到核销：拒绝 + 明确错误码 4006

**场景推演**：30:01 扫描器收场（占用单=4，券=0）；31:00 支付成功回调到达 `confirm` → `casConfirm(usage)` 谓词 `status=0` 不满足（已是 4）→ 编排层分类。

裁决：`checkConfirmable()` 补 TIMEOUT_CLOSED 分支，抛新错误码 `USAGE_TIMEOUT_CLOSED(4006, "占用单已超时关闭（券已回收/过期），核销拒绝")`。

- **为什么必须拒绝——逐笔推演的精确伤害**（评审修正：最初版本把伤害压缩成"一券两花"，暗示两笔补贴都直接落账——不实。直接落账只有一笔，第二笔藏在业务补偿里）。迟到核销到达时超时收场**已发生、券已回池**，而回池的券可能已被**新订单 B 重新锁走**：

```
10:00  订单A锁券：券=1，占用单A=0
10:31  超时收场：占用单A→4【合同关闭】，券→0【回池】
11:00  用户拿这张券下新单B：券→1【B的锁】，占用单B=0
11:30  订单A的支付回调终于到达（迟到核销）
       ↑ 此刻券 status=1 是合法可核销形态——但它是 B 的锁！
```

  **设定**：满 1000 减 200 的券一张，属于用户张三；订单 A、订单 B 都是张三的订单（一张券只服务它的主人）。"放行"指假设拆掉 4006 这道闸、让 A 的迟到核销成功执行。先备两个背景：**事务**＝把多条数据库写入捆成一包，要么全部生效要么全部作废；**release（释放）**＝用券三段的第三段接口，订单取消时订单侧调用，含义"这个订单不用这张券了，退回去"（做占用单 0→2、券 1→0 两件事）。

  - **10:00 订单 A 锁券**：券 0→1；插入占用单 A（status=0 占用中）。
  - **10:31 锁定超时，扫描器收场**：占用单 A 0→4（合同关闭）；券 1→0（张三在券包里看见券回来了）。
  - **11:00 张三用这张券下新单 B**：券 0→1（这次是 B 的锁定）；插入占用单 B（status=0）。
  - **11:30 订单 A 的支付回调迟到到达，被（假设性地）放行**——核销方法在一个事务里依次执行两条 UPDATE：
    1. 改占用单 A：4→1（已核销），写入抵扣金额 200 分。**这是平台账上真实记下的第一笔补贴，付给了一份已经关闭的合同**。
    2. 改券：1→2（已核销，终态）。这一步的执行条件是"券当前 status=1"，恰好满足——但这个 1 是 **B 的锁定**，A 的核销偷走了 B 的位置。
    此刻数据库自相矛盾：券显示"已核销"（账记在 A 头上），同时还有一份活着的占用单 B 声称"订单 B 正在用这张券"。
  - **12:00 订单 B 支付成功，正常来核销**——同一个核销方法，两条 UPDATE：
    1. 改占用单 B：执行条件"占用单 status=0"满足，这步能改；
    2. 改券：执行条件"券 status=1"不满足（券已是 2），改了 0 行，方法抛出冲突异常；
    3. 因为两条捆在同一事务里，第 1 步已做的修改被撤销，数据库回到这次调用没发生过的样子。B 得到错误答复。
    因此**账面上平台仍然只付了一笔补贴（A 那笔）**。"两张占用单都已核销、账面直接付两次"不会发生——要发生，除非把"改占用单"和"改券"拆开、各自独立提交（不捆事务）：那样第一条落账后第二条失败也不撤销，才会留下双付账。§2.5 登记的 F1 正是那种写法的实例——过期扫描器把"改券"和"改占用单"分成两条独立 UPDATE 执行，中间崩溃会留下一半生效一半没做；核销方法因为捆了事务，不会出这种半截状态。
  - **12:05 起 B 的订单走投无路**：重试核销，每次都死在第 2 条 UPDATE 上，结果永远相同。若 B 放弃优惠、取消订单，按接口契约订单侧会调用 release 想把券退回去——release 同样是两条 UPDATE 捆一个事务：改占用单 B（条件"status=0"）能过；改券（条件"券 status=1"）改 0 行、抛异常、整体回滚。**B 连释放也失败**。
  - **此后的占用单 B 是一条永远不会变的死记录**：它所有可能的出路（核销/释放/过期关闭/超时关闭）每一条都要同时改券，而券躺在终态 2 里永不回头，所以没有任何代码会再推进这行数据。这样一行"声称某事正在进行、实际上永远不会进行"的数据库记录，称为**悬挂**。它的害处：统计"当前在途占用数"永久虚高一格；客服查张三的投诉时看到"占用中"，与事实（券早被 A 核销）矛盾；将来做占用单×券状态交叉对账（M1 规划项）这一条永远报不一致。它的结局与 F1 崩溃留下的残局（券已终态、占用单停在占用中、无人收尾）**一模一样，只是成因不同**：F1 是崩溃卡在两条独立 UPDATE 之间造成的，这里是放行迟到核销把券提前打进终态造成的。
  - **面额实际流出两次（三方资金流口径，见 §1.2）**：券系统账上记了一笔 200 分补贴（A 的核销凭证，凭它给 A 的商家结 200）。订单 B 这边：张三按优惠价付了 800、商家发了 1000 的货，缺口 200 分本应由平台凭 B 的核销凭证补给商家——但 B 核销失败、**凭证不存在**，结算系统看不到任何该为 B 补钱的记录，缺口悬在商家头上。现实中为不毁掉已支付的订单，结局通常是平台无凭证地自己吸收这 200 分（营销外支出），或整单退款毁掉交易。合计算：一张 200 分的券，平台实际掏了 400 分（A 的凭证补贴 200 + B 的无凭证垫付 200）；张三则两笔订单各少付 200——**一张券吃两次**。
  - **可被恶意构造**：有心人可以这样操作——下单 A 锁券但不支付；等 30 分钟超时收场、券回池；下新单 B 锁同一张券；然后让 A 的支付完成，使 A 的回调恰好落在"B 已锁定、B 尚未核销"的时间窗里。支付系统的回调重试机制天然会制造迟到回调——无心用户会撞出这个窗口，有心用户会专挑它。得手后的白嫖形态见上条：A 的凭证补贴 + B 的无凭证垫付，一张券吃两次；若 B 走整单退款，他也毫无损失地重试下一单。

  最关键不变：该窗口里**券侧 CAS 拦不住**（status=1 是 B 的合法锁），**唯一守卫就是占用单A 的 status=4**——这就是"占用单是裁判"的分量。另一交错（B 先核销完、券已 USED）下 A 被拦、无害——损害取决于交错顺序，但有害交错真实存在且可被主动构造。
- **同族边角（评审发现，随 L5 一并修）**：订单 A 在合同终结后**重放锁券请求**（重试风暴）——[TradeAppService.lock 幂等快检](../src/main/java/com/newcoupon/application/service/TradeAppService.java#L52-L55) 只查"占用单存在"就答"已锁定"，对终态（2/3/4）是谎报（券已回池甚至易主）。修法：快检只对 **0（占用中）** 回幂等成功，终态按状态冲突分类（提示换新订单号）。现状对 status=2 重放已错，L5 引入 4 会放大——登记 F2。
- **订单侧语义**（本系统边界外，写入对接文档）：拿到 4006 的订单自身通常也已支付超时（D1 的两域窗口对齐），标准处理是整单退款；若业务允许继续履约，则按无券价处理差额——决策在订单域。券系统只保证**不自相矛盾 + 错误可编程**，替订单域送钱（自动补券）是越权决策。
- **否了**：迟到核销放行（资损）；自动补发（越权 + 无审计口径）。

### D5 迟到释放：幂等成功 + 读券真实状态（顺带清偿 L15）

**现状 L15**（登记在案）：`release` 的幂等分支硬编码返回"待使用"——释放时券恰好已过期的话，重放会显示错状态。

**L5 新增场景**：收场后订单取消消息迟到到达 `release` → 取消的**意图已达成**（券早已回收），报错只会制造工单。

裁决：release 对"占用单已终态（2/3/4）"一律当**幂等成功**返回，且状态一律读券**新鲜快照**（`fresh.getStatus().getDesc()`）——L15 的硬编码分支顺带消灭。`checkReleasable()` 的 CONFIRMED 拒绝不变（资损红线：已核销不可释放）。

### D6 扫描器与审计：照抄 CouponExpireService 骨架

- **CouponReleaseService**：`@XxlJob("couponReleaseScanJob")` + `@Scheduled(fixedDelay=60s)` 双通道；RedisScanLock 新键 `c:rel:scanlock:0`（TTL 90s）；`scanOnce ≤20 批 × 500`；分片广播 `shard % total`。
- **processOne 分流（与 L2 的关键差异——收场链在事务里，根治 F1 同款窗口）**：

```
券不存在          → finish（任务意义消失）
券 = LOCKED       → tradeTxService.timeoutClose(couponId)  ← 一个事务：
                     占用单 0→4 + 券 1→IF(未过期?0:3) + LOCK_TIMEOUT 事件
                     成功后 finish
券 = 其他（0/2/3/4）→ finish（已核销=订单其实说话了；已释放=收场已完成；
                        已过期=L2 已收场）——幂等，重扫 0 件
单条失败          → backoff（指数退避，8 次死信）
```

- **与 L2 扫描的竞态分析**：两边 CAS 都从 `status=1` 出发，InnoDB 行锁天然串行——恰有一家赢。若"超时且已过期"同时满足：L2 赢 → 券 3/占用单 3；L5 赢 → 券 3（IF 分流）/占用单 4。终态不同但**都合法**——事件类型记录了"谁收的场"这一真相，财务可分辨。
- **T+1 审计（对称 L2 的漏注册审计）**：每日查"仍占用中但锁龄超窗口+10 分钟"的占用单补注册任务（防未来旁路产生锁定，如 M6 客服工具直接改库）。查询路径：券表 `status=1` 走 `idx_expire` 前缀（status 等值），LIMIT 1000，再对券查占用单判锁龄——**不给 usage 表拍脑袋加索引**，日频低量查询现有路径可承受，M3 压测后有数据再说。
- **F1 修复**（2.5 的顺带发现）：CouponExpireService.processOne 补一个分支——券已是终态（3）但该券占用单仍 `status=0` → 补跑 `casExpireByCouponId`（幂等 CAS，安全）。
