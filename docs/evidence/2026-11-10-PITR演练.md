## 1. 结论（先看这一节）

| 指标 | 目标（5C 口径） | 实测（2026-11-12 复跑轮） | 判定 |
|---|---:|---|---|
| 全量恢复基线（复用 5B） | 20 条断言 | **RESTORE PASS assertions=20**（restore 83.046s + verify 5.995s） | ✅ |
| 归档完整性闭环（S2③ 新增） | 重放前 sha256 校验 | `mysql-bin.000018 sha256 == manifest`（293d1ff0…4813） | ✅ |
| PITR：T 前数据在 | 3 行 marker + 1 张真实模板 | marker 3/3、`PITR-INC-20261112140822` 在 | ✅ |
| PITR：T 后数据不在 | 毒模板 + 2 行 marker 必须缺席 | `AFTER_T` 0 行、`PITR-ACC-20261112140822` 0 行 | ✅ |
| 重放不破坏 schema | flyway 历史行数 == dump 时刻 | 44 == 44；表数 = meta+1（只多 pitr_marker） | ✅ |
| binlog 归档（独立验证） | 幂等 + 世代检测 + flock | 重跑"归档 1/跳过 N"；模拟换卷→旧档自动 superseded 后继续（§2.1）；并发实例被锁拒绝 | ✅ |
| RPO：写入→已归档即时窗口 | — | **8.627 s**（含归档单轮 7.912s；机器上另有外来容器抢 IO，首跑轮同口径 4.111s） | 口径见 §4 |
| RPO：排班最坏窗口 | MVP ≤15min | **P(5min) + 单轮 4~9s ≈ 5.1~5.2min** | ✅（≤5min 的生产档不严格满足，见 §4） |
| 容器重建不丢数据 | compose 加 binlog 参数=重建 | force-recreate 前后 6 项计数完全一致（§2） | ✅ |
| 脚本输出 | — | **PITR DRILL PASS assertions=9**（EXIT=0） | ✅ |

**一句话**：从"只有 dump 级备份"升级到"全量基线 + binlog 增量 + 任意时间点恢复"——
误操作发生在 T 之后，恢复到 T：T 前的写入一笔不少地回来、T 后的毒数据一笔不进；
binlog 归档脚本幂等可排班（卷换了不卡死、撞车了不并行写、重放前先验档），RPO 从
"最坏丢一个 dump 排班周期（15min）"收紧到"归档周期 + 秒级"。

## 2. compose 变更与容器重建实测

`docker-compose.yml` mysql 服务新增（其余不变）：

```yaml
- --log-bin=mysql-bin     # 显式开 binlog，文件基名 mysql-bin.NNNNNN（8.0 默认基名是 binlog.*）
- --binlog-format=ROW     # 行级：重放的是行变更，与生产 PITR 同语义
- --server-id=1           # binlog 必需；GTID 未开（与生产差距见 scripts/backup/README.md）
- --sync-binlog=1         # 每提交 fsync——mysqld 崩溃不丢已提交事件（RPO 口径的一半）
```

**command 变更 = 容器重建，不是原地升级**。实测验证数据卷 `mysql-data` 无损：

```text
docker compose up -d --force-recreate mysql 前后各查一次：
tables=305 templates=57 flyway=44 audit=80 stock_used_sum=37213 user_coupon_rows(分片0+63)=1161
→ 六项完全一致（RECREATE_DATA_INTACT）
SHOW VARIABLES: log_bin=ON  binlog_format=ROW  server_id=1  sync_binlog=1
SHOW MASTER STATUS: mysql-bin.000001  157        （新基名序列从 000001 起）
注：旧基名的 binlog.000001..25 仍在卷里，不进新序列（README 已写明）
```

### 2.1 归档脚本的两个护栏实测（2026-11-12 审查修复轮，归档 `s1-supersede-test.log` / `s1-flock-test.log`）

- **卷世代切换**：在归档目录副本里把 `mysql-bin.000001.gz` 换成不同内容（模拟
  `down -v` 后新卷从 000001 重排）→ 脚本 WARN 判定世代切换、旧档整体移入
  `superseded-20261112-134810/` 留档、继续归档全部 10 个新卷文件、manifest 记录
  `superseded.movedTo`，**EXIT=0**；紧接着的重跑"归档 1/跳过 10"正常幂等。
- **flock 并发护栏**：持锁 10s 期间第二个归档实例退出码 1、输出
  `另一轮归档正在运行……本轮退出，未写任何文件`。

如实登记；两轮的相对结论不变。）

### 3.1 关键取舍（为什么这么设计）

- **重放到独立沙箱容器，而不是源实例的 newcoupon_restore**：ROW 格式 binlog 事件把库名
  编在 Table_map 二进制里，MySQL 版 mysqlbinlog 没有改写库名的选项（那是 MariaDB 的
  `--rewrite-db`）。同名库重放只能在另一台"服务器"上做——这也正是生产 PITR 的形态：
  沙箱恢复→核对→再切流量，绝不直接在源库回放。
- **位点（--start/stop-position）而不是 --stop-datetime**：dump 的 `.meta` 记的就是位点，
  位点精确到事件边界；datetime 受事件时间戳粒度影响。多文件时 start 只作用于首文件、
  stop 只作用于末文件（mysqlbinlog 语义），中间文件整段重放——脚本按文件编号选区间。
- **--database=newcoupon 过滤**：源实例上 restore.sh 的 `newcoupon_restore` 建库/导入
  也进了 binlog，重放必须按库过滤才不会把这些事件打进沙箱（断言"表数=meta+1"顺带钉住了它）。
- **沙箱镜像 mysql:8.0-debian**：默认 `mysql:8.0`（oracle 底）不带 mysqlbinlog（/usr/bin
  只有精简客户端），首跑实测 `command not found` 且因管道无 pipefail 假成功过——现在
  脚本预检工具存在 + 远端 `bash -c "set -o pipefail; ..."`。

## 4. RPO 口径与实测（本报告的核心数字）

**分层口径**（scripts/backup/README.md 同文）：

1. **mysqld 崩溃**：`sync-binlog=1`，已提交事务的 binlog 事件已 fsync 落盘——不丢，RPO=0。
2. **容器/卷整体丢失**（单机的真实风险）：丢失窗口 = 距上一次归档的时长。按周期 P 排班：

```text
最坏窗口 = P + 单轮归档耗时
实测（两轮）：写入→已归档即时窗口 4.111s（首跑，单轮 3.648s）/ 8.627s（复跑，单轮 7.912s，
机器上有外来容器抢 IO）；此前历轮单轮 3.3~7.4s
P=5min（5C 计划排班）→ 最坏 ≈ 5min + 4~9s ≈ 5.1~5.2min
  · MVP 目标 RPO≤15min：✅（余量约 3 倍）
  · 生产单机档 RPO≤5min：⚠️ 5min+ε 不严格满足——要严格达标需 P=4min 或半同步复制
  · RPO≈0：单机做不到，需同步复制（生产差距表见 scripts/backup/README.md）
```

**为什么最坏是 P+ε 而不是 P**：写入恰好在第 k 轮归档完成后落地 → 它所在的文件保持
活跃直到第 k+1 轮 FLUSH 才关闭、随后拷贝——所以是"等下一轮 + 本轮耗时"。

**单轮成本定界（审查反驳①的核实结论）**：原诉"5min cron 单轮成本无界增长"半对半错——
错的部分：FLUSH 是 O(1) 谈不上碎片成本；对的部分：**修复前** manifest 每轮对归档目录
**全部**文件重算 sha256，成本 ∝ 归档总量（归档不清理就无界）。已改为增量携带（历史条目
沿用入库当轮的 sha，只哈希本轮新增文件），单轮成本 ∝ 新增量；跳过路径的逐文件核对
（容器 sha vs 归档 sha）只遍历**容器里现存的**已关闭文件，被 binlog 30 天自动过期
（binlog_expire_logs_seconds=2592000）封顶。归档目录自身的清理（保留策略/对象存储
生命周期）仍属裁剪项。

## 5. RTO 构成（25MB 级库，不能外推；复跑轮，外来容器抢 IO）

| 段 | 实测（复跑轮） | 首跑轮 | 说明 |
|---|---:|---:|---|
| 沙箱容器起 + 初始化 | ~20s | ~16s | 一次性容器首建 |
| 全量导入 | 61.598s | 45.323s | gzip dump / 305 表 |
| binlog 重放 | 1.210s | 0.830s | 单文件位点区间（本轮区间内事件少） |
| 断言 | ~1s | ~1s | 9 条 |
| **合计（沙箱可核对）** | **~83s** | ~63s | 不含全量备份本身（首跑 2.227s，灾备时已存在） |

对照 5B 全量恢复 RTO（复跑轮 89.041s / 首跑 48.173s，同实例新库）：PITR 多出的只是
沙箱起 + 重放，代价可忽略；瓶颈仍在全量导入（大库时按导入速率另测，5B 已登记同样的边界）。
