## 1. 结论（先看这一节）

| 指标 | 目标（5C 口径） | 实测 | 判定 |
|---|---:|---|---|
| 全量恢复基线（复用 5B） | 20 条断言 | **RESTORE PASS assertions=20**（restore 44.845s + verify 3.328s） | ✅ |
| PITR：T 前数据在 | 3 行 marker + 1 张真实模板 | marker 3/3、`PITR-INC-20261110224229` 在 | ✅ |
| PITR：T 后数据不在 | 毒模板 + 2 行 marker 必须缺席 | `AFTER_T` 0 行、`PITR-ACC-20261110224229` 0 行 | ✅ |
| 重放不破坏 schema | flyway 历史行数 == dump 时刻 | 44 == 44；表数 = meta+1（只多 pitr_marker） | ✅ |
| binlog 归档（脚本断言外另验证） | 幂等可重跑 | 首轮归档 2 文件；重跑"归档 1 / 跳过 2"（sha256 核对） | ✅ |
| RPO：写入→已归档即时窗口 | — | **4.111 s**（含归档单轮 3.648s） | 实测口径见 §4 |
| RPO：排班最坏窗口 | MVP ≤15min | **P(5min) + 单轮 ~4-8s ≈ 5.1min** | ✅（≤5min 的生产档不严格满足，见 §4） |
| 容器重建不丢数据 | compose 加 binlog 参数=重建 | force-recreate 前后 6 项计数完全一致 | ✅ |
| 脚本输出 | — | **PITR DRILL PASS assertions=8**（EXIT=0） | ✅ |

**一句话**：从"只有 dump 级备份"升级到"全量基线 + binlog 增量 + 任意时间点恢复"——
误操作发生在 T 之后，恢复到 T：T 前的写入一笔不少地回来、T 后的毒数据一笔不进；
binlog 归档脚本幂等可排班，RPO 从"最坏丢一个 dump 排班周期（15min）"收紧到
"归档周期 + 秒级"。

## 2. compose 变更与容器重建实测

`docker-compose.yml` mysql 服务新增（其余不变）：

```yaml
- --log-bin=mysql-bin     # 显式开 binlog，文件基名 mysql-bin.NNNNNN（8.0 默认基名是 binlog.*）
- --binlog-format=ROW     # 行级：重放的是行变更，与生产 PITR 同语义
- --server-id=1           # binlog 必需；GTID 未开（与生产差距见 scripts/backup/README.md）
- --sync-binlog=1         # 每提交 fsync——mysqld 崩溃不丢已提交事件（RPO 口径的一半）
```

**command 变更 = 容器重建，不是原地升级**。实测验证数据卷 `mysql-data` 无损：

```text
docker compose up -d --force-recreate mysql 前后各查一次：
tables=305 templates=57 flyway=44 audit=80 stock_used_sum=37213 user_coupon_rows(分片0+63)=1161
→ 六项完全一致（RECREATE_DATA_INTACT）
SHOW VARIABLES: log_bin=ON  binlog_format=ROW  server_id=1  sync_binlog=1
SHOW MASTER STATUS: mysql-bin.000001  157        （新基名序列从 000001 起）
注：旧基名的 binlog.000001..25 仍在卷里，不进新序列（README 已写明）
```

## 3. 演练时间线与实跑输出（run 5，全绿）

```text
▶ 1. 全量备份      dump 4,432,704 bytes / 2.227s；重放起点（.meta sourceDataLine）
                   = mysql-bin.000007:1377
▶ 2. 全量恢复      RESTORE PASS assertions=20 restoreSeconds=44.845 rtoSeconds=48.173
▶ 3. T 前增量      模板 PITR-INC-20261110224229 + pitr_marker 3 行；最后一笔写入 22:42:29.8
▶ 4. 记录 T        T = mysql-bin.000007:25335329（22:42:29.9）——重放到此为止
▶ 5. T 后事故数据  毒模板 PITR-ACC-20261110224229 + marker 2 行
▶ 6. 归档          本轮归档 1 / 跳过（已归档）6；单轮 3648ms；写入→已归档 = 4.111s
▶ 7. 沙箱          newcoupon-mysql-pitr（mysql:8.0-debian，--disable-log-bin，不发布端口）
▶ 8. 导入全量      45.323s；导入后表数 == meta.tableCount（305）
▶ 9. 重放          mysqlbinlog --database=newcoupon --start-position=1377 \
                     --stop-position=25335329 mysql-bin.000007   → 0.830s
▶ 10. 断言（8/8）
  ✓ 沙箱表数 == meta.tableCount + 1（重放只多了 pitr_marker）（306）
  ✓ T 前 marker 行全部恢复（3 行）
  ✓ T 后 marker 行没有被恢复（0 行）
  ✓ T 前写入的真实模板在（PITR-INC-20261110224229）
  ✓ T 后的事故毒模板不在（PITR-ACC-20261110224229）
  ✓ 沙箱模板数 == meta.couponTemplates + 1（58）
  ✓ flyway 历史行数未被重放破坏（== meta.flywayRows）（44）
PITR DRILL PASS assertions=8      （EXIT=0；沙箱与源库演练痕迹收尾已清）
```

### 3.1 关键取舍（为什么这么设计）

- **重放到独立沙箱容器，而不是源实例的 newcoupon_restore**：ROW 格式 binlog 事件把库名
  编在 Table_map 二进制里，MySQL 版 mysqlbinlog 没有改写库名的选项（那是 MariaDB 的
  `--rewrite-db`）。同名库重放只能在另一台"服务器"上做——这也正是生产 PITR 的形态：
  沙箱恢复→核对→再切流量，绝不直接在源库回放。
- **位点（--start/stop-position）而不是 --stop-datetime**：dump 的 `.meta` 记的就是位点，
  位点精确到事件边界；datetime 受事件时间戳粒度影响。多文件时 start 只作用于首文件、
  stop 只作用于末文件（mysqlbinlog 语义），中间文件整段重放——脚本按文件编号选区间。
- **--database=newcoupon 过滤**：源实例上 restore.sh 的 `newcoupon_restore` 建库/导入
  也进了 binlog，重放必须按库过滤才不会把这些事件打进沙箱（断言"表数=meta+1"顺带钉住了它）。
- **沙箱镜像 mysql:8.0-debian**：默认 `mysql:8.0`（oracle 底）不带 mysqlbinlog（/usr/bin
  只有精简客户端），首跑实测 `command not found` 且因管道无 pipefail 假成功过——现在
  脚本预检工具存在 + 远端 `bash -c "set -o pipefail; ..."`。

## 4. RPO 口径与实测（本报告的核心数字）

**分层口径**（scripts/backup/README.md 同文）：

1. **mysqld 崩溃**：`sync-binlog=1`，已提交事务的 binlog 事件已 fsync 落盘——不丢，RPO=0。
2. **容器/卷整体丢失**（单机的真实风险）：丢失窗口 = 距上一次归档的时长。按周期 P 排班：

```text
最坏窗口 = P + 单轮归档耗时
实测：单轮归档 3.3~7.4s（三跑）；写入→已归档即时窗口 4.111s（含 3.648s 单轮）
P=5min（5C 计划排班）→ 最坏 ≈ 5min + 数秒 ≈ 5.1min
  · MVP 目标 RPO≤15min：✅（余量约 3 倍）
  · 生产单机档 RPO≤5min：⚠️ 5min+ε 不严格满足——要严格达标需 P=4min 或半同步复制
  · RPO≈0：单机做不到，需同步复制（生产差距表见 scripts/backup/README.md）
```

**为什么最坏是 P+ε 而不是 P**：写入恰好在第 k 轮归档完成后落地 → 它所在的文件保持
活跃直到第 k+1 轮 FLUSH 才关闭、随后拷贝——所以是"等下一轮 + 本轮耗时"。

## 5. RTO 构成（25MB 级库，不能外推）

| 段 | 实测 | 说明 |
|---|---:|---|
| 沙箱容器起 + 初始化 | ~16s | 一次性容器首建 |
| 全量导入 | 45.323s | 4.4MB gzip / 305 表 |
| binlog 重放 | 0.830s | 单文件 ~25MB 位点区间（本轮区间内事件少） |
| 断言 | ~1s | 8 条 |
| **合计（沙箱可核对）** | **~63s** | 不含全量备份本身（2.227s，灾备时已存在） |

对照 5B 全量恢复 RTO 48.173s（同实例新库）：PITR 多出的只是沙箱起 + 重放 ≈ 17s，
代价可忽略；瓶颈仍在全量导入（大库时按导入速率另测，5B 已登记同样的边界）。

## 6. 边界与裁剪登记

| 项 | 状态 | 说明 |
|---|---|---|
| GTID | 未开 | server-id 最简配置；生产开 GTID 后重放/重搭从库按 gtid_set 定位（差距表见 scripts/backup/README.md） |
| 复制 | 无 | RPO≈0 需同步复制，单机不做 |
| 归档排班 | 未常驻 | 脚本幂等可 cron；本轮为手动触发（演练形态）——排班属部署侧 |
| xxl_job 库 | 仍不含 | 5B 已登记；dump 仍只含 newcoupon |
| 增量数据形态 | 模板行 + marker 表 | 建模板走真实 INSERT；"领券几笔"用 marker 行替代——直接写 user_coupon 分表需分布式 ID/券码生成，且 PITR 机制对任意 DDL/DML 一致，用 marker 不弱化结论 |
| 多文件跨段重放 | 代码支持、本轮未走到 | 本轮 dump 位点与 T 同文件；脚本按编号选区间，跨文件路径未实测（登记） |
| 大库 | 未验证 | 25MB 级；线性外推无效（5B 同款边界） |
