## 3. 故障期行为与代码依据（不是臆造）

| 入口 | 实际返回 | 代码路径 |
|---|---|---|
| 同步领券 `/api/coupons/receive` | **5000** | `ReceiveAppService.withBreakers("mysql", SYSTEM_ERROR, ...)`；依赖失败与熔断打开都收敛到 `ErrorCode.SYSTEM_ERROR=5000` |
| 异步领券 `/api/coupons/receive-async`（gate+ul 已预热） | **5000** | Redis 预扣成功 → `taskService.acceptWithResult` 插入失败 → `ReceiveAsyncAppService` 捕获后 `issueGate.compensate(cmd)` → 抛 `SYSTEM_ERROR` |
| 异步领券（gate 未预热，首请求） | **5001** | `acquireWithRepair` 恢复 `GATE_MISSING` 要读 DB；DB 不可用走 `DataAccessException` 分支 → `ErrorCode.DEGRADED`（源码第 180 行）。**首轮实测**：gate 未预热时返回 5001，预热后才是 5000——两条线都是 fail-closed，报告只把后者当作"补偿路径"证据 |
| 核销 `/api/coupons/confirm` | **5000** | 占用单/券状态读取在 MySQL；异常由全局处理器收敛为 5000 |
| mysql 熔断器 | `CLOSED → OPEN` | 依赖级 `DependencyCircuitBreakers`（`TransientDataAccessResourceException` 在失败白名单里）；min-calls=5，本轮 failed=8 |

### 3.1 为什么熔断状态从 Prometheus 读

`/api/switches/breakers` 虽然只读内存，但它前面的管理面过滤器会用旧令牌查 RBAC 权限表（`LegacyAdminTokenAuthenticationFilter.authenticateTokenHolder` → `SELECT` 权限码）。MySQL 一挂，这个端点也不可用。`/actuator/prometheus` 走独立安全链（Basic），不碰业务库，因此作为故障期观测口。这是"观测面不能依赖被观测依赖"的一个具体案例。

### 3.2 一个被删除的断言：fast-fail 时延

最初版本断言"熔断打开后下一发应 <1.5s 返回"。第 9 轮实测：`state=open=1`，但下一发耗时 **3028ms**——因为模板/租户缓存已过期，请求在**进入熔断段之前**就因 `CachedOpenAppReader` 回源 DB 失败而返回 5000。这条路径不经过 breaker，所以"打开后第一发一定快速失败"不成立。现在钉住的证据是：`state=open=1` + `kind="failed"` 调用数 ≥5 + 日志状态转移行；三者都来自不同的观测面。

## 4. 脚本与护栏

- 三道护栏：`CONFIRM=yes`、`BASE` 必须是本机（远程需 `ALLOW_REMOTE=1`）、退出时（含 Ctrl-C）一定 `docker start` MySQL 并停掉脚本自己起的应用；残留状态文件 `/tmp/newcoupon-mysql-drill.state` 会在下次启动时提示。
- 幂等重跑：requestId 拼 `RUN_ID`（实测踩过：不拼时第二次演练的预热 requestId 命中上一次任务 → 1001）；模板每次新建（`validType=2, validDays=7`，不再写死 2026-12-31）。
- 时间盒：等待 MySQL 可用 90s、等熔断恢复 120s；超时即 fail，不无限等。
- 应用资源：`-Xmx384m`；worker 初始延迟 10 分钟，避免后台任务在故障期搅局。
- **2026-11-06 审查修正**：
  1. 删除"复用已有 8080 服务"分支——复用时不重写 `APP_LOG`，历史 `CLOSED → OPEN` 会让日志断言假通过；现在演练必须由脚本自启。
  2. `PORT/BASE` 在 `source lib.sh` **之前**决定（lib.sh 的 BASE 默认 8080 会覆盖后面的 `${BASE:-...}`）。
  3. cleanup 在 `docker start` 失败时保留状态文件并以非 0 退出，不再打印"清理完成"。
  4. 头注释删除"notPermitted 会增长"的错误承诺；库存核对文案 9→10（实际按 10 个未重试 requestId 查）。

## 5. 本轮发现（重要，需下个会话登记）

### 5.1 JDBC URL 缺 `allowPublicKeyRetrieval=true`：MySQL 重启后应用无法自愈

**现象**：用 dev 默认配置启动应用，`docker stop` 再 `docker start` MySQL 后，应用健康检查持续 `DOWN`，所有领券返回 5000。Hikari 日志：

```text
java.sql.SQLTransientConnectionException: HikariPool-2 - Connection is not available,
    request timed out after 3000ms (total=0, active=0, idle=0, waiting=0)
Caused by: com.mysql.cj.exceptions.UnableToConnectException: Public Key Retrieval is not allowed
```

`total=0` 说明重启后一条新连接都没建起来；不是"等一会就好"的瞬时错误（实测 2 分钟后仍 DOWN）。

**根因**：MySQL 8 的 `caching_sha2_password` 在服务端重启后丢掉了认证缓存，驱动回退到"请求服务端 RSA 公钥"的全量认证；`application-dev.yml` 的 `spring.datasource.url` 与 `application.yml` 的 `coupon.sharding.url` 都没有 `allowPublicKeyRetrieval=true`，驱动拒绝该操作。

**验证**：同一应用加上两条启动参数覆盖 URL（`...&allowPublicKeyRetrieval=true`）后重复同样的 stop/start，恢复请求第 2 次即 `code=0`，健康检查 `UP`（探针应用 8083，`WARM_CODE=0` → `heal-2 code=0`）。

**本轮处理**：遵守"本刀只改 L78 代码"的边界，**没有改仓库配置**；演练脚本用启动参数显式覆盖（脚本注释里写明了原因）。建议下个会话把 dev 配置补上（生产走 SSL 或显式参数，需按部署形态决定），并登记为一条债务。

### 5.2 其他观测

- Redis 熔断器（`redis`）在 C1 之后没有接线点（全仓库除预热/指标外无 `breakers.redis()` 使用），旧版 drill.sh 的"redis 熔断 OPEN"断言已不成立；本轮按实际行为改为验证异步 gate 的 5001 与 fail-open 指标，见 §6。
- MySQL 故障期间管理面 `/api/switches/breakers` 不可用（RBAC 查库），故障期观测应走 `/actuator/prometheus`。

## 6. Redis 故障演练（复用并更新既有 drill.sh）

### 6.1 为什么更新脚本

C1 之后 Redis 不再是库存权威：同步领券的库存/落库都在 MySQL，Redis 只做售罄提示（try/catch 降级）。旧版脚本在暂停 Redis 后打同步领券、期待 5000→5001 与 redis 熔断 OPEN，已与代码不符（而且 redis 熔断器没有接线点）。本轮把第 4/5 步改成验证真实强依赖：

1. `/api/coupons/receive-async` 在 Redis 暂停时按 `reject` 策略返回 **5001**（fail-closed），成功数必须为 0；
2. 风控闸 fail-open 指标 `coupon_ratelimit_failopen_total{dimension="risk_ip"}` 必须增长；
3. Redis-down 策略计数 `issue_gate_result_total{result="redis_down_reject"}` 必须增长；
4. **故障期同步领券 2/2 成功**（C1 的库存/落库不依赖 Redis，这是审查补上的真验证；旧版只打异步）；
5. 恢复后 `PING=PONG`，异步受理（新用户）与同步领券都恢复成功。

### 6.3 实现细节与脚本修正

- `docker pause`（不是 stop）：TCP 仍可连、命令不再响应——这正是"熔断/超时该保护"的形态。
- 失败时延：每个异步请求在 Redis 命令超时（1s 级）后返回 5001，3 发串行约数秒。
- **脚本修正（踩坑记录）**：第一版在恢复前抓 Prometheus，断言 `printf '%s' "$text" | grep -q ...`。响应约 99KB > 管道缓冲，`grep -q` 提前退出 → `printf` 收到 SIGPIPE → `set -o pipefail` 把整条管道判成失败；指标明明在文本里，断言却报"没有出现"。修正为**抓取落盘 + `grep` 文件**；同时抓取前打印 HTTP 状态，401（make run 默认随机 actuator 密码）会给出明确指引而不是被误报成"指标缺失"。失败运行与 PASS 运行分开记录：`/tmp/redis-drill2.log`（恢复前抓取，失败）、`/tmp/redis-drill3.log`（SIGPIPE 假失败）、`/tmp/redis-drill4.log`（修 pipefail 后第一次 PASS，13 断言）；审查补同步故障期断言后，最终证据是 `/tmp/redis-drill5.log`（14 断言）。
