## 1. 结论（先看这一节）

| 指标 | 目标值（MVP 单机） | 实测 | 判定 |
|---|---:|---:|---|
| 备份 RPO | ≤ 15 min | 单次 dump **3.935 s**；按 15 分钟排班即可满足 | ✅ |

## 2. 备份：做了什么、实测多少

### 2.1 命令

```bash
CONFIRM=yes bash scripts/backup/backup.sh
```

脚本内部实际执行（容器内 mysqldump）：

```bash
docker exec -e MYSQL_PWD=root123456 newcoupon-mysql \
  mysqldump -uroot \
    --single-transaction \
    --source-data=2 \
    --set-gtid-purged=OFF \
    --databases newcoupon | gzip -9 > target/backup/newcoupon-<timestamp>.sql.gz
```

参数理由：

- `--single-transaction`：InnoDB 一致性快照，不锁表，备份期间业务可读写；
- `--source-data=2`：把备份时刻的 binlog 位点写成注释行，给未来"binlog 归档 + PITR"留接口；
- `--set-gtid-purged=OFF`：当前单机没有 GTID 复制，关掉避免恢复到同实例新库时受 GTID 约束；
- `--databases newcoupon`：dump 内自带 `CREATE DATABASE` / `USE`，恢复整库重建。

## 3. 恢复演练：恢复到 newcoupon_restore 并逐项断言

### 3.1 命令

```bash
CONFIRM=yes bash scripts/backup/restore.sh   # 默认取 target/backup/latest.sql.gz
```

恢复方式：`gzip -dc dump | sed 's/`newcoupon`/`newcoupon_restore`/g' | mysql`，只替换反引号包裹的库名标识符；源库 `newcoupon` 全程不动。

### 3.2 恢复后验证（脚本内断言，22 条全绿）

```text
✓ 表数一致（305）
✓ flyway_schema_history 摘要一致（等价 flyway validate）（581462bc5c2537d76a8ce86b2a596370）
✓ 行数一致：coupon_template（13）
✓ 行数一致：coupon_stock_shard（208）
✓ 行数一致：coupon_issue_task（4000）
✓ 行数一致：coupon_daily_counter（0）
✓ 行数一致：coupon_user_daily_counter（0）
✓ 行数一致：audit_log（32）
✓ 行数一致：coupon_share_detail（12）
✓ 行数一致：coupon_outbox（4057）
✓ 行数一致：coupon_usage_0（0）
✓ 行数一致：risk_decision_log（68）
✓ 行数一致：open_app（13）
✓ 分表行数合计一致：user_coupon_*（4057）
✓ 分表行数合计一致：coupon_usage_*（6）
✓ 分表行数合计一致：coupon_expire_task_*（4057）
✓ 分表行数合计一致：coupon_release_task_*（6）
✓ 库存守恒：所有模板 Σused == 券行数（0）
✓ 全局 Σ coupon_stock_shard.used 一致（4057）
✓ 目标库默认字符集（utf8mb4）
✓ 含多字节字符的模板名数量一致（13）
✓ 模板名/编码内容摘要一致（中文/emoji 原样恢复）（eb4fdb202845065b001de249c63ad1d7）
RESTORE PASS assertions=22 restoreSeconds=48.341 verifySeconds=8.799 rtoSeconds=57.140
```

验证口径：

1. **flyway validate 的等价物**：逐行比较 `flyway_schema_history` 的 `installed_rank/version/description/type/script/checksum/success` 摘要；`installed_on` 会随导入时间变化，故不纳入。
2. **分表行数**：不写死表名，用 `information_schema` 实测 `user_coupon_*` / `coupon_usage_*` / `coupon_expire_task_*` / `coupon_release_task_*` 四组，确保分表布局变化时脚本仍成立。
3. **库存守恒**：与 `C1StockReconcileService` 等式②同口径——逐模板 `Σ coupon_stock_shard.used == COUNT(user_coupon)`，漂移模板数必须为 0。
4. **中文/emoji**：`HEX(name)` 命中高位字节的数量一致，且整行内容 MD5 一致；当前 13 个模板名全为中文，`emoji` 在现有数据中没有样本（字段已按 utf8mb4 建表，本次用中文验证了多字节往返）。

### 3.3 RPO / RTO 口径

- **RPO（恢复点目标）**：本次演练的备份是单事务一致性快照，快照时刻之后的数据不在 dump 内。生产 RPO 取决于备份排班——按 15 分钟一次 dump，最坏丢失 15 分钟。单次 dump 3.9 秒，排班可行。**没有 binlog 归档，就做不到"恢复到任意秒/PITR"，也做不到生产 5 分钟级 RPO 的严格保证**（见 §5）。
- **RTO（恢复时间目标）**：`restoreSeconds` 从 DROP/CREATE 目标库开始到导入完成；`verifySeconds` 是 22 条断言跑完；两者相加 57.14 秒。数据量 24.78 MB，属于小库；大库要按导入速率另测。
- **演练中的 RPO 实测值**：0（备份完成后立即恢复，没有新写入丢失）；这不是生产 RPO，只是"dump 本身自洽"的证明。

## 4. 复现步骤

```bash
docker compose up -d mysql
CONFIRM=yes bash scripts/backup/backup.sh
CONFIRM=yes bash scripts/backup/restore.sh
```

幂等性：backup 每次产生新时间戳文件并更新 `latest.sql.gz` 软链；restore 每次 `DROP DATABASE IF EXISTS newcoupon_restore` 后重建，可重复执行。首次恢复曾因脚本内 `SUM(c)` 缺列别名失败（数据本身没问题），修正脚本后重跑即 PASS——这也验证了"恢复失败时脚本会以非 0 退出，不会把半截结果当成功"。

## 5. 裁剪登记与边界

| 项 | 状态 | 说明 |
|---|---|---|
| binlog 归档 / PITR | **裁剪** | MySQL 8 默认开了 binlog（位点见 §2.2），但没有归档任务、没有 `mysqlbinlog` 回放演练；当前 MVP 只承诺 dump 级备份。升级路径：定时 `mysqlbinlog --read-from-remote-server` 或备份工具（XtraBackup/云 RDS）归档 binlog，恢复时先全量后回放。 |
| 生产 RPO ≤5 min | **当前做不到** | dump 排班 + 无 binlog 归档，最坏丢一个排班周期；要严格 5 分钟需 binlog 连续归档（或同步复制，单机更做不到）。 |
| Dump 只含 `newcoupon` | 有意 | XXL-JOB 的 `xxl_job` 库承载调度定义，本轮未纳入 dump；生产备份应把调度库与业务库同一次快照（计划 5C 原文要求），登记为升级项。 |
| 恢复到同实例新库 | 有意 | 演练不覆盖源库；真实灾难恢复到新实例/新机器需要额外验证网络、账号、连接串切换，未做。 |
| 大库 RTO | 未验证 | 24.78 MB / 57 秒；按线性外推只能作参考，生产需按实际数据量重测并写进 runbook。 |
| 备份加密/异地 | 未做 | 本地文件；生产备份落对象存储时需服务端加密 + 生命周期 + 异地副本。 |
