## 2. 备份：做了什么、实测多少

### 2.1 命令

```bash
CONFIRM=yes bash scripts/backup/backup.sh
```

脚本内部实际执行（容器内 mysqldump）：

```bash
docker exec -e MYSQL_PWD=root123456 newcoupon-mysql \
  mysqldump -uroot \
    --single-transaction \
    --source-data=2 \
    --set-gtid-purged=OFF \
    --databases newcoupon | gzip -9 > target/backup/newcoupon-<timestamp>.sql.gz
```

参数理由：

- `--single-transaction`：InnoDB 一致性快照，不锁表，备份期间业务可读写；
- `--source-data=2`：把备份时刻的 binlog 位点写成注释行，给未来"binlog 归档 + PITR"留接口；
- `--set-gtid-purged=OFF`：当前单机没有 GTID 复制，关掉避免恢复到同实例新库时受 GTID 约束；
- `--databases newcoupon`：dump 内自带 `CREATE DATABASE` / `USE`，恢复整库重建。

## 3. 恢复演练：恢复到 newcoupon_restore 并逐项断言

### 3.1 命令

```bash
CONFIRM=yes bash scripts/backup/restore.sh   # 默认取 target/backup/latest.sql.gz 及其 .meta
```

恢复方式：`gzip -dc dump | sed 's/`newcoupon`/`newcoupon_restore`/g' | mysql --one-database newcoupon_restore`。

**两道防"误伤源库"的保险（审查修正）**：

1. 导入前从 dump 首部解析内嵌库名（`CREATE DATABASE` / `USE`），必须等于 `DB_NAME`，否则中止——如果 `DB_NAME` 配错或 dump 内嵌库名不是预期，sed 替换会空操作，dump 自带的 `CREATE DATABASE`/`USE`/`DROP TABLE` 会直接命中真实源库；
2. mysql 客户端加 `--one-database $TARGET_DB`，即使替换失效，也只执行目标库的语句。
3. `backup.sh` 与 `restore.sh` 统一使用 `DB_NAME` 变量名；恢复前还会核对 `.meta.database == DB_NAME`。

### 3.2 恢复后验证（脚本内断言，20 条全绿）

```text
✓ 演练目标是本机新库：newcoupon_restore（源库 newcoupon 不动）
✓ 备份文件：target/backup/latest.sql.gz（1.7M），基准：.../newcoupon-20261106-163713.sql.gz.meta
✓ dump 内嵌库名 = newcoupon，与 DB_NAME 一致
✓ 目标库已重建：newcoupon_restore
✓ 导入完成（44.784 秒）
✓ 表数 == meta.tableCount（305）
✓ flyway_schema_history 行数 == meta.flywayRows（43）
✓ flyway 历史摘要 == meta（版本/脚本/checksum/成功标记，等价 validate）（67f37f...8d63）
✓ coupon_template 行数 == meta.couponTemplates（44）
✓ audit_log 行数 == meta.auditLogRows（64）
✓ coupon_issue_task 行数 == meta.issueTaskRows（13474）
✓ Σ coupon_stock_shard.used == meta.stockUsedSum（14876）

✓ 不存在'有券行但无库存行'的模板（0）

RESTORE PASS assertions=20 restoreSeconds=44.784 verifySeconds=5.613 rtoSeconds=50.397
```

验证口径：

1. **基准是 dump 时刻**：表数/关键表行数/4 组 64 分表合计/flyway 摘要/模板名摘要/多字节字符数全部与 `.meta` 对齐；不再与"当前源库"比较。
2. **枚举非空**：每组 64 分表先断言 `information_schema` 枚举到的表数 >0，避免枚举失败时 `0 == 0` 假通过。
3. **库存守恒**：与 `C1StockReconcileService` 等式②同口径——逐模板 `Σ coupon_stock_shard.used == COUNT(user_coupon)`；并反向检查"有券行但没有库存行"的模板数必须为 0。
4. **字符集/多字节**：目标库 utf8mb4；`HEX(name)` 高位字节数量与整行摘要都与 meta 一致。emoji 在现有数据中没有样本，未覆盖（如实登记）。

### 3.3 RPO / RTO 口径

- **RPO（恢复点目标）**：本次演练的备份是单事务一致性快照，快照时刻之后的数据不在 dump 内。生产 RPO 取决于备份排班——按 15 分钟一次 dump，最坏丢失 15 分钟。单次 dump 1.9 秒，排班可行。**没有 binlog 归档，就做不到"恢复到任意秒/PITR"，也做不到生产 5 分钟级 RPO 的严格保证**（见 §5）。
- **RTO（恢复时间目标）**：`restoreSeconds` 从 DROP/CREATE 目标库开始到导入完成；`verifySeconds` 是 20 条断言跑完；两者相加 **50.397 秒**。数据量 24.78 MB，属于小库；大库要按导入速率另测。
- **演练中的 RPO 实测值**：0（备份完成后立即恢复，没有新写入丢失）；这不是生产 RPO，只是"dump 本身自洽"的证明。

## 4. 复现步骤

```bash
docker compose up -d mysql
CONFIRM=yes bash scripts/backup/backup.sh
CONFIRM=yes bash scripts/backup/restore.sh
```

幂等性：backup 每次产生新时间戳文件并更新 `latest.sql.gz` 软链（meta 跟随真实文件名）；restore 每次 `DROP DATABASE IF EXISTS newcoupon_restore` 后重建，可重复执行。首次恢复曾因脚本内 `SUM(c)` 缺列别名失败（数据本身没问题），修正后重跑 PASS；审查后又发现 `latest.sql.gz.meta` 软链路径问题（meta 实际跟真实文件名），已修。

## 5. 裁剪登记与边界

| 项 | 状态 | 说明 |
|---|---|---|
| binlog 归档 / PITR | **裁剪** | MySQL 8 默认开了 binlog（位点见 §2.2），但没有归档任务、没有 `mysqlbinlog` 回放演练；当前 MVP 只承诺 dump 级备份。升级路径：定时 `mysqlbinlog --read-from-remote-server` 或备份工具（XtraBackup/云 RDS）归档 binlog，恢复时先全量后回放。 |
| 生产 RPO ≤5 min | **当前做不到** | dump 排班 + 无 binlog 归档，最坏丢一个排班周期；要严格 5 分钟需 binlog 连续归档（或同步复制，单机更做不到）。 |
| Dump 只含 `newcoupon` | 有意 | 5C 原计划要求同一次 dump 含 `xxl_job`；本轮**未包含**调度库。生产备份应把调度库与业务库同一次快照，登记为升级项。 |
| 恢复到同实例新库 | 有意 | 演练不覆盖源库；真实灾难恢复到新实例/新机器需要额外验证网络、账号、连接串切换，未做。 |
| 大库 RTO | 未验证 | 24.78 MB / 50 秒；按线性外推只能作参考，生产需按实际数据量重测并写进 runbook。 |
| 备份加密/异地 | 未做 | 本地文件；生产备份落对象存储时需服务端加密 + 生命周期 + 异地副本。 |
| emoji | 未覆盖 | 当前 44 个模板名全为中文；emoji 无样本，报告只承诺中文/多字节字符。 |
