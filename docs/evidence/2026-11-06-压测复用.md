## 1. 结论（先看这一节）

| 项 | 2026-10-23 基线 | 2026-11-06 本轮 | 判定 |
|---|---:|---:|---|
| 1k 异步受理（raw-bulk 模板） | 711–1382 req/s | **478.4 req/s**（1000×202/0，wall 2.090s） | 同数量级（本轮对账任务同时在跑） |
| 1k 异步受理（日限模板，3 轮） | — | **717.5 / 610.9 / 422.6 req/s**（3×1000 全 202/0） | 同数量级 |
| worker 清空 1k（raw-bulk） | 约 1.29k–1.6k task/s | **1001 条 / 1.202s ≈ 833 task/s** | 同数量级，略低 |
| worker 清空 3k（日限模板） | 单任务路径约 111 task/s（8 线程） | **3001 条 / 56.003s ≈ 53.6 task/s** | 路径不同（本轮 parallelism=2） |
| L78 `dly_reconcile_fix` | 未观测 | **2 行：delta=+1（实锤）与 delta=+52（冷启动大窗）** | 实锤 |
| 库存守恒 | — | 模板 40：Σused=1001/券 1001；模板 41：Σused=3001/券 3001 | ✅ |

**一句话**：1k 受理与 worker 清空都还在同一数量级；同一个压测窗口里，`dly_reconcile_fix` 出现了 `redis=3000 target=3001` 的 ±1 修复——L78 从文档推断变成实锤。修复为"dly 容差至少 1"，单测先红后绿。

## 2. 压测方法与环境

### 2.1 启动参数（照 10-23 报告）

```bash
java -Xms512m -Xmx1g -cp target/classes:<deps> com.newcoupon.NewCouponApplication \
  --server.port=8080 \
  --coupon.issue.worker.batch-size=2000 \
  --coupon.issue.worker.batch-tx-size=2000 \
  --coupon.issue.worker.parallelism=2 \
  --coupon.issue.worker.group-parallelism=16 \
  --coupon.issue.worker.raw-bulk-pool-size=4 \
  --coupon.sharding.pool.max-size=40 \
  --coupon.risk.ip-rate.enabled=false \
  --coupon.issue.worker.initial-delay-ms=15000 \
  --coupon.issue.gate-reconcile.fixed-delay-ms=500 \
  --coupon.issue.gate-reconcile.initial-delay-ms=5000
```

差异（相对 10-23）：本轮为了观测 L78，**对账任务每 500ms 跑一轮**（默认 1 小时），且在同一台机器上；这会对受理吞吐与 worker 清空产生可观测的干扰，下面的数字是"带对账"的口径。

### 2.2 两个模板

| 模板 | totalCount | dailyLimit | 用途 |
|---|---:|---:|---|
| B（id=40） | 6000 | 0 | raw-bulk 快路径 + worker 清空速率对照 |
| A（id=41） | 6000 | 6000 | 让每个受理 INCR dly，制造 L78 观测窗口 |

两模板都先跑一次"预热受理"（async 一次、等 worker 落完），把 Redis gate 建出来；否则 1000 并发首领会一起命中 `GATE_MISSING`，只有 1 个赢家能重建，其余按 5001 拒绝——那是冷启动保护，不是受理能力（第一版压测踩到：1k 里 516 个 5001）。

### 2.3 请求形态

`async_issue_load.py`：1000 个唯一用户/requestId，客户端预建 1000 条 TCP 连接，栅栏后同时发；延迟从栅栏释放算到读完响应。不是"线程数 ÷ 总耗时"的伪并发。

## 3. 原始结果

### 3.1 模板 B（raw-bulk，1k）

```json
{"total":1000,"concurrency":1000,"completed":1000,"wallSeconds":2.09,
 "throughputRps":478.4,"http":{"202":1000},"bizCode":{"0":1000},
 "latencyMs":{"min":57.4,"p50":1118.6,"p95":1740.2,"p99":1777.1,"max":1803.9,"mean":1088.8}}
```

worker 清空：`DRAIN_B_MS=1202`（模板 40 共 1001 条任务，含预热 1 条，全部 SUCCESS）≈ **833 task/s**。

### 3.2 模板 A（dailyLimit=6000，3×1k）

```json
{"total":1000,"concurrency":1000,"throughputRps":717.5,"http":{"202":1000},"bizCode":{"0":1000},
 "latencyMs":{"p50":812.7,"p95":1401.9,"p99":1438.0,"max":1518.9}}

{"total":1000,"concurrency":1000,"throughputRps":610.9,"http":{"202":1000},"bizCode":{"0":1000},
 "latencyMs":{"p50":1131.7,"p95":1626.9,"p99":1681.5,"max":1776.5}}

{"total":1000,"concurrency":1000,"throughputRps":422.6,"http":{"202":1000},"bizCode":{"0":1000},
 "latencyMs":{"p50":1492.9,"p95":2320.6,"p99":2356.5,"max":2372.9}}
```

worker 清空：`DRAIN_A_MS=56003`（模板 41 共 3001 条任务全部 SUCCESS）≈ **53.6 task/s**。  
**为什么慢**：模板 A 配了 `dailyLimit`，worker 的批量快路径要求"无模板日限/每人日限"，因此 3000 条走**单任务事务路径**；再加本轮 `parallelism=2`，与 10-23 的 raw-bulk 数字不可直接比。这个数字只用来证明"日限模板的清空速率"，不作为容量结论。

### 3.3 库存与任务核对

```text
template 40: status=2(SUCCESS) 1001 条；Σused=1001；券行=1001
template 41: status=2(SUCCESS) 3001 条；Σused=3001；券行=3001
```

（模板 40 的 1001 = 预热 1 + 压测 1000；模板 41 的 3001 = 预热 1 + 3×1000。）

## 4. L78 观测：dly 的 ±1 无意义修复（实锤）

### 4.1 观测方法

应用启动时把 `coupon.issue.gate-reconcile.fixed-delay-ms` 调到 500ms，在压测受理与 worker 清空期间持续跑 `GateCounterReconcileJob`；压测结束后查 `stock_drift_log`：

```sql
SELECT id, template_id, delta, detail, create_time
FROM stock_drift_log
WHERE action='dly_reconcile_fix' AND create_time >= '2026-11-06 15:06:52'
ORDER BY id;
```

### 4.2 观测到的行

```text
9   41   52   key=c:issue:dly:{41}:2026-11-06 redis=2948 target=3000   2026-11-06 15:07:21
10  41    1   key=c:issue:dly:{41}:2026-11-06 redis=3000 target=3001   2026-11-06 15:07:50
```

- **id=10，delta=+1**：Redis dly=3000、DB 目标=3001，旧代码（threshold=0）直接修——这就是 L78 描述的"高 QPS 下每轮做 ±1 无意义修复"。下一轮若目标又追上/Redis 被别的窗口改动，就可能反向再修一次（更早的压测里已观测到 `1001 -> 1000`、`1000 -> 1001` 的反向成对行）。
- **id=9，delta=+52**：冷启动并发窗口——1000 个新用户同时首次受理，Redis 已 INCR 而任务行还没全部落库/被 in-flight 查询看到。它比 ±1 大，**不在 L78 的"±1"范围内**；本轮修复（容差 1）仍会修它。是否需要按族放大容差，登记为观察项（见 §6）。

## 5. L78 修复：先红后绿

### 5.1 代码改动（仅 1 个生产文件）

`src/main/java/com/newcoupon/application/service/GateCounterReconcileJob.java`：

- `fixCounter(...)` 增加 `int tolerance` 参数；ul/uld 仍传 `threshold`（每用户键，单键并发低）。
- `reconcileTemplateDailyKey` 传 `Math.max(threshold, 1)`——与 gate 同一处理。
- 类注释更新：gate/dly 至少容 1，ul/uld 默认 0 的理由。

### 5.2 红：新测试在旧代码上失败

测试 `GateCounterReconcileJobTest.dlyToleranceAbsorbsAdmissionWindow`（照 `gateToleranceAbsorbsAdmissionWindow` 同款）：dly `cur=9 / target=10`（diff=+1）时**不**应调用 `repairTemplateDaily`；`cur=7 / target=10`（diff=+3）时才修。

```text
[ERROR] Tests run: 13, Failures: 1, Errors: 0, Skipped: 0
[ERROR] GateCounterReconcileJobTest.dlyToleranceAbsorbsAdmissionWindow -- FAILURE!
org.mockito.exceptions.verification.NeverWantedButInvoked:
redisIssueGate.repairTemplateDaily(<any long>, <any>, <any long>, <any long>);
Never wanted here: ...
But invoked here:
-> GateCounterReconcileJob.lambda$reconcileTemplateDailyKey$6(...)
   with arguments: [501, 2026-11-06, 10, 172800]
```

即：旧代码把 diff=+1 当成漂移修掉了——正是 L78 的行为。

### 5.3 绿：修复后同一测试通过

```text

```

全量回归（评审前提交 `af9e76a` 时点）：`mvn -o clean test` **868 例：0 失败 0 错误 + 2 例门控跳过，BUILD SUCCESS**（基线 867 + 新增 `dlyToleranceAbsorbsAdmissionWindow` 1 例）。2026-11-06 审查后补 2 个 dly 阈值边界用例（默认容差恰好 1、threshold=2 时沿用配置值），定向 `GateCounterReconcileJobTest` **15/15 绿**；全量由收尾人复跑（预计 870 例）。

## 6. 边界与观察项

| 项 | 说明 |
|---|---|
| 单机口径 | 客户端与服务端同机、共享 16 vCPU 与磁盘；数字是下限，不是生产 SLA。 |
| 对账任务干扰 | 本轮对账每 500ms 一轮（为观测 L78），吞吐与清空速率都比 10-23 的"无对账"口径低；只做同数量级对照。 |

| 2k/4k | 未做；本轮只要求 1k 复用。 |
| k6/阶梯/soak | 未做，属于 5D。 |
