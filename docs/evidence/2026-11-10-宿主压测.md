## 1. 结论（先看这一节）

| 轮次 | 客户端位置与路径 | 吞吐 | p50 / p99 (ms) | HTTP/业务 |
|---|---|---:|---|---|
| run 1（冷） | Windows → `127.0.0.1:8080` | 392.4 req/s | 1604 / 2496 | 1000×202 / 全 0 |
| run 2 | 同上 | **551.6 req/s** | 1079 / 1786 | 1000×202 / 全 0 |
| run 3 | 同上 | **535.7 req/s** | 1155 / 1857 | 1000×202 / 全 0 |
| 对照 A | 2026-11-06 同机（**带 500ms 对账干扰**） | 478.4 req/s | 1119 / 1777 | 同 |
| 对照 B | 2026-10-23 同机（无干扰，**旧版本代码**） | 711–1382 req/s | — | 同 |

- worker 清空：1000 条任务 **105ms 内全部 SUCCESS**（raw-bulk 快路径；对照 11-06 的 833 task/s 同数量级）；
- 库存守恒：模板 68 Σused=3001 == 64 分表券行合计 3001（三轮 3000 + 预热 1）；
- **结论一句话**：宿主分离后 1k 受理吞吐 535–552 req/s（热态），与"同机+对账干扰"的
  478.4 相比高约 12–15%，但仍低于 10-23 同机无干扰口径——内存隔离是真的，但 Windows→WSL
  的 mirrored 网络路径把往返延迟抬高了，吞吐没有免费午餐（§4 分析）。

## 2. 环境拓扑与"实际用的路径"（README 口径同文）

```
Windows 宿主（Python 3.13.7，1000 线程 + 1000 预建 TCP 连接）
    │  http://127.0.0.1:8080
    ▼ （WSL2 networkingMode=mirrored：宿主 127.0.0.1 直通 WSL 内监听端口）
WSL2（java 应用 :8080，-Xmx1g）──▶ MySQL / Redis 容器（docker）
```

- **CPU 仍共享**：WSL2 的 vCPU 是宿主逻辑核（AMD Ryzen 9 6900HX，16 逻辑核），客户端
  线程与应用/容器仍抢同一组核——这是 WSL2 的物理现实，"宿主分离"分离不了 CPU。
- **内存隔离是真的**：客户端 1000 线程（栈 512KB/线程）+ 连接缓冲全在 Windows 侧，
  不占 WSL 的 7.8G；观测栈（prometheus/grafana）按纪律提前停掉。
- **路径踩坑（重要，README 同文）**：
  1. `localhost` 在本机 Windows 解析优先 `::1`，mirrored 模式的 IPv6 回环到 WSL **不通**
     ——实测 Python 经 `localhost` 建连一次要 **8.019s**（先等 ::1 超时），1000 预建连接
     超过脚本的 240s 栅栏超时，首轮全军 `BarrierBroken`（输出存证
     `target/stability/p5c-host-run1-localhost-broken.json`，吞吐 6.2 req/s 假数据）；
  2. 显式用 **`http://127.0.0.1:8080`**（IPv4）后单连接 **0.031s**，一切正常；
  3. 直连 WSL eth0 IP（172.23.x.x）从 Windows **不可达**（mirrored 模式没有 NAT 回程，
     实测 curl 000 超时）——"查 WSL IP 方案"在此网络模式下不适用，IPv4 回环是唯一路径。

## 4. 对照分析（如实：什么变了、什么没变、口径能升级到哪）

**变量盘点**（与对照 A=478.4 比，变了三件事）：

1. 客户端挪出 WSL：客户端内存（~1G 级线程栈+缓冲）不再与应用/容器抢 7.8G——**这是
   本轮要验证的隔离**，成立；
2. 对账干扰移除（对照 A 每轮 500ms 对账，本轮默认排班）——吞吐应因此**回升**；
3. 网络路径变长：同机轮走 WSL 内回环（≈0 RTT），本轮每个请求都过一次宿主↔WSL 的
   mirrored 适配器（单连接建立 31ms，预建连接摊掉建连成本后每请求仍多一跳转发）。

**数字解读**：热态 535–552 req/s，比对照 A 高 12–15%（方向对：去掉对账 + 内存隔离的
收益 > 网络路径的损耗），但 p50（1079–1155ms）与对照 A（1119ms）同量级——说明瓶颈
不在客户端 CPU 抢核（否则 p50 应明显下降），**受理尾延迟由服务端 1000 并发下的
排队决定，网络跳数的增量被排队噪声淹没**。与对照 B（711–1382）不可直接比：那是
10-23 的代码与数据状态（此后新增了 5B/5C 的若干拦截链路），且同为同机口径。

**口径结论（能升级到什么程度）**：

- 可以说："1k 全并发异步受理，客户端与被测系统**内存隔离**（不同 OS 侧）、零失败
  （1000×202/业务码全 0），吞吐 536–552 req/s"；
- 不能说："客户端与被测系统**资源隔离**"——CPU 仍是同一颗 Ryzen 9 的 16 逻辑核，
  这台机器上不存在真正的客户端/服务端分离压测；
- "单机相对基线"的表述**维持不变**（对照 B 的边界原样有效），本轮只是把"客户端与
  服务端同进程组抢内存"这一条干扰因素排除了，属于口径硬化而非口径升级。

## 5. 边界与观察项

| 项 | 说明 |
|---|---|
| CPU 共享 | WSL2 vCPU = 宿主逻辑核；吞吐数字仍是"共享 16 核下的下限"口径 |
| 网络路径增量 | mirrored 适配器的每请求转发成本未单独测量（被排队噪声掩盖）；要单独量化需在 WSL 内同时跑同款基线（本轮未做，避免再引入同机对照组的变量） |
| run 1 冷态 | 392.4 req/s（首跑，JIT/路由缓存冷）；报告以热态 run 2/3 为准，冷态如实列出 |
| 2k/4k、阶梯、soak | 未做（属 5D k6 范围） |
| localhost 假数据 | 首轮 `BarrierBroken` 1000/1000（吞吐 6.2 req/s）已识别为路径问题非服务端问题，存证未计入任何对照 |
