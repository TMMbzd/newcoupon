## 2. 环境拓扑与"实际用的路径"（README 口径同文）

```
Windows 宿主（Python 3.13.7，1000 线程 + 1000 预建 TCP 连接）
    │  http://127.0.0.1:8080
    ▼ （WSL2 networkingMode=mirrored：宿主 127.0.0.1 直通 WSL 内监听端口）
WSL2（java 应用 :8080，-Xmx1g）──▶ MySQL / Redis 容器（docker）
```

- **CPU 仍共享**：WSL2 的 vCPU 是宿主逻辑核（AMD Ryzen 9 6900HX，16 逻辑核），客户端
  线程与应用/容器仍抢同一组核——这是 WSL2 的物理现实，"宿主分离"分离不了 CPU。
- **内存隔离是真的**：客户端 1000 线程（栈 512KB/线程）+ 连接缓冲全在 Windows 侧，
  不占 WSL 的 7.8G；观测栈（prometheus/grafana）按纪律提前停掉。
- **路径踩坑（重要，README 同文）**：
  1. `localhost` 在本机 Windows 解析优先 `::1`，mirrored 模式的 IPv6 回环到 WSL **不通**
     ——实测 Python 经 `localhost` 建连一次要 **8.019s**（先等 ::1 超时），1000 预建连接
     超过脚本的 240s 栅栏超时，首轮全军 `BarrierBroken`（输出存证
     `target/stability/p5c-host-run1-localhost-broken.json`，吞吐 6.2 req/s 假数据）；
  2. 显式用 **`http://127.0.0.1:8080`**（IPv4）后单连接 **0.031s**，一切正常；
  3. 直连 WSL eth0 IP（172.23.x.x）从 Windows **不可达**（mirrored 模式没有 NAT 回程，
     实测 curl 000 超时）——"查 WSL IP 方案"在此网络模式下不适用，IPv4 回环是唯一路径。

## 4. 对照分析（如实：什么变了、什么没变、口径能升级到哪）

**先撤回一个不可靠的旧结论**：原版"宿主分离比同机+对账（478.4）高 12–15%"建立在
未归档的 551.6/535.7 上，且复跑证明**跨天吞吐对照本身不可靠**——两天里机器负载不同
（复跑时有外来容器抢 IO/CPU，热轮 366.3 也只有旧值的 2/3）。吞吐绝对值不是本刀的
可防守结论，撤回百分比表述。

**仍可防守的结论（全部有归档）**：

1. **形态成立**：1000 线程/1000 预建连接的客户端在 Windows 宿主跑、服务端在 WSL——
   客户端内存（~1G 级线程栈+缓冲）不在 WSL 的 7.8G 里，**内存隔离成立**；
2. **零失败**：两轮各 1000×HTTP 202、业务码全 0、无 errors；worker 全 SUCCESS、
   库存守恒（§3 SQL 落盘）；
3. **CPU 仍共享**：WSL2 vCPU = 宿主逻辑核（Ryzen 9 6900HX，16 核），复跑轮外来容器
   把吞吐从 ~552 压到 277–366 正是共享的直接证据——"宿主分离"分离不了 CPU；
4. **网络路径**：mirrored 模式下 Windows→WSL 必须走 IPv4 回环（§2 踩坑），预建连接
   后每请求多一跳宿主↔WSL 转发——p50（1400–2321ms）与同机基线（1119ms）同量级偏上，
   排队仍是延迟主体，网络增量被排队噪声部分掩盖。

**口径结论（能升级到什么程度）**：

- 可以说："1k 全并发异步受理，客户端与被测系统**内存隔离**（不同 OS 侧）、零失败，
  两轮归档吞吐 277.1 / 366.3 req/s（当日机器负载口径）"；
- 不能说："客户端与被测系统**资源隔离**"，也不能给跨天的吞吐百分比——这台机器上
  不存在真正的客户端/服务端分离压测，吞吐数字只对当天机器状态负责；
- "单机相对基线"的表述**维持不变**（对照 B 的边界原样有效），本刀是口径硬化
  （排除"客户端与服务端同进程组抢内存"这一干扰因素），不是口径升级。

**压测延迟与 SLO 延迟不是一回事（口径预答）**：本轮 p50 1.4~2.3s / p99 2.7~3.6s 远超
receive 链路 SLO 的 P99≤300ms 档位——这不是违约，是两种负载形态：SLO 档位针对**常态
流量**（并发远低于容量，排队时间≈0）；本轮是**容量压测的饱和态**（1000 并发全在途，
延迟主体是排队与 1000 连接的接入排队）。用饱和态的 p99 对照常态 SLO 档位会得出
"系统违约十倍"的误判；反过来也不能拿 SLO 档位去质疑压测数字——两者回答的问题不同
（"平时够不够快" vs "极限能扛多少"）。

## 5. 边界与观察项

| 项 | 说明 |
|---|---|
| CPU 共享 | WSL2 vCPU = 宿主逻辑核；吞吐数字仍是"共享 16 核下的下限"口径 |
| **跨天吞吐不可比** | 复跑（277–366）vs 两天前（392–552），同一形态不同机器负载；任何跨天吞吐百分比都不可靠（本报告已撤回原 12–15% 表述） |
| 未归档历史数字 | 11-10 的热轮 551.6/535.7 未传 --output、无归档——降级为历史观察，不作证据；复跑两轮全部落盘 |
| 网络路径增量 | mirrored 适配器的每请求转发成本未单独测量（被排队噪声掩盖）；要单独量化需在 WSL 内同时跑同款基线（未做，避免再引入变量） |
| interop 瞬断（复跑排障） | WSL→Windows 进程通道 2026-11-12 出现分钟级瞬断（`UtilAcceptVsock accept4 failed 110`，首两次 driver 全军覆没、第三次自愈）——排障记录与失败输出归档 `p5cr1/p5cr2-client-stdout.txt`（67B 的 vsock 报错）；driver 加 interop 预检+重试后手动分步跑通 |
| 2k/4k、阶梯、soak | 未做（属 5D k6 范围） |
| localhost 假数据 | 首轮 `BarrierBroken` 1000/1000（吞吐 6.2 req/s）已识别为路径问题非服务端问题，存证未计入任何对照 |
