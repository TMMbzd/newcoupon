# Tracing 取证报告：Micrometer Tracing + OTLP + Jaeger（2026-11-12）

> 对应计划：V6 5B 生产化模拟刀 C2（[runbook/Tracing与E2E.md](../runbook/Tracing与E2E.md)、
> V6 计划 §5B Tracing 分节）。交付物：pom 追加 OTel bridge + OTLP exporter（Boot BOM 管版本）、
> `coupon.tracing.enabled` 总开关（默认关）+ `TracingOffConfig`（关=NoopTracer）、
> 业务里程碑 span（coupon-issue-persist / issue-worker-round / audit-write）、
> `ContextPropagatingExecutors`（OTel+micrometer 双层异步传播）、compose profile `observe` 的 jaeger。
> 环境：WSL2 单机；应用宿主机 `java -Xmx512m` :8080（dev profile，TRACING_ENABLED=true），
> MySQL/Redis/Jaeger（all-in-one 1.62.0，mem_limit 512m）走 compose；查证走 Jaeger REST
> `16686/api/traces`（与 UI 同源）。
> 证据等级：A=实测输出原文（本报告引用段逐字照抄 §6 归档清单里的文件）。

## 1. 结论（先看这一节）

| 验证项 | 结果 | 证据（逐字照抄归档，见 §6） |
|---|---|---|
| 开关契约（关=零导出零记录，bean 级） | ✅ | `TracingSwitchIntegrationTest` 三断言：注入 Tracer==NOOP + SpanExporter bean 数 0 + nextSpan 空 traceId |
| 异步传播（机制级，先红后绿） | ✅ | `TracingAsyncPropagationIntegrationTest`：只包 micrometer 快照时子 span **裂新 traceId**（先红 `c78c458d…` vs `031de620…`，mvn 日志留档）；双层包装（OTel Context.wrap）后 traceId 相同 |
| trace 存在且进 Jaeger（运行级） | ✅ | 归档 `c2-services.json`：`{"data":["jaeger-all-in-one","newcoupon-server"],…}` |
| 服务端 span 名低基数（路由模板） | ✅ | 归档 `c2-traces-summary.txt`：`http post /api/templates/{id}/publish`（参数路由显式 `{id}` 占位）、`http get /api/templates`——OTel 小写语义命名，实测与"POST /path"直觉不同 |
| 登录链 trace：审计异步 span 挂同一 trace | ✅ | 归档：`http post /console/api/auth/login`（root）→ `audit-write`（child，**coupon.thread=audit-writer**，action=ADMIN_AUTH_LOGIN_SUCCESS）——异步传播成立的直接证据 |
| 领券链 trace：落库里程碑 span | ✅ | 归档：`http post /api/coupons/receive`（root）→ `coupon-issue-persist`（child，milestone=issue-db-commit，template-id=74/75） |
| 批量 worker 轮 span（@Scheduled/XXL 入口） | ✅ | 归档：`task coupon-issue-task-worker.scheduled-tick`（root）→ `issue-worker-round`（child，issue.claimed=1，thread=scheduling-3） |
| 框架自动 span（Security/@Scheduled） | ✅ | 归档：security filterchain before/after、authorize request、secured request、task outbox-dispatcher.dispatch 等 |
| 开关关复跑零导出（对照） | ✅ | 归档 `c2-off-control.txt`：OFF 实例同流量复跑后，15:55:30 之后新 trace 数 **0**（唯一 1 条是 traced 实例停机秒 15:55:26.189 的 BatchSpanProcessor 收尾 flush，span 起始时刻甄别在档）；OFF 实例自身 200ms/轮的 tick 若在导出应每分钟 ~300 条——一条没有 |
| 内存预算 | ✅ | 归档 `c2-docker-stats.txt`：jaeger **45.57MiB / 512MiB**；应用 -Xmx512m；取证完容器已 stop 还原 |

**一句话**：`TRACING_ENABLED=true` + `--profile observe up -d jaeger` 之后，登录/领券的
trace 经 OTLP 真实落进 Jaeger：HTTP 路由模板 span（低基数）、Security 段落、落库里程碑、
audit-writer 线程上的审计写入全部挂在正确的 trace 位置上；关开关复跑，同样流量零导出。
两个实测出的关键事实写进了代码与 runbook：① Boot 3.3 的开关只拦导出器（需 TracingOffConfig
补 NoopTracer）；② micrometer 快照单独不够、异步传播必须 OTel Context.wrap 双层包装。

## 2. 关键设计事实（实测裁定，已写进代码注释与 runbook）

1. **Boot 3.3 开关语义缺口**：`management.tracing.enabled=false` 只拦 `@ConditionalOnEnabledTracing`
   标注的 bean（导出器族），OtelTracer/Sampler 仍装配、`nextSpan()` 仍返回带真实 traceId 的
   span 对象（实测 `b6b8e4c7…`，TracingSwitchIntegrationTest 先红证据）——补 `TracingOffConfig`
   提供 `Tracer.NOOP`（Boot 真实 tracer 是 @ConditionalOnMissingBean，让位）。
2. **异步传播双层必要性**：micrometer `ObservationThreadLocalAccessor`（SPI 自动注册）只恢复
   Observation；OTel bridge 的 `nextSpan()` 从 OTel 自己的 ThreadLocal 找父——只包 micrometer
   快照，工作线程子 span 裂新 traceId（实测复现）。`ContextPropagatingExecutors` =
   OTel `Context.current().wrap`（过 span 上下文）+ micrometer `ContextSnapshot`（过
   Observation/MDC），已包 audit-writer / audit-export-writer / issue-task-worker 三池。
3. **@Scheduled 自动 span 与量级**：Boot/Spring 6.1 给每个 @Scheduled 方法建 `task <bean>.<method>`
   根 span——issue worker 200ms/轮在 dev 全采下 ~5 span/s（本报告抓取窗口内 1141 条 tick
   span）。生产开 tracing 必须先定采样率（§5 裁剪登记）。
4. **worker 的批量快路径不经 issueC1**：dev 默认 `raw-bulk-enabled=true`，worker 轮 trace 里有
   `issue-worker-round` 但没有 `coupon-issue-persist`（里程碑 span 在同步领券/逐任务路径）——
   不是丢 span，是路径本身不同。

## 3. 部署形态（进了 git 的东西）

```

                                                     #   management.tracing.enabled / sampling / otlp.endpoint 映射
src/main/java/.../infrastructure/tracing/
  ├─ ContextPropagatingExecutors.java                # 双层包装（提交点在调用线程捕获）
  └─ TracingOffConfig.java                           # 关开关时的 NoopTracer（业务代码零分支的根据）
AuditService / AuditExportService / CouponIssueTaskWorker   # 三池包传播（+ audit-write span）
CouponIssueTxService#issueC1                         # 落库里程碑 span（coupon-issue-persist）
CouponIssueTaskWorker#runOnce                        # worker 轮根 span（@Scheduled 与 XXL 同入口）
docker-compose.yml                                   # jaeger（profile observe，16686 UI/API + 4318 OTLP，mem_limit 512m）
```

## 4. 实跑取证（Jaeger REST API 输出原文）

流量序列（应用 TRACING_ENABLED=true，dev profile，async+worker 默认开）：
控制台登录（CSRF 流，curl，响应 200 + 身份快照）→ 建模板+发布（X-Admin-Token，74/75 号）→
同步领券 1 笔（couponId 落库成功）→ 异步领券 1 笔（taskId=18485 ACCEPTED，worker 1 秒内领取）。

以下逐字照抄归档 `c2-traces-summary.txt`（`jaeger-summarize.py` 摘要，源 JSON 同目录归档）：

```text
== trace eaab2f715d38514f1d08cd9f994bcf04 (service=newcoupon-server, spans=6) ==
  +     0ms dur=   343us [root ] http post /console/api/auth/login  
  +     1ms dur=     1us [child] security filterchain before  
  +     2ms dur=     0us [child] authorize request  
  +     2ms dur=   339us [child] secured request  
  +   278ms dur=    55us [child] audit-write  coupon.thread=audit-writer audit.action=ADMIN_AUTH_LOGIN_SUCCESS
  +   342ms dur=     0us [child] security filterchain after  
```
→ 登录请求的 trace 里，audit-writer 线程上的审计写入（+278ms）是同 trace 的子 span：
**异步传播成立的直接证据**（提交线程→审计单线程池，traceId 不断线）。

```text
== trace f33ab5fb8c8c2cadaae1cb6b5959bfa3 (service=newcoupon-server, spans=6) ==
  +     0ms dur=   448us [root ] http post /api/coupons/receive  
  +    30ms dur=     1us [child] security filterchain before  
  +    31ms dur=     0us [child] authorize request  
  +    31ms dur=   415us [child] secured request  
  +   365ms dur=    64us [child] coupon-issue-persist  coupon.milestone=issue-db-commit coupon.template-id=74
  +   447ms dur=     0us [child] security filterchain after  
```
→ 同步领券的落库里程碑：`coupon-issue-persist`（+365ms，带 template-id）挂在请求 trace 上。

```text
== trace 2d9aa8d0877ebb5af7b98da44263185b (service=newcoupon-server, spans=7) ==
  +     0ms dur=   164us [root ] http post /api/templates/{id}/publish  
  +     1ms dur=     4us [child] security filterchain before  
  ...
== trace 553379fa84f36b02a609dd755c0b38c6 (service=newcoupon-server, spans=2) ==
  +     0ms dur=   144us [root ] task coupon-issue-task-worker.scheduled-tick  
  +    29ms dur=   114us [child] issue-worker-round  coupon.thread=scheduling-3 issue.claimed=1
```
→ 参数路由 span 名是 `{id}` 占位（低基数）；worker 轮根 span 是 @Scheduled 的 task span，
`issue-worker-round` 为其子 span（claimed=1）——XXL 入口（`couponIssueTaskJob`）与
@Scheduled 走同一 runOnce，同一形态。

## 5. 开关关对照（零导出）

逐字照抄归档 `c2-off-control.txt`（cutoff 15:55:26 停 traced 实例 → OFF 实例同流量复跑）：

```text
Jaeger API: GET /api/traces?service=newcoupon-server&start=15:55:26→ now（limit=100）
OFF 窗口内新 trace 数: 1
  947dedcc5f3a9415f029195fdeede433 [task coupon-issue-task-worker.scheduled-tick]

该 trace 的 span 起始时刻（关键甄别）：
  span start: 15:55:26.189547 task coupon-issue-task-worker.scheduled-tick
→ 15:55:26.1895 == 停机秒：这是 traced 实例的最后一次 scheduled tick（OTel
  BatchSpanProcessor 在进程关闭时 flush 的收尾 span），不是 OFF 实例导出的。

Jaeger API: start=15:55:30（排除停机 flush）→ now：
  OFF 窗口（15:55:30 后）新 trace 数: 0

OFF 实例同时段自身的 @Scheduled tick（200ms/轮）一个都没出现——若导出链活着，
这里应是每分钟 ~300 条 task span（对照：traced 实例同量级）。
```
