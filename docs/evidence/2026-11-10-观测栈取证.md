## 2. 部署形态（进了 git 的东西）

```
docker-compose.yml                 # prometheus + grafana（profile observe，默认不起；mem_limit 各 256m；
                                   #   prometheus TSDB 挂 named volume prometheus-data——容器重建不丢数据）
ops/prometheus/prometheus.yml      # 抓 newcoupon /actuator/prometheus（Basic：username 明文 + password_file），
                                   #   rule_files 挂 5A 三件套
ops/grafana/provisioning/datasources/prometheus.yml   # 数据源 → http://prometheus:9090（uid: prometheus）
ops/grafana/provisioning/dashboards/slo-provider.yml  # 大盘加载器
ops/grafana/slo-dashboard.json     # SLO 盘六面板（查询全部走 recording 规则名，不重写公式）
```

六面板：四链路可用性（1h/6h）、错误预算剩余（28d）、燃烧率三窗（1h/6h/3d，
阈值线 1×/6×/14.4×）、SLI 事件速率（journey×outcome）、断流状态（`up`，
state-timeline，UP/断流两色）、延迟 P99（分链路档位线 0.15/0.3/0.5s）。

凭据链（密码不落 git/配置文件）：`ACTUATOR_AUTH_PASSWORD`（compose 环境变量，缺省
回落仓库惯例 dev 凭据 `it-actuator-pass`）→ 容器启动命令写出 `/tmp/basic-auth-password`
→ `prometheus.yml` 的 `basic_auth_password_file` 引用。Prometheus 配置不支持环境变量
展开，这是把凭据从环境变量接进配置的标准接法。

### 3.2 停应用 90 秒：断流序列（`up` 面板的数据）

```text
$ GET /api/v1/query_range?query=up{job="newcoupon"}&step=15   #（最近 10 分钟）
samples: 18
  up=1  22:04:57 → 22:05:12  (2 samples)     ← 正常
  up=0  22:05:27 → 22:07:27  (9 samples)     ← 应用停机窗口（SIGTERM 22:05:11 → 重启健康 22:07:26）
  up=1  22:07:42 → 22:09:12  (7 samples)     ← 恢复
```

### 3.3 SLI 事件与可用性/燃烧率（bad=停 MySQL 期间 10 笔 code:5000）

```text
$ sum by (journey, outcome) (coupon_sli_events_total)
  receive/bad=10   receive/good=4      #（app 重启后 counter 重置，increase() 跨重置累计=good 14）

$ coupon:sli_availability_ratio:1h
  receive: 0.500000        # 记录规则首轮评估时点：good 10 / (10+10)
  receive: 0.5833333333333334   # 恢复期 4 笔 good 被下轮计入：14 / (14+10) —— 算术自洽

$ coupon:sli_burn_rate:1h
  burn:1h receive: 500.0x  # (1−0.5)/0.001，恰为 500 倍

$ coupon:sli_latency_p99_seconds:5m
  receive: 3.2141s         # 故障期 DB 连接失败的请求把 P99 顶到 3.2s（> 0.3s 档位）
  calculate/confirm/refund: nans   # 无流量链路的直方图空桶 → NaN（面板显示为无数据，不是 0）
```

### 3.4 告警：真实触发与状态演化

```text
22:07:54  停 MySQL → 10 笔 receive 全部 code:5000（bad）
22:08:35  MySQL 恢复健康 → 恢复期 4 笔 receive code:0
22:09:40  /api/v1/rules: CouponSloLatencyBudgetTicket state=pending
22:12:10  /api/v1/alerts:
  ALERT CouponSloFastBurn          severity=page   journey=receive  activeAt=2026-11-10T14:09:23Z   → firing
  ALERT CouponSloLatencyBudgetTicket severity=ticket journey=receive  activeAt=2026-11-10T14:06:23Z → firing
```

FastBurn 的时序自洽：bad 事件 22:07:54–22:08:35 → burn:1h=500× 首次过阈评估
22:09:23（activeAt）→ `for: 2m` 持续满足 → 22:12:10 观察到 firing。500× ≫ 14.4×
阈值，正是"1 小时烧掉 2% 预算"的 page 语义被真实数据触发。

规则加载（`/api/v1/rules`）：`slo-recording` 9 条（4 窗可用性 + 预算 + 3 窗燃烧率 +
延迟 P99）+ `slo-alerts` 4 条（快烧/慢烧/延迟/断流），全部来自 5A 三件套，零改动。

## 4. 首跑翻车记录（值得留档的坑）

1. **prom/prometheus 镜像默认 ENTRYPOINT 是 `/bin/prometheus`**：用 compose `command`
   传 `sh -c` 包装会变成 prometheus 的命令行参数（`unexpected sh` 崩溃循环）。必须
   同时覆盖 `entrypoint: ["sh", "-c"]`。
2. **无凭据默认 + compose up 的重建语义**：首版把 `ACTUATOR_AUTH_PASSWORD` 的 compose
   default 留空、靠容器内 `:?` 检查 fail-loud——结果任何一次没带环境变量的
   `docker compose up`（哪怕只点名 grafana）都会把 prometheus 容器重建成无凭据崩溃
   循环，且**容器重建即 TSDB 清零**，首跑取证窗口因此作废重跑。修正两处：default
   回落仓库惯例 dev 凭据（生产显式覆盖）；TSDB 挂 named volume `prometheus-data`。
3. **整目录挂载 provisioning 的副作用**：`./ops/grafana/provisioning:/etc/grafana/provisioning`
   会把镜像自带的 `plugins/`、`alerting/` 子目录遮没（启动日志报错）。改为只挂
   `datasources/` 与 `dashboards/` 两个子目录。

## 5. 复现

```bash
docker compose up -d                                    # mysql/redis
# 起应用（Basic 凭据必须显式给，否则密码随机=抓不到）：
ACTUATOR_AUTH_USER=actuator ACTUATOR_AUTH_PASSWORD=it-actuator-pass \
  java -Xmx512m -cp target/classes:$(cat target/stability-cp.txt) com.newcoupon.NewCouponApplication \
    --server.port=8080 --coupon.risk.ip-rate.enabled=false --coupon.issue.worker.initial-delay-ms=600000 &
docker compose --profile observe up -d prometheus grafana
# 建模板/发布 → 打 good 流量 → kill 应用 ~90s → 重启 → docker stop mysql → 10 笔 receive（5000）
# → docker start mysql → 恢复流量 → 等 2~3 分钟看告警 → 取证 → 收尾：
docker compose stop prometheus grafana
```

收尾已执行：observe profile 两容器已停、应用已停（环境还原，不留常驻观测栈）。
