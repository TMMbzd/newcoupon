### 3.4 告警：真实 firing 的完整取证（2026-11-12 复跑轮）

  ≫ 14.4× 阈值，正是"1 小时烧掉 2% 预算"的 page 语义被真实数据触发）
- 抬升的持续性（for 窗内表达式恒真）有区间序列归档 `b1r-latency-range.log`：
  receive P99 自 13:45:32 起 1.75~30s，贯穿整个 10 分钟窗口。

3 窗燃烧率 + 延迟 P99）+ `slo-alerts` 4 条（快烧/慢烧/延迟/断流），全部来自 5A 三件套，零改动。

## 4. 首跑翻车记录（值得留档的坑）

1. **prom/prometheus 镜像默认 ENTRYPOINT 是 `/bin/prometheus`**：用 compose `command`
   传 `sh -c` 包装会变成 prometheus 的命令行参数（`unexpected sh` 崩溃循环）。必须
   同时覆盖 `entrypoint: ["sh", "-c"]`。
2. **无凭据默认 + compose up 的重建语义**：首版把 `ACTUATOR_AUTH_PASSWORD` 的 compose
   default 留空、靠容器内 `:?` 检查 fail-loud——结果任何一次没带环境变量的
   `docker compose up`（哪怕只点名 grafana）都会把 prometheus 容器重建成无凭据崩溃
   循环，且**容器重建即 TSDB 清零**，首跑取证窗口因此作废重跑。修正两处：default
   回落仓库惯例 dev 凭据（生产显式覆盖）；TSDB 挂 named volume `prometheus-data`。
3. **整目录挂载 provisioning 的副作用**：`./ops/grafana/provisioning:/etc/grafana/provisioning`
   会把镜像自带的 `plugins/`、`alerting/` 子目录遮没（启动日志报错）。改为只挂
   `datasources/` 与 `dashboards/` 两个子目录。
4. **`/api/v1/alerts` 的坑（审查修复轮实证）**：该接口**同时列出 pending 与 firing**
   的告警，且本报告首版的提取脚本没取 `state` 字段——把 pending 的
   LatencyBudgetTicket 误标成 firing，还引出了一个 activeAt+for 算术对不上的"矛盾"。
   教训两件：读告警必须带 state 字段；没有归档的即时查询值不进报告。
5. **起观测栈复跑时要显式带凭据起应用**：2026-11-12 复跑首启应用漏了
   `ACTUATOR_AUTH_PASSWORD`（应用随机生成密码）→ prometheus 全程 401、target down。
   凭据必须两侧同源（runbook §4 的原话就是为这个场景写的）。

## 5. 复现

```bash
docker compose up -d                                    # mysql/redis
# 起应用（Basic 凭据必须显式给，否则密码随机=抓不到）：
ACTUATOR_AUTH_USER=actuator ACTUATOR_AUTH_PASSWORD=it-actuator-pass \
  java -Xmx512m -cp target/classes:$(cat target/stability-cp.txt) com.newcoupon.NewCouponApplication \
    --server.port=8080 --coupon.risk.ip-rate.enabled=false --coupon.issue.worker.initial-delay-ms=600000 &
docker compose --profile observe up -d prometheus grafana
# 建模板/发布 → 打 good 流量 → kill 应用 ~90s → 重启（up 跌落取证）
# 慢事件取证（等满 for 窗）：×6 轮 [docker stop mysql → 3 笔 receive(5000) → start mysql，
#   间隔 150s]，全程 10s 快照 /api/v1/rules → Latency activeAt+10m 后捕获 firing →
#   /api/v1/alerts（带 state）落盘 → 收尾：
docker compose stop prometheus grafana
```

收尾已执行（两轮皆是）：observe profile 两容器已停、应用已停（环境还原，不留常驻观测栈）。
