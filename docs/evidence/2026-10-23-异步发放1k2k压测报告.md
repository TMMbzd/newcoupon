# 异步发放 1k/2k 压测报告（2026-10-23）

> 对应设计：[ADR-0019 异步发放任务表 WAL](../adr/ADR-0019-async-issue-task-wal.md)  
> 对应库存模型：[ADR-0018 C1 固定分片](../adr/ADR-0018-stock-model-c1-fixed-shards.md)  
> 压测脚本：[scripts/load/async_issue_load.py](../../scripts/load/async_issue_load.py)  
> 环境：WSL2 单机，MySQL 8.0.46 / Redis 7 容器，应用 `-Xmx1g`；本地环境模拟生产，不是线上容量认证。

## 1. 结论（先看这一节）

### 1.1 受理面：1k/2k 通过

| 场景 | 请求数 | 并发 | 结果 | 观测吞吐 | p99 |
|---|---:|---:|---|---:|---:|
| 1k 并发受理 | 1000 | 1000 | 1000×HTTP 202，业务码 0 | **711–1382 req/s** | 744–1464 ms |
| 2k 并发受理 | 2000 | 2000 | 2000×HTTP 202，业务码 0 | **1050–2122 req/s** | 737–1777 ms |

同一份服务端代码、同一台机器复跑，吞吐会随 JVM 预热/CPU 争用波动；上表是保守观测区间，不是稳定 QPS 承诺。另有预热后 2k=5208 req/s、4k=6033 req/s 的单次快照，不纳入区间。**能钉死的结论是：1k/2k 并发请求全部拿到 202，正确性检查全过；不要拿某一次快照当稳定 SLA。**

口径：客户端先建立 1000/2000 条 TCP 连接，全部就绪后在栅栏处同时发请求；延迟从栅栏释放开始，到读完响应体结束。不是“线程数 ÷ 总耗时”的伪并发指标。

### 1.2 正确性：不超发、不超日限、不重复

| 验证 | 输入 | 结果 |
|---|---|---|
| 库存不超发 | 库存 3000，4000 并发请求 | 3000×202 受理；1000×3001 售罄；最终 success=3000、`Σused=3000`、券行=3000 |
| 模板硬日限 | 500 个任务，`dailyLimit=300` | success=300；rejected=200，错误码 3003；`coupon_daily_counter.used=300`、`Σused=300` |
| 每人硬日限 | 同一用户 3 个任务，`perUserDailyLimit=1` | success=1；rejected=2，错误码 3002；`coupon_user_daily_counter.used=1` |
| requestId 幂等 | 同一 user+requestId 并发 100 次 | 任务行=1、券行=1、`Σused=1`；96 次 202，4 次在“任务尚未落库”的窗口返回可重试的 1001 |
| 重复检查 | 上述库存压测 | 按 `(user_id, request_id)` 重复任务=0；按 user 重复=0 |

`requestId` 并发的 4 次 1001 是预约语义的已知窗口：Redis gate 已把幂等键置为 `PENDING`，但同步任务表还没提交，后到的请求查不到任务，返回“请求正在处理中，请勿重复提交”。它不是重复发券，客户端按可重试处理即可；如果要求“重复请求必须拿到同一个 taskId”，需要受理侧对 PENDING 做短暂等待/回查，登记为可选优化。

### 1.3 worker 单实例吞吐：裸 JDBC 物理表批量写后达到 1k+

| 阶段 | 做法 | 观测 |
|---|---|---:|
| 单线程逐条 | 每任务一个事务 | 约 32 task/s |
| 多线程逐条 | 8 线程 | 约 111 task/s |
| 按库存分片分组（ShardingSphere 批量 SQL） | 16 组并行 | 约 364–500 task/s |
| **裸 JDBC 物理表批量写（最终）** | 整块多行 INSERT + 库存按分片扣减 + 任务 CASE 回写 | **约 1.27k–1.6k task/s** |

最终态 4k 积压（worker 延迟启动、无并发受理干扰）约 **3.1 s** 清空：两个 2000 任务块分别约 1.9 s、1.3 s。单块 2000 任务的分阶段耗时（debug 日志）：库存 26 ms、对象构造 37 ms、券 360 ms、过期任务 227 ms、事件+outbox 976 ms、任务状态 171 ms、提交 84 ms。第二块在缓存/连接预热后更快。

- **受理面达到并超过 1k/2k**；异步的价值是把同步请求从“等 5 条业务写”里解放出来。
- **单实例 worker 已达到 1k+（本机约 1.3k–1.6k task/s）**；2k 突发可在 2 s 量级消化。
- 这条快路径用裸 JDBC 直写物理表，绕开 ShardingSphere 的逐行解析；单任务/日限路径仍走 ShardingSphere，批量失败会回退，见 §3.5。未来拆 16 物理库时，裸写必须按库路由或设置 `raw-bulk-enabled=false`，这是明确的迁移条件。
- 多实例是另一条扩容路径，但当前单实例已满足本地 1k+；正式多实例压测要在各实例 `coupon.id.worker-id` 互异、worker 同时启动的条件下做。

## 2. 测试环境与参数

### 2.1 机器

- WSL2，`nproc=16`，内存 7.8 GiB（与压测客户端同机，客户端也吃 CPU；数字是下限）。
- MySQL 8.0.46 容器，`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`（默认持久化，没有为了跑分关 fsync）。
- Redis 7 容器。
- 应用 `java -Xms512m -Xmx1g`，ShardingSphere + Hikari 业务池 40（压测调参，默认 20）。
- `coupon.risk.ip-rate.enabled=false`：压测机只有一个源 IP，不关会被 30 次/分钟的风控频控挡住；生产不能关，异步入口已补上同一道 IP 频控。
- `logging.level...LogEventPublisher=WARN`：默认 `log` 传输会把每条 outbox 消息打成一行 INFO，压测时是日志 I/O 噪声；生产切 RocketMQ 后不走这个 publisher。

### 2.2 worker 参数

最终压测参数：

```text
coupon.issue.worker.batch-size=2000
coupon.issue.worker.batch-tx-size=2000
coupon.issue.worker.parallelism=2
coupon.issue.worker.group-parallelism=16
coupon.issue.worker.raw-bulk-enabled=true
coupon.issue.worker.raw-bulk-pool-size=4
coupon.sharding.pool.max-size=40
```

代码默认值更保守（`batch-size=50`、`batch-tx-size=50`、`parallelism=4`、`group-parallelism=16`、`raw-bulk-pool-size=4`），按压测结果再调大。`group-parallelism` 只在中路径（按分片回退）使用；`raw-bulk-pool-size` 是裸 JDBC 批量写专用小池。

### 2.3 客户端方法

`scripts/load/async_issue_load.py`：

1. 每个请求一个唯一 `userId` 和 `requestId`；
2. 用 `http.client` **预先建立全部 TCP 连接**，再在 `threading.Barrier` 处同时发请求；
3. 记录 HTTP 状态、业务码、p50/p95/p99/max 和 wall time；
4. 预连接失败、读超时、连接重置都计数，不静默丢样本。

为什么预连接：第一轮直接在栅栏后开 2000 条新连接，测到大量连接失败/35 秒长尾，那是 TCP accept 队列/建连风暴，不是服务端受理能力。预连接后 2k 全部 202，观测吞吐 1050–2122 req/s、p99 737–2320 ms；同一台机器、同一份服务端代码，差别只在客户端怎么建连以及 JVM 是否预热。

> 6k 并发预连接在本机仍会有约 1.9k 条 `OSError`（监听队列/客户端资源上限），所以库存正确性用 4k 并发验证；这不影响 2k 目标。

## 3. 实施过程中发现并修掉的问题

### 3.1 单任务一事务在 WSL/单盘上只有约 32 task/s

第一轮 worker `batch-size=100`、单线程逐条处理，1001 个任务耗时约 31 s，约 32 task/s。原因不是 Snowflake/Java，而是每条任务一个本地事务、每次提交都要 fsync；WSL 的虚拟盘把提交吞吐钉死。

修法分三层：

1. **按库存分片分组、并行事务**（`CouponIssueTaskProcessor.processBatch`）：
   - 只对“同一模板 + 模板日限=0 + 每人日限=0 + 批内用户不重复”启用；
   - 每组的任务先算好 `MAX(seq)+1` 和首选分片；
   - 每个分片一个事务，组间并行；
   - 任一组失败（库存满、幂等、死锁等）只回滚该组，再逐条重跑，错误码仍由单任务路径裁决。
2. **outbox 批量标记**：投递器原来逐行 `UPDATE ... status=1`，100 行=100 次 autocommit；改成一条 `IN` 更新，100 次提交变 1 次（`CouponOutboxMapper.markDispatchedBatch`）。
3. **Snowflake 回拨日志限流**：WSL 时钟回拨时每个 ID 打一行 ERROR，759 行日志本身成为 I/O 噪声；改为 1 行/秒并记录被抑制条数，发号策略不变（借用未来毫秒保证唯一）。

效果：4k 积压从约 31 s/1k 降到约 11 s/4k（≈364 task/s，约 11 倍），2k 热态突发更快。

### 3.2 先按整块任务开事务反而更慢

最初的“批量事务”把 50 条任务放进一个事务，逐个分片加锁。实测约 133 task/s，比并行分组还慢：一个事务会依次锁 16 个库存分片并持有到提交，其他批只能排队等 shard 0。

随后改成 **按库存分片分组**：一个事务只锁一行 `coupon_stock_shard`，16 个分片组可以并行提交。这是 ADR-0019 §9 所说“按分片分组”的中间实现；最终又被 §3.5 的裸 JDBC 整块批量写替代。

### 3.3 批量路径跨模板串券（审查抓到的真问题）

worker 最初按领取顺序每 50 条切一块，`processBatch` 只读第一行的模板。若一批里混入模板 A 和 B，会用 A 的模板发 B 的券。

修复：worker 先按 `templateId` 分组，再在组内切块（`CouponIssueTaskWorker.runOnce`），并新增集成测试 `AsyncIssueWorkerIntegrationTest.batchPathKeepsTemplateOwnership`，断言同一轮混跑两个模板时券归属不串。

### 3.4 异步入口的两个治理缺口

- `/api/coupons/receive-async` 原本不在 `AdminTokenFilter.BUSINESS_WRITE_PATHS`，内部异步入口会被管理令牌挡住，而 `/open/v1` 同名入口走签名链又能进——同一业务两套身份前提。已补白名单并加结构性断言。
- `RiskControlFilter` 只匹配 `POST .../receive`，改走 `/receive-async` 就绕开了 IP 频控。已把 `/receive-async` 纳入同一判据并补测试；压测时显式关闭频控，生产不能关。

### 3.5 ShardingSphere 解析成为新瓶颈：裸 JDBC 物理表批量写

**发现过程**：按库存分片分组已经到约 500 task/s，但每 2000 条任务仍要写约 8000 行。分阶段日志显示：

```text
任务状态逐条 JDBC batch  ≈ 1475 ms
coupon_event + outbox     ≈ 1127 ms
user_coupon（64 张表）      ≈ 288 ms
coupon_expire_task（64 张） ≈ 294 ms
```

另做裸 MySQL 对照：同样 4 类共 8000 行、一个事务，`mysql` 客户端约 **0.76 s**；经过 ShardingSphere 解析/改写则要 4–5 s。结论：**瓶颈从数据库提交变成了中间件逐行解析 + 每条任务一次 MAX(seq) 回查 + 2000 条任务 UPDATE**。

**优化一：直接用任务表里的 seq，不再逐条 `MAX(seq)`**

- 受理时 Redis gate 已把 `seq` 写进 `coupon_issue_task`，它本来就在 WAL 里；
- 批量路径直接使用 `task.seq`；2000 条任务就少 2000 次 ShardingSphere 单表查询；
- seq 失效（并发/空洞）由 `uk_user_seq` 唯一索引兜底：批量失败后单任务路径会重新 `MAX(seq)+1`。

**优化二：`CouponIssueTaskRawBulkWriter` 直写物理表**

- 独立懒加载 Hikari 小池（`raw-bulk-pool-size=4`），只在第一次批量写时建连接；
- 一个本地事务内：库存按分片汇总后每片一条 `used=used+N` 条件更新；`user_coupon_N` / `coupon_expire_task_N` 按 `user_id % 64` 分表，每表一条多行 INSERT；`coupon_event`、`coupon_outbox` 各一条多行 INSERT；任务成功用一条 `CASE id ...` 更新；
- 表名只由 0..63/0..15 的整数拼出，不接收外部字符串；
- 任一步失败 rollback，Processor 退回“按分片拆组”再失败逐条走 ShardingSphere，单任务裁决逻辑完全不改。

**优化三：任务成功一条 CASE 更新**

逐条 `UPDATE` 放入 JDBC batch 实测约 1.5 s；改成一条 `UPDATE ... coupon_id = CASE id WHEN ? THEN ? ... END WHERE id IN (...) AND lease_owner=? AND status=1` 后约 120–170 ms，且影响行数能精确校验租约是否丢失。

**优化四：崩溃窗口的幂等修复**

把“券已提交、任务状态未提交”的任务重置后再跑，原逻辑先看到 `MAX(seq)+1 > perUserLimit` 就判 3002，误伤已成功的请求。现在在判限领前先按 `(user_id, appId, requestId)` 查已存在的券；命中同模板就补 SUCCESS，命中其它模板才 REJECTED。新增集成测试 `retryAfterCouponCommittedButTaskNotMarkedIsIdempotentSuccess`。

**代价与边界**：

- 裸写绕过了 ShardingSphere 的路由/解析，只适用于当前“1 物理库 × 64 表”的布局；未来拆 16 物理库时，必须让裸写按库路由，或设置 `coupon.issue.worker.raw-bulk-enabled=false` 回到 ShardingSphere，这是迁移前必须处理的约束。
- 批量路径只处理“同模板 + 无模板日限/每人日限 + 批内用户不重复”；日限/重复用户照旧走单任务事务。
- 裸写不是唯一写通道：单任务、日限、批量失败回退都在 ShardingSphere 路径上；测试同时覆盖两条路径。

### 3.6 回退开关 `raw-bulk-enabled=false` 的回归

**发现的问题**：开关是拆物理库时的回退手段，但此前只验证了“批量事务失败后回退”，没有验证“配置关闭后完全不调用裸写”。如果 `@Value` 没绑定、协调器分支写反，或者测试只断言“最终有券”，即使裸写仍在执行也可能误判为通过。

**测试设计**（两层，分别回答不同问题）：

1. `CouponIssueTaskBatchTxServiceTest`（纯 Mockito，7 例）
   - 开关关闭 → `processAll` / `process` 对每条任务调用 `CouponIssueTaskTxService.process`，`CouponIssueTaskRawBulkWriter.write` 零调用；
   - 开关打开且同模板、无日限、批内用户不重复 → 整批一次 `write`，单任务事务零调用；
   - 单分片组入口在“模板有日限”“批内用户重复”时逐条回退；
   - `processAll` 是整批入口，调用方必须先判定资格；传入日限批次时抛守卫异常，避免误走裸写。

2. `AsyncIssueWorkerRawBulkDisabledIntegrationTest`（真实 MySQL/Redis，1 例）
   - `@SpringBootTest(properties = "coupon.issue.worker.raw-bulk-enabled=false")`，worker 真实领取并处理 5 条同模板任务；
   - 断言 5 条任务全部 SUCCESS、`Σused=5`、券行=5、`coupon_event`=5、`coupon_outbox`=5、每个用户的 `coupon_expire_task`=1；
   - 用 `@SpyBean` 给真实 `CouponIssueTaskRawBulkWriter` 包一层记录调用的代理，断言 `write` 从未被调用。这样即使最终数据正确，只要开关被忽略，测试也会失败。

**顺带修掉的观测问题**：定向跑集成用例时，日志在开关关闭的情况下仍打印 `issue task whole-batch committed`，会让人误以为整批走了一个裸写事务。现在 Processor 改为打印 `issue task batch completed`，协调器在关闭分支额外打印 `raw bulk disabled, processing batch with per-task transactions`。

**结果**：协调器单测 10/10、`AsyncIssueWorkerIntegrationTest` 9/9、关闭开关真实库 1/1、关闭用例+C1 库存审计组合 9/9；全量 `mvn clean test` **530 例：529 绿 + 1 例门控跳过 + 0 失败/0 错误**，BUILD SUCCESS，8:00。首次定向跑关闭开关集成用例耗时 159.7 s，成本主要是 Testcontainers 启动和第二个 Spring 上下文；全量共享容器，增量主要是一个上下文。

**全量回归发现的测试脆弱性**：第一次全量执行时该用例失败，worker 只领到 5 条中的 2 条。日志显示任务创建期间 WSL 发生约 18 秒时钟回拨：前 3 条任务的 `next_scan_time` 落在回拨后的“未来”，worker 的 `now` 比它们小，`next_scan_time <= now` 不成立，所以只领到后 2 条；这 2 条确实走了 `raw bulk disabled` 的逐条路径。修复只改测试：创建任务后显式把 `next_scan_time` 置为 `2000-01-01`，并循环领取直到本用例任务到终态。生产代码没有改；如果生产 JVM 发生时钟回拨，任务可能延迟到时钟追上，登记在 ADR-0019 的风险表里。

**对抗审查补强（同日）**：审查还发现几处会让测试“绿得没有证据”的问题，已一并处理：

- **裸写快路径缺真实物理表正向覆盖**：原有 worker 测试即使裸写 SQL 写错，也会被 Processor 的逐条回退接住，测试仍然有券。新增 `rawBulkWriterWritesPhysicalTables`：直接调用 `CouponIssueTaskRawBulkWriter.write`，用独立裸库连接查询 `user_coupon_<uid%64>`、`coupon_expire_task_<uid%64>`、`coupon_event`、`coupon_outbox`，并断言任务 SUCCESS；同时把 `AsyncIssueWorkerIntegrationTest` 的 `raw-bulk-enabled` 固定为 true。
- **测试清理污染 C1 审计**：原清理只删 `coupon_stock_shard`，留下已发布模板和券行，后续 `C1StockIntegrationTest.auditAll()` 会看到 `Σquota=0`、`Σused=0` 而券行还在。两个 worker 测试类改为保留库存行，模板/券/库存三张表一起自洽；用 `AsyncIssueWorkerRawBulkDisabledIntegrationTest,C1StockIntegrationTest` 组合跑验证（1+8=9/9）。
- **开关关闭时 raw-bulk 连接池仍启动**：`new HikariDataSource(config)` 会在构造时启动池，actuator 的 `Map<String, DataSource>` 又会绕过 `@Lazy`。改成无参 `HikariDataSource` + setter，第一次 `getConnection()` 才建池；关闭开关的集成用例断言 `isRunning()` 为 false，日志中不再出现 `raw-bulk - Starting...`。
- **关闭分支可能没被真正验证**：给禁用用例加 `@SpyBean CouponIssueTaskBatchTxService`，断言 `processAll` 确实被调用；只断言 `write` 零调用不够，因为绕过 `processAll` 也可能让数据正确。
- **每人日限分支缺覆盖**：协调器单测补 `perUserDailyLimit` 的整批守卫和单分片组回退两例，避免删除该条件后无测试变红。
- **`Long` 引用比较**：`bulkEligible` 原用 `item.template().getId() != first.getId()`，超过 `Long` 缓存范围会把同 id 的两个模板实例判成不同模板；改为 `.equals`，并补两个实例同 id 的单测。

**当前测试数**：协调器单测 10/10、`AsyncIssueWorkerIntegrationTest` 9/9、关闭开关真实库 1/1；清理+审计组合 9/9（1+8）。全量 `mvn clean test` **530 例：529 绿 + 1 例门控跳过 + 0 失败/0 错误**，BUILD SUCCESS，8:00。

**边界**：这个用例验证的是“开关关闭时走单任务事务且数据完整”，不是性能对比；它不代表裸写已经适配 16 个物理库。拆库前仍需按库路由或保持开关关闭。

## 4. 复现命令

```bash
# 1. 本地依赖
docker compose up -d mysql redis

# 2. 应用（压测参数示例；本地库会被 Flyway 迁移）
java -Xms512m -Xmx1g -jar target/newcoupon-server-0.1.0-SNAPSHOT.jar \
  --coupon.issue.worker.initial-delay-ms=30000 \
  --coupon.issue.worker.batch-size=2000 \
  --coupon.issue.worker.batch-tx-size=2000 \
  --coupon.issue.worker.parallelism=2 \
  --coupon.issue.worker.group-parallelism=16 \
  --coupon.issue.worker.raw-bulk-pool-size=4 \
  --coupon.sharding.pool.max-size=40 \
  --coupon.risk.ip-rate.enabled=false

# 3. 建议先跑单测（不依赖本地 compose）
mvn -q -Dtest=AsyncIssueWorkerIntegrationTest test

# 4. 建模板并发布（dev 管理令牌；生产用 ADMIN_TOKEN）
curl -sS -H 'Content-Type: application/json' -H 'X-Admin-Token: dev-admin-token' \
  -d '{"name":"PRESSURE-2K","activityId":900140,"couponType":1,"faceValue":100,
       "threshold":1000,"totalCount":6000,"perUserLimit":1,"validType":1,
       "validStart":"2026-10-20T00:00:00","validEnd":"2026-11-30T23:59:59",
       "dailyLimit":0,"perUserDailyLimit":0}' \
  http://127.0.0.1:8080/api/templates
# 返回 data.id 即 <TPL>
curl -sS -X POST -H 'X-Admin-Token: dev-admin-token' \
  http://127.0.0.1:8080/api/templates/<TPL>/publish

# 5. 2k 受理（用户 id 从 90000000000 起，避免与之前的用户重复）
python3 scripts/load/async_issue_load.py \
  --template-id <TPL> --total 2000 --concurrency 2000 \
  --user-base 90000000000 --request-prefix manual-2k \
  --output /tmp/2k.json
```

库存/日限核对 SQL 见本文第 5 节；券表是 64 张物理分表，按模板统计时要逐表 `SUM`。

### 5.4 worker 最终态：4k 隔离排空

worker 延迟 60 s 启动，先把 4000 条任务灌满，再观察排空（1 s 轮询）：

```text
13:07:47  2000 pending, 2000 processing
13:07:49  0 pending, 2000 processing, 2000 success
13:07:51  4000 success
```

阶段耗时（debug 日志，2000 条一块）：

```text
stock=26ms, build=37ms, coupons=360ms, expire=227ms,
event+outbox=976ms, task=171ms, commit=84ms     -> 约 1.88s / 2000
stock=48ms, build=14ms, coupons=256ms, expire=163ms,
event+outbox=601ms, task=134ms, commit=40ms     -> 约 1.26s / 2000
```

合计约 **3.1 s 清空 4000 条**（≈1.29k task/s）；另一轮预热后两块约 1.07 s + 0.70 s（≈1.6k task/s）。这是本机单实例数字，不是线上 SLA。

### 7.4 证据口径

- 1k/2k/4k 数字是 2026-10-23 本机 WSL2 单次观测，客户端与服务端同机、共享 16 vCPU 与磁盘；不是生产 SLA，也不能直接外推到 5k。
- 延迟分位数为客户端观测，包含排队、服务端处理、响应体读取；不是服务端内部纯执行时间。
- worker 最终态用隔离 4k 的 debug 阶段日志：两个 2000 块合计约 3.1 s（≈1.29k task/s）；另一轮预热后约 1.8 s（≈1.6k task/s）。轮询粒度 1 s，不把它写成精确 SLA；阶段日志是可复算的更强证据。
- 1k/2k 受理吞吐是多次复跑的区间；1k=711–1382、2k=1050–2122 req/s。另有 2k=5208、4k=6033 的预热快照，不纳入保守区间。简历/汇报用“2k 并发全部受理 + 观测约 1.0k–2.1k req/s”比单写某个峰值更诚实。
- 裸 JDBC 批量写是当前“单物理库 × 64 表”的专用快路径；拆物理库后必须重新路由或关闭，见 §3.5。
