## 2. 命令与形态

```bash
make up
CONFIRM=yes bash scripts/stability/dual-instance-smoke.sh
```

脚本行为：

1. 起实例 A（:18091）→ 等健康 → 起实例 B（:18092）→ 等健康；
2. 通过 A 建并发布一个模板（两实例共享库；B 首次访问时从 DB 加载）；
3. 启动 `dual_instance_client.py`：按实例轮转发同步领券（唯一 userId/requestId，每次新建连接，连接阶段失败自动切另一台并计入 failover）；
4. 停 A（SIGTERM）→ 等退出 → 重启 A → 等健康 → 停 B → 重启 B → 等健康；
5. 停流量，读客户端 JSON：5xx / 在途 reset / 业务失败 / failover / 两实例成功数；
6. 查 `Σ coupon_stock_shard.used == COUNT(user_coupon)`。

资源纪律：两实例各 256m；脚本退出时（含 Ctrl-C）停掉两个实例与客户端。

### 3.1 滚动重启时间线

```text
✓ 实例 A 已就绪（:18091, worker-id=0）
✓ 实例 B 已就绪（:18092, worker-id=1）
✓ 两个实例都通过健康检查
✓ 两个实例的 Snowflake workerId 不同（A=0, B=1）
✓ 模板已发布：43
✓ 流量已开始
! 停止 实例 A（SIGTERM，优雅停机窗口 30s）
✓ 实例 A SIGTERM 后在 35s 内退出（实际 209ms）
✓ 实例 A 已重启（:18091, worker-id=2）
✓ 实例 A 重启后健康
✓ 重启后 A/B 的 workerId 仍不同（A=2, B=1）
! 停止 实例 B（SIGTERM，优雅停机窗口 30s）
✓ 实例 B SIGTERM 后在 35s 内退出（实际 208ms）
✓ 实例 B 已重启（:18092, worker-id=0）
✓ 实例 B 重启后健康
✓ 重启后 A/B 的 workerId 仍不同（A=2, B=0）
```

说明：

- **SIGTERM → 进程退出 0.2 秒**：`server.shutdown=graceful` 生效；脚本用新连接、无长轮询，停机时没有需要等满 30s 的在途请求。
- **应用重启（JVM 起到健康）约 30–60 秒**：这段时间该实例不服务，客户端把发往它的请求切到另一台（见 failover 404）。
- **worker-id 变化**：本轮用自动分配（原因见 §5），重启后 A=2、B=0，仍然互异；Snowflake ID 不受影响。

### 3.2 客户端统计（982 请求）

```text
请求=982 成功=982 failover=404 在途reset=0 5xx=0 业务失败=0 双实例不可用=0
按实例成功数：A=481 B=501
```

- `成功=982/982`：所有请求 HTTP 200 + 业务码 0（模板 totalCount=10000，用户唯一）。
- `failover=404`：两次停实例期间，发往已停实例的新连接失败、客户端立刻切另一台并成功——这正是滚动重启期望的流量迁移。
- `在途reset=0`：已建立连接、请求已发出的失败一次都没有；优雅停机没有 reset 在途请求。
- `A=481 / B=501`：两个实例都实际服务过，不是"一个实例全程扛"。

```text
✓ 模板 43 库存守恒（Σused == 券行数；不守恒行数 0）
```

## 5. 本轮发现：WorkerIdLease 关闭时不释放租约（需登记）

**现象**：第一版脚本给两实例显式传 `--coupon.id.worker-id=101/102`。停 A（进程 210ms 退出）后立刻用同一个 `WORKER_ID=101` 重启 A，启动失败：

```text
java.lang.IllegalStateException: WORKER_ID=101 已被其他实例占用
  at com.newcoupon.infrastructure.id.WorkerIdLease.allocate(WorkerIdLease.java:...)
```

观察 Redis：`c:id:worker:101` 在旧进程退出后仍然存在，直到 **60 秒 TTL** 到期才消失（`TTL` 从 ~60 递减）。也就是说 `@PreDestroy release()` 没有在关闭时删掉租约（或删除时 Redis 连接已被拆掉）。`WorkerIdLease` 的注释写的是"关闭时释放"，与实测不符。

**影响**：生产如果用固定 `WORKER_ID` 做滚动重启/重启，新进程会在最长 60 秒内起不来；K8s 滚动更新下会表现为 CrashLoopBackOff/重启变慢。自动分配（不显式配 `WORKER_ID`）不受影响——重启会换一个空闲 ID。

**本轮处理**：遵守"本刀只改 L78 代码"的边界，未改 `WorkerIdLease`；冒烟脚本改为**自动分配** workerId，并新增断言"A/B 的 workerId 互异"（重启后也互异）。建议下个会话修 `WorkerIdLease` 的关闭释放（例如在 `ContextClosedEvent` 里释放、或确认 Redis 连接生命周期顺序），并补一个"启动→关闭→同 ID 再启动"的集成测试。

> 注：V6 计划 5B 还提到 `POST /internal/admin/drain` 先摘流量再 SIGTERM；当前代码没有这个端点（全仓库无 `internal/admin/drain`）。本冒烟验证的是"纯 SIGTERM 优雅停机"这条底线；drain 端点属于后续增强。

## 6. 裁剪与边界

| 项 | 说明 |
|---|---|
| 只压同步领券 | 异步/批量/worker 流量未纳入本轮冒烟；双实例的 worker 协调由既有集成测试与 10-23 压测覆盖。 |
