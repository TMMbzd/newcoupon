## 1. 结论（先看这一节）

| 项 | 实测 | 判定 |
|---|---|---|
| drain 摘流量：实例侧 | health 立即 503（A、B 各验证一次） | ✅ |
| drain 摘流量：LB 侧 | 探针观察到 503 重试列表（`gw:18091, gw:18092` 形状）→ 被动出池 | ✅ |
| 出池确认窗口 | 被摘实例 20/20 窗口内零路由，全部由另一实例 200 服务（A、B 各一次） | ✅ |
| SIGTERM 优雅停机 | A **209ms**、B **209ms** 退出（<35s 判据；上界 30s graceful 窗口） | ✅ |
| 重启回池 | health UP 后 X-Served-By 重新出现本实例端口（A、B 各一次） | ✅ |
| 全程业务流量（经 LB） | 请求 **2134**，成功 **2134**，**0** 5xx，**0** 在途 reset，**0** 业务失败 | ✅ |
| 实例分布 | A=1028 / B=1106（每个成功请求都被 X-Served-By 盖章，Σ=2134） | ✅ |
| LB 视角健康探测 | **72 次探针全部 200**（探测打到被摘实例被 nginx 重试绕开，客户端无感） | ✅ |
| 库存守恒 | 模板 53：Σused == 券行数，不守恒 0 | ✅ |
| 脚本输出 | **DRILL PASS assertions=26** | ✅ |
| 老脚本回归（客户端兼容） | dual-instance-smoke.sh 复跑 **DRILL PASS assertions=18**（1278/1278，failover=541） | ✅ |

**一句话**：流量全走 nginx:8080 后，"drain → LB 出池 → SIGTERM 优雅退出 → 重启 → 回池"
的生产滚动序列对 A/B 两实例各完整走了一遍，全程经 LB 的领券流量零失败；每一步都有
可断言的观测（实例侧 health 码、LB 侧 X-Served-By 路由证据、探针 200 率）。

## 2. 命令与形态

```bash
make up
CONFIRM=yes bash scripts/stability/lb-rolling-drill.sh
```

脚本行为（与老冒烟的差异：流量入口从"两端口直连"升级为"经 nginx 单入口"）：

1. 起 nginx（compose profile `lbe2e`）→ 起实例 A(:18091)/B(:18092) → 直连健康检查；
2. **经 LB** 建并发布模板（顺带验证 LB 的 POST 通路）；
3. 启动压测客户端（单端点=LB 地址，按 X-Served-By 统计每请求实际服务者）
   + 每秒一次经 LB 的 health 探针（模拟 K8s/HAProxy 式主动探测）；
4. 对 A、B 各执行一轮：drain → 实例侧 health=503 → **暂停后台探针后由判定探针
   独占打出让 nginx 记失败**（观察到 503 重试列表）→ 出池窗口 20 个业务 GET 全部
   由另一实例服务 → SIGTERM（计时）→ 重启 → health UP → X-Served-By 重新出现
   （回池）；
5. 停流量/探针，核对：0 5xx、0 在途 reset、0 业务失败、双实例分布、Σ盖章==成功数、
   探针全程 200；
6. 库存守恒 SQL 核对（与老脚本同款）。

资源纪律：两实例各 256m + nginx（~10m）；退出（含 Ctrl-C）停实例/客户端/探针并停掉
演练 profile 的 nginx。

## 3. 原始结果（第 5 轮实跑，全部断言通过）

```text
▶ 4. 滚动重启：先 A 后 B（drain → 出池 → SIGTERM → 重启 → 回池）
  ── 滚动 A ──
  ✓ A drain 后实例侧 health=503
  ✓ LB 已对 A 计失败并出池 30s（探针尝试列表：192.168.65.254:18091, 192.168.65.254:18092）
  ✓ A 出池窗口内 20 个业务请求全部 200 且无一路由到它（合格 20/20）
  ✓ A SIGTERM 后在 35s 内优雅退出（实际 209ms）
  ✓ A 已重启（:18091, worker-id=2）
  ✓ A 已回池（实际服务者：192.168.65.254:18091）
  ── 滚动 B ──
  ✓ B drain 后实例侧 health=503
  ✓ LB 已对 B 计失败并出池 30s（探针尝试列表：192.168.65.254:18092, 192.168.65.254:18091）
  ✓ B 出池窗口内 20 个业务请求全部 200 且无一路由到它（合格 20/20）
  ✓ B SIGTERM 后在 35s 内优雅退出（实际 209ms）
  ✓ B 已重启（:18092, worker-id=3）
  ✓ B 已回池（实际服务者：192.168.65.254:18092）
▶ 5. 停止流量与探针，核对统计
  ✓ 请求=2134 成功=2134 在途reset=0 5xx=0 业务失败=0 LB不可达=0
  ✓ 按实例成功数（X-Served-By 聚合）：A=1028 B=1106（盖章总数 2134）
  ✓ LB 健康探针：72 次，非 200 共 0 次
  ✓ 模板 53 库存守恒（Σused == 券行数；不守恒行数 0）
```

worker-id 全程：A=0→2、B=1→3（Redis 租约自动分配，重启不撞车——老脚本已验证的既有语义）。

## 4. 三轮假红换来的三个修正（值得留档的排障记录）

### 4.1 标记权竞态（run 1/2：roll B 总是"观察不到重试列表"）

被动摘除只认"打到失败实例的请求"。后台探针（1/s）在 drain 与判定函数开跑之间的
空档抢先打到 503，"失败标记"就归了它；判定函数自己的探针从此只看到单地址响应，
25 秒等不到重试列表。两轮都在 roll B 复现（roll A 纯属侥幸通过）。
**修正**：判定函数进入前先 `touch` 暂停文件暂停后台探针（暂停要早于 drain 调用），
health 流量全程归判定探针独占——"谁打的 503"从概率事件变成确定事件。

### 4.2 客户端自旋放大器（run 3：3679 个 502 ≈ 950 rps × 4s）

客户端失败迭代之间不休眠，"连接秒失败"让它以 ~950 rps 自旋，把几秒的 LB 故障
放大成每秒近千请求的洪峰（nginx 访问日志实测）。**修正**：失败迭代退避 100ms——
压测客户端不许在故障窗口放大故障。

### 4.3 Docker Desktop host-gateway 的新建连接停滞（run 3/4 的根因）

法证手段：给 nginx 访问日志加 `up=$upstream_addr`，配合探针日志时间线，确认 502
全是 `up=newcoupon`（**no live upstreams**——两台都被动了标记）而非应用错误。
隔离实验（无 Java、无负载，容器 wget 打宿主 python http.server 2500 次）：

```text
FAIL at req 664 after 46s      FAIL at req 1636 after 125s
FAIL at req 817 after 68s      FAIL at req 2043 after 183s
                                  FAIL at req 2310 after 210s
DONE i=2500 fails=6            ← ~0.25% 新建连接停滞 >12s，与 Java/nginx 无关
```

结论：容器→宿主唯一通道（192.168.65.254 用户态代理）对**新建连接**有随机停滞率；
每请求新建连接=每请求抽签，抽中→connect 超时→好实例被被动摘除误伤→双实例同时
出池→no live upstreams。容器直连宿主 eth0（172.23.97.x）不通（SYN 被丢），换路无门。
**修正**（生产上本来就是最佳实践，不只是本机补丁）：
① upstream `keepalive 16` + `Connection ""`——建连接从每请求一次降到池化复用；
② `proxy_connect_timeout 10s`——几秒级停滞"慢而不败"（端口关闭是 RST 秒拒，
死实例检测不受拖累）；③ 探针/curl max-time 提到 15s、客户端 --timeout 30s、
`proxy_next_upstream_timeout 25s` 对齐预算。修正后第 5 轮全绿（§3）。

### 4.4 顺带修的

- run 2 发现疑似客户端残留过 cleanup（storm 在 cleanup 后仍在打 POST 10 秒）：
  cleanup 增加 `pkill -f "dual_instance_client.py.*lb-drill-$RUN_ID"` 兜底；
  根因未完全定位（客户端日志为空、无进程残留佐证），兜底后未再复现。
- 客户端兼容性：老冒烟（双端点直连 + failover 语义）复跑 **DRILL PASS assertions=18**
  （1278 请求 / 1278 成功 / failover 541 / 零失败），证明单端点与 X-Served-By
  统计是纯增量改动。

| | dual-instance-smoke.sh（保留） | lb-rolling-drill.sh（新） |
