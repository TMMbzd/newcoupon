## 2. 第二轮：25-agent 审查整改（C1/C2/C3/C5/C6）

### C1 [critical] 事务内 4007 不钉占用单 → 双重优惠

- 红：T1 追加断言（拒绝后 `timeoutClose` 必须 false、占用单必须 `CONFIRM_EXCEPTION`），
  修复前失败（实际仍是 OCCUPYING，超时任务会 true + TIMEOUT_CLOSED）。
- 绿：`TradeAppService` 事务调用外新增 `BizException` 出口，4007 时
  `markConfirmExceptionQuietly`；T1 通过。L64 复算的 4002 保持可重试、不钉（裁定）。
- 命令：`-Dtest='L75ConfirmToctouIntegrationTest#siblingReleaseInWindowRejectsSnapshotConfirm'`
  → 红 EXIT=1（expected CONFIRM_EXCEPTION）→ 绿 EXIT=0。

### C2 [major] 两线程证明事务内行锁真实存在

- 用例 T7：A 在"锁行之后、`casConfirm` 之前"挂起（`CouponUsageRepository` spy），
  B 并发释放 sibling；断言 500ms 时 B **未完成**，放行后两者都成功。
- 变异自检：临时把 `ORDER BY id FOR UPDATE` 改成 `ORDER BY id` → T7 红
  （`Expecting value to be false but was true`，B 立即完成）；恢复后绿。
- 结论：锁是真实的数据库行锁，不是注释论证。分片路由按 `user_id` 等值单分片、
  索引 `(user_id, order_no)`（V21 `idx_user_order`）；同分片多行按 id 升序申请。

### C3 [major] 事务层幂等重放

- 用例 T8：纯旧式金额路径（无 pricingId/items，编排层不短路）——目标券已核销、
  兄弟券已退款，重放必须返回 `duplicated=true`，而不是售后 4002。
- 变异自检：临时把 duplicated 判断移到售后/集合校验之后 → T8 红（4002）；
  恢复后绿。证明事务层 duplicated 分支确实被执行且顺序正确。

### C5 [minor] 跨租户同 user+orderNo 误杀

- 用例 T10：租户 A 与 B 使用同一 userId + 同一 orderNo，A 退款后 B 旧式核销
  必须成功（`coupon_usage` 无 app_id，锁集合会捞到两租户的行）。
- 红：修复前 B 收到 4002"订单已进入售后"；绿：新增 `sameTenantUsages`（按目标券
  `user_coupon.app_id` 过滤兄弟行）后成功。

### C6 [minor] 部分退款分支 + 文档数字

- 用例 T9：窗口内 sibling 被**部分退款**（PARTIALLY_REFUNDED），confirm 必须按
  售后 4002 拒绝。变异自检：临时从 `assertNoAfterSales` 去掉 PARTIALLY_REFUNDED →
  T9 红（退化为 4007 券集合）；恢复后绿。
- 数字核实：ADR **22** 份；迁移 **43** 个（最高 **V49**，版本号有跳号）；
  `AsyncIssueWorkerIntegrationTest` 实际 **27** 例（surefire 报告）；
  OpenAPI 基线 **28 path**（C4 定向新增 3 条后重新生成）。

## 4. 口径

- 红/绿是**同一份测试代码**在两个实现版本/变异版本上的输出；修复只改生产代码 + 单测 mock 签名适配。
- 窗口注入用 `@SpyBean` 包住 `prepareConfirm` / `calculateForOrderConfirm`：真实方法返回后、
  事务开始前执行 sibling 释放/退款；比两线程交错更可控。
- 行锁证明用第二条独立线程（T7）+ 摘锁变异，避免"测试自身就在事务里所以当然串行"的假绿。
- 全量 `mvn clean test` 由收尾人执行；本文件只覆盖 L75/C4 与相关回归面。
