## 第 0 部分：预备知识（读完这页，后面全能看懂）

### 0.1 术语表（每个词一句话白话解释）

| 术语 | 白话解释 |
|---|---|
| Lua 脚本/原子 | Redis 执行一段脚本期间不插入任何其他人的命令——脚本里的多个读写像一个不可分割的动作 |
| 预占（deduct） | 用户请求"过闸"的原子动作：可领数量减 1，同时发一张"在途令牌"记下是谁的请求 |
| 在途令牌（pend） | 一条小记录"用户 u 的请求 r 已扣库存、数据库还没定案"，带进闸时间。存在一个有序集合里 |
| 守恒式 | `可领 + 在途 + 已发放 + 已撤销 = 总投放量`。每一张券任一时刻必然处于四种状态之一，所以四个数加起来必须等于总量——对账就是验这个等式 |
| 清扫 | 每 60 秒，把超过 180 秒还没定案的令牌删掉。删掉的瞬间，被进程崩溃藏起来的账面差额就暴露了——这是"检测"的实现方式 |
| dbi（镜像计数） | Redis 里记"数据库已确认发放了多少张"的计数器。镜像检查 = 拿它和数据库的真实数字比 |
| T+1 审计 | 每天凌晨数一遍用户券明细表的行数，和账本核对——这是数据库内部自洽性的最后检查 |
| 漂移 | 守恒式不相等了，说明某个数字错了 |
| 白名单 + CAS 栅栏 | 自动修复前必须同时满足的 5 个条件；"栅栏"= 动手前再原子地核对一遍"我做决策时看到的数字没有被别人改过"，对不上就放弃 |
| so 标志（停流牌） | 售罄或下线后立的一个牌子，新请求在脚本第一行就被弹回，不再消耗任何资源 |
| REBUILD·NX / FORCE | 两种修复：NX=库存键整个丢了之后的重建（只在键不存在时写）；FORCE=账错了之后按数据库口径重置（有五条件守卫） |
| 热行 | 被所有请求争抢的那一行数据库数据。本项目里=券模板表的那一行（每个成功领券都要更新它的"已发放数"） |
| CAS（条件更新） | "比较并交换"——`UPDATE ... WHERE 已发放数 < 总量` 这样的 SQL，条件不满足就更新 0 行，靠这个保证绝不超发 |
| 线性一致 | 所有操作看起来像按某个顺序、一次一个地执行。Redis 单主节点上的脚本是天然满足的；主从切换丢写之后就不再满足 |
| epoch | Redis 主节点的一个"任期"。主从切换=换了任期，旧任期末同步的写入可能丢 |
| RTO / RPO / MTTR | 出事后恢复服务要多久 / 恢复时丢多少数据 / 平均修复耗时 |
| QPS | 每秒请求数 |
| bus factor | "被公交车撞了项目就瘫痪"的人数。1 = 只有你一个人懂 |

### 0.2 方案三分钟白话版（ADR-0009 在做什么）

**领券的写入分两步、跨两个系统**：第一步在 Redis 里原子地"预占"（可领量减 1、发一张在途令牌）；第二步在 MySQL 的事务里落券（条件更新模板行 + 插入券明细 + 唯一索引兜底）。第二步成功就"confirm"（已发放数+1、令牌销账），失败就"cancel"（按失败原因决定：瞬时故障把可领量加回去，售罄/下线则把额度永久退休进"已撤销"并立停流牌）。

**为什么不一步到位**：数据库那一行是所有请求争抢的热行，5000 QPS 直接打上去会串行排队（我们实测过 2000 并发撞连接池）。Redis 闸门先用内存速度挡掉超量请求，数据库只处理过闸的请求。代价是两步之间可能"卡在半路"（进程崩溃、网络断），所以要记账和对账。

**对账三层**：①守恒巡检（每 60 秒验一次四数之和=总量，不等=有错）；②镜像检查（dbi 和数据库真实已发数比，方向性地判"Redis 多记了"还是"少记了"）；③T+1 审计（每天数明细表行数对账本）。修复是"窄域自动"：五个条件全过才自动修，其余只告警留人工，且有总开关可一键关掉自动修复。

**这次面试要拷问的就是它**。

## 第 2 部分：答辩实录

### 面试官 A：交易库存资深架构师（9 题）

**A1 ❌"你的'单模板 2 万 QPS'这个数怎么来的？"**
考点：能不能区分"借来的数字"（素材文章里字节的 2 万）和"自己链路的数字"。
**我的回答**：这题我答砸了，且是方案里的**真实口径错误**。ADR-0006 写"吞吐升至 Redis 单分片量级（约 2 万 QPS）"——但每个成功请求仍要对模板**同一行**做条件更新，这行锁要持有到事务提交。我们自己阶段 0 的诊断就写着"单行行锁串行，天花板数百 QPS"，阶段 1 只是把**读校验**挪去了 Redis，**写热点还在同一行上**。所以诚实的公式是：**有效发放上限 = min(Redis 单分片上限, 数据库单行提交速率)**。单行"一次更新+两次插入+提交"持锁约 0.5~2 毫秒（取决于磁盘刷盘），单行天花板量级是 1k~5k TPS——5000 QPS 目标贴着刀口，"2 万"是把 Redis 的上限错当成了链路的上限。**已修**：撤回该声明（ADR-0006 加勘误横幅）；解热行的候选路径（分段增补=数据库一次加 N 张额度、写放大降为 1/N；或把模板计数拆成 N 行子计数随机扣）登记为 M3 压测的决策项；压测前不再宣称任何 QPS 数。

**A2 ⚠️"你所有键全挂 {tpl} 一个 hash tag——100 万用户来抢时，100 万个用户限领键 + 300 万个幂等键全钉在最热的那个分片上，内存账算过吗？还有'分桶就绪'就绪什么？"**
考点：hash tag（让一个模板的所有键落同一分片、保证 Lua 原子的代价）的真实成本账；"就绪"是不是改个键名就叫就绪。
**我的回答**：内存账没算过，现在算：幂等键数 ≈ QPS × 600 秒存活 = 5000×600 = **300 万个活键**，单键约 100 字节 ≈ **300MB，钉在一个分片上**——比在途令牌（常态约 100 个成员）大三个数量级，幂等键的 TTL 才是内存的第一旋钮。分桶：诚实承认"key schema 就绪"的说法**已失真**——守恒式、巡检 Lua、FORCE 推导全是"单模板五键同分片"的结构，分桶后守恒域变成"模板×桶"（每桶独立的五键+桶间调拨要作为显式转移记账），巡检要么按桶验、要么跨桶聚合验（跨分片=放弃单 Lua 原子），这是一次 ADR 级变更不是配置变更。**已修**：ADR-0009 v3 头部加"适用边界"条款（见 D6）；300MB 内存账与"用户维度键是否该改挂 {uid}"列为 M3 分桶设计的第一题。

**A3 ⚠️"现在把 Redis 整个拔了，用户看到什么？"**
考点：故障叙事有没有推到"Redis 没了"，而不只是"Redis 抖了"。
**我的回答**：用户看到全部领券请求 500。闸门调用在 try 块之外，异常直接穿透成系统错误——**没有熔断、没有降级开关**。而且有个更细的洞：数据库撞唯一键冲突后要调 cancel 归还 Redis，此时 Redis 也挂着，cancel 在 catch 块里再抛一次，把本该返回的"重复领取"也打成 500。我的立场辩护：**fail-fast 是决策不是疏忽**——直接降级成"纯数据库扣减"会把热行打回阶段 0 的数百 QPS 并可能雪崩，正确降级是"限流到数据库单行水位再放行"而不是全量直扣；但这个降级开关一行代码都没有、债表里也没登记，这就是疏忽。**已修**：①降级开关+哨兵的优先级排序登记进债表（哪个先做：先降级开关后哨兵，因为 SLA 99.95% 折算月错误预算约 22 分钟，单点 Redis 无高可用必然击穿）；②catch 内二次故障要 try 住补偿、保住业务语义（令牌交给 180 秒清扫兜底）。

**A4 ❌"你的在途令牌集合上界是多少？最坏形态算过吗？"**
考点：检测机制自己会不会变成故障放大器。
**我的回答**：完全没算过，这题暴露得漂亮。常态：在途数 ≈ QPS × 数据库时延 ≈ 5000×20ms ≈ 100 个成员，没问题。**最坏形态**：如果 confirm 系统性丢失而 deduct 一直成功（数据库 IO 尖刺 180 秒），在途集合 = 5000×180 = **90 万个成员，约 100MB 的大键钉在最热分片上**；然后 60 秒巡检的清扫一把删 90 万个成员——Redis 单线程，这一下卡住分片几百毫秒到秒级，**我的检测器自己变成了故障**。**已修**：①清扫分批（每次最多删 N 条，循环执行）；②在途集合规模阈值告警（超过常态 10 倍就报，别等 TTL 自然暴露）；③把这条"自伤上界"写进认账条款——"拿破坏当检测信号"的设计自带这个代价，权衡后仍值得，但必须有量化的自伤上界。

**A5 ⚠️"为什么恰好四个状态？void 这个最可疑——它的终值由修复公式定义，这不就是你自己骂过的'为凑公式造的会计科目'吗？"**
考点：状态机划分的第一性原理辩护能力。
**我的回答**：四态是总投放量在"发放生命周期"上的**穷尽无交划分**：每张券要么还能领（可领）、要么被某个请求攥着没定案（在途）、要么发出去了（已发放）、要么被运营/售罄退出了流通（已撤销）。少第四态会怎样？售罄/下线时那批额度只能**加回可领**（闸门重开，正是被否决的 N1 环）或**凭空蒸发**（守恒永久破）——所以 4 是下限，v1 的"污染洗白进 void"P0 恰是第四态写错时的活证。void 的疑点我认一半：它混装了"售罄退役"和"下线退役"两种语义事件，且修复时会被推导公式重置——辩护是：**重置不是发明业务事件，是把"已撤销 = 总量 − 其余三态"这个推导关系重新对齐**（撤销数本来就是可由独立事实推出的派生量）；但混装语义的代价真实存在。**已修**：ADR 明确"守恒域=发放生命周期"（用户侧过期/核销/退券不动发放守恒是业务规则，不是遗漏）；void 拆成两个键的触发条件写进边界条款。

**A6 ⚠️"你们自己的设计文档推荐过腾讯云式'分段增补'（数据库一次批 N 张、写放大 1/N），落地时被无声绕开了——推翻自己推荐的决策记录在哪？"**
考点：方案替换时有没有留下对比记录（ADR 的本职），有没有量化过恢复目标。
**我的回答**：没记录，这是流程违规。补上真实理由和账：分段增补的优点=热行写放大降到 1/N、Redis 蒸发时损失有界（≤ 当段大小）；缺点=段耗尽时热路径多一次同步数据库往返（尾部延迟）、段间不均衡、以及**与我们的每请求落库叠加后收益缩水**——我们每个成功请求本来就要插一行券明细（这笔写躲不掉），条件更新只是同一事务里多一次同行更新，边际成本很低，所以选了"全量配对"换取"任意时刻可验账"。代价就是 A1 的单行漏斗——两题合并成一个决策表。**已修**：分段增补 vs 全量配对的对比表（含 RTO/RPO 定量）写进 ADR-0009 v3，作为 M3 压测后的正式决策项；方案级 RTO/RPO 目标（检测≤120 秒、找回≤流量间歇、丢失上界=崩溃在途数）成文。

**A7 ✅"腾讯云否决了同步落库，你偏要每请求同步走完，数据库一抖这个同步链路的尾巴有多长？"**
答得住：同步/异步取舍在 docs/03 有带数字的完整对比（字节靠分片扛同步 vs 腾讯云异步+本地事务表），裁定"做成开关、默认同步、大促可切异步、共用同一套对账底座"，触发点 M3 压测；数据库劣化时的检测者=瞬时取消率 5 分钟熔断告警（v2 专门为"守恒全程绿灯的纯劣化段"加的）。待补的只有 P99 预算分解表和"取消率告警触发→切异步"的联动，已列入 v3。

**A8 ⚠️"自动修复要求'在途已清'——5000 QPS 持续流量下这道门可能永远过不去。高流量模板漂移 6 小时修不了，这个窗口你认吗？"**
考点：控制面的"活性"——不只是不错（安全性），还得最终能做成事（活性）。
**我的回答**：认。持续流量下修复饥饿真实存在，量化：过闸概率随流量指数下降，5000 QPS 时基本要等流量间歇。两个补充手段：①**短流修复协议**——修复前主动立停流牌几秒钟，制造"在途清空"的确定性窗口，修完按清除协议恢复（本质是拿秒级可用性换确定性修复，这是老手才会的取舍，该进设计语言）；②总开关关闭期间，挂起的破缺信号要有"起点/终点"语义（漂移日志加未结/已结状态），否则下次人来看时分不清历史残留和活故障。**已修**：两条都进 v3；"修复是拿可用性换一致性，默认在低峰做"写为设计原则。

**A9 ✅"主从切换丢的恰好是一段预占的效果——五本账整体退回扣减前，守恒式绿灯，你怎么发现？"**
答得住，这是全套设计的正典回答：守恒式是**和式不变量，对整体平移结构性失明**——但被污染的可领量放行多余请求后，数据库条件更新硬顶（零超发），被拒请求走分类→判售罄→钉零+立牌，环被掐死；检测信号=瞬时/售罄取消率熔断告警。一句话版："**守恒式管'和'，数据库管'绝对值'，取消率管'时序异常'——三层正交**"。

### 面试官 B：分布式原理拷问者（8 题）

**B1 ⚠️"先讲性质：'零超发'挂在哪个对象上、什么一致性模型下成立？五键转移是线性一致的吗？你们路线图红线写着'超领=0'，可日限只有 Redis 计数——红线和认账哪句是真的？"**
考点：能不能把含糊的"最终一致"按对象拆开说清。
**我的回答**：按对象分四层——①**总量零超发**：由 MySQL 单行条件更新给出，是"对已提交事务"的不变性质，**与 Redis 无关**（Redis 全错也不破它，Redis 全失效时系统退化为行锁串行、安全性质不变）；②**五键转移**：同分片+Lua 串行 ⇒ 主节点任期内全序（等价单对象线性一致）；异步复制下主从切换可丢已确认的整个效果集（Redis≥5 按效果复制、不会半撕裂），丢失=守恒按整转移破缺→巡检检出→修复收敛。诚实表述："**任期内线性一致，跨任期最终一致且破缺有界可检测**"；③**总限领**：数据库唯一索引兜底（同级别硬保证）；④**日限**：只有 Redis 计数、无数据库防线，主从切换丢一个计数=日限超领 1 张。**红线表述确实过头了**。**已修**：红线改写为"总量超发=0（数据库保证）；总限领=0（唯一索引保证）；日限=概率性，主从切换下敞口=丢失的计数数，靠 noeviction+主从写安全参数收窄"——写进路线图和 ADR。

**B2 ✅"守恒式是定理还是约定？隐含公理一条条列出来。有没有'补偿性双错'——两处反向等量污染让和恰好相等？"**
答得住：它是闭式转移系统上的**归纳定理**（转移表=归纳步骤，发布重置=归纳基础；例外是在途全清库的重建近似，已认账）。公理清单五条：键空间封闭（唯一写者）、总量只经协议变更、令牌恰入恰出（成员带用户和请求号、重复添加不双计）、脚本效果集复制原子（整丢=可检测破缺而非静默半写）、检查器独立于被检对象（总数/已发数取自数据库且确认步新鲜重读）。**补偿性双错确实存在**（可领和已发放各错 ∓1 使和相等、守恒绿灯）——这正是三层正交的理由：**守恒管"和"，账实相符是镜像层的责任**，dbi 对不上数据库真实数时镜像层接住。这句话 v3 里明写。

**B3 ⚠️"180 秒 TTL 你说'物理锚定'——锚的数字是 60 秒档还是代码注释里的 50 秒？3 倍系数是推导的还是拍的？DBA 明天把锁等待调到 120 秒，你的 180 秒就开始误清扫活请求——这个配置耦合登记在哪？"**
考点：'物理锚定'是修辞还是机制。
**我的回答**：被抓住自相矛盾——ADR-0008 写"60 秒档"、代码注释写"50 秒默认"、配置文件里根本没显式配锁等待参数，3 倍系数无推导。修正为机制：**公式=排队时延 + innodb_lock_wait_timeout（真实默认 50 秒）+ 事务余量，180 秒=50×3 的工程估计（系数来源=锁等待队列深度上界的估计，M3 压测后校准）**——承认是估计不是定理；**启动期校验**：应用启动时读数据库的锁等待参数，若 2×锁等待+余量 > TTL 则告警并强制提升 TTL——把配置耦合从"文档默契"变成"启动断言"。另认一个残留：v2 把令牌时间戳改用 Redis 服务端时钟了，但**日键还是应用机的本地时钟**——跨零点的误差上界=实例间时钟差，方向有界，登记为已知项。

**B4 ⚠️"为什么不用 2PC/TCC/Saga？别拿'性能差'一句话打发我。"**
考点：分布式事务选型的原理级对比。
**我的回答**：四点，此前确实从未成文——①**2PC 结构性不可行**：它要求参与者暴露"预备/提交"两阶段接口（XA 资源管理器），Redis 的 Lua 效果集没有"预备持有"这个概念——**在 Redis+MySQL 组合上 2PC 连讨论对象都不存在**，性能是次要论据；②**本方案=TCC 去掉事务管理器**：Try=预占记账（不是锁！），Confirm/Cancel=业务动作；协调者（应用进程）死亡的成本=1 个预占单位×180 秒，由 TTL 没收+审计修复收敛——**等价于用"超时默认决策+审计器"替换了 TM 的日志**；③**cancel 的非逆性=Saga 的语义补偿**：售罄分支退休进"已撤销"而不是原样归还（业务语义已变），Saga 的"无隔离性"缺点被我们的显式在途状态补了一层可观测的隔离；④**为什么用券不用这套**：用券是单数据库内的事务（状态机+条件更新=本地 ACID），领券是因为 5000 QPS 引入了第二个存储才需要跨资源协议——**协议选择=资源管理器数量 × 吞吐需求，不是口味**。已修入 v3。

**B5 ✅"dbi 是数据库的镜像，却由业务写者维护——镜子自己给自己作证？为什么不用 binlog/CDC？递归论证走到哪层闭合？"**
答得住（这是此前评审里反复锤炼过的）：CDC 镜像=再引入一个最终一致副本（Canal+MQ+消费幂等一整套新故障模式），**对账的对象不能是"另一个副本"，必须是事实源本身**；检测器闭合于"直接读主库+方向性判据"；零误报的偏序论证（confirm 的 dbi+1 严格晚于其提交的 ic+1，故新鲜 ic 下 dbi≤ic 恒成立）成立且前提（新鲜读在 Lua 读 dbi 之后）已写明。

**B6 ⚠️"'最终一致'的'最终'是多久？每类不一致摊开：检测时延、修复时延、期间业务后果。用户'领取成功'后立刻查券包，读写分离后看得到吗？"**
考点：把"最终一致"从口号变成可度量的收敛表；用户可见一致性（read-your-writes）有没有想过。
**我的回答**：数字都有但从未拼成一张表，现在拼（v3 成文）——dbi 滞后：检测≤120 秒、修复需在途清空（持续流量下推迟，30 分钟未修即告警）、**期间用户级后果=零**（用户资产在数据库里，错的只是 Redis 记账）；可领量污染：检出≤120 秒+修复即时，期间少卖=污染量（有界）；崩溃残留：180 秒暴露+流量间歇找回，期间少卖 1 张；日限计数丢失：债 L3，用户被误拒至自愈上线；主从切换余量虚高：数据库拒绝、体验退化、零超发。**用户可见一致性**：单库期天然满足（写读同库）；M4 读写分离后，领券走主库、券包查询若走从库=毫秒级最终一致，"读己之写"需显式路由读主（设计已有、未与 ADR 勾稽）。已修入 v3。

**B7 ✅"巡检一边验账一边销毁证据（先删过期令牌再求和）——'任意时刻成立'在清扫那一瞬间成立吗？两种残留在清扫后长得一模一样，归因靠什么？"**
答得住：准确命题是"**除受控清扫外任意时刻成立；清扫是唯一的合法破缺，其差值即检测信号**"——这是特性不是缺陷；归因分层=守恒层只报"有差额"这一个比特，区分形态靠镜像判据（数据库已发−dbi>0=confirm 丢失→修 dbi；相等=Redis 侧损坏→修可领量）；修复目标按形态分叉且必须分叉（v1 的洗白 P0 正是把两者混了的教训）。

**B8 ⚠️（时钟权威的代价追击）**：v2 把时间权威交给 Redis 服务端时钟是对的，但要认两笔账：①Redis 宿主机的时钟健康成了全局前提（它漂了所有人都漂）——NTP 从"建议"升级为"Redis 宿主机必配"；②日键残留应用机时钟（见 B3）。已修入 v3 认账。

### 面试官 C：SRE 生产运维专家（8 题）

**C1 ❌"你 ADR 里'告警'出现了二十多次——半夜两点，哪一条告警通过什么通道到达我？说实话，是不是一行 log.error 躺在没人看的日志里？"**
考点：告警是一个端到端系统（检测→分级→通道→认领→超时升级），不是日志打印语句。
**我的回答**：说实话：**是 log.error**。当前所有"告警"（守恒漂移/镜像/升级/熔断）的终点都是日志文件，STATUS 债表自己也写着"仅日志，运维盲飞"。ADR 把"检测语义"和"告警投递"混为一谈了——检测做完了，没有人被叫醒，等于检测没做完。**已修**（三件事）：①ADR 里每类告警标注分级（立即叫醒级：账实矛盾、幻影确认；工单级：推迟、囚禁；周报级：限频后的常规漂移）和**M2 告警通道建成前的过渡方案**——最小可行告警提前到本次实施：一个每 10 分钟跑一次的检查任务，查漂移日志表近 1 小时有无"已修复/升级"记录，有就发通知（哪怕是本地通知），让"分钟级暴露"在 M2 之前就兑现到"有人知道"；②告警文本自带处置手册链接和日志查询号；③"升级人工"必须指明升级给谁、多久未认领再升级谁。

**C2 ⚠️"'零误报'是定理不是运维事实——生产真响了一条假的，你怎么收场？凌晨三点运维手动 SET 了一下库存，你的零误报还成立吗？"**
考点：数学论证和运行时事实的区别；人为干预（最大的真实误报源）有没有被建模。
**我的回答**：论证只覆盖"无外部非协议写"的前提，而**人工改 Redis 恰是第一误报源**，我们目前只靠运行手册一行字"人工调低必须先立停流牌"——纪律不是机制。**已修**：①人工操作唯一合法入口=带存活时间的"维护标记键"（巡检见标记即豁免数轮并注明），纪律变协议；②漂移日志加"处置结果回填"字段（真异常/误报/人工操作）——精确率从不可度量变成可度量；③上线前两周告警只观察不升级，统计真实触发量后再定通道策略。

**C3 ⚠️"主从切换丢了写，2000 个模板同时漂移——接下来 10 分钟我会收到几条通知？两千条还是一条？限频计数器在应用内存里，扩到 4 个实例限频还作数吗？只增不删的日志表三年后多大？"**
考点：告警系统在最需要它的时刻（大面积故障）的噪音上限。
**我的回答**：会收到**每小时 2000 条日志+2000 行表**——没有跨模板聚合，这是真实的噪音灾难。**已修**：①聚合告警：单轮确认漂移的模板数超阈值（>5 或 >1%）时发一条"疑似全局事件"并自动抑制单模板告警；②限频与升级计数全局化——落到 Redis 键上（顺带解决多实例重复落表把"24 小时 5 次"升级阈值按实例数加速失真的问题）；③日志表生命周期：在线 90 天+按月归档，"不可修复态"改用持续事件（一条带起止时间）而不是每小时新行。

**C4 ⚠️"凌晨一点运营误操作清空了 Redis——第一小时你怎么过？讲操作序列，不要讲机制。"**
考点：恢复机制有没有翻译成人能执行的事故剧本。
**我的回答**：机制层是全套方案最强的（清库后零人工介入可用性恢复：预占撞"未初始化"→退避→懒重建，确认丢失由镜像 2-3 分钟收敛）——但**人的剧本一页都不存在**。**已修**：事故剧本成文（docs/runbook/redis-data-loss.md）：第 1 分钟确认是误清还是故障切换（决定要不要停写）→第 5 分钟决定是否临时限流（依据：用户限领计数归零=全量用户重新过闸，撞唯一索引的请求全打到数据库，等于一次计划外压测——连接池够不够要有数）→第 1 小时盯数据库压力+验证清单（巡检一轮全绿、日志表只剩确认丢失类修复、审计抽查）→对老板证明完整性的三件证据（巡检全绿+审计互证+修复日志可回放）。

**C5 ⚠️"自动修复某天夜里做错了事——你怎么把 Redis 恢复到修复前一分钟？日志里存了修复前读数，然后呢，有回放工具吗？"**
考点：审计留痕 ≠ 可回滚。
**我的回答**：留痕是认真的，但**日志表是黑匣子不是时光机**——"从前读数一键恢复五键"的运维端点不存在，出事后只能现场手写命令，而手写本身就是非协议写、会触发下一轮对抗。**已修**：①管理端点"从日志前读数一键恢复"（走同一段 Lua、带维护标记）；②**连续 2 次修复后仍漂移→自动停用修复**（熔断自己的修复环，防止修复-漂移-修复循环烧日志）；③修复事件触发一条即时通知，让值班知道"系统刚自己动了手术"。

**C6 ⚠️"总开关改一次要重启？四个实例滚动重启中间两个开两个关？自动修复上线第一天就默认开，你的影子模式呢？"**
考点：急停开关的真实可用性 + 自动修复的上线策略。
**我的回答**：三处都是真的——开关是静态配置（改=发版重启）、多实例滚动窗口内行为分裂、**默认开且从没被真实流量打过**。**已修**：①开关落 Redis 全局键（分钟级生效、多实例一致、"任一实例关=全员不修"的最保守语义，顺带解决热更）；②上线序列：**先影子模式跑 1-2 周**——修复推导照常计算、值只落日志表不执行，与实际漂移比对零异常后再开真修；③翻转子=一次变更大事，双人确认+自动落审计事件（这条 v2 已有）。

**C7 ⚠️"noeviction 钉死之后内存满了那一刻呢？预占脚本直接报错，全模板领券一起挂——你监控 Redis 内存吗？还有你代码注释写着'三本账随 TTL 自然消亡'——你查过那几个键到底有没有 TTL 吗？"**
考点：正确性决策（不许逐出）的可用性代价有没有配套；注释与实现矛盾（考真实掌握程度）。
**我的回答**：**那行注释是错的**——状态键全部裸 SET、没有 TTL，永不消亡，一万场活动后 Redis 里留一万个模板的僵尸键。这是"注释撒谎"+缓慢内存累积双重问题。**已修**：①修注释（或给退役模板的键补过期）；②容量预算成文：幂等键≈300MB 是大头（见 A2）、用户限领键=活跃模板×领过券的用户数×7 天、状态键=每模板 5 个永久键——据此定内存水位线（70% 工单、85% 叫醒，M2 第一批告警就该是它，排在一切业务告警前面）；③满载预案：可牺牲的只有幂等键（丢它=幂等退化到数据库终审，安全），日限键**不能**丢（丢了=超发方向），预案="批量删幂等键+立即扩容"写成脚本。

**C8 ❌"谁监视监视者？巡检线程哪天死了——什么都不发生。审计连续三天没跑，你会发现吗？一张空表和'一切正常'长得一模一样。"**
考点：检测系统自身的存活检测（对账系统的人必问）。
**我的回答**：**完全没有**。巡检死亡、异常被吞、调度配错——系统静默失去全部对账能力，而"每 60 秒被验证"和"从没人验证"在所有输出上不可区分。审计任务更是只有失败分支有告警、"今天没跑"无人检测——**缺勤比失败更沉默**。**已修**：①巡检心跳：每轮成功后写带存活时间的心跳键（3×巡检周期），心跳过期=一级告警；②审计成功也落一条当日摘要，"连续 2 天无摘要"=告警；③设计原则入 ADR："**每层检查必须自带心跳，静默=最危险故障**"。

### 面试官 D：技术总监兼 HR（8 题）

**D1 ⚠️"算笔账：数据库条件更新已经把超发锁死了，你这套东西防的全是'少卖几张'。命令你砍掉一半——砍哪半？每砍一层损失什么？折成钱是多少？"**
考点：能不能量化自己设计的边际收益，敢不敢做减法。
**我的回答**：先捅破窗户纸：**零流量阶段这套的生产投资回报是负的**，它的真实价值=资损红线的保险费+能力建设。砍序（v3 成文）：**第一刀关自动修复**（总开关一关降级为纯告警，损失=修复耗时从分钟级变成值班小时级——而且告警通道还没建，当前自动修复的真实收益本来就趋近零）；**第二刀简化 T+1**（与守卫④的账实互证重叠，留每日一条 SQL 即可）；**永远不砍的**：守恒巡检+方向性镜像——因为"三本账整体平移"只有镜像的"dbi>数据库已发"臂能抓、崩溃残留只有令牌+清扫能精确归位，全量重建无法区分"在途"和"丢失"。最后的诚实：数据库双防线在，最坏是少卖不是资损——**这套的定位是体验与运营效率，不是资损保险**。

**D2 ⚠️"3 个后端接手，第二周有人要给 cancel 加一个新变体——他得读几份文档、动几处代码才能安全上线？你怎么保证他不犯 v1 那个'污染洗白'的错？"**
考点：单人作品如何变成团队资产；文档可读性被第二个人验证过吗。
**我的回答**：安全网存在但不成体系：转移表每行带守恒效应列、13 项集成测试矩阵、新增变体必须"先补一行转移表+一条守恒推导+一条测试"——v1 的洗白错误正是被"污染可领量→售罄终止→修复归零"的钉死测试当场抓住的。缺的三样都认：①**变更检查单**（新转移要同步动的六处：Lua 脚本/巡检/镜像/修复推导/测试矩阵/日志表列）没有成文；②文档可读性**从没被第二个人验证过**（这份答辩文档就是第一次为人写的尝试）；③"新键必须说出业务事件"的门禁是口头纪律，应进化成 CI 检查（用对账思想治理自己的代码：Lua 脚本里的键清单 vs 注册表自动比对）。**已修**：三件都进 v3。

**D3 ⚠️"五天三个范式，且三次翻车全是外部评审抓的——是你不可靠，还是流程优秀？v2 为什么就是终态？"**
考点：个人可靠性与流程依赖的区分；设计有没有"退出标准"。
**我的回答**：拆开归因——**范式级盲区 100% 靠红队、实现级 Bug 有自己的测试矩阵抓的记录**（跨语言字符串失配被验收⑨的钉零断言当场抓住），两者的记录都在；单人的范式盲区是结构性的（你在自己的推理框架里看不到自己的框架），所以把红队**写进流程而不是当拐杖**——流程即产品。翻新成本低是因为生产前——上线后再推翻 ADR 才是真事故。但"为什么 v2/v3 是终态"确实没有标准，**已修**：冻结条件=①状态空间穷举论证②测试矩阵全绿③故障演练（杀进程/清库/逐出三类实操）把数学变成观测行为——三条全过才冻结；之后再改范式必须新开 ADR 重走红队。

**D4 ✅"这项目最失败的设计决策是什么？"**
答得住（这题是全项目答得最好的）：首答 ADR-0008 的 issued 键——病根是"先写恒等式再造状态"，违反业务建模的基本顺序；防复发已落成可执行门禁（新键必须说出业务事件）。成本侧补认：92 个测试三天作废，在学习项目是三天学费、在公司就是一个团队冲刺加一次信任损耗——所以教训不是"下次想清楚"而是"范式决策必须过对抗评审才能实施"，把防复发押在流程上，不押在"我下次更聪明"上。

**D5 ✅"重来一次，你会第一天就上这套吗？给你逃生机会：只留'扣减+数据库条件更新+每小时全量重建'，把四本账全扔——推一个故障场景证明令牌集合不是装饰品。"**
答得住：进程死在"预扣之后、数据库提交之前"——无令牌方案里这个缺口在 Redis 侧只表现为可领量少 1，**和"数据库还在锁等待里排队"不可区分**：全量重建=把一个可能还在途的请求名额抢走（或者不敢重建，等一小时）；带令牌的方案在 180 秒清扫后**精确知道"这个用户这个请求没人认领"**，修复精确回补 1 张。再加镜像独有捕获：cancel 误吞已提交事务是"整体平移"，守恒式瞎的，只有镜像抓——**每本账都有一个只有它能抓的故障类**，这就是不可约性。诚实收尾：第一天不会上全套（先扣减+双防线跑起来），账本是被真实故障签名逼出来的——但按"先定状态再写公式"的顺序重走，能直接到 v3，少绕两个弯。

**D6 ❌"你的方案保质期：M3 分桶时守恒巡检当场作废吧？M5 异步化后你 180 秒的物理锚点跟行锁有半毛钱关系？ADR 里为什么一个字不提？"**
考点：敢不敢写"我的方案什么时候会被我自己推翻"。
**我的回答**：没想到，也不该不写。**已修**（v3 头部加"适用边界与失效条件"）：①**M3 分桶触发时**：守恒域从"模板"变"模板×桶"，巡检 Lua、修复推导、转移表全部要按桶重设计——这是 ADR 级变更，触发即新开 ADR；②**M5 异步发放启用前**：在途 TTL 必须重新锚定到"消息队列端到端延迟 P99+重试预算"（行锁锚点作废），cancel 分类多出"消息死信"形态；③binlog 驱动镜像作为已论证的等价演进选项登记（监控基建到位后可替换应用侧 confirm）。

**D7 ⚠️"你 STATUS 里白纸黑字'无告警通道'——那这套检测机制现在真实的收益兑现率是多少？还有四个 P0 挂在'已提出'的 ADR 里等排期——你的 P0 响应纪律是什么？"**
考点：宣称收益与运行现实的落差；已知带伤的主干。
**我的回答**：自己捅破：**告警通道建成前，"分钟级暴露"的兑现率≈零**——暴露了也只写进一张表和日志，等人肉翻。所以过渡告警（见 C1）必须提前到本次实施。P0 纪律：四个现行 Bug 里至少两个（confirm 被抹账、跨天日键）**与范式无关、可以当天热修单独提交**——选择捆绑迁移是排期权衡却从未论证，这是错的。**已修**：P0 热修走独立通道（本周期即做），范式相关的修复才随迁移；规则成文："P0 修复永远有独立通道，不被 ADR 评审排期绑架"。

**D8 ⚠️"最后一道优先级题：你的券过期（L2，资损）和锁定超时（L5，资产悬挂）都标了'M1 立即无条件'，然后你把一周全花在对账范式的三轮翻新上。为什么最性感的分布式问题排在实际资损缺口前面？敢承认有一半是'挑有意思的做'吗？"**
考点：机会成本意识——招资深时最看重的题，答"完美"直接扣分。
**我的回答**：可辩护的一半：对账范式评审**正是发现那四个 P0 的过程**（包括会抹账的 Bug），且范式修复与 P0 修同一批代码，捆绑落地省一次全量回归——停下来反而留险。不可辩护的一半：**是的，有四成是我想做有意思的**——从范式定稿（09-11）到 v2 打磨（09-12）的边际投入，确实挤占了无条件"立即"级的资损债。**已修**：顺序修正为"P0 当天热修 → L2/L5（过期+锁超时）→ ADR-0009 迁移"，写进路线图并给自己立规矩：债的严重级排序是硬约束，插队要在路线图上留痕说明理由。

## 结语

四位面试官共同确认了一件事：**这套方案的正确性内核（四状态守恒+三层正交检测+数据库终审）在第四轮外部攻击下依然成立**；被打穿的全部是它与世界接口的地方——容量口径、告警投递、人的剧本、方案保质期、投入产出。这符合一个规律：**系统内部的数学靠设计，系统与现实的接缝靠工程纪律**——后者没有一劳永逸，只有一项项补。
