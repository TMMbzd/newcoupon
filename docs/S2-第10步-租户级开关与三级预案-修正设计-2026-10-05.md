## 1. 审查改变了什么（先看这一节）

审查的价值不在"补充细节"，而在**推翻了两个前提**——两个都不是第 10 步引入的缺陷，而是前面阶段就埋着的，
第 10 步会直接踩上去。

### 1.1 缺陷①：熔断器认不出最常见的 Redis 故障形态（**必须修，否则演练脚本跑不通**）

**症状链**（可复现，已实测）：

```
docker pause redis  →  TCP 连接还在、命令无响应
  →  Lettuce 等超时，抛 io.lettuce.core.RedisCommandTimeoutException（内层）
  →  Spring Data Redis 把它翻译成 org.springframework.dao.QueryTimeoutException（外层）抛给应用
  →  熔断白名单里登记的是【内层那个】，外层这个不在白名单
  →  熔断器失败计数恒为 0，永远不打开
```

**证据**：
- 白名单 7 项见 [DependencyCircuitBreakers.java:103-110](../src/main/java/com/newcoupon/infrastructure/resilience/DependencyCircuitBreakers.java#L103-L110)
- 日志实测：`org.springframework.dao.QueryTimeoutException` 在真实故障中出现 **119 次**（`logs/newcoupon.log`）
- **继承链用反射独立复核**（`/tmp/s2step10/HierarchyProbe.java`）：`QueryTimeoutException` 的祖先是
  `TransientDataAccessException → DataAccessException`，与白名单里的 `TransientDataAccessResourceException`
  是**兄弟类**，7 项白名单**一项都不匹配**
- 审查方另用探针实测：连喂 6 次 `QueryTimeoutException` → `state=CLOSED, failed=0`；
  直接喂内层 `RedisCommandTimeoutException` → `failed=5, state=OPEN`。**Resilience4j 只按抛出类匹配、不沿 cause 链**

**两个后果**：
1. **演练脚本的核心步骤做不成**——"注入故障 → 观察熔断打开"不会发生
2. **生产上更严重**——"Redis 挂起"（`docker pause` / 主从切换：TCP 在、命令不响应）**恰是熔断最该保护的形态**，
   现在完全不设防，每个请求都卡满超时后才失败

**为什么既有测试没抓到**：现有绿灯用例喂的是**合成异常** `SocketTimeoutException`
（[DependencyCircuitBreakerIntegrationTest.java:146-151](../src/test/java/com/newcoupon/integration/DependencyCircuitBreakerIntegrationTest.java#L146-L151)），
恰好是白名单里有的那一类。**"用了真实异常形态"和"用了白名单里有的异常"是两回事**。

### 1.2 缺陷②：三个缓存的 TTL 全部算错（防雪崩 / 防穿透失效）

`Expiry.expireAfterCreate` 的契约是返回**持续时长**（duration），Caffeine 内部自己会加 `now`。
但三处实现都写成了 `return now + 时长`——把绝对时刻当成了时长，于是 Caffeine 算成 `now + (now + 时长)`：

> 缓存项真实存活时间 ≈ **JVM 已运行时长 + 配置的 TTL**

| 文件 | 引入阶段 | 失效的防护 |
|---|---|---|
| [CachedTemplateReader.java:67](../src/main/java/com/newcoupon/application/service/CachedTemplateReader.java#L67) | P2c | 防穿透（负缓存短 TTL）+ 防雪崩抖动 |
| [CachedOpenAppReader.java:71](../src/main/java/com/newcoupon/application/service/CachedOpenAppReader.java#L71) | S1 | 同上 |
| [CachedTenantConfigService.java:71](../src/main/java/com/newcoupon/application/service/CachedTenantConfigService.java#L71) | S2 第 1 步 | 同上 |

**证据**：
- 权威契约：Caffeine 官方 javadoc "removed from the cache once **the duration** has elapsed after the entry's creation"；
  源码 `setVariableTime(created, expireAfterCreate(...))` 显示内部自行加 `now`
- **一手实测**：TTL 设 1000ms 的探针，跑到 t+4400ms 时 `loads` 仍为 1（**从未重新加载**），
  条目一直没过期 → `/tmp/s2step10/probe.log`
- 后果：JVM 跑 1 小时 → 缓存项活 1 小时 60 秒；跑 1 天 → 活 24 小时。负缓存（"这个模板不存在"）长期不失效
- 缓解事实（同样实测）：`refreshAfterWrite(30s)` **是有效的**（探针里 `loads` 正常递增），所以有流量时陈旧值最多存活约一个 refresh 周期

## 2. 四个已拍板的决定（2026-10-05）

| # | 问题 | 决定 |
|---|---|---|
| D1 | 预案作用域 | **按租户**——接口挂 `/api/apps/{appId}/plans/{level}`，复用现成存储/审计/隔离，天然受管理面令牌保护。不做"真·全站"（那需要新增一层动态全局覆盖存储，登记为后续项 L58） |

## 3. 前置修复 P（两个缺陷）

### 3.1 P1：熔断白名单改为"沿原因链匹配"

**做法**：把 `recordExceptions(Class...)` 换成 `recordException(Predicate<Throwable>)`，
谓词**沿 `getCause()` 链**匹配下面这组类：

```java
DataAccessResourceFailureException / TransientDataAccessResourceException
QueryTimeoutException                                   // ← 新增：Lettuce 命令超时的真实形态
RedisConnectionFailureException / RedisSystemException   // ← 新增后者：连接中断形态（日志中 709 次）
io.lettuce.core.RedisConnectionException / RedisCommandTimeoutException
SocketTimeoutException / TimeoutException
```

**为什么用谓词而不是简单往清单里加一项**：往清单里加 `QueryTimeoutException` 只能修"命令超时"这一种形态；
而沿原因链匹配能一次覆盖**当前已知与将来新增**的包装形态，且**不误伤**——审查方已实测：
`RedisSystemException(cause=RedisCommandExecutionException 脚本错误)` → `CLOSED`（不计入），
`QueryTimeoutException(cause=lettuce timeout)` → `OPEN` ✓

**注意**：`recordException(Predicate)` 与 `recordExceptions(Class...)` 互斥（后者会覆盖前者），不能同时写。

**红灯**：用**真实异常形态**喂熔断器——`new QueryTimeoutException("...", new RedisCommandTimeoutException(...))`
——断言熔断器打开。当前代码下它保持 CLOSED（红）。

### 3.2 P2：三处 Expiry 去掉多加的 `now`，并补读取失败兜底

**做法**：
```java
// 改前：return now + TimeUnit.NANOSECONDS.convert(jitter(...), TimeUnit.MILLISECONDS);
// 改后：
return TimeUnit.NANOSECONDS.convert(jitter(...), TimeUnit.MILLISECONDS);
```
三处同改。`expireAfterRead` 返回 `currentDuration`（读不续命）本来就是对的，不动。

**配套——读失败兜底**（修复 TTL 后行为会变：硬过期 + DB 故障时，首个读会**抛异常**而不是拿到旧值）：

| 位置 | 兜底 |
|---|---|
| `CachedTenantConfigService.load` | 捕获 `RuntimeException` → 记 WARN → **返回空 Map**（等价于"该租户没有任何配置"→ 全走默认值），不让 DB 抖动穿到调用方 |
| `SwitchService` 的租户层读取 | 再包一层 try/catch → WARN → **跳过租户层**，回落全站层/默认 |

第二层兜底不是冗余：`SwitchService` 挂在**全路径拦截器**上，它读配置失败会让**所有接口**失败——
开关这个"保命"组件绝不能自己变成故障放大器。

**红灯**：把缓存 TTL 压到 ~300ms，断言"过期后重新加载"（当前代码下永不过期 → 红）。

### 3.3 P0（不修，但要知道）：`CachedTemplateReader` 的负缓存治理

TTL 修好后，负缓存（"这个模板不存在"）会开始**真的按短 TTL 过期**——这是它本来就该有的行为，
但意味着"查不存在的模板"的回源次数会比之前多（之前永不失效，等于永久挡着）。
本项目已有 create/publish 主动失效兜底，判定为**行为回归到设计意图**，不改逻辑。

## 4. 主体 A：租户级开关

### 4.1 三层取值

```
租户层（open_app_config: switch.receive.enabled）   ← 有则用（最具体）
    ↓ 没有
全站层（coupon.switch.receive.enabled，S1 已有）
    ↓ 没有
默认 true（开关是"出事时关"，不是"上线时开"）
```

**判据实现（必须用可空原始值，禁止 `getBool`）**：

```java
public boolean isOn(SwitchKey key, String appId) {
    // ① 租户层——仅当有 appId（内部面/定时任务没有，见 §4.4）
    if (appId != null && !appId.isBlank()) {
        String raw = readTenantRawQuietly(appId, key);   // 读失败 → null（兜底见 §3.2）
        if (raw != null) {
            return parseBoolOrTrue(raw, key);             // 值非法 → true + WARN
        }
    }
    // ② 全站层
    String global = environment.getProperty(key.propertyName());
    if (global != null) {
        return Boolean.parseBoolean(global.trim());
    }
    // ③ 默认
    return true;
}
```

**为什么"值非法 → true"而不是 false**：沿用本项目"读宽容"的立场（S2 第 1 步三条铁律第 2 条）。
写入时已严格校验（非法值根本写不进去），运行时出现非法值只可能是有人手工改库——那种情况下
**保持现状（开）比静默关闭核心接口安全**，并且 WARN 要显眼到能被发现。

### 4.2 两套词表对齐（否则 `switch.*` 写不进库）

**问题**：租户配置的写入校验基于 `TenantConfigKey` 枚举（`fromKey` 精确匹配，未登记就整体拒绝）。
开关清单是另一个枚举 `SwitchKey`。今天 `PUT switch.receive.enabled` 会被拒。

**做法**（审查给的方案，只改两处校验入口）：

1. 新增小接口 `ConfigKeySpec { String configKey(); String description(); String validate(String); String defaultValue(); }`
2. `TenantConfigKey implements ConfigKeySpec`——加一行 `configKey()` 返回 `key()`
3. `SwitchKey implements ConfigKeySpec`——加 `configKey()` 返回 `"switch." + key`；
   `validate` 只接受 `true`/`false`；`defaultValue()` 返回 `"true"`
4. 新增 `SwitchKey.fromConfigKey(String)` 反查
5. `CachedTenantConfigService` 的 `put` / `remove` 两处校验改为**先查 `TenantConfigKey` 再查 `SwitchKey`**
6. `TenantConfigService` 新增 `String getRaw(String appId, String configKey)`——未配置返回 `null`、
   **不做任何解析与回落**（三层取值靠它区分"配了 false"与"没配过"）

**为什么不把 8 个开关复制进 `TenantConfigKey`**：两套清单必然漂移——漏复制一次，租户覆盖就静默失效；
拼错一个键，语义永远读不到。而 `SwitchKey` 的立论本身就是"清单是给运维的说明书"，复制会毁掉这个性质。

### 4.3 只读视图要给出"来源"

`SwitchView` 增加 `source` 字段（`TENANT` / `GLOBAL` / `DEFAULT`）：

```java
record SwitchView(String key, String description, boolean on, boolean configured, String source)
```

**为什么必须有**：加入租户层之后，`on=false` 到底来自哪一层从返回值看不出来——
排障路径会重新变长（"我明明配了怎么没生效"）。`configured` 只说明"全站层配过没有"，不够用。

### 4.4 内部面与定时任务的语义（明确的不对称）

| 路径 | appId | 生效层 |
|---|---|---|
| `/open/**` | 有（认证后写入 `RequestContext`） | **三层全用** |
| `/api/**` | `null`（`RequestContext.EMPTY`） | **只用全站层** |
| 定时任务（如 `OutboxDispatcher`） | `null` | **只用全站层** |

**这条不对称必须写进代码注释与管理面文案**：否则运维以为"租户级关闭"对内部面也生效，
在故障中会据此得出错误结论。同时修正 `WebMvcConfig` 里"拦截 `/**`"那段注释（它现在的说法会误导人）。

## 5. 主体 B：三级预案

### 5.1 模型：一组 `(键, 目标值)`

```java
record PlanEntry(String configKey, String targetValue) {}

enum SwitchPlan {
    BLUE  ("蓝", "预防：收一收，不影响体验"),
    YELLOW("黄", "局部降级：关非核心，保核心"),
    RED   ("红", "保命：只保留发券与用券 + 收紧限流");
}
```

**全量物化**（决定 D2 的配套）：每份预案对**全部已接线的开关**显式声明目标值（true/false），
这样"黄→红"与"直接套红"结果一致，不会留残影。

**已接线 = 有真实执行点**，只有这 6 个：
`RECEIVE` / `TRADE_LOCK` / `TRADE_CONFIRM` / `TRADE_RELEASE` / `TEMPLATE_PUBLISH`（5 个 HTTP 注解）
+ `OUTBOX_DISPATCH`（定时循环里的 `isOn`）。

`REDIS_DEPENDENCY` 与 `MESSAGE_CHANNEL` **全库无消费方**——进预案等于"套用成功但什么都没变"。
**处理**：在 `SwitchKey` 上标记未接线，且有单测断言"预案里的每个键都已接线"，
新增开关时若忘了接线，这条单测会红。

**预案内容**（限流阈值给的是占位值，实施时按本机容量校准）：

| 级别 | 开关 | 配置 |
|---|---|---|
| 蓝 | 全部 6 个 = `true` | `rate_limit.warmup_seconds=60`（打开预热）、`rate_limit.qps`=保守上限 |
| 黄 | 核心 4 个 = `true`；`template.publish` = `false`；`outbox.dispatch` = `false` | — |
| 红 | 核心 4 个 = `true`；其余 = `false` | `rate_limit.qps` = 更紧的上限 |

### 5.2 套用与恢复（快照补偿）

**套用** `apply(appId, plan, operator, reason)`：
1. 校验预案每一项都能解析（键已登记、值合法且已接线）——**先全部校验**
2. 读当前每个键的旧值（含"原本不存在"= null）→ 组成**快照**
3. **在一次事务里**：写入一行 apply 记录（含快照 JSON）+ 批量写配置（复用 `put` 的"先校验后写"）
4. 审计：逐键 `old→new` 落 `open_app_config_log`（复用），**且只在值真的变化时写**（幂等）
5. 套用新预案时，把该租户**上一条 status=1 的记录置为 3（被取代）**

**恢复** `revert(appId, operator, reason)`：
1. 取该租户当前 `status=1` 的 apply 记录
2. **CAS 式回滚**：逐键判断"当前值是否仍等于预案写入的值"——是则恢复为快照值（快照值为 null 则删除该项），
   否则**跳过并计入冲突数**
3. **单事务**完成（严禁 M 次 `remove` 循环——中途断电会留下半恢复状态）
4. 记录置 `status=2`，`reverted_at=now`；冲突数写进响应与日志

**为什么是 CAS 而不是无条件回滚**：运维可能在这期间手工改过某个键——那是**人的意图**，
机器不该覆盖它。跳过 + 报告冲突把决定权交回人手里。

### 5.3 新表（V16）

```sql
CREATE TABLE open_app_plan_apply (
  id          BIGINT UNSIGNED AUTO_INCREMENT,
  app_id      VARCHAR(32)  NOT NULL,
  plan_level  VARCHAR(16)  NOT NULL COMMENT 'BLUE / YELLOW / RED',
  operator    VARCHAR(64)  NOT NULL,
  reason      VARCHAR(128) DEFAULT NULL COMMENT '备注（演练脚本传 drill，便于与人工操作区分）',
  snapshot    TEXT         NOT NULL COMMENT '套用前快照（JSON：{"键": 旧值 或 null}）',
  applied_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  reverted_at DATETIME(3)  DEFAULT NULL,
  status      TINYINT      NOT NULL DEFAULT 1 COMMENT '1=生效中 2=已恢复 3=被新套用取代',
  PRIMARY KEY (id),
  KEY idx_app_status (app_id, status)
) COMMENT='预案套用记录（S2 第 10 步：快照补偿回滚的依据）';
```

**为什么需要预案级记录**：键级审计（`open_app_config_log`）能回答"这个键被谁改成什么"，
但回答不了"**我当时想套用哪份预案、应该改哪几个键、原值是什么**"——恢复与复盘都需要这个上下文。

## 6. 主体 C：演练脚本

### 6.1 顺序（**审查修正后**——故障期间不能走开放面）

```
① 前置检查：BASE 必须是 loopback；容器在跑；/actuator/health 可达；自建演练租户 A、B（drill- 前缀）
② 基线：A、B 各自 receive → code=0
③ 注入故障：docker pause newcoupon-redis
④ 观察（**走内部面** /api/coupons/receive）：
     轮询 → 断言先见 5000（依赖超时），再见 5001（熔断打开）
⑤ 恢复故障：docker unpause → 轮询直到 code=0（**必须轮询，不能睡固定值**）
⑥ 套用黄预案（租户 A）→ 行为验证：
     A: publish=5001 且 message 含"券模板发布开关"（证明预案生效）
     A: receive=0（证明核心链路仍可用）
     B: publish=0（证明租户隔离）
⑦ 恢复预案 → A: publish 回到 0
⑧ 打印 PASS/FAIL 与断言数
```

**两个关键修正**：
- **故障期间走内部面**：Redis 一挂，`/open` 的 nonce 检查 fail-closed 先拒（属**有意的**安全行为，不改）
- **开关验证放在恢复之后**：故障期间核心链路本来就不可用，"核心链路仍可用"没有验收对象

### 6.2 护栏（缺一不可）

| 护栏 | 防的是 |
|---|---|
| `trap cleanup EXIT INT TERM`（幂等：unpause + 恢复开关 + 验证） | 脚本中途失败/Ctrl-C/**断电**（本项目刚真实发生过）留下 paused 的 Redis 与被关的开关 |
| 前置检查 BASE 是 loopback（除非 `ALLOW_REMOTE=1`） | 对着共享环境误跑 |
| 必须显式 `CONFIRM=yes` | 手滑 |
| 状态文件（appId / 快照 / 进度），启动时发现残留即拒绝 | 断电后重跑时状态不明 |
| 请求总量控制在 30 次以内 | 触发 IP 频控（60s/30 次）把演练自己掐死、与熔断现象混淆 |
| 审计 `reason=drill` | 事后复盘分不清演练与真人操作 |

### 6.3 沿用现有脚本体系

`source lib.sh`（**签名只有一份实现**）、每步 `expect` 断言而非打印、`Makefile` 加 `drill` 目标。
新增的 `admin_put` / `admin_post` 两个管理面 helper 也加进 `lib.sh`，避免第二套实现。
