## 1. 先说清楚：什么叫"不阉割"

用户的要求是"避免阉割"。这句话在本次迁移里有**精确含义**——下面这张表里的每一行，
迁移后都必须仍然成立；哪一行做不到，就是一处语义损失，必须显式记录而不是悄悄丢掉。

| # | 现有能力 | 判定 | 靠谁兑现 |
|---|---|---|---|
| 1 | 租户 QPS 限流（按 appId） | ✅ 保持 | Sentinel FlowRule（`limitApp=appId`）+ **集群模式**保证跨实例精确 |
| 2 | **日配额（自然日重置 + Retry-After=到明天）** | ✅ 保持 | **自建**（官方规则模型表达不了——见 §3.1） |
| 3 | **IP 维度精确限流** | ✅ 保持 | **自建**（官方热点参数是 LRU 近似且容量不可配——见 §3.2） |
| 4 | 接口维度限流（平台级） | ✅ 保持 | Sentinel FlowRule（资源名，1.8.7+ 支持正则） |
| 5 | **429 契约**（业务码 + Retry-After + 维度名） | ✅ 保持 | **自建** BlockExceptionHandler（官方默认是 429 + 纯文本） |
| 6 | **fail-open + 可观测**（依赖故障放行且打点） | ✅ 保持 | **自建**（Sentinel 没有这个概念，且它的静默放行路径**全都没有指标**——见 §3.3） |
| 7 | 治理指标进 Prometheus | ✅ 保持 | **自建** MetricExtension → 项目现有 MeterRegistry（官方**没有 micrometer 适配器**） |
| 8 | 冷启动预热 | ➕ **新增**（原来只有 initialTokens 起步少放） | Sentinel `WARM_UP`（`warmUpPeriodSec`，`coldFactor` 是 JVM 级全局配置） |
| 9 | 匀速排队（漏桶） | ➕ **新增**（S2 曾决策不做） | Sentinel `RATE_LIMITER`（`maxQueueingTimeMs`） |
| 10 | 系统自适应保护 | ➕ **新增** | Sentinel `SystemRule`（BBR：`capacity = maxSuccessQps × minRt / 1000`） |

**第 8~10 行是这次迁移真正的收益**：它们正是 S2 阶段被我以"太复杂"为由砍掉的能力。
但要提前知道两条边界（官方源码级核实）：

- **预热与匀速排队只对 `grade=QPS` 生效**，非 QPS 时会被**静默降级**为快速失败。
- **集群模式下这两项失效**——源码 `ClusterFlowChecker` **完全不读 `controlBehavior`**，
  集群只支持"秒级滑动窗口 + 立即拒绝"。
  所以 §5 的部署设计里，**需要预热的资源走单机规则，需要跨实例精确的资源走集群规则**，
  两者不能同时要（这是本次设计的核心张力，见 §5.3）。

## 2. 架构总览

```
                       ┌─────────────────────────────────────────┐
   /open/**  请求 ───► │  OpenApiAuthFilter（认证，写 RequestContext）
                       ├─────────────────────────────────────────┤
                       │  ContextUtil.enter("open-api", appId)   │ ← origin = 租户身份
                       ├─────────────────────────────────────────┤
                       │  Sentinel Slot Chain（官方 SPI）         │
                       │   ├─ FlowSlot        ← 租户 QPS / 接口维度
                       │   ├─ ParamFlowSlot   ← （不用它做 IP，见 §3.2）
                       │   ├─ SystemSlot      ← 系统自适应
                       │   └─ DailyQuotaSlot  ← **自建**：日配额（§3.1）
                       │      IpExactSlot     ← **自建**：IP 精确（§3.2）
                       ├─────────────────────────────────────────┤
                       │  BlockExceptionHandler（**自建**）        │ ← 429 契约（§3.4）
                       └─────────────────────────────────────────┘
                                        │
              ┌─────────────────────────┼─────────────────────────┐
              ▼                         ▼                         ▼
      MySQL: open_app_config    Redis（自建 Slot 的计数）   Token Server（集群精确）
              │                                                  ▲
              └── 自建 DataSource ──► FlowRuleManager ───────────┘
                  （§4）              （规则全量替换）
```

**四个"自建"组件**是本设计的重点，官方文档里没有现成做法，但**官方都提供了扩展点**
（`ProcessorSlot` / `SlotChainBuilder` / `ReadableDataSource` / `MetricExtension` / `BlockExceptionHandler`），
所以做法是"用官方 SPI 实现"，不是"绕开 Sentinel 另起一套"。

## 3. 三处自建补足（官方做不到的部分）

### 3.1 日配额（自建 `DailyQuotaSlot`）

**为什么官方做不到**（源码级）：

- `FlowRule` 的 `grade` 只有 `QPS` / `THREAD`，QPS 的统计窗口是**秒级滑动**（默认 2×500ms 桶）——
  **没有任何日窗口的表达能力**；
- 而且 `TrafficShapingController` **不可插拔**（`FlowRule.setRater` 包私有、`FlowRuleUtil.generateRater` 是 `private static`），
  所以也无法通过自定义 Controller 扩展。
- `ParamFlowRule.durationInSec` 看似能配 86400，但实现是"窗口内固定预算 + 窗口一过补满、
  **锚点漂移、非墙钟对齐**"——它给出的不是"次日 0 点重置"，而是"从第一次请求起 24 小时"。
  这与我们现有的**自然日语义**和 `Retry-After=到明天的秒数` 都对不上。

**做法**：实现官方 `ProcessorSlot<Object>`，挂在 Slot Chain 上，内部沿用现有的 Redis 计数：

```java
public class DailyQuotaSlot extends AbstractLinkedProcessorSlot<Object> {
    @Override
    public void entry(Context ctx, ResourceWrapper resource, Object param, int count,
                      boolean prioritized, Object... args) throws Throwable {
        // 只对"开放面聚合资源"生效；其余资源直接放行给下一个 slot
        if (OPEN_API_RESOURCE.equals(resource.getName())) {
            String appId = ctx.getOrigin();
            int limit = /* 从租户配置读，与今天同一套 resolveLimit 逻辑 */;
            if (limit > 0 && !dailyQuotaAllows(appId, limit)) {   // Redis INCR + 次日 0 点过期
                throw new DailyQuotaBlockException(appId, secondsUntilTomorrow());
            }
        }
        fireEntry(ctx, resource, param, count, prioritized, args);   // 必须调用，否则链断
    }
}
```

**要点**：
- **必须 `fireEntry`**，否则整条链断掉（官方 SPI 的硬要求）；
- 抛的异常要能带出 `Retry-After`（自定义 `BlockException` 子类，见 §3.4）；
- 挂在链上的位置：**在 `FlowSlot` 之后**（先让 Sentinel 的规则拦，再轮到自建的），
  用 `SlotChainBuilder` SPI 装配。

### 3.2 IP 维度精确限流（自建 `IpExactSlot`）

**为什么不用官方的热点参数**（源码级）：

- `ParamFlowRule` 用 **LRU** 统计，容量是 `min(4000 × durationInSec, 200000)`，
  常量 **`private static final`，不可配置**（官方文档与 `csp.sentinel.*` 配置项里都查不到它）；
- **超出容量即淘汰，淘汰即该值的令牌状态丢失** → 被限的 IP 会"复活"；
- IP 是**请求方可控的无界维度**，用 LRU 做安全防线在原理上就不合适。

**做法**：同样用 `ProcessorSlot`，内部沿用现有的 Redis 精确计数（与日配额同一个模式）。
**这会多一次 Redis 往返**——这是"要精确"必须付的代价，在文档里记明。

### 3.3 fail-open 与可观测（自建打点）

> **⚠️ 本节在第 7 步被调研修正过**（原文的"做法"写的是"用 `MetricExtension` SPI 对接现有
> `MeterRegistry`"）。核实之后发现**那是错的**，改动理由见本节末尾的"修正记录"。

**Sentinel 的静默放行路径**（源码级核实，第 7 步又补了第 6 条）——它们的共同点是
"请求照常通过，而限流判定其实没生效"：

| 路径 | 行为 | 有指标吗 | 第 7 步怎么让它可见 |
|---|---|---|---|
| ① Slot Chain 数超 `MAX_SLOT_CHAIN_SIZE`（6000） | **新资源拿不到链**：不检查、不统计、不报错、**零日志** | ❌ | gauge `coupon_sentinel_slot_chain_count`（`CtSph.entrySize()`，public static） |
| ② `Constants.ON = false`（全局开关） | 连链都不建 → 全部放行（**我们的自建槽位也不执行**） | ❌ | gauge `coupon_sentinel_enabled`（`Constants.ON`，public static volatile） |
| ③ `CtSph` 内部异常 | `catch (Throwable)` 记一行它自己的日志后**照常返回 Entry**（放行） | ❌ | **链头看门狗槽位**：接住下游冒上来的 Throwable → 计数 `coupon_sentinel_internal_error_total` → 原样重抛 |
| ④ 规则源拉取失败 | 保留旧规则（fail-static），只记它自己的 INFO | ❌ | 我们的数据源自己 catch + `coupon_ratelimit_failopen_total{dimension="rule_source"}`（第 3 步已做，第 7 步接进指标） |
| ⑤ 集群 Token 失败 | 按 `fallbackToLocalWhenFail` 回退或放行 | ❌ | **留到第 9 步**（`ClusterTokenClient#getState()` 做就绪 gauge） |
| ⑥ **context 名超 `MAX_CONTEXT_NAME_SIZE`（2000）** → `NullContext` | 与 ①② 同样直接放行、零可见（第 7 步核实补录） | ❌ | 与 ② 同一条思路：本项目 context 名只有 2 个，超限只可能来自 bug（靠 gauge/断言兜） |

**另一条比"看不见"更危险的路径**（第 7 步新发现，不属于上面六条）：

| 路径 | 行为 |
|---|---|
| 规则源**读回空列表 / null** | `AutoRefreshDataSource` 只在 `loadConfig()` **抛异常**时才保留旧规则；空列表会一路推到 `FlowRuleManager` **把规则整表清空** → **所有租户静默不限流**（实测 rules 2 → 0） |

**做法**（第 7 步实际落地的四件小事）：
- **规则源空结果守卫**：`readSource()` 读到"登记表一行都没有"时**抛异常**（走 fail-static 保旧规则）
  并打 `failopen{rule_source}`；"租户行存在但全停用/全不限"仍按**合法的空**推送（拦它们会把
  运维的正常操作冻住，见 `TenantFlowRuleDataSourceTest`）；
- **链头看门狗槽位**（`SentinelWatchdogSlot`）：唯一能看到链内异常的位置——把 `SphU.entry`
  包一层是**没用的**（异常在 `CtSph` 内部就被吞了，调用方拿到的是正常 Entry，实测复核过）；
- **两条 gauge**（`SentinelSelfMetrics`）：`coupon_sentinel_enabled`、`coupon_sentinel_slot_chain_count`；
- **把已有但没人消费的信号接进指标**：数据源的 `LOAD_FAILURES`、
  `TenantFlowRuleMapper.dropped()`（预检丢弃的规则数——原来在唯一调用点被扔掉，等于白预检）。

**修正记录（第 7 步，2026-10-08）——原计划的 `MetricExtension` 为什么不能用**：
1. **它一条静默路径都看不到**（实测：填满 6000 条链后新增资源事件增量为 0；`ON=false` 后事件为 0）。
   它的定位是"把每次调用的统计事件外送"（pass/block/rt/exception/线程数），不是"防线失效告警"；
2. **它比看不见更危险**：扩展方法抛出的异常会被 `LogSlot` **静默吞掉**，
   直接让"拒绝"变"放行"（探针实测：`addBlock` 里抛异常之后，`count=0` 的规则不再拦人；
   连 SPI 文件写错一个类名都会让**所有请求放行**，只有一行 WARN）。
   把 Micrometer 的 meter 注册放在这种热路径上，等于给所有限流加了一个"可能静默全放行"的开关；
3. 它还会把 `BlockRejection` 已经定好的"维度/Retry-After/业务码"映射复制出第二个事实来源。

所以**拒绝的打点保持在出口 `BlockRejection`（唯一契约来源），故障的打点保持在发生处**——
这个分工是对的，第 7 步没有改它，只是把原先没有打点的几条路径补齐。
（另：官方确实有 JMX 与 Prometheus 的 exporter，但都是**拉模式**、且都不是基于 `MetricExtension`；
**没有 micrometer 适配器**。我们不需要它们——`/actuator/prometheus` 已经在导了。）

### 3.4 429 契约（自建 `BlockExceptionHandler`）

官方 `v6x` 适配器的 `BlockExceptionHandler` 默认实现是 `DefaultBlockExceptionHandler`
（**429 + 纯文本 `Blocked by Sentinel (flow limiting)`**），**文档与代码不一致**——
文档说可以配，但代码里默认值就是它，想改契约必须显式设置。

**做法**：实现 4 参接口（`v6x` 版本，1.8.8 起多了 `resourceName`）：

```java
public class OpenApiBlockExceptionHandler implements BlockExceptionHandler {
    @Override
    public void handle(HttpServletRequest req, HttpServletResponse resp,
                       String resourceName, BlockException e) throws Exception {
        // 从异常子类判维度（官方 5 个子类：Flow / ParamFlow / Degrade / SystemBlock / Authority）
        // 注意：**集群流控被限同样抛 FlowException**，无法从类型区分——需靠 resourceName 或自定义异常
        // 自定义的 DailyQuotaBlockException / IpExactBlockException 在这里被识别，并带出 Retry-After
        ...
    }
}
```

**边界**：Sentinel 的 `BlockException` **不带堆栈、`getRule()` 可能为 null**，
所以不能指望从异常里拿到完整的规则信息——维度判定要靠"资源名 + 异常类型 + 自定义异常"三者组合。

## 4. 规则源：MySQL → FlowRule（自建 DataSource）

**官方没有 MySQL/RDBMS 数据源模块**（官方点名的 pull 模式数据源是文件与 RDBMS，但没提供实现），
所以按官方 SPI 自研：

```java
public class TenantFlowRuleDataSource extends AutoRefreshDataSource<String, List<FlowRule>> {
    @Override
    public List<FlowRule> readSource() throws Exception {
        // 1) 查 open_app（登记表：qpsLimit/dailyQuota）+ open_app_config（租户覆盖）
        // 2) 摊平成 List<FlowRule>：
        //    · 接口维度：resource=各接口资源名, limitApp="default", count=平台阈值
        //    · 租户 QPS：resource="open_api", limitApp=appId, count=该租户阈值
        // 3) **非法规则预检**（FlowRuleUtil.isValidRule），丢弃前先打点告警
    }
}
```

**四个必须处理的坑**（都是研读核实的）：

| 坑 | 处理 |
|---|---|
| **一个 RuleManager 只能挂一个 `SentinelProperty`**，多次注册互相顶掉 | 全项目只注册一次，放在 `@PostConstruct` |
| **更新即全量重建 O(N)**，还有两条全量 INFO 日志 | 刷新周期放宽到 5~30s，并用 `MAX(update_time)` 做 `isModified` 短路 |
| **`InitFunc` SPI 的执行时机是"首次访问资源时"**（不是 Spring 启动），且拿不到 Spring bean | **不用 SPI**，改用 Spring `@PostConstruct` 装配 |
| **非法规则被静默丢弃**（只进 `${user.home}/logs/csp/sentinel-record.log`，**不进应用日志**） | 预检 + 自己的告警指标 |

**"写后推"**：管理面改完配置后，除了等 pull 刷新，**直接 `updateValue`** 一次 → 毫秒级生效
（与项目现有"本实例立即、其他实例等刷新"的模型一致）。

**注意一个语义变化**：现有实现是"租户 QPS 跨所有接口的一个聚合桶"（`c:open:qps:{appId}`），
而 Sentinel 的规则是 `(resource, origin)` 维度的。要保住现有语义，**需要额外 enter 一个聚合资源**
（如 `open_api`）——这在设计上是一个显式的取舍点，实施时要写清。

## 5. 部署：集群模式 + 两个应用实例

### 5.1 为什么必须上集群模式

单机模式下 Sentinel 的统计在 **JVM 内**：k 个副本 = k 份额度。
实测确认：**只有集群模式（Token Server）能兑现"跨实例精确"**
（`GLOBAL` 阈值 10、两实例合计通过 10，而单机模式下是各限各的 10）。

### 5.2 部署清单（实测数据）

| 组件 | 资源 | 说明 |
|---|---|---|
| **Token Server** | 独立进程，空载 **65.6 MB / 23 线程**（`-Xms64m -Xmx256m`，Java 17） | 端口 18730（协议）+ 8719（HTTP 命令口） |
| **应用实例 ×2** | 每个约 500 MB | 用 `--server.port` 错开；WSL 可用内存约 5 G，跑得动 |
| **Sentinel 控制台**（可选） | 约 21.7 MB | 官方明说"非生产就绪"、规则内存态重启即丢、仅 5 分钟监控、无 RBAC |

**关于"控制台改造"**：官方文档要求"使用集群流控需改造控制台"。
但**如果我们用自建数据源（§4）而非控制台推送规则，这条门槛可能不适用**——
实施第一步就要验证这一点（见 §7 步骤 1）。

### 5.3 核心张力：集群精确 vs 预热/排队

这是本设计**必须显式记录**的一处取舍：

> 集群模式只支持"秒级滑动窗口 + 立即拒绝"（源码 `ClusterFlowChecker` 不读 `controlBehavior`）。
> 所以**同一个资源不能既要跨实例精确、又要预热或匀速排队**。

**处理方式**：按资源的性质分配模式——

| 资源 | 模式 | 理由 |
|---|---|---|
| 租户 QPS（`open_api` 聚合资源） | **集群**（GLOBAL） | 要对账，必须跨实例精确 |
| 接口维度（平台保护） | **单机**（可配预热/排队） | 平台保护本就是"每个实例自保"，精确性要求低；而且预热/排队在这里才有意义 |
| 系统自适应（`SystemRule`） | **单机** | 它保护的是"这个 JVM 的负载"，天然是进程级 |

**这个划分本身就是本次迁移的一个设计结论**，要写进文档与教学材料。

## 6. 实施顺序（红绿灯步骤）

> **这 11 步是我的施工顺序，不是 11 次审批。**
> 只有第 0 步（可行性验证）单独做完给用户看——**因为它可能推翻设计**；
> 通过之后第 0.5~10 步连续跑完，中途只在遇到必须拍板的岔路时才停。

| 步 | 内容 | 先写的用例（红） |
|---|---|---|
| 0 | **可行性验证**（动手前必做）：Boot 3 适配器能否装上、Token Server 能否跑起来、**自建数据源能否替代"改造控制台"这道官方门槛** | 一条"规则从 MySQL 加载后真的生效"的冒烟用例 |
| 0.5 | **测试基础设施优化**（见 §6.1）：让同配置的测试类共享容器与 Spring 上下文 | ——（这一步的"验收"是全量耗时下降 + 374 例仍全绿） |
| 1 | 依赖 + Boot 3 适配器接线（`addInterceptor` + `RequestOriginParser`） | 一条请求被 Sentinel 资源名覆盖的用例 |

### 6.1 第 0.5 步：为什么先优化测试基础设施

**实测数据**（2026-10-08 全量，63 类 / 374 例 / 50:48）：

```
测试类内耗时合计：3035 秒（50.6 分钟）   ← 几乎就是全部耗时
编译 + Maven 开销：13 秒                 ← 可忽略
容器启动：MySQL 34 次 + Redis 34 次
```

**问题不在"用例重复"，而在"每个类重复付一遍启动成本"**：

| 现象 | 数字 |
|---|---|
| 平均每类耗时 | **48 秒**，而多数类只有 3~8 个用例 |
| 典型例子 | `DeadlineClipIntegrationTest`：**3 个用例 81 秒**；`OpenApiContextIntegrationTest`：3 个用例 96 秒 |

**根因**：每个测试类的 `@DynamicPropertySource` 都写 `MYSQL.getJdbcUrl()`——
**每个类拿到的是不同容器的 URL**，于是 Spring 的上下文缓存**完全无法复用**。
每个类都要重新走一遍：起容器 → 13 个 Flyway 迁移建表 → 起 Spring 上下文 → 跑 3 个用例 → 拆掉。

**做法**：让**配置相同的测试类共享同一个容器**（容器共享 → URL 相同 → Spring 上下文可复用）。
预计能省 **30~50%** 的全量时间。

**要处理的风险**（我们踩过的测试隔离问题，都已有对策）：
- 熔断器状态是进程级的 → 基类已有 `@AfterEach` 复位
- Redis 键共享 → 已有"每用例独有 subject/appId"的纪律
- 共享容器意味着**数据不再隔离** → 需要核对那些依赖"干净数据库"的用例

**为什么放在迁移之前做**：这次迁移要**重写约 20 例限流用例 + 演练脚本**，
迁移过程中会有大量"改一处 → 跑一批"的迭代。**先把迭代周期从 50 分钟压到 25 分钟**，
整个迁移都会更快——而且这个收益是**持续的**（以后每次全量都省）。

**顺序上的一个约束**：这一步会改动测试基座，**而基座是所有集成测试的公共依赖**——
按项目约定③（改动公共配置后必须跑受影响的既有用例），这一步做完必须**跑一次全量**确认 374 例仍全绿。

**实施结果（2026-10-08）**：根因确认——36 个子类各写 `@DynamicPropertySource` 注入
`MYSQL.getJdbcUrl()`，而 `@Testcontainers` + `@Container` 的语义是"**每个测试类**启动容器"，
于是**每个类拿到的 URL 都不同 → Spring 上下文缓存永远命中不了**。

改法是去掉那两个注解、把容器变成**整个 JVM 的静态单例**（静态块启动 + 关闭钩子停止）。

**实测效果**（6 个类的小批对照）：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| MySQL 容器启动 | 每类一次 | **1 次** |
| `OpenApiContextIntegrationTest` | 96 秒 | **3.0 秒** |
| `SentinelFeasibilityTest` | 40 秒 | **3.4 秒** |
| `Bucket4jWiringTest` | 35 秒 | **0.76 秒** |

**代价**：所有测试类共用同一个库与同一个 Redis，**数据不再按类隔离**。
这要求用例遵守两条既有纪律（本来就有，现在更要紧）：
① 数据自己建、用独有标识；② 有状态组件要复位（熔断器、**以及 Sentinel 的规则**——
后者是 JVM 级静态状态，本轮新引入）。

## 10. 第 6 步实施记录：IP 精确 Slot（2026-10-08）

设计（§3.2）说的是"自建 `IpExactSlot`，内部沿用 Redis 精确计数"。落到代码时
有三个必须自己拍的点，以及**三个顺手发现的缺陷**。都记在这里。

### 10.1 三个实施决策

**① IP 走专属资源 `open_api_ip`，不挂在 `open_api` 上。**

本步的验收标准是"连打超限被拒"，但真正决定成败的是**顺序**：平台级维度（IP）
必须排在租户维度之前判——否则"被 IP 限掉的请求"会先消耗租户的 QPS 与日配额，
租户的对账数字里就混进了**平台根本没服务**的请求。

而 Sentinel 的槽位是 `addLast` 追加的，挂在 `open_api` 上就只能排在 `FlowSlot`（租户 QPS）之后。
想插到前面就得复制 `DefaultSlotChainBuilder` 的实现自己重排——那是抄框架内部代码，
收益不值。所以改成：**资源名分开 + 控制器里先 enter IP 那个资源**
（`SphU.entry(open_api_ip)` → 判 → 立刻 exit），顺序与迁移前完全一致。

**② IP 通过 `args` 传进 Slot。**

源码实测（`CtSph` 字节码 + 1.8.10 源码）：`SphU.entry(name, type, count, args...)` 的
`args` **原样**逐棒传给 `ProcessorSlot.entry(..., Object... args)`；
而 `entry` 的第 3 个参数 `param` **不是用户传参通道**——`CtSph` 在链首硬编码传 `null`，
是 `NodeSelectorSlot` 把建出来的 `DefaultNode` 当作 `param` 往下传，
所以链尾（我们的槽位）拿到的 `param` 是**该资源的 Node**。搞错这一点会拿到一个
永远不为 null 的 Node，而真正的 IP 一个也读不到。

一条留给未来的红线：官方唯一消费 `args` 的是 `ParamFlowSlot`（在
`sentinel-parameter-flow-control` 模块，本项目 pom 没引）。将来若引入它并给这些资源配
`ParamFlowRule`，`paramIdx` 的含义就与我们的下标耦合（`0` 是 appId、`-1` 是 IP）——
**对不上不会报错，只会限错对象**。

**③ 槽位仍在链尾，但要抛 `BlockException` 子类。**

源码核实：`StatisticSlot` 是"先 `fireEntry`、下游不抛异常才记 pass"，并把 `fireEntry`
包在 `try` 里，`catch (BlockException)` 时记 blockQps 后 rethrow。所以
**排在 `StatisticSlot` 之后**（`addLast` 天然如此）的自建槽位，拒绝会被正确记进 block 统计；
若排到它前面，拒绝仍生效但统计里看不到这笔。另一条老红线不变：抛非 `BlockException`
会被 `catch (Throwable)` 静默吞掉（表现为"放行"）。

### 10.2 顺手修掉的三个缺陷（都是迁移过程中新产生或新发现的）

| # | 缺陷 | 判据从哪来 | 证据 |
|---|---|---|---|
| 1 | **租户维度的拒绝不再打点** | 迁移把拒绝响应收进统一出口时，把 `recordLimitRejected` 漏掉了 | **红灯**：在 HEAD 的独立 worktree 上跑新用例 → `被拒了却没有任何指标`，`Tests run: 1, Failures: 1` |
| 2 | **日配额的 Redis 故障变成"静默放行且无指标"** | 迁移到处理链后，`RedisDailyQuotaChecker` 抛的 `RuntimeException` 被 `CtSph` 的 `catch (Throwable)` 吞掉——**放行是对的，但没人打点** | **红灯**：把 fail-open 的 try/catch 临时撤回 → `redisDown_failsOpenAndIsVisible` 红 |
| 3 | **IP/接口维度的限流速率只有配置值的一半** | 调用处传的窗口 `Duration.ofSeconds(2)` 是固定窗口时代"键的 TTL"的遗留值；换成令牌桶后它变成**桶的补充周期**（源码：`Refill` 构造器把 period 整体存成 `periodNanos`） | **红灯**：把窗口改回 2 秒 → `rateMatchesConfiguredQps` 红，`expected: 10.0 but was: 5.0` |

缺陷 3 是"配置项名与行为分家"的典型：配置叫 `qps`，实际给的是 `qps/2`，
而且**没有任何东西会提示**。修法是窗口固定 1 秒（配置叫 qps，窗口就必须是 1 秒）。

另有两处清理：`DailyQuotaSlot` 里一行写在 `check()` **之前**的诊断日志
（后果是**每个放行的请求都打一条"拒绝"的 WARN**，把真告警淹掉），
以及 `GlobalExceptionHandler` 上一段关于日配额会走它的注释（**那是假的**——
日配额抛的是 `BlockException` 子类，由过滤器写响应，到不了 `@RestControllerAdvice`）。

### 10.3 第 6.5 步：上一步"留给用户拍板"的两件，调研后自己拍了（2026-10-08）

用户的原话是：**「我不懂这些，也不知道如何拍板。你不用太保守，如果你难以抉择，就去调研最合适的做法，
而不是投鼠忌器，蹑手蹑脚。」** 所以这两件不再"待办"，而是**先三路调研、再自己拍板并做完**。
（这条工作方式已写进长期记忆：能判定最优解的由我拍，只有涉及价值/预算/优先级的才问。）

#### ① 客户端 IP 的可信化——**做**（`server.forward-headers-strategy=native` + `clientIp()` 只读 `getRemoteAddr()`）

**为什么不能只登记为"部署前提"**：那个前提是"生产 Nginx 覆盖而不是追加代理头"，而它**在仓库里无法验证**，
且一旦不成立，"IP 维度能限住""风控能挡住刷子""审计里的 IP 是真的"三句话同时变成假的。
押在别处的安全前提，跟没有是同一件事。

**调研结论（Tomcat 10.1.31 源码 + Spring Boot 3.3.5 字节码 + 各厂官方文档）**：
- `RemoteIpValve` **只在"直连对端是可信代理"时才看这些头**（公网直连伪造头完全无效），
  且解析 XFF 是**从右往左、跳过内部/可信跳、取第一个不可信的**——代理往右追加真实来源，
  所以**追加与覆盖两种写法都能拿到真实客户端**（这正是应用自解析首跳会错的地方）；
- Spring 的 `framework` 策略（`ForwardedHeaderFilter`）取的是**最左**那个值（反的），不能用；
- 业界一致（Envoy / Nginx realip / Cloudflare / AWS ALB 文档）、OWASP 把"信任客户端可控头"
  列为限流与访问控制绕过 + 日志投毒的成因；Spring Cloud Gateway 官方文档把"取 XFF 第一个值"
  直接点名成 *"This approach is vulnerable to spoofing"*。

**红灯 → 绿灯**（两处，证据都在测试名与提交信息里）：
- 单测 `RiskControlFilterTest.clientIpDoesNotTrustHeaders`：带头 → 必须返回 `remoteAddr`；
- 集成 `OpenApiAuditIntegrationTest.clientIpIgnoresSpoofedLeftmostHop`：
  `X-Forwarded-For: 1.2.3.4, 198.51.100.7` → 审计表里的 `client_ip` 必须是 `198.51.100.7`。
  **红灯实测**：改前两处都是 `expected: "198.51.100.7" but was: "1.2.3.4"`——
  即**攻击者写的字符串真的进了审计表**。

**留了一个部署前置条件（写进 docs/11 §6）**：生产应把 `internal-proxies` 收窄为"代理→应用"的实际来源
（同机 Nginx 即 `127\.0\.0\.1`）；**不要置空**（Boot 文档说"置空=信任所有代理"与代码不符，
实际是阀门整体失效 → 所有客户端塌缩成一个键 → IP 维度自我 DoS）。核对手段是阀门的 TRACE 日志。

#### ② 风控的 `IpRateGate`——**部分合并**（计数统一、防线不合并）

调研把差异逐条摆开之后，结论很干净：两边的**全部**实质差异都是"策略"（阈值/窗口/范围/错误码/指标标签/默认开关），
业界（Nginx 多 zone、Envoy 多 descriptor、Cloudflare 多规则）做的正是"**一个引擎 + 多条按 key 的策略**"。
真正重复的只有那 5 行手写 `INCR`/`EXPIRE`。所以：

| 做 | 不做 |
|---|---|
| 计数改用统一的 `RateLimiter`（令牌桶；键 `c:risk:ip:{ip}`，前缀与主体不变，运维的排查习惯保持） | 不搬进 Sentinel 的 `IpExactSlot`（那会让 C 端领券热路径依赖 Sentinel 的 JVM 级静态接线，而本项目已被它咬过一次：单跑绿、全量红） |
| fail-open 补 ERROR 日志 + `coupon_ratelimit_failopen_total{dimension="risk_ip"}`（**改前连异常对象都丢掉了**——"风控闸失效"与"今天没人刷"在监控上完全一样） | 不改 7001 / 不改 `risk_ip` 标签 / 不改覆盖面 / 不改默认开启 |
| 429 补 `Retry-After`（秒数由闸门自己算：窗口/容量，下限 1） | 不新增 `receive_ip` 资源、不把过滤器改走 `SphU.entry` |

**代价（已写进文档）**：阈值语义从"每 60 秒 30 次（边界最多 2 倍）"变成"容量 30 + 每 2 秒补 1 个"——
挡脚本无差，NAT 出口略更严，**需要按命中率复核**。复议触发器：出现第三条 IP 键策略，
或风控引入人机识别/设备维度（那时它按 AWS 的分法属于另一种机制，本就不该与速率计数合并）。

**红灯 → 绿灯**：`RiskControlFilterTest.deniedResponseCarriesRetryAfter`（红：该 429 无此头）、
`IpRateGateTest`（5 例，含"委托给统一限流器"与"故障 fail-open + 指标"）。
**变异验证**：把新加的两行（`Retry-After` 与 fail-open 打点）临时撤掉 → 对应用例立刻红
（`expected: "2" but was: null`），证明断言不是摆设。

### 10.5 全量测试才照出来的三件事（第 6 步的意外收获）

本步的定向用例早就全绿了，但**全量**一跑（411 例）照出 3 个"单跑绿、全量红"的问题。
它们都不是 IP 维度本身的缺陷，而是**把 Sentinel 接进来之后才会出现的相互作用**：
Sentinel 的核心状态是 **JVM 级静态**的，而我们（共享容器之后）同一个 JVM 里有十几个 Spring 上下文。

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | `SentinelRuleSourceTest` 3 例红：**"数据源读到 69 个租户配额、其中含本租户=true，但当前规则总数=0"** | `FlowRuleManager` 的规则位**只能挂一个** `SentinelProperty`（我们自己的注释早就写过"多次注册互相顶掉"）。十几个上下文各注册一次 → 除了最后一个，其余数据源全部"脱挂"；它们的 `refreshNow()` 推给了一个没人听的 property。**而且取决于上下文创建顺序**——单跑绿、全量红 | 属性也做成 JVM 级的：新增 `SharedRuleProperty`（全进程一个、只注册一次），所有数据源都往它里面推（`TenantFlowRuleDataSource` 覆写 `getProperty()`——字节码核实过，定时任务与主动推都走这个方法）。于是"谁推都算数" |
| 2 | 59 个 error 连锁：`Too many connections` → 上下文加载失败 → 后续用例全崩 | 共享容器之后，**每个"配置组合"一个上下文且整场不销毁**，每个上下文都带着自己那套连接池（ShardingSphere + Hikari）活到 JVM 结束，把 MySQL 默认的 `max_connections=151` 吃穿 | 测试容器 `--max-connections=500`。**这不是连接泄漏**，是"共享容器"这个设计的容量前提变了（`docker inspect` 核实 CMD 已生效） |
| 3 | `SentinelBlockContractTest` 1 例红（"预期 429、实际 200"）、`SentinelFeasibilityTest` 同类风险 | 这两条老用例还在**手工 `FlowRuleManager.loadRules`** 灌规则——而规则位已被自建规则源接管，每 10 秒一次全量推送把它们冲掉（第 3 步就在另一个用例里踩过同一件事） | 换成**不受规则源影响的判据**：契约用例改用 `SystemRule`（规则源不碰它，确定性地拦住），可行性用例改为断言"资源在 Sentinel 里有统计"（那才是它当初要回答的问题：拦截器装上了吗、资源名对吗） |

**共性**：三件事都不是"代码写错了"，而是**"两个各自正确的设计叠在一起"**——
Sentinel 的 JVM 级静态状态 × 共享测试容器带来的多上下文。
识别这类问题的线索是**"单跑绿、全量红"**（顺序依赖），以及**"读得到、写进去看不见"**
（推给了一个已脱挂的对象）。

**给后续步骤的提醒**：Sentinel 侧凡是要"注册"或"绑定"的东西（规则位、`MetricExtension`、
集群 Token 客户端）都是 JVM 级的，第 7、9 步要按同一思路处理。

### 10.6 第 7 步实施记录：把"静默放行"变成看得见（2026-10-08）

**验收标准**（§6 步骤 7）："数据源故障时放行且有指标；`/actuator/prometheus` 能看到"。

#### 交付四件

| # | 交付 | 用例 | 解决了哪条静默路径 |
|---|---|---|---|
| 1 | 规则源**空结果守卫**：读到"登记表一行都没有"→ 抛异常保旧规则 + `failopen{rule_source}` | `TenantFlowRuleDataSourceTest`（4 例） | 那条"错一下就是全体不限流"的路径（比 §3.3 的六条都危险） |
| 2 | **链头看门狗槽位** `SentinelWatchdogSlot`：接住下游异常 → 计数 → 原样重抛 | `SentinelWatchdogSlotTest`（3 例） | ③ `CtSph` 内部异常 |
| 3 | **两条 gauge** `SentinelSelfMetrics`（`coupon_sentinel_enabled` / `coupon_sentinel_slot_chain_count`） | `GovernanceMetricsIntegrationTest`（抓 Prometheus 文本） | ①② 全局开关 / 链数超限 |
| 4 | 把**已有但没人消费**的信号接进指标：数据源的 `LOAD_FAILURES`、`mapper.dropped()` | 同 1（dropped 计入 `coupon_sentinel_rules_dropped_total`） | ④ 规则源失败/丢弃 |

#### 两个关键设计判断（都有实测支撑）

**① 看门狗为什么必须挂在链头、且必须"原样重抛"**：
`CtSph.entryWithPriority` 对链内异常是 {@code catch (Throwable) → 记一行它自己的日志 → 照常返回 Entry}，
调用方拿到的是**正常 Entry**——所以"把 `SphU.entry` 包一层"这条路根本抓不到异常（实测复核）。
唯一能看见它的位置是链内。挂链头 = 能覆盖整条链。**而它绝不能改变行为**：
接住、计数、重抛——否则看门狗自己就成了新的静默失效点（这一点写在类的注释里）。

**② 护栏"宁窄勿宽"**：只拦"登记表一行都读不到"，不拦"全部停用"与"全部不限"。
后者是运维的正常操作，拦下来会让"以为关了其实没关"——那比不关更糟。这也正是调研里
"反面意见"那条的合理内核（数据源的天职是忠实序列化 DB 真值），我们只把"0 行"
这一种**不可能合法的状态**拦下来（没有行 → 没有任何接入方能通过验签 → 这本身即异常）。

#### 变异验证

把两处新加的守卫临时撤掉 → 对应用例立刻红：
`downstreamError_isCountedAndRethrown`（`expected: 1.0 but was: 0.0`）与
`emptyRegistry_throwsInsteadOfClearingRules`（`Expecting code to raise a throwable`）。

#### 顺带记录：本项目在"静默失效"这件事上的一贯做法

第 7 步的调研还问了一个策略问题——"失效可见"业界更常用指标告警还是启动期断言。
结论是**两者各管一段**：启动期断言只能断言"接线在不在"（如本项目 `SwitchPlanStartupCheck`
与自建槽位的 `install()` 是否发生），运行期失效（Redis 挂、规则源读空、全局开关被关）
只能靠指标/告警。本项目现在两样都有：`*StartupCheck` + `coupon_ratelimit_failopen_total`
+ 这三条 Sentinel 自身的 gauge。
