## 1. 背景与目标

### 1.1 问题定义

券是有生命周期的营销资产：领取 → 可用 →（核销 | 过期）。其中"过期"是唯一**不需要任何用户动作、纯粹由时间驱动**的流转。当前系统对它的实现为零：`CouponTransition.EXPIRE / EXPIRE_ON_LOCK` 两条边已定义但无任何触发者；`EventType.EXPIRED` 已定义但无写入者。

### 1.2 为什么是当前最高优先级

按答辩后修正的 M1 顺序（ROADMAP：P0 热修 → **L2** → L5 → ADR-0009 迁移）：L2 是剩余正确性缺口中唯一**资损方向**的——过期券被成功核销等于平台为无效券支付补贴（§2 复现③实证）。L5（锁定超时）与 L2 共享"时间驱动的券状态流转"骨架，先做 L2 可为 L5 铺路。

### 1.3 目标与验收标准

| # | 验收 | 判定方式 |
|---|---|---|
| A1 | 过期券在任何入口不可用：核销被拒、锁定被拒、发放回补类操作同口径 | 复现③断言翻转：核销返回明确错误码，券转 EXPIRED，占用单关闭 |
| A2 | 券包不再显示"待使用"的过期券 | 复现①断言翻转：展示层按已过期渲染；物理状态由扫描收敛 |
| A3 | 过期流转落 EXPIRED 事件（统计/财务对账的事实源） | 事件表断言 |
| A4 | 批量过期不构成对业务表的冲击 | 任务表驱动、小批量、有退避与死信（§4 D5） |
| A5 | 中断可判定：任务有状态位，重跑幂等 | 注入失败后重跑，零遗漏零重复流转 |

## 2. 复现（过程可重跑）

### 2.1 环境与方法

- 环境：Testcontainers（MySQL 8.0 + Redis 7-alpine），`ExpiryBugReproductionTest`。
- 方法：正常链路领到真券后，`UPDATE user_coupon SET valid_end = now()-2d WHERE id=?`，等价于时间流逝到过期之后——不等待真实时间，也不绕过任何业务路径。改 2 天而非几秒的原因见 §2.5。

### 2.2 复现①：过期后券包仍显示"待使用"（状态悬挂）

```
步骤：freshCoupon() → expireNow(couponId) → userCouponRepository.findById(couponId)
实测输出：[复现①] 过期券在券包里的状态 = USABLE（0=待使用）
```
根因：状态从 USABLE 到 EXPIRED 的唯一合法路径是 `CouponTransition.EXPIRE`，全工程没有任何代码触发它；查询路径也无惰性判定。券状态与时间事实永久脱节。

### 2.3 复现②：过期未锁的券，锁定被拒（现有防线边界）

```
步骤：freshCoupon() → expireNow() → tradeAppService.lock(...)
实测输出：[复现②] 过期券 lock 结果 = 4002
```
根因与判定：`casLock` 的 SQL 自带 `AND valid_end > NOW()` 守卫（UserCouponMapper）。**此入口现状正确**——但它只守住了"锁"的门。真正的洞在复现③。

### 2.4 复现③：锁定期间过期，核销仍成功（资损）

```
步骤：freshCoupon() → lock 成功（有效期内，合法路径）
    → expireNow()（下单后拖延支付跨过有效期）
    → tradeAppService.confirm(usageNo, 1000)
实测输出：[复现③] 已过期券核销结果 = 已核销，券终态 = USED（2=已核销）
         ——平台为一张过期券付了 1000 分补贴，占用单 CONFIRMED 入账
```
根因：`casConfirm` 的 SQL 只有 `WHERE id=? AND status=1`，**无有效期谓词**。设计期防线只覆盖了"先过期后锁"的时序，漏掉了"先锁后过期"——而死亡可以发生在锁定期间。docs/06 §6.6 踩坑清单第 1 条（致命级）预言的正是此形态："核销只信 status，不带 expire_time 谓词……此谓词是全系统资损的最后防线"。

### 2.5 附带发现：测试环境时区错位（8 小时）

首轮复现用 `valid_end = now() - 1s` 未生效：容器内 MySQL 时区为 UTC、JVM 为 +08:00，Java 写入的"过去 1 秒"在 DB 的 `NOW()` 看来仍在未来 8 小时。所有以 `NOW()` 为谓词的守卫（casLock/casRelease/未来的核销谓词）**都隐含假设两侧时区一致**。处置见 §4 D9。

## 4. 技术方案（docs/06 v3 的 M1 裁剪：三层取二）

docs/06 的完整形态是三层：实时触发（秒级，MQ/ZSet）→ 兜底扫描（分钟级，任务表）→ 懒判断（零延迟，谓词）。**裁剪依据**：其一，docs/06 §6.3 自述"没有 MQ 定时消息能力、日过期量百万级以内，v2（任务表+扫描）就是够用的终点"——本项目 MQ 在 M5 引入；其二，第一层是加速器不是正确性依赖（第三层谓词与第二层任务表不依赖其载体）。**M1 落地第二层+第三层，第一层留 M5**。三条不变式（docs/06 §6.7）全部继承。

### D1 核销谓词与"锁定中过期"的收场（堵复现③，资损防线）

`casConfirm` 补谓词：`UPDATE ... SET status=2 WHERE id=? AND status=1 AND valid_end > NOW()`。0 行时事务外分类（与 casDeductStock 0 行同一模式，P0 热修④之后的既有范式）：读券真实状态 → 已过期 → 走 **EXPIRE_ON_LOCK 收场**：

- 券：LOCKED → EXPIRED（终态，状态机边已有）；
- 占用单：OCCUPYING → **新增终态 EXPIRED(3, "过期关闭")**（UsageStatus 增值，DB tinyint 兼容）。理由：这不是"释放"（券不可回可用），也不是"核销"（无补贴），它是第三种终结方式，对账时必须有独立可辨识的账目形态；
- 补贴不承担、事件落 `EXPIRED`。

### D2 注册唯一入口（防旁路漏注册，docs/06 踩坑 5）

`CouponIssueTxService.issue()` 事务内追加任务表 INSERT（同库本地事务）。任何未来新增的券产生路径（补发/客服/直发）必须复用该方法——架构约束写进类 javadoc 与本 ADR。

### D3 任务表（V5 迁移，docs/06 §6.4.1 的 M1 尺寸）

```sql
CREATE TABLE coupon_expire_task (
  id             BIGINT   NOT NULL AUTO_INCREMENT PRIMARY KEY,
  coupon_id      BIGINT   NOT NULL COMMENT 'user_coupon.id',
  user_id        BIGINT   NOT NULL COMMENT '冗余，M4 分片路由预留',
  shard          INT      NOT NULL DEFAULT 0 COMMENT '=coupon_id%16，分片广播预留',
  next_scan_time DATETIME NOT NULL COMMENT '下次应扫描时间；失败退避只推进此字段',
  status         TINYINT  NOT NULL DEFAULT 0 COMMENT '0待处理 1已终结 3死信',
  retry_count    INT      NOT NULL DEFAULT 0,
  create_time    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_coupon (coupon_id),
  KEY idx_scan (shard, status, next_scan_time)
) COMMENT '过期任务表=持久化待办队列（docs/06 v2/v3 兜底层）';
```

要点（与 docs/06 一致，理由见彼处）：无"处理失败"状态（失败只推进 next_scan_time 指数退避 `min(2^retry, 30min)`，超 8 次置死信+告警）；任务表本身即 DB 版延时队列（L5 锁定超时复用此骨架）。

### D4 执行器唯一入口 + 触发源标识

`ExpireExecutor.executeBatch(couponIds, TriggerSource)`：①主表批量 CAS `SET status=3 WHERE id IN (...) AND status=0 AND valid_end<=NOW()`（幂等，重复触发无害）；②任务批量终结；③真实流转者落 `EXPIRED` 事件。`TriggerSource{SCAN, RECONCILE, MANUAL}` 贯穿日志——M1 两源，M5 加实时层后占比成为健康指标。

### D5 兜底扫描（Spring @Scheduled，XXL-JOB 形态预留）

每分钟：按 `idx_scan` 捞 `shard IN (本实例分片) AND status=0 AND next_scan_time<=NOW()`，每批 500、单轮上限 200 批（防饿死）。多实例分片互斥当前用 Redis 扫描锁（`SET NX PX`），M2 引入调度锁后替换（L16 同源）。核销/释放事务内顺手终结任务（防御性，不依赖——执行器幂等天然容忍脏任务空转）。

### D6 T+1 对账与自动补注册

每日：`user_coupon WHERE status=0 AND valid_end < NOW()-10min`（走 idx_expire）LEFT JOIN 任务表——有券无任务→自动补注册；有任务未终结但主表已流转→终结；差异超阈值告警。同时扫 `status=2 AND valid_end < used相关时间` 形态兜底资损审计（docs/06 踩坑 1 的发现手段）。

### D7 展示层懒判断（零延迟防线的一部分）

券包查询对 `status=0 AND valid_end<=NOW()` 的券按"已过期"渲染（不写库，物理状态由 D5 收敛）；`TradeAppService` 入口快检同步补过期判断。**懒判断不做物理写**：查询路径保持无副作用，物理流转只经 D4 唯一入口。

### D8 L13（领取窗口竞态）的裁决

L13 的竞态产物是"出生即死券"（校验后、落库前窗口关闭）。**L2 落地后该券会被过期链路立即终结，危害自动收敛为一次无效领取**。裁决：不为 L13 增列，登记为"被 L2 吸收"，若产品要求领取时刻严格性再单独立项（STATUS 同步更新）。

### D9 时区统一（§2.5 的处置）

生产与测试统一：JVM `-Duser.timezone=Asia/Shanghai` + JDBC `serverTimezone=Asia/Shanghai` + 容器 `TZ=Asia/Shanghai`；**所有时间谓词一律用 DB 的 `NOW()`**（docs/06 踩坑 7：应用时钟只用于调度节奏，不用于判断）。写入 dev/prod 配置与 runbook。

## 5. 与 L5（锁定超时）的边界

两者共享任务表骨架（D3 的表即 docs/06 所说"时间驱动的待办队列"），但计时器不同：L5 计的是"锁定后 N 分钟未核销"（占用单视角），L2 计的是"券到期"（券视角）。交叠规则：**先到期者赢，后到者空转**——执行器都是幂等 CAS，重复触发无副作用。L5 实施时复用本表（`task_type` 扩列或同表两谓词，届时定）。

## 6. 实施步骤

1. V5 迁移（任务表 + UsageStatus 无 DDL 变更，代码枚举增值）；时区配置（D9）。
2. D1 核销谓词 + EXPIRE_ON_LOCK 收场（含 UsageStatus.EXPIRED 终态、状态机边校验）→ 复现③翻转。
3. D2 注册 + D4 执行器 + D7 懒判断 → 复现①②翻转（②从"碰巧有守卫"变为"设计内防线"）。
4. D5 扫描 + D6 对账。
5. 测试矩阵：三复现翻转断言 / 批量过期幂等重跑 / 退避与死信 / 中断恢复（A5）/ 事件断言 / 懒判断不写库 / 出生即死券收敛（D8）。

## 7. 认账

- 时效为分钟级（无第一层实时触发）：过期后最长 1 分钟 status 仍为 0——**资损防线不依赖时效**（D1 谓词零窗口），代价仅是展示/统计的分钟级脏窗；
- 任务表与主表同库双写使领券事务多一次 INSERT（毫秒级；M4 分库后按 user_id 同规则路由保住本地事务，docs/06 踩坑 8）；
- 出生即死券：接受（D8 裁决）；
- 占用单新增终态需下游（未来的统计域）感知，M5 计域实施时对账口径补 EXPIRED。
