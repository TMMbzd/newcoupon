# 第五章 用券核销与优惠计算（Usage & Settlement）

> 本章讲优惠券生命周期中"钱真正花出去"的一段：结算页试算、下单锁券、支付核销、取消回退，以及支撑这一切的优惠计算引擎。这是整个券系统中唯一同时满足**高并发读、低延迟强一致写、资金敏感**三个条件的域——领券超发损失的是"未来的优惠承诺"，核销算错损失的是"当场真金白银"。
>
> 素材说明：本章引用的五篇素材中，京东到家两篇（a15/a18）与字节跳动一篇（a09）重点覆盖存储架构、缓存优化、容量估算与服务治理，但均明确未展开核销/退券的完整链路实现；美团一篇（a04）仅在 TDD 案例中给出优惠券规则引擎的规则建模。因此本章的逆向链路、状态机、Lua 脚本、对账设计以通用交易系统工程实践补齐，素材标注过"未涉及"的内容不会假托素材之名。

## 5.1 该领域解决什么业务问题，在券系统全局中的位置

### 5.1.1 业务问题

用户领到一张券，只是获得了一个"优惠承诺"。这个承诺要变成真实的让利，必须经历四个动作：

1. **试算（Trial）**：用户在购物车/结算页看到"我有哪些券可用、用了能省多少钱"。这是读流量最大的入口——购物车每加一个商品、每切一次门店，都要重算一遍。
2. **锁券（Lock）**：用户点"提交订单"，选中的券从"可用"变为"锁定"，防止下单到支付之间的窗口期内被别的订单用掉或重复使用。
3. **核销（Settle/Consume）**：支付成功回调后，券正式变为"已使用"，优惠金额按商品行分摊入账，进入财务与统计口径。
4. **回退（Return/Unlock）**：订单取消（未支付超时、用户主动取消）或整单退款时，券要安全退回；已过有效期则走过期终态。

配套的**优惠计算引擎**回答两个问题："这张券在这笔订单上能不能用、能用的话优惠多少钱、摊到每个商品行各多少钱"。分摊是财务核算（商家承担多少、平台补贴多少、退款时按行退多少）的基础。

### 5.1.2 全局位置

```
                ┌──────────────────────────────────────────────────────┐
                │                  优惠券系统中台                        │
                │                                                      │
  运营/B端 ──►  │  [建券域]  券模板、规则、库存、审批、启用               │
                │      │ 模板数据                                       │
  用户/触达 ──► │  [发放/领券域]  领券中心、定向推券、防超领              │
                │      │ 领券产生"用户券实例"                            │
                │      ▼                                               │
                │  ╔═════════════════════════════════════════════╗     │
                │  ║   用券核销与优惠计算域（本章）                 ║     │
                │  ║   试算 ──► 锁券 ──► 核销 ──► 回退              ║     │
                │  ║   + 优惠计算引擎（资格/互斥/金额/分摊）         ║     │
                │  ╚═════════════════════════════════════════════╝     │
                │      │ 用券流水（唯一事实源）                         │
                │      ▼                                               │
                │  [统计/对账域]  使用率、ROI、分摊核算、差异修复        │
                └──────────────────────────────────────────────────────┘
                        ▲                    ▲
                        │ RPC                │ MQ（支付成功/订单取消事件）
                 [订单/交易系统]        [支付中心/售后系统]
```

上下游契约：**上游是订单系统**（下单时调锁券，携带订单号与选中券列表），**旁路是支付中心与售后系统**（通过 MQ 通知支付成功、取消、退款），**下游是统计对账域**（消费用券流水）。京东到家的分层（a18）把"结算页用券"独立成与"展示券"分开的核心交易系统，正是认识到这个域的流量模型和可用性要求与其他域完全不同。

### 5.1.3 本域的三个固有难点

- **读写不对称**：试算是读多（一次请求可能涉及数百到上千次缓存 IO，a18 实测购物车场景一次请求裂变 400~1000 次网络 IO），核销是写少但每笔都是钱。两者的容量规划、隔离手段完全不同。
- **跨系统一致性**：券状态必须与订单状态最终一致，但订单、支付、券是三个系统，必然引入两阶段（锁定/核销）与异步消息，就必须处理悬挂、乱序、重复。
- **计算正确性即资损**：面额算错、折扣无上限、分摊不守恒、并发双花，任何一条都直接是钱。

## 5.2 朴素实现（v1）会怎么挂

### 5.2.1 v1 长什么样

一个没有经验的同学会这样写：

- 结算页接口：`SELECT * FROM user_coupon WHERE user_id=? AND status=0`，然后循环每张券去 `coupon` 模板表查规则、逐条校验门槛与适用范围，Java 里累加优惠。
- 下单接口：先 `SELECT status FROM user_coupon WHERE user_coupon_id=?` 判断是"可用"，再 `UPDATE user_coupon SET status=2 WHERE user_coupon_id=?`（WHERE 条件里**没有** status）。
- 取消订单：订单系统更新完自己状态后，HTTP 调一下券系统的退券接口，失败就抛异常结束。
- 金额：`double` 运算，分摊用 `amount / total * discount` 后强转 `long`。

### 5.2.2 故障一：结算页被打挂（读侧）

量级参照：京东到家（a15）日均百万订单、用户券总量 40 亿、大促已领券人均 50~200 张（a18）。试算调用量是下单量的 20~50 倍——用户在购物车里每做一次操作都要重算。按 a18 的估算公式（8 次 RPC + 每张未领券 6 次 IO × 50 张 + 已领券 100 张各 1 次 IO ≈ 400+ 次 IO），大促高峰购物车几十万次/分钟的调用量会把全部压力翻译成**百万 QPS 级的 DB 查询**。而单 MySQL 的安全写入只有约 4000 QPS、单表千万行后查询效率大幅下降（a09 实测）。

现象：连接池耗尽 → 结算页 RT 从 200ms 飙到 10s → 网关超时 → 用户打不开结算页 → 下单量断崖。更糟的是这些 SELECT 与核销 UPDATE 混在同一个库，**展示流量把交易写流量拖死**（a15 明确把"高并发场景影响核心交易用券流程"列为拆系统前的三大问题之一）。

### 5.2.3 故障二：一券两用（写并发，直接资损）

v1 的"先查后改"（check-then-act）在并发下必然竞态：用户双开两个页面（或脚本）同时用同一张 100 元券提交两笔订单，两个请求都读到 `status=0`，都通过校验，都执行 UPDATE，两笔订单各优惠 100 元。大促秒杀场景这个窗口会被批量利用——黑产脚本刻意并发提交再取消不优惠的那笔。按单券面额与并发宽度，资损可达百万级；更麻烦的是这类损失往往事后对账才发现，钱已经以"优惠"形式出去，追不回。

### 5.2.4 故障三：券悬挂（一致性缺失）

用户下单锁了券但 30 分钟未支付，订单系统超时关闭订单，退券的 HTTP 调用失败（网络抖动/服务重启），v1 没有重试没有兜底——券永远停在"已使用"，用户申诉"我的券没用就没了"。按取消率 15~30% 估算，这是持续放大的客诉与赔付源。反向场景同样存在：支付回调与取消请求并发到达，先处理了取消再处理核销，钱收了券退了，又是一次资损。

### 5.2.5 故障四：金额与账目错误（计算正确性）

- `double` 运算：`0.1 + 0.2 != 0.3`，展示价与实付价差 1 分，支付网关校验金额不一致直接拒单。
- 分摊用逐行 `long` 截断：优惠 10 元摊 3 行各 3.33 元，合计 9.99 元，1 分钱**凭空消失**——财务日切对账永远差分，月末差额无法解释。
- 满折券无折扣上限：a05 记录了作者前公司因审核不严被薅走 200 余万、以及 B2B 大额订单（单笔 50 万~800 万）一笔就把整期营销费用薅秃的事故。
- 优惠倒挂不设防：3 元商品用 5 元无门槛券，优惠算 5 元，订单金额变 -2 元。

## 5.3 方案演进 v1 → v2 → v3

### v3 之前先看 v2：缓存 + 两阶段 + 原子 CAS + 幂等

v2 针对 v2.2 的四类故障逐个击破：

1. **读侧**：用户券搬进 Redis Hash（`key=userId, field=券实例ID`，即 a15 的用户券集群结构），券模板本地缓存 + Redis 二级缓存（a09 方案：实例定时刷新，刷 Redis 前加分布式锁防多实例重复写）。试算一次 `HGETALL` + 本地模板计算，DB 只承接回源。
2. **写侧**：引入**两阶段状态机**（可用 → 锁定 → 已核销），状态迁移用 Redis Lua 做 CAS（compare-and-set），把"查+改"压缩成单命令原子操作，一券两用的竞态窗口被消除。
3. **一致性**：锁券成功后发 MQ（事务消息/本地消息表）异步落库，订单取消走 MQ 事件 + **锁定带 TTL 的兜底扫描**，悬挂问题变成可自愈。
4. **幂等**：以 `事件+订单号+券实例ID` 构造唯一键，DB 唯一索引挡住重复消费与业务方重试。

**v2 引入的新问题**：Redis 与 MySQL 双写后，任何一边失败就出现状态分叉（Redis 说锁定、DB 说可用）；MQ 重复投递、乱序（回退消息先于核销消息到达）；用户券 Hash 在"券多 + value 大"时变成大 Key，单点阻塞整个集群（a18 的适用门店缓存事故：单 Value 近万门店，集群流出量 G/s 级）；Redis 宕机时核销链路怎么办。这些问题的答案不是更聪明的写法，而是**v3 的架构性兜底：以 DB 为准 + 对账修复 + 读写/冷热/故障三重隔离**。

### v3：大厂最终形态

v3 = v2 的全部 + 五件事：

1. **真相源分层**：Redis 只做"高并发路径上的状态闸门与读缓存"，MySQL 的 `user_coupon` 状态 + `coupon_consume_record` 流水才是最终事实源；任何分叉以 DB 为准修复（a15 的"Redis 数据可通过数据库回溯"思路）。
2. **对账兜底**：分钟级增量对账 + 日切全量对账，覆盖"流水 vs 状态 vs Redis"三方，差异自动修复或报警。双写不一致从"事故"降级为"会被夜间修复的噪音"。
3. **隔离**：试算（展示读）与锁券核销（交易写）拆成独立应用独立集群（a15 的应用隔离、a18 的"展示系统 vs 用券核心交易系统"拆分）；缓存按数据域拆集群（a18 的五集群：打标/门店券/用户券/活动/已使用）。
4. **数据规模治理**：user_coupon 按 user_id 分库分表（a15 演进为 8 库 × 1024 表；a09 用 user_id 后四位做分片键支撑"查我的券"），已核销/已过期券冷热归档（a15：40 亿降到 15 亿，支撑 3~5 年增长）。
5. **计算引擎规则化**：资格校验、互斥检查、金额计算、分摊各自策略化（a04 案例中 `CouponValidator / CouponCombinator / DiscountCalculator` 的职责分离思路），采用平行式计算（a05），把"规则正确性"固化在可枚举的测试用例里（a04 的"测试即需求文档"）。

## 5.4 大厂最终形态详解

### 5.4.1 用户券状态机

```
                 领券成功
                    │
                    ▼
              ┌──────────┐  锁券(下单)   ┌──────────┐  核销(支付成功)  ┌──────────┐
              │ AVAILABLE │ ──────────► │  LOCKED  │ ──────────────► │   USED   │
              │  可用(0)  │             │ 锁定(1)   │                 │ 已核销(2) │
              └──────────┘             └──────────┘                 └────┬─────┘
                    ▲                     │     ▲                          │
     回退(重置可用)  │                     │     │ 核销失败/乱序防护          │ 整单退款回退
                    └─────────────────────┘     └──────────────────────────┤
                    │                                                        ▼
                    │                       超时未支付/用户取消        ┌───────────┐
              ┌─────┴──────┐                (有效期内退回可用)         │ RETURNED  │
              │  EXPIRED   │ ◄──── 到期扫描(延时消息) ──────────────    │ 已回退(3) │
              │ 已过期(4)   │        (锁定/可用态到达有效期)            └───────────┘
              └────────────┘
```

要点：

- **回退是事件不是坟墓**：退券写一条"回退"流水，券本身若仍在有效期内重置回 AVAILABLE。这保证用户视角简单（券又回来了），统计视角完整（领券用券明细记录 1 用 + 1 退，与 a05 描述的"记 1 条用券 + 1 条退券"模式一致）。若回退时已过有效期，直接进 EXPIRED，不复活。
- **每个迁移都有唯一方向与唯一触发方**：AVAILABLE→LOCKED 只能由锁券触发；LOCKED→USED 只能由支付成功事件触发；USED→RETURNED 只能由整单退款触发。方向固定，乱序消息就能靠"期望状态不匹配"识别并丢弃。
- **过期扫描用延时消息**：RocketMQ 延时消息有时长上限而券有效期不固定，采用循环投递——到期检查一次，未到真正过期时间就重新投一条（a09 的循环投递方案）。

### 5.4.2 表结构 DDL

```sql
-- 用户券实例表：按 user_id 分库分表（8 库 × N 表，分片键 user_id）
CREATE TABLE `user_coupon_0000` (
  `id`             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_coupon_id` BIGINT UNSIGNED NOT NULL COMMENT '券实例全局唯一ID（雪花），对外暴露',
  `user_id`        BIGINT UNSIGNED NOT NULL COMMENT '分片键',
  `coupon_id`      BIGINT UNSIGNED NOT NULL COMMENT '券模板ID',
  `status`         TINYINT NOT NULL DEFAULT 0 COMMENT '0可用 1锁定 2已核销 3已回退 4已过期',
  `lock_order_id`  BIGINT UNSIGNED DEFAULT NULL COMMENT '当前锁定/核销对应的订单ID',
  `receive_time`   DATETIME(3) NOT NULL,
  `valid_start`    DATETIME(3) NOT NULL,
  `valid_end`      DATETIME(3) NOT NULL COMMENT '统一 23:59:59 口径',
  `version`        INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本',
  `create_time`    DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `update_time`    DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
                    ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_coupon_id` (`user_coupon_id`),
  KEY `idx_user_status` (`user_id`, `status`),
  KEY `idx_coupon` (`coupon_id`),
  KEY `idx_status_valid_end` (`status`, `valid_end`)
) ENGINE=InnoDB COMMENT='用户券实例';

-- 用券流水表：唯一事实源，统计/对账/财务全部以此为准，只插入不更新
CREATE TABLE `coupon_consume_record` (
  `id`              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `consume_id`      BIGINT UNSIGNED NOT NULL COMMENT '流水号（雪花）',
  `user_coupon_id`  BIGINT UNSIGNED NOT NULL,
  `user_id`         BIGINT UNSIGNED NOT NULL,
  `coupon_id`       BIGINT UNSIGNED NOT NULL,
  `order_id`        BIGINT UNSIGNED NOT NULL,
  `event`           TINYINT NOT NULL COMMENT '1锁定 2核销 3回退 4过期 5锁定超时释放',
  `discount_amount` BIGINT NOT NULL DEFAULT 0 COMMENT '该事件下的优惠总额（分），核销事件填写',
  `unique_key`      VARCHAR(96) NOT NULL COMMENT '幂等键：event:orderId:userCouponId',
  `event_time`      DATETIME(3) NOT NULL,
  `create_time`     DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_unique_key` (`unique_key`),
  KEY `idx_order` (`order_id`),
  KEY `idx_user_coupon` (`user_coupon_id`, `event`)
) ENGINE=InnoDB COMMENT='用券流水（唯一事实源）';

-- 优惠分摊明细：核销事件产生，按商品行拆分，退款按行冲销
CREATE TABLE `coupon_share_detail` (
  `id`             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `consume_id`     BIGINT UNSIGNED NOT NULL COMMENT '关联核销流水',
  `order_id`       BIGINT UNSIGNED NOT NULL,
  `order_item_id`  BIGINT UNSIGNED NOT NULL,
  `sku_id`         BIGINT UNSIGNED NOT NULL,
  `coupon_id`      BIGINT UNSIGNED NOT NULL COMMENT '成本归属：平台券/商家券分账依据',
  `share_amount`   BIGINT NOT NULL COMMENT '分摊到本行的优惠金额（分）',
  `is_tail`        TINYINT NOT NULL DEFAULT 0 COMMENT '1=倒挤尾差行',
  `create_time`    DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (`id`),
  KEY `idx_order` (`order_id`),
  KEY `idx_consume` (`consume_id`),
  KEY `idx_sku` (`sku_id`)
) ENGINE=InnoDB COMMENT='优惠分摊明细';
```

设计理由：

- **流水与状态分离**：状态表可归档、可分库分表随意迁移；流水表 append-only，是审计与统计的"领券用券明细"唯一事实源（a05 将其作为全部统计的数据源，典型的 event-sourcing 式设计）。
- **`uk_unique_key` 是整个逆向链路的定海神针**：MQ 重复投递、业务方重试、超时重发，全部在这张表的唯一索引上撞停。
- **分摊明细挂在核销流水下**，不在核销前生成——试算阶段的分摊只是预览，只有核销才落账。

### 5.4.3 Redis key 设计与数据结构选型

| 用途 | Key | 结构 | Value / 理由 |
|---|---|---|---|
| 用户券主存储 | `uc:{userId}` | Hash | field=`userCouponId`，value=`st\|endTimeSec\|couponId\|ruleBits\|thresholdFen\|valueFen`。选 Hash 的理由：结算页一次 `HGETALL` 拉全部券（单 key 单节点，原子性好），增删改单 field 不影响其他券——即 a15 的用户券集群结构 |
| 券模板 | `t:cb:{couponId}` | String | JSON/protobuf。模板是读强依赖且变更低频，前置**本地缓存**（Caffeine）+ 定时刷新 + 分布式锁保护回写（a09 二级缓存方案，根除 Redis 万分之 2~3 的超时失败） |
| 模板版本号 | `t:ver:{couponId}` | String(int) | 本地缓存对比版本，避免全量拉取 |
| 热点判定辅助 | `uc:used:{yyyyMMdd}` | Bloom/Set（可选） | 当日已核销 userCouponId 粗过滤，拦截重复核销的无效 DB 请求（a18"已使用集群"按数据域隔离的思路） |

三条治理红线（来自 a15/a18 的实战教训，直接适用于本域）：

1. **Hash value 必须极致精简**：大 Key 参考阈值为 String value > 8000 字节或集合元素 > 8000（a18）。用户 200 张券 × 60 字节 value ≈ 12KB，已在红线附近——所以 value 只放交易必需字段（状态/有效期/面额/门槛），券名称、规则描述绝不进这个 Hash（放模板侧，用本地缓存）。
2. **字段名与值压缩**：模板里 `couponName` 这类长字段名用缩写、数据优先用整数编码（a18：`couponId` 精简为 `a` 一类的做法），流出量可从 G/s 降到 M/s 量级。
3. **不要给用户券 Hash 设统一 TTL 后集中过期**：过期时间天然分散在各 field 内部（endTimeSec 由业务判断），如需清理必须用 Scan 渐进式或 `UNLINK`（a18：直接 DEL 大 Key 本身就会阻塞节点），且过期时间加随机抖动避免集中过期打满定期删除时间片。

### 5.4.4 核心 Lua：状态迁移 CAS

所有写路径（锁券/核销/回退）共用一个脚本，唯一区别是期望状态与目标值：

```lua
-- cas_transition.lua
-- KEYS[1] = uc:{userId}          用户券 Hash
-- ARGV[1] = userCouponId         Hash field
-- ARGV[2] = expectStatus         期望当前状态（CAS 校验）
-- ARGV[3] = nowEpochSec          服务端时钟（秒）
-- ARGV[4] = fullNewValue         写入的新 value 全量串（调用方组装好）
-- 返回: '0' 成功; '-1' 券不存在; '-2|curSt' 状态不符(CAS失败); '-3' 已过期
local val = redis.call('HGET', KEYS[1], ARGV[1])
if not val then return '-1' end

local f = {}
for tok in string.gmatch(val, '[^|]+') do f[#f + 1] = tok end
local st, et = tonumber(f[1]), tonumber(f[2])

if st ~= tonumber(ARGV[2]) then return '-2|' .. st end
if tonumber(ARGV[3]) > et   then return '-3' end

redis.call('HSET', KEYS[1], ARGV[1], ARGV[4])
return '0'
```

为什么是 Lua 而不是 `WATCH/MULTI/EXEC` 或分布式锁：Lua 在 Redis 单线程内执行，"读状态—校验—写回"天然原子，无竞态窗口；WATCH 是乐观重试，高并发下冲突重试风暴反而放大延迟；分布式锁在"单用户单券"这种细粒度上开销完全不成比例。注意脚本保持**纯内存、无阻塞命令**，执行时长必须微秒级，否则 Lua 本身会变成 a18 说的"阻塞节点的流量源"。

```java
@Service
public class LockService {

    /** 锁券主流程：Redis CAS 闸门 + 事务消息异步落库 */
    public List<LockResult> lock(LockCmd cmd) {
        String hashKey = "uc:" + cmd.getUserId();
        List<LockResult> results = new ArrayList<>(cmd.getUserCouponIds().size());
        for (long ucId : cmd.getUserCouponIds()) {
            String cur = redisTemplate.<String, String>opsForHash().get(hashKey, String.valueOf(ucId));
            if (cur == null) { cur = rebuildFromDb(cmd.getUserId(), ucId); }   // 回源重建，以 DB 为准
            String[] f = cur.split("\\|");
            int st = Integer.parseInt(f[0]);
            long endSec = Long.parseLong(f[1]);
            // 1) 前置业务校验：状态可用、有效期需覆盖支付窗口
            if (st != 0) { results.add(LockResult.busy(ucId, st)); continue; }
            if (nowSec() + PAY_WINDOW_SEC > endSec) { results.add(LockResult.expireSoon(ucId)); continue; }

            // 2) Lua 原子 CAS：0(可用) -> 1(锁定)
            String newVal = "1|" + f[1] + "|" + f[2] + "|" + f[3] + "|" + f[4] + "|" + f[5];
            String r = casScript.execute(hashKey, String.valueOf(ucId), "0",
                                         String.valueOf(nowSec()), newVal);
            if (!"0".equals(r)) { results.add(LockResult.casFail(ucId, r)); continue; }

            // 3) 事务消息异步持久化（RocketMQ 事务消息；unique_key 幂等）
            mqTemplate.sendMessageInTransaction(TOPIC_COUPON_EVENT,
                CouponEvent.locked(cmd.getUserId(), ucId, cmd.getOrderId(),
                                   "1:" + cmd.getOrderId() + ":" + ucId));
            results.add(LockResult.ok(ucId));
        }
        return results;   // 任一失败由订单侧决定整单回滚（先统一 rollback 已成功的）
    }
}
```

### 5.4.6 优惠计算引擎

**计算模式选平行式**（所有券均以商品总额为基数，互不分摊抵扣，a05 的主张）——理由见 5.5 分歧一。引擎分四步，职责分离（结构参考 a04 案例的重构产出）：

```
TrialCmd(订单明细+用户+门店) 
   │
   ▼ ① CouponValidator（资格校验，三维）
   ├── AmountValidator:   适用范围商品总额 ≥ 门槛（无门槛券=满0）
   ├── UserLevelValidator: 用户身份（新人券/会员券，依赖用户服务）
   └── ScopeValidator:    品类/单品/门店/渠道范围
   │
   ▼ ② MutualExclusionChecker（互斥与叠加）
   │     互斥组显式常量化，如 {满减券, 满折券} 互斥、新人券与一切互斥（a04 案例）
   │     组内按"可抵扣金额大者优先，同额临期优先"贪心选一张（a05 的排序两原则）
   │
   ▼ ③ DiscountCalculator（金额，全 long 分 + BigDecimal 中间值）
   │     满减: discount = min(faceValue, base)                ← 防倒挂
   │     满折: discount = min(base × (1 - rate), maxCap)      ← maxCap=折扣上限，必填
   │
   ▼ ④ Apportioner（分摊：比例 + 倒挤）
```

分摊算法（总额守恒的关键，a05 的倒挤法）：

```java
/** discountFen 优惠总额摊到各行；最后一行倒挤，保证 sum(shares) == discountFen */
public static List<Long> apportion(long discountFen, List<Long> baseFen) {
    long total = baseFen.stream().mapToLong(Long::longValue).sum();
    long used = 0;
    List<Long> shares = new ArrayList<>(baseFen.size());
    for (int i = 0; i < baseFen.size() - 1; i++) {           // 前n-1行按比例四舍五入
        long s = BigDecimal.valueOf(baseFen.get(i)).multiply(BigDecimal.valueOf(discountFen))
                .divide(BigDecimal.valueOf(total), 0, RoundingMode.HALF_UP).longValue();
        shares.add(Math.min(s, baseFen.get(i)));             // 行分摊不超行金额（防倒挂）
        used += shares.get(i);
    }
    shares.add(discountFen - used);                          // 尾行倒挤，标记 is_tail=1
    return shares;
}
```

除不尽的余数归属必须二选一并全链路统一：倒挤到最后一行（逻辑严密、实现最简，推荐），或加到金额最大/最小的行（a05 列出的第二种行业做法）。混用两种规则是对账差分的经典来源。

### 5.4.7 四条链路时序

**A. 试算（读，可降级）**

1. 购物车/结算页发起，网关按用户路由到试算应用（与交易写应用物理隔离）。
2. `HGETALL uc:{userId}` 取全部券；miss 则查 DB 重建 Hash（回源加分布式锁防击穿）。
3. 模板从本地缓存读取（miss 才走 Redis→DB；a09：二级缓存把 Redis 万分之 2~3 的超时失败率根除）。
4. 引擎四步：资格过滤 → 互斥分组排序 → 逐券金额计算（平行式）。
5. 返回：可用券列表（按"可抵扣降序、同额临期升序"排序）+ 推荐勾选组合 + 整单预估优惠。
6. 降级路径：本地缓存与 Redis 双 miss 且 DB 抖动时，返回"无可用券"并打标，**绝不让试算阻塞下单主链路**。

**B. 锁券（下单，写，高频）**

1. 订单服务创建订单，携带 `requestId + orderId + 选中券列表` 调 `lock`。
2. 逐券执行 Lua CAS：AVAILABLE→LOCKED（原子，消灭一券两用窗口）。
3. 任一券 CAS 失败：对已成功券执行反向 CAS 回滚，整单返回失败。
4. 全部成功：发 RocketMQ 事务消息（半消息→本地可提交→提交），异步落 DB（UPDATE status=0→1 + INSERT 流水，唯一键幂等）。
5. 返回订单系统继续走支付；锁同时带上"有效期需覆盖支付窗口"的前置校验（5.4.5 代码）。

**C. 核销（支付成功回调，写，低频但资金敏感）**

1. 支付中心回调订单系统，订单系统发出"支付成功"事件（MQ）。
2. 券系统消费：先查 `unique_key = settle:{orderId}:{ucId}` 幂等表，命中直接返回成功。
3. **DB 事务**（核销走强一致，与锁券的最终一致刻意不同）：`UPDATE user_coupon SET status=2 WHERE user_coupon_id=? AND status=1`（乐观并发，影响行数=0 说明乱序或分叉，进补偿）+ `INSERT coupon_consume_record(event=2)` + `INSERT coupon_share_detail`（分摊在此刻计算落账）。
4. 事务提交后同步刷 Redis：Lua CAS LOCKED→USED；失败仅记日志交给对账（Redis 是闸门不是账本）。
5. 发出"券已核销"事件供统计域消费（使用率、ROI 的数据源，a05 的九指标口径）。

**D. 回退（取消/退款，写）**

1. 未支付取消/超时：消费"订单取消"事件，Lua CAS LOCKED→AVAILABLE + DB `status=1→0` + 流水 `event=3`；若此刻已过期则迁 EXPIRED 不复活。
2. 已支付整单退款：USED→RETURNED + 流水；有效期内视产品策略决定是否回 AVAILABLE（默认回，与 a05"整单售后退全部优惠券"一致）。
3. **兜底扫描**：定时任务扫描 `status=1 AND update_time < now - 支付超时` 的悬挂锁，强制释放——这是对"取消消息丢失"的最后防线。
4. 部分售后**不退券**（a05 规则：已发货/履约后的部分售后不退），按 share_detail 行金额冲销财务账即可。

**E. 对账（兜底，v3 的灵魂）**

1. 分钟级：增量比对"近 10 分钟流水事件 vs user_coupon 状态"，分叉即修复（以流水+DB 为准重写 Redis）。
2. 日切：全量比对三方（DB 状态 / 流水 / Redis 抽样），校验 `sum(share_detail.share_amount) = consume_record.discount_amount`（分摊守恒），输出差异报告。
3. 金额异动（同订单优惠总额与支付流水不符）直接电话级报警。

### 5.4.8 容量与部署要点

- 分片键选 user_id（a09 用 user_id 后四位；a15 为 8 库 × 1024 表），因为读路径全部以用户为维度；`orderId` 查询靠流水表 `idx_order` 承接。
- 写容量估算方法（a09 的推导式）：核销 TPS ≈ 日订单量 ÷ 86400 × 峰值系数；锁券同量级；试算 = 下单 × 20~50 倍但全走缓存。单个 Redis 分片写安全值约 2w QPS（a09 实测），用户券 Hash 按用户天然散列，不会出热点——**热点只会出现在模板 key 上**，而模板已被本地二级缓存消化。
- 线上资源 = 压测值的 1.5 倍冗余；发券接口内部执行 100ms 内、超时设 500ms 拒绝异常请求（a09 服务治理参数，同样适用于锁券）。
- 核销链路对 Redis 的依赖要有降级预案：Redis 整体不可用时，锁券可临时退化到"DB 乐观锁 + 限流排队"模式（容量下降但资金安全），这比"Redis 挂了就不能下单"好得多。

## 5.5 素材间方案分歧与推荐

**分歧一：优惠计算用平行式、递进式还是最优组合？** a05 以血泪教训（2021 年项目含促销+券+会员权益的递进式最优计算，"4 位开发被干跑了"）主张平行式、不做最优；a04 的美团 TDD 案例却完整实现了位运算幂集枚举（O(2^n)）求全局最优组合。**推荐：平行式 + 互斥组内贪心（每组选可抵扣最大的一张），明确不做全局最优。** 理由：a04 的幂集是教学级实现，n 超过 20 张完全不可行（结算页用户券可达 200 张，a18），且最优组合还带来"用户看到的省额与实付不一致"的解释成本与资损面；a05 的教训证明其投产比在多数业务里为负。若某垂直业务确需最优，应加三层约束：n ≤ 10、互斥剪枝、离线预计算，并把幂集算法隔离在独立可降级的计算服务里。

**分歧二：退券后的状态建模。** a05 指出行业两种做法：定义独立"已取消"状态，或视同"待使用"（记 1 用 + 1 退两条明细）。**推荐：状态机层面"回到 AVAILABLE"（视同待使用），流水层面必记回退事件，不设长期驻留的"已取消"状态。** 理由：用户视角只有"券回来了/没了"两种，中间态是运营视角的负债（每多一个状态，所有查询、展示、统计分支翻倍）；而流水保留了完整可追溯性，两全。仅"已支付整单退款"保留 RETURNED 终态，因为它涉及资金冲销，需要与退款单强关联。

**分歧三：用户券缓存结构 Hash 还是打散 String。** a15 采用 Hash（key=userId, field=userCouponId）；a18 在大 Key 治理中把"券→适用门店集合"打散成 `CouponId+门店` 的单 Key（B 端写、C 端 EXISTS）。**推荐：用户券用 Hash（读路径是"取该用户全部券"，聚合读场景 Hash 一次网络往返最优）；适用范围类数据用打平单 Key（读路径是"判断这张券在不在范围内"，存在性判断不需要拉全量 value——a18 打平后流出量从 G/s 降到几十 M/s）。** 两者的选择标准是**读问题的形状**，不是数据本身。

**分歧四：核销写的同步性。** a09 的发券设计是"Redis 扣库存 + MySQL 一次非事务写入"，天然偏最终一致；但核销是资金动作，字节的素材也自述核销链路未展开。**推荐：锁券沿用"Redis 先行 + DB 异步最终一致"（高频，性能优先，错了可回退）；核销改为"DB 事务先行 + Redis 跟随"（低频，强一致优先，分摊与流水必须在同一事务落账）。** 两条链路刻意不对称，是性能与资金安全之间最重要的取舍。

**分歧五：排序优先级。** a05 给出两个原则（临期优先 / 可抵扣额大优先）但未定序。**推荐：可抵扣金额降序为主键、临期升序为次键。** 理由：可抵扣额直接对应转化率，是平台与用户的共同利益；临期只影响边际损耗，且大量临期券本就因门槛不可用，置顶反而干扰决策。

## 5.6 踩坑清单（按严重程度排列）

1. **一券两用（并发重复核销）——直接资损。** 发现：对账任务扫描同一 `user_coupon_id` 出现多条核销流水、或同券多订单占用；资金异动监控。防：Redis Lua CAS 原子迁移 + DB UPDATE 带 `AND status=期望值` 的乐观锁 + 流水表 `unique_key` 唯一索引，三层缺一不可（任何单层在故障时都会被穿透）。
2. **优惠倒挂与无上限折扣——单笔即可薅秃营销费用。** a05 记录了审核不严被薅 200 余万、B2B 单笔 50 万~800 万订单叠高折扣把整期费用一笔耗尽的事故。发现：实时监控"单订单优惠金额/订单金额"比值、单券种优惠总额日累计突增。防：计算层硬编码 `min(面额, 基数)` 与 `min(折扣额, 上限)` 双向封顶；建券侧强制满折券必须填折扣金额上限（a05：`min(上限, 可优惠金额)` 孰低）；交叉审核（建券与审券账号分离）。
3. **锁券后订单取消消息丢失——券悬挂，用户资产损失。** 发现：`status=1 AND update_time < now-支付窗口` 的存量扫描报表；客诉"没用券就没了"。防：锁定 TTL + 定时兜底释放任务 + 取消事件用事务消息保证可达；回退本身幂等（unique_key），重复投递无害。
4. **支付回调与订单取消并发乱序——钱收了券退了。** 发现：同订单既核销又回退的流水对；支付对账单与用券流水交叉核对。防：状态机方向固定 + CAS 期望状态校验，乱序消息因"状态不匹配"被拒绝并进入补偿队列人工/自动处理。
5. **Redis 与 DB 双写分叉。** 发现：分钟级三方对账（流水 vs 状态 vs Redis）。防：明确 DB 为唯一事实源，Redis 只做闸门与缓存；所有修复单向"以 DB 重写 Redis"（a15 的 DB 回溯思路）；Redis 更新失败不阻断主流程只记对账待办。
6. **分摊不守恒与 double 精度——财务永远差 1 分钱。** 发现：日切 `sum(share) ≠ discount_amount` 报警；财务月结差额。防：金额全链路 `long` 分 + BigDecimal 中间运算；尾行倒挤且 `is_tail` 标记；全链路只用一种余数规则。
7. **展示流量拖垮交易链路。** a15/a18 都把"高并发影响核心交易用券流程"列为拆分前的核心痛点。发现：试算流量高峰时核销接口 RT 联动上涨（共享连接池/共享 DB 的特征）。防：试算与锁券核销拆应用、拆缓存集群（a18 五集群），试算配置"可降级为不展示优惠"的开关。
8. **用户券 Hash 演化成大 Key。** 发现：从库 Scan 巡检 + 主从切换观察分片流出量（a18 的定位工具箱，最后兜底且一定有效）。防：value 只留交易必需字段、字段名缩写、整数优先；已核销/已过期 field 及时 HDEL；清理用 UNLINK 不用 DEL。
9. **模板读取强依赖 Redis 的固有超时。** a09 实测 Redis 超时概率万分之 2~3，在高 QPS 下放大为可观的失败量。发现：核心接口成功率监控按错误码拆分（timeout 类占比）。防：本地二级缓存 + 定时刷新 + 分布式锁保护回写（a09 方案）。
10. **规则变更无测试安全网。** 优惠规则是规则密集型逻辑，AI/人工改计算代码极易踩互斥与边界（a04：同一优惠券需求三轮提示词仍偏离业务）。发现：规则事故几乎都是上线后才被财务/客诉暴露。防：把叠加/互斥/门槛/边界用例固化为单元测试（a04"测试即需求文档"），改计算引擎必须先跑全量规则用例基线。

## 5.7 小结

用券核销与优惠计算域的设计主线只有一句话：**读走缓存且可降级，写走状态机且强幂等，钱以数据库流水为准，其余一切分叉靠对账修复。** v1 的四类死法（读打挂、写双花、券悬挂、账算错）分别对应终态的四件武器：二级缓存 + 应用隔离、Lua CAS 两阶段状态机、事务消息 + 兜底扫描 + 唯一索引幂等、平行式计算 + long 分 + 倒挤分摊。优惠计算上，平行式换掉递进式与最优组合，是用可解释性和确定性的小让利，换计算复杂度、资损面与研发成本的大幅收敛——这笔账，a05 的作者用 4 位开发的离职已经替行业算过一次了。
