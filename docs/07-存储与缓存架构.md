# 第七章 存储与缓存架构：券系统的数据底座

> 本章回答一个问题：一个目标承载十万级 QPS 发券、亿级用户券资产、大促瞬时热点不打挂的优惠券中台，它的 MySQL 怎么拆、Redis 怎么设计、两者之间怎么保持一致。所有设计均以"可直接照着写代码"为标准展开。

---

## 一、该领域解决什么问题，在全局中的位置

优惠券系统的数据有三个截然不同的画像，这是理解一切存储设计的起点：

1. **模板/规则数据**（创）：B 端低频写（运营建券，一天几百次），C 端超高频读（每次发券、每次算价都要读模板）。读多写少、体量小（万级模板）、但读流量是全系统最大的——字节的文章明确说查模板是发券的强依赖，Redis 超时率约万分之 2~3 都不可接受，最终用本地内存 + Redis 二级缓存根除。
2. **库存数据**（发）：高并发写、强正确性要求。一个爆款券模板的 12w QPS 扣减全部落在"一个数"上——这是全系统最尖锐的写热点。
3. **用户券资产**（用/查）：海量追加写（日均亿级，京东到家文章数据）、按用户维度查询（"我的券"）、生命周期状态推进（未使用→锁定→已使用/已过期/已回退）。

三种画像用同一种存储方案（比如单库 MySQL + 每次查库）必然顾此失彼。存储与缓存架构层的职责，就是把这三种数据各自放到正确的位置上，并定义它们之间的同步与兜底规则。

在券系统全局中的位置：

```
                ┌────────────────────────────────────────────────┐
                │              优惠券中台 · 应用层                  │
                │   建券服务 │ 发券服务 │ 核销/退券 │ 查券/算价     │
                └───────┬───────────┬────────────┬───────────────┘
                        │           │            │
        ================╪===========╪============╪==================
        【本章】 存储与缓存架构层（数据底座）
        ================╪===========╪============╪==================
                        │           │            │
          ┌─────────────▼──┐  ┌─────▼──────┐  ┌──▼──────────────┐
          │ 模板读路径       │  │ 库存写路径   │  │ 用户券读写路径     │
          │ 本地缓存         │  │ Redis 分段  │  │ userId 分库分表    │
          │   ↓ miss        │  │ 库存 key +  │  │ (N 库 × M 表)     │
          │ Redis 模板集群   │  │ Lua 原子扣  │  │   ↓ binlog/MQ    │
          │   ↓ miss        │  │ 对账表兜底  │  │ ES(运营侧查询)    │
          │ MySQL 主从      │  │            │  │                  │
          └────────────────┘  └────────────┘  └──────────────────┘
                        │
          ┌─────────────▼───────────────────────────────────┐
          │ 基础设施：MySQL 分片集群 / Redis 集群(按数据域拆分)  │
          │ RocketMQ(延时消息驱动状态推进) / 对账与巡检平台      │
          └─────────────────────────────────────────────────┘
```

京东到家的实践佐证了"按数据域拆缓存集群"的必要性：他们拆了 5 个 Redis 集群（打标、门店券、用户券、活动、已使用），目的就是故障隔离与独立扩容——用户券缓存出问题时不拖垮模板读取。

## 二、朴素实现（v1）会怎么挂：四个具体故障场景

v1 的样子：一个 MySQL 库，`coupon_template`、`coupon_stock`（单行单字段）、`user_coupon` 三张表，所有读写直连数据库，`UPDATE coupon_stock SET stock = stock - 1 WHERE template_id = ?` 扣库存，事务里同时扣库存、插券记录。

**场景 1：库存行锁把系统拖死（并发问题，1k QPS 即挂）**
`coupon_stock` 每个模板一行，所有扣减请求在 InnoDB 行锁上串行排队。实测单 MySQL 写入约 4000 QPS 是天花板（字节文章给的硬数据），而单行热点远到不了 4000——一条 UPDATE 持锁约 1~5ms，单行理论上限约 200~1000 TPS。一款爆款券 2000 人/秒抢购时：大量会话等行锁 → 连接池（典型 50~200 连接）被占满 → 后台查券、核销等所有不相关请求也拿不到连接 → 整库雪崩。错误现象是 `Connection is not available, request timed out after 30000ms` 刷屏，DB CPU 不高（都在等锁），典型的"锁等待型假死"。

**场景 2：单表千万级后查询退化（容量问题）**
`user_coupon` 以日均千万级增长，MySQL 单表过千万后索引变高、查询效率大幅下降（字节文章明确给出的阈值）。三个月后"我的优惠券"接口 P99 从 20ms 涨到 500ms+，运营侧按券维度圈人查询直接超时。

**场景 3：超领与重复发券（资损问题）**
- 同一用户并发两次抢同一张"每人限领 1 张"的券：请求 A 校验通过（count=0）但尚未落库，请求 B 校验也通过（count 仍是 0）→ 领到两张。vivo 文章把这个时序讲得很清楚。
- 上游超时重试：业务方领券请求网络超时后重试，接口不幂等 → 一个用户两张券，多出的券若可叠加使用就是直接资损。

**场景 4：热点模板把缓存打穿**
就算加了 Redis 缓存模板，一个秒杀券 12w QPS 全部打在同一个 key 上，超过 Redis 单分片约 10w QPS 的读上限、2w QPS 的写上限（字节实测数据），该分片网卡打满无响应，集群整体抖动。京东到家的案例则展示了另一种死法：门店适用券用 `CouponId → 上万门店ID集合` 的结构存 Redis，这个大 Value 每次读取都让 Redis 主线程卡一下，高峰期"所有接口都变慢"，而 Redis 慢日志里什么都没有。

## 三、方案演进：v1 → v2 → v3

### v2：读写分离 + Redis 缓存 + 分布式锁

针对 v1 的场景 1、2、4，v2 引入三件事：

1. **MySQL 读写分离**：模板查询、券列表走从库。vivo 文章提到主从延迟正常不超过 1ms，且券领取本身有时延过程，用户无感知。
2. **模板读走 Redis**：cache-aside，miss 回源 DB 并回填。
3. **Redis 分布式锁防超领**：领券前先抢 `用户id+模板id` 的锁，持锁完成"数量校验→扣减→落库"再释放（vivo 方案）。

**v2 解决了**：读压力与 DB 连接占用大幅下降；同用户并发超领被锁住。

**v2 引入的新问题**：

- **库存还在 DB 行锁上**，写热点没解决——这是 v2 最大的遗留。
- **Redis 与 DB 不一致**：缓存回填时机、失败回滚、Redis 宕机恢复，全都要重新设计。vivo 文章正是因此（当时流量下）没选 Redis incrby 扣库存，理由是要处理缓存丢失/宕机后数据恢复与不一致。
- **分布式锁的新坑**：批量领券时锁 key 若拼成 `用户id+A+B+C+D`，与单券请求的 `用户id+A` 不互斥，锁形同虚设——vivo 踩过，解法是逐券加锁、任一失败自旋等待。锁还引入了超时释放与业务执行时长的博弈。
- **缓存层的大 Key/热 Key 问题**（京东到家案例），以及查询缓存化后"过期时间怎么定、集中过期怎么办"。

### v3：分库分表 + Redis 原子扣减（分段库存）+ 二级缓存 + 异步化

针对 v2 的遗留，v3 做四件事：

1. **用户券表按 userId 分库分表**（vivo、字节共同选择），写容量线性扩展：字节按 12w QPS ÷ 4000 = 30 个 MySQL 主库分片规划。
2. **库存扣减挪到 Redis 并分段**：把一个模板的库存拆成 M 段子 key，随机不重复轮询扣减，写热点被打散到多个 Redis 分片（字节方案；vivo 在 DB 里做了同构的分段方案）。扣减用 Lua 保证"查 + 扣 + 用户限领计数"原子。
3. **模板二级缓存**：本地内存 + Redis，定时任务刷新回写 Redis 时加分布式锁防止多实例重复写（字节方案）。
4. **异步化与最终一致**：MySQL 只承担发券时"一次非事务性写入"（字节数据模型的核心简化），幂等靠唯一索引兜底；状态推进（过期）交给 RocketMQ 延时消息循环投递；库存的 Redis/DB 差异交给对账任务。

**v3 引入的新问题**（也是本章"最终形态"要收尾的部分）：

- 分库分表后**无法 join**：用户券表冗余模板字段（vivo：字段数要在性能与冗余之间平衡）。
- 分库分表后**批量插入失效**：不同用户路由到不同库表，需内存归集后分组插入，最多 M 次（vivo 定向发券亿级的做法）。
- **跨分片查询**：运营侧"查某模板所有领取人"要广播全分片——解法是 binlog/MQ 同步到 ES 或宽表（京东到家存储层就是 MySQL + ES）。
- **Redis 扣减成功但落库失败**的双写不一致——必须设计补偿与对账，否则就是超卖资损。
- **分段库存的段间不均衡**：某段扣尽而总量未尽，出现"假售罄"。

可以看到，每一次演进都是在"把当前最大瓶颈转移走"，同时制造出新的、更靠后、更可控的问题。这就是架构演进的本质。

## 四、大厂最终形态设计（可直接落地）

### 4.1 MySQL 表结构与分库分表

**模板库（coupon_db，不拆片，一主两从）**：

```sql
CREATE TABLE coupon_template (
  id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  template_id   BIGINT UNSIGNED NOT NULL COMMENT '模板ID，雪花生成，对外暴露',
  name          VARCHAR(64)  NOT NULL,
  biz_line      INT          NOT NULL COMMENT '业务线，多租户隔离',
  type          TINYINT      NOT NULL COMMENT '1满减 2折扣 3代金 4运费券',
  face_value    INT          NOT NULL DEFAULT 0 COMMENT '面额，单位分',
  threshold     INT          NOT NULL DEFAULT 0 COMMENT '门槛，0为无门槛',
  total_stock   BIGINT       NOT NULL COMMENT '总库存',
  seg_count     INT          NOT NULL DEFAULT 1 COMMENT '库存分段数，热点模板>1',
  limit_per_user INT         NOT NULL DEFAULT 1 COMMENT '每人限领',
  valid_type    TINYINT      NOT NULL COMMENT '1固定区间 2领后N天',
  valid_days    INT          DEFAULT NULL,
  valid_start   DATETIME     DEFAULT NULL,
  valid_end     DATETIME     DEFAULT NULL,
  status        TINYINT      NOT NULL DEFAULT 0 COMMENT '0草稿 1生效 2暂停 3终止',
  version       INT          NOT NULL DEFAULT 0 COMMENT '乐观锁，缓存失效依据',
  ext_json      VARCHAR(1024) DEFAULT NULL,
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_template (template_id),
  KEY idx_status_end (status, valid_end)

```

`version` 字段是缓存一致性的锚点：任何变更 version+1，缓存回源时比对版本决定是否重刷。

**库存分段对账表（与模板同库）**——Redis 的"真相副本"：

```sql
CREATE TABLE coupon_stock_segment (
  id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  template_id BIGINT UNSIGNED NOT NULL,
  segment_no  INT          NOT NULL COMMENT '段号 0..seg_count-1',
  total_qty   INT          NOT NULL COMMENT '该段分配量',
  db_used_qty INT          NOT NULL DEFAULT 0 COMMENT '对账后该段已发(以DB落券数为准)',
  updated_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_seg (template_id, segment_no)
) ENGINE=InnoDB COMMENT='库存分段账本，用于对账与Redis重建';
```

建券时初始化 M 行（总量尽量整除；不整除时余量放 0 号段），Redis 预热以 `total_qty - db_used_qty` 为准。

**用户券表（分库分表，路由键 user_id，N 库 × M 表）**：

```sql
CREATE TABLE user_coupon_0000 (  -- 每库 M 张同构表，此处展示一张
  id           BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  coupon_id    BIGINT UNSIGNED NOT NULL COMMENT '券实例全局唯一ID(雪花)',
  user_id      BIGINT UNSIGNED NOT NULL,
  template_id  BIGINT UNSIGNED NOT NULL,
  status       TINYINT      NOT NULL DEFAULT 0
               COMMENT '0未使用 1锁定(下单占用) 2已使用 3已过期 4已回退 5作废',
  -- ↓↓↓ 冗余模板字段：分片后无法join，控制在最少必要集
  face_value   INT NOT NULL,
  threshold    INT NOT NULL,
  valid_start  DATETIME NOT NULL,
  valid_end    DATETIME NOT NULL,
  source       VARCHAR(32) NOT NULL COMMENT 'APP/活动/定向/客服',
  idempotent_no VARCHAR(64) NOT NULL COMMENT '幂等号=上游业务方请求号',
  order_id     BIGINT DEFAULT NULL COMMENT '核销订单，退券回退依据',
  created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_idem (user_id, template_id, idempotent_no),  -- 幂等唯一索引(vivo方案)
  UNIQUE KEY uk_coupon (coupon_id),
  KEY idx_user_status (user_id, status, valid_end)           -- "我的可用券"
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

两条设计理由必须说透：

- **幂等唯一索引建在原表而不是新建幂等表**：vivo 在两者间权衡后选原表——新表多一次关联、对现有链路影响大；代价是要脚本刷历史数据补唯一值、为未传幂等号的业务方侧生成编号。
- **路由公式沿用 vivo 的算法**：`表后缀 = hash(user_id) % M`，`库后缀 = hash(user_id) / M % N`。它有一个扩容友好的性质：先整除再取模保证了 hash 相邻的 M 张表落在同一库，未来只扩库（N→2N）不改表数时，表后缀不变、整表搬迁即可，数据不需要跨表重分布。字节用"user_id 后四位"做分片键，实现更简单，但当运营做"尾号为 8 的用户定向发券"这类活动时会造成倾斜——推荐用完整 hash。

容量测算（字节方法论，可直接套用）：目标发券峰值 P QPS → MySQL 主库分片数 = P / 4000（每片只承担一次非事务写入）；Redis 分片数 = P / 20000（假设最坏情况全部打一个模板）。12w QPS → 30 个 MySQL 主分片 + 6 个 Redis 分片起步，线上资源再乘 1.5 倍冗余。

### 4.2 Redis Key 设计与数据结构选型

Key 规范先立三条（来自京东到地的实战教训）：① Key/字段名做缩写（`coupon_info_base`→`c_i_b` 这类思路），Value 数字优先于字符串；② 所有 key 必须设 TTL 且加随机数防集中过期；③ Value 硬上限——String 不超 8000 字节、集合元素不超 8000 个，超过必须在设计评审阶段拆。

| 用途 | Key | 结构 | TTL | 选型理由 |
|---|---|---|---|---|
| 模板信息 | `c:tp:{tplId}` | Hash（字段名精简为短名） | 24h+随机 | 读多写少，Hash 支持部分字段更新，冷热字段可再拆两个 key |
| 分段库存 | `c:sk:{tplId}:{segNo}` | String(int) | 券有效期+7d | 单 key 单 int，Lua 原子扣减最小单位；分段数=热点分摊系数 |
| 用户限领计数 | `c:ul:{tplId}:{userId}` | String(int) | 券有效期+1d | 与库存同 Lua 扣，防并发超领的核心 |
| 售罄标记 | `c:so:{tplId}` | String | 券有效期 | 全段扣尽后置位，前置到本地内存，拦截穿透流量 |
| 适用门店 | `c:ap:{tplId}:{shopId}` | String(空值) | 券有效期 | 打平设计：EXISTS 判定替代拉取上万门店集合，流出量从 G/s 级降到 M/s 级（京东到家实测） |
| 用户券列表 | `c:uc:{userId}:{tab}` | ZSet(score=valid_end) | 短TTL或不用 | "我的券"第一页加速；注意用户券是写多的资产数据，缓存收益有限，默认不缓存列表、只缓存模板 |

三个关键选型理由展开：

- **分段库存用 String 而非 Hash 的多 field**：`HINCRBY` 虽然也能原子扣，但所有段在一个 key 里就永远落在一个 Redis 分片上，分段就失去意义。分段的目的就是让 `c:sk:{tplId}:0`、`:1`、`:2`… 经 CRC16 哈希落到不同分片。这与字节"子库存 key 以分片编号结尾"的方案一致，也和"热 key 散列多份"通用做法同构。
- **适用门店打平**：改造前 `Key=CouponId, Value=上万门店ID集合` 是典型大 Key；打平后 C 端一次 EXISTS 就完成"这张券在该门店是否展示"的判定。代价是 key 数量 = 券数 × 门店数，写入放大，所以只对"门店级适用"这类判定型数据使用，且变更走 B 端一次性批量写入。
- **热 key 的读写分流**：读热点（模板）用"散列多份 + 随机读一份"或本地前置缓存；写热点（库存）必须用分段。京东到家明确指出 key 备份（同数据多副本打散读）只适合读多写少，套到发券扣减上是错误选型——副本扣减无法合并，会超卖。

### 4.3 库存扣减：Lua 脚本 + Java 实现

Lua 把"用户限领校验 + 分段库存扣减"合成一次原子操作（二者分开做，中间的并发窗口就是超领漏洞）：

```lua
-- KEYS[1]=c:ul:{tplId}:{uid}  KEYS[2]=c:sk:{tplId}:{segNo}
-- ARGV[1]=limit_per_user ARGV[2]=本次数量(1) ARGV[3]=计数TTL秒
local got = redis.call('GET', KEYS[1])
if got and tonumber(got) + tonumber(ARGV[2]) > tonumber(ARGV[1]) then
  return -1   -- 用户超限，换段也没用，直接终止
end
local stock = redis.call('GET', KEYS[2])
if (not stock) or tonumber(stock) < tonumber(ARGV[2]) then
  return -2   -- 该段售罄，可尝试下一段
end
redis.call('DECRBY', KEYS[2], ARGV[2])
redis.call('INCRBY', KEYS[1], ARGV[2])
redis.call('EXPIRE', KEYS[1], ARGV[3])
return 0      -- 扣减成功
```

Java 侧（Spring 风格伪代码，含字节的"随机不重复轮询 + 售罄段跳过"）：

```java
@Service
public class ClaimService {
    private static final DefaultRedisScript<Long> DEDUCT_LUA = new DefaultRedisScript<>(LUA, Long.class);
    private final Set<Long>[] exhaustedSegs; // 每实例本地记录的已耗尽段(定期重置)

    /** 发券/领券核心。返回值三态：成功 / 用户超限 / 售罄 */
    public ClaimResult claim(long userId, long templateId, String idemNo) {
        Template t = templateCache.get(templateId);            // ① 二级缓存读模板
        Asserts.check(t.getStatus() == 1 && t.inValidPeriod(), "模板不可用");
        if (soldOutCache.isSoldOut(templateId)) return ClaimResult.SOLD_OUT; // ② 售罄前置

        for (int seg : shuffleSkipExhausted(t.getSegCount())) { // ③ 随机不重复轮询
            Long r = stringRedisTemplate.execute(DEDUCT_LUA,
                List.of(ulKey(templateId, userId), skKey(templateId, seg)),
                String.valueOf(t.getLimitPerUser()), "1",
                String.valueOf(ttlWithRandom()));
            if (r == 0)   return persistCoupon(userId, t, idemNo, seg);
            if (r == -1)  return ClaimResult.OVER_USER_LIMIT;   // 超限无需换段
            exhaustedSegs[(int) templateId].add((long) seg);    // -2: 标记跳过
        }
        soldOutCache.markSoldOut(templateId);                   // 全段尽 → 置售罄标记
        return ClaimResult.SOLD_OUT;
    }

    private ClaimResult persistCoupon(long userId, Template t, String idemNo, int seg) {
        UserCoupon uc = UserCoupon.of(Snowflake.nextId(), userId, t, idemNo);
        try {
            userCouponMapper.insert(uc);                        // ④ 分片路由落库(唯一索引兜底幂等)
            mqProducer.sendAsync(FLOW_TOPIC, FlowEvent.issue(uc)); // ⑤ 异步流水/计数
            return ClaimResult.ok(uc);
        } catch (DuplicateKeyException e) {                     // ⑥ 幂等冲突
            rollbackRedis(t, userId, seg);                      //    回滚本次Redis扣减
            return ClaimResult.duplicated(userCouponMapper.findByIdem(idemNo));
        } catch (Exception e) {
            compensateRecorder.save(userId, t.getTemplateId(), seg, idemNo); // ⑦ 补偿表
            return ClaimResult.ok(uc); // 库存已扣、券已定，按成功返回，补偿任务保证落库
        }
    }
}
```

第 ⑦ 步是整个方案资损控制的命门：Redis 扣成功、DB 落库失败时，绝不能简单返回失败让用户重试（幂等号相同会再撞一次），而是进补偿表，由定时任务重试插入；多次失败则人工介入。对账兜底见 4.5。

### 4.4 领券全链路时序（编号）

1. 上游携带 `userId / templateId / idempotentNo / source` 调用发券接口（超时 500ms，内部预算 100ms，字节的服务治理基线）。
2. 读本地缓存取模板；miss 则读 Redis，再 miss 回源 MySQL 主库并回填两级。
3. 校验：模板状态、有效期、人群/黑白名单（适用门店打平 key EXISTS 判定）。
4. 查本地售罄标记，售罄直接快速失败。
5. 生成分段随机不重复序列，逐段执行 Lua（限领 + 扣减原子）。
6. 某段扣减成功 → 雪花生成 couponId → 按 userId 路由分片插入 `user_coupon`（一次非事务写入）。
7. 唯一索引冲突 → 回滚 Redis 扣减，查库返回历史结果（幂等语义）。
8. 插入异常（非冲突）→ 写补偿表，按成功应答，异步补偿。
9. 成功 → 异步发 MQ 流水（发放统计、ES 同步、消息中心通知）。
10. 兜底：小时级对账任务 + 券到期由 RocketMQ 延时消息循环投递推进状态（延时上限小于有效期时，消息到期检查未过期则重新投递）。

### 4.5 一致性、对账与故障重建

- **库存对账（每小时）**：`Redis各段扣减总量` vs `DB 该段实际落券数(按template_id聚合user_coupon)`，差异行写 `coupon_stock_segment.db_used_qty` 并告警。Redis 侧只作为"加速副本"，账本真相在 DB。
- **Redis 故障重建**：以 `total_qty - db_used_qty` 为基准重建分段 key，并额外扣减一个安全余量（如每段 5%，封顶补偿）——原则是**宁可少卖不能超卖**：少卖可人工补段，超卖是资损。
- **模板缓存一致性**：变更时 DB `version+1` → 删 Redis key → 发版本广播（MQ 广播模式）让所有实例失效本地缓存；定时任务兜底刷新，回写 Redis 前抢分布式锁防止多实例重复回源（字节方案）。
- **跨片查询**：运营侧按模板/时间/人群检索，通过 binlog → Canal → RocketMQ → ES 异步宽表，禁止线上广播全分片。

### 4.6 定向发券与退券回退在存储层的动作

两条低频但量大/敏感的链路，存储动作与 C 端领券不同，单独说明：

**定向发券（后台圈人，亿级）**：不抢 Redis 库存（人群包是运营圈定的，库存按人群包大小预占，建任务时就把各分段配额划走），存储侧动作是三件事的组合（vivo 的优化范式）：① 去事务——不包大事务，每个批次独立落库，失败的记入失败明细表供重试，走最终一致；② 内存归集批量插入——圈人结果按 `hash(uid)` 预路由，把同一库同一表的用户归成一堆，一次 batch insert，总插入次数最多等于库表总数 M，而不是用户数；③ 参数动态调速——单批人数、单次读库量、发往消息中心的用户数全部可配置，用配置控制峰值写入速率，避免把分片集群打抖。

**退券回退（订单退款）**：核销时把 `user_coupon.status` 置 2 并写 `order_id`；退款回退则走状态机 `2 → 4`（或重新激活为 0，取决于券是否还在有效期）。存储要点有二：其一，回退必须带 `order_id` 做条件更新（`WHERE coupon_id=? AND status=2 AND order_id=?`，乐观风格），防止并发退款把一张券回退两次、用户拿一张券核销两单；其二，若回退时补发库存，走与领取相同的分段通道（随机段 INCRBY），保证对账口径不变。

## 五、素材间的方案分歧与推荐

1. **库存扣减放 DB 还是 Redis**（最大分歧）：vivo 选"MySQL 分段库存字段 + 随机段扣 + 定时同步"，明确说了放弃 Redis 的原因是缓存丢失/宕机恢复与不一致难处理；字节选"Redis 扣减 + MySQL 一次非事务写入"，用幂等索引与补偿对账兜一致性。
   **推荐：按峰值决策。** 发券峰值 < 数千 QPS 且团队小 → vivo 的 DB 分段方案，强一致、免对账，是性价比极高的解；目标十万级 QPS → 只能走 Redis Lua 扣减（30 个 MySQL 分片全给落库都不够，没预算再扛行锁库存）。两套方案的公共骨架其实相同：**分段打散 + 唯一索引兜底 + 定时对账**，差别只在"扣减的前台"是 DB 还是 Redis。
2. **分片键算法**：vivo 的 `hash(uid)%M / hash/M %N` vs 字节的 uid 后四位。推荐完整 hash（抗运营倾斜），并保留 vivo 公式的扩容友好性。
3. **热点打散手段**：字节"分段库存"（写）与京东到家"散列多份/本地前置"（读）并不冲突，是读写两条路径各自的正解；真正的分歧点在于"key 备份"是否可用于发券——京东到家明确否定（写场景多副本无法合并扣减），推荐严格遵守。
4. **模板缓存回源策略**：字节用"定时任务刷新 + 分布式锁保护回写"，常规做法是 cache-aside 按需加载。推荐两者叠加：模板低频变更、高频读取，变更主动失效（删 key + 广播本地）保实时性，定时刷新保最终一致，被动回源只做最后兜底。
5. **用户券列表是否进 Redis**：京东到家建了用户券缓存集群，字节未提及。推荐谨慎：列表写多读相对少，缓存失效率高、一致性成本大；只缓存模板与计数类小 key，列表靠分库分表 + 索引直查，读不动再加短 TTL 的第一页缓存。

## 六、踩坑清单（按严重程度降序）

1. **【资损级】Redis 扣减成功、DB 落库失败后不做补偿** → 库存虚扣、用户没券或对账时超发。发现：对账任务出现"Redis 扣减量 > DB 落券数"的系统性差值。防：补偿表 + 重试落库 + 回滚脚本双通道；唯一索引冲突必须捕获 `DuplicateKeyException` 转幂等返回，而不是当普通异常抛给用户。
2. **【资损级】限领校验与库存扣减不在同一原子操作** → 并发窗口内同一用户领超（vivo 的超领时序）。发现：压测脚本同一 uid 并发 50 次领券，落库数 > 限领数。防：Lua 内同做两件事（4.3 脚本）；批量领券必须逐券加锁/逐券原子，组合 key 互斥是假锁。
3. **【可用性级】大 Value 让整个 Redis 集群"集体变慢"且无慢日志** → 京东到家真实案例：上万门店集合 value 单次读阻塞主线程，200+ key 场景经验定位失效。发现：分片流出带宽监控 + "主从切换观察流出量搬家"这一兜底手段。防：设计期 Value 上限评审（8000 阈值）；判定型数据一律打平成 EXISTS；清理大 key 用 SCAN 渐进或 UNLINK，禁止 DEL。
4. **【可用性级】单模板写热点打爆 Redis 分片**（单分片写约 2w QPS）。发现：单分片 QPS/网卡监控告警、其他分片空闲的倾斜形态。防：热点模板建券时预分段 + 随机不重复轮询；售罄后置本地售罄标记拦住穿透流量。
5. **【资损级】分段库存段间不均衡造成假售罄**：随机扣减天然使各段同步耗尽，但定向发券/补偿路径固定打某几段时会出现"0 号段空、其他段有货却返回售罄"。发现：段间余量方差监控。防：记录耗尽段并跳过（字节方案）；对账任务触发段间余量再平衡（从富余段搬库存到耗尽段）。
6. **【资损级】Redis 宕机后按"总库存"全量重建** → 已发部分被凭空补回，必然超卖。发现：重建后对账持续为负。防：重建公式固定为 `分段总量 - DB已落券数 - 安全余量`，DB 是唯一账本。
7. **【一致性级】本地缓存模板陈旧 → 已暂停的券继续发出**。发现：运营停券后仍有限量发券流水。防：本地缓存短 TTL（秒级）+ 变更广播失效 + 模板携带 version 比对；本地缓存只放"小而不常变"的数据，防 GC 压力（京东到地的提醒）。
8. **【性能级】缓存 key 集中过期**：定期删除占用 CPU 时间片（源码上慢周期最多占 25% CPU），大批同 TTL key 集中到期会拖慢整个实例。发现：周期性 CPU 毛刺与过期 key 数曲线重合。防：所有 TTL 加随机抖动；key 尽量都设过期，配合在非高峰期对主节点 SCAN 触发惰性清理。
9. **【性能级】主从延迟下从库读到脏数据**：刚领的券从库里查不到、从库 count 校验不准。发现：用户反馈"领完列表没有"；主从延迟监控（正常 <1ms，vivo 数据）。防：写后读走主库或读 Redis；限领类计数校验一律走 Redis 主节点而非 DB 从库。
10. **【演进级】分片键选错（如按券码/订单号分片）** → "查我的券"退化为全分片广播。发现：一次查询放大成 N×M 次 DB 查询的监控形态。防：以最高频查询"用户维度查券"定分片键（userId），跨维度查询一律走 ES/宽表异步链路；上线前用查询流量画像评审。
