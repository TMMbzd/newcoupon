# L3+L4 计数自愈与占用单×券状态交叉核对——复现与技术方案（2026-09-15）

> **状态：已批准并实施（2026-09-15，用户批准；4 红灯转绿 + 134/134 全量回归；多方评审见 §6）**。
> 前置阅读：无。两项独立，可分别批准。
> 配套：教学文档 study/09b；STATUS 勾稽 L3/L4。

---

## 0. 一句话

**L3**：Redis 用户限领计数失忆后，合法领取被**永久拒绝**且计数永不修复——修法是撞索引时以 DB 行数为权威自愈并透明重试。**L4**：对账只查库存维度，"券状态↔占用单状态"这一族不一致**无人查**——修法是日审加双向交叉核对，不一致落漂移表告警。

---

## 1. L3：用户限领计数自愈

### 1.1 复现（红灯实锤，2026-09-15）

场景推演（限领 3、已领 2、Redis 计数失忆）：

```
领第3张 → 闸门读到 ul=0（失忆）→ 放行，seq = ul0+1 = 1
        → DB 插入 seq=1 撞 uk_user_seq（该用户已有 seq=1,2）→ 事务回滚
        → cancel 把 ul 减回 0 → classifyAfterRollback 抛"已达限领上限"
用户视角：只领了 2/3，第 3 张被拒；重试 → seq 又从 1 数起 → 又撞 → 又被拒——**永久拒绝**
```

红灯输出：`BizException: 已达限领上限`（L3①）；`expected: 2L`——真达限被拒后计数也没修复（L3②）；控制组（L4③ 同理）不误伤。病灶代码：[ReceiveAppService.classifyAfterRollback 行226-235](../src/main/java/com/newcoupon/application/service/ReceiveAppService.java#L226-L235)——撞 uk_user_seq 时直接抛 3002，无任何修复。

**为什么不修会一直疼**：DB 唯一索引兜住了超发（红线未破），但计数永远错着——该用户今后每次领券都白走一次 DB 写-回滚，且错误提示是谎言（"已达限领"实际是 2/3）。

### 1.2 设计裁决

| # | 裁决 | 理由 | 否了什么 |
|---|---|---|---|
| D1 | 自愈锚点=撞 uk_user_seq 的时刻，权威=DB 行数 COUNT(user_id, template_id) | 撞索引这一刻恰好证明"Redis 计数 ≠ DB 事实"；COUNT 走 uk_user_seq(user_id, template_id, seq) 最左两列——**零新增索引** | 定时巡检自愈（周期慢；撞索引时刻是天然免费的触发点） |
| D2 | 两分支：COUNT ≥ 限领 → SET ul=COUNT + 抛 3002（**正确的拒绝**）；COUNT < 限领 → SET ul=COUNT + **透明重试本次领取一次** | 真达限就该拒（但计数修好，下次闸门在 Redis 层就拦住）；未达限说明失忆，用户无感补上 | 一律拒绝让用户自己重试（提示已是谎言，重试一次凭什么就成） |
| D3 | 重试复用原 requestId，仅一层（retryOnce 标志防循环） | cancel 已 DEL Redis 幂等键（允许同请求重试是既有设计）；DB 侧 uk_idem 因第一次回滚不存在 | 换新 requestId（凭空造请求；幂等锚点漂移） |
| D4 | SET 与并发 INCR 的竞态：重置可能覆盖并发请求的 +1 | 最坏=计数短暂偏低→闸门多放行→seq 重复→**又撞索引**（回到兜底，不超发）——方向安全，比永久拒绝好 | 加锁串行化自愈（为一个低频事件引入分布式锁，负资产） |
| D5 | 新端口两枚：UserCouponRepository.countByUserAndTemplate；RedisStockGateway.setUserCount | 最小改动 | —— |

### 1.3 实施清单（L3）

| 文件 | 改动 |
|---|---|
| `UserCouponMapper` / `UserCouponRepository`(+Impl) | + `countByUserAndTemplate(userId, templateId)`：`SELECT COUNT(*) ... WHERE user_id=? AND template_id=?`（走 uk_user_seq 最左两列） |
| `RedisStockGateway` | + `setUserCount(templateId, userId, n)`（无条件 SET——重置语义，与懒重建的条件 SET 区分） |
| `ReceiveAppService` | `classifyAfterRollback` 改造：uk_idem 命中→幂等（不变）；否则 COUNT→D2 两分支；receive 增加 retryOnce 内部重试通道 |

## 2. L4：占用单×券状态交叉核对

### 2.1 复现（红灯实锤，2026-09-15）

两个注入场景 + 现有全部对账跑完，漂移表零记录：

- 正向注入：券被改回"待使用"、占用单仍"占用中"（模拟人工改库/历史残留）→ 日审沉默；
- 反向注入：占用单被改"已释放"、券仍"已锁定"→ 同样沉默；
- 控制组：一致的锁定对不误报 ✅（现状已成立）。

成因谱系：历史 bug（如已修复的 F1 半收场残局）、人工改库、未发现的并发窗口——**没人查就永远沉默**，直到客服/用户投诉才暴露。

### 2.2 设计裁决

| # | 裁决 | 理由 | 否了什么 |
|---|---|---|---|
| D6 | 双向核对基于两个**小集合**：A=全部占用中合同（`coupon_usage WHERE status=0`，走 V7 idx_occupy 前缀——在途占用天然小）；B=全部锁定中券（`user_coupon WHERE status=1`，走 idx_expire 的 status 前缀）。A 中券不在 B=USAGE_HANGS；B 中券不在 A=LOCK_HANGS | 两个集合都索引命中、都是"在途"小集合（容量数学同 08c §4.5 的论证：在途占用≈在途订单数） | 逐占用单回查券（反向无 user_coupon_id 索引）；全表 JOIN |
| D7 | 执行位置=并入库存日审（同一任务、同一把锁、同一张漂移表） | 频率低（每日）、集合小；独立任务等量级到了再拆 | 并入 60s 巡检（资产审计不需要秒级）；新任务（多一个调度入口换不来收益） |
| D8 | **只告警不自愈**（落表+ERROR 日志，不修数据） | 状态谁对谁错无从判定（人工改库可能是对的）——与"账本自相矛盾→人工"同一立场 | 自动修复（没有可信基准，是赌博） |
| D9 | 复用 stock_drift_log：template_id 取券的模板、库存三列填 0、action 用新值 `USAGE_HANGS`/`LOCK_HANGS`、detail 带券id+usage_no+两侧状态 | 表结构通用（"漂移留痕"本就不限库存维度）；避免新表 | 新建表（一张每天几行的表不值得） |
| D10 | 两侧各 LIMIT 5000/轮，超出按数量告警 | 防一次捞爆；真出事数量先炸（同审计 LIMIT 1000 的定位） | 无限捞 |

### 2.3 实施清单（L4）

| 文件 | 改动 |
|---|---|
| `CouponUsageMapper`(+Repository/Impl) | + `selectOccupying(limit)`：`SELECT usage_no, user_coupon_id, order_no FROM coupon_usage WHERE status=0 LIMIT ?` |
| `UserCouponMapper`(+Repository/Impl) | + `selectLockedBrief(limit)`：`SELECT id, template_id FROM user_coupon WHERE status=1 LIMIT ?` |
| `StockReconcileService.dailyAudit` | 日审末尾追加交叉核对段（D6 双向 diff + D9 落表 + 告警日志） |

## 6. 多方评审记录（2026-09-15，用户裁定"多方审查、集思广益"）

Workflow 四视角（并发/正确性/容量/运维）×27 agent，13 条发现经独立怀疑者对抗核实全部为真，去重后 4 个根因。**全部修复（回归 +1：L3③ 空洞场景）+ 3 项登记**：

| 根因 | 确认发现 | 修复 |
|---|---|---|
| **A·seq 空洞死循环**（high×2） | 自愈值用 COUNT，但重试序号=ul+1——补偿路径泄漏的在途计数会造持久空洞（行集 {1,2,3,4,6}，COUNT=5、MAX=6），用 COUNT 自愈→重试 seq=6 撞行 6→retryOnce 耗尽→**永久 3002 且无告警** | 两个 DB 读数分工：COUNT 管**限领判断**（行数语义），MAX(seq) 管**自愈写入值**（下一序号必须大于全部现有）；重试仍撞+未达限→落漂移表（UL_HOLE）+抛可重试 DEGRADED（绝不谎报"已达限领"）。新增 maxSeqByUserAndTemplate（同走 uk_user_seq 前缀） |
| **B·L4 假阳性**（medium×2+截断3条） | A/B 两集合非同一瞬间（秒级窗口），窗口内提交的 lock/confirm/release/超时收场都制造方向相反的假"需人工"；截断后仍 diff→批量假阳性 | 三重防护：A 侧只取"占用超10分钟"（在途排除，复用锁龄阈值语义）；**截断前置早退**（触顶只落 CROSSCHECK_TRUNCATED，不出残缺 diff）；每个候选**点查复核**（重读券+点查占用单——单券原子事务使二次确认后假阳性收敛到近零，同巡检两轮确认的惯例） |
| **C·限频吞告警**（low×2） | 交叉核对复用按模板 1 小时限频——同模板多张真悬挂只有第一张落表，审计留痕系统性少记 | L4 专用落表通道（天级任务无需限频，try-catch 防阻断） |
| **D·SET 覆盖并发 INCR**（low×2） | 自愈 SET 与同用户并发请求的 INCR 竞态→偶发假拒绝 | 已被 A 的"DEGRADED 替代 3002"顺带修掉（错误码诚实化，终态自愈）；per-user 自愈锁**登记不做**（为低频事件加锁是负资产） |

**登记未修**（评审建议的后续项）：① 治本——对账修复路径把泄漏的 per-user ul 一并校准（并入 ADR-0009 迁移时的 ul 维度对账）；② 交叉核对两查询投影列收窄（SELECT * → 仅 diff 所需列，集合小暂不做）；③ USAGE_HANGS 复核的 findById 为 64 分表广播（只在异常候选触发，正常态零次）。

测试基线 **135**（+6：L3 三场景含空洞回归、L4 三场景、单测 +2 更新语义）。
