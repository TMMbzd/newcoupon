# ADR-0014：结算主体可选与出资/结算正交

- **状态**：已接受（框架，2026-10-18）；**核心参数待拍板**：结算模式、字段名、旧模板处理
- **实施状态**：环 1 已实施（V22，灰度 `trade.settle_party.enabled` 默认关）；主体日汇总/门店/结算时点未做
- **关联**：00 §3.2、01 G1/G5/G10、02 §2.2/§2.6/§2.7/§2.8、05 环 1、ADR-0012、ADR-0015

## 背景

一个租户下可以有多个商家：电商平台有商家/门店，本地生活有门店，车企有经销商，银行有商户。券的优惠最终要记到“谁头上”、平台和“谁”结算，不能只记一个笼统的“商家承担”。

当前实现只有：

- `funder_type`：平台/商家/共担；
- 分账行上的 `platform_burden` / `merchant_burden`；
- 没有 `settle_party_id`；
- `merchant_burden` 是历史字段名，实际表示“非平台出资方承担的成本”，**不是“平台应付商家的钱”**。

这带来三个问题：

1. 平台券跨多个商家时，平台补贴无法按商家拆分；
2. 商家出资/共担券无法证明“只作用于绑定商家的行”；
3. 退款只能按原分账冲回金额，但无法按商家出结算数据。

同时，视频会员、SaaS 等产品没有“商家”概念，不能被强制要求传主体。

## 决策

### 1. 结算主体是可选维度

- 订单行可选 `settlePartyId`（**推荐名**，最终命名待拍板；`merchantId` 只作为电商场景的领域别名，不作为契约字段）；
- **平台券 / 没有商家概念的产品**：不传主体落 `__default__`，不冒充真实主体；
- **商家出资/共担券**：必须绑定一个主体；每个命中的订单行必须有主体（或与模板绑定的主体一致）。**缺失时返回明确错误/不可用，禁止用 `__default__` 兜底**，避免把 A 商家的券算到未归属行；
- 平台券默认租户级（跨主体）；**是否允许模板指定“只作用于某些主体”待拍板（#3）**；
- 模板上的“绑定主体”只对商家出资/共担券必填，发布后不可变。

### 2. 出资与结算正交

| 维度 | 回答的问题 | 字段 |
|---|---|---|
| 成本承担 | 优惠成本由谁承担 | `funder_type` + `platform_burden` / `merchant_burden` |
| 结算归属 | 平台和谁结算 | `app_id` + `settle_party_id` |

示例：平台出 10 元补贴、和商家 M 结算。

- 成本承担：平台 10、商家 M 0；
- 结算应付：平台应付 M 10；
- 不能因为“商家承担 0”就认为平台不用付钱。

**平台应付是条件公式，不是已拍板口径**：

- 在“商家自己收款、平台补差额”模式下，平台应付某结算主体 ≈ 该主体行上的 `platform_burden` 净额；
- 在“平台代收再结算”模式下，应付口径可能包含服务费、全额结算、退款冲正、尾差，不能直接用 `platform_burden`；
- 结算模式本身**尚未拍板（#4）**，因此环 3 出结算数据前必须先拍板；环 1 只落“归属字段”，不产出平台应付；
- `merchant_burden` 是商家自己少收的钱，不是平台现金支出。

### 3. 行级归属落到分账与退款明细

- `coupon_share_detail` 增加 `app_id` + `settle_party_id`；
- `coupon_refund_detail` 增加 `app_id` + `settle_party_id`；
- 退款单头只加 `app_id`（退款是聚合单据，主体在明细）；
- **退款从原分账行复制主体**，不读取退款请求里的主体，避免调用方改归属；
- 老式核销（无 `items`）/老式退款不伪造行级归属，不进入按主体结算。

### 4. 范围过滤顺序

先按结算主体过滤，再按品类/SKU 过滤；门槛/折扣基数按“主体范围内、进入本层前的行剩余金额”算：

```text
订单行
  → 过滤出本券绑定的结算主体行
  → 再过滤出本券范围（品类/SKU）
  → 按剩余金额判门槛
  → 按剩余金额比例分摊
```

商家 A 的券不能拿商家 B 的金额凑门槛；平台券跨 A/B 时按行拆平台应付。

### 5. 迁移策略（V22）

- `coupon_template` 加 `settle_party_id VARCHAR(64) NULL`（平台券可空；商家/共担必填；发布时校验）；可选 `rule_version`；存量 `settle_party_id` 置 `__default__` + `LEGACY_PARTY_MISSING` 告警；
  - 平台券语义：`NULL` = 租户级（按订单行主体解析）；`__default__` = 历史兼容哨兵（视同未绑定，但打告警）。新平台券建议写 `NULL`，不要写 `__default__`；
- `coupon_share_detail` / `coupon_refund_detail` 加 `app_id VARCHAR(32) NOT NULL DEFAULT '1'`、`settle_party_id VARCHAR(64) NOT NULL DEFAULT '__default__'`；
  - 推荐“非空 + 默认哨兵”，而不是“可空 + 每行非空”的自相矛盾；`__default__` 表示“未归属/无商家概念”，不表示真实主体；
  - 存量 `app_id` 从 `coupon_template.app_id` 回填；存量 `settle_party_id` 置 `__default__`，不猜真实主体；
- **`pricing_id` 不在 V22**：它是环 2 的 V23 快照表/列，避免把价格快照和主体迁移绑在一起；
- 加索引（每个索引对应一个查询）：
  - `idx_share_party (app_id, settle_party_id, create_time)`：按主体日汇总/查询；
  - `idx_share_tpl_party (template_id, settle_party_id, create_time)`：按模板+主体查退款/对账；
  - 退款明细同构；具体索引名以迁移为准；
- **不动 64 张 `coupon_usage` 分表**；主体在分账/退款明细，不进入占用单；
- 旧模板处理是**环 1 开工前必须拍板**的阻塞项（#2）：
  - 推荐：存量商家/共担模板迁移时标 `__default__` 并打 `LEGACY_PARTY_MISSING` 告警；新模板在发布时强制要求主体；
  - 不推荐：让旧商家/共担模板静默落 `__default__` 并参与真实结算——会把未归属行算成真实主体；
- 回滚：新列有默认值、新索引可删；关闭新路径即回退旧行为，不删数据。

### 6. 旧调用方兼容

- **平台券 / 没有商家概念的产品**：不传主体仍成功，落 `__default__`，行为与旧版一致；
- **商家出资/共担券**：如果订单行没有主体，券不可用/返回明确错误；**不能**用 `__default__` 兜底。旧模板（商家/共担但没有主体）按 §5 的迁移策略处理，且不能进入真实结算；
- 老式核销/退款不写主体，不能按主体结算；接入指南写明；
- 旧调用方不获得“按主体结算”的保证；要获得该保证，必须传主体/升级到新模板。

## 理由

1. **多商家租户的财务前提**：没有主体，平台补贴无法按商家拆，商家也无法对账；
2. **退款归属**：退款必须冲回原主体，不能由退款请求改归属；
3. **可选性**：视频/SaaS 没有商家，强制主体会迫使它们造假数据；
4. **不改 64 张分表**：主体是分账/退款维度，不是占用单状态；改 64 张分表代价高、风险大；
5. **与价格快照解耦**：主体先落库，`pricingId` 再冻结“每行主体+分摊”；顺序不能反。

## 后果

### 正面

- 一单多主体可分账、可退款、可按主体出日汇总；
- 平台券跨主体时能拆平台应付；
- 没有商家的产品不受影响，落 `__default__`。

### 代价与边界

- 存量订单没有真实主体，只能 `__default__`，财务无法追溯真实商家；
- 模板没有更新接口，主体变更只能新建模板；
- 商家主数据/结算账户/打款不在内核，主体 ID 由订单系统提供；
- 结算只到“数据”，不做结算单/打款/发票/税务；
- 老式核销/退款不进入按主体结算。

## 备选方案（已否决）

1. **所有模板强制 `merchantId`**：视频/SaaS 没有商家，会被迫造假；否决。
2. **把 `settle_party_id` 放到 `coupon_usage`**：要改 64 张分表，代价高；且主体是行级属性，不是占用单状态；否决。
3. **结算完全留给订单/财务系统**：券内核仍需要行级归属来退款和出结算数据；没有主体，退款只能按金额不能按商家；否决。
4. **只做模板级主体，不做行级**：平台券跨多商家时无法按行拆；否决。
5. **用 `merchant_burden` 直接当平台应付**：语义错误，会把“商家少收”当成“平台应付”；否决。

## 验收（环 1）

- 一单 A/B 两个主体，分账/退款主体正确；
- A 商家券只命中 A，B 不能帮凑门槛；
- 退 A 只冲 A；平台券跨主体按行拆分应付；
- 旧调用方不传主体仍成功，落 `__default__`；
- 跨租户读写拒绝；
- 老式核销/退款不伪造主体，且文档写明不可按主体结算。
