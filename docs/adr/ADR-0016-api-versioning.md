# ADR-0016：API 版本与兼容策略

- **状态**：已接受（框架，2026-10-18）；**参数待拍板**：v2 触发条件、迁移期、契约测试工具、事件 Schema 格式
- **实施状态**：部分实现；`/open/v1` 已存在，正式废弃流程/契约测试/沙箱未做
- **关联**：01 §7、03 §11、04 §6、05 环 4、ADR-0013

## 背景

券内核服务多个产品/外部企业，接入方一旦上线，不能因为内核改字段/改语义就被动宕机。当前已有 `/open/v1`、稳定错误码、字段只增不改的约定，但还缺：

- 正式的废弃/下线流程；
- 契约测试；
- 沙箱；
- 事件/Webhook 的 Schema 版本；
- 旧版本行为变化的公告机制。

行业公开做法差异很大：

- Voucherify：日期化整版 API，项目 pin 版本，请求头可覆盖；
- Stripe：月度非破坏版本 + 半年 major，`Stripe-Version` 头；
- Shopify：季度版本，支持约 12 个月；
- 阿里 TOP：协议版本 `v=2.0` + 带日期公告；
- 京东：协议版本 `v=1.0/2.0` + 方法名；
- 美团：固定 `version=2` + 字段级回收通知。

我们不需要复制某一家，但需要一个**接入方敢依赖**的稳定契约。

## 决策

### 1. 路径版本

- 开放面：`/open/v1`；
- 破坏性变更：新增 `/open/v2`，不改变 `/open/v1` 的已有语义；
- 不做“按租户/按接入方”的多版本矩阵——版本是 API 面的属性，不是租户属性；
- 内部面 `/api` 不是面向租户的版本化 API，但平台运营脚本仍按兼容规则演进。

### 2. 字段兼容

- **只增不改**：新增字段可选；不删除已有字段、不改变已有字段语义/默认值；
- 客户端必须忽略未知字段（服务端 Jackson 默认忽略未知字段，签名头解析也忽略未知字段）；
- 枚举新增值视为兼容变更，但客户端必须有“未知值兜底”；
- 破坏性变更（删除/改语义/改必填/改默认）必须走新版本。

### 3. 错误码兼容

- 错误码只增不改；已有错误码语义不变；
- 分段保持：0 成功 / 1xxx 参数 / 2xxx 模板 / 3xxx 领券 / 4xxx 用券 / 5xxx 系统 / 6xxx 开放面 / 7xxx 风控；
- HTTP 状态与业务码的映射保持稳定；新增错误码要进 01/03 的表；
- 错误信息可读，但不泄露堆栈/SQL/密钥；
- **已知例外（L63）**：存在性语义尚未统一（403/6011 二选一），在拍板前不承诺所有错误路径的 HTTP 映射完全稳定；这条例外不构成“给已有错误码加新语义”的许可。

### 4. 废弃流程

```text
公告（日期、影响、迁移方式）
  → 双版本并行
  → 迁移期（按接入方数量定）
  → 下线
```

- 公告必须写明：变更内容、影响的接口/字段、迁移步骤、截止日期、联系人；
- 迁移期内旧版本继续可用；
- 不静默删除字段/改变语义；
- 紧急安全下线可以缩短流程，但要留公告与补救方案。

### 5. 契约测试

- 提供方维护契约用例：认证、幂等、错误码、金额、状态、隔离；
- 接入方接入前跑一遍；CI 里跑提供方契约；
- 契约测试覆盖“旧版本兼容”用例；
- 沙箱（目标态）：外部产品先在沙箱跑通试算/锁/核销/退款，再上生产。

### 6. 事件/Webhook 版本

- 事件信封带 `eventId`、`eventType`、`eventVersion`、`occurredAt`、`data`（与 03 §10.3 的目标信封一致；`data` 即业务负载，不再另起 `payload` 字段）；
- 事件类型只增不改；新增字段可选；删除/改语义走新 `eventVersion`；
- 投递语义：至少一次 + 消费方幂等；不承诺恰好一次/顺序；
- Webhook 目标态：HMAC 签名、重试/退避、死信、URL 审批/私网拦截（见 04 §4.9）。

### 7. 当前状态

- `/open/v1`：✅ 已有；
- 字段只增不改：✅ 约定已有，但没有自动化检查；
- 错误码稳定：✅ 已有表；
- 废弃流程：❌ 未做；
- 契约测试：❌ 未做；
- 沙箱：❌ 未做；
- 对外 Webhook：❌ 未做；内部发件箱当前只有 ISSUED 事件投递。

## 理由

1. **接入方敢依赖**：多产品/外部企业接入，不能每次内核升级都改代码；
2. **可验证**：契约测试把“兼容”从口头承诺变成 CI 证据；
3. **可退出**：废弃流程让旧版本有明确生命周期，不是“永远兼容”；
4. **事件可演进**：Schema 版本 + 消费方幂等，避免 Webhook 变成不可维护的隐式契约。

## 后果

### 正面

- 接入方有稳定的升级路径；
- 兼容性有测试证据；
- 废弃/下线有公告和迁移期，减少突发故障。

### 代价与边界

- 双版本并行有维护成本；
- 契约测试需要持续维护；旧版本用例不能删；
- 沙箱需要独立 appId/环境与数据隔离；
- **v1 的下线时间由最慢租户决定**：路径版本是“API 面属性”，不能按租户单独退役；迁移期要按接入方数量留足，最慢的接入方会拖住 v1 退役；
- `/api` 不是租户版本化面，平台运营脚本仍可能受内部变更影响；
- 事件不承诺恰好一次/顺序，消费方必须自己做幂等。

## 备选方案（评估后未选）

1. **不做版本，永远只增不改**：破坏性变更不可避免（字段语义/默认值/状态机），最终会堆出无法维护的兼容层；否决。
2. **按租户多版本**：版本矩阵爆炸，测试/文档/运维成本不可控；否决。
3. **请求头/日期化版本 pin（Stripe `Stripe-Version` / Voucherify 式）**：
   - 优点：同一路径可按调用方 pin 版本，v1 退役不必等所有租户一起迁；
   - 代价：每个请求都要解析版本、灰度矩阵、缓存/签名/日志都要带版本；对接入方和运维更复杂；
   - 结论：当前接入方数量/团队规模不需要，保留为未来选项；如果 v2 迁移被最慢租户拖死，再评估。
4. **GraphQL 替代 REST 版本**：当前团队/接入方/工具链不匹配，且不解决语义兼容；否决。
5. **只靠公告、不做契约测试**：兼容性无法证明，回归靠人肉；否决。
