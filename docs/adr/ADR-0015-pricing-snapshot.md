# ADR-0015：试算价格快照 `pricingId`

- **状态**：已接受（框架，2026-10-18）；**核心参数待拍板**：写语义/幂等键、TTL、存储、错误码、灰度
- **实施状态**：目标态；环 2 实施，当前未实现
- **关联**：01 G4、02 §2.10/§3.2、03 §4/§5/§6、04 §4.7/§4.8、05 环 2、ADR-0014、ADR-0016

## 背景

试算（`calculate`）和核销（`confirm`）是两次调用。中间可能发生：

- 模板面额/门槛/范围/叠加规则被修改；
- 活动/预算/黑名单变化；
- 扩展点（资格/范围/出资）重新计算，结果不同；
- 订单行/券集合变化。

如果核销按“当前规则”重新计算，用户看到的价格、支付金额、核销记账可能不是同一套数：试算 20、核销 15，或试算不可用、核销可用。这是客诉和资损的来源。

行业公开做法提供了相邻机制，但没有一个能直接等同于“订单级价格快照”：

- Voucherify：validation 不消耗、redemption 才消耗；有可选 LOCK session，但只锁用量，不保证价格；
- SAP：购物车/订单保存促销规则版本快照，但它是规则版本，不是“一次试算的报价”；
- 美团：团购核销 prepare→consume，是验券流程，不是价格快照；
- 淘宝：活动报名有价格校验窗口/普惠券后价，是活动治理，不是订单级快照；
- 京东：价保按下单时基准，是售后补差，不是结算价快照。

所以 `pricingId` 是内核自己的契约设计，不是照抄某一家。

## 决策

### 1. 一次试算 = 一个快照

- `calculate` 返回 `pricingId`；
- 一个快照覆盖这一单的：全部商品行、券集合、每张券每行分摊、每行结算主体、模板/规则版本、归属；
- 同一订单的多张券核销**可以共用一个快照**；快照不能跨订单/跨租户复用。

### 1.1 写语义与幂等（新增，修正“试算只读”）

`calculate` 的语义分两种：

| 场景 | 行为 | 幂等 |
|---|---|---|
| 不带 `orderNo` | 纯只读，不写快照，不返回 `pricingId` | 天然幂等 |
| 带 `orderNo` 且启用 `pricingId` | 写/复用快照，返回 `pricingId` | 同 `(appId,userId,orderNo,券集合,行摘要)` 在 TTL 内复用同一 `pricingId`；行/券集合变化则生成新 ID |

- 写快照是**旁路记录**，不占券、不改券状态；但它不再是“纯只读”，01/03 的“试算只读”要改成“默认只读；带 orderNo 时写快照”；
- 同摘要复用还是每次新建，是环 2 开工前要拍板的实现细节（#1）；推荐“同摘要复用”，避免调用方重试产生多份快照；
- 快照写入失败时：不带 `pricingId` 的旧路径仍可用；带 `pricingId` 的请求 fail-closed，不静默降级。

### 2. 绑定关系

`pricingId` 必须匹配：

```text
appId + userId + orderNo + 券集合
```

- 缺少 `orderNo` 时，`pricingId` 不可用（明确报错或返回空，二选一在环 2 开工前拍板）；
- 跨租户/跨用户/跨订单/券集合不一致 → 拒绝；
- 快照不可修改；要改只能重新试算生成新 ID；
- **L70 前置契约**：券集合假设接入方在支付前把订单全部券锁完。少锁一张，快照看不到该券，“试算=核销”不成立；环 2 必须把“少锁券”作为负例/告警，或改为核销请求显式携带订单券列表。

### 3. TTL 与生命周期

- TTL 与锁券窗口/支付窗口对齐；具体值待定；
- 创建 → 锁券/核销使用 → 过期/清理；
- 过期后带 ID 拒绝（fail-closed），不静默回退到“按当前规则重算”；
- 清理任务、存储容量、监控在环 2 设计。

### 4. 快照内容

至少包含：

- 商品行：`lineNo`、金额、数量、结算主体；
- 券集合：模板/券 ID、层序、互斥组、门槛、范围、出资；
- 每券每行：优惠、平台承担、非平台承担；
- 规则版本：模板版本/规则摘要，便于审计；
- **必需扩展的结果**：资格/范围/出资的 `decisionId` 与结果；核销读冻结结果，不重新调用必需扩展；
- 不允许扩展直接返回“最终优惠金额”；内核只接受可校验的决策/参数。

### 5. 消费方式

- `calculate`：返回 `pricingId`（带 `orderNo` 时）；
- `lock` / `confirm`：可选带 `pricingId`；
- 带 ID 但过期/归属不符/券集合不一致 → **fail-closed**，返回稳定错误码；**推荐新增 `4007 PRICING_SNAPSHOT_INVALID`，不复用 1000/4002/4004**（复用已有错误码会违反 ADR-0016 的“错误码只增不改”）；最终在环 2 开工前登记 01/03；
- 不带 ID 的旧调用方：
  - 带 `items` 的核销 → 回退到现有整栈复算；
  - 不带 `items` 的老式核销 → 按调用方金额记账，不做门槛/范围/占比复算；
  - 旧调用方不获得“试算=核销”的保证。

### 6. 支付后核销失败

扩展点上线前必须先有异常态（目标 `CONFIRM_EXCEPTION`）：

- 用户已支付、核销失败时，**不能走普通释放/超时关闭把券放回 `USABLE`**；
- 否则“用户已付款 + 券回可用 = 双重优惠”；
- 异常态要暂停超时释放，进入人工/补偿流程；
- 该状态必须与 `pricingId` 一起设计，不能等扩展点上线后再补；
- **这是 02 状态机的独立变更**：在 02 §3.2 增加 `OCCUPYING → CONFIRM_EXCEPTION` 及人工/补偿出边，明确暂停 30 分钟超时释放、券不得回 `USABLE`；在 02 落地前，本节只是依赖项，不是已实现能力。

## 理由

1. **价格一致**：用户看到的价格、支付金额、核销记账必须是同一套数；
2. **扩展可回放**：必需扩展的结果冻结进快照，核销不重新调用，避免结果漂移；
3. **审计**：快照是“为什么这单是这个价”的证据；
4. **兼容**：不带 `pricingId` 的旧调用方仍可按旧路径工作，新接入方获得强保证；
5. **fail-closed**：带 ID 但校验失败时拒绝，比“静默改价”安全。

## 后果

### 正面

- 试算后改模板，带 `pricingId` 核销金额不变；
- 扩展点上线后不会因重新计算产生双重优惠；
- 客诉/资损可追溯到快照。

### 代价与边界

- `CalculateRequest` 当前没有 `orderNo`，契约要加字段；
- 快照存储/清理/大小（大订单/多券）；
- TTL 与锁窗/支付窗口要配平；
- 快照与占用单的券集合一致性要校验；
- 不带 `pricingId` 的旧调用方不获得强保证；
- 快照不能替代分账；核销后仍以分账明细为准。

## 备选方案（已否决）

1. **不做快照，核销总是按当前规则重算**：价格漂移、扩展结果漂移；否决。
2. **只快照最终金额，不快照行级分摊/主体**：退款、结算、审计没有行级依据；否决。
3. **核销时重新调用必需扩展**：结果可能变，支付后核销失败可能双重优惠；否决。
4. **每张券一个快照**：同一订单多券无法共享上下文，L64 整栈复算失去一致性；否决。
5. **快照长期保存、不过期**：存储膨胀、数据保留/隐私问题；否决。

## 验收（环 2）

- 试算后改模板，带 `pricingId` 核销金额不变；
- 过期/跨租户/跨用户/券集合不一致拒绝；
- 重复核销结果不变；
- 不带 `pricingId` 的旧调用方行为不变；
- 试算请求没有 `orderNo` 时，`pricingId` 明确不可用；
- 扩展结果冻结用例（目标）；
- 支付后核销失败进入异常态，不把券放回 `USABLE`（目标）。
