# ADR-0005: 阶段 0 省略审批流，建券即视为审批通过

- **状态**：已接受（2026-09-04）
- **背景**：设计上模板是双状态机（审批状态 × 发布状态正交），配套交叉审核（建券账号不能审券）——来自"审核不严被薅 200 余万"的真实资损事故（docs/01 第 4.3 节）。但阶段 0 是单人开发，没有第二个审核角色。
- **决策**：`CouponTemplate.create()` 初始状态固定为 `APPROVED + UNPUBLISHED`；发布仍需显式调用（两段式保留）。审批流与交叉审核在阶段 3（中台化，多角色）补齐。
- **理由**：审批的价值在"第二双眼睛"，单人环境下模拟审批角色是仪式不是防线；保留发布动作的显式性，保证"未发布不可领"的约束仍然生效。
- **后果**：上线多人运营前**必须**补齐审批流，否则本 ADR 成为资损敞口——已在 docs/00 实施路线阶段 3 验收项中登记。

## 补齐的触发条件与方案（2026-09-05 澄清补充）

**本 ADR 跳过的是"实现"，不是"设计"**——审批是 P0 级内控（交叉审核来自 200 余万资损事故的整改，docs/01 第 4.3 节），最终形态必含。当前跳过仅因单账号环境下"自己审自己"安全收益为零。

**触发条件（先到先做，不按部就班等阶段号）**：
1. 出现第二个可配置券的账号（含测试阶段）——"第二双眼睛"从这一刻起有真实价值，审批流必须先于其上线；
2. 阶段 3 中台化——多角色权限体系（RBAC）在该阶段落地，审批流是同一基础设施上的用例，边际成本最低。

**补齐方案（已预留接口，无表结构变更）**：
- `approve_status` 列与"审批通过才可发布"的校验（checkPublishable）从 V1 起即存在；
- 改动仅三处：① create() 初始状态 APPROVED→PENDING；② 新增 approve/reject 接口（校验审批人≠建券人）；③ 发布逻辑不变。
- 配套：审批消息通知、审批列表（M端）、审批操作审计入 coupon_event。
