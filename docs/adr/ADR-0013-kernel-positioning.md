# ADR-0013：券能力内核的定位与边界

- **状态**：已接受（方向，2026-10-18）；待拍板项见文末
- **实施状态**：目标态；当前实现覆盖券资产 + 计价 + 行级售后，结算主体（V22）与价格快照（V23）已实施且灰度默认关；信任边界/扩展框架/结算数据未完成
- **关联**：00 定位与能力边界、01 内核能力契约、06 能力对照与大厂实践

## 背景

多个产品都需要优惠券，但它们的活动、人群、页面、投放、商家结构各不相同。可选的路有：

1. 每个产品各自建一套券系统；
2. 建一个“大而全”的营销平台，把活动、商家、页面、结算都做进去；
3. 建一个**券能力内核**，只提供券的通用能力，产品在上层组合自己的玩法。

第 1 条会重复造轮子，且每个产品的金额/状态/幂等都要重新踩坑；第 2 条会把内核变成业务系统，任何一个产品的活动需求都可能改内核，最终不可维护。我们选择第 3 条，但必须把“内核做什么、不做什么”写死，否则会自然漂移。

## 决策

### 1. 内核做“券资产 + 计价 + 结算数据”

- **券资产**：模板、用户券实例、占用单、状态机、锁/核销/释放/退款/过期/超时；
- **计价**：试算、叠加/互斥、门槛/范围、行级分摊、出资拆分；
- **结算数据**：模板日账单、退款明细、按结算主体的日汇总（目标态）；
- **不做**：活动编排、人群圈选、页面搭建、投放、触达、商家入驻、店铺、广告、支付/打款/发票/税务。

一句话：**内核管“怎么正确地算、锁、核、退、记账、留证据”，产品管“为什么发、发给谁、怎么营销”。**

### 2. 两类接入面

| 接入面 | 用途 | 租户隔离 |
|---|---|---|
| `/open/v1` | 产品/外部企业接入；appId + HMAC + nonce + 时间窗 + 配额 | ◐ 按 appId 做资源归属隔离；**L73 未修，严格隔离未成立**（环 4） |
| `/api` | 平台运营/运维动作 + 可信平台调用方的业务写接口（lock/confirm/release/refund 白名单） | ❌ 不构成多租户隔离面 |

**需要数据隔离、配额、审计、结算边界的内部产品，也必须走 `/open/v1`。** `/api` 不是“内部产品免签名通道”；它没有 appId 身份，跨租户读写无法归因。

### 3. 机制与政策分离

- 内核提供**机制**：怎么校验、怎么算、怎么锁、怎么退、怎么记、怎么审计；
- 产品提供**政策值**：券类型、门槛、力度、范围、叠加规则、退款政策；
- 标准原语 + 配置覆盖大多数场景；长尾玩法走扩展点或产品层；
- **不做万能规则引擎**：任意规则表达式会把内核变成不可维护的黑盒，测试组合爆炸，产品也说不清“为什么这单用了这张券”。

### 4. 结算主体可选，出资与结算正交

- **出资方**回答“优惠成本由谁承担”：平台/非平台/共担；
- **结算主体**回答“平台和谁结算”：商家/门店/经销商/业务单元/租户自己；
- 没有商家概念的产品（视频会员、SaaS）不传主体，落 `__default__`；不强迫所有产品都有“商家”。

### 5. 目标态与真实态分开

- 00~07 写“应该是什么样”；
- `docs/STATUS.md`、代码、测试写“现在是什么样”；
- 冲突时先记录差距，不把目标写成已完成；
- 对外材料只引用有证据的能力，不拿目标态当卖点。

## 理由

1. **复用**：模板/实例/锁/核/退/分摊/幂等/审计是多个产品共同的，重复建设只会重复踩坑；
2. **隔离**：appId + 配额 + 审计 + 结算边界，让一个租户的问题不扩散到其他租户；
3. **可维护**：标准原语 + 配置 + 少量扩展点，比“每个产品改内核”更容易测试和演进；
4. **诚实边界**：内核不冒充营销平台、风控大脑、支付结算系统；需要外部证据的事，明确留在外部。

## 后果

### 正面

- 产品接入不需要改内核代码；标准需求用配置表达；
- 金额/状态/幂等/审计有统一实现，出问题能按同一套证据排查；
- 内核 API 可以稳定演进，不被单个产品的活动节奏拖拽。

### 代价

- 长尾玩法必须走扩展点或产品层，短期内会有“内核不直接支持”的摩擦；
- 内核不能承诺“所有产品开箱即用”；接入方需要理解原语和边界；
- `/api` 不是多租户面，内部产品要额外走 `/open/v1` 的接入流程；
- 结算只做数据，不做打款/发票/税务，财务仍需外部系统。

## 备选方案（已否决）

1. **每个产品各建一套券系统**：重复建设、金额/状态/幂等各自实现，长期维护成本最高；否决。
2. **做一个大而全的营销平台**：活动、商家、页面、结算全做；内核会被单个产品需求拖成业务系统；否决。
3. **只做券资产，不做计价**：券的可用性/分摊留在订单系统；但退款、结算、审计都需要行级归属，券资产无法独立闭环；否决。
4. **只做计价，不做券资产**：券状态/锁/核/退仍在各产品；幂等和状态机重复实现；否决。
