# ADR-0011：发件箱（Outbox）而非事务消息

日期：2026-09-23 ｜ 状态：已裁决（用户授权按路线图 P2d 开工） ｜ 关联：ADR-0006（异步补偿凭证）、ROADMAP P2d

## 决策

1. **选发件箱（Outbox），不选 RocketMQ 事务消息。**
2. **coupon_event 保持只追加的事实账本；新增 coupon_outbox 表承载投递状态**（同事务双写：事件行 + 发件箱行）。
3. **传输与发件箱解耦**：阶段一投递器写结构化日志（LogEventPublisher，MQ 未接入前可观测、可测试）；阶段二 RocketMQ 容器就绪后换实现类，**发件箱语义与表结构零改动**。

## 为什么不是事务消息（被否方案）

RocketMQ 事务消息的机制：生产者发半消息 → 回查本地事务 → 提交/回滚。否决理由：

1. **回查依赖"事务状态可查"**——我们需要为每个事件实现回查接口（按什么查？还得一张状态表），等于把 outbox 表换个名字再写一遍，却多了半消息协议的复杂度。
2. **强绑定 RocketMQ**——事务消息是 RocketMQ 私有语义，换 Kafka/RabbitMQ 全部重写；outbox 是数据库层的通用模式，传输可插拔（本次决策第 3 条直接兑现这一点）。
3. **测试与运维复杂度**——半消息、回查、悬挂消息三态需要专门演练；outbox 的失败模式就是"表里有行、status=0"，肉眼可查、SQL 可修。

（大厂实践对照：阿里内部广泛使用事务消息的场景是"跨系统分布式事务"；我们的场景是"本地事务成功后确保事件最终到达 MQ"——outbox 的标准适用域。）

## 为什么新表而不是给 coupon_event 加投递列（被否方案）

给事件表加 status/retry 列 = **投递器回写事实账本**，破坏"coupon_event 只追加不修改"的铁律（它是流式对账的事实源，ADR-0012 候选——binlog 消费的原料；原料允许被改，整个旁证体系塌方）。代价只是同一事务多一次 INSERT——对账发件箱行数 ≡ 事件行数（发放类）的守恒校验反而白得一条。

## 表与协议

```sql
coupon_outbox（单表，随 coupon_event 同库不分片）：
  event_no（UK，= coupon_event.event_no）｜event_type｜payload（JSON，消费方契约）
  status（0待投递/1已投递/2死信）｜retry_count｜next_scan_time（退避 2^retry 秒）｜last_error
```

- **写入**：领券事务内（CouponIssueTxService.issue 第四连写之后的第五写）。
- **投递**：独立调度（双通道 @XxlJob+@Scheduled，1 秒级轮询；单飞锁防多实例重复）——投递成功置 status=1；失败退避重试；**重试 ≥8 次置死信 status=2 + 漂移表告警**（人工介入，绝不丢消息——死信行还在表里）。
- **消费方幂等锚点**：payload 内嵌 event_no（与事件幂等号同源）——消费者按它去重，重投/重复消费 no-op。
- **守恒**：T+1 日审追加一条：发放类事件行数 ≡ 发件箱行数（status 任意）——同事务双写的直接推论，破了即双写协议被绕过。

## 后果

- 正面：MQ 接入日前就有可测试的投递链路（日志传输）；换 MQ 零表结构变更；消息永不丢（最坏死信在库）。
- 负面：领券事务多一次 INSERT（同库同事务，微秒级）；投递有轮询延迟（1 秒档，发券通知场景可接受；秒杀级实时场景将来需另议）。
- 阶段二待办（下一批）：RocketMQ 容器 + RocketMQEventPublisher + 消费端幂等协议 + rocketmq-exporter。
