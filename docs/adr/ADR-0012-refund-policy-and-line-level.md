# ADR-0012：行级分账与按行退款政策（2026-10-18）

## 状态

已采纳，已实施（V5 第 2 步算钱域行业标准版）。

## 背景

V5 第 2 步算钱域原先只支持“整单维度”的退款：`refund(usageNo)` 把占用单标成已退款，并给
`coupon_share_detail` 写一行镜像负行。它解决了“退款后钱不冲回”的问题，但离电商真实
售后还有四段距离：

1. 试算有行级分摊，核销落库却是订单粒度（`order_line_no` 永远为 NULL）；
2. 退款不能按商品行 + 数量退，只能整单退；
3. 核销是单券复算，不带同订单其他券的叠加上下文（L64）；
4. 范围券的门槛与折扣基数按整单金额，分摊还可能超过行金额（L66）。

行业事实（2026-10-18 调研）：

- 美团 `sku_benefit_detail` 按 SKU 记录优惠分摊，`applyPartRefund` 支持按件部分退；
- 微信支付单品退款用 `goods_detail` + `out_refund_no`，同一笔支付可多次部分退，重试复用同一单号；
- 京东限品类券的门槛按“订单中可用券商品金额”判断；
- 淘宝/京东/拼多多退一件按“下单时该件分摊后的实付价”退，读取下单快照，不按退款时活动重算；
- 部分退款通常不退券，整单退款才进入退券判断；门槛是否追回是政策，行业默认不追。

## 决策

### 1. 行号贯穿试算、核销、退款

`OrderItem` 新增可选 `lineNo`。不传时平台按列表顺序生成 `L1/L2/...`；同一订单的
试算/核销/退款必须保持相同顺序。核销按行落 `coupon_share_detail`（行号、行金额、行数量、
行优惠、平台/商家出资），每行守恒。

### 2. 范围券按范围内金额算

- 门槛：按“本券范围内、进入本层前的行剩余金额”判断；
- 折扣基数：满折按同一范围内金额算；满减/无门槛按范围内金额封顶；
- 分摊：每层按进入本层前的行剩余金额比例分，前 n-1 行向下取整、末行兜底；
  单行不超过该行剩余金额，末行溢出（最多 n-1 分）补给还有余量的行；
- 非 ALL 但没配范围值 = 配置错误，按不可用处理（不再放行全部商品）。

### 3. 核销带订单级上下文（L64）

核销时按 `(user_id, order_no)` 找回同订单**占用中/已核销**的全部占用单，按与试算相同的
“层序 + 互斥组 + 递进门槛 + 范围金额 + 逐行分摊”整栈复算，再取当前券份额。
订单里已有券进入售后（部分/全部退款）时，拒绝再核销其他券。

### 4. 退款单号是退款业务的幂等键

- 请求新增 `refundNo`；同号同参重放返回首次结果，同号异参（或已用于别的占用单）报冲突；
- 不传时服务层生成 `AUTO:<usageNo>`（只适合旧调用方“整单退一次”）；
- 同一占用单最多 50 次退款（`coupon.trade.max-refund-times`，对齐微信支付）；
- 退款单号要求**全局唯一**（建议“订单号 + 退款序号”）。当前 `coupon_refund_order.refund_no`
  是全局唯一索引，不按 appId 分作用域；不同租户复用同一退款单号会互相冲突。这与既有
  `usageNo`（订单号 + 券id）的全局唯一假设一致；多租户订单号本身应全局唯一。

### 5. 退款金额读核销快照，不重算

- 行优惠按“前 n-1 个单位取整、最后一个单位拿余数”排布；
- 本次冲回 = 累计到 `已退数量+本次数量` 的应退额 − 已冲回额；
- 平台/商家按行累计比例冲回，商家 = 行冲回 − 平台；多次退款累计不重不漏；
- 退款明细落 `coupon_refund_detail`，日账单用正分账行 − 退款明细净额（兼容旧负行）。

### 6. 券处置政策

- **部分退款**：券继续“已核销”，不退券；
- **整单退完**：券在有效期内 → 回到“待使用”；已过期 → 转“已过期”；
- **一券最多退 3 次**（`coupon.trade.max-return-times`），防止“下单-退款-再用”刷券；
- **门槛不追回**：部分退款后剩余金额跌破门槛，也不从退款中扣回已享受优惠；
  退款上限就是核销时的分摊成交价。恶意凑单由风控处理，不在退款链路现场重算。

状态机同步调整：`USED` 不再是绝对终态，新增 `REFUND_RETURN`（USED→USABLE）一条出边，
仅整单退款使用；`EXPIRED`/`INVALID` 仍是无出边终态。`CouponStateMachineTest` 从
“USED 无出边”改为“USED 只能退回到 USABLE，不能迁到其他状态”。

## 后果

### 正面

- 按行退款、行级对账、逐行出资方冲回全部闭环；
- 核销与试算同一把尺子，堵住“绕过试算直接核销”的宽松口径；
- 退款可多次、可重试、可审计，金额不受模板后续变更影响。

### 代价与已知边界

- `coupon_share_detail` 由一行变多行；日账单的 `confirm_count` 从“核销笔数”变为“分账行数”；
- 老式核销（只传 `discountAmt`、没有 items）没有行级分账，只能整单退，且没有出资方冲回明细；
  该路径仅作过渡兼容，新接入方必须传 items；
- 退款/退券次数是全局配置，暂未做租户级差异化（后续可加）；
- `coupon_usage` 在 V9 预建的 `refund_no` 列仍未使用；退款单表 `coupon_refund_order`
  是退款幂等的权威来源（列保留不删，避免再动 64 张分表）；
- L64 依赖接入方遵守“支付前把订单所有券都锁完”的契约；若某张券在核销另一张时尚未锁定，
  本次整栈复算看不到它。契约已在接入指南与测试中钉住。

## 备选方案

1. **只补退款端点，不做行级**：最快，但按行退款是电商售后核心能力，否决。
2. **在 `coupon_share_detail` 上用 `lineNo:REFUND:<refundNo>` 写负行**：能少建表，
   但行号语义被污染、多次退款易撞唯一键、退款单无法独立审计，否决。
3. **退款时按当前模板重算门槛/优惠**：与“下单快照”原则冲突，会产生“退一件显示价≠退款额”
   的客诉，否决。
4. **部分退款也追回优惠**：资金最严谨，但规则复杂、客诉高；行业默认不追，否决。
