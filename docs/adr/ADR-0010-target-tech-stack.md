# ADR-0010: 终局技术栈定版——亿级流量形态的技术选型一次性定死

- **状态**：已接受（2026-09-12）。依据用户指令："及时上最好的东西；目标是千万级甚至亿级流量系统；不要总盯着当前是单体、什么都往简单做后面大改；一开始就定好技术。"
- **本 ADR 的性质**：从此不再存在"到时候再选"的技术决策——每一层的终局选型**现在**定死；执行分批落地，但批次表同样现在写死。

---

## 0. 决策框架：两类决策，两种"定死"方式

| 类别 | 定义 | 晚定的代价 | 定死方式 |
|---|---|---|---|
| **不可逆类**（数据层） | 分库分表路由、ID 体系、数据模型、事件 schema、Redis key 规范、唯一索引 | **十倍级**：亿级数据迁移、ID 重发、索引重建都是停机级工程 | **立即全部定死并落地**（本 ADR §2 批次表；两项历史欠账=ID 与分片路由，批次二立即补） |
| **部署形态类**（运行层） | 调度平台、服务拆分、编排、消息、监控 | 一倍级：换组件不动业务代码 | **终局选型现在定死 + 分批落地 + 每项的落地触发条件现在写死**（不是"到时候再评估"） |

安全网（为什么敢上大组件）：本项目全部正确性锚在数据库原子判断（条件更新+唯一索引+恒等式对账），**不依赖任何平台件的恰好一次语义**——平台件全部可替换、可降级。这是"第一天敢用终局组件"的前提。

## 1. 终局技术栈（每层定死）

| 层 | 终局选型 | 落地 | 选择理由（一句） |
|---|---|---|---|
| 调度平台 | **XXL-JOB 2.4** | **✅ 已落地（本 ADR 同日）** | 控制台管理/执行留痕/分片广播/错过补跑；国产事实标准、文档全中文 |
| 分布式 ID | **雪花算法（Snowflake，workerId=实例序号）**，M6 升级 Leaf 号段模式 | 批次二（立即） | 自增 ID 与分库分表互斥——亿级下换 ID=全量重发，必须先于分片落地 |
| 分库分表 | **ShardingSphere-JDBC，user_id 路由，16 库 × 64 表逻辑分片，先 1 物理库承载全部逻辑表** | 批次二（立即） | 路由先行使**未来扩库=加连接串配置**，业务 SQL 零改动、无迁移窗口 |
| 消息队列 | **RocketMQ 5.x**（事务消息+任意时刻定时消息） | M5（异步化里程碑） | 定时消息替代自建加速层；事务消息承接 outbox |
| 缓存 | Redis 7（AOF），**M4 起 Redis Cluster** | 现单机→M4 集群 | hash tag/分桶已预留；Cluster 前先压测单分片上限（M3） |
| 服务形态 | **模块化单体（限界上下文包结构=拆分预案）→ 按 M8 触发条件拆微服务**；注册/配置中心 Nacos 随拆分引入 | M8 | 拆分触发条件见 §3——条件已写死，非"再看看" |
| 部署编排 | Docker Compose（现在）→ **K8s（M7，kind 本地集群演练）** | M7 | K8s 的价值在多服务编排之后；单体期上 K8s 收益为负、复杂度为正 |
| 可观测 | **Prometheus + Grafana + Alertmanager**，链路追踪 SkyWalking | M2 | Micrometer 指标先行（M2 第一批告警=Redis 内存水位+调度心跳） |
| CI/CD | Gitea + act_runner（本地，Actions 兼容）→ 可迁云端 | M2 | 全本地成本约束下的 Actions 语法兼容路线 |

## 2. 落地批次表（同样现在定死）

- **批次一（✅ 2026-09-12 已落地）**：XXL-JOB——compose 起 xxl-job-admin（复用主 MySQL 的 xxl_job 库，官方 2.4.1 建表脚本入库 docker/xxl-job/）；应用侧 xxl-job-core 执行器**条件装配**（`xxl.job.enabled`，测试默认 false）。
- **批次二（下一工作项，先于 L5）**：雪花 ID + ShardingSphere 逻辑分片路由（1 物理库 × 16 库 64 表逻辑拓扑，user_coupon/coupon_usage/coupon_expire_task 三表先行）。
- **批次三（M2）**：Prometheus/Grafana/Alertmanager + Gitea CI 流水线 + 双实例部署与蓝绿演练。
- **批次四（M3）**：全链路压测 → 数据驱动的分桶/缓存/连接池配平（压测是验证手段，不是"要不要扩"的决策点——扩的形态已由本 ADR 定死）。
- **批次五（M4-M8）**：Redis Cluster → ShardingSphere 扩物理库 → RocketMQ → kind K8s → 微服务拆分（触发条件 §3）。

## 3. 微服务与 K8s 的拆分/落地触发条件（写死，消除"到时候再说"）

**微服务拆分（M8）满足任意两条即执行**：①第三个业务方接入中台；②发布节奏冲突实害化（一域发版拖累全域 ≥2 次/月）；③单服务资源画像分化（某域需独立扩容，如发放域 5 倍于券模板域）。拆分预案=现有包边界（coupon/trade/stat/infra），Nacos+OpenFeign 届时引入。

**K8s（M7）**：微服务拆分完成或 M6 结束（先到者）；单体期间用 compose+双实例演练水平扩容（M2）。

**诚实记录（本 ADR 保留的两条专业立场）**：
1. 正确性不依赖平台件——上 XXL-JOB/消息/K8s 的前提是任务幂等、状态机原子，这些已就位（历次评审验证）。顺序反了（先平台件后幂等）的系统，平台件一挂全错——这是 18 篇素材的一致结论，也是本项目恒等式对账存在的原因。
2. ADR-0008 的教训：被推翻的从来不是"选型不够好"，是"验证不够狠"。终局组件同样要过红队评审才实施（本 ADR 的批次二起适用）。

## 4. XXL-JOB 落地细节（运维必读）

- **双通道设计**：四个调度方法同时挂 `@XxlJob`（生产通道）与 `@Scheduled`（降级通道，测试与无中心环境）——两通道同时激活时由 RedisScanLock 仲裁同轮次恰一执行（正确性本不依赖调度器）。M2 稳定一个里程碑后移除 @Scheduled。
- **执行器**：appname=`newcoupon-executor`，端口 9999，accessToken 与调度中心一致（`default_token`）；`xxl.job.enabled=true` 时装配（compose 环境变量 `XXL_JOB_ENABLED=true`）。
- **控制台**：`http://127.0.0.1:8280/xxl-job-admin`（admin/123456）。需建四个任务：

| JobHandler | cron | 路由策略 | misfire | 说明 |
|---|---|---|---|---|
| couponExpireScanJob | `0 * * * * ?` | **分片广播** | 错过立即补偿 | 过期扫描（分片=%16） |
| couponStockPatrolJob | `0 * * * * ?` | 第一个 | 错过忽略 | 库存恒等式巡检（锁内单片） |
| couponStockAuditJob | `0 47 3 * * ?` | 第一个 | 错过立即补偿 | 库存 T+1 审计 |
| couponExpireAuditJob | `0 23 4 * * ?` | 第一个 | 错过立即补偿 | 过期 T+1 审计 |

- **初始化**：`docker/xxl-job/tables_xxl_job.sql`（官方 2.4.1）随 MySQL 卷首建自动执行；老卷补装一行命令见 compose 头注释。

## 5. 后果

- 正面：所有"到时候再选"已消解为"批次表里的某一行"；批次二（ID+分片路由）完成后，亿级演进路径上**不再存在任何数据迁移级工程**；调度获得控制台/留痕/手动触发/分片广播/错过补跑全部能力。
- 认账：调度中心自身成为需运维的组件（高可用=单实例+重启策略起步，compose restart=unless-stopped；其库表随主 MySQL 备份）；双通道过渡期内同任务可能双触发（锁仲裁，代价=一次空抢）；@XxlJob 注解在测试关闭时静默不注册（依赖条件装配，若误开 enabled 测试将连不上中心——回归由 `xxl.job.enabled` 默认 false 保证）。
