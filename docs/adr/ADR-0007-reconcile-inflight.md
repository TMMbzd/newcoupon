# ADR-0007: 对账在途治理——在途计数器 + 二次复核 + 方向不对称

- **状态**：已接受（2026-09-08，评审发现 L21 后当日修复）
- **背景**：ADR-0006 第 5 条的原始对账实现（精确相等比较 + 无条件重建）存在在途竞态（L21）：领券写序"先 Redis 后 DB"，在途窗口内 Redis 必然比 `total − DB已发` 少"在途数"——流量期必然误报；重建用过期 DB 快照 SET，与在途扣减/补偿竞态，对账自己引入漂移。DB 双防线保证不超发（后果限误告警/过闸被拒/临售罄窗口，不资损），但误报与误修必须根治。
- **决策（三件套，每层杀死一种误报/误修）**：
  1. **在途计数器精确扣除**：`ReceiveInFlightCounter`（AtomicLong）在过闸后 inc、DB 终结（成功/补偿）后 finally dec。对账判定改为 `diff = expected − remaining`，`0 ≤ diff ≤ 在途 + 5（三方读残差）` ⇒ 一致。把时序差从"误差"变成"可扣除的数"；
  2. **二次复核**：疑似漂移先等 `coupon.reconcile.recheck-ms`（默认 5s，覆盖 DB 事务毫秒级+连接等待 3s）让在途落定，再量一次——**两次都超界才重建**。瞬态差异自愈，杜绝"为看起来不对就覆盖 Redis"；
  3. **方向不对称**：在途只能让 Redis 偏低（先扣后提交）；`diff < 0`（Redis 偏高）无任何合法在途解释（旧重建竞态/补偿重复征兆）——任何幅度进复核。
  - key 整个缺失（`remaining == null`）无在途歧义，立即重建。
  - `reconcileAll` 返回重建数（可观测）。
- **理由**：docs/03 素材原话即"差额定阈值告警+差异落表供财务复核"（保守路线），本 ADR 用计数器比"拍一个阈值"更精确——阈值需覆盖最大在途（并发高时误报），计数器随流量自适应。比较"瞬时电平"的跨系统对账必然撞在途窗口，这是结构性约束。
- **后果**：
  - 正面：流量期零误报；瞬态差异（在途/读错位）自愈；真漂移（kill -9/丢补偿）复核后正确重建；Redis 偏高（危险方向）任何幅度都被处理。
  - 认账：计数器是单 JVM 口径，多实例部署需换 Micrometer 汇总（并入 L16/M2）；5s 复核窗口内真漂移修复延迟 5s（可接受）；懒重建（-7）路径的重建仍有毫秒级在途竞态，量级极小（key 缺失时本就无扣减流量），不处理。
- **验证**：单测 5 分支（在途不误报/真漂移复核后重建/瞬态自愈/偏高异常/key缺失立即重建）+ 集成 3 项（真漂移重建含重建计数断言、瞬态不重建、在途窗口 Redis 不被触碰、请求完成后计数器归零）。83 测试全绿。


> ⚠️ **勘误与待加固（2026-09-07 四专家审查）**：本 ADR 三处论断需修正——①"懒重建竞态量级极小"的 dismissal 在 Redis 清库风暴场景不成立（N2）；②RESIDUAL_TOLERANCE=5 在数百 QPS 即不够（提交泄漏，R3 修正）；③"Redis 偏高无合法形态"高峰不成立。新发现 N1（售罄自持环）/N3（ul 7天TTL失忆）为高危。完整裁定与分级加固方案见《对账方案评审与加固方案-2026-09-07.md》——修复方案待批准后实施并更新本 ADR。
