# ADR-0002: 数据库 Schema 一律走 Flyway 版本化迁移

- **状态**：已接受（2026-09-03）
- **背景**：Schema 变更（建表/加列/加索引）如何管理？可选项：手工执行 SQL / Wiki 存脚本 / 迁移工具（Flyway/Liquibase）。
- **决策**：所有 DDL/DML 变更写成 `src/main/resources/db/migration/V{n}__描述.sql`，应用启动时 Flyway 自动按序执行；**禁止任何人手工改任何环境的库结构**。
- **理由**：
  1. 大厂 DBA 红线：手工改库 = 环境漂移——dev 加的索引 prod 没有，"我这里好的"事故源头；
  2. 变更进入 git 评审流：加一个索引要像改代码一样被 review（还记得 docs/01a 第八节——每个索引必须指着一条查询）；
  3. 新环境一条命令重建（`docker compose up` + 启动应用），新人第一天就能跑起完整环境；
  4. 变更历史即审计记录：谁在哪个版本改了什么，可追溯。
- **后果**：
  - 规范：脚本只增不改——已合入的 V{n} 脚本禁止修改，写新的 V{n+1} 纠正；
  - 失败的迁移要修复数据后手工处理 flyway_schema_history，团队需具备基本排查能力。
