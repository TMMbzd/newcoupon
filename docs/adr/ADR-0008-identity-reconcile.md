# ADR-0008: 库存恒等式对账与记账加固（外部方案评审综合，A1'-A8'+B4）

- **状态**：已接受（2026-09-09，用户裁定五决策点："采纳A4'，采纳A3'，保留窄域自动重建，采纳B4，维持M3压测触发"）
- **背景**：外部 AI 提交了替代架构方案（docs/方案评审.md：预留令牌 + 事件驱动修复 + 恒等式对账 + 分桶）。四视角对抗核查后确认：其**范式方向正确**（在途显式化、复式记账、恒等式验账——恒等式经修复后结构上优于我方容忍带方案，此让步由对抗核查员用逐状态验证逼出）；但其落地文档有 5 处硬伤（CROSSSLOT 结构性矛盾、pending_set 未实现、30s TTL < 50s 锁等待、3 处对我方方案的事实误读）。完整对比与裁定过程见《对账方案对比-替代架构评审与综合-2026-09-09.md》。
- **决策（把它的范式装进我们的骨架）**：
  1. **A3' 复式记账**：deduct Lua 原子追加 `INCR c:issued:{tpl}`（借方）与在途令牌 `ZADD c:pend:{tpl}`（member=`{uid}:{requestId}`，score=进入时刻 ms）。现有幂等键 `c:idem:*` 退回**纯去重缓存**职责，不再承担记账。
  2. **A4' 恒等式（无 CDC 版）**：`issued − dbi − pending ≡ 0` 任意时刻成立。
     - confirm（DB 提交成功后）：`dbi+1` 与 `ZREM 令牌` **一个 Lua 原子配对**（在途转贷方）；
     - cancel（DB 失败分类后）：`issued−1` 与 `ZREM 令牌` 原子配对（借方与在途同减）；
     - **令牌单次使用**：confirm/cancel 均以 ZREM 结果为门——重复 confirm、迟到 cancel 天然 no-op（比幂等键门控更根本的幂等）；
     - **崩溃检测**：在途令牌按时间清理（`ZREMRANGEBYSCORE`，TTL=`coupon.reconcile.inflight-ttl-ms` 默认 180s = 3×行锁等待 60s 档，物理锚定，全方案唯一时间参数）——清理掉的残留令牌立刻暴露为差值；
     - 第一层巡检（60s，一条 Lua 原子快照）：期望精确 0，**无容忍带**。连续 2 轮非 0 才进第二层（防一次性干扰；JVM 计数器 `ReceiveInFlightCounter` 整体删除）；
     - 第二层深对账：读 DB 账本归因（confirm-lost / redis-side），三守卫后修复：①pending==0 ②第二不变式 `issued_count == COUNT(user_coupon)`（互证失败=账本自相矛盾=人工，`GUARD_FAILED`）③修复幂等（三本账重置为 DB 口径）+ 漂移落表 + 24h≥5 次升级人工。
  3. **A1' 售罄分类先行 + 钉零**：`StockDeductRejectedException` 后先取新快照分类再取消——售罄 `SET stock 0`（不 INCR 回加，断 N1 过补偿自持环）；下线同样钉零；瞬时才 INCR 回加。
  4. **B4 售罄标志**：`c:so:{tpl}`，售罄取消时 SET，deduct Lua **首行短路**（售罄后 DB QPS 归 1）；**清除协议显式化**：修复后余量>0 必须 DEL（否则模板永久假死）——修复至 0 则保留。
  5. **A2' 懒重建条件化**：-7 后随机退避 50~200ms + Lua 条件 SET（风暴中首个生效）；对账修复走独立 `repair`（三本账+库存一次重置，仅守卫全过后）。
  6. **A8 漂移审计**：V3 表 `stock_drift_log`（只追加）记录三本账快照/DB 读数/动作/归因；T+1 定时审计第二不变式（`dailyAudit`）。
  7. **A5/R4/R7**：巡检单模板 try/catch 隔离；调度线程池 size=2（巡检与审计不互相饿死）。
  8. **不采纳**：第一天分桶（维持 M3 压测触发，key schema 已就绪）；对账永远只读（保留窄域自动修复，理由见下）；CDC/binlog 镜像（推迟至 M2+ 监控基建到位，confirm 侧镜像同为原子配对记账，慢速层兜住残余）。
- **理由**：恒等式把对账从"统计推断"（三方读+时间窗+容忍带+压测验证公式）变成"逻辑必然"（期望精确 0，差 1 即异常）——R3 提交泄漏、R2 模板间串扰、M1-novel 高峰隐形全族结构性消失。我方幂等键本就是预留令牌（hash tag 已修），实为小增量非重写。保留窄域自动修复的权衡：误状态在"只告警"下无自愈路径（凌晨人工），而恒等式让"修错"可探测（修错=新漂移=下轮再告警）——风险收益比与只读哲学相比已经反转。
- **后果**：
  - 正面：崩溃（kill -9）残留 180s 内暴露并在下轮修复（集成验收④）；2000 并发后三本账精确归零（验收③）；售罄自持环根除（验收⑨）；清库风暴零丢失（验收⑩）；confirm/cancel/repair 全幂等（验收⑧）；漂移全程留痕可升级。
  - 认账：成功路径多一次 confirm Redis RTT（~0.5ms）；confirm 自身失败（Redis 抖动）不阻断响应，以 dbi 滞后形态由对账按 confirm-lost 修复（少卖 0 张、多一次修复）；慢于在途 TTL 的请求会被巡检误伤一次（走修复通道自愈，非数据错误）；第一层差值≠0 恒为真事件（无"自愈"路径，唯一例外是外部瞬时干预）——两轮确认是为此保留的缓冲。
  - 已知残余：cancel 晚于 TTL 清理会 no-op（保守方向少卖 1 张额度，由修复找回）；多实例下 driftRounds 状态在 JVM 本地（仅影响确认轮数计数，不影响正确性——两实例各自达到 2 轮才修，等效限频）。
- **验证**：单测 8 分支（恒等成立/首轮疑似/确认修复/复核自愈/守卫①推迟/守卫②冻结/售罄态修复不清标志/条件重建）+ 编排层 15 分支（三变体取消形态断言、confirm 成功路径）+ 集成 10 项验收。**92 测试全绿**。实施中抓到并修复 1 个跨语言契约 Bug：Java 发送 `'sold_out'`（枚举名小写）而 Lua 比较 `'soldout'`，失配落 else 分支导致售罄走了 INCR 回加——集成验收⑨的钉零断言当场抓住。教训：跨语言字符串协议无编译器保护，契约字面量应集中在网关单侧定义。
