# 第一章 领域模型与券状态机

> ⚠️ **实现偏差指引（2026-09-05 更新至 V2 后现状）**：本章 4.2 节 DDL 是设计参考基线；实际表结构以 `src/main/resources/db/migration/` 的 V1+V2 迁移脚本为准，现状差异：① coupon_template 增加 issued_count/daily_limit/per_user_daily_limit 列；② user_coupon 增加 seq 列，唯一索引为 **uk_user_seq(user_id, template_id, seq)**（限领 N 张，V2 取代了设计稿的 uk_user_template 限领1张）；③ coupon_stock_segment 表未建（库存走 Redis 闸门 + template 行双防线，ADR-0006）。冲突裁决：表结构以迁移脚本为准，业务语义以本章为准；全部偏差见 STATUS.md。

> 本章是整个优惠券中台的"宪法层"。发放的高并发、优惠计算的组合爆炸、统计对账的口径，全部挂在这套模型之上。模型一旦定错，后面全是补丁；模型定对了，后面的难点只是"性能问题"而不是"正确性问题"。

## 1. 这个领域解决什么业务问题，在全局的位置

优惠券的商业本质是**价格歧视（差别定价）**：同一杯奶茶成本 5 元，定价 15 元卖给 60 个不敏感用户，再向 40 个心理价位 10 元的用户发 5 元券，利润 60×10+40×5=800 元，高于统一定价的 500~600 元。且"降价容易涨价难"，直接降价会打穿价格锚点，发券不会。用户侧，券是"努力获得的虚拟资产"，触发损失厌恶（同量损失的负效用约为收益正效用的 2.5 倍），"抢到不用不能忍"——这是券的核销率天然高于普适性促销的原因。

要把这个商业工具变成一个支撑字节/美团体量的中台，领域模型要回答四个问题：

1. **一张券在系统里是什么？** 是运营配的一个"模板"，还是用户手里的一张"实例"？两者必须分开建模（后面会讲为什么）。
2. **券的一生有哪些状态、谁能触发流转？** 领取、锁定、核销、退回、过期、作废，每一步都可能涉及资损。
3. **谁来约束发券的成本？** 预算、活动、批次、库存、四层领取限额，一层都不能少——某公司券审核不严被薅走 200 余万的事故就是缺层的代价。
4. **券的数据如何成为唯一事实源？** 领券、用券明细要能支撑财务核算、ROI 与对账，口径必须自洽。

在全局架构中的位置：

```
                    ┌────────────────────────────────────────────┐
```

中台以"创、发、用、计"四大环节对外提供能力，而本章的领域模型是四个环节共享的底座：创环节写模板，发环节产实例、扣库存，用环节驱动状态机流转，计环节消费事件明细。与外部的订单、支付、风控、CRM 交互，一律通过防腐层（ACL）做模型翻译，把耦合压在数据耦合层级——这是美团抽奖平台实践中验证过的上下文映射方式（开放主机服务 + 发布语言对外，防腐层对内）。

## 2. 朴素实现（v1）会怎么挂

v1 的典型样子：一张大表 `coupon`，模板字段（面额、门槛、库存）和用户字段（user_id、status）混在一起，status 是 varchar 随便写，业务代码"先 SELECT 判断，再 UPDATE 改状态"。

**故障一：check-then-act 竞态导致超领（资损）。** 领券逻辑是"SELECT count(*) WHERE user_id=? AND template_id=? 判断限领 1 张，未超则 INSERT"。同一用户并发两个请求同时通过校验，各插一条，领到 2 张。放大到库存校验同理：`SELECT remaining WHERE id=?` 读到 1，两个请求都判断"够"，各 UPDATE 减 1，库存变 -1。一场 10 万张的大额券活动，峰值 5000 QPS，超发率通常在 1%~5%——按 10 万张 10 元券、超发 3% 算，**直接资损 30 万元**，且超发的券核销后才在对账里现形，追不回来。

**故障二：库存单行热点打挂数据库（可用性）。** 所有扣减都是 `UPDATE coupon SET stock=stock-1 WHERE id=?`，全部请求在**同一行**上排队等 InnoDB 行锁。5000 QPS 时，单事务平均 5ms，行锁队列长度迅速堆到上万，连接池被扣减请求占满，整个库上所有业务（包括与券无关的）一起超时——雪崩。库存扣挂了，券系统连"查我的券"都不可用。

**故障三：状态无状态机，重复核销与重复退券（资损）。** status 由各处业务代码随手 UPDATE，没有合法迁移约束。用户取消订单，退券逻辑 `UPDATE status='UNUSED'` 执行两次（MQ 重试），一张已核销的券被回退成可用，用户再下一单再用一次——**一张 100 元券花两次**。更恶劣的是"下单-取消-套券"恶意套利：黑产批量锁券又取消，占用库存却不消费，真实用户领不到，活动效果归零。

**故障四：模板与实例混存，改模板"变性"历史券（资损+核算崩塌）。** 运营把进行中活动的面额从 10 元改成 30 元，所有已领用户的券一夜之间变 30 元；财务按 10 元入的营销费用账，核销时按 30 元扣，账面直接对不上。同批次券核心字段不一致，ROI 计算彻底作废。

v1 的根因不是性能，是**模型缺失**：没有模板/实例分离、没有状态机约束、没有幂等键、没有库存独立抽象。先修模型，再谈性能。

## 3. 方案演进：v1 → v2 → v3

### v2：模板/实例分离 + 锁 + 分段库存 + 唯一索引（vivo 商城路线）

vivo 商城优惠券系统独立中台时的做法，解决了 v1 的四个问题：

1. **模板表与用户券表分离**，用户券表按 userId 分库分表（`库后缀 = hash(userId)/M % N`，`表后缀 = hash(userId) % M`），路由因子选 userId 保证同用户资产同库同表——查询聚合、批量入库都受益。分表后 join 不到模板表，就在用户券表**冗余规则快照字段**，冗余度在性能与字段数间平衡。
2. **防超领用 Redis 分布式锁**：领券先取锁 `用户id+模板id`，再校验领券数量，扣库存、落库成功后释放。批量一键领 A/B/C/D 时**逐券加 4 把锁**并自旋等待——因为组合 key `用户id+A+B+C+D` 与单券请求的 `用户id+A` 不互斥，这是真实踩过的坑。
3. **库存分段**：把总库存拆成 M 份子库存字段，随机选一段 UPDATE，把单行锁分散成 M 行，定时任务汇总同步。选它而非 Redis incrby 的理由：不用处理缓存丢失/宕机后的数据恢复与不一致。
4. **幂等靠数据库唯一索引**：在现有用户券表上加唯一字段，历史数据脚本刷唯一值，未传码的业务方由券系统侧生成唯一编码兼容。
5. **不停机迁移七步法**（如你从单体迁中台）：停后台静态操作→单写旧库→迁静态数据→双写→迁动态数据→切数据源（可回滚）→关双写。

**v2 的新问题**：① 锁内包含"查 DB + 扣库存 + 落库"全链路，持锁时间几十毫秒，虽锁粒度是单用户单券冲突低，但每次领券多两次 Redis 往返，链路长、超时率高；② 分段库存仍在 DB，M 通常只有几十，热点券（10 万+ QPS 的明星券）扣减压力还是打在 DB 写上，段间还会不均衡——某段扣尽而总量未尽，用户领不到；③ 分库分表后跨库无法做"模板维度"的唯一约束与聚合统计，必须另建异构索引表或走明细汇总；④ 核销/退券与订单的一致性（分布式事务）仍未解决。

### v3：大厂最终形态——Redis 原子扣减 + 状态机条件更新 + 独立占用单 + 事件事实源

演进动机：把"正确性"从锁的时序里拿出来，交给**原子操作**和**约束式更新**；把"热点"从 DB 完全挪到 Redis；把"一致性"从分布式事务改成**本地事务 + 事件 + 对账补偿**。

1. **库存与限领计数进 Redis，Lua 脚本原子扣减**——"查库存、判限领、扣库存"一个脚本完成，check-then-act 竞态从根上消灭，v2 的分布式锁在领券主链路不再需要（DB 唯一索引仍兜底）。
2. **券状态机用条件 UPDATE 流转**：`UPDATE ... SET status=2 WHERE id=? AND status=1`，影响行数为 0 即并发冲突，业务侧重试或报错。合法迁移集中在一处定义，贫血的"随手改 status"被禁止。
3. **占用单（锁券单）独立成聚合**，借鉴点评交易把订单拆成订单/支付单/履约单/凭证/退款单的思路：用户券只管资产状态，占用单管"哪张券为了哪个订单锁定/核销/释放了多少分摊金额"。退券回退的是占用单驱动的状态迁移，重复退券被"占用单号幂等"挡住。
4. **领券/核销/退券/过期全部落事件明细**，作为唯一事实源（single source of truth）——统计三层报表、财务对账、Redis 与 DB 的库存对账，全部从明细回放，这是 event-sourcing 式的数据设计。
5. 剩余一致性缺口用**对账任务 + 补偿**收口：Redis 扣了 DB 没落、锁了券订单取消了消息丢了，都由扫描任务从明细和状态里发现并修复。

**v3 的新问题（要正视）**：Redis 与 DB 库存可能不一致（扣减成功落库失败），需要补偿回加与对账；Redis 宕机要能降级到 DB 分段限流发放；异步事件可能延迟或丢失，状态机必须能被定时任务驱动自愈（如过期）。

## 4. 大厂最终形态详细设计

### 4.1 实体层级与限界上下文

自上而下五层实体，每层承载一个成本/归因约束：

```
预算 Budget ──1:N──▶ 活动 Campaign ──1:N──▶ 券模板 Template(批次) ──1:N──▶ 用户券 UserCoupon
                                                │                                │
                                                │ 库存/四层限额                   │ 1:N
                                                ▼                                ▼
                                     [库存上下文][计数上下文]              占用单 CouponUsage(锁券/核销单)
                                                                        │
                                                                        ▼
                                                              事件明细 CouponEvent(事实源)
```

- **预算→活动→批次**的三层硬约束来自 O2O 券平台的通用实践：无预算不能建活动、无活动不能产批次、批次时间必须落在活动期内。它保证"每张券都能向上归因到预算科目"，否则效果无法追踪、财务无法交代。
- **限界上下文划分**（按语义而非技术分层）：券模板上下文（M 端配置，复杂低频）、领券/交易上下文（C 端，高频）、**库存上下文**（独立，因为库存的行为与券本身解耦、关注核销、可被券之外的东西复用）、**计数上下文**（限领次数，被领券/风控/准入共用）、占用核销上下文。C 端与 M 端彻底拆开——运营配置"复杂但低频"，用户使用"高频且无感知"，两套系统解耦后互不拖累发布与容量。
- **一个事务只修改一个聚合实例**：领券事务只写 user_coupon（聚合根）；库存扣减在 Redis；占用单、事件明细各自独立事务，跨聚合用最终一致。这是把强一致从性能瓶颈处剥离的关键决策。

### 4.2 表结构 DDL

```sql

  event_no    VARCHAR(64) NOT NULL COMMENT '事件幂等号',

  user_coupon_id BIGINT NOT NULL,
  user_id     BIGINT NOT NULL,

```

要点：用户券表唯一索引 `(user_id, idempotent_key)` 含路由因子 userId，分库分表后仍局部有效——**唯一约束必须落在路由因子能覆盖的维度内**，这是分片幂等的铁律。核销明细的 amount 放"实际抵扣额"而非面额，因为满折券要按 `min(discount_cap, 计算优惠额)` 孰低取值，财务按实际抵扣额入账。

### 4.3 券状态机

**模板侧是双状态机（正交）**：审批状态（待审→通过/拒绝，配套**交叉审核**：建券账号不能审券，防内部舞弊——前文 200 余万资损事故的直接教训）与生命周期状态（未发布→已发布→已下线）。只有"审批通过+已发布+在有效期"才可被领取。两者不合并成一个 status，因为审批与上下线是不同角色在不同时机的动作，合并后流转表会指数膨胀。

**用户券实例状态机（7 态，含终态标记）**：

```
                领券成功                    到期未用(定时+惰性)
   [Init] ──────────▶ USABLE(0待使用) ───────────────▶ EXPIRED(3已过期,终)
                        │       ▲                        ▲
             下单锁券    │       │ 释放回退(订单取消/     │ 锁定期到期仍未核销
             (条件更新)  │       │ 支付超时,且券未过期)   │
                        ▼       │                        │
                   LOCKED(1已锁定) ────────────────────────┘
                        │  释放时若 valid_end<now 则直接过期
        支付成功核销     │
        (订单回调)       ▼
                   USED(2已核销,终)
                        │ 风控冻结/运营作废(任意非终态可到)
                        ▼
                  INVALID(4已作废,终)
```

合法迁移表（唯一入口，代码里枚举收敛）：

| 从 | 到 | 触发事件 | 动作 |
|---|---|---|---|
| - | USABLE | 领券/发券成功 | 固化快照与 valid_end，写发放事件 |
| USABLE | LOCKED | 下单锁券 | 条件 UPDATE，插占用单(占用中) |
| LOCKED | USED | 支付成功回调 | 条件 UPDATE，占用单→已核销，写核销事件+分摊金额 |
| LOCKED | USABLE | 订单取消/未支付超时 | 占用单→已释放(幂等号防重)，写释放事件 |
| LOCKED | EXPIRED | 锁定期超时未核销 | 占用单→已释放 |
| USABLE | EXPIRED | 定时扫描+访问惰性判断 | 写过期事件 |
| USABLE/LOCKED | INVALID | 风控冻结、运营作废 | 写作废事件，可配置是否回补库存 |

三条资损红线在迁移表里固化：① **USED 是终态**，退款不自动回券（已发货/已履约的整单售后、部分售后均不退券），需要例外时走运营审批的定向补发而不是改状态机；② LOCKED→USABLE 只能由占用单状态驱动且以 usage_no 幂等，MQ 重复消费不会二次回退；③ 模板"张数只增"、面额/门槛/适用商品等核心字段不可改，从模型上杜绝"变性"。

### 4.4 模板可变性与历史券：混合模式

"运营改了券，用户手里已领的券变不变"有三个方案：静态快照（历史券完全不变）、动态关联（实时同步）、混合（按属性分）。**推荐混合模式**，按字段分类落地：

- **静态快照字段（领券时固化到 user_coupon）**：面额、门槛、折扣上限、有效期——核心权益，改了要么伤用户要么伤财务。有效期缩短、范围缩小这类"降权益"操作只对新领券生效。
- **动态关联字段（用时报模板实时查）**：适用门店/商品范围的**扩展**（新增门店 C 自动适用）、优惠力度升级（满100减10→满80减10）——加权益允许同步生效，且运营端修改时强制弹窗提示"将影响 N 张历史券"。
- **只增字段**：total_count 增券（预估不足/活动延长），必须同步回补 Redis 与分段库存。

快照与动态的分界线就一条：**改动方向是加权益还是减权益**。加权益走模板实时读（省得重刷亿级用户券表），减权益只影响增量（保护存量用户，避免客诉与合规风险——单方面缩限需提前通知并补偿，这是有赞等平台的成熟做法）。

### 4.5 Redis key 设计与数据结构选型

| key | 结构 | 用途 | 选型理由 |
|---|---|---|---|
| `c:stk:{templateId}` | String(int) | 总库存余量 | 单 key 单值 DECRBY 原子；热点券单 key 可承受 10w+ QPS（Redis 单分片），不够再分桶 `c:stk:{tplId}:{0..63}` |
| `c:ul:{templateId}:{userId}` | String(int)+TTL | 用户累计限领计数 | 计数天然适合 String INCR；TTL=活动结束时间，自动清理 |
| `c:uld:{yyyyMMdd}:{templateId}:{userId}` | String(int)+TTL 当日 | 用户每日限领 | 日限与总限分开计数，按天滚动用自然日拼 key 最简单 |
| `c:dly:{yyyyMMdd}:{templateId}` | String(int) | 每日发放上限 | 同上 |
| `c:tpl:{templateId}` | Hash | 模板规则缓存 | 字段级读写（校验只要 3 个字段时不必整对象反序列化）；Cache Aside 由 Repository 收拢 |
| `c:lock:rcv:{userId}:{templateId}` | SET NX PX | 兜底互斥（v3 非必须） | 批量领券/定向发券与单券并发的兜底；主链路已被 Lua 取代 |
| `c:idem:{requestId}` | SET NX PX | 领券幂等前置 | 挡住重试穿透到 DB；DB 唯一索引仍是最后防线 |

不把库存放 Hash 的理由：Hash 的 HINCRBY 虽也能原子扣，但"总余量"只有一个字段，String 语义最直白；分桶时用多个 String key 而非一个 Hash field，是因为分桶的目的就是打散热点到不同分片，同一 Hash 的 field 仍在同一分片。限领计数不用 Hash（`HINCRBY c:ul:{tplId} {userId} 1`）的理由：大 key 隐患（一场活动百万用户 = 百万 field），且过期只能整 key 过期、无法按用户独立清理。

**Redis 是"算子"不是"账本"**：所有 Redis 数据可由 DB 重建（发布模板时从分段库存求和灌入 `c:stk`），Redis 丢数据不等于资损——大不了多发了由 DB 唯一索引挡住、少发了由对账任务回补。

### 4.6 核心代码

**Lua：库存+限领原子扣减（领券主链路，v3 核心）**

```lua
-- KEYS[1]=c:stk:{tplId}  KEYS[2]=c:ul:{tplId}:{uid}  KEYS[3]=c:uld:{date}:{tplId}:{uid}
-- KEYS[4]=c:dly:{date}:{tplId}
-- ARGV[1]=perUserLimit ARGV[2]=perUserDailyLimit ARGV[3]=dailyLimit ARGV[4]=当天秒数
local stock = redis.call('GET', KEYS[1])
if not stock then return {-1, 'STOCK_NOT_INIT'} end          -- 未初始化需回源重建
if tonumber(stock) <= 0 then return {-3, 'SOLD_OUT'} end
local daily = tonumber(ARGV[3])
if daily > 0 and tonumber(redis.call('GET', KEYS[4]) or '0') >= daily
then return {-4, 'DAILY_LIMIT'} end
local ul = redis.call('INCR', KEYS[2])
if ul > tonumber(ARGV[1]) then
  redis.call('DECR', KEYS[2])                                 -- 回滚，保持对称
  return {-5, 'USER_LIMIT'}
end
local uld = redis.call('INCR', KEYS[3])
redis.call('EXPIRE', KEYS[3], tonumber(ARGV[4]))
if uld > tonumber(ARGV[2]) then
  redis.call('DECR', KEYS[3]); redis.call('DECR', KEYS[2])   -- 两处都要回滚
  return {-5, 'USER_DAILY_LIMIT'}
end
redis.call('DECR', KEYS[1])
if daily > 0 then redis.call('INCR', KEYS[4]) end
redis.call('EXPIRE', KEYS[4], tonumber(ARGV[4]))
return {0, tonumber(stock) - 1}
```

注意**回滚对称性**：先 INCR 计数再查库存/日限的顺序，任一失败必须把已 INCR 的全部 DECR 回去，否则用户的限领额度被"幽灵扣减"，最终表现为"明明没领过却提示超限"。

**领券服务（Java，含同步落库与失败补偿）**

```java
@Service
public class CouponReceiveService {

    /** 单券领取：Lua 原子扣减 + DB 唯一索引幂等 + 同步落库 */
    @Transactional
    public UserCouponDO receive(ReceiveCmd cmd) {
        TemplateDO tpl = templateRepository.get(cmd.getTemplateId());   // Cache Aside
        // 1. 静态校验：审批通过+已发布+在领取期+用户在目标客群(风控/CRM走防腐层)
        tpl.assertReceivable(cmd.getUserId());
        // 2. Redis 幂等前置，挡重试穿透
        if (!idempotentRedis.tryMark(cmd.getRequestId())) {
            return userCouponRepo.findByIdempotent(cmd.getUserId(), cmd.getRequestId());
        }
        // 3. Lua 原子扣库存+限领（替代 v2 的分布式锁+DB分段）
        long r = stockRedis.decrForReceive(cmd.getTemplateId(), cmd.getUserId(), tpl);
        if (r != 0) throw new BizException(StockLua.codeOf(r));
        try {
            // 4. 落库：状态机初始化为 USABLE，快照固化，valid_end 统一 23:59:59
            UserCouponDO uc = UserCouponDO.init(tpl, cmd);   // 领取后N天→最后一天23:59:59
            userCouponRepo.insert(uc);                        // 唯一索引(user_id,idem_key)兜底
            eventRepo.append(CouponEvent.issued(uc));         // 事实源，同事务
            return uc;
        } catch (DuplicateKeyException e) {
            return userCouponRepo.findByIdempotent(cmd.getUserId(), cmd.getRequestId());
        } catch (Exception e) {
            // 5. 落库失败：投补偿队列回加 Redis 库存与限领（或由对账任务兜底）
            compensateClient.submitRollback(cmd);
            throw e;
        }
    }

    /** 批量一键领券：逐券独立事务，单券失败不影响其他券 */
    public List<ReceiveResult> batchReceive(BatchReceiveCmd cmd) {
        return cmd.getItems().stream()
            .map(c -> tryReceive(c))     // 每张券独立事务+独立幂等键，失败记入结果
            .collect(toList());
    }
}
```

领券**同步落库**是刻意选择：用户券按 userId 分片，单用户的写不存在热点（热点在库存，已挪去 Redis），而"领完立刻能看到券"直接影响转化——定向发券这类亿级批量场景才走"去事务+内存归集分表批量插入+参数动态调速"的异步管线。

**状态机流转（核销与释放，条件 UPDATE）**

```java
public int lock(UserCouponDO uc, String orderNo) {          // USABLE -> LOCKED
    return jdbc.update("UPDATE user_coupon_? SET status=1 WHERE id=? AND status=0 AND valid_end>?",
        tableOf(uc.getUserId()), uc.getId(), now());
}   // 影响行数=0 → 已被并发锁定/已过期，抛冲突，调用方换券重试

public void confirm(long userId, long ucId, String usageNo, long discountAmt) { // LOCKED -> USED
    CouponUsageDO usage = usageRepo.lockByNo(usageNo);       // SELECT ... FOR UPDATE 或乐观锁
    if (usage.isConfirmed()) return;                          // 幂等：重复回调直接成功
    usage.assertOwning(ucId);
    int n = jdbc.update("UPDATE user_coupon_? SET status=2 WHERE id=? AND status=1", ...);
    if (n == 0) throw new StateConflictException("券不在已锁定态: " + ucId);
    usageRepo.confirm(usageNo, discountAmt);                  // 占用单→已核销
    eventRepo.append(CouponEvent.used(ucId, usageNo, discountAmt));  // 分摊后实际抵扣额
}

public void release(long userId, long ucId, String usageNo) { // LOCKED -> USABLE/EXPIRED
    CouponUsageDO usage = usageRepo.lockByNo(usageNo);
    if (usage.isReleased()) return;                            // 幂等：MQ 重复消费安全
    if (usage.isConfirmed()) throw new IllegalStateException("已核销不可释放");
    jdbc.update("UPDATE user_coupon_? SET status=IF(valid_end>?,0,3) WHERE id=? AND status=1", ...);
    usageRepo.release(usageNo);                                // 占用单→已释放
    eventRepo.append(CouponEvent.released(ucId, usageNo));
}
```

### 4.7 核心时序（编号步骤）

**A. 用户领券（抢券，C 端，峰值 5w+ QPS）**
1. 网关限流+风控前置（设备/黑名单在接入层挡掉，a 系列产品素材中的"设备号限领"在风控层落地）。
2. 读模板缓存 `c:tpl:{id}`（miss 回源 DB，Repository 收拢，Cache Aside）。
3. 静态校验：审批通过、已发布、领取期内、客群匹配（CRM 防腐层）。
4. Redis SET NX 幂等标记 `c:idem:{requestId}`。
5. 执行 Lua：日限→个人总限→个人日限→库存，四项原子判扣。
6. 本地事务：insert user_coupon（USABLE，快照+valid_end 固化）+ insert 发放事件。
7. 返回券详情；落库失败投补偿回滚 Redis。
8. 领券数异步累计进统计（消费事件明细，不在主链路）。

**B. 下单用券（锁券→核销→可能释放）**
1. 结算页查询可用券：`idx_user_status` 取 status=0 且 valid_end>now，内存过滤适用范围（白名单/黑名单缓存）。
2. 优惠计算引擎选券（见第 5 节分歧 1 的推荐策略），提交订单带 couponId。
3. 订单服务创建订单，同事务内调券中台 `lock`：条件 UPDATE 0→1 + 插占用单（usage_no=orderNo+couponId）。
4. 锁失败（并发冲突/过期）→订单侧换券或无券重算价格。
5. 支付成功回调（MQ）：`confirm` 1→2，占用单已核销，写核销事件（含按比例分摊到商品行的金额，除不尽最后一件倒挤，保证分摊和=抵扣总额）。
6. 订单取消/支付超时（MQ）：`release` 1→0（或 1→3 若已过期），usage_no 幂等防重复回退。
7. 锁定超时兜底：定时任务扫"占用中且超过锁定时限"的单子强制释放——防 MQ 丢失导致券永久锁死。

**C. 过期（定时+惰性双保险）**
1. 每小时分页扫 `idx_expire(status=0/1, valid_end < now)`，批量置 3，写过期事件。
2. 用户访问券列表时惰性判断 valid_end，不等定时任务——扫挂了也不影响正确性。
3. 过期后库存不回补（除非模板显式配置回补，默认不回补防止"过期循环抢"）。

**D. 定向发券（亿级批量）**
1. 圈人（标签组合/文件导入/SQL），生成发放任务。
2. 无事务化：失败记录可重试，最终一致。
3. 轻量校验：定向券类型限制配置规避重校验。
4. 内存计算分片后缀、按表归集批量插入（最多插 M 次）；库存一次性预扣入独立发放额度池。
5. 消息中心推送控制速率（单批数量、批间隔可配），推送记录备查。

### 4.8 接口签名（对订单/交易域的发布语言）

```java
public interface CouponReceiveFacade {          // C端领券

    List<ReceiveResultDTO> batchReceive(BatchReceiveCmd cmd);
}
public interface CouponTradeFacade {            // 交易链路（订单域调用）
    LockResult lock(LockCmd cmd);               // cmd: usageNo,userId,userCouponId,orderNo
    ConfirmResult confirm(ConfirmCmd cmd);      // cmd: usageNo,discountAmt(分摊后)
    ReleaseResult release(ReleaseCmd cmd);      // cmd: usageNo,reason

public interface CouponTemplateFacade {         // M端配置（运营后台）
```

所有 Facade 入参必带幂等号（requestId/usageNo），返回值带确定性结果码（SUCCESS / DUPLICATED（幂等命中，返回已有结果）/ STOCK_OUT / LIMIT_EXCEEDED / STATE_CONFLICT），调用方对 STATE_CONFLICT 重试、对 DUPLICATED 视为成功——**把幂等语义写进接口契约**，而不是靠文档口口相传。

### 4.9 一致性收口：对账

Redis 与 DB 每日三次对账：`DB 各段 remaining 之和 + 已发放未核销数` 与 `c:stk` 比对，差额生成补偿单（回加 Redis 或修 DB），差异明细落表供财务复核。占用单状态与券状态交叉对账：不存在"占用中"却 USABLE 的券、不存在 USED 却无"已核销"占用单的券。事件明细按天汇总与模板领取数/核销数核对——三层核对全部由明细回放，这就是"事实源"的含义。

## 5. 素材间的方案分歧与推荐

**分歧 1：平行式 vs 递进式优惠计算。** 一份素材强烈建议平行式（所有券均以商品总额为基数，计算量小、用户优惠多），并给出"递进式+最优组合把 4 位开发干跑了"的教训；另一份素材的计算示例却是递进式（单品 8 折后满减门槛按折后 270 元判定）。
**推荐**：两者不在同一维度——前者说的是**多张券之间**是否互为基数，后者说的是**券与促销叠加的层级顺序**。落地取混合：跨类别（单品券→折扣券→满减券→无门槛券）按四级优先级**递进**（每层门槛以前序优惠后的金额判定，防止"折后再满减"过度让利）；**同类别内多张券平行**（以进入该层时的金额为共同基数）；不做用户可选组合的穷举最优，只做系统自动勾选的贪心最优（每类选抵扣额最大、同额选有效期最近的）。既有确定性资损上限，又把计算复杂度从排列组合压到线性。

**分歧 2：库存扣减选 DB 分段还是 Redis。** vivo 明确选了 DB 分段、放弃 Redis incrby（怕缓存丢失/宕机不一致）。
**推荐**：按量级分。vivo 的量级（商城级，性能支撑 3-5 年即可）与团队维护性下选 DB 分段是理性的；但对标字节/美团的抢券峰值（单一热点券 10w+ QPS），DB 分段数有限、段间不均衡，扛不住。最终形态用 **Redis Lua 为主 + DB 分段为底账与降级通道**：Redis 可由 DB 重建（"算子不是账本"），宕机时降级到 DB 分段限流发放，两个方案的优点合并。

**分歧 3：防超领用分布式锁还是原子操作。** vivo 用"分布式锁→校验→扣减→落库→释放锁"，批量领券还踩了组合 key 不互斥的坑。
**推荐**：锁的目的是保护"check-then-act"，把 check 和 act 合进 Lua 原子脚本后主链路不再需要锁；批量领券逐券独立事务天然规避组合 key 问题。锁只保留在定向发券等低频批量场景做兜底。教训抽象成规则：**需要一把锁保护的临界区，先试试能不能变成一个原子操作**。

**分歧 4：退券后的状态定义。** 一份素材说有的平台记"已取消"、有的视同"待使用"（明细记 1 条用券+1 条退券）。
**推荐**：回"待使用"（若未过期），不要设"已取消"态——"已取消"与"已作废"语义重叠会造成两套终态。真正的关键是把回退动作挂在**占用单**上以 usage_no 幂等，券状态只是占用单驱动的投影；明细记"锁定→释放"两条事件，对账口径同样自洽。

**分歧 5：状态机枚举数量。** 一份素材给 3 态（待使用/已使用/已过期），另一份给 4 态（增加"已占用"）。
**推荐**：7 态（待使用/已锁定/已核销/已过期/已作废 + 初始化 + 终态语义）+ 占用单 3 态。"已锁定"必须有——没有它，"下单未支付"期间券既不能被别的订单用、又不能算核销，两头出错；"已作废"与"已过期"必须分开——过期是时间驱动可进入过期统计，作废是风控/运营驱动要留审计与补偿。

**分歧 6：领券异步还是同步落库。** vivo 明确"领券必须实时落库，异步用户看不到券影响转化"；也有大厂实践 Redis 扣完即返回、MQ 异步落库。
**推荐**：同步落库。用户券按 userId 分片后写入无热点，瓶颈只在库存（已在 Redis）；同步落库换来"DB 是完整账本、唯一索引即时兜底幂等"，省掉"读己之写"的复杂度。异步只用于定向发券与事件统计。

## 6. 踩坑清单（按严重程度排序）

1. **check-then-act 超领/超发（资损 P0）**。现象：库存为负、限领 1 张的用户手里 2 张，大促中对账才发现。发现：DB 加 `remaining>=0` check 约束 + 每日对账；防：库存与限领全部原子化（Lua），DB 唯一索引兜底，任何"先查后改"代码评审一票否决。
2. **已核销券被退款流程回退、二次核销（资损 P0）**。现象：一张大额券核销两次，退款 MQ 重复消费时爆发。发现：占用单与券状态交叉对账（USED 必有唯一已核销占用单）；防：USED 设为终态，回退只认占用单且 usage_no 幂等，confirm/release 前先判占用单状态。
3. **Redis-DB 不一致 / Lua 回滚不对称（资损 P1）**。现象：Redis 显示有库存 DB 已空（多发请求穿透），或用户没领过券却提示超限（计数幽灵扣减）。发现：Redis 值与分段求和+发放数对账，差额定阈值告警；防：Lua 内 INCR/DECR 严格对称，落库失败投补偿回加，Redis 只当算子可随时重建。
4. **幂等缺失，重试超发（资损 P1）**。现象：业务方超时重试，用户领两回。发现：按幂等键 group by count>1 的巡检；防：接口契约强制幂等号，DB 唯一索引含路由因子，DuplicateKey 当成功返回已有结果。
5. **锁粒度/锁内长事务（可用性 P1）**。现象：批量领券与单券并发互不互斥照样超领（组合 key 坑）；锁内含多次 DB IO，超时线程堆积。发现：压测并发同用户领券场景 + 锁等待监控；防：优先原子操作替代锁，必须用锁时逐券加锁、锁内只做内存操作。
6. **改模板导致历史券"变性"（资损+核算 P2）**。现象：面额改大后营销费用爆掉，财务账目对不上。发现：模板变更审计 + 变更前后快照 diff；防：核心字段（面额/门槛/有效期/适用范围缩限）改配置即拒——接口层不提供 update；张数只增；历史券靠快照字段免疫。
7. **分库分表后唯一约束/聚合失效（正确性 P2）**。现象：跨库重复插入、模板维度统计跑不动。发现：分片键路由验证用例 + 全局巡检；防：唯一键必须含 userId（路由因子）；全局唯一用号段/雪花；模板维度统计走事件明细异构汇总表，不跨库聚合。
8. **占用单泄漏：锁券后订单取消消息丢失（体验/客诉 P2）**。现象：用户券卡在"已锁定"，什么也干不了。发现：扫描"占用中超过锁定时限"的单子；防：锁定超时强制释放任务 + 释放以 usage_no 幂等可重放。
9. **有效期口径坑（客诉 P2）**。现象：相对有效期"领取后 7 天"算出 3/27 20:35，用户当天 21:00 用不了；满折面额 8.5/85/0.85 三种填法并存。发现：客诉归类 + 配置扫描；防：截止统一到最后一天 23:59:59 并在领券时固化；折扣统一基点制（85 折=8500）+ 配置端强校验提示。
10. **过期定时任务扫全表（可用性 P3）**。现象：每小时一次大范围扫描拖慢主库。发现：慢 SQL 监控；防：走 `idx_expire(status,valid_end)` 按分表并行小批量翻页，配合访问时惰性判断，任务挂了正确性不受影响。

## 7. 小结

领域模型与状态机的设计质量决定了券系统是"性能问题"还是"正确性问题"。记住五条：模板与实例分离且核心字段冻结；库存与计数独立成上下文、用原子操作不用锁；实例状态机七态收敛、条件 UPDATE 流转；占用单作为交易链路的幂等锚点与资产状态的驱动源；一切写操作落事件明细，让对账与统计有唯一事实源。这五条立住之后，高并发只是把热点从 DB 挪到 Redis 的工程活。
