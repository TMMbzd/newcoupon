# 02 · 高并发发券（领券）链路设计

> 本章讲的是券系统里压力最大、资损风险最高的一条链路：**用户点击"领取"之后发生了什么**。读者定位：正在从零实现一个对标字节/美团体量的优惠券中台的 Java 工程师。文中所有方案都给到表结构、Key 设计、Lua 脚本与代码骨架，可直接落地；素材间的分歧在第 5 节明确列出并给出推荐。

---

## 1. 这个领域解决什么问题，在券系统全局的位置

### 1.1 一句话定义

发券链路要解决的问题：**把一张有预算上限的券，在秒级流量洪峰下，发给正确的用户——不超发（资损）、不少发（体验与转化损失）、不重复发（资损 + 客诉）**。

它同时是四个约束的交集：

| 约束 | 含义 | 违反后果 |
|---|---|---|
| 库存安全 | 全批次发放数 ≤ 配置总量 | 超发 → 核销时平台贴钱，直接资损 |
| 限领安全 | 单用户领取数 ≤ 用户限领（总量/每日） | 超领 → 羊毛党囤券，营销预算被掏空 |
| 幂等 | 同一业务请求重试 N 次只发 1 张 | 重试风暴下翻倍超发 |
| 吞吐/时延 | 秒杀洪峰下 RT 保持毫秒级 | 链路雪崩，拖垮整个券系统乃至上游交易 |

业务背景的量级参考（来自几家大厂公开数据，做容量目标用）：
- 字节春节红包场景：单系统 **12w~13w QPS 发券**，成功率 99.9%+；
- 京东到家：领券接口 TPS 日常峰值 15 万/分钟（约 2.5k TPS）、大促 45 万/分钟（约 7.5k TPS），日发券 5000 万、大促上亿，用户券总量 40 亿条；
- 腾讯云 MALL：派发压测目标万级 TPS，典型**瞬时毛刺**流量；
- 京东到家整体：峰值百万级 TPS、亿级 QPS（含展示读流量）。

发券是券系统唯一的**高并发写入口**。展示是读热点（可以用缓存副本、本地缓存解决），用券核销是低频强一致写（订单驱动），而发券是"高并发 + 写 + 有预算上限"三者的叠加，所以它是整个中台架构分层的原动力——京东到家就是因为"高并发领券/展示流量影响核心用券交易流程"才把 C 端拆成展示系统与用券核心系统，并把缓存按数据域拆成 5 个集群做故障隔离。

## 2. 朴素实现（v1）会怎么挂：具体故障场景

一个没有高并发经验的工程师写的 v1 大概是这样：

```java
@Transactional
public void issue(long templateId, long userId) {
    Template t = templateMapper.selectById(templateId);
    if (t.getLeftStock() <= 0) throw new BizException("已抢光");
    if (t.getReceiveEndTime().before(now())) throw new BizException("活动结束");
    // 查用户已领数量
    int cnt = userCouponMapper.countByUserAndTemplate(userId, templateId);
    if (cnt >= t.getMaxPerUser()) throw new BizException("超出限领");
    templateMapper.updateStock(templateId);          // update set left_stock=left_stock-1
    userCouponMapper.insert(new UserCoupon(userId, templateId)); // 同事务插券
}
```

这个实现在大促场景下的死亡过程，按时间线推演：

**场景设定**：某满减券 10:00:00 开抢，库存 10 万，瞬时 5w QPS，单实例 200 并发线程。

**T+0s，库存行锁排队**。`update ... where id = ?` 全部串行等同一行的 InnoDB 行锁。单条 update 按字节跳动文章的实测数据，单 MySQL 写入约 4000 QPS 后 I/O 时延急剧增长——5w QPS 是其 12 倍。锁等待时间从微秒涨到秒级。

**T+2s，连接池耗尽**。200 个线程全部卡在 `SELECT ... FOR UPDATE` / update 的锁等待上，Druid/HikariCP 连接池占满，后续请求在获取连接处排队。

**T+3s，线程池打满，上游超时**。Tomcat 工作线程全部阻塞，请求堆积在 accept 队列；上游（活动页 BFF）设了 500ms 超时，开始超时**重试**——注意，重试流量叠加在原始流量上，QPS 从 5w 恶化到 8w，这是雪崩的正反馈回路。

**T+5s，雪崩扩散**。因为 v1 把领券做成了 `@Transactional`（查券 + 查计数 + 扣库存 + 插券四步一个事务），事务持锁时间更长；同一 MySQL 实例上还住着"查我的券"等其他业务，全被拖死。这正对应京东到家/vivo 都讲过的教训：高并发营销流量与核心流程不隔离，会拖垮整站。

**而即使在库没被打挂的小流量下，它也在静默资损**：

1. **check-then-act 超发**：`if (left <= 0)` 与 `update` 之间没有任何原子性。库存剩 1 时两个请求同时通过校验、都 update 成功（`left = left - 1` 执行两次变成 -1，且 SQL 无 `and left_stock > 0` 条件），超发。10 万库存的批次在 5k QPS 下超发几十张是常态——按面额 50 元算，就是几千元的静默资损，且用户无感知、运营只能在对账时发现。
2. **用户超领**：用户双击按钮，两个请求并发执行 `countByUserAndTemplate`，都读到 cnt=0，都通过 maxPerUser=1 校验，各插一张。vivo 文章里明确复盘过这个场景。
3. **重试重复发券**：接口无幂等。领券成功但响应在网络层丢失，上游重试，再发一张。字节的文章把这点列为幂等设计的目标："业务方通过重试/补偿再次请求，最终只发出一张券，防止资金损失"。
4. **单表千万级后查询衰减**：字节实测 MySQL 单表千万级后查询效率大幅下降，`countByUserAndTemplate` 这种校验查询会越来越慢。

一句话总结 v1 的三宗罪：**校验与扣减不原子（超发）、无幂等（重发）、单行锁 + 长事务（雪崩）**。后面所有架构演进，都是围绕消灭这三个问题展开的。

## 3. 方案演进：v1 → v2 → v3

### v1：数据库直扣（上文）

- 问题：单行锁串行 + 长事务 + check-then-act 超发 + 无幂等。
- 优点：强一致，实现零成本。

### v2：数据库优化——乐观锁 + 分段库存 + 唯一索引幂等

第一步改进是 SQL 层面的：扣库存改成 `update coupon_template set left_stock = left_stock - 1 where id = ? and left_stock > 0`，利用影响行数判断成败，消灭 check-then-act 超发；用户券表加 `(user_id, request_id)` 唯一索引，插入冲突即幂等命中。

第二步是 **DB 分段库存**（vivo 的最终选型）：把库存字段拆成 M 份子库存行（vivo 是一行内拆 M 个字段，等价做法是多行），领券时随机选一段扣，把单行锁分散到 M 行，定时任务汇总各段已领数同步总量。

- 解决：超发（条件更新）、幂等（唯一索引）、行锁热点部分缓解（M 段）。
- 引入的新问题：
  1. **段间不均衡**：随机扣减下某段先扣尽而总量未尽，请求要换段重试，尾部成功率下降（vivo 文章只写了"随机选取 + 定时同步"，未讨论该边界）；
  2. **吞吐天花板仍在 DB**：按字节实测 4000 QPS/实例，M=32 段分散在 32 个分片上也只能扛数万 QPS，且 DB 的扩容成本、连接成本远高于 Redis；
  3. 用户限领的 `count` 校验仍是读操作，高并发下读本身也成为压力。
- vivo 选它的理由是"实现简单、不用考虑缓存丢失与不一致"——这个取舍在万级 TPS 以下成立，在十万 QPS 量级不成立。

### v3：Redis + Lua 原子扣减（腾讯云 MALL 方案骨架）

把库存与限领计数全部搬进 Redis，用一个 Lua 脚本完成"幂等 + 库存 + 批次日限 + 用户日限 + 用户总限"五重校验和五次计数写——Lua 在 Redis 单线程内原子执行，校验与扣减天然不可分割。券记录（用户券）的生成异步化：扣减成功后写本地事务表，经 MQ 异步落库，用"本地事务表 + 最大努力通知"达成最终一致。

- 解决：吞吐（Redis 单分片写 ~2w QPS，读 ~10w QPS，横向扩容成本低）、原子性（Lua）、DB 压力（写被削峰）。
- 引入的新问题：
  1. **一致性**：Redis 扣成功但落库失败/Redis 宕机丢数据怎么办？——腾讯云用"库存异步分段增补 + Redis 库存 ≤ DB 库存不变式"兜底：DB 是总账，Redis 只是发放额度，Redis 崩了最多丢 N 个额度，DB 唯一索引是最后防线；
  2. **热点单 Key**：同一批次所有请求打同一个 stockKey，单分片 Lua 串行执行决定单批次上限（腾讯云自己承认这是遗留坑）；
  3. **最终一致窗口**：用户"抢到了但券包暂时看不到"；
  4. Redis 成为强依赖，挂了发券全停。

### v4（最终形态）：v3 + 热点分段 Key + 二级缓存 + 对账闭环

针对 v3 的遗留问题叠加字节的热点治理与二级缓存方案：热点模板的库存 Key 再拆成 S 个子 Key 分散到不同 Redis 分片、随机不重复轮询、售罄分片跳过；模板读取用"本地缓存 + Redis"二级缓存根除 Redis 超时导致的固有失败率；异步落库配本地事务表 + 重试 + 定时对账。这就是下一节要展开的"大厂最终形态"。

**演进动机主线**（给读者的心智模型）：v1→v2 解决"对不对"（不超发、幂等），v2→v3 解决"快不快"（吞吐、削峰），v3→v4 解决"热不热、稳不稳"（热点、强依赖、容灾）。每一次演进都是把旧方案的"新问题"变成下一个方案的主目标。

## 4. 大厂最终形态：可落地的完整设计

### 4.1 表结构（MySQL DDL）

```sql
-- 1. 券模板表（建券写入，读多写少，整表缓存）
CREATE TABLE coupon_template (
  id             BIGINT UNSIGNED PRIMARY KEY,
  template_name  VARCHAR(64) NOT NULL COMMENT '券名称',
  coupon_type    TINYINT NOT NULL COMMENT '1满减 2折扣 3红包 4运费券',
  face_value     INT NOT NULL COMMENT '面额，分',
  threshold      INT NOT NULL DEFAULT 0 COMMENT '使用门槛，分',
  total_amount   INT NOT NULL COMMENT '总库存（账面，不变）',
  max_per_user   INT NOT NULL DEFAULT 1 COMMENT '用户总限领',
  daily_max_per_user INT NOT NULL DEFAULT 1 COMMENT '用户每日限领',
  daily_max_total INT NOT NULL DEFAULT 0 COMMENT '批次每日发放上限, 0不限',
  slot_num       INT NOT NULL DEFAULT 1 COMMENT 'Redis子库存分段数(热点模板>1)',
  receive_start  DATETIME NOT NULL,
  receive_end    DATETIME NOT NULL,
  valid_type     TINYINT NOT NULL COMMENT '1固定区间 2领取后N天',
  valid_days     INT NOT NULL DEFAULT 0,
  valid_start    DATETIME, valid_end DATETIME,
  status         TINYINT NOT NULL DEFAULT 0 COMMENT '0草稿 1生效 2暂停 3终止',
  create_time    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_status_time (status, receive_start)
) COMMENT '券模板';

-- 2. 库存总账表（DB 是最后防线；issued 是已同步到DB的发放数）
CREATE TABLE coupon_stock_ledger (
  id            BIGINT UNSIGNED PRIMARY KEY,
  template_id   BIGINT UNSIGNED NOT NULL,
  total_amount  INT NOT NULL COMMENT '同模板total_amount',
  replenished   INT NOT NULL DEFAULT 0 COMMENT '已增补进Redis的额度累计',
  issued_in_db  INT NOT NULL DEFAULT 0 COMMENT 'DB实际落库的券数(对账基准)',
  version       INT NOT NULL DEFAULT 0 COMMENT '乐观锁',
  update_time   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_tpl (template_id)
) COMMENT '库存总账';

-- 3. 用户券表（分库分表，路由键 user_id；亿级数据的主存储）
CREATE TABLE user_coupon_0000 (  -- 8库 x 1024表 或按容量定
  id            BIGINT UNSIGNED PRIMARY KEY COMMENT '分布式ID=券码',
  user_id       BIGINT UNSIGNED NOT NULL,
  template_id   BIGINT UNSIGNED NOT NULL,
  request_id    VARCHAR(64) NOT NULL COMMENT '上游业务幂等号',
  status        TINYINT NOT NULL DEFAULT 0 COMMENT '0已领取 1已使用 2已过期 3已冻结 4已回退',
  receive_time  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  expire_time   DATETIME NOT NULL,
  rule_snapshot VARCHAR(512) NOT NULL COMMENT '规则快照冗余(分表后无法join模板)',
  UNIQUE KEY uk_user_req (user_id, request_id),   -- 幂等最后防线
  KEY idx_user_status (user_id, status, expire_time)
) COMMENT '用户券';

-- 4. 本地事务表（与领券写操作同库同事务，保证消息可靠投递）
CREATE TABLE coupon_issue_msg (
  id             BIGINT UNSIGNED PRIMARY KEY,
  biz_no         VARCHAR(64) NOT NULL COMMENT '=templateId:userId:requestId',
  payload        VARCHAR(1024) NOT NULL COMMENT '落库所需全部字段',
  status         TINYINT NOT NULL DEFAULT 0 COMMENT '0待投递 1已投递 2已完成 3死信',
  retry_count    INT NOT NULL DEFAULT 0,
  next_retry_time DATETIME NOT NULL,
  create_time    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_biz (biz_no)
) COMMENT '发券落库事务消息';
```

设计要点说明：
- **user_coupon 以 user_id 为路由键**（字节用 user_id 后四位分片、vivo 用 `hash(userId)/M%N` 定库 + `hash(userId)%M` 定表），因为最高频查询是"查我的券"；代价是无法 join 模板表，所以 `rule_snapshot` 冗余规则快照（vivo 的做法），冗余字段要克制。
- **`uk_user_req (user_id, request_id)` 是全链路幂等的最后防线**。注意唯一键里必须有 user_id（路由键），否则跨分片无法全局唯一；request_id 的全局唯一性由上游保证（上游不传则领券服务生成并回传，下次重试必须带同一个）。
- 40 亿用户券规模的配套动作是**冷热归档**（京东到家把过期券归档后在线表从 40 亿降到 15 亿）。

### 4.2 Redis Key 设计与数据结构选型

| Key | 结构 | TTL | 选型理由 |
|---|---|---|---|
| `ct:{tplId}` | String(JSON, 压缩字段名) | 24h+随机 | 模板读多写少；字段名精简（如 couponName→a，京东到家实践）减流出量；配本地缓存 |
| `cs:{tplId}:{slot}` | Hash: `l`=剩余额度, `{yyyyMMdd}`=当日发放量 | 活动结束后 | **库存与日计数放同一 Hash，Lua 内同脚本原子**；slot 使热点模板可拆到多分片 |
| `us:{tplId}` | Hash: field=uid, value=总领取数 | 活动结束+7d | 用户总限领计数；field 无法单独过期，靠整 Key TTL |
| `usd:{tplId}:{yyyyMMdd}` | Hash: field=uid, value=当日领取数 | 3d | **日期入 Key 而非 field**（腾讯云做法），跨天自动换 Key，天然滚动，无需清零逻辑 |
| `ik:{tplId}:{requestHash}` | String "1" | 24h | 幂等指纹，SET NX 语义在 Lua 内做；String 而非 Hash 因为要 per-key TTL |
| `uc:{userId}` | Hash: field=券ID, value=券摘要 | 30d+随机 | 用户券读模型（京东到家 40 亿条验证过的结构），领券成功即写，保证"我的券包"立即可见 |
| `sold:{tplId}` | String "1" | 活动结束 | 全局售罄标记，命中后网关层快速失败，保护 Redis |

两个关键选型理由展开：
1. **库存用 Hash 而不是 String**：剩余量与"当日发放量"必须在同一个 Lua 脚本里原子读写。若拆成两个 String Key，在集群模式下可能落在不同分片，Lua 的 KEYS 跨槽会直接报错（这是很多人第一次写集群 Lua 脚本踩的坑——所有 KEYS 必须同槽，必要时用 hash tag `{tplId}` 强制同槽）。
2. **用户计数用 Hash 而不是 String**：`us:{tplId}` 一个 Key 承载全批次用户的计数，`HINCRBY` 单命令完成"读-判-写"的原子性依赖 Lua 包裹；比每用户一个 String Key 节省内存且天然聚合。风险是 Key 会膨胀到"领取用户数 × 40 字节"，百万级用户约几十 MB，已接近大 Key 红线（京东到家给的经验阈值：集合元素 > 8000 需警惕），所以活动结束必须设 TTL 回收。

### 4.3 核心Lua脚本（校验 + 扣减原子执行）

```lua
-- KEYS[1]=cs:{tplId}:{slot}   库存Hash(含剩余额度l、当日发放量{date})
-- KEYS[2]=us:{tplId}          用户总领取Hash
-- KEYS[3]=usd:{tplId}:{date}  用户当日领取Hash
-- KEYS[4]=ik:{tplId}:{reqHash} 幂等Key
-- ARGV: 1=userId 2=reqHash 3=maxPerUser 4=dailyMaxPerUser
--       5=dailyMaxTotal 6=date(yyyyMMdd) 7=nowTs(秒) 8=idemTtl
-- 返回: >=0成功(剩余额度) | -1批次日上限 | -2用户总限 | -3库存不足
--       -6幂等命中 | -7用户日限

-- ① 幂等：指纹已存在 = 该请求已发过券
if redis.call('EXISTS', KEYS[4]) == 1 then return -6 end
-- ② 批次当日发放上限
if tonumber(ARGV[5]) > 0 then
  local d = tonumber(redis.call('HGET', KEYS[1], ARGV[6]) or '0')
  if d >= tonumber(ARGV[5]) then return -1 end
end
-- ③ 用户总限领
local ut = tonumber(redis.call('HGET', KEYS[2], ARGV[1]) or '0')
if ut >= tonumber(ARGV[3]) then return -2 end
-- ④ 用户当日限领
local ud = tonumber(redis.call('HGET', KEYS[3], ARGV[1]) or '0')
if ud >= tonumber(ARGV[4]) then return -7 end
-- ⑤ 剩余额度
local l = redis.call('HGET', KEYS[1], 'l')
if (not l) or tonumber(l) <= 0 then return -3 end
-- ===== 校验全过，以下写操作与校验原子执行 =====
redis.call('HINCRBY', KEYS[1], 'l', -1)
redis.call('HINCRBY', KEYS[1], ARGV[6], 1)
redis.call('HINCRBY', KEYS[2], ARGV[1], 1)
redis.call('HINCRBY', KEYS[3], ARGV[1], 1)
redis.call('SET', KEYS[4], '1', 'EX', ARGV[8])
return tonumber(l) - 1
```

这正是腾讯云文章的脚本骨架（它用 ZSet 做幂等、五次 HINCRBY/ZADD），我做了一处替换：幂等从 ZSet 改为带 TTL 的独立 String Key。理由：ZSet 的 member 不能单独过期，大批次跑完后 `{stockKey}:coupon:zset` 会积累百万级 member 成为大 Key，且脚本内 ZCARD/ZSCORE 的复杂度随规模退化；独立 String + 24h TTL 让幂等窗口与内存占用都可预期。（权衡：String 方案的幂等只有 24h，超长周期的重复请求靠 DB 唯一索引兜底——所以是双层幂等。）

### 4.5 完整时序（编号步骤）

1. 上游调用 `issue(cmd)`，携带 requestId 与 bizToken；网关层按 source 维度限流（券系统是底层服务，被多个上游调用，必须按上游限额保护自身——字节实践），校验 bizToken 与券模板绑定的 Token 一致（京东到家中台的防越权设计）。
2. 读模板：先查服务实例本地缓存（Caffeine，定时任务刷新，刷 Redis 时加分布式锁防多实例重复写——字节实践），miss 则查 Redis `ct:{tplId}`，再 miss 回源 DB 并回填。校验领取时间窗、模板状态。
3. 风控前置：设备指纹/黑名单/频率，羊毛党拦截在打 Redis 之前。
4. slot 路由：生成长度为 slotNum 的随机不重复数组，按序尝试；本地售罄负缓存直接跳过已空 slot。
5. `EVAL` 执行 4.3 的 Lua 脚本（注意集群下所有 KEYS 用 `{tplId}` hash tag 同槽）。返回负数错误码即终态返回（`-6` 幂等命中时回查已发券 ID 返回 DUPLICATE）。
6. Lua 成功 = 扣减完成。生成分布式 ID 作为 couponId，`HSET uc:{userId} {couponId} {摘要}`——用户券包**立即可见**（京东到家以 Redis 为 C 端主数据源、DB 可回溯的双存储思路，化解"异步落库导致看不到券"的体验问题）。
7. 写 `coupon_issue_msg`（本地事务表，独立短事务）。写失败则执行 Lua 逆操作回补额度（HINCRBY +1、删幂等 Key），保证 Redis 与"待落库消息"一致。
8. 返回 `SUCCESS + couponId`（接口内控 100ms、上游超时 500ms——字节的服务治理参数）。
9. 后台任务扫 `coupon_issue_msg`（status=0）投递 MQ；消费者 INSERT `user_coupon`（分库分表路由到 user_id 对应库表），**唯一索引冲突 = 幂等命中，直接 ACK 成功**；失败按退避重试，超限进死信 + 人工兜底。这是"本地事务表 + 最大努力通知"的最终一致闭环。
10. 库存分段增补：定时任务发现 Redis 各 slot 剩余额度合计 < M 时，从 DB 总账 `replenished + N ≤ total_amount` 约束下取 N 个额度增补到某 slot——**保证 Redis 额度始终 ≤ DB 账面**，Redis 整个崩掉最多超发上限就是已增补未落库的差额，DB 唯一索引仍兜底（腾讯云的双保险不变式）。
11. 对账：定时汇总 `user_coupon` 落库数（`issued_in_db`）与 Redis 各计数 Key、发券成功日志三方比对，差异超阈值告警 + 以 DB 为准修复 Redis 计数。
12. 状态推进/回收：RocketMQ 延时消息驱动券过期；延时超上限用**循环投递**（到期未到过期时间则再投一次）；活动结束后给各 Key 设 TTL，过期时间加随机值防集中过期打满 Redis 定期删除时间片（京东到家源码级分析得出的工程动作）。

### 4.6 容量估算方法（字节数字的复用）

- 实测锚点：MySQL 单机写 ~4000 QPS；单表千万级查询衰减；Redis 单分片写 ~2w、读 ~10w QPS。
- 12w QPS 目标 → MySQL 主库 120000/4000 ≈ **30 个分片**（若异步落库且削峰后写峰值减半，可减到 16 左右）；最坏情况 12w QPS 打同一模板 → Redis 至少 **6 个分片**（120000/20000），即 slotNum ≥ 6 且确保 slot 落在不同分片。
- 资源冗余：**线上资源 = 压测数据的 1.5 倍**。压测自底向上：单实例瓶颈 → MySQL 读写瓶颈 → Redis 单分片瓶颈 → 整体压。

## 5. 素材间的方案分歧与推荐

1. **库存扣减放 DB 还是 Redis**：vivo 选 DB 分段库存（理由：简单、无缓存一致性难题）；腾讯云与字节选 Redis（理由：吞吐）。**推荐 Redis+Lua + DB 总账分段增补**。理由：vivo 方案在万级 TPS 成立，但 DB 分段的天花板（行锁仍存在、扩容贵、连接贵）在十万 QPS 量级不可行；腾讯云的"Redis ≤ DB"不变式恰好补上了 vivo 担心的一致性问题，两个方案的优点可以叠加。
2. **防用户超领：分布式锁 vs Lua 计数**：vivo 用 Redis 分布式锁（领前获取、发放后释放、批量领券逐券加锁 + 自旋）；腾讯云把限领计数放进 Lua 原子校验。**推荐 Lua 计数**。理由：锁是"用串行化换正确性"，自旋等待在洪峰下浪费连接且加剧抖动，批量场景锁数量随券数线性增长；Lua 计数无锁、正确性由原子性保证。vivo 的锁方案可作为无法改造计数的存量系统过渡。
3. **幂等载体**：腾讯云用 Redis ZSet（Lua 内查 couponId）；vivo/字节用 MySQL 幂等（vivo 明确用唯一索引 + 历史数据刷数）。**推荐双层：Redis 快速幂等（带 TTL 的 String Key）+ DB 唯一索引兜底**。理由：纯 Redis 幂等受 TTL 与数据丢失影响；纯 DB 幂等在高并发下把读压力打回 DB。vivo 关于"唯一索引加现有表还是新建表"的选择（现有表，免表关联、利于性能）值得照抄。
4. **落库同步 vs 异步**：字节同步落库（单次发券对 MySQL 仅一次非事务性写入，30 分片扛 12w）；腾讯云异步 + 本地事务表；vivo 明确反对异步（用户账户不能实时看到券，影响体验与转化）。**推荐：Redis 用户券读模型同步可见 + DB 异步落库**。即领券成功立即 HSET 用户券 Redis（读路径以 Redis 为主数据源，京东到家验证过 40 亿条规模），DB 落库走本地事务表异步。这样同时拿到"立即可见"（vivo 的诉求）与"DB 削峰"（腾讯云的诉求）。若团队没有 Redis 主数据源 + 回溯的运维能力，退化为字节式同步落库也可接受，代价是 DB 分片数量翻倍。
5. **热点打散**：字节用"分段子库存 Key + 随机不重复轮询 + 售罄跳过"（写热点）；京东到家列出"散列多份副本"（读热点）与本地前置缓存；腾讯云列了分桶/聚合扣减/DB 热点更新三选。**推荐按读写性质分流**：库存扣减是写热点，副本方案无效（字节明确指出 key 备份只适合读多写少），用分段轮询；模板读取是读热点，用本地缓存 + 多副本。聚合扣减（合并多请求为一次批量扣减）实现复杂度高且引入聚合窗口时延，除非单分片已到极限否则不建议首先采用。
6. **一致性强度的取舍**：腾讯云坦承"Redis 故障最多丢 N 个库存"是可接受损失且未给降级路径。**推荐补上降级预案**：Redis 集群级故障时切"DB 条件更新直扣 + 限流到 DB 可承受水位"的降级模式，宁可限流慢发，不可无界超发。

## 6. 踩坑清单（按严重程度排序）

1. **校验与扣减不原子 → 超发资损**（最致命）。发现：对账任务发现发放数 > 库存、核销时财务报警。防：一切校验与写必须在单个 Lua 脚本内；SQL 层保留 `where left_stock > 0` 条件更新 + DB 总账不变式双保险。
2. **无幂等 → 重试风暴重复发券**。发现：客诉"我领到两张一样的券"；日志中同 requestId 多次成功。防：requestId 强制透传 + Redis 快速幂等 + DB `uk_user_req` 唯一索引兜底，三层缺一不可；插入冲突必须当成功处理（否则重试永远失败）。
3. **Redis 扣减成功但落库失败无补偿 → "抢到了但没券"**。发现：`coupon_issue_msg` 积压监控、Redis 发放计数与 DB 落库数差值告警。防：本地事务表与扣减结果对齐 + 逆操作回补额度 + 退避重试 + 死信人工兜底 + 每日对账。
4. **Redis 持久化/故障导致额度丢失 → 超发**。发现：Redis 主从切换后库存计数凭空变大。防：AOF everysec、额度来源于 DB 分段增补（丢失上限 = N）、重启后从 DB 总账重建 slot 额度、重建期间模板熔断限流。
5. **分布式锁 key 粒度错误 → 超领**（vivo 亲自踩过：批量领券用"用户id+多券id拼接"与单券请求的锁互不互斥）。发现：批量领券后用户券数超限的定向客诉。防：若用锁，粒度必须是"用户id+单券id"并逐券加锁；根治方案是改 Lua 原子计数，锁自然消失。
6. **单模板热点打挂 Redis 分片**（字节：12w QPS 全打一个库存 Key）。发现：某分片 CPU/带宽单点报警、该分片上所有 Key 的 RT 集体抬升（Redis 单点阻塞的表征是"整个集群都慢"，京东到家复盘过大 Key/热点导致全集群变慢、且问题分片每天漂移、慢日志却无记录的排查困境）。防：建券时对预估热点模板配 slotNum>1；轮询必须随机不重复（固定从 1 号分片开始等于没拆，字节踩过）；售罄 slot 本地负缓存跳过。
7. **计数 Key 无过期 → 内存膨胀与大 Key**。发现：Redis 内存水位单调上涨；从集群 Scan 巡检大 Key（生产禁用 KEYS）。防：日期入 Key 天然滚动、所有 Key 强制 TTL 且加随机偏移（同时防集中过期雪崩）、活动结束主动清理用 UNLINK 而非 DEL（DEL 大 Key 本身就阻塞主线程）。
8. **售罄后流量仍全量穿透到 Redis**。发现：售罄后 Redis QPS 不降、错误率飙高。防：模板级 `sold:{tplId}` 标记 + 本地缓存快速失败 + 前端置灰联动。
9. **本地缓存模板不一致 → 已下架/改限领的券还在发**。发现：运营改配置后线上仍按旧规则发券。防：本地缓存短 TTL + 配置变更广播失效 + 模板版本号校验；本地缓存只放小且少变的数据，否则 GC 受累（京东到家的提醒）。
10. **多实例并发刷缓存重复写打 Redis**（字节踩过）。防：刷写加分布式锁或按实例分片刷新。
11. **延时消息时长上限 < 券有效期 → 券永不过期**（字节踩过 RocketMQ 上限问题）。防：循环投递；或过期状态改为惰性判断（查询/核销时比对 expire_time）+ 兜底扫描任务。
12. **不做压测直接上大促**。防：自底向上压测单点瓶颈再整体压；线上资源按 1.5 倍冗余；大促实时盯盘 + 核心成功率告警。

## 7. 小结

发券链路的全部设计可以收敛成一句话：**用 Redis+Lua 把"校验+扣减"压成一个原子动作换取吞吐，用"DB 总账 + 分段增补 + 唯一索引 + 本地事务表 + 对账"把正确性兜回来，用"分段 Key + 二级缓存 + 限流隔离"把热点和故障域隔离开**。写代码时优先保证前半句的原子性不可破坏——所有后来者犯的资损错误，几乎都是在 Lua 原子边界之外又加了一次"先查后改"。
