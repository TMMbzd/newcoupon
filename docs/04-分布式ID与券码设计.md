# 第四章 分布式ID与券码设计

## 4.1 这个领域解决什么问题，在券系统中台中的位置

这个领域实际上包含两件容易混淆、但设计目标完全不同的事：

| 维度 | 分布式ID（内部发号） | 券码（外部编码） |
|---|---|---|
| 服务对象 | 数据库主键、内部流水号（券模板ID、券实例ID、领券流水、核销流水） | 暴露给用户/商户/第三方的外部字符串 |
| 典型形态 | 8 字节 long 数字 | 11 字符 Base62 字符串 |
| 核心要求 | 全局唯一、趋势递增（InnoDB 聚簇索引友好）、高可用、低延迟 | 唯一、可本地校验、可反解业务字段、不可被伪造/枚举/逆推 |
| 生成时机 | 运行时逐个/小批量申请 | 活动创建后离线批量预生成（一个批次几十万到百万张） |
| 量级 | 大促峰值数万到数十万 QPS | 单活动千万级总量，但生成是吞吐型任务而非在线请求 |

一句话定位：**ID 是给数据库和内部链路看的，券码是给外部世界看的**。两者的公共底座是"发号"能力，但券码在发号之上叠加了编码学层面的要求（校验、混淆、短码）。

在券系统中台全局中的位置：

```
              ┌─────────────────────────────────────────────────────┐
              │                 优惠券系统中台                        │
              │                                                     │
 运营/采销 ───▶ 活动中心 ──▶ 券模板管理 ──▶ 批次/预算管理                │
              │                                 │                    │
              │                                 ▼                    │
              │                     ┌────────────────────┐           │
              │   （离线）           │    券码生产服务      │──▶ coupon_code 码库
              │                     │  位段拼装+签名+混淆  │      （预生成）
              │                     └────────────────────┘           │
              │                                                         │
 用户/交易 ───▶ 领券/发券/抢券 ──▶ 用户券包 ──▶ 下单核销 ──▶ 核销流水     │
              │    （在线，峰值 10w+ QPS）   （券码本地校验/反解）        │
              │                                                         │
              └──────────────┬───────────────────────────┬────────────┘
                             ▼                           ▼
              ┌─────────────────────────────────────────────────────┐
              │        基础发号服务（Leaf：segment / snowflake）        │
              │   biz_tag 隔离：template / batch / instance / flow     │
              │   以及券码生产专用的 seq 区间分配                        │
              └─────────────────────────────────────────────────────┘
```

券系统中台要同时支持两类券：**账户型**（用户领到券包里，核销走内部 instance_id，不需要外部码）和**兑换码型**（印刷在物料上、卡密分发给渠道，凭码激活/核销）。前者只依赖发号服务，后者还依赖券码生产服务。本章覆盖这两个组件。

需求侧还有一个必须先想清楚的矛盾：美团 Leaf 的素材（a02）明确指出，**"单调递增"与"不可预测"互斥，一个方案不可能同时满足**。券系统里两类诉求都存在——流水号要趋势递增（写入性能），对外券码要不可预测（防竞对推算发券量、防黑产枚举）。所以最终形态一定是**双轨制**，而不是找一个"万能 ID"。

## 4.2 朴素实现（v1）会怎么挂

v1 是一个零经验工程师最自然的写法：

```java
// 券实例主键
coupon.setId(UUID.randomUUID().toString());
// 券码：随机串 + 先查后插
String code = RandomStringUtils.randomAlphanumeric(8);
if (codeMapper.selectByCode(code) == null) {   // 查重
    codeMapper.insert(code);                    // 插入
}
```

这个版本在日发券几万的小系统上能跑，上量后按以下四种方式死：

**故障一：UUID 当 InnoDB 主键，写入性能雪崩。**
大促 0 点发券峰值 5w QPS。UUID 36 字符、完全无序，插入时落点随机分布在 B+ 树各处，数据页频繁分裂、页内空间利用率降到一半以下，写放大 3~5 倍；同时主键长度直接进所有二级索引叶子节点，索引体积翻倍、buffer pool 命中率下降。现象：平时单库 2w TPS 的写入掉到 3k，慢查询堆积 → 连接池（200）打满 → 发券接口大面积超时 → 上游抢券线程池被拖垮 → 交易链路整体雪崩。这是把全公司最贵的组件（InnoDB）按最差访问模式使用。

**故障二：短随机码碰撞，生日悖论。**
8 位字母数字随机码空间 62^8 ≈ 2.18×10^14，看似天文数字，但一个活动生成 1000 万张时，至少一对碰撞的概率 ≈ 1 − e^(−n²/2N) ≈ 1 − e^(−0.23) ≈ **20%**——不是小概率，是几乎必然发生。碰撞叠加"先 SELECT 查重再 INSERT"的竞态（两个请求都没查到，然后同时插入），要么撞唯一索引导致批量任务失败重试风暴，要么（没建唯一索引时）**两张不同面额的券共享同一个码**。资损后果：A 用户和B用户各持同码的一张 100 元券，都能核销，等于凭空多印了一张券；或反过来，用户领到"已被核销"的券，客诉+赔付。

**故障三：顺序码可枚举，被黑产扫号。**
为了修碰撞，v1.1 改成 `activityId + 自增序列` 明文拼接。爬客拿到两张券后发现规律，写脚本遍历序列区间，直接对核销接口穷举。若核销接口再无频控，一个晚上可以扫掉一个批次数十万张券——**这是本章所有故障里唯一直接、大规模资损的**。同时明文序列让竞对通过两个时间点的券码相减精确推算你的发券量。

**故障四：DB 自增 ID 分库分表后重复，主从切换后重复。**
单库 auto_increment 撑不住，按 Flickr 老方案拆 N 台机器步长 N。两个死法：一是扩容要重排所有机器的步长和初始值，机器一多就是运维噩梦（a02 原话级别）；二是主从切换瞬间，复制延迟/半同步退化导致新主重复发号，落到券上就是两条流水同 ID，对账永远差一分钱。

## 4.3 方案演进 v1 → v2 → v3

**v2：数据库号段（单 buffer） + 64-bit 结构化明文券码。**

发号侧引入号段模式：发号服务每次从 DB 批量取一段号（如 1000 个）缓存在 JVM 里递增分配，DB 读写频率从"每号一次"降到"每 1000 号一次"，ID 是趋势递增的 64 位数字，做主键完美。券码侧改成位段结构（版本|活动|批次|序列|校验），seq 由 Redis INCR 保证批次内唯一，末位拼一个校验位拦截乱输的非法码。

v2 解决了：唯一性稳定（号段内递增、Redis 原子 INCR 无碰撞）、主键性能（趋势递增）、券码携带信息可反查、明显非法的码进库前被拦截。

v2 引入的新问题：
1. **号段边界尖刺**：号段耗尽的临界点同步走一次 DB，网络抖动或慢查询时所有发号请求挂起，TP999 出现周期性尖刺，上游恰好按 TP999 配了超时，引发重试放大。
2. **券码明文可逆推**：Base62 解码后位段结构裸露，外部可以精确识别出活动位、批次位、序列位，重新回到"可枚举"问题。
3. **Redis INCR 逐个发号**：一个百万张的批次要打一百万次 Redis，网络往返浪费且引入新的单点依赖；Redis 主从异步复制下切换还可能发出重复 seq。
4. **批量落库大事务**：千万行一把 INSERT，undo log 膨胀、主从延迟拉爆。

**v3：双 buffer 号段 + 可逆混淆 + Base62 + 批量生产流水线。**

- 号段双 buffer：当前号段消耗 10% 时异步预加载下一段，切换零阻塞；号段长度按"高峰 QPS × 600"配置，DB 短暂宕机仍可发号 10~20 分钟。
- 券码混淆：位段拼装 + 校验位之后，对整个 64-bit 做"乘法置换（奇数 MUL）+ XOR 密钥"，再 Base62 输出 11 字符。外观完全随机，但服务端用模逆元可完整还原——同一活动同批次 seq 仅差 1 的两张券，码面毫无相似度。
- 批量生产改为流水线：按 1~5 万一批分片并行生成、批量插入、异步落库，批次表记录进度，支持断点续跑和对账。

v3 之后仍然遗留、必须在最终形态里补的：snowflake 路线的时钟回拨、workerId 分配、混淆密钥的版本化轮换、校验位强度不足时的频控补偿、生成与落库的幂等与对账、码库的分库分表。

## 4.4 大厂最终形态

### 4.4.1 总体架构：双轨制

```
内部ID轨（在线、逐个）                     外部券码轨（离线、批量）
┌──────────────────────┐               ┌───────────────────────────┐
│ Leaf-segment 双buffer  │               │ 券码生产流水线              │
│  biz_tag 隔离         │               │  位段拼装(64bit)           │
│  DB: leaf_alloc 表    │               │  → checksum(4bit)         │
├──────────────────────┤               │  → 乘法混淆+XOR            │
│ Leaf-snowflake        │               │  → Base62(11字符)          │
│  ZK分配workerId+本地兜底 │               │  → 分批落库 coupon_code    │
│  时钟回拨分级处理       │               │  seq 区间: coupon_batch    │
└──────────────────────┘               │   .next_seq 号段式分配      │
                                       └───────────────────────────┘
```

选型逻辑：绝大多数内部 ID（模板、批次、实例、流水）用 segment——趋势递增、8 字节、可从指定 max_id 起始以兼容迁移；对外不可预测的需求（订单类流水、券码）不用 segment（可推算），其中需要反解业务字段的用"结构化位段+混淆"，不需要反解的用 snowflake。

### 4.4.2 内部ID：Leaf-segment 双 buffer

号段分配表 DDL：

```sql
CREATE TABLE `leaf_alloc` (
  `biz_tag`     varchar(128) NOT NULL COMMENT '业务标签: coupon_template/coupon_batch/coupon_instance/coupon_issue_flow/coupon_verify_flow',
  `max_id`      bigint       NOT NULL DEFAULT '1'  COMMENT '该业务当前已分配的最大号',
  `step`        int          NOT NULL DEFAULT '1000' COMMENT '号段长度, 建议=高峰QPS×600',
  `desc`        varchar(256) DEFAULT NULL,
  `update_time` timestamp    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`biz_tag`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='号段分配表';
```

号段申请（单事务）：

```sql
BEGIN;
UPDATE leaf_alloc SET max_id = max_id + step WHERE biz_tag = 'coupon_instance';
SELECT biz_tag, max_id, step FROM leaf_alloc WHERE biz_tag = 'coupon_instance';
COMMIT;
-- SELECT 返回的 max_id 即新区间上界，本次分得区间 (max_id - step, max_id]
```

双 buffer 核心逻辑（骨架）：

```java
public class SegmentBuffer {
    private final Segment[] segs = new Segment[2];
    private volatile int pos = 0;
    private final AtomicBoolean loading = new AtomicBoolean(false);

    public long next(String bizTag) {
        for (;;) {
            Segment cur = segs[pos];
            long v = cur.value.getAndIncrement();
            if (v <= cur.max) {
                maybePreloadNext(cur);      // 已发超10% 且另一buffer空 → 异步预加载
                return v;
            }
            Segment nxt = segs[(pos + 1) % 2];
            if (nxt != null && nxt.loaded) {
                pos = (pos + 1) % 2;        // 无缝切换，不阻塞
                continue;
            }
            loadNextSync(bizTag);           // 极端情况：预加载没赶上，退化为同步
        }
    }
    private void maybePreloadNext(Segment cur) {
        long total = cur.max - cur.min + 1, used = cur.value.get() - cur.min;
        if (used * 10 >= total && segs[(pos+1)%2] == null
                && loading.compareAndSet(false, true)) {
            asyncLoad();                    // 起独立线程取下一号段
        }
    }
}
```

要点：①号段长度 `step = 高峰期发号 QPS × 600`（约 10 分钟量），DB 宕机仍可发号 10~20 分钟；②DB 一主两从分机房 + 半同步复制 + DBProxy 切换，承认半同步退化风险，强一致需求上 MGR；③Leaf 服务分机房部署、同机房优先；④自定义 `max_id` 起始值，存量系统迁移不用改历史 ID。性能基线（美团压测）：4C8G 单机 QPS 接近 5w、TP999 = 1ms。

### 4.4.3 内部ID：snowflake 轨与时钟回拨

位段沿用标准 `1 + 41 + 10 + 12`（41 bit 毫秒时间可用 69 年；10 bit 机器 = 32 IDC × 32 台；12 bit 序列 = 单机 409.6w/s 理论值）。

workerId 分配：启动时连 ZK，在 `leaf_forever` 父节点下查自己是否注册过——注册过直接取回顺序节点号；没注册过创建持久顺序节点，取回顺序号当 workerId。同时**在本机文件系统缓存一份 workerId**，ZK 故障且恰好机器重启时仍能启动（对第三方组件弱依赖）。

时钟回拨分级处理（运行期）：

```java
if (timestamp < lastTimestamp) {                 // 发生了回拨
    long offset = lastTimestamp - timestamp;
    if (offset <= 5) {
        try {
            wait(offset << 1);                   // 偏差<=5ms：等待两倍时长再取一次时间
            timestamp = timeGen();
            if (timestamp < lastTimestamp) throw new ClockBackwardsException(timestamp);
        } catch (InterruptedException e) { throw new RuntimeException(e); }
    } else {
        throw new ClockBackwardsException(timestamp); // 偏差>5ms：拒绝发号并报警
    }
}
```

启动时的防线：先比对本机时间与 ZK `leaf_forever/${self}` 节点记录时间，小于则判定大步长回拨、启动失败报警；新节点则通过 RPC 收集所有存活节点时间取均值做时间投票，偏差超阈值同样拒绝启动。运行期每 3s 上报本机时间。这是"检测+规避"而非根治——根治只有放弃系统时钟（如单调时钟源），工程上普遍接受前者。

### 4.4.4 券码位段设计（核心数据模型）

```
| version(4) | activityId(24) | batchId(12) |   seq(20)   | checksum(4) |
  版本/密钥族     活动号<=1677万     批次<=4095      单批<=1048575     防伪校验
                          合计 64 bit == 一个 Java long
```

- **seq 是唯一性的唯一来源**，绝对不可重复；其余字段是"业务坐标"。
- 容量核算：单活动上限 = 4095 批 × 104.85 万/批 ≈ **42.9 亿张**，亿级体量安全的前提是**单批次不超 1048576、超了拆批**（推荐做法），而不是改位段。
- **version 不是容量预留，而是密钥族/算法版本号**：轮换混淆密钥、调整位段时，解码先看 version 再选常量组，旧码永久可解。这是素材（a10）把 version 停在 v1 的字段被长期误用的地方——它真正的价值在轮换那一刻。

编码/解码（可直接抄）：

```java
public final class CouponCodeCodec {
    // 每个版本一组常量，KMS 下发，严禁硬编码进仓库
    private static final long SECRET = 0xA5A5A5A5A5A5A5A5L; // checksum 密钥
    private static final long MUL    = 0x9E3779B97F4A7C15L; // 乘法置换, 必须为奇数
    private static final long XORK   = 0xC3A5C85C97CB3127L; // XOR 混淆密钥
    private static final long MUL_INV = modInverseOdd(MUL); // mod 2^64 模逆元

    public static String encode(int ver, int act, int batch, int seq) {
        checkRange(ver < 1 << 4, act < 1 << 24, batch < 1 << 12, seq < 1 << 20);
        long raw = (((long) (ver   & 0xF))     << 60)
                 | (((long) (act   & 0xFFFFFF)) << 36)
                 | (((long) (batch & 0xFFF))    << 24)
                 | (((long) (seq   & 0xFFFFF))  << 4);
        raw |= (raw ^ SECRET) & 0xF;                 // 4bit checksum 塞进低 4 位
        long perm = raw * MUL ^ XORK;                // Java long 溢出即 mod 2^64
        return Base62.encode(perm);                  // 固定 11 字符
    }

    public static CodeFields decode(String code) throws CodeVerifyException {
        long perm = Base62.decode(code);
        long raw  = (perm ^ XORK) * MUL_INV;         // 逆混淆
        if ((raw & 0xF) != ((raw ^ SECRET) & 0xF))   // 本地校验, 不查库
            throw new CodeVerifyException("bad checksum");
        return new CodeFields((int)(raw >>> 60) & 0xF, (int)(raw >>> 36) & 0xFFFFFF,
                              (int)(raw >>> 24) & 0xFFF, (int)(raw >>> 4) & 0xFFFFF);
    }

    static long modInverseOdd(long a) {              // 牛顿迭代, 仅奇数有逆元
        long inv = a;
        for (int i = 0; i < 6; i++) inv *= 2 - a * inv;
        return inv;
    }
}
```

数值自检用例（用于单测黄金样本）：`ver=1, act=1, batch=1, seq=1` → raw64 = 1152921573343100949 → 混淆后 perm = 4256394637395565726 → Base62 = `54qkCv1w1AO`；seq=2 时为 `2HYmzNkLPFc`——同批相邻 seq 码面完全不同。

为什么用"乘法置换 + XOR"而不是哈希或真加密：混淆必须**可逆**（核销端要反解出活动/批次做路由和审计），哈希不可逆；AES 等分组密码引入 IV/块对齐复杂度，而一次奇数乘法 + 一次 XOR 是 O(1)、无碰撞、可完整还原，对"防结构逆推"这个威胁模型足够。它的安全边界也必须讲清：这是弱混淆，常量一旦泄露即失效，所以必须 KMS 管理 + version 版本化轮换，不能当加密用。

校验位为什么只给 4 bit：Base62 下只占 1 个字符，随机穷举的到达率降到 1/16，配合验证接口频控（见 4.4.9）即可；再加长会拉长码面，损害印刷/口播体验。**checksum 拦截的是"乱输/误输"，不是"定向伪造"**——后者靠混淆常量保密 + 频控。

编码字符集：Base62 输出 11 字符；若业务场景含人工手输/客服口播，换 Crockford Base32（剔除 0/O/1/I，大小写不敏感，长度 13 字符），用 version 位区分编码集。

### 4.4.5 表结构 DDL（在素材基础上的改进版）

```sql
CREATE TABLE `coupon_batch` (
  `id`           bigint       NOT NULL COMMENT '主键, 号段服务分配',
  `activity_id`  int unsigned NOT NULL COMMENT '活动ID, <2^24',
  `batch_no`     int unsigned NOT NULL COMMENT '活动内批次号, <4096',
  `total_count`  int          NOT NULL COMMENT '计划生成数量, <=1048576',
  `next_seq`     int unsigned NOT NULL DEFAULT 0 COMMENT '下一个可分配 seq（号段式分配游标）',
  `gen_count`    int          NOT NULL DEFAULT 0 COMMENT '已生成数量（对账用）',
  `issued_count` int          NOT NULL DEFAULT 0 COMMENT '已发放数量',
  `status`       tinyint      NOT NULL DEFAULT 0 COMMENT '0待生成 1生成中 2已生成 3已作废',
  `create_time`  datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`  datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_act_batch` (`activity_id`, `batch_no`),
  KEY `idx_activity` (`activity_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='券码批次表';

CREATE TABLE `coupon_code` (
  `id`          bigint       NOT NULL COMMENT '主键, 号段服务分配',
  `code`        varchar(16)  NOT NULL COMMENT 'Base62 券码, 11字符',
  `activity_id` int unsigned NOT NULL COMMENT '冗余: 反解所得, 支持唯一约束与检索',
  `batch_id`    bigint       NOT NULL COMMENT '冗余: 分片键',
  `seq`         int unsigned NOT NULL COMMENT '冗余: 批内序列号',
  `status`      tinyint      NOT NULL DEFAULT 0 COMMENT '0未发放 1已发放 2已核销 3已过期 4已作废',
  `user_id`     bigint       DEFAULT NULL COMMENT '发放对象',
  `issue_time`  datetime     DEFAULT NULL,
  `redeem_time` datetime     DEFAULT NULL,
  `create_time` datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_abs`  (`activity_id`, `batch_id`, `seq`),  -- 语义唯一性兜底
  UNIQUE KEY `uk_code` (`code`),                            -- 编码正确性自检兜底
  KEY `idx_batch_status` (`batch_id`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='券码表, 按 batch_id 分库分表(16/64分片)';
```

相对素材（a10）原始 DDL 的关键改动及理由：①`activity_id/batch_no/seq` 从 bigint 收紧为 `int unsigned`——索引更小，且天然在数据库层强制 2^24/2^12/2^20 上界；②**两个唯一索引用途不同**：`uk_abs` 是业务唯一性的最终防线（即使编码改版也成立），`uk_code` 是编码正确性自检（撞它说明 codec 有 bug，必须报警而不是 IGNORE）；③去掉单列 `idx_status`（3 个取值、选择性极差），并入 `(batch_id, status)` 复合索引；④去掉冗余 `checksum` 列——checksum 就在 code 里，`decode()` 即得，落库反而多一份一致性负担；⑤补 `update_time/next_seq/gen_count`，支撑断点续跑与对账；⑥`coupon_code` 按 `batch_id` 取模分片——同批次物理聚集，批次对账、按批次作废都是单分片操作；按活动查则先反解 code 得 activity，再走批次清单路由。这就是**结构化券码与分库分表的联动红利：一个码自己就是路由键**。

### 4.4.6 seq 的号段式分配（批次内）

单批次生成通常是一个吞吐型任务，可能多实例并发分片执行。seq 的分配采用与 Leaf 同源的号段思想，落在批次表上：

```sql
UPDATE coupon_batch
   SET next_seq = LAST_INSERT_ID(next_seq + #{n})   -- 把新值写进会话变量
 WHERE id = #{id} AND next_seq + #{n} <= 1048576;   -- 上界校验, 防溢出进位
SELECT LAST_INSERT_ID();   -- 返回区间上界, 本次分得 (ret-n, ret]
```

`UPDATE` 的行锁天然串行化并发分片，affected rows = 0 说明批次容量耗尽，直接报错拆批。Redis 侧等价实现（跨实例高并发时可选）用 Lua 保证"INCRBY + 上界校验"原子：

```lua
-- KEYS[1]=coupon:batch:seq:{activityId}:{batchId}  ARGV[1]=n  ARGV[2]=1048576
local hi = redis.call('INCRBY', KEYS[1], tonumber(ARGV[1]))
if hi > tonumber(ARGV[2]) then
  redis.call('DECRBY', KEYS[1], tonumber(ARGV[1]))
  return -1
end
return hi - tonumber(ARGV[1]) + 1   -- 返回区间起点(含)
```

### 4.4.7 批量生产流水线（时序）

1. 运营/上游在活动中心创建券模板与批次，写 `coupon_batch`（status=0，total_count ≤ 1048576），触发生产任务。
2. 生产服务做容量断言：activityId < 2^24、batch_no < 2^12、total_count ≤ 2^20，任一越界直接拒绝（拆批或换活动）。
3. 将 total_count 按 chunk（默认 2 万）切分为 N 个子任务投递线程池/MQ，状态置 1（生成中）。
4. 每个子任务按 4.4.6 的号段 SQL 领一段 seq 区间 `[s, s+n)`。
5. 循环 `seq ∈ [s, s+n)`：`CouponCodeCodec.encode(...)` 得 11 字符码，组装行。
6. 每积累 1~5 万行执行一次多值批量 `INSERT`（不使用 INSERT IGNORE——期望零冲突，撞唯一键必须抛错报警）；子任务完成回写 `gen_count += n`（乐观锁防覆盖）。
7. 服务重启的断点续跑：以 `coupon_code` 中 `(activity_id, batch_id)` 的 max(seq) 与 `next_seq` 对比，只补缺失区间。
8. 全部子任务完成后批次置 2（已生成），投 MQ 通知发放侧预热码库缓存。
9. 对账Job定时校验 `count(*) == gen_count == total_count`，缺号区间自动触发补生成，连续不一致报警。

### 4.4.8 Redis key 设计

| key | 结构 | TTL | 用途 | 选型理由 |
|---|---|---|---|---|
| `coupon:code:st:{code}` | Hash（f: status/activity_id/batch_id/user_id） | 1 天，核销后永久 | 核销前置缓存 | 多字段按需读写（HGET 单字段）避免 String+JSON 的读改写；code 反解可得 batch_id 作 key 的一部分，天然打散 |
| `coupon:code:vf:{uid或ip}` | String，INCR | 60s | 验证接口频控 | 计数器必须用 INCR 原子自增；补偿 4bit checksum 的 1/16 穿透率 |
| `coupon:batch:seq:{act}:{batch}` | String，INCRBY | 批次生命周期 | seq 区间分配（4.4.6 备选） | 一次网络往返拿整段，配合 Lua 做上界校验 |
| `coupon:code:lock:{code}` | String，SET NX | 5 分钟 | 核销/兑换进行中互斥 | 防同一码双端并发核销（与核销章的分布式锁衔接） |

### 4.4.9 核销侧本地校验时序

1. 收到券码，先过频控（`vf` 计数超阈值直接拒绝，不进入解码）。
2. 规整输入：trim、大写归一（Base32 场景）、校验长度 11/13。
3. `Base62.decode` → 逆 XOR → 乘模逆 → checksum 校验，失败即拒（**这一步不碰任何存储**）。
4. 拆字段得 version → 选对应密钥组常量（支持轮换）。
5. 用 `activity_id/batch_id/seq` 定位分片，读 `coupon_code` 或 `st` 缓存做业务校验（状态、归属、有效期）。
6. 通过后进入核销事务（SET NX 锁 + 状态机流转，详见核销章）。

### 4.4.10 接口签名汇总

```java
public interface IdGenService {                      // 内部发号
    long nextId(String bizTag);                      // 在线逐个
    List<Long> nextIds(String bizTag, int n);        // 在线小批量
    IdSegment applySegment(String bizTag, int size); // 号段租借: (min, max]
    long registerWorker(String ip);                  // snowflake workerId 注册
}

public interface CouponCodeService {                 // 外部券码
    BatchGenResult produceBatch(BatchGenCmd cmd);    // cmd: activityId,batchNo,totalCount,chunkSize
    CodeFields verifyLocal(String code);             // 纯本地校验+反解, 抛 CodeVerifyException
    void compensate(Long batchId);                   // 对账补号
}
```

容量与性能基线：Leaf-segment 单机（4C8G）≈ 5w QPS、TP999 = 1ms；snowflake 理论 409.6w/s；step = 600 × 高峰 QPS；批量插入 1~5 万行/批；单活动券码容量上限 ≈ 42.9 亿。

### 4.4.11 监控与报警清单（上线前配齐）

发号与编码是"静默组件"——坏了不报错，只发坏号。必须用指标把它照亮：

- 发号侧：每个 biz_tag 的 QPS 与号段消耗速率（用于反推 step 是否够 600 倍）、取号段耗时、TP999（盯周期性尖刺即单 buffer 病）、DB 主从延迟、workerId 重复注册次数。
- 时钟侧：`lastTimestamp - 当前时间` 回拨次数与幅度（任何一次 >5ms 的拒绝都必须报警）、节点时间与集群均值偏差。
- 券码侧：checksum 校验失败率与每秒失败次数（突增 = 穷举攻击或上游改码规则）、`uk_code` 撞索引次数（非 0 即编码 bug）、`uk_abs` 撞索引次数（非 0 即 seq 分配 bug）、批次 `gen_count vs total_count` 对账差值、Base62 decode 异常数。
- 密钥侧：常量版本分布（解码请求中各 version 占比，轮换后旧版本占比应单调下降，长期不降说明有硬编码旧常量的存量服务）。

## 4.5 素材间的方案分歧与推荐

1. **seq 的来源**：券码素材（a10）建议"Redis INCR，为避免单点可用 Snowflake"；ID 素材（a02）的哲学是号段批量预取。**推荐号段式区间分配**（4.4.6）：百万张批次逐个 INCR 是一百万次网络往返；Snowflake 产出的 64-bit ID 根本塞不进 20-bit 的 seq 字段，不可行；号段一次往返拿整段，且上界校验天然防 seq 溢出。
2. **"不可预测"的实现路径**：a02 用双方案并存（segment 承认可预测、snowflake 解决预测）表达"单调与不可预测互斥"；a10 用可逆混淆解决。两者不冲突而是**分工**：内部流水要趋势递增 → segment；对外券码既要不可预测又要可反解 → 结构化+混淆（snowflake 不可反解业务字段，不满足"本地校验+路由"诉求）。
3. **workerId 分配**：a02 给了手动配置（小规模）和 ZK 顺序节点 + 本地文件兜底（大规模）两条路。券中台发号集群通常几十台，**推荐先用号段 DB 直接发 workerId**（workerId 本身就是一个 biz_tag）+ 本地文件缓存，少维护一套 ZK；跨机房数百节点再上 ZK。
4. **唯一性由谁保证**：a10 用 `uk_code` 唯一索引兜底；a02 的立场是发号服务是唯一权威（生成器保证）。**推荐双保险 + 职责分离**：生成器对唯一性负责，`uk_abs` 兜语义、`uk_code` 兜编码 bug——但要把"撞 uk_code 即报警"写进运维手册，唯一索引是防线不是常态路径。
5. **checksum 强度**：a10 自认 4 bit "扛住大部分暴力穷举"偏弱。推荐维持 4 bit 但**强制配频控**（4.4.9 第 1 步），而不是加长签名——码长每 +1 字符，口播/印刷成本都在涨，而频控对定向攻击的抑制远强于多 4 个 bit。

## 4.6 踩坑清单（按严重程度降序）

1. **snowflake 时钟回拨发重号**（资损级：重复流水/重复码）。发现：启动时 ZK 时间戳比对 + 运行时回拨检测 + 报警；2017 闰秒真实发生过。防：≤5ms 等待两倍时长、>5ms 拒绝发号、NTP 用 slew 模式渐进同步、每 3s 上报时间做节点时间投票。
2. **MUL 用了偶数**（灾难级：无模逆元，全部券码解码失败，整批次作废）。发现：单测断言 `(MUL & 1) == 1` + encode/decode 回环测试 + 黄金样本（`54qkCv1w1AO`）。防：常量进代码评审 checklist，modInverseOdd 启动时自校验。
3. **seq 越界进位污染高位字段**（资损级：seq 到 2^20 后溢出改写 batchId/activityId，券码串到别的批次）。发现：解码后 batch/activity 与批次表对不上、uk_abs 撞索引。防：编码前显式 range 断言 + 分配 SQL 的 `next_seq + n <= 1048576` 上界 + 字段收紧为 int unsigned。
4. **明文码可枚举被扫号**（资损级）。发现：核销接口出现批量顺序尝试的特征（失败率突增、来源集中）。防：混淆常量必上、验证频控、checksum 前置拦截、监控"校验失败/QPS"比值。
5. **密钥硬编码进 Git / 不版本化**（潜伏资损：泄露后混淆形同虚设）。发现：安全审计、红队。防：KMS 下发、version 字段作密钥族号、解码按 version 路由常量组，泄露后灰度轮换。
6. **DB 主从切换重复发号**。发现：主从数据校验任务、流水对不上账。防：一主两从 + 半同步 + DBProxy；接受小概率并保留业务唯一索引兜底；强一致场景上 MGR。
7. **号段耗尽尖刺打挂上游**。发现：TP999 周期性毛刺与上游超时重试同时出现。防：双 buffer + 10% 阈值预加载 + step = 600 × QPS；监控每 biz_tag 消耗速率。
8. **千万行单事务插入**。发现：主从延迟报警、undo 表盘暴涨、批量任务超时回滚。防：1~5 万/批 + 异步分片 + 断点续跑。
9. **UUID 当 InnoDB 主键**（性能级）。发现：写入 TPS 与页分裂率监控。防：趋势递增 64 位主键；主键尽量短（二级索引叶子含主键值）。
10. **验证接口无频控，4bit checksum 被高频穷举穿透**（1/16 到达率直打 DB）。发现：DB 读 QPS 异常、checksum 失败率曲线。防：`vf` INCR 频控先行、非法码在解码层全部拦截。
11. **Base62 的 0/O/1/l 混淆与大小写敏感**（体验级：客服口播必错）。发现：客诉。防：手输场景用 Crockford Base32，入口统一大写归一。
12. **生成任务无对账**（完整性级：重启丢区间，码库缺号，发放侧库存对不上）。发现：`count(*) vs gen_count vs total_count` 定时校验。防：对账 Job + 缺号区间自动补生成。

## 4.7 小结

这一章的骨架只有三句话：内部 ID 走"号段双 buffer + biz_tag 隔离 + snowflake 补位"的双轨发号服务，对外券码走"64-bit 位段 + 4bit 校验 + 奇数乘法混淆 + Base62"的预生成码库；唯一性的权威在生成器，防线在唯一索引；seq 的 2^20 上界、MUL 的奇性、密钥的版本化、时钟的回拨，是四个上线前必须逐条打钩的硬约束。下一章的发放与防超发，将直接消费本章的批次库存模型与码库分片。
