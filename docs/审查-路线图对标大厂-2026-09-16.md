## 1. 总览：这次审查最重要的五个判断

1. **M1 的"正确性收口"方向是对的，但收口的是"账内正确性"**——对账体系自己（同应用写双方账本）对代码对称性 bug 是盲的（P0 Bug① 实证：confirm 抹账让三层对账全盲，靠外部评审而非任何运行时防线挖出）。**独立数据源的旁证核对**（事件流水×状态机）是缺失的下一层。
2. **全路线最大的结构性缺口是"钱的后半程"**：活动/预算实体层缺失（成本按金额管控无实体）、成本分摊落账（share_detail）缺失、退款冲销链路缺失且三份文档三种口径——发放侧防线（防超发）世界级，**核销之后的钱**（分摊/冲销/结算）基本空白。这恰是大厂"计"域的核心。
3. **止血能力悬空**：全部对账异常出口止于"告警+人工"，而最严重的 GUARD_FAILED 意味着 DB 账本不可信——此时最后一道防线带伤仍在发放。蚂蚁五段论（发现→定性→止血→恢复→复盘）里"止血"必须自动化。最小落点已被两位专家独立核实：复用 soldout 短路原语加一个 c:fz 冻结标志，约 5 行。
4. **可用性侧一片空白且被三个领域同时点名**：Redis 强依赖的降级链路（设计四处成文、实现零、登记零）、Redis 部署参数基线（红线声称的收窄手段在 compose 里不存在）、熔断/限流的形态与维度。M2 必须从"监控告警"升级为"监控+止血+降级"。
5. **热路径性能炸弹两枚（当场可修）**：六个 casXXX 谓词全部缺 user_id → 核销/释放/收场全部 64 分表广播（M3 压测前必修）；压测若在袖珍数据集上跑，容量结论系统性高估（需百万级造数铺垫）。

## 3. 对账升级立项草案（待批准）

**用户的裁定**："对账按大厂标准来，一开始就应有清晰计划和目标，不要拖到后面积重难返。"结合资金域三位专家的质证结论（CDC/Flink 平台不该提前上，但分层目标必须现在定死），立项如下：

**目标（分级发现 SLA）**——对账从"一套巡检"升级为"三档速度"：

| 档 | 对象 | 发现时效 | 载体 |
|---|---|---|---|
| 资金核心 | 恒等式/在途/账本互证 | 分钟级（现状 60s×2 轮，保持） | Redis 原子快照巡检（已有） |
| 资产维度 | 占用单×券状态/交叉核对/悬挂 | **小时级**（现状 24h，升级） | 独立 XXL 任务 1h（M2，B3） |
| 账证旁证 | 事件流水×状态机配对 | 小时级→分钟级演进 | 批次增量核对（M4，D4）→ 流式（量级触发） |

**架构原则（大厂标准的可迁移部分）**：①账证分离——旁证核对的采集链路独立于业务代码（binlog 消费，不依赖同一个应用写双方）；②流水是最高优先级证据（事件表已是事务性 outbox，M1-M3 只需守住"每个状态变迁必落事件"纪律——已基本成立）；③每档验收=资损注入演练+MTTD 度量（B6），不是"对上了就行"。

**流式（Flink）的触发条件写死**：M5 落地后若 日发>500 万 或 单模板 QPS 使 1h 档的敞口不可接受 → 上 CDC+Flink 双流 join（复用 outbox 事件流+binlog 状态流，规则三句：按 event_no 配对/恒等式累加/超窗报警）。**此前不建平台**（符合"无痛点技术是负资产"）。

**顺手修掉的两条独立发现**：日键探测器（B4，补"日限敞口不可探测"）；对账自身元监控（B5，安全网活性）。

### 交易核心与营销玩法（trade）
**A1 [high/missing] 用券-退款退券（售后逆向链路）**
- 缺口：质证属实且比报告更严重——是三处不自洽而非两处：docs/01:234 规定'USED 是终态，退款不自动回券，例外走运营定向补发'；docs/05:393 规定'已支付整单退款 USED→RETURNED，有效期内默认回 AVAILABLE'；docs/05:414 又规定'仅整单退款保留 RETURNED 终态'（终态与回可用自相矛盾）。实现侧跟的是 docs/01：EventType 仅 1~7 无退款事件，CouponTransition 无任何 USED 出边，释放只覆盖 LOCKED→USABLE，coupon_usage 幂等锚点是订单号+券id、无 refund_no。STATUS §4 漂移表把 docs/05 标为'✅ 三段已实现'却未标注该条款未实现/被取代——即矛盾既无 ADR 裁决也无漂移登记。ROADMAP M1-M8 与 L1-L22 均无售后逆向条目，M6-⑦ 客服补发只是人工通道。而 M5-④ 财务对账口径依赖的 share_detail（docs/05 自带'退款按行冲销'注释）没有退款冲销规则就无法闭环。
- 大厂做法：美团/京东到家标准做法：整单退款且券在有效期内→自动回退可用，回退动作挂退款单号幂等（防 MQ 重复消费二次回退），一券限退 N 次防'下单-退款'刷券套利；部分退款不退券，只按优惠分摊明细行冲销商家承担/平台补贴两本账；回退券效期一律不顺延，特殊赔付走定向补发专券。阿里系：benefit share 随退款逆向按行冲销，资金流与优惠流分离对账。
- 建议：M5 开题前置 ADR 裁决三处矛盾并同步修正 STATUS §4 对 docs/05 的漂移标注；裁决本身免费，两个方向的最小落点都便宜：若裁'退款回可用'——refund_no 幂等锚点+一券限退 N 次频控+效期不顺延，与 M5-③ share_detail 同批落地（行冲销依赖分摊明细）；若裁维持 docs/01'USED 终态'——最小落点收窄为 share_detail 按行冲销（部分退款财务口径仍需要）+ M6-⑦ 补发通道关联退款单号。报告建议的'回退走占用单新增终态而非改 USED 语义'是可行候选方案之一，由 ADR 定。
