# S2 流量治理与租户策略 —— 需求清单与设计（2026-10-04）

> **本文档的位置**：ROADMAP V2 的 S2 阶段，工序 = **需求清单 → 设计文档 → 用户批准 → 红绿灯实施**。当前状态：**待批准**。
> **上游依据**：[ROADMAP-V2](ROADMAP-V2.md) §2 S2（2026-10-04 扩版）；[对标-大厂能力地图](对标-大厂能力地图-2026-09-30.md) 域⑦（流量治理）；[S1 设计文档](S1-开放接入层-需求与设计-2026-10-01.md)（插槽与遗留项）。
> **一句话**：让系统**在被打的时候不垮**，并且**能按租户分别调**——把租户从一个"身份"变成一份"可运营的策略"。

---

## 1. 起点：S1 留下了什么，缺什么

| 方面 | S1 完成的部分 | S2 要补的 |
|---|---|---|
| 身份 | appId + 签名认证，每个请求都有可信身份 | —— |
| **配额** | 按 appId 的 QPS / 日配额，**固定窗口**（边界最多放行 2 倍） | 换成限流器家族（滑动窗口 / 令牌桶 / 漏桶 + 冷启动预热） |
| **治理 key** | 资源命名 `接口[:维度[:值]]` 已就位 | 多维度限流真正用上它（IP / 接口 / 链路） |
| **开关** | 全站级开关（注解 + 拦截器），**全开或全关** | 租户级开关 + **三级预案**（一组开关的批量切换） |
| **超时** | `deadline` 只在上下文里**透传**，不做实际裁剪 | 接上：按 deadline 裁剪下游调用超时，快到期就不做非必要工作 |
| **依赖故障** | 没有任何熔断：Redis 挂了每个请求都要等超时 | 调用熔断（Resilience4j）：依赖不可用时快速失败 |
| **配置** | 参数散落在代码默认值 + 全局配置文件里 | **租户配置中心**：超时 / 阈值 / 开关默认值按租户配 |
| **观测** | 只有领券 RT 与结果分布 | 治理指标：限流命中、熔断状态、租户用量 |

**为什么把这四块放在同一个阶段**：第 0 块（租户配置）是另外三块的**共同输入**——熔断要按租户读阈值、限流要按租户读参数、开关要按租户取默认值。分开做的话，每做一项都要回来补一次"从哪读配置"。

## 2. 决策点（需要拍板）

### D1｜限流的多维度怎么组合？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）** | **多维度独立计数，任一超限即拒**。appId 是主维度；IP / 接口 / 链路作为可选维度，各自有独立阈值，互不影响 | 每个维度一次存储往返（可合并成一次 Lua） |
| B | 只保留 appId 维度（S1 现状，只换算法） | 治理能力不完整：挡不住"某个 IP 打某个接口" |
| C | 支持维度**组合规则**（如"IP+接口"联合计数） | 表达力最强，但要引入规则引擎与规则管理，成本翻倍 |

**推荐 A**。理由：A 覆盖了大厂治理矩阵里"多个独立维度"的常见形态，且实现是把同一个限流器跑多遍；C 的联合计数属于"规则引擎"范畴，本项目在 [对标-P2对照](对标-P2实现对照-2026-09-30.md) §4 已明确不做规则引擎。

### D2｜"匀速排队"做不做？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）** | **本阶段不做排队**，只做"快速失败 + Warm Up 预热" | 少一种流控效果 |
| B | 做排队（请求进队列、按固定速率放行） | **在同步 Servlet 模型下，排队 = 占住请求线程等待**。QPS 一高，线程池先被打满，结果是"整个服务不可用"而不是"请求变慢" |

**推荐 A**，并把理由写进文档：**排队适合异步/网关模型（Netty 事件循环，等待不占线程），不适合同步阻塞模型**。本项目的超时预算是 3 秒、Tomcat 线程池有限——排队会把"拒绝一部分"变成"全部拖死"。列入增量清单，触发条件 = 引入网关层或异步化之后。

### D3｜熔断的粒度：依赖级还是租户级？

| 选项 | 说明 |
|---|---|
| **A（推荐）** | **依赖级（全局）为主 + 租户级为辅**。依赖熔断管"Redis/MySQL 整体不可用"；租户熔断管"某个租户把依赖打出异常" |
| B | 只做依赖级 | 一个租户的异常流量会持续打依赖，别家跟着受影响 |
| C | 只做租户级 | 依赖整体挂了时，每个租户要各自探测一遍才熔断——探测本身就是压力 |

**推荐 A**。两层的关系是：**依赖级是"总闸"，租户级是"分闸"**。依赖级先熔断（保护依赖），租户级随后识别出"是谁在制造异常"并把它单独拦下。

### D4｜熔断之后返回什么？

| 依赖 | 熔断后的行为 | 理由 |
|---|---|---|
| Redis 闸门 | `5001 降级中，请稍后重试` | 库存扣不了就是发不了券，但**是可恢复的**（Redis 回来就好），告诉调用方重试 |
| MySQL | `5000 系统繁忙，请稍后重试` | 同上，但它是更底层的故障，语义上归"系统繁忙" |
| **MQ 投递（发件箱）** | **不熔断** | 发件箱本身就是"重试 + 退避 + 死信"的机制；再套一层熔断等于**给同一个问题加两套解决办法**，还会让"投递归属不清" |
| 外部触达（S6 才有） | 跳过 + 落表标记未发送 | 触达不是核心链路，失败不该影响发券 |

**推荐按依赖区分**（上表）。这一条的价值在于**明确说出"哪里不熔断"**——不加区分地给每个外部调用套熔断，是常见的过度设计。

### D5｜租户配置怎么生效？

| 选项 | 说明 | 生效延迟 | 成本 |
|---|---|---|---|
| **A（推荐）** | 数据库表 + 本地缓存 + 定时刷新（30 秒）+ 管理面改动主动失效 | ≤30 秒（本实例立即） | 一张表 + 一个带缓存的读取服务（与已有的接入方缓存同款） |
| B | 只放配置文件 | 要重启 | 最低，但"改一个租户的阈值要重启全站"不可接受 |
| C | 接入配置中心（Nacos/Apollo） | 秒级 | 引入一个新组件与一套新运维 |

**推荐 A**。理由：S1 已经有一套成熟的缓存模式（防击穿 / 负缓存 / TTL 抖动 + 主动失效），复用即可；配置中心的收益（秒级、多实例）在单实例阶段用不上，触发条件是"多实例部署"。

**回落策略（必须写死）**：读不到配置 → 用**全局默认值**并记一条 WARN。**不让"配置缺失"变成"功能不可用"**。

### D6｜三级预案是什么形态？

| 选项 | 说明 |
|---|---|
| **A（推荐）** | **预案 = 一组预置的开关组合**。蓝（预防）/ 黄（局部降级）/ 红（保命）各是一份"哪些开关置为什么值"的清单；执行预案 = 批量套用 + 记审计 |
| B | 独立的预案对象 + 状态机（含自动升降级） | 自动升降级需要可靠的判据，容易误判；本阶段先做"人按一下" |

**推荐 A**。理由：预案的价值在**"出事时人不用临场想"**——把"该关哪些"提前写好、一键套用。自动升降级是下一步（而且它依赖 S2 的观测数据积累）。

## 3. 需求清单（批准后即为实施与验收的依据）

| # | 需求 | 验收（可演示可测） |
|---|---|---|
| **RQ-1** | ✅ **租户配置中心**：`open_app_config` 表 + 带缓存的读取服务 + 管理面读写接口 + 变更审计 | 给租户 A 配阈值、租户 B 不配 → A 用自己的、B 用默认值；把缓存里的配置读坏 → 回落默认值且有 WARN |
| **RQ-2** | ✅ **现有配额改读租户配置**：S1 的固定窗口 QPS/日配额，阈值来源改为租户配置（含算法可选） | 改一个租户的 QPS 阈值 → 30 秒内生效、**不重启**、不影响其他租户 |
| **RQ-3** | ✅ **限流器家族**：滑动窗口 / 令牌桶 / 漏桶三种实现 + **Warm Up 冷启动预热** | 三种算法各有一条用例证明其形状差异（如令牌桶允许突发、漏桶匀速、滑动窗口无边界双倍） |
| **RQ-4** | ✅ **多维度限流**：appId / IP / 接口 / 链路，各自独立阈值，可单独启停 | 关掉 appId 维度只留 IP 维度 → 同一个 IP 被限、别的 IP 不受影响 |
| **RQ-5** | ✅ **调用熔断（依赖级）**：Redis 闸门 / MySQL 两个依赖的熔断 + 各自降级语义 | 把 Redis 打出连续异常 → 熔断打开 → 快速失败（不再等超时）→ 恢复后半开探测成功；给出状态变化 |
| **RQ-6** | ✅ **调用熔断（租户级）**：识别并隔离"制造异常的租户" | 让租户 A 持续触发依赖异常 → A 被单独熔断 → 租户 B 仍然正常 |
| **RQ-7** | ✅ **deadline 裁剪**：把 S1 透传的超时预算接上（用预算裁剪下游调用超时） | 传 200ms 预算 → 下游调用超时被压到预算内；剩余预算不足时跳过非必要工作 |
| **RQ-8** | ✅ **租户级开关 + 三级预案**：开关支持租户覆盖；蓝/黄/红三份预置清单，一键套用 | 一键套用"黄" → 预设的非核心开关批量关闭、核心链路仍可用；套用过程有审计 |
| **RQ-9** | ✅ **演练脚本**：注入故障 → 一键降级 → 验证 → 恢复，全程可复现 | 一条命令跑完演练，输出每步的现象与判定 |
| **RQ-10** | ✅ **治理观测**：限流命中数、熔断状态与切换次数、租户用量进 Prometheus | `/actuator/prometheus` 能看到这些指标 |
| **RQ-11** | ✅ 教学文档（`study/v2/`）+ 面试刁难卡 | 按既有硬约束写 |

**本阶段不做（列入"随时可插的增量"）**：匀速排队（理由见 D2）、集群配额（Token Server 思想）、热点参数限流、系统自适应保护（BBR 思路）、超时预算的全链路传播（跨服务）。
**紧随 S2 之后**：舱壁隔离（按租户分线程池/连接池）。

## 4. 详细设计

### 4.1 租户配置中心（RQ-1）

**表**：

```sql
CREATE TABLE open_app_config (
  id           BIGINT UNSIGNED AUTO_INCREMENT,
  app_id       VARCHAR(32)  NOT NULL COMMENT '归属接入方',
  config_key   VARCHAR(64)  NOT NULL COMMENT '配置键，如 rate_limit.qps',
  config_value VARCHAR(256) NOT NULL COMMENT '配置值（统一按字符串存，读取时按类型解析）',
  update_time  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_app_key (app_id, config_key)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='租户策略配置（S2）';
```

**为什么值统一按字符串存**：配置项会不断增加，每加一项就改表结构不现实；键值对形态让"加一项配置"变成"插一行"。
**代价**：类型错误只能到读取时才暴露——所以读取时**解析失败必须回落默认值并记日志**，绝不让一个写错的配置把请求打挂。

**配置键的命名**（与资源命名、开关命名同一套词汇）：

| 键 | 含义 | 默认 |
|---|---|---|
| `rate_limit.algorithm` | 限流算法：`fixed_window` / `sliding_window` / `token_bucket` / `leaky_bucket` | `sliding_window` |
| `rate_limit.qps` | 每秒上限（0=不限） | 来自 `open_app.qps_limit`（兼容 S1） |
| `rate_limit.daily_quota` | 每日上限（0=不限） | 来自 `open_app.daily_quota` |
| `rate_limit.warmup_seconds` | 冷启动预热时长（0=不预热） | 0 |
| `timeout.default_ms` | 未带 `X-Timeout-Ms` 时的默认预算 | 3000 |
| `circuit_breaker.failure_rate` | 异常比例阈值（%） | 50 |
| `circuit_breaker.slow_call_ms` | 慢调用界线 | 1000 |
| `circuit_breaker.open_seconds` | 熔断保持时长 | 30 |
| `switch.<key>.enabled` | 该租户的开关默认值（覆盖全站默认） | 继承全站 |

**读取服务**：`TenantConfigService`

```java
public interface TenantConfigService {
    /** 读一个租户的某项配置；未配置或解析失败 → 回落全局默认值（并记 WARN） */
    String get(String appId, TenantConfigKey key);

    int getInt(String appId, TenantConfigKey key);
    boolean getBool(String appId, TenantConfigKey key);
}
```

缓存沿用 S1 的三兄弟模式（`refreshAfterWrite` 防击穿 / 负缓存防穿透 / TTL 抖动防雪崩）+ 管理面改动后 `invalidate(appId)`。

**管理面接口**：`PUT /api/apps/{appId}/config`（体是键值对数组）——写操作受管理令牌保护，且**每次变更落审计**（谁在什么时候把哪个租户的哪一项从什么改成了什么）。

**为什么变更要审计**：租户配置直接决定"这个租户能被限多少、超时多久"——改错了就是一次线上事故，必须能追溯。

### 4.2 限流器家族（RQ-3、RQ-4）

**四个实现同一个接口**（S1 已定下这个接口的形状）：

```java
public interface RateLimiter {
    boolean tryAcquire(String key, int limit, Duration window);
}
```

| 实现 | 适用 | 已知特性 |
|---|---|---|
| `FixedWindowRateLimiter`（S1 已有） | 成本最低 | 窗口边界最多放行 2 倍 |
| `SlidingWindowRateLimiter` | 默认 | 用两个相邻窗口的加权计数近似，边界平滑 |
| `TokenBucketRateLimiter` | 允许突发 | 桶容量决定突发上限，令牌按速率补充 |
| `LeakyBucketRateLimiter` | 匀速输出 | 请求先入桶再按固定速率流出 |

**Warm Up（冷启动预热）怎么做**：给令牌桶一个"阈值从小到大爬升"的启动阶段——服务刚起来（或缓存刚清空）时，如果立刻放开全量阈值，冷启动的 JVM 会被打满。预热的具体做法是**在接受请求的同时，把允许的阈值按时间线性抬到目标值**。

**多维限流的组合**（D1 的落地）：

```
请求进来 → 依次检查启用的维度：[appId, ip, resource, (链路)]
           任一维度超限 → 429 + 该维度的错误码 + Retry-After
           全部通过   → 放行，且各维度计数都已 +1
```

**"任一超限即拒"的一个细节**：被拒绝时，前面已经计数的维度**不回滚**——被拒的请求也消耗了它的配额。这是有意的：否则一个被限的调用方可以通过"多打几次"来试探阈值。

**每种维度各自的存储键**：

```
c:rl:app:{appId}:{窗口标识}
c:rl:ip:{ip}:{窗口标识}
c:rl:res:{resource}:{窗口标识}
```

### 4.3 调用熔断（RQ-5、RQ-6）

**选型**：Resilience4j **2.2.0**，依赖 `resilience4j-spring-boot3`（Boot 3 适配）+ `resilience4j-all`（编程式装饰器）。

**为什么用编程式而不是注解式**：熔断要加在**基础设施层的具体调用点**（Redis 闸门的一次 Lua、MySQL 的一次查询），而不是 Controller 方法上。编程式的 `CircuitBreakerRegistry` 能按名字取到熔断器并装饰任意调用：

```java
CircuitBreaker breaker = registry.circuitBreaker("redis:" + appId, configFor(appId));
String result = breaker.executeSupplier(() -> stockGateway.deduct(cmd));
```

**关键能力**：`registry.circuitBreaker(name, customConfig)` **支持按名字给不同配置**——这正是"按租户调熔断阈值"需要的。配置从 §4.1 的租户配置中心读。

**两个层次**：

| 层次 | 名字 | 保护对象 | 触发后 |
|---|---|---|---|
| 依赖级 | `redis` / `mysql` | 所有租户共用的依赖 | 全局快速失败（返回 5001/5000） |
| 租户级 | `redis:{appId}` / `mysql:{appId}` | 单个租户对依赖的使用 | 该租户被单独快速失败 |

**顺序**：先租户级、后依赖级（先看是不是某个租户的问题，再看是不是依赖整体的问题）。

**熔断器实例的容量控制**：`(依赖数 × 租户数)` 个实例。租户多了会膨胀——Resilience4j 的 registry 支持"清理不活跃实例"，本阶段直接按"租户数 ≤ 100"估算（内存开销可忽略），并在文档里登记"租户数上千时要加清理"。

**不熔断的地方（与 D4 呼应）**：**MQ 投递**。发件箱已有退避与死信机制，再套熔断是给同一个问题加两套解决办法。

**半开探测**：熔断打开后等 `open_seconds`，放**少量**试探请求过去；成功则闭合，失败则继续打开。Resilience4j 用 `permittedNumberOfCallsInHalfOpenState` 控制试探数量。

### 4.4 开关与三级预案（RQ-8）

**开关的三层取值**（从具体到宽泛）：

```
租户级配置（open_app_config: switch.receive.enabled）   ← 最具体
    ↓ 没有则取
全站配置（coupon.switch.receive.enabled，S1 已有）
    ↓ 没有则取
默认值 true
```

**三级预案**（D6 的落地）：三份预置清单，本质是"一组开关的目标状态"。

| 级别 | 意图 | 典型内容 |
|---|---|---|
| **蓝（预防）** | 提前收一收，不影响体验 | 打开限流的冷启动预热、降低非核心接口的阈值 |
| **黄（局部降级）** | 关掉非核心，保住核心 | 关闭触达外呼、关闭报表查询、关闭模板发布 |
| **红（保命）** | 只保留发券与用券 | 关闭所有非核心接口 + 收紧全局限流 + 拒新活动发布 |

**执行预案 = 批量套用 + 审计**。**预案不自动升降级**（D6 的理由：自动判据容易误判，本阶段先做人按一下）。

**演练脚本（RQ-9）**：一条命令跑完

```
① 制造故障（如把 Redis 打成持续异常）
② 观察：熔断打开 → 请求快速失败（不再等超时）
③ 一键套用"黄"预案 → 非核心接口关闭、核心链路仍可用
④ 恢复故障 → 半开探测 → 熔断闭合
⑤ 恢复预案 → 全部开关回到默认
⑥ 输出每步的现象与判定
```

### 4.5 deadline 裁剪（RQ-7）

S1 已经在上下文里放了"最晚做到什么时候"（`RequestContext.deadline()`），但只记录不裁剪。本阶段接上：

```java
// 伪代码：把剩余预算传给下游调用
long remaining = RequestContext.current().remainingMs();
if (remaining <= 0) {
    throw new BizException(ErrorCode.DEGRADED, "请求预算已用尽");
}
// Redis / MySQL 调用的超时设为 min(默认超时, remaining)
```

**为什么要有这一步**：没有它，一个"上游已经放弃"的请求还会继续占用资源走完全程；有了它，快超时的请求会提前退出，把资源让给别人。这是**过载保护的一部分**，不只是体验优化。

**边界**：预算只传当前进程内（跨服务的传播留增量），且**不因预算不足而跳过写操作**（读可以跳，写不行——写跳了会造成"用户以为成功其实没做"）。

### 4.6 与 S1 插槽的接线

| S1 留的插槽 | S2 怎么用 |
|---|---|
| 资源命名 `接口[:维度[:值]]` | 作为限流的维度之一（`c:rl:res:{resource}`），也是熔断器的命名依据 |
| 请求上下文 `deadline` | §4.5 的实际裁剪 |
| 开关注解 + 拦截器 | 扩展为支持租户覆盖；预案通过批量改开关实现 |
| 接入方缓存模式 | 租户配置的读取服务复用同一套（防击穿/负缓存/TTL 抖动 + 主动失效） |
| 6xxx 错误码段 | 限流拒绝复用 6006/6007；熔断降级复用 5000/5001 |
