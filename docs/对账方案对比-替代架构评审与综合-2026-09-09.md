## 一、替代方案在说什么（四个核心概念，从零解释）

### 1.1 预留令牌（Reservation Token）——把"在途"变成看得见的东西

**它批评我的什么**：我方的在途计数器（JVM 里的 AtomicLong）只能"数个数"，不能"认人"——对账时知道有 5 个请求在途，但不知道是哪 5 个。

**它怎么做**：领券的 Lua 脚本在扣库存的**同一个原子操作里**写一个钥匙牌 `rsv:{requestId}`（有效期 30 秒）。这个牌子的含义是"这个请求已经扣了 Redis、还没落 DB"。DB 成功后牌子销毁（confirm），失败后分类销毁（cancel）。任何时刻，系统可以**精确**知道哪些请求在途——不是估算，是点名。

```
我方：计数器 = 教室门口挂个"内有 5 人"的牌子（数对但不知道是谁）
对方：令牌   = 每人进门领一块号码牌（随时能念出名单）
```

### 1.2 事件驱动修复——"当事人自己收拾自己"，审计员不动手

**它批评我的什么**：我方对账每小时带着**写权限**跑（能 SET Redis）——审计员自己会做手术，就会跟正常流量打架（N1 售罄自持环、R1 假修复都是这个根源）。

**它怎么做**：所有修复都发生在**请求自己的失败路径上**——DB 拒绝的那一瞬间，请求自己分类（售罄？下线？超时？）自己修复（售罄就把桶钉零、计数回滚）。后台对账**永远只读**：发现不一致就告警、落表，从不 SET。"危险动作从架构上不存在，而不是被条件限制。"

### 1.3 恒等式对账——从"测量"变成"验账"（本方案最核心的思想）

**它批评我的什么**：我方对账是"三个不同时刻读三个地方（DB→Redis→计数器），差值和容忍带比"——中间隔着时间窗，窗口里的流量变化全靠估算（R3 提交泄漏的根源），容忍带=统计推断，压测验证公式=经验工程。

**它怎么做**：在 Redis 里维护**两本账**，让系统任意时刻满足一个恒等式：

```
Redis侧已发放计数（issued） = DB侧已发放镜像（db_issued_mirror） + 在途令牌数（pending）

其中 db_issued_mirror 由 binlog（MySQL 的变更日志，经 Canal→MQ→消费者管道）驱动，
  每落一张券 +1——把"DB 的真相"变成 Redis 里一个 O(1) 可读的数字。
```

**每笔操作都成对记账**：Lua 扣减时 issued+1 且令牌+1（等式两边同增）；DB 落库后镜像+1 且令牌-1（同减）。校验 = 一次读三个数做减法，**期望值精确为 0，不为 0（哪怕差 1）就是 bug**——没有容忍带，没有时间窗，不需要压测验证公式。这就是会计的复式记账法：每笔交易借贷两方同记，月底试算平衡差一分钱都能发现。

### 1.4 分桶（Bucket）——把一个 key 的库存拆成 N 份

把单模板库存拆成 N 个桶（`stock:{tplId}:b0..bN`），扣减时随机轮询，单 key 热点分散到多个 Redis 分片；一个桶丢失只损失 1/N 容量（N2 风暴半径缩小）。

## 二、对抗核查结果：我的反驳哪些成立、哪些被推翻

> 这是最需要诚实的部分。我列出的四个反驳，核查员（专门试图推翻我）的裁定如下。

### 2.1 判断一【恒等式有 binlog 竞态窗口】——**部分被推翻（按文写法我对，范式上我错）**

**我对的部分（有实锤）**：按方案评审.md 原文实现，恒等式**确实不成立**。时间线：

```
t0  Lua 扣减：issued+1, 令牌+1                      → 等式 = 0 ✓
t1  DB 提交成功
t2  应用侧 confirm：DEL 令牌（t1 后毫秒级）            → 此刻 issued+1, 令牌-1, 镜像+0
                                                      → 等式 = +1 ✗
t3  binlog 消费者：镜像+1（t1 后 100ms~1s+）           → 回到 0 ✓
```

**t2 和 t3 是两条独立的异步路径**（应用线程 vs Canal→MQ→消费者），中间的每个请求都贡献 +1，窗口 = binlog 链路迟滞。5000 QPS × 500ms 迟滞 → 流量期**稳态假差异 ≈ +2500**——要么告警刷屏，要么被迫配一条 ≈2500 的容忍带。**"换了位置的容忍带"，这个批评对按文写法成立**。其文档原则 3 还有一个概念偷换："每笔成功发放同时写入 DB(+1) 和删除令牌(-1)"——等式里的 DB 项是**镜像**不是 DB 本身。

**我被推翻的部分（核查员用反例逼我承认）**：这不是范式的根本错误，是**可修复的局部缺陷**。修复方式：把令牌的删除从 confirm **挪到 binlog 消费者**，和镜像 +1 放进**同一个原子 Lua**。逐状态验证（每步都是 Redis 单 slot 原子操作）：

| 状态 | issued | pending | mirror | 等式 |
|---|---|---|---|---|
| 未扣减 | 0 | 0 | 0 | 0 |
| 已扣减、DB 未提交 | +1 | +1 | 0 | 0 |
| DB 已提交、**binlog 未消费（迟滞被 pending 在等式内部吸收！）** | +1 | +1 | 0 | 0 |
| binlog 已消费（镜像+1 与令牌-1 同原子） | +1 | 0 | +1 | 0 |
| 失败 cancel（issued-1 与令牌-1 同原子） | 0 | 0 | 0 | 0 |

**每个状态转移都保持 0**。binlog 迟滞不再需要被"界定"——迟滞只是让 pending 变大（2500 个成员，内存无压力）。这与容忍带有本质区别：容忍带说"差值≤B 良性（B 靠估算+压测验证）"——真漂移 ≤B 时高峰期隐形（我方 R3/M1 一族痛点）；修复后的恒等式说"**差 1 就是 bug**"。**核查员的结论：我攻击掉的是它的文档实现，不是它的范式。该范式修复后恰恰根除我方 A4/R3/M1 的整族问题。承认这一点不丢人。**

### 2.2 判断二【它对我 A1 的描述失准】——成立（对文表述夸大了差异）

核实（代码级）：我方 **A1 钉零生效后**，后续请求在 deduct Lua 的 `stock<=0` 检查处**直接被拒（-3）**——不进 DB 写事务、不触发补偿，**与它的 soldout 标志短路效果等价**。它的对比表写"作者：售罄时 Redis 仍承担流量然后修复"，但其正文自己承认 A1"环断。修复有效"；它的 soldout 标志**同样是第一次 DB 拒绝时才设置**（触发点相同），"DB 售罄 QPS=1"忽略了并发在途。

两处精度修正（核查员给我挑的）：①"不碰 DB"应说"不碰 DB **写路径**"（每请求仍有 2 次索引查询：模板预读 + 陈旧重放检查——M3 缓存后消除前者）；②soldout 标志有一个真实优点是它没说清的：**独立于 stock 值、抗误写**——但代价是**需要显式清除协议**（合法加量/账本修正后必须 DEL soldout，否则模板永久假死），而它的文档通篇没写清除协议，这个风险与它自己批我方的 N3"计划性失忆"同类。**两个设计在损害轴上等价，各有半步优劣。**

### 2.3 判断三【"作者要扩容必须在 M 系列之外新做分桶"是事实错误】——成立

核实：ROADMAP M3 交付③ 明确含"需要则热点分桶（L9）"；docs/10 §10.6 有"QPS>2万→分桶"决策树；§10.2 的 key 规范已预留 `c:stk:{tplId}:b{n}` 分桶形态；§10.10 已预设计分桶的两段式方案。**分桶在我方规划之内、已预设计，对方的事实陈述为假。**它的另一半批评（"单key→分桶是一次架构变更，有成本"）是对的——但那是成本判断，不是规划缺口。

"第一天分桶 vs 压测触发"的诚实评估：**压测触发更适合本项目**——①5000 QPS 目标下单 key 有 2.6~13 倍余量（按对方自己的口径也算 20 倍）；②违反"没有痛点的技术是负资产"的治理原则（对方自己 §六 也把投资边界定在 QPS>3000）；③**关键反击：它的"第一天水平扩展"在自己的 Lua 上不成立**——见判断四。

### 2.4 判断四【CROSSSLOT 结构性矛盾 + pending_set 未实现 + 30s TTL 不够】——成立，且比我说的更严重

三项全部核实属实，且第一项升级为**结构性自相矛盾**：

- **CROSSSLOT**：它的 §2.2 Lua 把 8 个 key（stock/issued/ul/uld/dly/soldout/rsv/idem）放进单脚本。Redis Cluster 要求同脚本所有 key 同 slot：全挂 `{tplId}` tag → **同模板所有桶挤一个分片，"分桶水平扩展"化为泡影**；按桶分 tag → **8 键跨 slot 直接报错**，且 ul（用户维度）随换桶键名分裂会把限领计数打散（同用户第二请求落另一桶时计数归零→限领失效）。这不是漏写 tag，是"§2.1 分桶扩展"与"§2.2 单 Lua 原子"**互斥**——正是我方 docs/10 §10.10 预先裁决过的"原子性 vs 横向扩展的刚性权衡，**任何声称两全的方案都隐藏了正确性漏洞**"。它的方案恰是那个声称两全的方案。
- **pending_set 脱节**：§2.4 恒等式依赖 `SCARD pending_set`，但 §2.2 的 Lua / §2.3 的 confirm/cancel **没有任何一处 SADD/SREM**——按文实现 SCARD 恒 0，流量期恒等式持续假告警，核心卖点自毁。且 Redis 的 Set 成员**没有单独过期时间**，"30s 内的令牌集合"用 SADD/SCARD 做不出来（需 ZSET+时间戳或周期清扫，均未提）。
- **30s TTL 不够**：行锁等待默认 50s（innodb_lock_wait_timeout，我方评审 R11④ 已确认）> 30s——事务超时窗口内防重真空 + 恒等式假告警**同时发生在系统最异常（锁等待）的时刻**。

### 2.5 它对我方的批评里，哪些是**真的**（认账清单）

不护短，这些批评成立且值得吸收：

1. **"JVM 计数器是估算、令牌是精确"**——成立。计数器只能数不能认人；R1/R2/R3 一族问题的共同起点确实是"在途无显式表示"。
2. **"容忍带是统计推断、恒等式是逻辑必然"**——范式上成立（见 2.1 的让步）。我方 A4 是把估算优化得更好，不是消灭估算。
3. **"审计员不该做手术"**——哲学上成立。我方保留窄域自动重建是风险换自愈（见 §四的权衡分析）。
4. **"A3 的 Map<tplId, AtomicLong> 在 M1-M2 之间仍是 JVM 本地，R1 失配窗口仍在"**——成立，我方自己登记过（C1 在 M2、B3 断言只是止损）。

## 三、它没有说/没有算的账（我方的补充分析）

1. **binlog 链路是新的一整套分布式子系统**：Canal + MQ + 消费者，自带故障模式（Canal 断连→镜像停更→恒等式持续假告警或依赖 pending 膨胀；MQ 积压→迟滞放大）。我们刚花了一整轮评审证明**每个 at-least-once 表面都要一整套幂等机器兜底**（补偿幂等、消费者幂等 consumed 守卫——核查员自己也列为其修复的前置条件）。镜像本质上是"另一个需要对账的副本"，递归。
2. **永远只读的代价**：误钉零/误状态（如它的 TEMPLATE_OFFLINE 误判）在"只告警不修复"下**无自愈路径**——凌晨三点的人工介入。我方评审 novel-M2/M3 表明漂移源多样，全人工修复的运维负担真实存在。
3. **写放大**：它自己承认每次扣减 +4 次 Redis 操作（令牌 SETNX/DEL/SADD/SREM + 镜像 INCR）——5000 QPS 下约 +2 万 ops/s，可承受但是真实成本。
4. **"无 @Scheduled"是文字游戏**：分钟级校验和 T+1 审计总要有东西调度——只是从 Spring 调度器挪进了 Flink/Canal 基建。它对我方 R7 的批评（M1 调度线程饥饿）成立，但"无调度器依赖"言过其实。

## 四、综合建议：把它的范式装进我们的骨架（不推倒重来）

**关键洞察（核查一的最大产出）**：我们的代码**离恒等式比想象中近得多**——我们的幂等键（`c:idem:{tplId}:{uid}:{reqId}`，deduct 写入/compensate 删除）**就是它说的"预留令牌"**，而且我们已经修好了它没修的 hash tag 问题。缺的只有三样：Redis 侧 issued 计数器、DB 侧镜像、恒等式检查。**这是小增量，不是重写。**

### 为什么这样综合（一句话）

它的**范式**（显式在途 + 复式记账 + 恒等式）是对的，采纳——但用我们的**骨架**（现有幂等键/网关/Lua 结构、已验证的 hash tag、窄域自愈）落地，不用它的**纸面实现**（CROSSSLOT 矛盾/pending_set 缺失/binlog 依赖/只读哲学），也不接受它对分桶时点的判断。
