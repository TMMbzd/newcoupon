# 第 6 章 券过期与异步任务设计

## 6.1 这个领域解决什么问题，在券系统全局的位置

优惠券是有生命周期的营销资产：领取→生效→可用→（核销 | 过期）。其中"过期"是唯一一个**不需要任何用户动作、纯粹由时间驱动**的状态流转。这决定了它的两个本质特征：

1. **它是强制的，不是可选的**。券过期后如果状态没有流转，后果直接是资损：用户拿着一张实际已过期、但系统里仍是"可用"的券去下单抵扣。中台每天的核销请求里只要有万分之一命中这种"僵尸可用券"，按日均千万级核销量算就是每天上千笔资损订单。
2. **它是批量的、持续涌入的**。按对标体量设定：2 亿用户、5 亿存量券实例，每天约 100 万张券过期，大促后一天可能冲到 500 万（活动券集中到期）。这不是"一个定时任务"的问题，是一个**时间驱动的海量异步任务调度问题**。

"过期"之外，券系统里还有一族同构问题：订单用券超时未支付要解冻券、拼团券团到期未成团要回收、临期提醒（到期前 24h 推送）、营销预算的到期释放、退券回补库存。它们的全集就是本章的"异步任务域"——**凡是"到某个时间点对某条记录做某件事"的需求，都复用同一套注册/触发/执行/兜底骨架**。过期只是这条骨架上负载最大的一个业务。

在券系统全局中的位置：

```
                          优惠券中台
   ┌──────────┐    ┌──────────┐    ┌──────────────┐    ┌──────────┐
   │  创建域   │ →  │  派发域   │ →  │  使用/核销域   │ →  │ 统计结算域 │
   │ 批次/规则 │    │ 库存/领券 │    │  锁券/核销/退  │    │ 对账/报表 │
   └──────────┘    └────┬─────┘    └──────┬───────┘    └────┬─────┘
                         │ 领券落库时         │ 核销前最后校验     │ 预算回冲
                         │ 注册过期任务        │ (懒过期判断)      │ 事件订阅
                         ▼                  │                │
        ┌───────────────────────────────────────────────────────┐
        │              过期与异步任务域（本章）                       │
        │   · 任务注册（领券/补发/后台发放统一入口）                    │
        │   · 实时触发层：Redis ZSet 延时桶 / MQ 定时消息（秒级）      │
        │   · 兜底扫描层：任务表分片轮询（分钟级，source of truth）     │
        │   · 执行器：批量幂等状态流转 1→3 + 发布 ExpiredEvent        │
        │   · 对账：T+1 全量比对，自愈补注册                           │
        └───────────────────────────────────────────────────────┘
```

一句话概括本章的设计哲学：**过期流转的"可信源"永远在数据库（任务表+主表状态机），Redis 与 MQ 只是加速层；而资损的最后防线既不在任务调度、也不在消息投递，而在核销与展示 SQL 里的一个谓词**。后面所有方案演进都围绕这个分层展开。

## 6.2 朴素实现（v1）会怎么挂：三起具体事故

v1 是几乎所有团队的第一反应——调度中心定时扫主表：

```sql
UPDATE coupons SET status = 3
WHERE expire_time < NOW() AND status = 1;
```

以 5 亿行主表、单批命中 100 万行为背景，这个方案会按以下顺序挂掉：

**事故一：数据库 I/O 打满，领券核销全线超时。** `expire_time < NOW()` 是一个随时间推移命中越来越多的无界条件。若没有 `(status, expire_time)` 类联合索引，5 亿行的全表扫描直接把 Buffer Pool 洗一遍，DB CPU 100%，此时领券写请求 RT 从 5ms 涨到秒级，网关层连接池耗尽，全站雪崩。就算补了索引避免了全扫，**单次 UPDATE 100 万行 = 一个百万行级大事务**，redo/undo log 体积以 GB 计，日志刷盘把磁盘 I/O 打满，binlog 同步给从库造成分钟级主从延迟，读库上查到的券状态全是旧的。

**事故二：行锁长持，用户付款被卡死。** InnoDB 对匹配的 100 万行逐行加锁，整个事务持锁可达数分钟到十几分钟。这期间用户恰好要核销其中一张临期券——核销的 UPDATE 和过期任务的 UPDATE 争抢同一行的行锁——用户付款页面转圈直到锁等待超时。**营销系统的后台批处理卡死了 C 端交易**，这是最典型的"非核心链路杀死核心链路"事故。

**事故三：任务中断后的不可判定。** 任务更新到 50 万行时 DB 宕机。重启后无法判断哪些已更新：重跑则重复更新（虽然 status 条件让重跑近似幂等，但要再次承受百万行扫描与锁）；不跑则遗留 50 万张"僵尸可用券"，且**没有任何记录告诉你漏了哪些**。最后只能人工全表比对，修复窗口以小时计，期间持续资损。

三起事故的共同根因：**把一个海量、持续、可拆分的异步任务，当成了一个不可拆分的大同步事务，并且直接压在了业务主表上**。修复思路也因此清晰：拆（小批量）、隔（离开主表）、记（有凭据可判定）。

## 6.3 方案演进：v1 → v2 → v3

### v2：过期任务表——"轻量中间层 + 小批量轮询"

v2 是业界公开的主流解法（素材 a17，5 亿券/日 100 万过期的任务表方案），核心动作三步：

1. **领券时双表同事务**：在同一个本地事务里，向 `coupons` 主表和 `coupon_expire_task` 任务表各插一条。任务表是窄表，只存券标识、`expire_time`、任务状态三要素，用 `uk_coupon_code` 唯一键防重复注册。
2. **分布式定时任务小批量处理**：XXL-JOB 每分钟触发，每批只捞 1000 条（`WHERE expire_time < NOW() AND task_status = 0`，走 `(expire_time, task_status)` 联合索引），**先批量更新主表状态为"已过期"，再更新任务表为"已处理"**。顺序刻意设计成"先业务表后任务状态"：中途失败时任务仍是"待处理"，下一轮自动重捞——一个无 MQ 依赖的"至少一次处理 + 幂等重试"语义，成本极低。
3. **配套治理**：核销时同事务删任务（避免无效扫描）；每天凌晨删除"已处理且超 30 天"的记录防膨胀。

v2 解决了 v1 的全部三个事故：扫描从 5 亿行主表换成百万级窄表且走索引；1000 行的小事务持锁毫秒级；任务状态位让中断后完全可判定。**但 v2 引入了四个新问题**：

- **吞吐上限贴地飞行**：1000 条/分钟 × 1440 分钟 ≈ 144 万/天，刚好勉强覆盖设定的 100 万/天。大促后 500 万/天集中到期时，任务滞后数小时，滞后期间僵尸可用券持续存在。根因是单实例串行分批，没有分片并行。
- **时效只有分钟级**：券真实过期后最长 1 分钟内 status 仍是 1，若下游只信 status，这个窗口就是资损窗口。
- **双表事务耦合领券链路**：领券事务多一次 insert，且任务表必须与主表同库才保得住本地事务——一旦主表分库分表而任务表是中央单表，就退化成跨库分布式事务。
- **状态机有死角**：素材 a17 定义了 task_status=2"处理失败"，但代码里从未差异化处理它——失败的任务既没有退避重试也没有死信告警，会永远卡在"待处理"与"失败"之间的灰色地带。

### v3：三层防线——实时触发 + 兜底扫描 + 懒判断

v3 的演进动机不是"v2 不安全"，而是"v2 的时效与吞吐撑不住大促，且资损防线太薄"。它不推翻任务表，而是把任务表降级为**兜底层与可信源**，在其上加两层：

1. **第一层·实时触发（秒级）**：领券事务提交后，把 `couponId` 以 `expireTime` 为 score 写入 Redis ZSet 延时桶（或直接发 MQ 定时消息）。搬运器每 500ms 取出到期成员批量执行。
2. **第二层·兜底扫描（分钟级）**：v2 的任务表扫描原样保留，但改为**分片并行**（XXL-JOB 分片广播，每实例认领自己的 shard）。任何第一层丢失（Redis 故障、消息丢失）由它补偿。
3. **第三层·懒判断（零延迟，资损最后防线）**：核销与展示不再盲信 status。核销 UPDATE 携带 `expire_time > NOW()` 谓词，券包列表对 `status=1 AND expire_time<=NOW()` 的券直接按"已过期"渲染。**即使前两层全挂，资损也是 0**——只是状态字段"脏"了一段时间。

v3 引入的新问题：链路变长（注册要写 DB 任务表又要写 Redis/MQ，多了一处可能不一致）；MQ 故障恢复后百万延迟消息集中投递的"惊群"；Redis 延时桶的 bigkey 与并发搬运去重。6.4 节的最终形态逐一给出对策。同时必须诚实说明：**如果团队没有 MQ 定时消息能力、日过期量稳定在百万级以内，v2 就是够用的终点；v3 买的是时效、余量与资损防线，代价是运维复杂度**。

## 6.4 大厂最终形态：可直接落地的设计

### 6.4.1 表结构 DDL

主表（简化到本章相关的字段，分库分表按 `user_id` 16 库 × 64 表，具体见存储章）：

```sql
CREATE TABLE coupon_0064 (
  id              BIGINT       NOT NULL AUTO_INCREMENT,
  coupon_id       BIGINT       NOT NULL COMMENT '分布式ID，全局唯一，核销/过期均以它为凭据',
  batch_id        BIGINT       NOT NULL COMMENT '批次ID',
  user_id         BIGINT       NOT NULL COMMENT '分片键',
  status          TINYINT      NOT NULL DEFAULT 1 COMMENT '1可用 2已使用 3已过期 4已冻结(锁券)',
  denomination    DECIMAL(10,2) NOT NULL,
  receive_time    DATETIME     NOT NULL,
  effect_time     DATETIME     NOT NULL,
  expire_time     DATETIME     NOT NULL,
  used_time       DATETIME     NULL,
  expire_notified TINYINT      NOT NULL DEFAULT 0 COMMENT '临期提醒已发送标记',
  version         INT          NOT NULL DEFAULT 0 COMMENT '乐观锁版本',
  PRIMARY KEY (id),
  UNIQUE KEY uk_coupon_id (coupon_id),
  KEY idx_user_status (user_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='券实例主表';
```

过期任务表（与主表**同库、同 user_id 分片规则**落库——这是保住"领券本地事务"的前提）：

```sql
CREATE TABLE coupon_expire_task_0064 (
  id             BIGINT   NOT NULL AUTO_INCREMENT,
  coupon_id      BIGINT   NOT NULL COMMENT '券实例ID（分布式ID，直接路由，不用varchar code）',
  user_id        BIGINT   NOT NULL COMMENT '冗余分片键，与主表同规则路由',
  shard          INT      NOT NULL COMMENT '扫描分片号 = coupon_id % 64，分片广播并行用',
  next_scan_time DATETIME NOT NULL COMMENT '下次应被扫描的时间；失败退避只改此字段',
  status         TINYINT  NOT NULL DEFAULT 0 COMMENT '0待处理(含重试) 1已终结 3死信',
  retry_count    INT      NOT NULL DEFAULT 0,
  create_time    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_coupon_id (coupon_id),
  KEY idx_scan (shard, status, next_scan_time) COMMENT '兜底扫描核心索引'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='过期任务表=持久化待办队列';
```

相对素材 a17 版本的关键改造及理由：

- **coupon_id 用 BIGINT 分布式 ID 替代 VARCHAR coupon_code**：任务表与主表同分片路由时可以直接用整数哈希定位库表；varchar 唯一索引空间大、比较慢，且与第 4 章 ID 体系脱节。
- **新增 shard 列 + `idx_scan(shard, status, next_scan_time)`**：让分片广播的扫描谓词 `WHERE shard=? AND status=0 AND next_scan_time<=NOW()` 精确命中索引前缀。素材 a17 的吞吐瓶颈正是缺这一层。
- **去掉"2-处理失败"状态，失败只推进 `next_scan_time`（指数退避 `min(2^retry_count, 30min)`）**：扫描谓词里 `status` 保持单值等值，索引利用最优；"失败"不再是一个会漏扫的状态，而是"晚一点再扫"。retry_count 超上限（如 8 次）才置 3 死信并告警。这修掉了素材 a17"定义了 status=2 却从未使用"的状态机死角。
- **`next_scan_time` 兼职"延时队列"**：任务表本身就是一个按时间驱动的 DB 版延时队列——这是素材 a17 自己点破的通用性（订单超时关闭、红包过期同构）。

### 6.4.2 Redis key 设计与数据结构选型理由

| Key | 结构 | member/field | score/value | 理由 |
|---|---|---|---|---|
| `ct:exp:z:{yyyyMMdd}:{s}`（s=0..15，桶号=coupon_id%16） | ZSet | couponId | expireTime 毫秒 | 按到期时刻取批是天然 score 查询，`ZRANGEBYSCORE` O(logN+M)；**按到期日分桶**保证桶内成员当天全部到期、次日桶必空可删，杜绝 bigkey；再按 16 桶横向拆，日 100 万量级下单桶约 6 万 member、几 MB，健康 |
| `ct:exp:scanlock:{shard}` | String SET NX PX 60000 | — | 实例ID | 兜底扫描的实例选主锁（XXL-JOB 已保证分片互斥，此锁是防御性双保险） |
| `ct:exp:notify:{couponId}` | String NX PX 86400 | — | 1 | 临期提醒防重（同族任务示例） |

**为什么 ZSet，而不是其他三个候选**：

- **Redis keyspace notification（expired 事件）**：把券也存成带 TTL 的 key，监听过期事件。不可用——Redis 过期采用惰性+定期删除，key 不被访问就可能迟迟不触发事件；事件是"即发即丢"的 pub/sub，消费者重启期间的事件永久丢失；到期密集时事件延迟无界。**它只能当加速器，永远不能当唯一触发器**。
- **List / Stream**：FIFO 语义无法按时间优先取。一张 3 天后到期的券会排在 10000 张 30 天后到期的券前面注册，取队头时它不该被执行却没有跳过手段（除非遍历）。Stream 的 consumer group 很好，但没有 score 概念。
- **MQ 定时消息**：可靠性、容量、可观测都优于自建 ZSet 搬运，日 100 万条完全在 RocketMQ 舒适区。代价是精度与产品耦合：RocketMQ 4.x 只有 18 个固定延迟级别（最长 2h，需配兜底扫描修正到分钟精度），5.x timer 消息才支持任意时刻；Kafka 原生不支持。**有 RocketMQ 5.x 就用 MQ 定时消息做第一层；没有就用 ZSet 自持**——两者在本设计中可互换，因为第三层兜底与懒判断不依赖第一层的具体载体。

**ZSet 的定位必须是"可丢弃的加速层"**：Redis AOF everysec 最坏丢 1 秒、主从切换可能回退数秒，ZSet 成员丢失是常态假设不是故障。可信源永远是 DB 任务表，ZSet 随时可由任务表全量重建（`rebuild` 接口）。这直接采纳了素材 a08 的不变式思想——她的库存设计里"Redis 库存 ≤ DB 库存，DB 是最后防线"，本章对应的是"**Redis 加速层可丢，DB 任务表可补，核销谓词不可穿透**"。

### 6.4.3 核心代码

**（1）领券侧：注册任务 + 事务后投递（与主表插入同一事务）**

```java
@Service
public class CouponIssueTxService {

    /** 领券落库事务：主表 + 任务表 + 事务提交后注册加速层，三处一个方法收敛，
     *  后台补发/营销直发/客服补偿必须复用，禁止旁路直插主表 */
    @Transactional(rollbackFor = Exception.class)
    public void issueInTx(CouponRecord c) {
        couponMapper.insert(c);                          // 主表
        expireTaskMapper.insert(ExpireTask.of(c));       // 任务表(同库同分片,本地事务)
        // 加速层写入推迟到提交后，失败不回滚业务，交给 send_log 重试(最大努力通知)
        TransactionSynchronizationManager.registerSynchronization(
            new TransactionSynchronization() {
                @Override public void afterCommit() {
                    delayProducer.register(c.getCouponId(), c.getExpireTime());
                }
            });
    }
}
```

```java
/** 加速层统一门面：ZSet 桶 或 MQ 定时消息，可配置切换 */
public interface CouponDelayProducer {
    /** 失败必须落 send_log 表（本地事务表），由重试job最大努力通知式补发 */
    void register(long couponId, Date expireTime);
    /** 从任务表全量重建加速层（Redis 灾后/新集群冷启动） */
    void rebuild(LocalDate day, int bucket, int limit);
}
```

**（2）搬运器：Lua 原子认领，杜绝多实例重复搬运**

```lua
-- KEYS[1] = ct:exp:z:{yyyyMMdd}:{bucket}
-- ARGV[1] = 当前毫秒, ARGV[2] = 本批上限(200)
local ids = redis.call('ZRANGEBYSCORE', KEYS[1], 0, ARGV[1], 'LIMIT', 0, tonumber(ARGV[2]))
if #ids > 0 then
  redis.call('ZREM', KEYS[1], unpack(ids))   -- 取出即移除，天然认领
end
return ids
```

```java
@Scheduled(fixedDelay = 500)
public void pump() {
    for (int bucket = 0; bucket < 16; bucket++) {
        String key = "ct:exp:z:" + today() + ":" + bucket;
        List<Long> ids = claimLua.execute(key, System.currentTimeMillis(), 200);
        if (!ids.isEmpty()) expireExecutor.executeBatch(ids, TriggerSource.REDIS_ZSET);
    }
}
```

**（3）执行器：批量幂等流转（三种触发源共用同一入口）**

```java
public ExpireBatchResult executeBatch(List<Long> couponIds, TriggerSource src) {
    // 1. 主表条件更新：只动 status=1 且确已过期的行（幂等CAS,重复消息无害）
    int affected = couponMapper.batchMarkExpired(couponIds);   // SQL见下
    // 2. 已核销/已处理/未到期的券,任务同样终结——任务的存在意义已消失
    if (couponIds.size() > 50) expireTaskMapper.batchFinish(couponIds); // status 0->1
    else for (Long id : couponIds) expireTaskMapper.finish(id);
    // 3. 对真实流转成功的券发布领域事件：预算回冲、过期通知（通知域订阅）
    if (affected > 0) eventBus.publish(new CouponExpiredEvent(couponIds, src));
    return new ExpireBatchResult(couponIds.size(), affected);
}
```

```sql
-- batchMarkExpired：唯一正确的过期流转语句
UPDATE coupon SET status = 3, version = version + 1
WHERE coupon_id IN (...) AND status = 1 AND expire_time <= NOW();

-- finish：任务终结（无条件、幂等）
UPDATE coupon_expire_task SET status = 1
WHERE coupon_id IN (...) AND status = 0;

-- 核销（第三层防线）：过期谓词写进核销,affected=0 即拒绝,资损为0
UPDATE coupon SET status = 2, used_time = NOW(), version = version + 1
WHERE coupon_id = #{couponId} AND status = 1
  AND effect_time <= NOW() AND expire_time > NOW();
```

**（4）兜底扫描：XXL-JOB 分片广播并行**

```java
@XxlJob("couponExpireFallback")
public void fallback() {
    int shardIdx = XxlJobHelper.getShardIndex();      // 0..63,与任务表shard列对齐
    int total    = XxlJobHelper.getShardTotal();
    if (!scanLock.tryLock("ct:exp:scanlock:" + shardIdx)) return;
    for (int round = 0; round < 200; round++) {       // 单次调度最多200轮,防饿死其他分片
        List<ExpireTask> tasks = expireTaskMapper.scanPending(
            shardIdx, Date.now(), 500);               // WHERE shard=? AND status=0
                                                      --   AND next_scan_time<=NOW() LIMIT 500
        if (tasks.isEmpty()) break;
        try { executeBatch(idsOf(tasks), TriggerSource.FALLBACK_SCAN); }
        catch (Exception e) {                          // 失败退避:只推进next_scan_time
            expireTaskMapper.backoff(idsOf(tasks),    -- next_scan_time =
                Backoff.min(2, tasks.get(0).getRetryCount()));  --   now+min(2^retry,30min)
        }
    }
}
```

### 6.4.4 端到端时序（编号列出）

领券→过期注册：

1. 领券请求经派发域 Redis+Lua 校验扣减（库存/限领，见第 3 章）；
2. 生成分布式 couponId，开启本地事务；
3. INSERT 主表 coupon_0064；
4. INSERT 任务表 coupon_expire_task_0064（shard=couponId%64，next_scan_time=expire_time）；
5. 提交事务；afterCommit 钩子注册加速层（ZADD 延时桶或发 MQ 定时消息）；发送失败落 send_log 由重试 job 补发（最大努力通知，采纳素材 a08 的本地事务表模式）。

实时过期（第一层，秒级）：

6. 搬运器/ MQ 到期投递，拿到一批到期 couponId；
7. `executeBatch`：主表条件 UPDATE（status=1 且 expire_time<=NOW）；
8. 任务表批量 status 0→1；
9. 发布 CouponExpiredEvent（预算回冲、用户通知由下游订阅消费）。

兜底过期（第二层，分钟级）：

10. XXL-JOB 分片广播，64 分片各实例并行；scanLock 防御性加锁；
11. 各分片按 `idx_scan` 捞 next_scan_time 到期的任务，每批 500，最多 200 轮；
12. 重复步骤 7-9；异常则退避推进 next_scan_time；retry_count>8 置死信并告警。

对账自愈（T+1）：

13. 每日凌晨按分片跑：`status=1 且 expire_time < NOW()-10min` 的主表记录 LEFT JOIN 任务表与加速层；
14. 有券无任务 → 自动补注册（覆盖后台补发等旁路漏写）；有任务未终结但主表已流转 → 直接终结；差异超阈值（如单分片>100）触发告警人工介入。

### 6.4.5 对外接口签名汇总（照此定义即可编码）

```java
/** 触发源标识：贯穿日志/监控/对账，任何一次执行都能回答"谁叫我来的" */
public enum TriggerSource { REDIS_ZSET, DELAY_MQ, FALLBACK_SCAN, RECONCILE, MANUAL }

/** 批次执行结果：total=本批任务数, transitioned=真实发生1→3流转的行数,
 *  finished=任务表终结数; transitioned远小于total即存在空转(脏任务/重复消息),是监控信号 */
public record ExpireBatchResult(int total, int transitioned, int finished) {}

/** 过期域对外唯一门面。领券/补发只准调register;执行入口只有一个executeBatch */
public interface CouponExpireDomain {

    /** 领券/后台补发落库事务内调用:INSERT任务表(与主表同事务),并挂afterCommit投递加速层 */
    void register(CouponRecord coupon);

    /** 唯一执行入口,幂等,三种触发源共用;内部完成主表流转+任务终结+领域事件发布 */
    ExpireBatchResult executeBatch(List<Long> couponIds, TriggerSource src);

    /** 加速层全量重建:按天+桶从任务表回灌ZSet,Redis灾后/新集群冷启动用 */
    void rebuildAccelerator(LocalDate expireDay, int bucket, int limit);

    /** T+1对账:返回差异明细(有券无任务/有任务未终结),支持自动补注册 */
    ReconcileReport reconcile(LocalDate day, int shard);

    /** 同族任务示例:临期提醒(到期前24h),复用shard扫描骨架,只换谓词与动作 */
    ExpireBatchResult remindBeforeExpire(int shard, int batchSize);
}
```

接口层面有三条纪律需要强调。**第一，`register` 是任务注册的唯一入口**，任何能产生券实例的代码路径（App 领券、后台补发、客服补偿、营销活动直发）都必须经由它，这是防住踩坑清单第 5 条（旁路漏注册）的架构级手段，比靠人记住"要双写"可靠得多。**第二，`executeBatch` 是执行的唯一入口**，触发源只是参数——这保证了无论消息来多少次、无论哪个层先触发，落库语义完全一致，幂等性集中在一处而非散落在各消费者里。**第三，`TriggerSource` 必须落日志与监控**，正常状态下第一层应承担 99% 以上的执行量，若兜底层占比上升，说明实时链路在悄悄劣化，这个比例是本域最重要的健康指标之一。

临期提醒 `remindBeforeExpire` 展示了骨架的复用方式：谓词从 `next_scan_time <= NOW()` 换成 `expire_time BETWEEN NOW() AND NOW()+24h AND expire_notified=0`，动作从"流转状态"换成"发通知+置 expire_notified=1"，其余（分片、批量、退避、对账）原样不动。订单超时解冻券、拼团到期回收、批次预算到期释放，都是同样的换法——这正是 6.1 所说"异步任务基础设施"的含义。

### 6.4.6 吞吐性能账（验证设计余量）

日 100 万过期，平均 12 条/s；大促峰值按 100 倍估 1200 条/s。执行器单批 200、单次一条 IN 更新（毫秒级），单实例 10 批/s 即 2000 条/s——**10 个执行器实例对 1200/s 峰值有 16 倍余量**。兜底层：64 分片 × 500/批 × 每分钟一轮 = 192 万/h，即使第一层全挂也能在小时内追平一天的量。任务表日增 100 万行、30 天归档后稳态 3000 万行窄表，单分片约 47 万行，索引扫描毫无压力。

## 6.5 素材间的方案分歧与推荐

**分歧一：触发机制——纯任务表分钟级轮询（a17） vs 延迟消息实时触发。** a17 明确承认分钟轮询存在时效局限但未给解法。**推荐 v3 三层**：第一层买时效（秒级），第二层保可靠，第三层堵资损。理由：时效不仅是体验问题，窗口内核销依赖下游自觉校验 expire_time 的话，等于把防线外包给了每一个调用方。

**分歧二：加速层载体——Redis ZSet 自持 vs MQ 定时消息。** 两者在本设计中可互换（因为兜底层不依赖载体）。**推荐**：已有 RocketMQ 5.x（任意时刻定时消息）选 MQ——容量、可观测、堆积告警都是现成的；只有 4.x（固定 18 级别）或 Kafka 时选 ZSet 自持，避免精度损失。**不推荐** keyspace notification（见 6.4.2，事件不可靠）。

**分歧三：任务表写入时机——领券双表同事务（a17） vs 异步补齐。** **推荐同库同分片下坚持本地事务双写**（a17 方案）：一次额外 insert 的成本远小于"异步补齐"引入的对账复杂度。只有当任务表无法与主表同库时，才降级用素材 a08 的"本地事务表+最大努力通知"最终一致，并强制开 T+1 对账。这也是任务表带 user_id 分片键的原因——它决定了自己该落在哪个库。

**分歧四：核销后任务表清理——"同步删除或标记"（a17 原文二选一未定） vs 无为而治。** **推荐：核销事务内顺手 DELETE，但不依赖它**。因为执行器的条件 UPDATE（status=1 才动）天然幂等，残留脏任务被捞起后 affected=0、直接终结，无害只是空转。防御性设计优于约定式设计——不把正确性寄托在"每个核销入口都记得删任务"上。

**分歧五：吞吐扩展——素材 a17 未给分片策略。** **推荐 shard 列 + 分片广播**（见 6.4.1/6.4.3），这是把 a17 方案从 144 万/天抬到数千万/天的关键一步，成本仅是一列冗余和一个索引前缀。

## 6.6 踩坑清单（按严重程度排列）

1. **【致命】核销只信 status，不带 expire_time 谓词**——过期流转存在秒~分钟窗口，窗口内僵尸可用券被核销即资损。怎么发现：T+1 对账 SQL 扫 `used_time > expire_time` 的记录，出现即已资损。怎么防：核销 UPDATE 强制携带 `expire_time > NOW()`（6.4.3 第 4 段 SQL），此谓词是全系统资损的最后防线，code review 一票否决项。
2. **【致命】用 Redis expired 事件做唯一过期触发**——惰性删除导致事件延迟无界、pub/sub 事件即发即丢、消费者重启期间事件永久丢失。发现：ZSet/key 已消失但主表 status=1 的券持续堆积。防：expired 事件最多做展示加速，状态流转必须走任务表+扫描兜底。
3. **【严重】主表无界大 UPDATE**（v1 事故二/三重现）——即使从任务表驱动，若一次 IN 数万券批量更新仍是大事务。发现：慢日志、redo 刷盘率、主从延迟告警、C 端锁等待超时。防：批量上限硬编码（200~1000），索引精确匹配扫描谓词，执行器与核销共用行锁时持锁毫秒级。
4. **【严重】MQ 故障恢复后延迟消息惊群**——百万定时消息集中补投，消费者直接打爆 DB。发现：消费堆积告警后 DB 活跃线程数飙高。防：消费端限流（如单实例 10 批/s）+ 批量合并执行 + 兜底层天然削峰（扫描有轮次上限）。
5. **【严重】领券新入口漏注册任务**——后台补发、客服补偿、营销系统直发若旁路直插主表，任务表永远等不到这些券。发现：T+1 对账"有券无任务"差异。防：注册动作收敛为 `issueInTx` 单一领域方法（6.4.3 代码注释），加对账自动补注册。
6. **【中】多实例并发搬运 ZSet 重复执行**——浪费执行资源（幂等下无害但空转）。发现：执行日志中 TriggerSource.REDIS_ZSET 批次 affected 远小于批量大小。防：Lua 里 ZRANGEBYSCORE+ZREM 原子认领（6.4.3 脚本）。
7. **【中】执行时间以应用机器时钟为准**——机器时钟回拨会导致提前过期（资损）或批量延后。发现：单批次 affected 异常抖动、跨机房执行结果不一致。防：所有过期/核销 SQL 用 DB 的 `NOW()` 做判断源，应用侧时间只用于调度节奏。
8. **【中】分库分表后任务表与主表不同库**——本地事务失效退化为跨库双写。发现：领券事务里偶发一边成功一边失败的数据差异。防：任务表带 user_id 按主表同规则路由（6.4.1 DDL 注释），架构评审时校验两套路由一致性。
9. **【中】死信无人处理**——a17 的 task_status=2 定义了从未使用，失败任务悬死。发现：任务表 status 分布监控里非 0/1 状态存量上涨。防：失败走 next_scan_time 退避、超 8 次进死信+告警+人工处理界面。
10. **【低】任务表只写不删膨胀**。发现：表容量水位监控。防：每日凌晨归档"status=1 且 update_time<30 天"记录，删除也按分片小批量。

## 6.7 本章小结

过期与异步任务域的设计压缩成三条不变式：**一，主表状态机的流转条件永远是数据库内的原子谓词（status=1 AND expire_time<=NOW），任何触发源都只是"提醒"而非"授权"；二，DB 任务表是唯一可信源，Redis ZSet 与 MQ 定时消息都是可丢弃、可重建的加速层；三，资损的最后防线在核销 SQL 的 expire_time 谓词上，与调度层的健康状况完全解耦**。在此之上，shard 分片把素材 a17 的任务表方案从日百万级抬到日数千万级，素材 a08 的本地事务表+最大努力通知补齐了加速层投递的可靠性缺口——骨架复用到订单超时关闭、临期提醒、预算释放，就是这一域作为中台"异步任务基础设施"的真正价值。
